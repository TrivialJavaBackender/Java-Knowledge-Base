# Модель памяти Java: контракт, а не «сброс кэша»

> **Какую проблему решает.** Отвечает, почему корректный на вид код не работает: поток не видит
> чужую запись, объект приходит недостроенным, две операции меняются местами. И почему это не баг
> JVM, а разрешённое поведение.
> **Кому это надо.** Тому, кто пишет что-то сложнее «положил в `ConcurrentHashMap`»: свои
> синхронизаторы, ленивую инициализацию, кэши, флаги остановки. И всем, у кого на собеседовании
> спросят про `volatile` или happens-before — а спросят почти наверняка.
> **Когда НЕ надо.** Если весь общий доступ идёт через `java.util.concurrent`, гарантии там уже
> обеспечены — модель памяти нужна, чтобы понимать, *почему* они работают, а не чтобы ими пользоваться.

Здесь только правила видимости и порядка. Живые проблемы, которые из них вырастают
(deadlock, livelock, голодание) — в [`PROBLEMS.md`](PROBLEMS.md). Что физически происходит с потоком
при блокировке — в [`JUC_INTERNALS.md`](JUC_INTERNALS.md).

## 1. Эксперимент первый: флаг остановки, который не останавливает

```java
// Hoist.java — java Hoist.java
public class Hoist {
    static boolean running = true;                 // обычное поле, без volatile

    public static void main(String[] a) throws Exception {
        Thread t = new Thread(() -> {
            long i = 0;
            while (running) i++;
            System.out.println("поток вышел, итераций=" + i);
        });
        t.start();
        Thread.sleep(1000);
        running = false;                           // просим остановиться
        t.join(3000);
        System.out.println(t.isAlive() ? "ЗАВИС: поток не увидел running=false" : "завершился");
        System.exit(0);
    }
}
```

На этой машине (Temurin 21.0.9, Apple M4):

```
### без volatile:
ЗАВИС: поток не увидел running=false

### с volatile:
поток вышел, итераций=3656610981
завершился
```

Обычное объяснение — «запись не дошла до другого ядра, кэш не сбросился». **Оно неверно**, и вторая
строка вывода это доказывает: с `volatile` поток успел сделать **3.6 миллиарда** итераций за секунду,
то есть читал поле каждую итерацию, и увидел изменение мгновенно. Никакой кэш не «сбрасывался»
дольше секунды.

Что произошло на самом деле: JIT увидел, что внутри цикла `running` не меняется, и **поднял чтение
из цикла** (loop hoisting) — примерно так:

```java
boolean local = running;          // прочитали один раз
while (local) i++;                // и больше никогда не читаем
```

Это законная оптимизация: в отсутствие синхронизации компилятор имеет право считать, что поле никто
не меняет параллельно. Проблема возникла **до всякого железа**, на уровне сгенерированного кода.

## 2. Эксперимент второй: обе стороны видят «ничего не произошло»

```java
// Reorder.java — java Reorder.java  (200 000 повторений)
static int x, y, r1, r2;
// Поток 1:  x = 1;  r1 = y;
// Поток 2:  y = 1;  r2 = x;
```

Переберём все возможные порядки выполнения четырёх операций «на бумаге». В каждом из них хотя бы
одна запись успевает произойти до чужого чтения, поэтому `r1 == 0 && r2 == 0` — **невозможно**.

Реальный прогон:

```
итераций=200000, случаев r1==0 && r2==0: 810
```

810 раз результат оказался «невозможным». Причины две, и обе легальны:

- **Процессор.** Запись `x = 1` попадает в буфер записи (store buffer) ядра и становится видимой
  другим ядрам не сразу; чтение `r1 = y` тем временем уже выполнилось. Такое переупорядочивание
  (`StoreLoad`) разрешено и на x86, и на ARM — на ARM модель памяти слабее, и переупорядочиваний
  больше.
- **Компилятор.** Между независимыми записью и чтением разных полей нет зависимости по данным,
  и JIT вправе поменять их местами.

**Вывод из двух экспериментов.** Без синхронизации ваш код исполняется не так, как написан, а так,
как удобно компилятору и процессору. Единственное, что они обязаны сохранить — результат
однопоточного исполнения. Всё, что видит *другой* поток, не гарантировано ничем.

## 3. Чего `volatile` НЕ делает: миф про сброс кэша

Формулировки «выход из `synchronized` сбрасывает записи в основную память», «`volatile` заставляет
читать не из кэша, а из памяти» — распространены, но описывают несуществующий механизм.

Кэши процессоров **когерентны**: протокол вроде MESI гарантирует, что не бывает двух ядер с разными
значениями одной строки кэша. Ядру не нужно ничего «сбрасывать», чтобы другое ядро увидело запись —
как только запись дошла до кэша, она видна всем. С точки зрения программиста кэшей как бы нет.

Настоящих причин расхождения две, и обе показаны выше:

| Причина | Что происходит | Чем лечится |
|---|---|---|
| Оптимизации компилятора | чтение поднято из цикла, значение держится в регистре, операции переставлены | запрет на такие оптимизации для этого поля |
| Буфер записи процессора и слабый порядок | запись ещё не покинула ядро, порядок операций не сохранён | барьер памяти в машинном коде |

`volatile` делает ровно две вещи: запрещает компилятору оптимизировать доступ к полю и заставляет
JIT вставить нужные барьеры. Какие именно барьеры и куда — расписано в «JSR-133 Cookbook for
Compiler Writers» Дуга Ли; там же видно, почему `StoreLoad` (запись `volatile`, затем чтение
`volatile`) — самый дорогой из барьеров.

**Правило формулировки.** Говорите не «сбрасывает кэш», а «устанавливает отношение happens-before».
Первое — про воображаемое железо, второе — про то, что действительно гарантировано.

## 4. Happens-before: контракт между вами и JVM

Модель памяти Java (JLS §17.4) — это договор: **компилятор и процессор могут переупорядочивать что
угодно, пока не нарушено отношение happens-before**.

> Если действие `A` happens-before действия `B`, то все эффекты `A` (включая записи в любые поля)
> обязаны быть видны в `B`.

Что важно понять в этой формулировке:

- Это **не** «видно немедленно» и **не** «видно через N наносекунд». Времени в модели нет вовсе.
- Это **не** отношение между потоками — это отношение между *действиями*.
- Если между двумя действиями нет happens-before, то вопрос «увидит ли поток B запись потока A»
  не имеет ответа: допустим любой результат, и он может отличаться от запуска к запуску (см. §2).

### Правила, порождающие happens-before

| Правило | Ситуация, из которой оно нужно |
|---|---|
| **Порядок программы** | внутри одного потока всё выглядит так, как написано (иначе программировать было бы нельзя) |
| **Монитор**: выход из `synchronized` happens-before последующего входа в тот же монитор | два потока по очереди меняют структуру данных под общим локом |
| **`volatile`**: запись happens-before последующего чтения того же поля | флаг остановки, публикация ссылки, «данные готовы» |
| **`Thread.start()`**: всё, сделанное до `start()`, happens-before первой операции нового потока | сконструировали объект и передали его в поток |
| **`Thread.join()`**: всё, сделанное потоком, happens-before возврата из `join()` | посчитали результат в потоке и читаем его после `join()` |
| **Завершение конструктора `final`-поля** | безопасная публикация неизменяемого объекта (см. §6.3) |
| **Транзитивность**: A → B и B → C даёт A → C | главный рабочий инструмент, см. ниже |
| **Прерывание**: `t.interrupt()` happens-before обнаружения прерывания в `t` | кооперативная отмена |

### Транзитивность — то, ради чего всё работает

Обычно синхронизируют **один** флаг, а видимость получают для **всех** данных:

```java
int[] data;                 // обычное поле, без volatile
volatile boolean ready;     // единственное синхронизированное

// Поток-производитель:
data = compute();           // (1) обычная запись
ready = true;               // (2) запись volatile

// Поток-потребитель:
if (ready) {                // (3) чтение volatile
    use(data);              // (4) обычное чтение — гарантированно видит (1)
}
```

Цепочка: (1) happens-before (2) по порядку программы, (2) happens-before (3) по правилу `volatile`,
(3) happens-before (4) по порядку программы. По транзитивности (1) happens-before (4). Поэтому
`data` видно целиком, хотя само поле никак не помечено.

**То же самое даёт любой лок**: всё, что сделано до `unlock`, видно после `lock` того же лока.
Именно поэтому `ConcurrentHashMap` не требует, чтобы значения были `volatile`.

## 5. `volatile`: точный список гарантий

**Даёт:**

- Видимость: чтение всегда возвращает последнее записанное значение (порядок — по §4).
- Запрет на переупорядочивание относительно этого доступа.
- **Атомарность чтения и записи `long`/`double`.** Без `volatile` 64-битные поля JVM вправе читать
  и писать двумя 32-битными операциями — то есть чтение может вернуть половину старого значения и
  половину нового (JLS §17.7). На 64-битных JVM так обычно не бывает, но гарантии нет.

**Не даёт:**

- Атомарности составных операций. `count++` — это чтение, увеличение и запись; между ними может
  вклиниться кто угодно:

```java
volatile int count;
count++;                     // три операции — гонка сохраняется
// нужно: AtomicInteger.incrementAndGet() или лок
```

- Взаимного исключения: `volatile` не мешает двум потокам одновременно быть в одном участке кода.

**Когда `volatile` достаточно:** один пишет — остальные читают (флаг), либо публикация ссылки на
неизменяемый объект. Как только требуется «прочитать и на основе прочитанного записать» — нужен
`Atomic*` ([`ATOMIC_CAS.md`](ATOMIC_CAS.md)) или лок ([`LOCKS.md`](LOCKS.md)).

## 6. Безопасная публикация

### 6.1 Что ломается

```java
public class Holder {
    private int n;
    public Holder(int n) { this.n = n; }
    public void check() { if (n != n) throw new AssertionError("невозможно?"); }
}

// Поток A:
holder = new Holder(42);      // ссылка публикуется без синхронизации
// Поток B:
holder.check();               // может бросить AssertionError
```

`new Holder(42)` — это три шага: выделить память, записать поле, записать ссылку в `holder`.
Без happens-before другой поток вправе увидеть **ссылку раньше, чем поле** — и получить объект с
`n == 0`. Условие `n != n` при этом действительно может сработать: два чтения одного поля без
синхронизации могут вернуть разное. Это классический пример из JCiP.

### 6.2 Способы опубликовать безопасно

```java
static final Holder H = new Holder(42);        // статическое final — гарантия загрузчика классов
volatile Holder h = new Holder(42);            // volatile
final AtomicReference<Holder> ref = new AtomicReference<>(new Holder(42));
synchronized (lock) { this.h = new Holder(42); }   // под локом (читать тоже под ним)
map.put(key, new Holder(42));                  // через потокобезопасную коллекцию
```

### 6.3 `final`-поля: отдельная гарантия

JLS §17.5 даёт `final`-полям особую гарантию: если объект не «утёк» из конструктора, любой поток,
получивший ссылку, увидит его `final`-поля **полностью инициализированными — даже без синхронизации**.

```java
public final class Point {          // неизменяемый объект
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }
}
// Point можно передавать между потоками без volatile и без локов
```

Оговорка, о которой часто забывают: гарантия теряется, если ссылка на `this` покидает конструктор
(регистрация слушателя, запуск потока, передача в чужой метод) — тогда другой поток может увидеть
объект до «заморозки» полей.

**Почему это важно на практике.** Неизменяемость — самый дешёвый способ обойтись без синхронизации
вообще: у неизменяемого объекта нет состояния гонки, потому что нет изменений. Это первый вопрос,
который стоит задать перед выбором лока.

### 6.4 Двойная проверка блокировки (double-checked locking)

```java
// ❌ Сломано: без volatile другой поток увидит недостроенный объект (§6.1)
private static Singleton instance;
static Singleton get() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}

// ✅ Одно слово чинит всё: volatile запрещает переупорядочивание «ссылка раньше полей»
private static volatile Singleton instance;
```

Практическая заметка: для ленивого синглтона проще и надёжнее идиома holder-класса — она опирается
на гарантии загрузчика классов и не требует ни `volatile`, ни блокировок:

```java
private static class Holder { static final Singleton INSTANCE = new Singleton(); }
static Singleton get() { return Holder.INSTANCE; }
```

## 7. Гонка данных и состояние гонки — это разные вещи

### Гонка данных (data race)

Два потока обращаются к одной переменной, хотя бы один пишет, и между обращениями **нет
happens-before**. По модели памяти результат не определён — допустимо любое значение.

```java
int x = 0;                                     // без синхронизации
new Thread(() -> x = 1).start();
new Thread(() -> System.out.println(x)).start();   // 0 или 1 — гарантий нет
```

Отдельно про «безобидную гонку»: иногда гонка «случайно работает» (например, все пишут одно и то же
значение). Формально это всё равно неопределённое поведение, и полагаться на него нельзя —
оптимизатор вправе воспользоваться отсутствием гарантий.

### Состояние гонки (race condition)

**Логическая** ошибка: результат зависит от порядка выполнения. Существует и при полностью корректной
синхронизации каждого отдельного действия:

```java
if (!map.containsKey(key)) {     // проверка — атомарна
    map.put(key, expensive());   // действие — атомарно
}                                // но вместе — нет: между ними влез другой поток
```

```java
if (ref.get() == null)           // атомарное чтение AtomicReference
    ref.set(new Value());        // атомарная запись — и всё равно гонка
// правильно: ref.compareAndSet(null, new Value())
```

| | Гонка данных | Состояние гонки |
|---|---|---|
| Природа | нарушение модели памяти | ошибка логики |
| Признак | доступ без happens-before | «проверил — сделал» без атомарности целого |
| Бывает без другого | да (гонка данных без логической ошибки) | да (всё синхронизировано, а результат неверен) |
| Чинится | `volatile` / лок / `Atomic*` | атомарной составной операцией (`computeIfAbsent`, `compareAndSet`, лок на всю операцию) |

## 8. Как это проверять

Обычный тест бесполезен: гонка проявляется раз на миллион и зависит от JIT, железа и нагрузки.
Эксперименты из §1–§2 — минимальный вариант: много повторений и подсчёт «невозможных» исходов.

Промышленный инструмент — **jcstress** (OpenJDK). Он генерирует обвязку, прогоняет пары операций
миллионы раз в разных режимах JIT и раскладывает исходы по категориям (ожидаемый, приемлемый,
запрещённый моделью). Тест `Reorder` из §2 в jcstress — десяток строк, а результат статистически
достоверен.

Проверить, что именно наделал JIT, можно и напрямую:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly Hoist    # требует hsdis
java -XX:+PrintCompilation Hoist                                # что и когда скомпилировалось
```

## 9. Шпаргалка

```
Один пишет, все читают (флаг)             → volatile
Прочитать и на основе этого записать      → Atomic* (CAS) или лок
Составная операция над структурой         → лок или атомарный метод коллекции
Объект не меняется после создания         → final-поля, синхронизация не нужна вовсе
Ленивая инициализация                     → holder-класс; если нужен DCL — поле обязано быть volatile
Передать данные в новый поток             → всё, что до start(), уже видно
Забрать результат из потока               → join() даёт видимость
Синхронизировали один флаг                → по транзитивности видно и всё, что записано до него
```

Три формулировки, которые хорошо звучат на собеседовании:

1. «Модель памяти — это контракт: компилятор и процессор вправе переупорядочивать всё, что не
   нарушает happens-before».
2. «`volatile` не сбрасывает кэш — кэши когерентны; он запрещает оптимизации компилятора и ставит
   барьеры».
3. «Синхронизируют один флаг, а видимость получают для всех данных — за счёт транзитивности
   happens-before».

## Вопросы для самопроверки

1. Почему цикл `while (running) {}` не завершается без `volatile`, хотя запись `running = false`
   давно произошла? Причина в кэше?
2. Два потока пишут `x = 1` и `y = 1` и читают чужую переменную. Может ли каждый прочитать 0?
   Почему это не противоречит «порядку программы»?
3. Что именно означает «A happens-before B»? Есть ли в этом определении время?
4. Поле `data` не помечено `volatile`, а `ready` — помечено. Почему после `if (ready)` видно `data`?
5. Что `volatile` гарантирует для `long`, чего не гарантирует для него обычное поле?
6. Почему двойная проверка блокировки без `volatile` — ошибка? Что именно увидит второй поток?
7. Чем гарантия `final`-полей отличается от `volatile`? Когда она теряется?
8. Приведите пример состояния гонки в коде, где каждая отдельная операция атомарна.
