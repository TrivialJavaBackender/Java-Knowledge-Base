# Зачем конкурентность и чем мы за неё платим

> **Какую проблему решает.** Объясняет, откуда вообще берётся многопоточный код: почему сервер
> не может обойтись одним потоком, сколько потоков нужно на самом деле и почему их удвоение
> не удваивает производительность.
> **Кому это надо.** Тому, кто настраивает пул потоков, выбирает между блокирующим и асинхронным
> стилем или собирается сказать на собеседовании «взял `newFixedThreadPool`» — и должен объяснить,
> почему именно столько.
> **Когда НЕ надо.** Если нужен конкретный API (`ReentrantLock`, `ConcurrentHashMap`) — идите сразу
> в профильный файл. Здесь нет ни одного рецепта, только модель, из которой рецепты выводятся.

Все замеры ниже сняты на машине, где написан этот текст: **Apple M4, 10 ядер, Temurin 21.0.9,
macOS 26.5**. Это не JMH — это порядок величин, а не бенчмарк. Каждый замер сопровождается кодом:
запускается одной командой `java Файл.java`, повторите у себя, цифры будут другие, выводы — те же.

## 1. Задача, из которой вырастает весь модуль

Сквозной пример для всего модуля:

> HTTP-сервис принимает **1000 запросов в секунду**. Обработка одного запроса — три вызова
> внешних систем, по 100 мс каждый. Итого запрос живёт **300 мс**, из них процессор занят
> примерно **1 мс**, остальные 299 мс поток ждёт сеть.

Один поток обработает 1000/0.3 ≈ 3.3 запроса в секунду. Нужно 1000. Значит, обрабатывать надо
одновременно. Вопрос — **сколько именно** одновременных обработок должно быть в системе.

---

## 2. Сколько потоков нужно: закон Литтла

Ответ даёт закон Литтла — соотношение из теории очередей, применимое к любой стабильной системе:

```
L = λ × W

L — среднее число заявок, находящихся в системе одновременно
λ — интенсивность поступления (запросов в секунду)
W — среднее время пребывания заявки в системе (секунды)
```

Подставляем: `L = 1000 × 0.3 = 300`. **В любой момент внутри сервиса находится 300 запросов.**
Это не оценка и не запас — это тождество: если поступает 1000 в секунду и каждый живёт 300 мс,
то одновременно их 300, иначе очередь растёт неограниченно.

Если модель «один поток на запрос», то нужно 300 потоков. Не 10, не 50 — ровно столько, сколько
диктует закон Литтла. Это видно на замере: 300 задач по 300 мс через пулы разного размера.

```java
// Little.java — java Little.java
import java.util.concurrent.*;

public class Little {
    public static void main(String[] a) throws Exception {
        int tasks = 300, workMs = 300;
        for (int pool : new int[]{10, 50, 300}) {
            ExecutorService ex = Executors.newFixedThreadPool(pool);
            long t0 = System.nanoTime();
            CountDownLatch done = new CountDownLatch(tasks);
            for (int i = 0; i < tasks; i++)
                ex.submit(() -> { try { Thread.sleep(workMs); } catch (Exception e) {} finally { done.countDown(); } });
            done.await(); ex.shutdown();
            System.out.printf("пул=%3d: %d задач по %d мс за %d мс%n",
                pool, tasks, workMs, (System.nanoTime() - t0) / 1_000_000);
        }
    }
}
```

```
пул= 10: 300 задач по 300 мс за 9117 мс
пул= 50: 300 задач по 300 мс за 1825 мс
пул=300: 300 задач по 300 мс за  333 мс
```

Пул из 10 потоков не «немного медленнее» — он **в 27 раз** медленнее, потому что превращает
параллельное ожидание в последовательное. Работы в задачах нет вообще (`sleep`), процессор
простаивает во всех трёх случаях. Тормозит не нехватка вычислительной мощности, а нехватка
**мест для ожидания**.

**Правило.** Для задач, которые ждут ввода-вывода, размер пула определяется законом Литтла
(`λ × W`), а не числом ядер. Число ядер ограничивает пул только для задач, которые считают.
Как это превращается в формулу для смешанной нагрузки — в [`EXECUTORS_FUTURES.md`](EXECUTORS_FUTURES.md).

## 3. Чем платит поток

300 потоков — это много или нормально? Ответ зависит от того, во что обходится один поток.

### 3.1 Память: стек

Каждый платформенный поток получает собственный стек. Его размер задаётся флагом `-Xss`,
значение по умолчанию зависит от платформы — узнать своё:

```bash
java -XX:+PrintFlagsFinal -version | grep ThreadStackSize
#      intx ThreadStackSize  = 2048   {pd product} {default}
```

На этой машине — **2048 КБ, то есть 2 МБ на поток**. Важная оговорка: это *резерв виртуального
адресного пространства*, а не сразу занятая физическая память — ОС выделяет страницы по мере роста
стека. Но резерв реален: 10 000 потоков — это 20 ГБ адресного пространства, и на 32-битной JVM
программа бы просто не запустилась.

Стек нельзя сделать маленьким «на всякий случай»: его глубина определяется самым глубоким
стектрейсом приложения, а во фреймворках вроде Spring он легко достигает сотни кадров.

### 3.2 Время: создание потока

```java
// Create.java
int N = 10_000;
long t0 = System.nanoTime();
Thread[] pt = new Thread[N];
for (int i = 0; i < N; i++) { pt[i] = new Thread(() -> {}); pt[i].start(); }
for (Thread t : pt) t.join();
System.out.println("платформенные: " + (System.nanoTime() - t0) / 1_000_000 + " ms");

t0 = System.nanoTime();
Thread[] vt = new Thread[N];
for (int i = 0; i < N; i++) vt[i] = Thread.ofVirtual().start(() -> {});
for (Thread t : vt) t.join();
System.out.println("виртуальные:   " + (System.nanoTime() - t0) / 1_000_000 + " ms");
```

```
платформенные: ~220 ms   → ~22 мкс на поток
виртуальные:   ~15 ms    → ~1.5 мкс на поток
```

Разница почти в 15 раз, и она принципиальна: создание платформенного потока — это системный вызов
и работа планировщика ядра. Создание виртуального — это выделение объекта в куче. Именно поэтому
платформенные потоки принято **переиспользовать через пул**, а виртуальные — создавать на каждую
задачу и выбрасывать.

### 3.3 Время: переключение контекста

Когда поток блокируется, ядро снимает его с процессора и ставит другой. Замер — пинг-понг двух
потоков через `wait/notify`, 200 000 переключений:

```
200 000 переключений за ~250 мс  →  ~1.2 мкс на переключение
```

1.2 мкс — это примерно **3000 тактов процессора**. Для сравнения, ненагруженный вызов метода —
единицы наносекунд. То есть одно переключение контекста стоит как несколько тысяч обычных операций.
Пока переключений тысячи в секунду — незаметно; когда сотни тысяч — это становится основной работой
процессора.

### 3.4 Итог: настоящий потолок

Утверждение «JVM держит примерно 10 000 потоков» — не про какой-то жёсткий лимит, а про сумму
трёх ограничений:

| Ограничение | Что упирается |
|---|---|
| Адресное пространство под стеки | 10 000 × 2 МБ = 20 ГБ резерва |
| Стоимость переключений | планировщик ОС начинает занимать заметную долю процессора |
| Планировщик ОС ничего не знает о ваших запросах | справедливость раздаётся между потоками, а не между пользователями |

Для нашей задачи (300 потоков) всё это укладывается. Для 10 000 одновременных соединений — уже нет.
Отсюда исторически и выросли два ответа: **не блокировать поток** (асинхронный стиль,
[`ASYNC_COMPOSITION.md`](ASYNC_COMPOSITION.md)) и **сделать поток дешёвым**
([`VIRTUAL_THREADS.md`](VIRTUAL_THREADS.md)).

## 4. Почему больше потоков ≠ быстрее

Предыдущий раздел мог создать впечатление, что потоков надо просто «побольше». Это верно ровно до
тех пор, пока потоки **ждут**. Как только они начинают трогать общие данные, картина переворачивается.

### 4.1 Замер, который стоит запомнить

Восемь потоков увеличивают один счётчик, каждый по миллиону раз — итого 8 миллионов инкрементов.
Для сравнения — те же 8 миллионов инкрементов в один поток без всякой синхронизации.

```java
// Cost.java (фрагмент): 8 потоков × 1 000 000 инкрементов одного счётчика
class SyncCounter   { long v; synchronized void inc() { v++; } }
class LockCounter   { final ReentrantLock l = new ReentrantLock(); long v;
                      void inc() { l.lock(); try { v++; } finally { l.unlock(); } } }
class AtomicCounter { final AtomicLong v = new AtomicLong(); void inc() { v.incrementAndGet(); } }
class AdderCounter  { final LongAdder  v = new LongAdder();  void inc() { v.increment(); } }
class PlainCounter  { long v; void inc() { v++; } }   // один поток, без синхронизации
```

Три прогона на этой машине:

| Способ | Время (8 потоков × 1 млн) |
|---|---|
| `LongAdder` | **5–6 мс** |
| `synchronized` | 41–74 мс (сильно плавает от прогона к прогону) |
| `ReentrantLock` | 64–66 мс |
| `AtomicLong` | **234–247 мс** |
| один поток, вообще без синхронизации, те же 8 млн | **9 мс** |

Читаем внимательно. **Восемь потоков на восьми ядрах сделали ту же работу в 26 раз медленнее,
чем один поток.** Не «дали ускорение меньше восьмикратного» — дали замедление в двадцать шесть раз.

Причина не в блокировках: у `AtomicLong` блокировок нет вовсе. Причина в том, что все восемь ядер
дерутся за одну и ту же строку кэша: чтобы выполнить `compareAndSet`, ядро должно получить строку в
эксклюзивное владение, а значит — отобрать её у другого ядра. Строка ходит между ядрами, и вся
работа превращается в её перекидывание. `LongAdder` быстрее в 40 раз именно потому, что даёт каждому
потоку свою ячейку и суммирует их в конце (разбор — в [`ATOMIC_CAS.md`](ATOMIC_CAS.md)).

### 4.2 Закон Амдала: потолок ускорения

Пусть доля кода, которая принципиально последовательна (общий счётчик, единственный лок, запись в
общий файл), равна `p`. Тогда ускорение на `N` процессорах не превысит:

```
S(N) = 1 / ( (1 - p) + p/N )        при N → ∞:   S = 1/p
```

Если последовательны 5% работы — потолок ускорения **20×**, сколько ядер ни добавляй. Если 20% —
потолок 5×. Это верхняя граница в идеальном мире: без стоимости синхронизации, без переключений,
без когерентности кэшей.

### 4.3 Universal Scalability Law: почему бывает хуже, чем потолок

Закон Амдала говорит «ускорение выйдет на плато». Реальность из §4.1 хуже: производительность
**падает** с ростом числа потоков. Модель Гантера (Universal Scalability Law) добавляет к
последовательной доле второе слагаемое — стоимость **согласования** между участниками (та самая
перекидываемая строка кэша), которая растёт как `N²`:

```
C(N) = N / ( 1 + σ(N-1) + κN(N-1) )
         σ — доля, требующая сериализации (Амдал)
         κ — стоимость когерентности (её у Амдала нет)
```

Из-за `κ` кривая не выходит на плато, а имеет **максимум**: после некоторого числа потоков добавление
следующего делает систему медленнее. Замер `AtomicLong` — ровно этот эффект.

**Правило.** Конкурентность окупается там, где потоки **ждут** (сеть, диск, БД), и очень плохо
масштабируется там, где они **пишут в одно и то же место**. Прежде чем добавлять потоки, посмотрите,
что находится в общей точке — и нельзя ли её убрать (неизменяемость, разбиение по ключу, локальные
счётчики).

## 5. Одна задача — четыре стиля

Вернёмся к сквозному примеру: три вызова по 100 мс, из них второй и третий независимы.

**Стиль 1 — блокирующий, поток на запрос.**

```java
Profile profile = api.fetchProfile(id);   // 100 мс, поток стоит
Orders  orders  = api.fetchOrders(id);    // 100 мс, поток стоит
Prefs   prefs   = api.fetchPrefs(id);     // 100 мс, поток стоит
return render(profile, orders, prefs);    // 300 мс, 1 поток занят целиком
```

Код читается сверху вниз, отладчик работает, стектрейс полный. Цена — поток занят все 300 мс,
и по закону Литтла таких потоков нужно 300.

**Стиль 2 — колбеки.** Поток не занят, но код выворачивается наизнанку: вложенность, ошибки надо
ловить в каждом уровне вручную, `try/catch` вокруг вызова не работает (исключение прилетит в чужом
потоке). Подробный разбор — в [`ASYNC_COMPOSITION.md`](ASYNC_COMPOSITION.md).

**Стиль 3 — `CompletableFuture`.** Пирамида выпрямляется в цепочку, независимые вызовы честно идут
параллельно:

```java
CompletableFuture<Profile> p = supplyAsync(() -> api.fetchProfile(id), pool);
CompletableFuture<Orders>  o = supplyAsync(() -> api.fetchOrders(id),  pool);
CompletableFuture<Prefs>   f = supplyAsync(() -> api.fetchPrefs(id),   pool);
return p.thenCombine(o, Pair::of).thenCombine(f, this::render);   // ~100 мс
```

Обратите внимание: это первый вариант, где **задержка одного запроса уменьшилась** — с 300 мс до
~100 мс, потому что три вызова пошли одновременно. Цена — код перестал быть обычным кодом.

**Стиль 4 — виртуальные потоки (JDK 21).** Код стиля 1, цена стиля 2:

```java
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Profile> p = ex.submit(() -> api.fetchProfile(id));
    Future<Orders>  o = ex.submit(() -> api.fetchOrders(id));
    Future<Prefs>   f = ex.submit(() -> api.fetchPrefs(id));
    return render(p.get(), o.get(), f.get());
}
```

Тот же замер из §2 на виртуальных потоках: **316 мс** против 333 мс у пула на 300 потоков —
но без 300 стеков по 2 МБ и без 300 системных потоков.

| | Поток занят при ожидании | Код читается линейно | Сколько потоков ОС на 1000 rps | Отладка |
|---|---|---|---|---|
| Блокирующий + пул | да | да | ~300 | простая |
| Колбеки | нет | нет | единицы | тяжёлая |
| `CompletableFuture` | нет | частично | единицы | средняя |
| Виртуальные потоки | нет (снимается с носителя) | да | единицы | простая |

Пятый стиль — корутины Kotlin — это, по сути, третий, но с генерацией колбеков компилятором;
почему так и чем он отличается — в [`kotlin-coroutines/WHY_COROUTINES.md`](../../kotlin-coroutines/theory/WHY_COROUTINES.md).

## 6. Задержка и пропускная способность — это разные цели

Частая путаница на собеседовании: «мы добавили потоков, стало быстрее». Быстрее — что именно?

- **Пропускная способность** (сколько запросов в секунду) растёт от конкурентности почти всегда,
  пока есть свободные ресурсы: больше мест для ожидания — больше запросов в полёте.
- **Задержка одного запроса** от конкурентности **не улучшается**. 300 мс останутся 300 мс, сколько
  потоков ни добавь. Уменьшить её можно только одним способом: распараллелить работу **внутри**
  запроса (стиль 3 и 4 в §5 — три вызова одновременно вместо трёх подряд).
- Хуже того, при перегрузке они конфликтуют: пул с неограниченной очередью держит пропускную
  способность, но задержка растёт неограниченно, потому что запрос ждёт в очереди. Отсюда требование
  **ограниченной очереди** и обратного давления (backpressure) — см. [`EXECUTORS_FUTURES.md`](EXECUTORS_FUTURES.md).

**Правило.** Формулируйте цель до выбора инструмента: «держать 1000 rps» и «отвечать за 150 мс» —
это два разных технических решения.

## 7. Когда конкурентность НЕ нужна

Многопоточность — это не бесплатное улучшение, а размен: вы платите сложностью, недетерминизмом и
целым классом ошибок (гонки, дедлоки, утечки), которых в однопоточном коде не существует.

Не нужна, когда:

- **Запрос — это один блокирующий вызов.** Обычный CRUD «принял → сходил в БД → отдал» уже
  конкурентен на уровне сервера приложений: контейнер сам держит пул потоков. Добавлять внутри
  собственный пул незачем.
- **Узкое место — не процессор.** Если упираемся в БД (пул соединений, блокировки строк, диск),
  то потоки приложения будут стоять в очереди за соединением. Оптимизировать надо БД.
- **Работа короче накладных расходов.** Обработка занимает 50 мкс, а передача задачи в пул плюс
  переключение — 5–10 мкс с обеих сторон. Параллелить имеет смысл от миллисекунд и выше.
- **Данные общие и часто изменяются.** См. §4: восемь потоков могут оказаться в 26 раз медленнее
  одного. Иногда правильный ответ — «сделать однопоточно и быстро» (так работают Redis и LMAX Disruptor).
- **Нужен строгий порядок.** Гарантировать порядок обработки на N потоках — отдельная задача,
  которая часто съедает весь выигрыш.

## Источники

**Теория очередей и масштабируемость:**
- [John D. C. Little (1961) — «A Proof for the Queuing Formula L = λW» (Operations Research 9(3))](https://www.jstor.org/stable/167570) — оригинал закона Литтла.
- [Gene Amdahl (1967) — «Validity of the Single Processor Approach to Achieving Large-Scale Computing Capabilities»](https://dl.acm.org/doi/10.1145/1465482.1465560) — закон Амдала.
- [Neil Gunther — «Guerrilla Capacity Planning» / Universal Scalability Law](http://www.perfdynamics.com/Manifesto/USLscalability.html) — модель с когерентностью, объясняющая падение производительности.

**Книги:**
- *Java Concurrency in Practice* (Goetz et al., 2006) — Ch. 1 (Introduction), Ch. 11 (Performance and Scalability) — про стоимость переключения контекста и конкуренции за лок.
- *Systems Performance*, 2nd ed. (Brendan Gregg, 2020) — Ch. 6 (CPUs) — стоимость переключений на уровне ОС.

**Официальная документация:**
- [JEP 444: Virtual Threads (JDK 21)](https://openjdk.org/jeps/444) — раздел Motivation формулирует ровно эту проблему: «поток на запрос» упирается в стоимость потока ОС.
- [`java` — опции `-Xss`, `-XX:+PrintFlagsFinal` (JDK 21 tools reference)](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html)
