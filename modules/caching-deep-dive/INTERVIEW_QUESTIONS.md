# Interview Questions — caching-deep-dive

## 19. Почему кэш-иерархия работает — что общего у L1 CPU-кэша, Caffeine в JVM и CDN?

На каждом следующем уровне — от регистра CPU до origin-сервера — задержка растёт на 1–3 порядка, а объём — на порядок и больше: L1 CPU-кэш отвечает за ~1 нс и держит десятки килобайт, Redis — за ~1 мс и держит гигабайты, CDN edge — за десятки миллисекунд и держит терабайты. Иерархия работает не потому, что каждый уровень «лучше» предыдущего, а потому что дешёвый быстрый уровень маленький, а дорогой медленный — большой, и правило архитектора здесь простое: если 99% запросов решаются на верхнем уровне, общая latency определяется именно им, а нижний уровень нужен только для «холодных» оставшихся процентов. Отсюда практическое следствие для дизайна кэша: важнее не абсолютная скорость конкретного уровня, а то, какая доля трафика на нём оседает — near-cache (L1 в приложении поверх Redis L2) существует именно потому, что даже миллисекундная задержка Redis слишком дорога в hot path, если её можно вообще избежать локальным попаданием.
> theory/BASICS.md §2

## 1. В чём разница между cache-aside и read-through?

**Cache-aside (lazy loading):** приложение само управляет кэшем. На чтении: сначала смотрит в кэш; если miss — читает из БД, кладёт в кэш, отдаёт клиенту. Кэш не знает о БД.

**Read-through:** приложение работает только с кэшем. Кэш сам подгружает данные из БД через зарегистрированный `CacheLoader`. Источник скрыт за кэшем.

Cache-aside проще и универсальнее, но логика загрузки дублируется в каждом месте. Read-through централизует логику, но требует поддержки в библиотеке (Caffeine `LoadingCache`, Redis модулей нет — нужно писать самому).
> theory/CACHE_PATTERNS.md §1

## 2. Чем write-through отличается от write-behind, и какие у каждого риски?

**Write-through:** запись синхронно идёт и в кэш, и в БД, прежде чем вернуть ответ. Консистентность сильная, но латентность записи = max(cache, DB).

**Write-behind (write-back):** запись идёт в кэш сразу, а в БД асинхронно (батчем/очередью). Латентность записи минимальна, но при крэше до flush'а данные теряются. Также возможна несогласованность при чтении из реплик БД.

Write-behind хорош для высокого write throughput с допуском к eventual durability (логирование, метрики). Write-through — для финансовых данных и т.п.
> theory/CACHE_PATTERNS.md §4

## 3. LRU vs LFU vs W-TinyLFU — когда что выбирать?

- **LRU (Least Recently Used):** выбрасывает то, что давно не запрашивали. Прост, но плохо переживает scan-резистентность (один большой обход выбивает горячие данные).
- **LFU (Least Frequently Used):** считает частоту, выбрасывает наименее частое. Чувствителен к старению (frequency у древнего ключа остаётся высокой).
- **W-TinyLFU (Caffeine):** комбинация admission filter (TinyLFU sketch с count-min) + main LRU. Решает оба недостатка: scan-resistance + затухание частот через aging. На реальных нагрузках hit-ratio выше, чем у чистого LRU.

В 90% случаев в JVM — Caffeine (W-TinyLFU). В Redis — `allkeys-lru` или `allkeys-lfu` в зависимости от паттерна.
> theory/EVICTION_POLICIES.md §2

## 20. Чем `expireAfterWrite` отличается от `expireAfterAccess`, и когда это меняет поведение кэша?

`expireAfterWrite` (TTL) отсчитывает время от момента записи — если положить значение в 10 утра и читать его каждую минуту, оно всё равно исчезнет ровно через настроенный интервал после записи, независимо от того, как часто к нему обращались. `expireAfterAccess` (TTI, time-to-idle) отсчитывает время от последнего обращения — каждое чтение или запись продлевает жизнь записи, и она живёт, пока её кто-то трогает хотя бы раз в интервал. Разница становится значимой на горячих данных с длинным хвостом обращений: TTL гарантирует, что значение не протухнет старше N (важно, когда данные меняются в источнике и нужен предел staleness), а TTI держит «живыми» только то, что реально используют, и выкидывает забытое даже если оно моложе TTL. Их можно комбинировать: `expireAfterWrite=1h` вместе с `expireAfterAccess=10m` — «максимум час, но если 10 минут не трогают — выкидываем раньше» — то есть TTL задаёт верхнюю границу свежести, а TTI управляет памятью, выкидывая неиспользуемое быстрее, чем истечёт формальный срок.
> theory/EVICTION_POLICIES.md §3

## 4. Что такое cache stampede и как его предотвратить?

**Cache stampede / thundering herd:** в момент expiry горячего ключа сотни клиентов одновременно проваливаются в БД и одновременно её перегружают.

Защиты:
1. **Single-flight / request coalescing:** только один поток запускает rebuild, остальные ждут результат (например, `ConcurrentHashMap.computeIfAbsent` с `CompletableFuture`).
2. **Mutex/lock per key:** аналогично, но через распределённый lock в Redis (SETNX + TTL).
3. **Early refresh / refresh-ahead:** обновлять до expiry в фоне (Caffeine `refreshAfterWrite`).
4. **Stale-while-revalidate:** возвращать stale-значение пока идёт rebuild.
5. **TTL jitter:** делать TTL = base ± random, чтобы expiry не происходил одновременно у тысяч ключей (защита от cache avalanche).
> theory/ANTI_PATTERNS.md §1

## 5. Cache penetration vs breakdown vs avalanche?

- **Penetration:** запросы идут на несуществующие ключи → каждый раз miss → нагрузка на БД. Решение: negative caching (TTL=минуты для null-результата) или bloom filter перед кэшем.
- **Breakdown:** один очень горячий ключ истекает, и тысячи клиентов одновременно идут в БД за ним. Решение: mutex/single-flight (см. п.4) + refresh-ahead.
- **Avalanche:** массовый одновременный expiry (например, все TTL = 60s, заданные при старте) → пик промахов. Решение: jitter TTL.
> theory/ANTI_PATTERNS.md §2

## 6. Double-write problem: какие 4 порядка операций возможны и какие проблемы у каждого?

Записать в БД и в кэш можно в 4 порядка (D=DB, C=cache):

1. **D → C:** если C падает — стейл в кэше (и долго). На concurrent update'е другой поток может записать старое C поверх нового.
2. **C → D:** если D падает — кэш ушёл вперёд БД (lost update в реплике, неправильная инвалидация при rollback).
3. **D → invalidate C:** проще всего; миссы в кэш дают свежее значение из БД. Но между шагами читатель может закэшировать стейл.
4. **invalidate C → D:** на чтении между шагами читатель прогрузит из БД старое значение и закэширует его → стейл застревает в кэше.

Безопасный путь: **write-through или D → invalidate C + защита от race** (например, через CDC, версии, или delayed double-delete).
> theory/CONSISTENCY.md §1

## 30. Пользователь обновил профиль и сразу же его читает — почему кэш иногда отдаёт старое значение, и как это исправить?

Наивная последовательность «записать в БД → инвалидировать кэш → следующий запрос перечитает из БД» ломается, если чтение после инвалидации попадает не в master, а в реплику БД, которая ещё не получила репликацию только что сделанной записи — тогда промах кэша заново закэширует именно устаревшее значение, и оно проживёт до следующего TTL. Проблема не в кэше, а в том, что путь чтения после записи «доверяет» кругу из нескольких асинхронных систем (инвалидация, репликация, повторное чтение) вместо того, чтобы использовать то, что уже известно в момент записи. Решение — не полагаться на круговой путь, а сразу после успешной записи в master положить в кэш то же самое значение, которое только что записали (`cache.put`, а не `invalidate`), и отдельно разослать инвалидацию другим инстансам, у которых есть свой near-cache L1. Это гарантирует read-after-write consistency для того потока, который сделал запись, независимо от состояния репликации БД, оставляя проблему репликационного лага только тем читателям, которые не участвовали в записи.
> theory/CONSISTENCY.md §3

## 7. Redis: RDB vs AOF — что выбрать?

- **RDB:** бинарный snapshot всей БД (по расписанию или вручную). Компактен, быстро восстанавливается, но между snapshot'ами потеря данных.
- **AOF (Append-Only File):** лог всех write-команд. `appendfsync everysec` (default) — потеря не более 1с. `always` — durable, но медленно. `no` — на усмотрение OS.

Для durable workload — AOF с `everysec`. Для cache-only (где БД источник истины) — RDB или вообще без persistence. Часто используют оба (AOF для durability + RDB для быстрого restart).
> theory/REDIS.md §2

## 21. Как Redis Cluster шардирует данные, и почему `MGET` по нескольким ключам иногда падает с ошибкой?

Redis Cluster делит всё пространство ключей на 16384 фиксированных hash slot, распределённых между master-узлами; принадлежность ключа вычисляется как `CRC16(key) % 16384`. Клиент, обратившийся не к тому узлу, получает `MOVED` (постоянный редирект, слот-таблица клиента обновляется) или `ASK` (временный редирект во время resharding, когда слот мигрирует между узлами). Проблема с multi-key операциями (`MGET`, `MSET`, транзакциями) в том, что они физически выполняются одним узлом и требуют, чтобы все затронутые ключи лежали в одном slot — иначе Redis отвечает ошибкой `CROSSSLOT`. Решение — hash tags: `{user:42}:profile` и `{user:42}:settings` хешируются не целиком, а только по части в фигурных скобках, поэтому оба ключа гарантированно попадают в один slot, и по ним можно делать multi-key операции и транзакции, а resharding при этом продолжает работать на уровне отдельных ключей вне тега.
> theory/REDIS.md §6

## 22. Зачем в Redis нужны `MULTI/EXEC` и Lua-скрипты, если это key-value хранилище?

Redis однопоточный, и это единственная причина, почему `MULTI/EXEC` и `EVAL` вообще дают атомарность: команды между `MULTI` и `EXEC` копятся в буфер и применяются одним куском, без переключения на другого клиента между ними — но это не транзакция в SQL-смысле, потому что при ошибке выполнения одной команды остальные всё равно выполнятся, откатывать нечего. Более гибкий инструмент — Lua-скрипты через `EVAL`/`EVALSHA`: весь скрипт выполняется атомарно, потому что интерпретатор Lua работает в том же однопоточном цикле, что и сами команды. Это делает Lua идеальным инструментом для compare-and-set: прочитать текущую версию ключа, сравнить с ожидаемой и записать новое значение — без риска, что между чтением и записью вклинится другой клиент, ровно та же задача, что решает `WATCH` при optimistic locking, но без необходимости повторять транзакцию при конфликте. Цена — Lua-скрипт с долгим циклом блокирует весь Redis на время выполнения, поэтому длинные вычисления внутри `EVAL` — прямой путь к деградации всего инстанса, а не только одного клиента.
> theory/REDIS.md §9

## 8. Что делает `refreshAfterWrite` в Caffeine и чем он отличается от `expireAfterWrite`?

- **`expireAfterWrite(t)`:** через `t` после записи ключ помечается expired; следующий `get` блокируется до загрузки нового значения (или возвращает старое и асинхронно перезагружает в `AsyncLoadingCache`).
- **`refreshAfterWrite(t)`:** через `t` следующий `get` возвращает **старое** значение, но триггерит асинхронный refresh. Ключ не expires — просто обновляется в фоне.

Combo: `refreshAfterWrite=1m` + `expireAfterWrite=5m` → горячие ключи всегда свежие (refresh каждую минуту), холодные удаляются через 5m.
> theory/CAFFEINE.md §5

## 23. Чем `LoadingCache` защищает от cache stampede, если это просто обёртка над `get`?

Обычный `ConcurrentHashMap.computeIfAbsent` не даёт такой гарантии сам по себе на всех реализациях — а вот `LoadingCache` в Caffeine гарантирует, что для одного и того же ключа `CacheLoader` вызовется в один момент времени ровно один раз: если сто потоков одновременно делают `cache.get("u:42")` при промахе, только один реально пойдёт в `loadFromDb`, а девяносто девять остальных заблокируются на этом же вызове и получат тот же результат, когда он придёт — это и есть single-flight, встроенный в библиотеку, а не то, что нужно реализовывать вручную поверх map. Именно поэтому `LoadingCache` — стандартный ответ на вопрос «как защититься от stampede в JVM-локальном кэше»: она превращает потенциальный N-кратный удар по источнику данных в один запрос, без явного mutex или `CompletableFuture`-обвязки в коде приложения.
> theory/CAFFEINE.md §3

## 24. Зачем нужен `AsyncLoadingCache`, если `LoadingCache` уже даёт single-flight?

`LoadingCache.get` при промахе блокирует вызывающий поток до завершения загрузки — это нормально для классических потоков, но становится проблемой в реактивном или корутинном стеке, где блокировка потока — это заблокированный воркер event loop или диспетчера корутин, а не просто «подождать». `AsyncLoadingCache` возвращает `CompletableFuture<V>` немедленно: промах не блокирует вызывающего, а результат приходит по завершении асинхронной загрузки, которую можно выполнить на любом executor'е. Гарантия single-flight сохраняется — конкурентные `get` по одному ключу схлопываются в один `CompletableFuture`, на который подписываются все вызовы — просто без блокировки потока в ожидании. Для Kotlin-корутин это интегрируется напрямую через `future.await()` из `kotlinx-coroutines-jdk8`, что делает `AsyncLoadingCache` естественным выбором для suspend-функций, обращающихся к кэшу.
> theory/CAFFEINE.md §4

## 25. Почему выбор пал на Caffeine, а не на Guava Cache или голый `ConcurrentHashMap`?

Три варианта решают разные объёмы задачи. `ConcurrentHashMap` не умеет ни eviction, ни TTL сам по себе — это просто потокобезопасная map, всё остальное пришлось бы писать руками, включая защиту от stampede. Guava Cache умеет TTL и eviction, но её алгоритм вытеснения — классический LRU без защиты от scan: один проход по редко используемым ключам вымоет из кэша всё горячее. Caffeine использует W-TinyLFU, который на реальных нагрузках даёт на 5–25% выше hit-ratio, чем чистый LRU, за счёт admission filter на основе частоты, и при этом остаётся в разы быстрее Guava на чтении благодаря амортизированной, почти безлоковой реализации через batched ring buffer — а не потому что Guava плохо написана, а потому что её структуры проектировались раньше и под другие компромиссы. Guava при этом не заброшена в проектах (легаси Hadoop, старый Spring), но новый код в 2020-х пишут на Caffeine, потому что она активно развивается, а Guava Cache — фактически заморожена.
> theory/CAFFEINE.md §10

## 26. Какие есть топологии распределённого кэша и в чём их принципиальный компромисс?

Централизованная топология (Redis, Memcached) — один кластер хранит данные, все клиенты ходят по сети за каждым чтением: единый источник истины, но каждое обращение платит сетевой latency порядка 0.5–2 мс. Реплицированная (Hazelcast, Ignite) — каждый узел хранит полную копию, чтение локально и почти мгновенно, но запись должна разойтись по всем узлам, а объём данных ограничен памятью одного узла — это годится для небольших часто читаемых датасетов вроде справочников, а не для основного кэша данных. Near-cache — гибрид: маленький локальный L1 поверх общего L2, чтение идёт L1 → L2 → DB, и большинство горячих запросов оседает на L1 с наносекундной задержкой, а L2 даёт большой общий объём — но за это приходится платить главной сложностью топологии: кросс-нодовой инвалидацией L1 при изменении данных, потому что у каждого инстанса своя локальная копия. Общий компромисс во всех трёх случаях один: чем ближе данные к вызывающему коду, тем быстрее чтение и тем сложнее держать копии согласованными между узлами.
> theory/DISTRIBUTED_CACHING.md §1

## 9. Что такое near-cache и зачем он нужен?

**Near-cache:** локальный JVM-кэш (L1) поверх удалённого распределённого кэша (L2 = Redis/Hazelcast). Чтение: L1 → L2 → DB. Запись: invalidate L1 + write L2.

Зачем: latency удалённого кэша (~1ms) всё равно дорогая в hot-path; локальный hit ~nanoseconds.

Цена: каждый узел может иметь свою копию → нужна кросс-нодовая инвалидация (pub/sub в Redis, gossip в Hazelcast). Иначе двое читают разное.
> theory/DISTRIBUTED_CACHING.md §4

## 10. Consistent hashing — зачем и как работает?

**Проблема:** при шардинге `hash(key) % N` добавление/удаление узла переместит почти все ключи (N+1 узлов → 100% reshuffle).

**Consistent hashing:** ключи и узлы мапятся на круг хешей \[0, 2^32). Ключ принадлежит первому узлу по часовой стрелке. Добавление узла перемещает только ключи в его сегменте (1/N).

**Virtual nodes:** каждый физический узел представлен M точками на круге → лучшая балансировка и плавная миграция.

Используется в: Cassandra, DynamoDB partitioning, Memcached client-side sharding, CDN edge selection. Redis Cluster использует фиксированные **16384 slots** — родственная, но другая идея.
> theory/DISTRIBUTED_CACHING.md §3

## 27. Распределённый кэш подвержен CAP-теореме — что это значит на практике для Redis Cluster?

Redis Cluster при разрыве сети между частями кластера выбирает доступность, а не согласованность: партиция с кворумом продолжает принимать запросы, а партиция без кворума теряет право на запись (`min-replicas-to-write`), но при этом обе стороны какое-то время могут расходиться в состоянии. После восстановления сети данные, записанные в меньшинстве после разрыва, теряются — это AP-выбор, а не CP. Для распределённой базы данных это было бы неприемлемо, но для кэша это обычно нормально по конструкции: источник истины — не кэш, а БД, и потерянная запись в кэше означает лишь один лишний промах после восстановления, а не потерю данных. Отсюда практический вывод: спрашивать «какая консистентность у моего распределённого кэша» имеет смысл только применительно к staleness между кэшем и БД (см. double-write problem), а не в терминах CAP — CAP-компромисс здесь заранее решён в пользу доступности, и это осознанное архитектурное решение, а не недостаток.
> theory/DISTRIBUTED_CACHING.md §6

## 28. Redis почти всегда побеждает Memcached в новых проектах — значит ли это, что Memcached хуже?

Нет, они оптимизированы для разных вещей. Memcached хранит только строки, не персистит данные, не реплицирует их из коробки — но именно поэтому он проще устроен и на чистом get/set с высоким параллелизмом (многопоточная модель, slab allocator с низкой фрагментацией памяти) может быть быстрее. Redis — однопоточный (начиная с версии 6.0 — с отдельными I/O-потоками для сети, но не для выполнения команд), но взамен даёт rich data types (списки, множества, sorted sets, streams), встроенную persistence (RDB+AOF) и master-replica репликацию — то есть покрывает не только «кэш», но и легковесную очередь, счётчики, distributed lock и pub/sub на той же инфраструктуре. Выбор Redis по умолчанию в современном стеке — это выбор в пользу функциональности и операционной зрелости (persistence, replication, cluster mode), а Memcached остаётся правильным выбором именно там, где нужен только предельно простой и дешёвый key-value кэш без дополнительных требований.
> theory/DISTRIBUTED_CACHING.md §7

## 11. ETag vs Last-Modified — что использовать?

- **`Last-Modified`:** дата последнего изменения. Гранулярность — 1 секунда. Проблема: при clock skew или быстрых обновлениях недостаточно.
- **`ETag`:** произвольный токен (хеш контента, версия в БД). Сильный (`"abc"`) — точное совпадение байт; слабый (`W/"abc"`) — семантическое совпадение.

Сервер генерит ETag → клиент шлёт `If-None-Match: "abc"`. Если совпало — `304 Not Modified` без body.

ETag предпочтительнее: точнее, нет clock issues, можно использовать как версию для optimistic locking (`If-Match` на PUT).
> theory/HTTP_CDN_CACHE.md §2

## 29. Зачем нужен заголовок `Vary`, и почему `Vary: Cookie` — почти всегда ошибка?

`Cache-Control` сам по себе не говорит кэширующей стороне, что один и тот же URL может отдавать разные ответы в зависимости от других заголовков запроса — например, сжатый gzip или brotli ответ, либо контент на разных языках. `Vary: Accept-Encoding, Accept-Language` явно сообщает CDN и браузеру: храните отдельную копию для каждой комбинации значений этих заголовков, а не одну на URL. Механизм работает, только пока множество значений заголовка из `Vary` ограничено — `Accept-Encoding` принимает буквально несколько вариантов (gzip, br, identity). Проблема начинается, когда в `Vary` попадает заголовок с высокой кардинальностью: `Vary: User-Agent` даёт практически уникальное значение на каждого пользователя из-за версий браузеров и устройств, а `Vary: Cookie` — тем более, потому что у каждого посетителя свой набор кук. В обоих случаях кэш вынужден хранить отдельную копию почти на каждого пользователя, что на статике эквивалентно полному отключению кэширования при видимости, что «кэш вроде настроен».
> theory/HTTP_CDN_CACHE.md §3

## 12. Stale-while-revalidate — что это и зачем?

`Cache-Control: max-age=60, stale-while-revalidate=300`.

**Семантика:** до 60s — отдаём из кэша как fresh. От 60s до 360s — отдаём stale **сразу** + асинхронно перевалидируем. После 360s — обязательная синхронная revalidation.

Польза: устраняет latency spike в момент expiry (нет блокировки на rebuild), пользователь всегда получает быстрый ответ. Аналог refresh-ahead на уровне HTTP.
> theory/HTTP_CDN_CACHE.md §1

## 13. CDN purge vs versioned URLs — какой подход лучше?

- **Purge:** API/dashboard CDN'а удаляет ресурс с edge'ей. Минусы: задержка распространения (минуты), стоит денег за вызовы, иногда не работает на всех PoP сразу.
- **Versioned URLs (`/static/app.abc123.js`):** новая версия = новый URL. Cache-Control: `max-age=31536000, immutable`. Старые версии живут в кэше до eviction; новые — мгновенно доступны всем без покурга.

Versioned URLs — golden standard для статики (build-time hash). Purge — для контента, который **должен** исчезнуть (legal removal, breaking bug в API response).
> theory/HTTP_CDN_CACHE.md §4

## 14. Какие данные **нельзя** кэшировать?

- **Часто меняющиеся:** real-time котировки, счётчики (если важна точность).
- **Персонализированные:** одна страница для каждого user_id → cardinality взрывается.
- **Большие/редкие:** один запрос в час, 100MB ответ — занимает место без выгоды.
- **Чувствительные:** PII, токены, пароли — даже хешированные.
- **Транзакционные:** баланс счёта в момент переводов.

Перед добавлением кэша спросить: **какова частота чтения, частота изменения, и допустимый stale**? Если частота изменения ≈ частоте чтения или допустимый stale = 0 — кэш не нужен.
> theory/ANTI_PATTERNS.md §13

## 16. Как защитить кэш от penetration на несуществующих ключах?

Сценарий: атакующий шлёт запросы по случайным id (`user/9999999`). Каждый — miss → удар по БД.

Решения:
1. **Negative caching:** при miss класть в кэш `NULL_MARKER` с коротким TTL (минуты) → следующие запросы попадают в кэш.
2. **Bloom filter:** перед кэшем держать bloom со всеми существующими id. False-negative невозможен → если bloom говорит "нет", сразу 404 без запроса в кэш/БД. False-positive (несколько процентов) проходит дальше — ничего страшного.
3. **Rate limiting:** на уровне API gateway по IP/токену.

Bloom filter лучше при больших корпусах ключей (миллионы) и низкой частоте новых ключей (можно перестраивать раз в час).
> theory/ANTI_PATTERNS.md §2

## 17. Big keys и hot keys в Redis — почему это проблема?

**Big key:** одиночный ключ занимает мегабайты (огромный hash, list на миллион элементов). Проблемы: команды по нему блокируют single-threaded Redis (`HGETALL` на 100MB hash — секунды), миграция при resharding медленная, eviction уносит большой кусок данных за раз.

**Hot key:** один ключ получает 90% трафика (счётчик популярного товара). Шард с этим ключом перегружен, остальные простаивают. Sharding не помогает.

Решения для big keys: разбить (`user:42:profile`, `user:42:settings`, ...), использовать `HSCAN`/`SSCAN` для итерации. Для hot keys: in-memory near-cache (L1) с коротким TTL, локальная репликация ключа на несколько шардов с суффиксом (`counter:1`, `counter:2`, ...) и aggregation на чтении.
> theory/ANTI_PATTERNS.md §6

## 18. `maxmemory-policy` в Redis — что выбрать?

При достижении `maxmemory` Redis выбирает, что выкинуть:
- **`noeviction`** (default): возвращает ошибку на write. Подходит для durable storage, не для cache.
- **`allkeys-lru` / `allkeys-lfu`:** evict из всех ключей по LRU/LFU. Для cache-only.
- **`volatile-lru` / `volatile-lfu`:** evict только из ключей с TTL. Подходит, если в Redis смешаны cache + persistent данные (но это запах).
- **`allkeys-random` / `volatile-random`:** случайный выбор. Используется редко.
- **`volatile-ttl`:** evict ключ с ближайшим expiry первым.

Default рекомендация для pure cache: **`allkeys-lfu`** (исследования показывают чуть лучше hit-ratio, чем LRU на типичных нагрузках).
> theory/REDIS.md §3
