# Domain-Driven Design — Стратегическое проектирование

Стратегический DDD отвечает на вопрос «**как разбить большую систему на части и как эти части связать**» — и он важнее тактики: неправильно нарезанные границы не спасут никакие агрегаты. Всё дальше показано на сквозном примере интернет-магазина с четырьмя контекстами: «Каталог», «Заказы», «Склад», «Счета».

## Домен и поддомены

**Домен** — сфера деятельности бизнеса (здесь: интернет-магазин). Внутри домен делится на **поддомены**, и они не равноценны. От ценности поддомена зависит, сколько инженерных усилий в него вкладывать:

| Тип поддомена | Что это | Инвестиции | В примере магазина |
|---|---|---|---|
| **Core (ядро)** | то, чем бизнес отличается от конкурентов; источник прибыли | полный DDD, лучшие люди, максимум внимания | «Заказы» (полная гексагональная разбивка), «Счета» (Event Sourcing) |
| **Supporting (поддерживающий)** | нужен бизнесу, но не даёт преимущества | проще: без церемоний, но аккуратно | «Склад», «Каталог» |
| **Generic (общий)** | давно решённая всеми задача | купить или взять готовое, не писать самим | шина сообщений (Kafka), аутентификация, email |

**Практический вывод: не всем контекстам одинаковая архитектура.** Это ключевая мысль, которую часто упускают. В примере «Заказы» разнесены на три модуля (domain / application / infrastructure), а «Склад» обходится пакетами внутри одного модуля — тяжесть решения соответствует ценности поддомена. Тратить полный гексагон на Generic-справочник — та же ошибка, что и лепить Core-домен на коленке.

Как отличить Core: спросите бизнес — «если это будет работать как у конкурентов, но чуть хуже, мы разоримся?». Если да — это ядро, сюда идут лучшие силы.

## Ubiquitous Language (единый язык)

Ubiquitous Language — общий словарь бизнеса и разработчиков, который используется **в коде**, а не только в вики и разговорах. Одно и то же понятие — одно слово везде: в требованиях, в разговоре с экспертом, в имени класса и метода.

Признак сломанного языка: чтобы понять код, нужен «переводчик с программистского» — эксперт говорит «оформить заказ», а в коде `updateStatus(2)`.

Три проявления единого языка в коде примера:

**1. Операции названы по-бизнесовому.** Бизнес говорит «оформить заказ» → в коде `Order.place()`, а не `setStatus(2)`:

```kotlin
order.place()          // оформить
order.confirm()        // подтвердить
order.cancel(reason)   // отменить
// а не order.updateStatus(2) — что такое «2»? снова нужен «переводчик»
```

**2. Разные понятия — разные типы, даже если поля похожи.** Бизнес различает «корзину» и «заказ» — значит, это два класса, `Cart` и `Order`, хотя набор полей у них близок. У них разные инварианты и разный смысл: корзину можно бросить, заказ — обязательство перед покупателем.

**3. Значимые перечисления вместо магических строк.** Причина отмены — `enum CancellationReason`, а не строка `"cancelled by user"`, которую в каждом месте пишут чуть иначе.

Единый язык — не «документация», а инструмент мышления: пока команда не может назвать вещь одним словом, она её не до конца понимает. Уточнение языка на воркшопах (см. [EVENT_STORMING.md](EVENT_STORMING.md)) — это и есть проектирование.

## Bounded Context — граница непротиворечивой модели

Bounded Context (ограниченный контекст) — граница, внутри которой модель и язык **непротиворечивы**. Одно слово внутри контекста значит ровно одно. Снаружи то же слово может значить другое — и это нормально: универсального смысла на всю компанию не существует.

Главная иллюстрация — **три модели «товара»** в одном магазине:

| Контекст | Класс | Что такое «товар» здесь |
|---|---|---|
| Каталог | `Product` | витринная карточка: название, описание, цена, доступность |
| Заказы | `OrderLine` | позиция заказа: ссылка по ID + снэпшот цены + количество |
| Склад | `StockItem` | единица хранения: остаток и резерв по Sku |

Каждая модель знает только то, что нужно ей. Каталог — витринное описание:

```kotlin
// Контекст «Каталог»: товар — это витринная карточка
class Product(
    val sku: String,
    val title: String,
    val description: String,
    val priceAmount: BigDecimal,
    val priceCurrency: String,
    val availability: Availability,   // FOR_SALE / DISCONTINUED / PREORDER
)
```

Заказы — позиция с зафиксированной ценой и ссылкой на товар только по идентификатору:

```kotlin
// Контекст «Заказы»: товар — позиция заказа со снэпшотом цены
class OrderLine internal constructor(
    val productId: ProductId,   // ссылка на товар каталога — только по ID!
    val unitPrice: Money,       // снэпшот цены на момент заказа, не «живая» цена каталога
    quantity: Int,
)
```

Склад про цену и описание вообще не знает — в его модели их просто нет:

```kotlin
// Контекст «Склад»: товар — остаток и резерв
class StockItem(val sku: Sku, quantityOnHand: Int) {
    var reserved: Int = 0; private set
    val available: Int get() = quantityOnHand - reserved   // вычисляется, не хранится
    // Инвариант: reserved <= quantityOnHand — нельзя обещать больше, чем лежит
}
```

Один физический предмет — три модели. Попытка слить их в «универсальный Product» со всеми полями сразу дала бы God Object, который знает всё и нужен всем, а меняется от любого запроса любого отдела (см. [ANTIPATTERNS.md](ANTIPATTERNS.md)).

Обратите внимание и на идентификаторы: в «Заказах» товар — это `ProductId`, а на «Складе» — `Sku`. Разные контексты не только по-разному моделируют, но и по-разному **называют** один предмет:

```kotlin
// Один предмет — разные типизированные ID в разных контекстах
@JvmInline value class ProductId(val value: String)   // язык «Заказов»
@JvmInline value class Sku(val value: String)         // язык «Склада»
```

**Логическая граница против физической.** Bounded Context — это **логическая** граница (единство модели и языка); модуль или сервис — её **физическое** воплощение. В примере каждый контекст — отдельный Gradle-модуль в одном процессе, и граница защищена сборкой: код заказов физически не может импортировать внутренности склада. В продакшене те же контексты могли бы стать микросервисами — суть не изменится: своя модель, своё хранилище, интеграция только через контракты. Глубже связь «Bounded Context ↔ микросервис» (database-per-service, модульный монолит) разобрана в [ARCHITECTURE.md](ARCHITECTURE.md).

## Context Map — карта отношений между контекстами

Bounded Context не живут в вакууме: они обмениваются данными. Context Map (карта контекстов) фиксирует, кто с кем связан и — что важнее — **какие между командами отношения**. DDD выделяет девять типовых видов связи. Разделим их на технические паттерны интеграции и модели отношений команд. Два ключевых направления связи: **upstream** (поставщик, выше по течению) и **downstream** (потребитель, ниже по течению) — поставщик диктует формат, потребитель приспосабливается.

### Технические паттерны интеграции

**Shared Kernel (разделяемое ядро).** Небольшая модель, которую несколько контекстов **физически разделяют** как общий код. В примере «Заказы», «Счета» и «Склад» разделяют `Money`, типизированные идентификаторы и базовый `DomainEvent`:

```kotlin
// shared-kernel: общий на несколько контекстов Value Object
class Money private constructor(val amount: BigDecimal, val currency: Currency) {
    operator fun plus(other: Money): Money {
        requireSameCurrency(other)          // складывать можно только одну валюту
        return Money(amount + other.amount, currency)
    }
}
```

Правила Shared Kernel жёсткие: ядро **минимально** и меняется только по общему согласию всех команд-совладельцев. Каждый класс в ядре — точка сцепления команд, поэтому «удобные утилиты» и «положу-ка я сюда хелпер» туда не попадают. Показательно: «Каталог» в соглашении **не участвует** — у него всё своё, даже денег он не разделяет. Раздутый Shared Kernel — известный антипаттерн: он превращает независимые контексты в одну связанную массу.

**Open Host Service (OHS, открытый хост-сервис).** Когда у контекста **много** потребителей, индивидуальная интеграция с каждым дорога. Контекст публикует **один** стабильный документированный протокол для всех сразу. В примере это фасад каталога:

```kotlin
// Каталог как Open Host Service: один вход для всех потребителей
interface CatalogApi {
    fun findProduct(sku: String): ProductResource?
}
```

В реальной системе это был бы REST/gRPC API с версией (`/api/v1/products`) и гарантией обратной совместимости.

**Published Language (опубликованный язык).** Формально описанный формат обмена, **не совпадающий** с внутренней моделью. Внутреннюю модель команда меняет свободно; опубликованный формат — контракт, который ломать нельзя. Формат каталога намеренно сделан «историческим и неудобным» — как это сплошь и рядом с реальными внешними API, которые «слишком важны, чтобы их менять»:

```kotlin
// Published Language каталога: контракт, а НЕ внутренняя модель Product
data class ProductResource(
    val sku: String,
    val nm: String,    // название (сокращение из старой CRM 2000-х)
    val prc: String,   // цена СТРОКОЙ: "4990.00 RUB"
    val st: Int,       // статус МАГИЧЕСКИМ числом: 1 = продаётся, 2 = снят, 7 = предзаказ
)
```

Внутреннюю модель `Product` меняем как хотим; `ProductResource` — только совместимо. В событийной интеграции роль опубликованного языка играют версионированные контракты (`order-placed.v1`).

**Anticorruption Layer (ACL, антикоррупционный слой)** — самый важный интеграционный паттерн. Это переводчик на границе downstream-контекста (потребителя): вся «грязь» чужого формата (цена строкой `"4990.00 RUB"`, статус числом `st=7`) запирается в одном классе и не просачивается в домен. Домен видит только свой порт на своём языке:

```kotlin
// Доменная сторона ACL — порт на языке «Заказов». Ни слова про HTTP и строки:
interface ProductPriceProvider {
    fun currentPrice(productId: ProductId): Money?   // Money или null (недоступен)
}

// Адаптер-переводчик — единственное место, знающее чужой формат:
class CatalogAclAdapter(private val catalog: CatalogApi) : ProductPriceProvider {
    override fun currentPrice(productId: ProductId): Money? {
        val resource = catalog.findProduct(productId.value) ?: return null
        return when (resource.st) {
            FOR_SALE, PREORDER -> parsePrice(resource)   // "4990.00 RUB" -> Money
            DISCONTINUED       -> null   // «снят с продажи» = «цены нет» на языке заказов
            else -> throw CorruptedCatalogDataException("неизвестный статус ${resource.st}")
        }
    }
    // parsePrice — единственное место в системе, знающее формат "4990.00 RUB"
}
```

ACL переводит **понятия**, а не переименовывает поля: факт `st = 2 (снят с продажи)` превращается в `null` («цены нет»), потому что именно так это звучит на языке заказов. Каталог сменит формат или переедет на GraphQL — изменится один файл.

### Модели отношений команд (в коде не показать)

Следующие виды связи — не про технику, а про **баланс сил и договорённости между командами**. Их не увидеть в одном репозитории, но на собеседовании про них спрашивают.

| Отношение | Суть | Пример |
|---|---|---|
| **Partnership (партнёрство)** | две команды взаимозависимы, планируют релизы и выкатываются вместе | «Заказы» и «Счета» вместе выпускают «оплату частями»: синхронизируют контракты, выкатываются согласованно |
| **Customer–Supplier (заказчик–поставщик)** | upstream (поставщик) учитывает потребности downstream (заказчика) при планировании | команда каталога добавляет поля в `ProductResource` по запросам команды заказов |
| **Conformist (конформист)** | downstream не может влиять на upstream и принимает его модель как есть | внешний «слишком важный» API, который не изменить |
| **Separate Ways (каждый своей дорогой)** | лучшая интеграция — никакой | проще продублировать крошечный справочник в двух контекстах, чем сцеплять их |

Тонкость про Conformist на примере: «Заказы» по **силе переговоров** — конформист (формат каталога не изменить), но по **технике** — нет: чужую модель внутрь не пустили, поставив ACL. Conformist без ACL — это когда `prc: String` расползается по всему коду заказов. То есть Conformist и ACL — ответ на один и тот же расклад сил, но с разной инженерной дисциплиной.

**Big Ball of Mud (большой ком грязи).** Девятое «отношение» — честная пометка на карте: «вот внутри этой системы границ нет, модели перемешаны, менять страшно». Ценность пометки в том, что она задаёт правило: с комом грязи общаемся **только через ACL**, чтобы его грязь не расползлась в чистые контексты. Постепенное вытеснение унаследованного кома новыми контекстами — это паттерн Strangler Fig; он разобран в системном дизайне, см. [../../system-design/theory/microservice_patterns.md](../../system-design/theory/microservice_patterns.md).

## Эвристики поиска границ контекстов

Как понять, где проходит граница? Несколько практических признаков:

- **Одно слово значит разное для разных отделов** → это разные контексты. «Товар» для витрины, склада и заказа — три разные сущности.
- **Разные темпы изменений или разные команды** → разные контексты. Если одна часть меняется еженедельно, а другая раз в год — их стоит разрезать.
- **Модель тащит поля «на всякий случай для соседей»** → граница проходит прямо через неё; лишние поля принадлежат другому контексту.
- **Транзакция «должна» охватить данные двух отделов** → скорее всего это не транзакция, а сага между контекстами (см. [INTEGRATION_PATTERNS.md](INTEGRATION_PATTERNS.md)).
- **Меняется жаргон в разговоре экспертов** → там, где меняется словарь, обычно проходит граница контекста.

Инструмент, систематизирующий поиск границ на практике, — Event Storming: поворотные (pivotal) события на потоке часто совпадают с границами контекстов. Об этом — следующий файл.
