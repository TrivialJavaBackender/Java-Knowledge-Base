# Domain-Driven Design — Проектирование агрегатов

Агрегат — центральный и самый трудный паттерн тактического DDD. Остальные блоки (Value Object, Entity, Repository) введены в [TACTICAL_PATTERNS.md](TACTICAL_PATTERNS.md); здесь — глубокий разбор: что такое граница агрегата, по каким правилам её проводят, как её защищает код и почему от размера агрегата зависят согласованность, конкурентность и производительность.

## Агрегат и Aggregate Root

Aggregate (агрегат) — кластер объектов (Entity + Value Object), который рассматривается как **единое целое для изменений**. Один из объектов — Aggregate Root (корень агрегата): единственная точка входа. Внешний код ссылается на агрегат только по идентичности корня и никогда не трогает внутренние сущности напрямую.

В модели заказов агрегат — это `Order` (корень) + список внутренних `OrderLine` + Value Object (`Money`, `OrderStatus`, `ShippingAddress`). Главное уравнение, которое стоит запомнить:

> **Агрегат = граница инвариантов = граница транзакции = единица конкурентного доступа и блокировки.**

Инвариант — бизнес-правило, которое обязано выполняться **в любой зафиксированный момент**. Агрегат — то место, где инварианты защищены синхронно, в одной транзакции. У `Order` их четыре:

- **И1:** состав заказа меняется только в статусе `DRAFT`;
- **И2:** в заказе не больше `MAX_LINES` позиций;
- **И3:** оформить (`place`) можно только непустой заказ;
- **И4:** переходы статусов только по схеме `DRAFT → PLACED → CONFIRMED` (с ветками отмены).

Все четыре защищены **внутри** кода агрегата — их невозможно обойти, потому что состояние снаружи не редактируется.

## Четыре правила проектирования (Вернон)

Вон Вернон в «Effective Aggregate Design» свёл проектирование агрегатов к четырём правилам. Все они видны в `Order`.

**Правило 1. Моделируй истинные инварианты в границе агрегата.** В агрегат входит только то, что должно быть **строго** консистентно в одной транзакции. «Сумма заказа = сумма строк» — да, это инвариант, обе части нужны одновременно. «Остаток на складе уменьшился при заказе», «деньги списаны» — **нет**: это другие агрегаты в других контекстах, согласованность с ними **итоговая** (eventual), через события и сагу. Проверочный вопрос: правило действительно обязано выполняться в **каждый** момент — или допустимо, что оно станет истинным «через секунду»? Если итоговая согласованность приемлема — это отдельный агрегат.

**Правило 2. Проектируй маленькие агрегаты.** `Order` не хранит объект `Customer` и всю его историю заказов — только `customerId`. Большой агрегат — это конкуренция за него (contention: много команд соперничают за один объект), лишняя память при загрузке и длинные транзакции. Предпочитай много мелких агрегатов одному большому.

**Правило 3. Ссылайся на другие агрегаты только по идентичности.** Внутри — `customerId: CustomerId`, `productId: ProductId`, а не `val customer: Customer` или `val product: Product`. Держать объект чужого агрегата внутри своего — значит склеить границы транзакций и лишиться возможности разнести контексты по разным сервисам и базам.

**Правило 4. Обновляй другие агрегаты через итоговую согласованность.** Наружу агрегат общается **доменными событиями**: копит их и отдаёт при сохранении (`pullEvents()` → outbox → шина), а подписчик меняет другой агрегат в **отдельной** транзакции. Оркеструет такую цепочку сага.

```kotlin
fun place() {
    check(status == OrderStatus.DRAFT) { "Заказ уже оформлен (статус $status)" }
    check(_lines.isNotEmpty()) { "Нельзя оформить пустой заказ" }        // И3
    status = OrderStatus.PLACED
    _events += OrderPlaced(id, customerId, total, Instant.now())          // Правило 4: наружу — событием
}
```

## Механика инкапсуляции корня

Правила Вернона — не благие пожелания, а конкретные механики Kotlin, делающие обход инвариантов **невозможным**:

```kotlin
class Order private constructor(
    val id: OrderId,
    val customerId: CustomerId,           // Правило 3: ссылка на чужой агрегат по ID
    val shippingAddress: ShippingAddress,
    status: OrderStatus,
    lines: MutableList<OrderLine>,
) {
    var status: OrderStatus = status
        private set                        // читать можно всем, менять — только методам агрегата

    private val _lines: MutableList<OrderLine> = lines
    val lines: List<OrderLine>
        get() = _lines.toList()            // наружу — НЕИЗМЕНЯЕМАЯ КОПИЯ

    val total: Money                       // сумма ВЫЧИСЛЯЕТСЯ, а не хранится полем —
        get() = _lines.fold(Money.zero(currency)) { acc, l -> acc + l.lineTotal }  // инвариант по построению

    companion object {
        fun draft(customerId: CustomerId, shippingAddress: ShippingAddress): Order =
            Order(OrderId.new(), customerId, shippingAddress, OrderStatus.DRAFT, mutableListOf())
    }
}
```

- `private set` на статусе — извне статус не выставить, только через `place()`/`confirm()`/`cancel()`, которые проверяют переходы (И4).
- `class OrderLine internal constructor(...)` и `internal set` на количестве — за пределами модуля `domain` строку не создать и не изменить; править её может только корень.
- `val lines: List<OrderLine> get() = _lines.toList()` — отдать наружу `MutableList` значило бы позволить `order.lines.add(...)` в обход инвариантов; отдаём read-only копию.
- Приватный конструктор + именованная фабрика `Order.draft(...)` — невозможно создать заказ в произвольном состоянии, только валидный черновик.
- Сумма — **вычислимое** свойство, а не хранимое поле: хранимый `total` рано или поздно разъехался бы со строками; вычислимый делает инвариант «сумма = сумма строк» истинным по построению.

Внутренняя сущность несёт ту же дисциплину со своей стороны: конструктор и мутирующие методы `OrderLine` помечены `internal`, поэтому вне модуля `domain` строку не собрать и не изменить в обход корня.

```kotlin
class OrderLine internal constructor(       // за пределами domain строку не создать
    val id: OrderLineId,
    val productId: ProductId,               // Правило 3: чужой агрегат — по ID
    val unitPrice: Money,                   // снэпшот цены на момент добавления, не «живая» цена каталога
    quantity: Int,
) {
    var quantity: Int = quantity
        internal set                         // менять может только Order

    internal fun increaseBy(added: Int) { require(added > 0); quantity += added }
    override fun equals(other: Any?): Boolean = other is OrderLine && other.id == id  // Entity: по ID
}
```

Обрати внимание на `unitPrice`: это **снэпшот** цены на момент добавления, а не ссылка на «живую» цену каталога. Каталог поменяет цену — сумма уже оформленного заказа не «поплывёт»; скопированный Value Object фиксирует факт «покупатель согласился на такую цену». Это тоже часть инвариантов агрегата.

Прямое следствие такой чистоты — тесты инвариантов не требуют ни моков, ни базы, ни Spring: домен тестируется как обычные объекты (`assertFailsWith<IllegalStateException> { order.place() }` на пустом заказе).

## Внутри агрегата: Entity или Value Object?

Не всякий член агрегата — сущность. Внутри границы живут и внутренние Entity, и Value Object, и выбор между ними тот же, что и для корня, только идентичность у внутренней сущности **локальная**.

- **Внутренняя Entity** — когда у члена есть собственная идентичность, за которой нужно следить, и изменяемое состояние. `OrderLine` — Entity: у неё `OrderLineId` и меняющееся `quantity`, строку нужно уметь адресовать («увеличить количество вот этой позиции») и отличать от одинаковой по составу соседней.
- **Value Object внутри** — когда член заменяется целиком и различать «который именно» не нужно. Будь позиция неизменяемой и безымянной (цена + количество без своего ID), она была бы Value Object, и «изменение» означало бы замену всего списка.

Практическое следствие: внутренних Entity в агрегате должно быть как можно меньше. Каждая — это идентичность, за жизненным циклом которой обязан следить корень; там, где хватает Value Object, его и берут — он проще, неизменяем и не заводит лишней «бухгалтерии идентичностей». `OrderLine` остаётся Entity только потому, что бизнесу важны адресуемость строки и её независимое изменение внутри черновика.

## Транзакционная и итоговая согласованность

Из «агрегат = граница транзакции» следует практическое правило Вернона:

> **Одна транзакция изменяет ровно один агрегат.**

Если два агрегата «должны» меняться вместе — это сигнал: либо (редко) это на самом деле один агрегат, либо (обычно) их согласованность должна быть **итоговой**. Критерий разбиения — кому правило нужно немедленно: то, что обязано быть согласованным **сейчас**, — в один агрегат; то, что терпит краткую задержку, — в отдельный агрегат плюс итоговая согласованность.

| | Транзакционная (strong) | Итоговая (eventual) |
|---|---|---|
| Где | внутри одного агрегата | между агрегатами / контекстами |
| Механизм | одна ACID-транзакция | доменные события + сага |
| Гарантия | инвариант истинен всегда | согласуется «через миг» |
| Пример | «сумма = сумма строк» | «оформлен заказ → списаны деньги → зарезервирован товар» |

Конкретно в модели заказов итоговая согласованность выглядит так: `Order.place()` порождает `OrderPlaced` → сага просит `Billing` списать деньги → затем `Warehouse` зарезервировать товар → при успехе сага вызывает `order.confirm()`. Три агрегата (`Order`, `Account`, `StockItem`) меняются **по очереди, отдельными транзакциями**, а не разом. Если шаг падает, сага запускает компенсацию — `order.cancel(...)` с осмысленной причиной (`PAYMENT_FAILED`, `OUT_OF_STOCK`): «отмену» нельзя «откатить», её можно только скомпенсировать встречным действием. Сама механика саги и Outbox — в связанных файлах ниже; здесь важно, что граница агрегата **вынуждает** такой сценарий, а не наоборот.

**Когда правило нарушают.** Оно прагматичное, а не догма. `FundsTransferService` переводит деньги между **двумя** агрегатами `Account` в одной транзакции БД — потому что счета в одном контексте и одной базе, а для денег нужна строгая согласованность. Это осознанный компромисс, о котором стоит говорить вслух: в распределённой системе тот же перевод стал бы сагой. Нарушать правило «один агрегат на транзакцию» можно — но только сознательно и понимая цену.

> Механику итоговой согласованности — сага (хореография против оркестрации), компенсирующие транзакции, Outbox — держит [../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md](../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md); как она выглядит внутри этого модуля (Domain/Integration Event, Outbox, CQRS) — в [INTEGRATION_PATTERNS.md](INTEGRATION_PATTERNS.md).

## Проектируй по инвариантам, а не по данным

Частая ошибка — нарисовать ER-диаграмму, а затем обернуть каждую таблицу в класс. Так получаются произвольные границы агрегатов и анемичная модель. DDD переворачивает порядок: **сначала находишь инварианты** (какие правила обязаны выполняться всегда), и уже они рисуют границы агрегатов. Агрегат — граница **согласованности**, а не рамка вокруг таблицы.

Связь 1:N в базе сама по себе **не** означает, что сторона «N» лежит внутри агрегата. `OrderLine` живёт внутри `Order`, потому что инварианты «сумма = сумма строк» и «состав меняется только в DRAFT» требуют обеих частей одновременно. А `Order` и `Customer` — **разные** агрегаты, хотя в базе между ними внешний ключ: нет инварианта, связывающего их в каждый момент. Отношение в данных ≠ граница агрегата.

## Проблема set-based validation

Некоторые правила охватывают **множество** экземпляров агрегата и потому не помещаются внутрь одного: «email уникален среди всех клиентов», «две брони не пересекаются по времени для одной комнаты». Агрегат видит только себя и такое правило проверить не может. Три решения:

1. **Ограничение БД** (уникальный индекс) — самое дешёвое и прагматичное: множество стережёт база. Минус — правило утекает из домена в схему, а нарушение всплывает как `ConstraintViolation`, который надо перевести обратно в доменную ошибку.
2. **Доменный сервис с запросом** — перед созданием проверяет множество через репозиторий или проекцию чтения, потом создаёт. Остаётся окно гонки (TOCTOU: проверил — кто-то вставил — создал дубль), если не подстраховать ограничением БД.
3. **Выделенный агрегат**, владеющий множеством (например, `CustomerRegistry`), сериализует инвариант внутри себя. Тяжело; оправдано, только когда уникальность — первоклассное бизнес-понятие само по себе.

Прагматичный дефолт: уникальный индекс БД плюс перевод нарушения в доменную ошибку. Заводить агрегат-реестр ради простой уникальности email — избыточное усложнение.

## Размер агрегата и его цена

Большой агрегат обходится дорого по трём осям:

- **Конкуренция за агрегат (contention).** Агрегат — единица блокировки и транзакции. Чем он крупнее, тем чаще параллельные команды соперничают за него и тем больше повторов из-за оптимистичной блокировки.
- **Память.** Загрузка агрегата тянет все его внутренности. `Order` со 100 000 строк — проблема и по памяти, и по задержке.
- **Длина транзакции.** Больше данных на запись — дольше удерживаются блокировки.

Поэтому `Order` ограничивает число строк сотней (`MAX_LINES = 100`) — это сознательная граница. Если бы строк могло быть неограниченно много, «добавить строку загружает весь заказ» стало бы узким местом, и моделировать пришлось бы иначе (например, каждую строку — отдельным агрегатом со ссылкой на заказ по ID).

**Выбор корня.** Корнем становится сущность, которая владеет инвариантами, служит естественной точкой входа, имеет глобально осмысленную идентичность и переживает свои внутренности. У внутренних сущностей идентичность **локальная**: `OrderLineId` имеет смысл только внутри своего заказа, снаружи на строку по её ID никто не ссылается.

**`Cart` как намеренно простой агрегат.** Корзина — второй агрегат контекста, контрастный `Order`: у неё минимум инвариантов, нет статусной машины и доменных событий, она даже **не хранит цены** (их актуализирует `OrderFromCartFactory` при оформлении). Не каждый агрегат обязан быть сложным — сложность модели должна соответствовать сложности бизнес-правил, а не амбициям архитектора.

## Оптимистичная блокировка версией агрегата

Раз агрегат — единица конкурентного доступа, параллельные изменения разрешают на уровне агрегата целиком. Классический механизм — **оптимистичная блокировка**: агрегат несёт `version`; при сохранении ожидаемая версия сверяется с хранимой; несовпадение значит, что кто-то изменил агрегат параллельно, — тогда `ConcurrencyException`, перечитать и повторить команду. Версия стережёт **всю границу инвариантов**, а не отдельную строку таблицы.

В event-sourced `Account` это видно буквально: версия — число применённых событий истории, а Event Store сверяет её с фактической длиной потока:

```kotlin
fun append(streamId: String, expectedVersion: Long, events: List<AccountEvent>) {
    val stream = streams.getOrPut(streamId) { mutableListOf() }
    if (stream.size.toLong() != expectedVersion) {                 // кто-то успел записать раньше
        throw ConcurrencyException(streamId, expectedVersion, stream.size.toLong())
    }
    events.forEach { stream += StoredEvent(streamId, stream.size.toLong(), it) }
}
```

Два процесса загрузили счёт (`version = 5`), оба провели списание, оба сохраняют. Первый `append` с `expectedVersion = 5` проходит (поток стал длиной 6), второй падает с `ConcurrencyException`: его инвариант «баланс не уйдёт в минус» проверялся на устаревшем состоянии. Так агрегат защищает инварианты **без** пессимистичных блокировок. (В реляционном хранилище тот же приём — колонка `version` и `UPDATE ... WHERE id = ? AND version = ?`; в Event Store — уникальный индекс по `(stream_id, seq)`.)

> Механику оптимистичной и пессимистичной блокировки на уровне JPA/Hibernate (`@Version`, `LockModeType.OPTIMISTIC` против `PESSIMISTIC_WRITE`, `OptimisticLockException`) держит [../../hibernate-jpa/theory/TRANSACTIONS_LOCKING.md](../../hibernate-jpa/theory/TRANSACTIONS_LOCKING.md). Здесь — только **доменная** причина: почему единицей блокировки является именно агрегат.

## Чек-лист проектирования агрегата

- Сформулируй инварианты — правила, истинные в каждый момент. Они рисуют границу.
- Втяни в агрегат только то, что этим инвариантам нужно синхронно; остальное — итоговая согласованность.
- Держи агрегат маленьким; на другие агрегаты ссылайся по ID.
- Один корень, одна точка входа; внутренности — за `private`/`internal`, наружу — копии.
- Одна команда меняет один агрегат в одной транзакции; исключения — осознанны.
- Согласуй агрегаты доменными событиями, а конкурентность — версией (оптимистичная блокировка).

- Vaughn Vernon. *Implementing Domain-Driven Design*, ch. 10 «Aggregates». Addison-Wesley, 2013.
- Eric Evans. *Domain-Driven Design*, ch. 6 «The Life Cycle of a Domain Object» (Aggregates, Factories, Repositories). Addison-Wesley, 2003.
- Vlad Khononov. *Learning Domain-Driven Design*, ch. 6 «Tackling Complex Business Logic» (агрегаты через инварианты). O'Reilly, 2021.
- Martin Fowler. *DDD_Aggregate* — краткое определение. martinfowler.com/bliki.
