# Domain-Driven Design — Гибкий дизайн (Supple Design)

Часть III «Синей книги» Эванса — про то, как сделать модель, которую **легко менять**. Модель живёт не в тот момент, когда её нарисовали, а годами — под потоком новых требований. Жёсткая модель сопротивляется изменению: каждая правка рвётся эхом по всему коду. **Гибкий дизайн (supple design)** — набор приёмов, делающих модель податливой: разработчик, меняющий её, может рассуждать локально, комбинировать части свободно и доверять их поведению не читая реализацию.

Гибкий дизайн — это не «красивый код вообще», а конкретные строительные блоки плюс процесс, которым модель до них доводят. Разбираем и то, и другое.

## 1. Строительные блоки гибкого дизайна

Эванс называет шесть приёмов. Все они служат одной цели — **локальности рассуждения**: чтобы понять и безопасно изменить часть модели, разработчику не должно требоваться держать в голове всю систему. Ниже — каждый блок и его роль.

| Блок | Что даёт гибкости | Пример в демо |
|---|---|---|
| Intention-revealing interfaces | смысл виден без чтения реализации | `spec.isSatisfiedBy(order)` |
| Side-effect-free functions | запрос можно звать и комбинировать безопасно | `money.plus(other)` |
| Assertions | контракт метода явен и проверяем | `check` в `Order.place()` |
| Conceptual contours | изменение остаётся локальным | границы `Order` / `OrderLine` |
| Standalone classes | класс понятен в изоляции | `Specification<T>` |
| Closure of operations | свободная композиция без новых понятий | `Money + Money = Money` |

### Intention-revealing interfaces (интерфейсы, раскрывающие намерение)

Имя класса, метода, аргумента должно говорить **что** делается и **зачем**, а не **как** это реализовано. Клиент такого интерфейса рассуждает в терминах домена, не заглядывая в тело метода. Как только приходится читать реализацию, чтобы понять смысл вызова, — инкапсуляция потеряна.

`Specification` из демо — образец: имя `isSatisfiedBy` дословно переводит бизнес-фразу «кандидат удовлетворяет правилу», и клиент читает намерение, не зная про `if` внутри.

```kotlin
interface Specification<T> {
    fun isSatisfiedBy(candidate: T): Boolean       // ЧТО спрашиваем, не КАК проверяем
}
```

Сравните `order.total` (намерение: «сумма заказа») с `order.calc(2)` — второе заставляет лезть в код за смыслом «двойки». Имя из Ubiquitous Language — уже часть гибкого дизайна.

### Side-effect-free functions (функции без побочных эффектов)

Операции делятся на **команды** (меняют состояние) и **запросы** (возвращают ответ, ничего не меняя). Запрос без побочных эффектов можно вызывать сколько угодно раз, в любом порядке, комбинировать с другими — не боясь испортить состояние. Правило: **как можно больше сложной логики выносить в запросы без эффектов, а состояние менять как можно проще**. Естественный дом для таких функций — Value Object, который вдобавок неизменяем.

`Money` целиком построен на запросах: `plus`, `times`, `isPositive` возвращают новое значение или ответ, не трогая аргументы.

```kotlin
operator fun plus(other: Money): Money {           // запрос: новый Money, this не изменён
    requireSameCurrency(other)
    return Money(amount + other.amount, currency)
}
fun isPositive(): Boolean = amount > BigDecimal.ZERO   // чистый запрос
```

Сложная арифметика денег живёт в неизменяемом VO без эффектов; изменяемое состояние агрегата (`Order.status`) меняется отдельными простыми командами. Побочный эффект локализован — рассуждать о системе проще.

### Assertions (утверждения)

Поведение метода должно быть задано **пост-условиями и инвариантами**, а не пересказом реализации. «После `place()` статус — `PLACED`, событие `OrderPlaced` порождено» — это контракт, за который отвечает метод; как именно — его дело. Где язык позволяет выразить утверждение в коде (`require`, `check`, тесты-характеризации, контракты) — выражаем; где нет — **проговариваем явно** в имени и документации, чтобы контракт не растворился.

```kotlin
fun place() {
    check(status == OrderStatus.DRAFT) { "Заказ уже оформлен (статус $status)" }
    check(_lines.isNotEmpty()) { "Нельзя оформить пустой заказ" }   // пред-условие как assertion
    status = OrderStatus.PLACED                                     // пост-условие: гарантия метода
    _events += OrderPlaced(id, customerId, total, Instant.now())
}
```

`check`-и здесь — исполняемые утверждения инвариантов; они документируют контракт и ломаются громко при его нарушении.

Сильнейшая форма утверждения — **инвариант по построению**, когда нарушить его нельзя в принципе. Инвариант «сумма заказа = сумма строк» можно было бы охранять `assert`-ом при каждой правке; вместо этого сумма **вычисляется** из строк и не хранится полем — тогда рассинхрону просто неоткуда взяться:

```kotlin
val total: Money get() = _lines.fold(Money.zero(currency)) { acc, l -> acc + l.lineTotal }
```

Хранимое поле `total` рано или поздно разъехалось бы с реальностью, и его пришлось бы охранять утверждением; вычислимое — держит инвариант само. Лучшая assertion — та, которую не нужно писать.

### Conceptual contours (концептуальные контуры)

Резать модель нужно **по естественным швам домена**, а не по техническому удобству. Когда границы классов и модулей совпадают с тем, как устроена сама предметная область, изменение одного бизнес-правила задевает один участок кода. Когда границы проведены поперёк смысла — простое требование расползается правками по всей системе. Признак верных контуров: частые изменения оказываются локальными; вы редко правите десять файлов ради одной идеи.

Пример: требование «в оформленном заказе состав менять нельзя» касается **только** `Order` и его правил перехода — потому что состав заказа и его статус лежат в одном контуре (агрегате). А вот требование «при оформлении уменьшить остаток на складе» контур `Order` **не** задевает: остаток — другой контур (другой агрегат в другом контексте), и связь между ними — итоговая согласованность через событие, а не поле внутри заказа. Неверные контуры выдали бы себя тем, что правка правила доставки заставляла бы трогать и склад, и оплату.

### Standalone classes (независимые классы)

Каждая зависимость — это то, что нужно держать в голове, чтобы понять класс. Чем меньше у класса связей с остальным миром, тем ниже связанность (low coupling) и тем легче его понять и изменить в изоляции. Идеал — класс, который читается и тестируется сам по себе.

Не всякая зависимость вредна — вредна **лишняя**. Зависимость `Order` от `Money` осмысленна: заказ действительно про деньги. А вот зависимость доменного класса от базы или фреймворка — концептуально лишняя, она нагружает понимание техникой. Гибкий дизайн вычищает именно такие связи, стягивая наиболее сложную логику в классы, которые можно понять поодиночке.

`Specification<T>` независим: он не знает ни про `Order`, ни про базу, ни про фреймворк — только про тип-параметр `T`. Его можно осмыслить и проверить, не загружая половину системы.

### Closure of operations (замкнутость операций)

Операция **замкнута**, если её аргумент(ы) и результат — **одного типа**. Такая операция не тянет за собой новых понятий и свободно комбинируется сама с собой. `Money + Money = Money` — замкнутая операция: сумма денег — снова деньги, поэтому суммы складываются в любую цепочку.

```kotlin
operator fun plus(other: Money): Money     // Money × Money → Money — замкнуто
```

Замкнутость есть и на уровне `Specification`: `and`, `or`, `not` принимают и возвращают `Specification<T>`, поэтому правила складываются в сколь угодно сложные, оставаясь тем же типом:

```kotlin
infix fun and(other: Specification<T>): Specification<T>    // Spec × Spec → Spec — замкнуто
// freeShipping = amountAtLeast(threshold) and shipsDomestically   ← читается как бизнес-фраза
```

Замкнутость операций — прямой мост к функциональному DDD: именно она даёт свободную композицию неизменяемых значений, см. [FUNCTIONAL_DDD.md](FUNCTIONAL_DDD.md).

## 2. Процесс: как модель доходит до гибкости

Гибкий дизайн не проектируют заранее — к нему **приходят** через итеративное моделирование вместе с экспертами.

- **Knowledge crunching (перемалывание знаний).** Модель рождается не в голове аналитика, а в разговоре разработчиков и экспертов домена: гипотеза → пример → противоречие → уточнённая модель. Это не разовый сбор требований, а непрерывное «перемалывание» сценариев в понятия, у которых есть имя в Ubiquitous Language. Пример работы механизма: разработчик слышит «а этот заказ мы ещё не подтвердили, но уже оформили» — и понимает, что «оформлен» и «подтверждён» это **разные** состояния с разными правилами, а не одно «активен». Так из речи эксперта выкристаллизовывается `OrderStatus` с явными переходами.
- **Model exploration whirlpool (водоворот исследования модели).** Процесс не линеен, а закручен: берём конкретный сценарий, проигрываем его на модели, находим место, где модель «не тянет», правим — и снова к сценариям. Множество быстрых итераций вокруг живых примеров, а не большой проект наперёд.
- **Refactoring toward deeper insight (рефакторинг к более глубокому пониманию).** Здесь рефакторят **не код, а модель**. Обычный рефакторинг сохраняет поведение и чистит структуру; этот — меняет **набор понятий**, когда команда вдруг понимает домен точнее: скрытая концепция получает имя и становится явным типом. Технические рефакторинги (переименования, извлечения) — лишь инструмент, которым правку модели вносят в код.
- **Breakthrough (прорыв).** Мелкие улучшения модели накапливаются, а затем случается скачок: разрозненные правки складываются во **внезапную ясность** — вся область вдруг описывается заметно проще и мощнее. Прорыв нельзя запланировать, но к нему ведёт дисциплина непрерывного рефакторинга модели; после него часть старого кода отправляется в переработку — и это нормально.

**Пример «рефакторинга к пониманию».** Сначала правило бесплатной доставки живёт как `if (order.total >= threshold && order.address.isDomestic())` в глубине сервиса. Перемалывая сценарии, команда замечает: у этого `if` есть имя — «политика бесплатной доставки», и оно повторяется в трёх местах с расхождениями. Скрытое понятие делают **явным типом** — `Specification`, — и модель обретает слово, которого в ней не было:

```kotlin
val freeShipping = amountAtLeast(threshold) and shipsDomestically   // правило с именем
if (freeShipping.isSatisfiedBy(order)) { /* … применить бесплатную доставку … */ }
```

Изменилась не строчка кода, а **набор понятий**: в языке появилась «спецификация доставки», в коде — переиспользуемый объект-правило, комбинируемый через `and`/`or`. Это и есть рефакторинг модели, а не кода: технический шаг (извлечь класс) — лишь способ занести в код новое понимание домена.

Сквозной принцип всей части III: **язык и модель — одно целое**. Меняется модель — обязан поменяться Ubiquitous Language (новые понятия получают слова); всплывает новое слово в речи экспертов — это сигнал, что модели не хватает понятия. Рассинхрон языка и кода — первый симптом деградирующей модели.

## 3. Дистилляция: где вкладываться в гибкость

Довести до по-настоящему гибкого дизайна всю систему невозможно и не нужно — это дорого. **Дистилляция (distillation)** отвечает, **куда** вкладывать усилие: она отделяет ценное ядро от всего остального.

- **Core Domain (ядро)** — то, ради чего система существует и в чём компания превосходит конкурентов. Сюда идут лучшие люди и весь бюджет на гибкий дизайн.
- **Generic Subdomains (генерические поддомены)** — необходимое, но не отличающее вас (нотификации, справочники). Их берут готовыми или делают проще некуда — гибкий дизайн им не нужен.
- **Segregated Core (выделенное ядро)** — техника: физически **отделить** код ядра от вспомогательного (в отдельный модуль/пакет), убрав примеси, чтобы самая ценная часть читалась и менялась изолированно и получила максимум внимания.

Отсюда — карта «куда вкладывать гибкость»: усилие на податливость модели распределяют неравномерно, по ценности поддомена.

| Тип поддомена | Вклад в гибкий дизайн | Как реализуют |
|---|---|---|
| **Core Domain** | максимальный | лучшие люди, вылизанная модель, Segregated Core, непрерывный рефакторинг |
| **Supporting Subdomain** | умеренный | своя модель, но без перфекционизма — «достаточно хорошо» |
| **Generic Subdomain** | нулевой | готовое решение, покупка или простой CRUD — моделировать нечего |

Определение и типология поддоменов (Core / Supporting / Generic) — не здесь, а в [STRATEGIC_DESIGN.md](STRATEGIC_DESIGN.md); на этой странице дистилляция важна как **техника фокусировки** гибкого дизайна: вылизывать модель до податливости стоит там, где домен ценен и правила сложны, а не равномерно по всей системе.

## 4. Как это собирается вместе

Три пласта главы отвечают на разные вопросы и работают в связке:

- **Строительные блоки** — *каким* должен стать код: интерфейсы по намерению, запросы без эффектов, явные утверждения, верные контуры, независимые классы, замкнутые операции. Это цель, финальная форма гибкой модели.
- **Процесс** (knowledge crunching → whirlpool → refactoring toward deeper insight → breakthrough) — *как* до этой формы дойти: не проектированием наперёд, а итеративным перемалыванием знаний и рефакторингом самой модели вместе с экспертами.
- **Дистилляция** — *где* прикладывать усилие: вылизывать модель до податливости стоит в Core Domain, а Generic-поддомены брать готовыми.

Общий индикатор здоровья — синхронность языка и кода: пока новое слово экспертов сразу находит место в модели, а рефакторинг модели меняет язык команды, дизайн остаётся гибким. Как только код и разговор о домене расходятся — модель начала костенеть.
