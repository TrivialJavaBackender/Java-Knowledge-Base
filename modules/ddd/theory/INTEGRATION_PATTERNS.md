# Domain-Driven Design — Интеграция контекстов

Контексты автономны: у каждого своя модель и своё хранилище. Как тогда работает сквозной процесс «заказ → оплата → резерв», если ни одна транзакция не может охватить их все? Ответ — набор интеграционных паттернов. Ниже собственная территория DDD (различие двух видов событий, трансляция, доменная рамка итоговой согласованности) раскрыта полно; механика паттернов-инфраструктуры (Outbox, Saga, CQRS, Event Sourcing, Circuit Breaker, idempotency key) описана рамочно и уходит по ссылке к владельцу в модуле `system-design`.

## Domain Event против Integration Event

Это центральное различие интеграции и **собственная территория DDD**.

| | Domain Event | Integration Event |
|---|---|---|
| Аудитория | свой контекст | чужие контексты |
| Назначение | зафиксировать факт внутри модели | опубликовать факт наружу (Published Language) |
| Типы полей | доменные (`Money`, `OrderId`, enum) | примитивы (`String`, `Int`) — сериализуется без сюрпризов |
| Эволюция | свободная, меняем когда захотим | контракт: только обратно совместимо, версия в топике |
| Где определён | `domain/events/` контекста | пакет `*.contracts` + `platform/IntegrationEvent.kt` |
| Идентификатор | не обязателен | `eventId` (для идемпотентности) + `eventVersion` |

Одно и то же случившееся — «заказ оформлен» — существует в двух формах:

```kotlin
// ВНУТРИ контекста — доменное событие, доменные типы, живёт в domain-слое
data class OrderPlaced(
    val orderId: OrderId,
    val customerId: CustomerId,
    val total: Money,
    override val occurredAt: Instant,
) : DomainEvent

// НАРУЖУ — контракт: только примитивы + идентификатор и версия схемы
interface IntegrationEvent {
    val eventId: String       // уникален для СОБЫТИЯ (не сущности) → идемпотентность
    val eventVersion: Int     // несовместимое изменение = новый топик order-placed.v2
}

data class OrderPlacedIntegrationEvent(
    val orderId: String,
    val customerId: String,
    val totalAmount: String,          // Money разобран на две строки —
    val totalCurrency: String,        // получатель не тянет наш класс Money
    val occurredAt: String,
    override val eventId: String = UUID.randomUUID().toString(),
    override val eventVersion: Int = 1,
) : IntegrationEvent
```

### Транслятор — зеркальный близнец ACL

Перевод внутренней формы во внешнюю делает **транслятор**:

```kotlin
class OrderEventsTranslator {
    /** null — событие внутреннее, наружу не выходит. */
    fun toIntegration(event: DomainEvent): Pair<String, IntegrationEvent>? = when (event) {
        is OrderPlaced -> OrderingTopics.ORDER_PLACED to OrderPlacedIntegrationEvent(
            orderId = event.orderId.toString(),
            customerId = event.customerId.value,
            totalAmount = event.total.amount.toPlainString(),   // Money → строки
            totalCurrency = event.total.currency.currencyCode,
            occurredAt = event.occurredAt.toString(),
        )
        is OrderConfirmed -> /* ... */
        else -> null                                            // не всё едет наружу
    }
}
```

Транслятор — зеркальный близнец Anticorruption Layer (ACL). Обе стороны реализуют один принцип: **модель не пересекает границу контекста в сыром виде — на каждой границе стоит переводчик**.

```
              вход                                   выход
   чужая модель ──[ ACL ]──► наши типы     наши типы ──[ транслятор ]──► контракт
   защищает НАС от ЧУЖОЙ модели             защищает ЧУЖИХ от НАШЕЙ модели
   (CatalogAclAdapter: "4990.00 RUB"→Money) (OrderEventsTranslator: Money→строки)
```

Почему нельзя публиковать доменные события напрямую: тогда внутренняя модель де-факто становится контрактом. Любой рефакторинг `Money`, переименование поля или смена типа `OrderId` ломает чужих потребителей. Транслятор разрывает эту связь: внутренняя модель свободна меняться хоть каждый день, а наружу всегда едет стабильный контракт, эволюционирующий отдельно и только совместимо.

## Итоговая согласованность между контекстами

Раз контексты автономны и общей транзакции нет, между ними всегда **итоговая согласованность** (eventual consistency). Это не дефект реализации, а следствие границы: как только факт пересёк границу контекста, получатель узнаёт о нём с задержкой.

Доменная рамка согласованности выстраивается по границам агрегатов и контекстов:

- **внутри одного агрегата** — сильная согласованность: инвариант держится немедленно, в одной транзакции;
- **между агрегатами и между контекстами** — итоговая: согласуется через события.

Та же линия — граница агрегата — задаёт и границу транзакции (см. [AGGREGATE_DESIGN.md](AGGREGATE_DESIGN.md)).

**Цена синхронной интеграции.** Вызвать чужой REST прямо в момент операции просто, но это связывает **доступность**: Billing лёг — заказы не оформляются. Асинхронное событие развязывает: заказ оформляется сразу, оплата случится, когда Billing поднимется. Где синхронный вызов неизбежен (например, актуальная цена из каталога), его на границе оборачивают таймаутом и Circuit Breaker — но домен об этом не знает, это забота адаптера за портом.

> Circuit Breaker (состояния Closed/Open/Half-Open, пороги, реализации) — `../../system-design/theory/microservice_patterns.md`, углублённо — `../../system-design/theory/RELIABILITY_PATTERNS.md`.

## Transactional Outbox — проблема двойной записи

Событие должно пересечь границу контекста. Но «сохранить агрегат в БД» и «отправить событие в брокер» — это **две** системы без общей транзакции (**проблема двойной записи**, dual write). Упали между ними — агрегат сохранён, а событие потеряно навсегда: сага никогда не стартует, контексты молча разошлись.

Почему это критично именно в доменной интеграции: интеграционное событие — единственный канал, которым факт из одного контекста доходит до другого. Потерять событие = потерять сквозной процесс. Значит, доставка события должна быть так же надёжна, как сохранение агрегата.

Механика коротко: событие пишется **в ту же БД, в той же транзакции**, что и агрегат — в таблицу `outbox`; отдельный процесс (relay или CDC) читает outbox и публикует в брокер. В демо это `OutboxOrderRepository` — декоратор, кладущий агрегат и его транслированные события одним `save`:

```kotlin
override fun save(order: Order) {
    delegate.save(order)                       // ─┐
    order.pullEvents().forEach { e ->          //  │ одна «транзакция»:
        translator.toIntegration(e)            //  │ агрегат + события
            ?.let { (topic, ie) -> outbox.add(topic, ie) }
    }                                          // ─┘
}
```

Гарантия — доставка **как минимум один раз** (at-least-once): relay может упасть между публикацией и отметкой «отправлено», поэтому дубли возможны — отсюда следующий раздел.

> Полная механика Outbox (устройство таблицы, фоновый опрос против Debezium/CDC, семантика доставки) — владелец `../../system-design/theory/microservice_patterns.md`, раздел «Outbox Pattern».

## Идемпотентный консьюмер

At-least-once означает: любой обработчик обязан переживать повторную доставку. Два способа защиты, оба видны в демо:

**Дедупликация по идентификатору события.** `WarehouseHandler` помнит обработанные `eventId` и молча пропускает дубль:

```kotlin
if (!processedEventIds.add(request.eventId)) return   // дубль — выходим, ничего не меняя
```

**Проверка шага процесса.** Сага не хранит все `eventId`, а сверяет текущий шаг — повторный `PaymentCompleted` не сдвинет процесс дважды:

```kotlin
if (state.step != SagaStep.AWAITING_PAYMENT) return   // не тот шаг — это дубль
```

В обоих случаях запись «обработано» должна лечь **в той же транзакции**, что и бизнес-изменение, иначе между «зарезервировал» и «запомнил eventId» останется щель.

> idempotency key (клиентский ключ, область действия, хранение, TTL, дедупликация in-flight) — `../../system-design/theory/RELIABILITY_PATTERNS.md`.

## Saga / Process Manager

Сквозной процесс «исполнить заказ» затрагивает три агрегата в трёх контекстах: `Order` (Заказы), `Account` (Счета), `StockItem` (Склад). Обернуть их одной транзакцией нельзя — контексты автономны. **Saga** заменяет распределённую транзакцию **цепочкой локальных**, каждая меняет один агрегат; сбой откатывается не rollback-ом, а **компенсирующим действием** — семантическим обратным шагом (не «отменить списание», а «сделать возврат», причём возврат остаётся в истории).

Доменная рамка: saga — прямое следствие правила «одна транзакция — один агрегат». Раз агрегат есть граница согласованности, процесс над несколькими агрегатами обязан быть многошаговым и итогово согласованным. Saga выносит этот доменный процесс в явную сущность (Process Manager) с хранимым состоянием — по нему всегда видно, где «завис» заказ.

```
успех:   OrderPlaced → PaymentCompleted → StockReserved → Order.confirm()
сбой 1:  PaymentFailed          → Order.cancel(PAYMENT_FAILED)
сбой 2:  StockReservationFailed → refund + Order.cancel(OUT_OF_STOCK)   ← каскад компенсаций
```

Каскад (сбой 2) — самый показательный: деньги уже списаны, резерв упал, система возвращается в согласованность возвратом и отменой, и **оба факта остаются в выписке** Billing.

**Оркестрация против хореографии** (эвристика выбора):

- **Оркестрация** (как в демо): процесс явно описан в одном классе `OrderFulfillmentSaga`, шаги — в хранимом `SagaState`. Всегда видно целиком, где заказ. Цена — центральный координатор.
- **Хореография**: координатора нет, контексты реагируют на события друг друга напрямую (склад сам слушал бы `OrderPlaced`). Проще для 2–3 шагов, но процесс «размазан» — его никто не видит целиком, а компенсации быстро превращаются в клубок.
- Эвристика: линейный короткий поток — хореография; ветвления, компенсации, таймауты — оркестрация.

> Механика Saga (координатор, лог саги, семантика шагов, вариант choreography против orchestration как инфраструктурный паттерн) — владелец `../../system-design/theory/microservice_patterns.md`.

## CQRS — разделение записи и чтения

Один и тот же агрегат `Order` плохо обслуживает две разные задачи:

- **запись**: провести операцию, не нарушив инвариант — нужен агрегат, загруженный целиком, с бизнес-методами;
- **чтение**: показать список «50 заказов с именем клиента и суммой» — агрегат мешает (лишние загрузки, нет плоского представления).

CQRS разделяет их: модель записи (агрегат) и модель чтения (плоская проекция) — разные объекты.

- запись: `PlaceOrderUseCase → Order → OrderRepository`;
- чтение: `OrderQueries → OrderSummaryProjection`, которая строится по событиям, **мимо агрегата и репозитория**.

Доменная рамка: единственная работа агрегата — защищать инварианты на записи. Навешивать на него запросы для экранов — растягивать границу агрегата под чужую задачу. CQRS снимает это давление: проекция читает события и складывает денормализованную витрину, ничего не зная про инварианты.

```kotlin
class OrderSummaryProjection(bus) : OrderQueries {
    private val summaries = LinkedHashMap<String, OrderSummaryDto>()
    // OrderPlaced → status = PLACED; OrderConfirmed → CONFIRMED; OrderCancelled → CANCELLED
    override fun findSummary(id: String): OrderSummaryDto? = summaries[id]
}
```

Уровни внедрения (по возрастанию сложности): (1) одна БД, разные классы чтения и записи — хватает почти всегда; (2) проекции по событиям (как здесь); (3) физически разные хранилища (Postgres для записи + Elasticsearch для чтения).

Цена — итоговая согласованность: пока событие лежит в outbox, витрина отстаёт. Демо показывает это честно: сразу после оформления `findSummary` возвращает пусто, после relay №1 — `PLACED`, после relay №2 — `CONFIRMED`.

> Механика CQRS как паттерна масштабирования (раздельное масштабирование чтения и записи, read replicas, физическое разделение хранилищ) — `../../system-design/theory/microservice_patterns.md`.

## Event Sourcing — состояние как журнал фактов

Обычный агрегат хранит **текущее состояние** (строку `balance = 95010.00`), затирая прошлое при каждом UPDATE. Event-sourced агрегат хранит **историю фактов** («счёт открыт с 100000», «списано 4990»); текущее состояние — свёртка (fold) истории.

Доменная рамка: Event Sourcing — это способ **персистентности агрегата**, а не архитектура всей системы. Агрегат остаётся тем же (границей инвариантов); меняется лишь то, как он сохраняется — вместо строки в таблице журнал событий.

Механика — команда в два такта:

```kotlin
fun withdraw(amount: Money, reason: String) {
    if (balance < amount)                         // 1. КОМАНДА проверяет инвариант
        throw InsufficientFundsException(...)     //    на ТЕКУЩЕМ состоянии
    raise(MoneyWithdrawn(id, amount, reason))     //    → порождает СОБЫТИЕ
}

private fun applyEvent(e: AccountEvent) {         // 2. APPLY меняет состояние
    when (e) {                                    //    ПО событию, БЕЗ проверок
        is MoneyWithdrawn -> balance -= e.amount  //    (факт уже случился)
        /* ... */
    }
}
```

Почему проверка и применение разделены: при восстановлении история проигрывается через `applyEvent` **напрямую, минуя команды** (`replay`). Если бы инвариант проверялся в apply, изменение бизнес-правила «задним числом» ломало бы загрузку старых счетов, которые были законны по правилам своего времени. Событие — свершившийся факт, ему поздно отказывать.

Что это даёт:

- **аудит бесплатно** — журнал фактов и есть история (деньги, юридически значимые операции);
- **путешествие во времени** — баланс на любую дату = replay префикса истории;
- готовые события для CQRS-проекций и интеграции;
- **оптимистичная блокировка по версии потока**: append с `expectedVersion` падает `ConcurrencyException`, если поток уже вырос → перечитать и повторить команду (защита инварианта без пессимистичных локов).

Цена — сложность: версии, снапшоты, миграция схем событий. Поэтому ES — **точечный** инструмент: `Account` — да (история сама по себе ценность), `Order` — нет (хранится обычным способом). Смешивать оба подхода в одной системе нормально.

> Механика Event Sourcing как инфраструктурного паттерна (event store, снапшоты, проекции, связь с CQRS) — владелец `../../system-design/theory/microservice_patterns.md`, раздел «Event Sourcing».

## Сводная картина одного заказа

```
[сценарий] checkout → Order.place() → save
[outbox]     ← OrderPlaced (лежит; витрина ещё не знает)
[relay №1] outbox → шина
[сага]       старт → PaymentRequested ─────────► [счета]  withdraw, append событий (ES)
[сага]       ← PaymentCompleted ◄───────────────  publish
[сага]       → StockReservationRequested ──────► [склад]  проверить всё → reserve (идемпотентно)
[сага]       ← StockReserved ◄──────────────────  publish
[сага]       Order.confirm() → save → outbox ← OrderConfirmed
[relay №2] outbox → шина → [витрина CQRS] CONFIRMED
```

Одна строка процесса задействует все паттерны страницы: Outbox (надёжная публикация), транслятор (домен → контракт), сага (оркестрация с компенсациями), идемпотентный консьюмер (склад), Event Sourcing (счета), CQRS (витрина). Каждый решает свою часть одной задачи — провести факт через границы контекстов, не потеряв его и не связав контексты жёстко.
