# Domain-Driven Design — Архитектура (Hexagonal / Onion / Clean)

У любой «DDD-совместимой» архитектуры одна цель: **все зависимости смотрят внутрь, к домену**. Домен — чистая модель предметной области — не знает ни о базе данных, ни о шине сообщений, ни о веб-фреймворке. Инфраструктура знает о домене; домен об инфраструктуре — никогда.

Зачем: доменная логика — самая ценная и самая долгоживущая часть системы. База, брокер, фреймворк — сменные детали. Если домен зависит от них, каждая смена детали задевает ядро; если наоборот — ядро остаётся нетронутым, а на замену идёт один адаптер. Всё остальное на этой странице выводится из этого единственного правила.

## 1. Hexagonal (Ports & Adapters)

Модель Алистера Кокбёрна: домен — шестиугольник в центре, снаружи — адаптеры, соединённые с ядром через **порты**.

- **Порт** — интерфейс, объявленный доменом или прикладным слоем **на своём языке**. Он выражает потребность («дай цену товара», «сохрани заказ»), не называя технологию.
- **Адаптер** — реализация порта во внешнем кольце. Он говорит с конкретной технологией (HTTP, JDBC, Kafka) и переводит её на язык порта.

```
            ВХОДЫ (driving)                       ВЫХОДЫ (driven)
   REST-контроллеры, потребители,          хранилища, ACL-адаптеры,
   шедулеры (в демо — сценарии App)        шлюзы в шину
              │                                        ▲
              ▼                                        │ реализуют порты
   ┌────────────────────────────────────────────────────────────┐
   │  application    PlaceOrderUseCase, сага, команды/запросы    │
   │  ┌──────────────────────────────────────────────────────┐  │
   │  │  domain      Order, Cart, Value Objects, события,     │  │
   │  │              ПОРТЫ: OrderRepository, ProductPrice-    │  │
   │  │              Provider, PaymentGateway                 │  │
   │  └──────────────────────────────────────────────────────┘  │
   └────────────────────────────────────────────────────────────┘
```

**Driving-адаптеры (входящие)** запускают сценарии: REST-контроллер, потребитель сообщений, шедулер. Они вызывают прикладной слой. **Driven-адаптеры (исходящие)** вызываются доменом через порт и реализуют его.

Конкретное соответствие «порт → адаптер» в контексте «Заказы»:

| Порт (объявлен внутри) | Направление | Адаптер (реализация снаружи) | Что прячет |
|---|---|---|---|
| `OrderRepository` | driven | `OutboxOrderRepository` над `InMemoryOrderRepository` | хранилище + запись событий в outbox |
| `ProductPriceProvider` | driven | `CatalogAclAdapter` | чужой формат каталога |
| `PaymentGateway` / `StockGateway` | driven | `BusPaymentGateway` / `BusStockGateway` | шина сообщений и чужие контракты |
| `OrderQueries` | driven (чтение) | `OrderSummaryProjection` | денормализованная витрина CQRS |

Симметрия важна: домен никогда не импортирует адаптер — ни входящий, ни исходящий. И вызов сценария снаружи, и обращение к хранилищу изнутри проходят через интерфейс, объявленный внутри кольца. Направление зависимости к ядру не нарушается ни на одной границе.

Порты объявляет домен — на своём языке, без единого упоминания технологии:

```kotlin
// domain — ПОРТЫ, объявленные доменом
interface OrderRepository {
    fun findById(id: OrderId): Order?
    fun save(order: Order)                 // сохраняет агрегат целиком, атомарно
}

interface ProductPriceProvider {
    fun currentPrice(productId: ProductId): Money?   // ни слова про HTTP
}
```

Адаптеры реализуют эти порты во внешнем кольце и запирают в себе всю «грязь» технологии:

```kotlin
// infrastructure — АДАПТЕРЫ
class CatalogAclAdapter(
    private val catalog: CatalogApi,       // чужой API каталога
) : ProductPriceProvider                   // перевод "4990.00 RUB" → Money

class OutboxOrderRepository(
    private val delegate: OrderRepository,
    private val outbox: OutboxStore,
    private val translator: OrderEventsTranslator,
) : OrderRepository                         // save агрегата + его события атомарно
```

На границе порта стрелка зависимости **разворачивается**: не домен зависит от адаптера базы, а адаптер базы — от домена (он реализует доменный интерфейс). Это архитектурное применение инверсии зависимостей (принцип DIP из SOLID).

## 2. Onion и Clean Architecture — три имени одной идеи

| Название | Автор | Центр | Внешнее кольцо | Механизм границы |
|---|---|---|---|---|
| Hexagonal (Ports & Adapters) | Cockburn | домен | адаптеры | порт-интерфейс |
| Onion | Palermo | доменная модель + доменные сервисы | инфраструктура / UI | инверсия зависимостей |
| Clean Architecture | Martin | entities + use cases | frameworks & drivers | Dependency Rule |

Все три говорят одно: зависимости направлены только внутрь; пересечение границы к ядру — всегда через интерфейс, объявленный **внутри**. Отличаются терминология и число колец, идея — нет. Выбирать можно любую; в этом модуле используется словарь Hexagonal (порт / адаптер) как самый операциональный.

## 3. Классическая слоёнка против инверсии

Классическая слоёная архитектура: `UI → Service → Domain → DAO → БД`. Стрелки — зависимости по компиляции; домен **зависит** от слоя доступа к данным, а тот — от драйвера БД. Поменяли хранилище — поменяли то, на что смотрит домен.

Инверсия разворачивает нижнюю стрелку. Интерфейс `OrderRepository` физически лежит в модуле `domain`, а его реализация — в `infrastructure`:

```
Слоёнка:   Domain ───────────────► DAO ──► БД        (домен зависит от БД)
Инверсия:  Domain ◄──реализует──── Adapter ──► БД     (адаптер зависит от домена)
             △ объявляет OrderRepository
```

Программно это одно ключевое решение — **где живёт интерфейс**. Всё остальное (Hexagonal / Onion / Clean) — обвязка вокруг него.

## 4. Граница, защищённая сборкой

Правило «домен чистый» держится не на дисциплине программиста, а на инструменте. Три уровня строгости:

1. **Модуль сборки без лишних зависимостей** (самый жёсткий). Весь список зависимостей доменного модуля:
   ```kotlin
   // ordering/domain/build.gradle.kts
   dependencies {
       implementation(project(":shared-kernel"))   // и всё
   }
   ```
   Импортировать в домен шину или каталог физически нельзя — не соберётся. Проверить границу можно и вручную — в домене нет ни одного упоминания инфраструктуры:
   ```bash
   grep -rn "platform\|infrastructure\|catalog" ordering/domain/src/main --include="*.kt"
   # (пусто)
   ```

2. **ArchUnit** — тест-правило «пакет `..domain..` не зависит от `..infrastructure..`» для монолита без модульной границы (место таких архитектурных тестов в пирамиде — `../../software-engineering/theory/TESTING.md`).

3. **Конвенция пакетов** — самый слабый уровень: держится на код-ревью.

Следствие для тестов: тесты домена не содержат ни одного мока инфраструктуры — инварианты проверяются на чистых объектах. Это самые быстрые и самые ценные тесты системы (основание пирамиды тестирования).

## 5. Composition Root

Где-то реализации портов всё-таки должны встретиться с доменом. Это место — **Composition Root**, единственная точка, где выбираются конкретные адаптеры и всё связывается воедино. В демо это `app/DemoApp.kt` — обычные конструкторы, без DI-фреймворка:

```kotlin
// порт ProductPriceProvider ← ACL-адаптер к чужому Published Language
val priceProvider = CatalogAclAdapter(catalog)

// порт OrderRepository ← хранилище в памяти, обёрнутое Outbox-декоратором
val orders: OrderRepository =
    OutboxOrderRepository(InMemoryOrderRepository(), outbox, OrderEventsTranslator())

val placeOrder = PlaceOrderUseCase(orders, priceProvider)
```

Ручная сборка читается **как карта архитектуры**: видно каждый порт и подставленный ему адаптер; видно, что домена здесь нет вообще — конструируются только адаптеры и сценарии. DI-контейнер (Spring, Koin) автоматизирует ровно эту сборку — но принцип «зависимости приходят снаружи» от контейнера не зависит.

Важно не путать два разных понятия:

- **Внедрение зависимостей** (Dependency Injection, DI) — техника: объект получает свои зависимости снаружи, а не создаёт сам.
- **Инверсия зависимостей** (Dependency Inversion) — архитектурное правило: зависеть от абстракций, а направление зависимости к ядру задаётся интерфейсом внутри ядра.

DI — способ доставки, инверсия — направление стрелки. Composition Root применяет оба сразу.

## 6. Насколько тяжёлой делать архитектуру

Полная гексагональная разбивка **каждого** контекста — избыточное проектирование (оверинжиниринг). Инвестиция в архитектуру должна быть пропорциональна ценности поддомена (Core / Supporting / Generic — см. [STRATEGIC_DESIGN.md](STRATEGIC_DESIGN.md)):

| Контекст | Разбивка | Почему |
|---|---|---|
| `ordering` | 3 модуля (domain / application / infrastructure) | Core Domain: сложные инварианты, сага |
| `billing` | 1 модуль, слои пакетами | сложная механика (Event Sourcing), малый объём |
| `warehouse` | 1 модуль | Supporting: один агрегат, один обработчик |
| `catalog` | 1 модуль | почти справочник (Generic) |

Правило: сложность решения не должна превышать сложность задачи.

## 7. DDD и микросервисы

DDD и микросервисы — независимые идеи, которые хорошо сочетаются: DDD даёт **стратегию декомпозиции**, микросервисы — один из способов её физического воплощения.

**Bounded Context ↔ граница сервиса.** Ключевое соответствие: граница сервиса должна проходить по границе Bounded Context, а не поперёк неё.

- Один BC = один сервис — типовой случай.
- Один BC = несколько сервисов — допустимо (контекст большой, внутри — своя декомпозиция).
- Один сервис на два BC — **антипаттерн**: сервис наследует спутанность двух моделей и теряет автономию.

BC — логическая граница модели; сервис — физическая граница развёртывания. Сначала находят контексты (Event Storming, Context Map — см. [STRATEGIC_DESIGN.md](STRATEGIC_DESIGN.md)), и только потом решают, резать ли их на отдельные процессы.

**Своя база на каждый сервис (database-per-service).** Прямое следствие автономии контекста: у каждого сервиса своё хранилище, чужую таблицу никто не читает напрямую — только через опубликованный контракт. Общая БД на два сервиса возвращает связанность, которую разрезали по коду, — теперь через схему данных.

**Модульный монолит — валидная альтернатива.** Микросервисы не обязательны. Модульный монолит хранит те же границы контекстов как модули сборки в одном процессе (ровно как это демо): та же дисциплина зависимостей, но без сетевых вызовов, распределённых транзакций и эксплуатационной цены. Разумный дефолт — начать с модульного монолита с чёткими границами BC и выделять сервис только там, где нужна независимая масштабируемость или независимое развёртывание. Границы, поставленные по DDD, делают позднее выделение дешёвым.

> Механику микросервисной декомпозиции — database-per-service, API Gateway, Service Discovery, размер сервиса, синхронная против асинхронной связи — держит модуль `../../microservices/` (см. `DECOMPOSITION.md`, `DATA_OWNERSHIP.md`, `EDGE_AND_MESH.md`). Здесь дана только **доменная рамка**: где проводить границу и почему по контексту.
