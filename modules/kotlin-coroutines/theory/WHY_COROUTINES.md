# Зачем нужны корутины

> **Какую проблему решают.** Асинхронный код, который читается как обычный последовательный, но не
> занимает поток на время ожидания.
> **Кому это надо.** Тому, кто пишет сервис, где на один входящий запрос приходится несколько
> сетевых вызовов или обращений к БД, и кто уже сталкивался с колбеками, `CompletableFuture` или
> «нам не хватает потоков в пуле».
> **Когда НЕ надо.** Один блокирующий вызов на запрос, простой CRUD, чисто вычислительная задача —
> см. §7.

Этот файл — не про API. Он про то, откуда корутины взялись и какую именно боль убирают. Механику
(«что генерирует компилятор», «кто возобновляет») разбирает [`SUSPEND_INTERNALS.md`](SUSPEND_INTERNALS.md),
а конкретные билдеры — [`BASICS.md`](BASICS.md).

---

## Сквозная задача

Через весь этот файл (и дальше — через [`INTEROP.md`](INTEROP.md)) идёт одна задача:

> Собрать страницу профиля. Нужны три независимых источника: профиль пользователя, его заказы и
> рекомендации. Каждый вызов идёт по сети и занимает ~300 мс.

Ниже она решается четырьмя способами. Важно смотреть не на то, «какой код короче», а на то,
**что происходит с потоком** во время этих 300 мс и **что будет, когда что-то пойдёт не так**.

---

## 1. Мир первый: поток на запрос

Самый простой и до сих пор самый распространённый способ.

```kotlin
fun buildPage(userId: Long): Page {
    val profile = api.loadProfile(userId)          // блокируемся на 300 мс
    val orders = api.loadOrders(userId)            // ещё 300 мс
    val recommendations = api.loadRecommendations(userId)  // ещё 300 мс
    return Page(profile, orders, recommendations)
}
```

Читается идеально: сверху вниз, `try/catch` работает, отладчик работает, стектрейс полный.

### Где ломается

**Проблема первая — цена ожидания.** Метод выполняется 900 мс, из которых ~900 мс поток **ничего не
делает**: он стоит в `SocketInputStream.read` и ждёт байты. Всё это время поток занят и недоступен
другим запросам.

**Проблема вторая — арифметика.** Поток платформы JVM резервирует стек (`-Xss`, по умолчанию около
1 МБ на 64-битных JVM) и является объектом ядра ОС. Чтобы обслужить 1000 одновременных запросов по
этой модели, нужно 1000 потоков — это порядка гигабайта только под стеки плюс планировщик ОС,
который вынужден перекладывать эти потоки между ядрами. Отсюда классическое «увеличили пул до 500,
стало хуже»: переключений контекста стало больше, полезной работы — нет.

**Проблема третья — нет параллельности там, где она бесплатна.** Три вызова независимы, но идут
последовательно: 900 мс вместо 300.

> Ограничение здесь не в Kotlin, а в модели «одна задача = один поток ОС». JDK 21 атакует ту же
> проблему с другой стороны — виртуальными потоками, см.
> [`concurrency/theory/VIRTUAL_THREADS.md`](../../concurrency/theory/VIRTUAL_THREADS.md) и §7 ниже.

## 2. Мир второй: колбеки

Раз ожидание — это простой, давайте не ждать. Отдадим библиотеке функцию, которую она вызовет,
когда данные приедут.

```kotlin
fun buildPage(userId: Long, onDone: (Page) -> Unit, onError: (Throwable) -> Unit) {
    api.loadProfile(userId, { profile ->
        api.loadOrders(userId, { orders ->
            api.loadRecommendations(userId, { recs ->
                onDone(Page(profile, orders, recs))
            }, onError)
        }, onError)
    }, onError)
}
```

Поток теперь свободен: `loadProfile` только регистрирует колбек и сразу возвращает управление.
Проблема первая решена. Взамен появились пять новых.

**1. Инверсия управления.** Код перестал читаться сверху вниз. То, что должно произойти последним,
записано глубже всего. Три вызова дали три уровня вложенности; реальный обработчик с ветвлениями,
циклом по списку и парой условий превращается в «пирамиду», где отступ важнее логики.

**2. `try/catch` не работает.**

```kotlin
try {
    api.loadProfile(userId, { … }, { … })
} catch (e: IOException) {
    // сюда никогда ничего не прилетит
}
```

`loadProfile` вернулась мгновенно и без ошибки. Настоящая ошибка случится через 300 мс **в другом
потоке** — в потоке HTTP-клиента. Обычный механизм исключений языка перестал работать: ошибку
приходится передавать вручную, отдельным параметром `onError`, и вручную же протаскивать через все
уровни (обратите внимание, как `onError` дублируется в примере выше).

**3. Отмена — вручную.** Клиент закрыл вкладку — надо прекратить три вызова. Значит, каждый вызов
должен вернуть какой-то `Cancellable`, эти хендлы надо где-то хранить, не забыть отменить все, и
при этом не вызвать `onDone` после отмены.

**4. Композиция.** «Сделать три вызова параллельно и дождаться всех трёх» на колбеках — это счётчик,
общий мутабельный контейнер результатов и синхронизация вокруг них. То, что в последовательном коде
делает `val a = …; val b = …`, здесь превращается в отдельный примитив.

**5. Диагностика.** Стектрейс ошибки показывает поток HTTP-клиента и ничего не говорит о том, какой
запрос это был и что происходило до.

Это и есть «callback hell»: проблема не в отступах, а в том, что **выключились штатные средства
языка** — возврат значения, исключения, `try/finally`, `for`.

## 3. Мир третий: futures

`CompletableFuture` возвращает композицию: вместо передачи колбека внутрь мы получаем объект-обещание
и строим из обещаний цепочку.

```kotlin
fun buildPage(userId: Long): CompletableFuture<Page> {
    val profile = api.loadProfileAsync(userId)
    val orders = api.loadOrdersAsync(userId)
    val recs = api.loadRecommendationsAsync(userId)
    return profile.thenCombine(orders, ::Pair)
        .thenCombine(recs) { (p, o), r -> Page(p, o, r) }
        .exceptionally { e -> Page.fallback(e) }
}
```

Стало заметно лучше: пирамида выпрямилась в цепочку, три вызова идут параллельно (300 мс вместо
900), ошибки обрабатываются в одном месте (`exceptionally`), а не в каждом колбеке.

### Что осталось

**Код всё ещё не обычный.** Условие «если у пользователя нет заказов — не грузить рекомендации»
в последовательном коде это `if`. В цепочке это `thenCompose` с вложенной цепочкой внутри.

**Типы текут наружу.** Как только внутри цепочки появляется коллекция асинхронных вызовов, тип
становится `CompletableFuture<List<CompletableFuture<Item>>>`, и его надо разворачивать вручную
(`allOf` + повторный обход). Сигнатура функции перестаёт описывать смысл и начинает описывать
механику.

**Соблазн заблокироваться.** Любой `.join()`/`.get()` в середине цепочки возвращает нас в мир
первый, причём незаметно для читающего.

**Отмена не сквозная.** `future.cancel(true)` не отменяет вызовы, которые уже стартовали внутри
цепочки: `CompletableFuture` не знает, кто её порождает.

**Стектрейсы.** Ошибка приходит завёрнутой в `CompletionException`, а трейс показывает поток пула,
а не место, где цепочку собрали.

> Полный разбор самого API `CompletableFuture` — в
> [`concurrency/theory/EXECUTORS_FUTURES.md`](../../concurrency/theory/EXECUTORS_FUTURES.md).
> Как стыковать его с корутинами — в [`INTEROP.md`](INTEROP.md).

## 4. Мир четвёртый: suspend

```kotlin
suspend fun buildPage(userId: Long): Page = coroutineScope {
    val profile = async { api.loadProfile(userId) }
    val orders = async { api.loadOrders(userId) }
    val recs = async { api.loadRecommendations(userId) }
    Page(profile.await(), orders.await(), recs.await())
}
```

Сравните с миром первым: та же структура, те же локальные переменные, тот же `return`. При этом:

- три вызова идут параллельно — 300 мс;
- поток на время ожидания свободен, как в мире втором;
- `try/catch` вокруг `buildPage` ловит ошибку любого из трёх вызовов;
- если упал один вызов — два других **автоматически отменяются** (это делает `coroutineScope`);
- если отменили того, кто вызвал `buildPage`, — отменятся все три вызова.

### Главный тезис

**Корутина — это не «лёгкий поток». Это мир второй, в котором колбек пишет компилятор.**

`suspend`-функция буквально компилируется в функцию с дополнительным параметром-колбеком
(`Continuation`) и телом-автоматом. То, что в §2 писали руками — сохранение «что делать дальше»,
передача результата, передача ошибки — генерируется. Отсюда и «поток не блокируется»: механизм тот
же, что у колбеков, просто он спрятан.

Это не метафора: [`SUSPEND_INTERNALS.md`](SUSPEND_INTERNALS.md) показывает сгенерированную
сигнатуру через `javap` на коде из этого же модуля.

## 5. Четыре стиля рядом

| | Поток на запрос | Колбеки | `CompletableFuture` | Корутины |
|---|---|---|---|---|
| Читается сверху вниз | да | нет | частично | да |
| Поток занят на время ожидания | **да** | нет | нет | нет |
| Штатный `try/catch` | да | **нет** | нет (`exceptionally`) | да |
| `try/finally` для очистки | да | вручную | вручную | да |
| Параллельный запуск нескольких | новый поток | счётчик вручную | `allOf`/`thenCombine` | `async` + `await` |
| Отмена | `interrupt`, частично | вручную | не сквозная | встроенная, по дереву |
| Ошибка «потеряется» | нет | легко | легко (забыть `exceptionally`) | нет (structured concurrency) |
| Цена одной задачи | ~1 МБ стека | объект колбека | объект future | объект-продолжение, сотни байт |

## 6. Что корутины дают сверх «колбеков от компилятора»

Если бы дело было только в синтаксисе, хватило бы `async/await` как в некоторых других языках.
Библиотека `kotlinx.coroutines` добавляет три вещи, которых у колбеков нет в принципе:

1. **Структурная конкурентность.** У каждой корутины есть родитель. Родитель не завершится, пока не
   завершатся дети; отмена и ошибки ходят по дереву. Это означает: не бывает «осиротевшей» фоновой
   задачи, которую никто не ждёт и никто не отменит. Разбор —
   [`STRUCTURED_CONCURRENCY.md`](STRUCTURED_CONCURRENCY.md).
2. **Кооперативная отмена как часть модели.** Отмена — не «убить поток», а сообщение «результат
   больше не нужен», которое доставляется в точках приостановки. Разбор —
   [`CANCELLATION_EXCEPTIONS.md`](CANCELLATION_EXCEPTIONS.md).
3. **Потоки данных.** Одно значение — `suspend fun`; много значений во времени с преобразованиями и
   обратным давлением (backpressure) — `Flow`. Разбор — [`FLOW.md`](FLOW.md).

## 7. Когда корутины НЕ нужны

Честный критерий. Корутины дают выигрыш там, где **много одновременных ожиданий**. Если этого нет,
они добавляют сложность без выгоды.

| Ситуация | Что делать |
|---|---|
| Один блокирующий вызов на запрос, нагрузка не упирается в пул потоков | оставить блокирующий код |
| Простой CRUD-сервис на Spring MVC + JDBC | оставить как есть; на JDK 21 включить виртуальные потоки — блокировка станет дешёвой без переписывания |
| Чистая вычислительная задача (парсинг, сжатие, расчёт) | обычный пул/`parallelStream`; приостанавливаться не на чем |
| Скрипт, миграция, разовая утилита | блокирующий код проще и отлаживается лучше |
| Нужны миллионы одновременных ожиданий, потоки данных, отмена по дереву | корутины |

Отдельно: **корутины и виртуальные потоки не конкуренты**. Виртуальные потоки делают дешёвой
блокировку; корутины дают структурную конкурентность, отмену и `Flow`. Рабочая комбинация — корутины
как модель конкурентности плюс диспетчер на виртуальных потоках как исполнитель блокирующих вызовов
(см. [`DISPATCHERS.md`](DISPATCHERS.md)).

### Чего корутины не делают

`suspend` **не превращает блокирующий вызов в неблокирующий**. Вот это по-прежнему занимает поток
целиком:

```kotlin
suspend fun bad(): ByteArray {
    Thread.sleep(1000)                 // блокирует
    return File("/tmp/x").readBytes()  // блокирует
}
```

Приостановка возможна только там, где вызываемый код умеет отдать своё продолжение. Для честно
блокирующих API есть `Dispatchers.IO` (пул потоков, которые не жалко заблокировать) и
`runInterruptible` — см. [`INTEROP.md`](INTEROP.md).

## 8. Как мигрировать существующий код

Типичная ошибка — «пометим всё `suspend`». Это ломает сборку веером: `suspend` заразен вверх по
стеку вызовов, и одно изменение тянет за собой контроллеры, тесты и Java-код.

Рабочая стратегия — **с краёв внутрь**:

1. **Найти границу.** Обычно это HTTP-обработчик, consumer очереди или планировщик — место, где
   начинается операция и где есть естественный владелец жизненного цикла.
2. **Поставить адаптер на границе, не трогая середину.** Наружу в Java/фреймворк отдаём
   `CompletableFuture` через `scope.future { … }`; внутрь затягиваем существующие асинхронные API
   через `await()` / `suspendCancellableCoroutine`. Оба моста — в [`INTEROP.md`](INTEROP.md).
3. **Переводить по одному слою**, начиная с того, где реально есть параллельные вызовы. Слои без
   ожиданий не трогать вообще.
4. **Блокирующие вызовы не переписывать**, а завернуть: `withContext(io) { runInterruptible { … } }`.
5. **Диспетчер — параметром конструктора** с самого начала, иначе новый код сразу станет
   нетестируемым (см. [`TESTING_INTEROP.md`](TESTING_INTEROP.md)).

Признак, что миграция идёт правильно: количество `runBlocking` в продакшен-коде не растёт. Каждый
`runBlocking` вне `main` и тестов — это возврат в мир первый, спрятанный от вызывающего.

## Шпаргалка

- Поток на запрос: просто, но поток занят ожиданием и стоит ~1 МБ; потолок — тысячи.
- Колбеки: поток свободен, но выключаются `try/catch`, `finally`, композиция и отмена.
- Futures: цепочки вместо пирамиды, но типы текут, отмена не сквозная, легко заблокироваться `join()`.
- Корутины: код как последовательный, поток свободен, плюс структурная конкурентность, отмена и `Flow`.
- **Корутина — это колбек, сгенерированный компилятором**, а не «лёгкий поток».
- `suspend` не делает блокирующий вызов неблокирующим.
- Нет множественных одновременных ожиданий — корутины не нужны.
- Мигрировать с краёв внутрь, через адаптеры, а не «пометим всё `suspend`».
