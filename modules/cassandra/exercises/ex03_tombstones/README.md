# Ex03 — Tombstone: воспроизвести, измерить, устранить

## Условие

Статусы заказов чистятся ночным заданием: строки со статусом `CANCELLED` старше 30 дней
удаляются запросом на удаление по ключу партиции и диапазону кластеризации.

Через несколько недель разработчики жалуются: чтение «последние 20 заказов пользователя»
у части пользователей стало отвечать по 300–800 мс вместо 5 мс, а в логах кластера появились
предупреждения о превышении порога.

## Задание

1. Воспроизведи проблему на живом кластере: создай таблицу, вставь заказы одного пользователя,
   удали часть из них и добейся того, чтобы **чтение 20 строк читало значительно больше ячеек,
   чем возвращает**. Шаги запиши в `repro.cql`.
2. Измерь эффект. Приложи в `analysis.md` настоящий вывод: трассировку запроса и статистику
   таблицы. Придуманные цифры не принимаются.
3. Объясни, почему после `nodetool flush` и принудительной компактизации tombstone могут
   никуда не деться.
4. Предложи два разных решения задачи «чистить отменённые заказы» — и назови, чем платит каждое.

## Критерии приёмки

- [ ] В трассировке видно число прочитанных tombstone — приложен реальный вывод.
- [ ] Названы оба порога кластера (предупреждение и отказ) и откуда взяты их значения.
- [ ] Объяснена роль `gc_grace_seconds` и связь с ремонтом кластера.
- [ ] Названо, при каком условии удалённые данные могут «воскреснуть».
- [ ] Для каждого из двух решений сказано, что именно оно ухудшает.

## Проверка

```bash
docker exec -i cass cqlsh < repro.cql
docker exec cass nodetool tablestats marketplace.orders_by_user | grep -i tombstone
docker exec cass cqlsh -e "TRACING ON; SELECT ... ;"
```
