# Ex01 — История заказов маркетплейса

## Условие

Проектируешь хранение заказов. Нагрузка: 50 млн пользователей, пик 20 тыс. записей в секунду,
средний пользователь делает 30 заказов за всё время жизни аккаунта, активный продавец —
до 500 заказов в сутки.

Приложение обязано обслуживать ровно три запроса:

1. **Последние 20 заказов пользователя** — от новых к старым, с постраничным продолжением.
2. **Заказ по идентификатору** — `order_id` известен из письма или ссылки поддержки.
3. **Заказы продавца за календарный день** — для отчёта в личном кабинете продавца.

Заказ содержит: `order_id`, `user_id`, `seller_id`, `created_at`, `status`, `total_amount`,
`currency`, список позиций (артикул, количество, цена).

## Задание

Заполни `schema.cql`: keyspace, таблицы и запросы под все три сценария.

## Критерии приёмки

- [ ] Ни один из трёх запросов не требует `ALLOW FILTERING` — проверь буквально, выполнив их.
- [ ] Запрос 1 возвращает данные в нужном порядке **без** `ORDER BY` в самом запросе.
- [ ] Позиции заказа хранятся так, что чтение одного заказа — одна партиция.
- [ ] Для каждой таблицы написано в комментарии: что является ключом партиции, сколько строк
      в партиции ожидается на горизонте года и почему это приемлемо.
- [ ] Объяснено, что происходит при записи заказа, если приложение упало между вставками
      в разные таблицы.

## Проверка

```bash
docker exec -i cass cqlsh < schema.cql
docker exec cass cqlsh -e "DESCRIBE KEYSPACE marketplace;"
```
