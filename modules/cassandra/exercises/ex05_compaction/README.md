# Ex05 — Выбор стратегии компактизации

## Условие

В маркетплейсе три таблицы с принципиально разным профилем нагрузки:

1. **`orders_by_user`** — заказы пользователя. Запись один раз, изменение статуса 3–5 раз
   в течение недели после создания, чтение постоянное, хранение бессрочное.
2. **`order_events`** — журнал событий заказа для отладки. Только вставка, чтение редкое
   (расследование инцидента), хранение 30 дней, затем данные не нужны.
3. **`seller_daily_stats`** — агрегаты продавца за день. Полная перезапись строки при каждом
   пересчёте (до 100 раз в сутки на строку), чтение частое, хранение год.

## Задание

Для каждой таблицы выбери стратегию компактизации и запиши решение в `decisions.md`,
а схему — в `schema.cql`.

## Критерии приёмки

- [ ] Для каждой таблицы названа стратегия и **какой именно вид амплификации** она ухудшает
      ради какого улучшения.
- [ ] Для таблицы с ограниченным сроком хранения объяснено, почему удаление данных получается
      почти бесплатным, и какое условие обязано выполняться, чтобы это работало.
- [ ] Названо, что случится с таблицей 3, если выбрать стратегию по умолчанию.
- [ ] Указано, как проверить, что выбор оказался верным — какие метрики смотреть.
- [ ] Если для какой-то таблицы подходит унифицированная стратегия из Cassandra 5.0 —
      объяснено, чем она заменяет классический выбор.

## Проверка

```bash
docker exec -i cass cqlsh < schema.cql
docker exec cass nodetool compactionstats
docker exec cass cqlsh -e "SELECT table_name, compaction FROM system_schema.tables WHERE keyspace_name='marketplace';"
```
