# Модель данных: первичный ключ и всё, что из него следует

> **Какую проблему решает.** В [`WHY_CASSANDRA.md`](WHY_CASSANDRA.md) §3 показано, что у таблицы есть
> ровно один дешёвый путь доступа. Здесь разбирается, из чего этот путь состоит: почему `PRIMARY KEY
> ((user_id, order_month), order_id)` — три разных решения в одной строке, и что ломается при
> перестановке любого из них.
> **Кому это надо.** Тому, кто пишет `CREATE TABLE`: после первой записи изменить ключ нельзя, только
> создать новую таблицу и переложить данные.
> **Когда НЕ надо.** Читать этот файл как справочник по типам не стоит: коллекции, UDT и счётчики
> разобраны здесь только там, где у них есть цена в хранении (§6–§8). Полный перечень операций над
> ними — в документации CQL, и он вам почти не понадобится.

**Что рядом.** Как из трёх запросов маркетплейса получается набор таблиц и что делать с растущей
партицией — [`QUERY_FIRST_DESIGN.md`](QUERY_FIRST_DESIGN.md). Как ключ партиции превращается в токен и
кому этот токен принадлежит — [`CLUSTER_TOPOLOGY.md`](CLUSTER_TOPOLOGY.md) §1. Что происходит с
записью физически и почему удаление — тоже запись — [`WRITE_READ_PATH.md`](WRITE_READ_PATH.md) §1, §4.

Прогоны выполнены на кластере в контейнере, Apache Cassandra 5.0.9; выводы в блоках — реальные.
Дальше первого раза команда сокращена до `cqlsh …` вместо `docker exec cass-theory cqlsh …`.
Схема сквозного примера:

```cql
CREATE TABLE theory_dm.orders_by_user (
  user_id uuid, order_month text, order_id timeuuid,
  seller_id uuid, status text, total decimal,
  PRIMARY KEY ((user_id, order_month), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
```

---

## 1. Первичный ключ: партиция решает «где», кластеризация — «в каком порядке»

**Задача.** «Последние 20 заказов пользователя». В ключе три поля — где ставить внутренние скобки?

**Наивное решение.** Не ставить вовсе: `PRIMARY KEY (user_id, order_month, order_id)`.

**Где ломается.** Внутренние скобки не косметика — они делят ключ на две части с разным смыслом. Без
них ключ партиции равен одному `user_id`: все заказы пользователя за всю жизнь попадают в одну
партицию, которая растёт без потолка (§4). Противоположная ошибка — `PRIMARY KEY ((user_id,
order_month, order_id))`: партиций становится столько же, сколько заказов, и запрос «последние 20»
превращается в 20 обращений по разным ключам вместо одного.

**Механизм.** Ключ партиции определяет, *где* лежит строка, ключ кластеризации — *в каком порядке*
внутри уже найденного места. Первое видно по токену: у двух заказов одного месяца он совпадает, у
заказа соседнего месяца — другой.

```
$ docker exec cass-theory cqlsh -e "SELECT token(user_id, order_month) AS tok, order_month, order_id FROM theory_dm.orders_by_user;"

 tok                  | order_month | order_id
----------------------+-------------+--------------------------------------
 -1701293370827722341 |     2026-10 | 30000000-0000-1000-8000-000000000003
  4171329810690023163 |     2026-09 | 20000000-0000-1000-8000-000000000002
  4171329810690023163 |     2026-09 | 10000000-0000-1000-8000-000000000001
```

Отсюда же требование давать ключ партиции целиком: по половине его токен не считается, а значит,
неизвестно, кого спрашивать.

```
$ docker exec cass-theory cqlsh -e "SELECT order_id FROM theory_dm.orders_by_user WHERE user_id = 11111111-1111-1111-1111-111111111111;"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this
query as it might involve data filtering and thus may have unpredictable performance. …"
```

Второе — порядок — видно по тому, что строки в выводе идут `20000000…` перед `10000000…`, хотя
`ORDER BY` в запросе нет: это `CLUSTERING ORDER BY (order_id DESC)` из схемы (§3).

**Правило.** Внутренняя скобка — граница между «на каком узле» и «в каком порядке». По ней же проходит
граница атомарности и изоляции ([`WHY_CASSANDRA.md`](WHY_CASSANDRA.md) §4), и передвинуть её после
первой записи нельзя — только создать другую таблицу и переложить данные.

## 2. Составной ключ партиции: группа полей хешируется как одно целое

**Задача.** У оптового покупателя тысяча заказов в месяц. Партиция по одному `user_id` растёт всю
жизнь аккаунта и остановиться ей нечем.

**Механизм.** Второе поле в скобках не создаёт «вложенных» партиций: хешируется вся группа целиком,
поэтому `(user_id, '2026-09')` и `(user_id, '2026-10')` — два независимых ключа с разными токенами
(вывод в §1). Партиция снова становится ограниченной: её размер задаётся не сроком жизни аккаунта, а
шириной окна.

**Цена.** Ключ вычисляется хешем, а хеш не сохраняет порядок — значит, диапазон по месяцу невозможен
в принципе, месяцы можно только перечислить:

```
$ cqlsh -e "SELECT order_id FROM theory_dm.orders_by_user
            WHERE user_id = 11111111-1111-1111-1111-111111111111 AND order_month > '2026-08';"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this
query as it might involve data filtering and thus may have unpredictable performance. …"

$ cqlsh -e "SELECT order_month, order_id FROM theory_dm.orders_by_user
            WHERE user_id = 11111111-1111-1111-1111-111111111111 AND order_month IN ('2026-09','2026-10');"

 order_month | order_id
-------------+--------------------------------------
     2026-09 | 20000000-0000-1000-8000-000000000002
     2026-09 | 10000000-0000-1000-8000-000000000001
     2026-10 | 30000000-0000-1000-8000-000000000003
```

Отсюда два следствия для приложения: «за последний год» — это двенадцать ключей, а не один запрос, и
порядок гарантирован только внутри партиции, поэтому склеивать результат придётся на клиенте. Как
выбирать ширину окна и что делать, когда даже месяц оказывается слишком широк, — приём бакетирования
в [`QUERY_FIRST_DESIGN.md`](QUERY_FIRST_DESIGN.md) §3.

**Правило.** Добавляя поле в ключ партиции, вы меняете неограниченный рост на фиксированное число
запросов. Размен выгоден, пока это число известно заранее и мало.

## 3. `CLUSTERING ORDER BY`: физический порядок на диске, а не сортировка на лету

**Задача.** Показать заказы пользователя, отсортированные по сумме, — «сначала самые дорогие».

**Наивное решение.** `ORDER BY total DESC`. В РСУБД это стоило бы одной строки в запросе.

**Где ломается.** Сервер отказывает, и формулировка отказа объясняет причину лучше любого пересказа:

```
$ cqlsh -e "SELECT order_id, total FROM theory_dm.orders_by_user
            WHERE user_id = 11111111-1111-1111-1111-111111111111 AND order_month = '2026-09' ORDER BY total;"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Order by is
currently only supported on the clustered columns of the PRIMARY KEY, got total"

$ cqlsh -e "SELECT order_id FROM theory_dm.orders_by_user ORDER BY order_id ASC;"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="ORDER BY is only
supported when the partition key is restricted by an EQ or an IN."
```

**Механизм.** `CLUSTERING ORDER BY` — не указание, как сортировать при выдаче, а объявление, в каком
порядке строки лежат в SSTable. Чтение партиции — это проход по уже упорядоченному участку, поэтому
разрешены ровно два направления: то, что записано, и обратное ему (`ORDER BY order_id ASC` на нашей
`DESC`-таблице проходит). Любая другая колонка потребовала бы собрать партицию в память и отсортировать
— то есть операции, которой на пути чтения нет. Вторая ошибка — та же мысль с другой стороны: пока
партиция не локализована, сортировать просто нечего, потому что глобального порядка между партициями
не существует.

Направление тоже фиксируется навсегда: `ALTER TABLE … WITH CLUSTERING ORDER BY` не парсится — такой
формы в грамматике нет.

**Правило.** Выбирайте направление под главный запрос, а не «по возрастанию, как привычно». Для
«последних 20 заказов» это `DESC` — тогда нужные строки лежат в начале партиции, а `LIMIT 20`
останавливает чтение сразу.

## 4. Wide row: где на самом деле предел партиции

**Задача.** Сколько заказов можно держать в одной партиции — есть ли жёсткий предел?

**Наивный ответ.** Есть, и он огромен: «Cassandra's hard limit is 2 billion cells per partition»
(Apache Cassandra 5.0, Data Modeling / Evaluating and Refining) — значит, можно не думать.

**Где ломается.** Посчитаем, что такое 2 млрд ячеек в наших единицах. Размер партиции меряется
ячейками по формуле с той же страницы: `Nv = Nr (Nc − Npk − Ns) + Ns`; у `orders_by_user` шесть
колонок, три из них в ключе, статических нет — три ячейки на строку. Загрузим 100 000 заказов в одну
партицию и посмотрим инструментом, а не оценкой:

```
$ docker exec cass-theory /opt/cassandra/tools/bin/sstablepartitions --min-size 1 \
      /var/lib/cassandra/data/theory_dm/orders_big-*/*Data.db

Processing theory_dm.orders_big-f2134160ab6911f18f5a33e098cec400 #2 (big-nb) (5.228 MiB uncompressed, 1.913 MiB on disk)
  Partition: '11111111-1111-1111-1111-111111111111:2026-09' (…) live, size: 5.228 MiB,
             rows: 100000, cells: 300000, tombstones: 0
```

Формула сошлась точно: `100000 × (6 − 3 − 0) + 0 = 300 000` — ровно `cells: 300000`. Отсюда цена
формального лимита: 2 млрд ячеек — это 667 млн таких строк, то есть одна партиция примерно на
**34 ГиБ** (`2·10⁹ / 3·10⁵ × 5.228 МиБ`). До неё вы не доживёте: партиция — единица чтения и единица
уплотнения, её читают и переписывают целиком ([`WRITE_READ_PATH.md`](WRITE_READ_PATH.md) §2,
[`COMPACTION.md`](COMPACTION.md) §1), и трудности начинаются на три порядка раньше.

Тот же замер даёт рабочую единицу: 55 байт на строку из трёх узких ячеек (реальный заказ с адресом и
позициями — кратно больше). Пользователь с 20 заказами в месяц — партиция в единицы килобайт.
Продавец с 20 тыс. заказов в день — 1,1 МБ в сутки, 33 МБ за месяц без бакетирования; это уже тот
диапазон, где партицию видно на графиках задержки ([`OPERATIONS_PITFALLS.md`](OPERATIONS_PITFALLS.md) §1).

**Правило.** Считайте не строки, а ячейки и мегабайты, и держите верхнюю оценку в десятках мегабайт.
«2 миллиарда ячеек» отвечает на вопрос «когда сломается формально», а не «когда станет плохо».

## 5. Статические колонки: значение на партицию, а не на строку

**Задача.** В таблице «заказы продавца за период» рядом с каждым заказом нужно имя продавца.

**Наивное решение.** Обычная колонка `seller_name` в каждой строке.

**Где ломается.** У продавца с 20 тыс. заказов в день переименование магазина превращается в 20 тыс.
перезаписей — и все они попадут в память и в SSTable как настоящие мутации. Место тоже платное: одно
и то же имя лежит в партиции столько раз, сколько в ней строк.

**Механизм.** Статическая колонка объявляется словом `static` и хранится **один раз на партицию**,
отдельным блоком перед строками:

```
$ docker exec cass-theory bash -c '/opt/cassandra/tools/bin/sstabledump /var/lib/cassandra/data/theory_dm/orders_by_seller-*/*Data.db'
    "rows" : [
      { "type" : "static_block", "position" : 57,
        "cells" : [ { "name" : "seller_name", "value" : "Acme Tools", … } ] },
      { "type" : "row", "clustering" : [ "20000000-0000-1000-8000-000000000002" ],
        "cells" : [ { "name" : "total", "value" : 320.50 } ] },
      { "type" : "row", "clustering" : [ "10000000-0000-1000-8000-000000000001" ],
        "cells" : [ { "name" : "total", "value" : 149.00 } ] }
    ]
```

Имя записано одной вставкой без `order_id` — статическую колонку пишут и читают, не называя строку;
при `SELECT` сервер подставляет её в каждую строку партиции. Отсюда ограничение: без колонки
кластеризации в партиции ровно одна строка, «общее для всех» вырождается в «обычное», и такую таблицу
сервер не создаст:

```
$ cqlsh -e "CREATE TABLE theory_dm.bad_static (id uuid PRIMARY KEY, name text static, total decimal);"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Static columns are
only useful (and thus allowed) if the table has at least one clustering column"
```

Заметьте побочный эффект бакетирования из §2: ключ партиции здесь `(seller_id, order_day)`, поэтому
«одно значение на партицию» означает одно значение **на продавца в день**. Переименование стоит не
одной записи, а одной записи на каждый бакет, где есть заказы.

**Правило.** Статическая колонка — для атрибута, который принадлежит **партиции**, а не строке: имя
продавца, версия формата записи, признак «партиция закрыта». Чем уже бакет, тем больше копий такого
атрибута, — считайте их так же, как считали строки в §4.

## 6. Коллекции: frozen как один блок, non-frozen как ячейка на элемент

**Задача.** У заказа набор меток: `gift`, `express`, позже добавляется `fragile`.

**Наивное решение.** `set<text>` — и добавлять по одной: `SET tags = tags + {'fragile'}`. Слово
`frozen` выглядит необязательным украшением.

**Механизм.** Оно и есть выбор физического формата. В одной таблице объявлены обе версии, вставлены
одинаково, и после `nodetool flush` видно, чем они отличаются:

```
$ docker exec cass-theory bash -c '/opt/cassandra/tools/bin/sstabledump /var/lib/cassandra/data/theory_dm/order_tags-*/*Data.db'
        "cells" : [
          { "name" : "frozen_tags", "value" : ["express", "gift"] },
          { "name" : "tags", "deletion_info" : { "marked_deleted" : "2026-09-08T09:43:41.692204Z", … } },
          { "name" : "tags", "path" : [ "express" ], "value" : "" },
          { "name" : "tags", "path" : [ "fragile" ], "value" : "", "tstamp" : "2026-09-08T09:43:41.696974Z" },
          { "name" : "tags", "path" : [ "gift" ], "value" : "" }
        ]
```

`frozen_tags` — **одна** ячейка, значением которой является вся коллекция. `tags` — по ячейке на
элемент, у каждой свой путь; у `fragile`, добавленного отдельным `UPDATE`, и метка времени своя. Из
этой разницы следуют все три практических вывода.

*Частичное обновление frozen запрещено — менять нечего, ячейка одна:*

```
$ cqlsh -e "UPDATE theory_dm.order_tags SET frozen_tags = frozen_tags + {'fragile'} WHERE order_id = 4444…4444;"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Invalid operation
(frozen_tags = frozen_tags + {'fragile'}) for frozen collection column frozen_tags"
```

*Присваивание non-frozen коллекции целиком — это удаление плюс вставка.* `deletion_info` в дампе
появилась от `INSERT` со всем набором сразу: сервер не знает, каких элементов больше нет, и стирает
всю коллекцию, ставя на неё tombstone ([`WRITE_READ_PATH.md`](WRITE_READ_PATH.md) §4). Поэтому опасен цикл
«прочитал набор, изменил, записал целиком»: он даёт tombstone на каждое обновление.

*Добавление в `list` не идемпотентно.* Элемент получает свежий timeuuid в качестве пути, поэтому
повтор того же `UPDATE` даёт два одинаковых элемента, а не один:

```
$ cqlsh -e "UPDATE theory_dm.order_events SET notes = notes + ['packed'] WHERE order_id = 6666…6666;"   # дважды
$ cqlsh -e "SELECT * FROM theory_dm.order_events;"
 66666666-6666-6666-6666-666666666666 | ['packed', 'packed']

$ sstabledump …/order_events-*/*Data.db
  { "name" : "notes", "path" : [ "3ade3440-ab6a-11f1-8f5a-33e098cec400" ], "value" : "packed", … },
  { "name" : "notes", "path" : [ "3ade8260-ab6a-11f1-8f5a-33e098cec400" ], "value" : "packed", … }
```

Это записано и в спецификации типа: «some lists operations are not idempotent by nature …, making
their retry in case of timeout problematic» (CQL / Data Types) — драйвер, повторивший запрос по
таймауту, добавит элемент второй раз ([`DRIVER_AND_APP.md`](DRIVER_AND_APP.md) §3).

**Правило.** `frozen` — когда значение меняется целиком; non-frozen — когда элементы добавляются по
одному и их число ограничено сверху. Потолок обязателен, потому что постранично коллекцию прочитать
нельзя: «even to access a single element of a collection, the whole collection has to be read (and
reading one is not paged internally)» (CQL / Data Types). Растущий без границ набор — это не
коллекция, а колонка кластеризации в отдельной таблице.

## 7. UDT: структура без отдельной таблицы — и её цена при эволюции схемы

**Задача.** У заказа адрес доставки: улица, город, индекс. Три плоские колонки читаются нормально, но
адресов может быть несколько, и хочется говорить о них как о целом.

**Наивное решение.** Отдельная таблица `addresses` и ссылка на неё из заказа. Только соединять их
нечем ([`WHY_CASSANDRA.md`](WHY_CASSANDRA.md) §3) — каждый показ заказа станет двумя обращениями.

**Механизм.** UDT кладёт структуру в ту же строку, то есть читается вместе с заказом бесплатно.
Хранится он так же, как коллекция из §6: у non-frozen UDT ячейка на поле, и поле можно обновить
точечно (`SET addr.city = 'Munich'`), а `frozen` схлопывает всю структуру в одну ячейку.

```
$ docker exec cass-theory bash -c '/opt/cassandra/tools/bin/sstabledump /var/lib/cassandra/data/theory_dm/order_ship-*/*Data.db'
        "cells" : [
          { "name" : "addr", "deletion_info" : { "marked_deleted" : "2026-09-08T09:44:16.700162Z", … } },
          { "name" : "addr", "path" : [ "street" ], "value" : "Main 1" },
          { "name" : "addr", "path" : [ "city" ], "value" : "Berlin" },
          { "name" : "addr", "path" : [ "zip" ], "value" : "10115" }
        ]
```

Внутри коллекции выбора нет — там UDT обязан быть `frozen` и в 5.0:

```
$ cqlsh -e "CREATE TABLE theory_dm.bad_udt (order_id uuid PRIMARY KEY, addrs list<shipping_address>);"
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Non-frozen UDTs are
not allowed inside collections: list<shipping_address>"
```

**Цена — эволюция.** `ALTER TYPE … ADD` меняет только описание типа, ни одной записанной строки он не
трогает: в дампе выше ячейки `country` просто нет, и читается она как `null`.

```
$ cqlsh -e "ALTER TYPE theory_dm.shipping_address ADD country text;"
$ cqlsh -e "SELECT addr FROM theory_dm.order_ship WHERE order_id = 55555555-5555-5555-5555-555555555555;"
 {street: 'Main 1', city: 'Berlin', zip: '10115', country: null}

$ cqlsh -e "ALTER TYPE theory_dm.shipping_address DROP zip;"
<stdin>:1:SyntaxException: line 1:38 no viable alternative at input 'DROP'
(ALTER TYPE theory_dm.shipping_address [DROP]...)
```

Поле можно добавить и переименовать (`RENAME zip TO postal_code` проходит) — убрать нельзя, такой
формы в грамматике нет.

**Правило.** UDT берут, когда структура всегда читается вместе с владельцем и её поля меняются реже,
чем данные. Каждое добавленное поле остаётся в типе навсегда, а `null` в старых строках придётся
отличать от осмысленного «значения нет» — это работа приложения, а не базы.

## 8. Счётчики: отдельный тип таблицы и почему они не идемпотентны

**Задача.** Показывать продавцу счётчик «заказов за сегодня».

**Наивное решение.** Колонка `orders_total int` рядом с `seller_name`: прочитал, прибавил, записал.
На двух параллельных заказах это классическая потеря обновления — оба прочитали 10, оба записали 11.

**Где ломается тип `counter`.** Он существует ровно для этого случая, но живёт по отдельным правилам,
и все три сервер объявляет сам:

```
$ cqlsh -e "CREATE TABLE theory_dm.bad_counter (seller_id uuid PRIMARY KEY, orders_total counter, name text);"
<stdin>:1:InvalidRequest: … "Cannot mix counter and non counter columns in the same table"

$ cqlsh -e "INSERT INTO theory_dm.seller_stats (seller_id, order_day, orders_total) VALUES (2222…2222, '2026-09-08', 1);"
<stdin>:1:InvalidRequest: … "INSERT statements are not allowed on counter tables, use UPDATE instead"

$ cqlsh -e "UPDATE theory_dm.seller_stats USING TIMESTAMP 1000 SET orders_total = orders_total + 1 WHERE …;"
<stdin>:1:InvalidRequest: … "Cannot provide custom timestamp for counter updates"
```

**Механизм.** Третий отказ и есть объяснение первых двух. Обычная запись идемпотентна по устройству:
ячейка несёт значение и метку времени, конфликты разрешаются как last-write-wins
([`WRITE_READ_PATH.md`](WRITE_READ_PATH.md) §3), поэтому повтор той же мутации неотличим от оригинала.
У счётчика метки времени нет — ни своей, ни задаваемой: реплика хранит накопленную сумму дельт и на
каждое обновление прибавляет ещё одну. Повторить дельту нельзя, потому что «та же самая» и «ещё одна»
для неё — одно и то же. Отсюда и запрет на соседство с обычными колонками: у них разные правила
слияния, и в одной таблице они не уживаются.

Спецификация формулирует последствие прямо: «if a counter update fails unexpectedly (timeout or loss
of connection to the coordinator node), the client has no way to know if the update has been applied
or not. In particular, replaying the update may or may not lead to an over count» (CQL / Data Types).

**Правило.** Счётчик — для величин, где расхождение на единицу допустимо: просмотры, лайки, «примерно
столько заказов». Там, где число обязано сходиться, считайте строки в обычной таблице или ведите
журнал событий с ключом идемпотентности — повтор счётчика драйвер вам не сделает безопасным
([`DRIVER_AND_APP.md`](DRIVER_AND_APP.md) §3).

## 9. Шпаргалка

| Что у вас на руках | Чем это выражается в модели |
|---|---|
| атрибут принадлежит партиции, а не строке | `static` (§5) |
| набор из единиц элементов, меняется целиком | `frozen<set/list/map>` (§6) |
| набор растёт по одному, потолок известен | non-frozen коллекция (§6) |
| набор растёт без потолка | колонка кластеризации в отдельной таблице (§6) |
| структура всегда читается вместе с владельцем | UDT; внутри коллекции — только `frozen` (§7) |
| счёт, где расхождение на единицу недопустимо | строки в обычной таблице (§8) |
| счёт, где ±1 не важен | `counter` в отдельной таблице (§8) |

После первой записи **изменить нельзя**: состав ключа партиции, состав и порядок колонок
кластеризации, `CLUSTERING ORDER BY`, `frozen` у коллекции, наличие поля в UDT (удалить нельзя даже
до записи). **Можно**: добавить обычную колонку, добавить и переименовать поле UDT — но старые строки
при этом не переписываются (§7).

### Формулировки для собеседования

- «Внутренние скобки в `PRIMARY KEY` делят его на "где лежит" и "в каком порядке"; ключ партиции
  хешируется целиком, поэтому диапазон по нему невозможен, а перечисление — можно».
- «`CLUSTERING ORDER BY` — это порядок строк на диске. Сортировать по другой колонке нечем: на пути
  чтения нет операции сортировки, есть проход по упорядоченному участку».
- «Формальный предел партиции — 2 млрд ячеек, но это десятки гигабайт на партицию; реальный предел
  задаёт то, что партиция читается и уплотняется целиком».
- «non-frozen коллекция — ячейка на элемент, frozen — одна ячейка; поэтому у первой можно менять
  элемент, а у второй только всё значение».
