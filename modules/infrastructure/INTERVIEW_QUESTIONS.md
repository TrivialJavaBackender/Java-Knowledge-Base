# Вопросы для собеседования

62 вопроса по инфраструктурным темам для backend-разработчика.

---

## Docker (Q1–Q8)

### Q1: Чем отличается `COPY` от `ADD` в Dockerfile?
**A:** `COPY` просто копирует файлы из контекста сборки в образ — это предпочтительный вариант для большинства случаев. `ADD` дополнительно умеет распаковывать tar-архивы и загружать файлы по URL. Именно из-за неявного поведения `ADD` рекомендуется использовать только когда нужна распаковка; для простого копирования всегда предпочитайте `COPY`.

### Q2: Что такое слой образа? Почему порядок инструкций в Dockerfile важен?
**A:** Каждая инструкция в Dockerfile создаёт новый слой — неизменяемый diff файловой системы. Docker кэширует слои: если слой не изменился, он берётся из кэша. Если поставить `COPY . .` перед `RUN mvn dependency:go-offline`, то любое изменение исходного кода инвалидирует кэш зависимостей и Maven скачивает их заново. Правильный порядок: сначала `pom.xml` + загрузка зависимостей, потом исходный код.

### Q3: В чём смысл многоэтапной (multi-stage) сборки?
**A:** Multi-stage позволяет разделить build-окружение и runtime-окружение. На первой стадии используется образ с JDK и Maven для компиляции. На второй копируется только собранный `*.jar` поверх минимального JRE-образа (~70 МБ вместо ~500 МБ). В финальный образ не попадают Maven, исходный код и промежуточные артефакты — меньше размер, меньше attack surface.

### Q4: Чем отличается `ENTRYPOINT` от `CMD`?
**A:** `ENTRYPOINT` задаёт исполняемый файл контейнера, который нельзя переопределить при запуске без флага `--entrypoint`. `CMD` — аргументы по умолчанию, которые легко заменяются через `docker run <image> <args>`. Для приложений рекомендуется `ENTRYPOINT ["java", "-jar", "app.jar"]` с `CMD` для дефолтных флагов. Форма exec (`["java", "-jar"]`) предпочтительнее shell-формы (`java -jar`) — PID 1 получает сигналы напрямую.

### Q5: Как контейнеры общаются друг с другом в docker-compose?
**A:** Контейнеры в одной compose-сети могут обращаться друг к другу по имени сервиса как по DNS-имени. Например, сервис `app` обращается к `postgres:5432` — имя `postgres` резолвится внутри сети автоматически. Контейнеры в разных сетях изолированы и не видят друг друга, если только сеть не объявлена как `external` или сервис не подключён к обеим сетям.

### Q6: Зачем запускать контейнер от non-root user?
**A:** По умолчанию процессы в контейнере запускаются от root. Если злоумышленник получает RCE в приложении, он получает root внутри контейнера. При монтировании хоста или container escape это может означать root на хосте. Non-root пользователь ограничивает blast radius: нет доступа к системным файлам, нет возможности открыть привилегированные порты (<1024). Создаётся через `RUN useradd -r appuser && USER appuser`.

### Q7: Чем именованный volume (named volume) отличается от bind mount?
**A:** Bind mount монтирует конкретный путь на хосте (`-v /host/path:/container/path`) — зависит от файловой системы хоста, удобен для разработки. Named volume (`-v mydata:/container/path`) управляется Docker: хранится в `/var/lib/docker/volumes/`, переносим между хостами через `docker volume export`, не зависит от структуры директорий хоста. Для продакшене данных (база данных, файлы приложения) используйте named volumes.

### Q8: Что такое `HEALTHCHECK` и зачем он нужен?
**A:** `HEALTHCHECK` задаёт команду, которую Docker периодически запускает для проверки состояния контейнера. Если проверка проваливается N раз подряд, контейнер помечается как `unhealthy`. В docker-compose это позволяет `depends_on` с `condition: service_healthy` ждать реальной готовности сервиса, а не просто факта его запуска. Без HEALTHCHECK `depends_on` лишь гарантирует порядок старта, но не готовность.

## Kubernetes (Q9–Q16)

### Q9: В чём разница между Pod и Deployment?
**A:** Pod — минимальная единица деплоя в Kubernetes, группа контейнеров с общей сетью и хранилищем. Pod смертен: при падении он не восстанавливается автоматически. Deployment управляет ReplicaSet, который обеспечивает нужное количество живых Pod. Deployment умеет делать rolling update (постепенную замену под новой версией) и rollback. На практике под в изоляции почти не создают — только через Deployment или другие контроллеры.

### Q10: Как Kubernetes узнаёт, что Pod готов принимать трафик?
**A:** Через `readinessProbe`. Пока проверка не проходит, Pod не добавляется в Endpoints сервиса и трафик на него не идёт. `livenessProbe` — другая проверка: если она падает, kubelet перезапускает контейнер. Важно: не давать им один endpoint, иначе кратковременная проблема (например, высокая нагрузка) вызовет перезапуск вместо того, чтобы просто временно вывести под из балансировки.

### Q11: Чем ConfigMap отличается от Secret?
**A:** ConfigMap — для нечувствительной конфигурации (URL сервисов, feature flags). Secret — для чувствительных данных (пароли, токены). Оба монтируются как env variables или файлы. Ключевое различие в типе и контроле доступа: Secret отдельно индексируется в RBAC, на него можно дать строже permissions. Главный миф: «Secret — это зашифровано». По умолчанию это **base64**, не encryption — любой с правом `get secret` видит plain text. Реальное шифрование — это **etcd encryption at rest**, которое нужно явно включать (часто не включено в managed Kubernetes). Для серьёзного secrets management используют Vault, Sealed Secrets, или External Secrets Operator.

### Q12: Что происходит, если `livenessProbe` провалилась?
**A:** Kubelet перезапускает контейнер (не под целиком). Если `restartPolicy: Always` (по умолчанию для Deployment), контейнер перезапустится с экспоненциальным backoff (10s, 20s, 40s... до 5 минут). Если `livenessProbe` настроена слишком агрессивно (маленький `timeoutSeconds` или `failureThreshold`), приложение с медленным стартом будет постоянно перезапускаться — это crashloop. Решение: `startupProbe` для защиты медленного старта.

### Q13: Как работает HPA? Что нужно задать обязательно?
**A:** HPA (Horizontal Pod Autoscaler) периодически (каждые 15 секунд) смотрит на текущее потребление ресурсов под и сравнивает с целевым значением. Если CPU > 70% → добавляет реплики, если CPU < 70% → убирает (с кулдауном). Обязательно нужны `resources.requests` в Pod spec — без них HPA не знает относительно чего считать проценты. `requests` ≠ `limits`: requests определяет расчёт для HPA и scheduler, limits — жёсткий потолок.

### Q14: Чем ClusterIP отличается от NodePort?
**A:** ClusterIP — виртуальный IP внутри кластера, доступен только изнутри (Pod ↔ Pod). NodePort — открывает порт (30000-32767) на каждой ноде кластера, делая сервис доступным снаружи через `<node-ip>:<node-port>`. LoadBalancer — NodePort + создание облачного балансировщика. Для внутреннего взаимодействия микросервисов всегда ClusterIP. NodePort/LoadBalancer — только для внешних запросов. DNS имя сервиса внутри кластера: `<service>.<namespace>.svc.cluster.local`.

### Q15: Что такое resource requests vs limits? Какие QoS классы есть?
**A:** `requests` — гарантия: scheduler размещает под на ноде, где есть столько ресурсов. `limits` — потолок: при превышении CPU контейнер throttle-ится, при превышении памяти — OOMKilled. QoS классы: **Guaranteed** (requests == limits для всех контейнеров) — Pod выселяется последним; **Burstable** (requests < limits) — средний приоритет; **BestEffort** (нет requests/limits) — выселяется первым при нехватке ресурсов.

### Q16: Зачем нужны namespaces?
**A:** Namespaces — виртуальные кластеры внутри одного физического кластера. Обеспечивают: изоляцию ресурсов (два сервиса с именем `api` в разных пространство имён не конфликтуют), контроль доступа через RBAC (команда А видит только свой namespace), ResourceQuota (ограничение CPU/memory для namespace), LimitRange (дефолтные requests/limits). Типичное деление: `production`, `staging`, `monitoring`, `infra`.

## Helm (Q17–Q20)

### Q17: Что такое Helm release? Чем отличается от chart?
**A:** Chart — пакет с шаблонами Kubernetes манифестов и `values.yaml`. Release — конкретная установка чарт в кластер с определёнными values. Один чарт можно установить несколько раз под разными именами release (например, `myapp-prod` и `myapp-staging`). Helm хранит историю релизов в Kubernetes Secrets, что позволяет делать `helm rollback` к предыдущей версии.

### Q18: Как передать значения в chart при установке?
**A:** Три способа: `--set key=value` (CLI, для единичных значений), `--values custom.yaml` (файл, для многих значений), `--set-string` (форсировать тип string). При `helm upgrade` значения из предыдущего релизе не сохраняются автоматически — нужно `--reuse-values` или явно передать все нужные. В CI/CD обычно используют `-f values-prod.yaml` для разных окружений.

### Q19: Зачем нужны Helm hooks? Приведи пример.
**A:** Hooks позволяют запускать `Jobs` в определённые моменты lifecycle release: `pre-install` (до создания ресурсов), `post-install`, `pre-upgrade`, `post-upgrade`, `pre-delete`. Типичный пример: Job с DB миграцией как `pre-upgrade` hook — Helm ждёт его завершения перед деплоем новых Pod. Без `hooks` пришлось бы вручную координировать миграцию и деплой. Ресурсы `hooks` не управляются как обычные релизе ресурсы: нужен `hook-delete-policy` чтобы их убирать.

### Q20: Что делает `helm rollback`?
**A:** Откатывает релизе к предыдущей ревизии (или к указанной). Helm берёт сохранённые манифесты предыдущей ревизии из Kubernetes Secret и применяет их. Важно: rollback создаёт новую ревизию (не удаляет текущую). Hooks `pre-rollback` и `post-rollback` тоже выполняются. Ограничение: если между деплоями была DB миграция, rollback приложения не откатывает схему БД — нужна отдельная down-миграция.

## Observability (Q21–Q24)

### Q21: В чём разница между метриками, логами и трейсами?
**A:** Метрики — агрегированные числовые показатели во времени (RPS, error rate, latency p99). Дёшевы для хранения и запросов, но теряют детали. Логи — записи конкретных событий с контекстом. Дороги при большом объёме, но незаменимы для отладки. Трейсы — путь запроса через несколько сервисов (распределённая трассировка). Показывают где именно тратится время в цепочке. На практике используются вместе: метрика сигнализирует о проблеме, лог объясняет что произошло, трейс показывает где.

### Q22: Что такое SLI, SLO, SLA? Дай пример для API сервиса.
**A:** SLI (Service Level Indicator) — измеримый показатель качества: "доля запросов, выполненных за < 200ms". SLO (Service Level Objective) — целевое значение SLI: "99% запросов выполняются за < 200ms". SLA (Service Level Agreement) — контракт с пользователем с последствиями нарушения (скидка, штраф). SLO строже SLA — чтобы иметь запас до нарушения контракта. Пример: SLI = `rate(http_requests_total{status!~"5.."}[5m]) / rate(http_requests_total[5m])`, SLO = 99.9% success rate.

### Q23: Что такое error budget?
**A:** Error budget = 1 - SLO. Если SLO = 99.9%, то error budget = 0.1% = ~43 минуты недоступности в месяц. Пока бюджет не исчерпан, команда может деплоить новые фичи. Когда бюджет исчерпан — фокус переключается на надёжность, новые деплои замораживаются. Это механизм баланса между скоростью разработки и стабильностью. Для разработчика важно понимать: каждый выкатка несёт риск, который измеряется в минутах error budget.

### Q24: Как связать лог, метрику и трейс в production?
**A:** Через correlation ID — уникальный идентификатор запроса, который прокидывается через все три системы. В логах он присутствует как поле (`trace_id`), в метриках — реже (высокая кардинальность), в трейсах — это trace ID. Современный стандарт: W3C TraceContext заголовок (`traceparent`). В Spring Boot + Micrometer Tracing trace ID автоматически добавляется в MDC и лог. Grafana позволяет из дашборда перейти по trace ID к Loki-логам и Jaeger-трейсам.

## Logging (Q25–Q29)

### Q25: Почему структурированное логирование лучше строк?
**A:** Строковые логи парсятся regex — хрупко и медленно. JSON логи легко индексируются и фильтруются: `{level: "ERROR", userId: "123", orderId: "456"}`. В Loki/Elasticsearch можно делать `userId = "123"` вместо regex. Структурированные поля позволяют строить агрегации: "все ошибки по `userId` за последний час". На практике это разница между "grep в панике" и "SQL-запрос к логам".

### Q26: Что такое MDC? Как работает с async?
**A:** MDC (Mapped Diagnostic Context) — thread-local Map, автоматически добавляемая к каждой записи в лог. Пример: `MDC.put("requestId", uuid)` → все последующие `log.info(...)` в том же потоке будут содержать `requestId`. Проблема с async: при передаче задачи в другой поток MDC не копируется автоматически. Решение: `TaskDecorator` в Spring, который перед выполнением задачи копирует MDC из родительского потока, а после очищает.

### Q27: Что логировать на уровне ERROR vs WARN?
**A:** `ERROR` — ситуация, требующая немедленного внимания: неожиданное исключение, недоступность внешней зависимости, нарушение инварианта данных. На `ERROR` должен срабатывать алерт. `WARN` — нештатная, но обрабатываемая ситуация: retry успешен после 2 попыток, запрос упал на rate limit, deprecated API. `INFO` — нормальные бизнес-события: заказ создан, платёж прошёл. `DEBUG` — детали реализации, не нужные в production.

### Q28: Как реализовать correlation ID в Spring Boot?
**A:** Через `OncePerRequestFilter`: если в запросе есть заголовок `X-Request-ID` — берём его, иначе генерируем UUID. Кладём в MDC: `MDC.put("requestId", id)`. Добавляем заголовок в ответ. В `finally` блоке: `MDC.remove("requestId")`. Если сервис делает HTTP-вызовы downstream — нужно прокидывать ID через `RestTemplate`/`WebClient` interceptor. Для Kafka — через message header.

### Q29: Что такое антипаттерн "log and throw"?
**A:** Логирование исключения и одновременное его перебрасывание. Это приводит к дублированию одного и того же exception stacktrace несколько раз в логах — на каждом уровне вызовов. Правильно: либо логировать и обрабатывать (`catch + log`), либо пробрасывать без логирования (`throw`). Логировать нужно только один раз — там, где исключение обрабатывается окончательно (обычно на уровне верхнего exception handler).

## Metrics (Q30–Q36)

### Q30: Чем Counter отличается от Gauge?
**A:** Counter — монотонно возрастающее значение (только увеличивается), например, количество обработанных запросов. Никогда не уменьшается, только сбрасывается при рестарте. Для анализа используют `rate()` или `increase()`. Gauge — текущее значение, которое может расти и убывать: размер очереди, количество активных соединений, использование памяти. Gauge читается напрямую без `rate()`.

### Q31: Когда использовать Histogram, а когда Summary?
**A:** Histogram считает наблюдения по корзинам (предопределённые границы, например `[0.1, 0.5, 1, 5]` секунд) на стороне приложения и позволяет агрегировать percentile в Prometheus через `histogram_quantile()` — работает при нескольких инстансах приложения. Summary считает percentile в самом приложении — не агрегируется между инстансами. Правило: почти всегда используйте Histogram. Summary имеет смысл только если percentile нужны сразу без PromQL и инстанс один.

### Q32: Как работает pull-модель Prometheus?
**A:** Prometheus сам ходит к каждому приложению по расписанию (scrape interval, обычно 15s) и забирает метрики с endpoint `/metrics`. Приложение должно предоставить эндпоинт в формате Prometheus text exposition. В Spring Boot это `/actuator/prometheus` при наличии `micrometer-registry-prometheus`. Альтернатива — push через Pushgateway (для batch jobs, которые живут меньше scrape interval). Pull проще для service discovery и гарантирует что мертвые сервисы не шлют метрики.

### Q33: Что такое `rate()` в PromQL? Почему нельзя применять к Gauge?
**A:** `rate(counter[5m])` вычисляет среднюю скорость изменения `counter` за 5 минут (per second). Корректно обрабатывает resets (перезапуск приложения). `irate()` — то же, но по двум последним точкам (реагирует быстрее). К Gauge применять `rate()` нельзя: Gauge может убывать, а `rate()` предполагает что значение только растёт и обрабатывает "уменьшение" как reset. Для Gauge используют прямое значение, `delta()` или `deriv()`.

### Q34: Как настроить метрики в Spring Boot?
**A:** Добавить `micrometer-registry-prometheus` в зависимости. В `application.properties`: `management.endpoints.web.exposure.include=prometheus`. Метрики доступны на `/actuator/prometheus`. Для кастомных метрик: инжектировать `MeterRegistry` и использовать `registry.counter("orders.created", "status", status).increment()`. Аннотация `@Timed` на методе автоматически создаёт Timer. Spring Boot автоматически регистрирует метрики JVM, HTTP, DataSource.

### Q35: Что такое кардинальность (cardinality) в контексте метрик? Почему важно?
**A:** Кардинальность — количество уникальных комбинаций label. `http_requests_total{method, status}` с 5 методами × 10 статусов = 50 time series. Если добавить `userId` (миллион пользователей) — получим 50M time series. Высокая кардинальность убивает Prometheus: память, disk, время запросов. Правило: не использовать в `label` значения с неограниченным множеством (user ID, email, URL без нормализации). Группируйте: вместо конкретного status code — `2xx`, `4xx`, `5xx`.

### Q36: Как `histogram_quantile()` вычисляет p99?
**A:** Histogram хранит счётчики по корзинам: сколько запросов выполнились быстрее 0.1с, 0.5с, 1с, и т.д. `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` интерполирует внутри bucket, в котором находится 99-я перцентиль. Точность зависит от корзин: если 99-я перцентиль между 0.5с и 1с, но корзин между ними нет — будет приближение. Для Spring Boot/Micrometer корзины настраиваются через `management.metrics.distribution.sla.*`.

## Дополнительные актуальные темы (Q37–Q50)

### Q37: Что произошло с Docker в Kubernetes 1.24?
**A:** В мае 2022 Kubernetes 1.24 убрал `dockershim` — компонент-переводчик между kubelet и Docker API. Это **не** означает, что Docker-образы перестали работать в Kubernetes; образы — это OCI-формат, и они работают в любом OCI-совместимом runtime (containerd, CRI-O). Под капотом Docker всегда использовал `containerd`; теперь kubelet общается с containerd напрямую через CRI, минуя Docker daemon. Меньше слоёв, меньше ресурсов на ноде, меньше attack surface. Для разработчика всё прежнее — `docker build` и `Dockerfile` остаются актуальными инструментами.

### Q38: Что такое reconciliation loop и почему это foundation Kubernetes?
**A:** Reconciliation loop — это паттерн декларативного управления: контроллер постоянно сравнивает желаемое состояние (yaml в etcd) с реальным (что запущено в кластере) и применяет разницу. Аналогия — термостат: задано 22 °C → измерил → меньше → включил отопление. В Kubernetes так работает **всё**: Deployment controller следит за replicaCount, NodeController за статусом нод, EndpointsController за Service endpoints. Из этого вытекает идемпотентность (`kubectl apply` 100 раз = 1 раз), самовосстановление (упал Pod → пересоздался) и eventual consistency (между «применил» и «сошлось» проходит время). Без понимания этого паттерна большинство «непонятных» поведений Kubernetes выглядят магией.

### Q39: Чем StatefulSet отличается от Deployment? Когда что использовать?
**A:** Deployment создаёт **взаимозаменяемые** поды со случайными именами (`api-7d8f9-abc12`), запускает в произвольном порядке. Подходит для сервисов без состояния. StatefulSet даёт стабильную identity: имена детерминированы (`mysql-0`, `mysql-1`), порядок старта строгий (сначала -0, потом -1), у каждого пода свой Persistent Volume через VolumeClaimTemplate. Используется для БД и кластерных систем (Kafka, ZooKeeper, Elasticsearch), где узлы знают друг друга в лицо и нужна stable storage. Обязателен Headless Service (`clusterIP: None`) для per-Pod DNS. Для большинства приложений нужен Deployment; StatefulSet — только если есть конкретная stateful causa.

### Q40: Зачем нужен init container и что такое sidecar pattern?
**A:** **Init container** — контейнер, который выполняется **до** основных и должен завершиться успешно. Используется для bootstrap: миграция БД, ожидание зависимостей (`until nc -z postgres 5432; do sleep 1; done`), скачивание конфигов. Запускаются последовательно по списку, основной контейнер стартует только после всех init exit 0. **Sidecar** — отдельный контейнер в том же поде, работающий **параллельно** с основным, разделяющий network namespace и volumes. Используется для: log forwarding (Fluent Bit читает stdout), service mesh proxy (Envoy в Istio), metrics exporter, dynamic config reload. Главное преимущество — переиспользование cross-cutting concerns без модификации кода приложения.

### Q41: Что делает NetworkPolicy и почему важно?
**A:** По умолчанию в Kubernetes **все поды могут общаться со всеми** — это удобно при старте, но катастрофа для security: compromise одного пода = compromise всех. NetworkPolicy — ingress/egress правила, аналог фаервола на уровне подов: «к API могут обращаться только поды с label frontend на порт 8080, всё остальное — отбрасывать». Особенно важно в мультиарендных кластерах (несколько команд) и при защите чувствительных сервисов (БД, сервисы с PII). NetworkPolicy реализуется CNI плагином (Calico, Cilium, Weave); если CNI её не поддерживает, yaml применится, но эффекта не даст. Production-best practice: default-deny policy + явные allow rules.

### Q42: Стоит ли ставить CPU limits на Pod в production?
**A:** Спорный вопрос. Memory limits ставить **обязательно** (memory нельзя throttle, при превышении — OOMKilled). С CPU сложнее: при превышении ядро троттлит процесс по квоте в каждом периоде (100 ms). Это вызывает latency spikes на burst-нагрузках (GC compaction, инициализация). Multiple companies (Datadog, Buffer, Grafana Labs) пишут, что CPU limits часто вредят. Альтернативная стратегия: ставить только `requests.cpu` (для планировщик и HPA), без `limits.cpu` — пусть процесс берёт сколько есть свободного на ноде. Это не universal truth: в мультиарендных с noisy neighbor проблемой `limits` всё-таки нужны. Стоит проверить, действительно ли в вашем случае `limits` помогают.

### Q43: Helm vs Kustomize — когда что выбирать?
**A:** Helm — template-based: шаблоны с переменными + values.yaml. Хорош для distribution (BD-чарт Bitnami, Prometheus operator, etc.). Минус: высокая кривая обучения (Go templates, scoping, helpers), сложно отлаживать. Kustomize — overlay-based: базовый YAML + патчи. Без шаблонов, чистый YAML. Встроен в kubectl с 1.14. Хорош для управления собственными манифестами в monorepo. Минусы: нет dependency management, нет release history. На практике часто **оба**: Helm для third-party (Postgres, Prometheus), Kustomize для своих сервисов. Argo CD поддерживает оба. Главный практический критерий: «нужно ли публиковать это наружу» (Helm) или «просто упорядочить свои yaml» (Kustomize).

### Q44: Зачем `helm upgrade --atomic --wait` в CI/CD?
**A:** Без флагов `helm upgrade` возвращает успешные сразу после `apply` в apiserver — не дожидаясь, что Deployments масштабировались, поды стартовали, healthchecks прошли. Если новая версия сразу падает, кластер в полусломанном состоянии: часть ресурсов обновилась, часть — нет. `--wait` блокирует до `Ready` всех ресурсов. `--atomic` идёт дальше: если в течение `--timeout` не сошлось, **автоматически rollback** к предыдущей revision. Идеально для CI/CD: либо всё хорошо, либо вернулись к рабочему состоянию. Без `--atomic` нужны были бы внешние health-checks + manual rollback скрипты.

### Q45: Чем monitoring отличается от observability?
**A:** Monitoring — про **known unknowns**: вы знаете, какие метрики важны (CPU, error rate, latency p99), настроили дашборды и алерты. Реактивный режим: «оранжевая лампочка → on-call». Observability — про **unknown unknowns**: возможность исследовать систему, задавать новые вопросы без предварительной инструментации. «Почему 0.3% запросов от пользователей из Германии после 14:05 получили 503 на checkout endpoint?» — вы не предсказывали этот вопрос, но должны мочь его задать. Не «либо-либо», а оба нужны: monitoring для здоровья и алертов, observability для debugging. Термин в IT популяризировала Charity Majors (Honeycomb) около 2016.

### Q46: Что такое head-based и tail-based sampling в distributed tracing?
**A:** Хранить 100% трасс дорого (миллиарды отрезков в сутки). Sampling — записывать только часть. **Head-based**: решение «сохранять трассу или нет» принимается в начале, на первом сервисе, обычно случайно (sample 1%). Дёшево, просто, downstream сервисы видят флаг в trace context и следуют. Недостаток: решение принимается **до** того, как стало известно об ошибке — error trace могут пропускаться. **Tail-based**: все отрезков собираются в Collector (буфер 30 sec), решение принимается **после** того, как трасса полностью собран. Можно сохранять, например, все трасса с ошибками или с высокой latency. Лучше для incident debugging, но требует stateful collector. Production-стандарт — гибрид: head-sample 1% baseline + tail-sample 100% error trace.

### Q47: Чем ELK отличается от Loki для хранения логов?
**A:** **ELK** (Elasticsearch + Logstash + Kibana): **полная индексация** всех полей логов — быстрый поиск по любому полю в миллисекунды. Минус: индексы 3–5× размера raw logs, ELK дорого по хранилищу и RAM. **Loki** (Grafana Labs): индексирует **только labels** (app, env, namespace, pod), сами логи лежат сжатыми chunks. Поиск по содержимому = grep по chunks, медленнее ELK. Зато в **~10× дешевле** по storage. Loki хорошо ложится на Kubernetes (labels-driven, как Prometheus). High-cardinality поля (`user_id`) **не должны** быть labels — они идут в JSON body. Trade-off: если нужен быстрый произвольно поиск по произвольным полям — ELK; если main use-case «дай логи моего сервиса за час» — Loki хватит.

### Q48: Что нельзя логировать и почему?
**A:** Никогда: PII (имена, email, IP-адреса — для GDPR в EU это тоже PII), credentials (пароли, JWT, API keys, OAuth tokens), полные номера карт (PCI-DSS), CVV, медицинские данные (HIPAA), полные тела запросов с этими данными. Регуляторные последствия: GDPR штрафы до 4% годового выручки или €20M; PCI-DSS — потеря права принимать карты. Технические последствия: Cloudflare Cloudbleed (2017) — утечка чужой памяти через response payloads попала в кэши Google/Bing, удаление заняло месяцы. Правило: логировать **identifiers** (userId, orderId), не **values** (email, cardNumber). При необходимости — маскировать: `j***@example.com`, `452000******1234`. Защита: даже если ваши логи защищены, retention 7 дней — данные могли уйти куда-то ещё. Никогда не пишите чувствительные в логи в первую очередь.

### Q49: rate() vs irate() в PromQL — когда что использовать?
**A:** `rate(metric[5m])` — средняя скорость роста по **всем** точкам в окне 5 минут. Сглажено, устойчиво к шуму. `irate(metric[5m])` — скорость роста только по **двум последним** точкам внутри окна (окно нужно лишь как ограничитель для query). Реактивный, показывает мгновенный rate. Правила: для алертов и trending dashboards — всегда `rate` (сглаживание защищает от false positives на всплесках). Для live debug «что прямо сейчас творится» — `irate`. Никогда не используйте `irate` для длинного окна: `irate(metric[1h])` даст `rate` последних двух точек, окно роли не играет — это типичная ошибка новичков, которые думают, что окно — это период усреднения.

### Q50: Что такое cardinality bomb и как её избежать в Prometheus?
**A:** Каждая уникальная комбинация label values = отдельный time series в Prometheus storage и в RAM. `http_requests_total{userId=...}` с миллионом пользователей × 20 instances = 20M time series только по одной метрике. Prometheus хранит head block в RAM — OOM или severe slowdown. Правила: никогда не использовать в `labels` поля с неограниченным множеством значений: `userId`, `email`, `orderId`, `sessionId`, IP-адрес, full URL без template. Нормализуйте: `/api/orders/123` → `/api/orders/{id}`; группируйте: `200, 201, 202` → `2xx`. Если нужен высокая кардинальность для drill-down — это работа для трасса системы (Jaeger/Tempo) или wide events (Honeycomb), не для метрик. Exemplars позволяют связать метрику с конкретным trace_id, не раздувая cardinality.

## Секреты (Q51–Q56)

### Q51: Почему Kubernetes Secret не является секретом?
**A:** Потому что это base64, а не шифрование. Проверяется за две команды: `kubectl create secret generic db-cred --from-literal=password='s3cr3t-p@ss'`, затем `kubectl get secret db-cred -o go-template='{{.data.password | base64decode}}'` возвращает `s3cr3t-p@ss` — никакого ключа не понадобилось, потому что расшифровывать нечего. Практический смысл: право `get secret` в пространстве имён равносильно знанию пароля, и то же самое верно для любого, кто получил копию снимка etcd. Что с этим делают: включают шифрование etcd при хранении (защищает от кражи диска, но не от человека с правами), сужают RBAC и выносят источник истины наружу — во External Secrets Operator, Vault Agent или CSI-драйвер, чтобы секрет попадал прямо в файловую систему пода, минуя etcd. И монтируют файлом в tmpfs, а не переменной окружения: переменная видна в `docker inspect`, в `/proc/<pid>/environ` и в дампе памяти при падении.
> `modules/infrastructure/theory/SECRETS.md` — раздел «Kubernetes Secret: почему base64 — это не шифрование»

### Q52: Что такое задача первого секрета (bootstrap problem) и как её решают?
**A:** Чтобы получить пароль из Vault, надо аутентифицироваться в Vault. Чтобы аутентифицироваться, нужен какой-то credential. Где он лежит — это и есть задача первого секрета, и на ней обрывается большинство ответов «мы храним всё в Vault». Плохое решение — положить токен Vault в переменную окружения или в образ: тогда весь Vault защищён ровно этим токеном. Правильные решения выстраиваются по возрастанию надёжности. Уровень 1 — роль IAM облака: приложение получает временные учётные данные через сервис метаданных экземпляра, статического секрета не существует вовсе, красть нечего. Уровень 2 — Kubernetes-аутентификация Vault: под предъявляет токен своего ServiceAccount, который выдал кластер и который сам ротируется. Уровень 3 — AppRole для случаев вне облака и вне кластера: `role_id` лежит в конфигурации, `secret_id` выдаётся одноразово и с коротким сроком. Общий принцип: первый секрет должен быть либо отсутствующим (удостоверение выдаёт платформа), либо короткоживущим и одноразовым.

### Q53: Что такое конвертное шифрование и зачем оно нужно?
**A:** Данные шифруются ключом данных (DEK), а сам DEK шифруется ключом шифрования ключей (KEK), который живёт в KMS и оттуда не выходит. Хранится пара: зашифрованный DEK плюс зашифрованные им данные. Для расшифровки KMS расшифровывает DEK — это единственная операция, которую он выполняет, — а дальше данные расшифровываются локально. Зачем так: KMS не должен пропускать через себя весь объём данных (это дорого и медленно), а ротация ключа при таком устройстве означает перешифровать только DEK, а не терабайты. Так работают Vault, AWS KMS, GCP KMS и шифрование etcd в Kubernetes.

### Q54: Секрет случайно закоммитили в git и удалили следующим коммитом. Что делать?
**A:** Считать секрет скомпрометированным и **отозвать** его — это первое и обязательное действие. История git вечна: удаление файла следующим коммитом ничего не меняет, значение достаётся из истории командой в одну строку, а если репозиторий был публичным или у него есть форки и зеркала, оно уже могло быть проиндексировано ботами (они сканируют публичные репозитории именно на это). Чистка истории (`git filter-repo`, BFG) и принудительная перезапись — второй шаг, а не первый: она не отменяет того, что значение уже утекло, и не действует на чужие клоны. Профилактика: `.gitignore` на файлы с секретами, предкоммитные хуки со сканированием (gitleaks, trufflehog) и вынос секретов туда, где их не приходится класть в файл.

### Q55: Чем динамический секрет отличается от статического и в чём выигрыш?
**A:** Статический секрет — это пароль, который кто-то однажды создал и который живёт, пока его не поменяют руками; срок жизни украденного статического пароля равен интервалу ротации, то есть на практике часто году или больше. Динамический секрет Vault создаёт под конкретный запрос: приложение просит доступ к базе, Vault создаёт в ней временную учётную запись со сроком аренды (lease) в час, отдаёт её и по истечении аренды удаляет. Выигрыш в том, что украденное протухает само, без участия человека, а по журналу Vault видно, кому и когда какая учётная запись выдавалась, — то есть появляется аудит обращений, которого у статического пароля нет в принципе. Цена: Vault становится системой на критическом пути (его недоступность мешает выдаче новых учётных данных), и база должна позволять создавать пользователей программно.

### Q56: Чем mTLS отличается от обычного TLS и какую задачу решает?
**A:** В обычном TLS сертификат предъявляет только сервер: клиент убеждается, что говорит с тем, с кем собирался, а сервер о клиенте не знает ничего и вынужден аутентифицировать его отдельно — паролем, токеном, ключом API. В mTLS сертификат предъявляют обе стороны, и сервер получает удостоверение вызывающего на уровне транспорта, до всякой прикладной логики. Задача, которую это решает между сервисами: убрать общие статические учётные данные, которыми сервисы доказывают друг другу, кто они, и заменить их короткоживущими сертификатами, выдаваемыми автоматически. Ограничение, о котором стоит помнить: mTLS отвечает на вопрос «кто вызывает», но не на вопрос «что ему разрешено» — авторизация остаётся отдельным слоем. Как это устроено в service mesh и что такое SPIFFE ID — в модуле microservices.

## Облако (Q57–Q62)

### Q57: Чем регион отличается от зоны доступности?
**A:** Регион — географическая единица (Франкфурт, Северная Вирджиния); зона доступности внутри региона — независимый домен отказа: отдельные здания, отдельное питание, отдельное охлаждение, но связанные каналом с задержкой порядка 1–2 мс. Различие практическое, а не терминологическое: несколько зон в одном регионе дают отказоустойчивость почти без потери задержки и почти без усложнения, поэтому это стандартная конфигурация продакшена. Несколько регионов дают устойчивость к потере региона целиком, но приносят задержку в десятки миллисекунд, вопросы согласованности данных и заметный трафик между регионами в счёте — это берут по требованию (RTO в минутах, регуляторное присутствие), а не «на всякий случай». Отсюда самая частая ошибка: три экземпляра приложения в одной зоне доступности не надёжнее одного, потому что домен отказа у них общий.
> `modules/infrastructure/theory/CLOUD.md` — раздел «Структура облачной инфраструктуры»

### Q58: Что такое RPO и RTO и как они влияют на архитектуру?
**A:** RPO (Recovery Point Objective) — сколько данных допустимо потерять, измеряется временем: RPO = 15 минут означает, что при аварии теряется до 15 минут работы. RTO (Recovery Time Objective) — сколько времени допустимо лежать. Обе величины назначает бизнес, а инженеры называют цену каждой. Влияние на архитектуру прямое: RPO в часах закрывается ежедневными копиями, RPO в минутах требует непрерывного архивирования журнала, а RPO = 0 требует синхронной репликации — и оплачивается задержкой **каждой записи**, потому что подтверждение ждёт вторую площадку. RTO в сутки допускает восстановление из копии, RTO в минутах требует постоянно работающего горячего резерва, то есть примерно двойной стоимости инфраструктуры. Практическая проверка: резервные копии, которые ни разу не восстанавливали, не дают ни того ни другого — работоспособность подтверждается восстановлением, и ничем другим.

### Q59: Чем высокая доступность (HA) отличается от аварийного восстановления (DR)?
**A:** HA — про то, чтобы отказ **не заметили**: резерв внутри региона, переключение автоматическое и за секунды, платится постоянно, потому что резерв всё время работает. DR — про то, чтобы **вернуться** после крупной аварии: другая площадка или другой регион, переключение обычно по решению человека, оплачивается готовность. Первое не заменяет второго, и это важнее всего в ответе: реплика в другой зоне повторяет не только сбои оборудования, но и логические ошибки — удалённая по ошибке таблица реплицируется в резерв так же исправно, как и всё остальное, а повреждённые данные — тем более. От этого класса отказов защищают только резервные копии с восстановлением на точку во времени, то есть DR. Обратное тоже верно: DR с RTO в четыре часа не поможет пережить отказ одного узла незаметно для пользователя.

### Q60: Почему облако не всегда дешевле своего железа?
**A:** Потому что продаётся не мощность, а право не угадывать её заранее. Если нагрузка непредсказуема — пики в десять раз, рост, который не спрогнозировать на полгода, — это право стоит своих денег: альтернатива в том, чтобы купить железо под пик и одиннадцать месяцев в году платить за простой. Если нагрузка ровная и известна на три года вперёд, вы платите за опцион, которым не пользуетесь, и своё железо оказывается дешевле. Промежуточная ступень — зарезервированные мощности и планы экономии: обязательство на год или три в обмен на скидку порядка 30–60%, то есть буквально продажа обратно того самого опциона. Отсюда заметный после 2021 года отъезд из облака: 37signals отчиталась об экономии порядка миллиона долларов в год, Dropbox — о 75 миллионах за два года после ухода с S3. Общее у обоих — ровный профиль нагрузки и своя команда эксплуатации; ни одно из этих условий не выполняется у стартапа, и именно поэтому их случаи не переносятся на всех подряд.

### Q61: Счёт за облако вырос на 60% при росте нагрузки на 20%. С чего начинать разбор?
**A:** Не с самой крупной строки. Самая крупная обычно вычисления, и она же самая понятная — она растёт пропорционально нагрузке. Непропорциональный рост дают скрытые статьи, которые по отдельности малы: исходящий трафик (входящий бесплатен, исходящий — нет, и это регулярный сюрприз для тех, кто раздаёт файлы или отвечает большими ответами), NAT-шлюз (плата за час плюс за каждый обработанный гигабайт, включая трафик к сервисам самого провайдера), трафик между зонами доступности (обращение к базе в соседней зоне тарифицируется в обе стороны), накопившиеся снимки дисков и незакреплённые IP-адреса. Признак, что искать надо здесь: рост счёта опережает рост числа запросов. Инструмент — разбивка счёта по тегам ресурсов; отсюда же следует, что теги должны быть проставлены заранее, иначе разбирать нечего.

### Q62: В чём смысл выбора между управляемой базой и своей?
**A:** Это обмен контроля на эксплуатацию, и сравнивать по цене железа — ошибка. В цену управляемой входит не мощность, а работа: настроенное и проверенное переключение на реплику, резервные копии с восстановлением на точку во времени, обновления безопасности и обязательство по доступности, за нарушение которого отвечает провайдер. Пока эту работу никто не делал, экономии нет — есть отложенный счёт, который предъявляется в момент, когда база не поднялась, а последняя проверенная копия оказалась трёхмесячной. Взамен вы теряете конкретные вещи: произвольные расширения (список задаёт провайдер — критично, если нужны PostGIS, TimescaleDB, pgvector), часть параметров и `pg_hba.conf`, свободу в выборе версии, суперпользователя и контроль над физическим расположением данных. Правило: управляемую берут по умолчанию и отказываются по конкретной причине — нужное расширение, требование к расположению данных, масштаб, на котором надбавка перевешивает зарплату администратора. «Мы сами умеем» — не причина: вопрос не в умении поднять, а в готовности дежурить.
