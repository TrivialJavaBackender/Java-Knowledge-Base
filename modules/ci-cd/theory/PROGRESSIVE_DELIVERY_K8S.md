# Канареечный, blue-green и A/B релиз на Kubernetes

> **Какую проблему решает.** Новая версия `payments` выкатилась на все поды за сорок секунд, и все сорок секунд она отдавала пятисотки — половине пользователей, потому что никто не стоял между «поды заменились» и «трафик пошёл».
> **Кому это надо.** Тому, кто пишет шаг раскатки и должен ответить, как выкатить на 5% пользователей, как это автоматически откатить и чем канарейка отличается от A/B.
> **Когда НЕ надо.** Если у сервиса нет метрики, по которой видно «плохо», прогрессивная раскатка даёт только отсрочку: она замедлит выкат, но решение всё равно примет человек по графику, который он и так смотрел.

## 1. `RollingUpdate` — это не канарейка

Штатная стратегия Deployment заменяет реплики пачками и не умеет остановиться на 10% и подождать. Управляющих ручек ровно две — `maxSurge` и `maxUnavailable`, обе про скорость замены, ни одной про долю трафика и ни одной про «подожди и проверь».

```yaml
strategy:
  rollingUpdate: { maxSurge: 25%, maxUnavailable: 25% }   # быстро или медленно
  type: RollingUpdate                                      # но всегда до конца
```

Единственная пауза, которую даёт Deployment, — отказ ехать дальше, если новые поды не проходят пробу готовности. Это ловит «не запустился», но не ловит «запустился и отдаёт пятисотки на четверти запросов»: такой под готов с точки зрения кластера.

**Следствие.** Канарейка — это внешний по отношению к Deployment механизм: кто-то должен держать две версии одновременно, дозировать между ними трафик и иметь право нажать «стоп».

## 2. Канарейка на репликах: минимальный вариант и его потолок

Держим два Deployment с общей меткой, на которую смотрит Service, и разным числом реплик. Трафик делится не потому, что кто-то его делит, а потому, что kube-proxy раскидывает соединения по endpoint'ам примерно поровну.

```yaml
apiVersion: v1
kind: Service
metadata: { name: payments }
spec:
  selector: { app: payments }        # ловит оба Deployment: stable и canary
  ports: [{ port: 80, targetPort: 8080 }]
---
# payments-stable: replicas: 9, метки app=payments, track=stable
# payments-canary: replicas: 1, метки app=payments, track=canary   → ~10% трафика
```

Потолок этого способа — арифметика: доля канарейки равна `1/N`, где `N` — общее число подов. На девяти стабильных подах ближайшие доступные доли — 10%, 20%, 33%. Пятипроцентная канарейка требует двадцати подов, полупроцентная — двухсот. Документация Argo Rollouts описывает то же ограничение прямо: без управления трафиком контроллер делает «best effort attempt to achieve the percentage listed in the last `setWeight` step», и на десяти репликах 10% — это буквально один под.

**Следствие.** Способ честно работает на сервисах с большим числом реплик и грубыми долями. На трёх подах «канарейка 5%» — это самообман: минимум, который вы можете выдать, — 33%.

## 3. Вес в маршруте: канарейка, которой управляет не число подов

Доля трафика становится настоящей ручкой, когда её задаёт маршрутизатор. В Gateway API это поле `weight` у `backendRefs`: два сервиса, два веса, и число подов больше ни при чём.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: payments }
spec:
  hostnames: [payments.example.com]
  rules:
  - backendRefs:
    - { name: payments-stable, port: 80, weight: 95 }
    - { name: payments-canary, port: 80, weight: 5 }
```

Три свойства поля `weight`, которые стоит знать дословно, потому что на них ловят:

- **Это доли, а не проценты.** Спецификация определяет долю бэкенда как его вес, делённый на сумму весов правила. Пара `90/10` и пара `9/1` означают одно и то же.
- **Вес по умолчанию — `1`.** Забытый `weight` у одного из двух бэкендов даёт не «ноль», а равную долю с другим.
- **Один бэкенд получает всё.** «If only a single backend is specified for a route rule it implicitly receives 100% of the traffic, no matter what (if any) weight is specified» — `weight: 0` на единственном бэкенде трафик не отключает.

**Следствие.** С весами в маршруте канарейка на 1% возможна при двух подах, а шаг раскатки становится обычным `PATCH` одного поля — то есть операцией, которую умеет делать конвейер.

## 4. A/B: маршрут по заголовку, и почему это другая задача

Тот же `HTTPRoute` умеет выбирать бэкенд не по случайности, а по признаку запроса: заголовку, куке, значению из токена.

```yaml
  rules:
  - matches:
    - headers: [{ name: x-beta-user, value: "true" }]   # правило с match — первое
    backendRefs: [{ name: payments-canary, port: 80 }]
  - backendRefs: [{ name: payments-stable, port: 80 }]  # всё остальное
```

Механика похожа на канарейку, но задача противоположная:

| | Канарейка | A/B-эксперимент |
|---|---|---|
| Кого пускаем | случайные 5% | заданный сегмент, устойчиво |
| По какой метрике решаем | доля ошибок, задержка | конверсия, продуктовая метрика |
| Сколько длится | минуты | дни и недели |
| Кто читает результат | конвейер | продуктовая аналитика |

Различие не академическое: канарейку можно и нужно катить автоматически, эксперимент — нельзя. Пятиминутного окна не хватит ни одной продуктовой метрике, а «плохая конверсия» не повод для автоматического отката.

**Следствие.** A/B по заголовку — это доставка **двух живущих версий**, а не этап раскатки. Если эксперимент длится неделю, обе версии неделю живут в проде, и обе нужно поддерживать.

## 5. Blue-green: переключение указателя

Blue-green держит два полных стека и переключает трафик одним изменением: селектор Service начинает указывать на другой набор подов. Откат — то же изменение в обратную сторону, поэтому он занимает секунды, а не время новой раскатки.

Argo Rollouts делает это стратегией `blueGreen`, где Service'ов два: боевой и превью — для проверки новой версии до переключения.

```yaml
strategy:
  blueGreen:
    activeService: payments            # обязательное поле: боевой трафик
    previewService: payments-preview    # опциональное: новая версия без пользователей
    autoPromotionEnabled: false         # по умолчанию true — переключит само
    scaleDownDelaySeconds: 30           # значение по умолчанию
    prePromotionAnalysis: { templates: [{ templateName: smoke }] }
```

Три детали, каждая из которых кого-нибудь однажды удивила:

- `autoPromotionEnabled` **по умолчанию `true`**: не выставив его, вы получите не blue-green с ручным переключением, а blue-green, который переключается сам, как только новый ReplicaSet готов.
- Контроллер переключает трафик, дописывая в селекторы сервисов хеш ReplicaSet — то есть меняет объект Service, а не создаёт новый.
- `scaleDownDelaySeconds` существует не «на всякий случай»: после смены селектора таблицы маршрутизации на узлах обновляются не мгновенно, и старые поды ещё несколько секунд получают пакеты.

**Цена** — двойной ресурс на время релиза и требование, чтобы обе версии одновременно работали с одной схемой БД ([`RELEASE_STRATEGIES.md` §7](../../engineering-process/theory/RELEASE_STRATEGIES.md)). Второе жёстче первого: blue-green не спасает от миграции, которая ломает старую версию, — он гарантированно её ломает, потому что старая версия в этот момент жива.

## 6. Argo Rollouts: раскатка, разбитая на шаги

`Rollout` — замена `Deployment` (те же `template` и `selector`), у которого стратегия выражена списком шагов. Контроллер исполняет их по очереди и останавливается там, где сказано.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: payments }
spec:
  replicas: 10
  strategy:
    canary:
      canaryService: payments-canary    # обязательны оба, когда есть trafficRouting
      stableService: payments-stable
      trafficRouting:
        plugins:
          argoproj-labs/gatewayAPI: { httpRoute: payments, namespace: prod }
      steps:
      - setWeight: 5
      - pause: { duration: 10m }        # без duration — пауза до ручного промоута
      - setWeight: 25
      - analysis: { templates: [{ templateName: success-rate }] }
      - setWeight: 50
      - pause: { duration: 10m }
  template: { }                         # обычный pod template, как у Deployment
```

Что здесь важно знать точно:

- **`pause` без `duration` ждёт бесконечно** — это и есть штатный «ручной гейт»: дальше едет `kubectl argo rollouts promote payments`, назад — `abort`.
- **`setWeight` без `trafficRouting` — это опять реплики** со всеми ограничениями §2; `trafficRouting` по умолчанию не задан.
- **Gateway API подключается плагином**, а не встроенной поддержкой: в ядре живут Istio, NGINX, ALB, SMI, Traefik, Kong, APISIX, и новые туда не принимают.
- `maxSurge` и `maxUnavailable` у канарейки те же, что у Deployment, и по умолчанию тоже `25%`.

**Следствие.** Конвейер перестаёт быть тем, кто «выкатывает», и становится тем, кто **запускает** раскатку и ждёт её исхода. Само решение «ехать дальше» принимает контроллер или дежурный.

## 7. Автоматический гейт: анализ вместо взгляда на график

`AnalysisTemplate` превращает «посмотрели графики» в условие, которое проверяет контроллер. Шаг `analysis` в списке блокирует раскатку до вердикта; анализ, объявленный в `strategy.canary.analysis`, идёт фоном всю раскатку.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
  - name: success-rate
    interval: 1m           # как часто измерять
    count: 5               # сколько измерений; 0 в фоновом анализе = бесконечно
    failureLimit: 1        # сколько провалов терпим до отката
    successCondition: result[0] >= 0.99
    provider:
      prometheus:
        address: http://prometheus.monitoring:9090
        query: |
          sum(rate(http_server_requests_seconds_count{service="payments",status!~"5.."}[2m]))
          / sum(rate(http_server_requests_seconds_count{service="payments"}[2m]))
```

Главная ошибка здесь не в синтаксисе, а в арифметике. При 40 запросах в секунду и весе канарейки 5% на новую версию приходит две транзакции в секунду: за минуту — 120 запросов. Рост доли ошибок с 0.1% до 1% — это разница между «ожидаем 0.12 ошибки» и «ожидаем 1.2 ошибки», то есть шум. Тот же порог на весе 25% и окне 10 минут — 6000 запросов и 60 ошибок против 6: это уже сигнал.

**Следствие.** Длину шага задаёт не солидность цифры «10 минут», а число запросов, которое за него попадёт на канарейку. Считайте его до того, как настраивать `successCondition`: на низком трафике канарейка в 5% не докажет ничего, и честнее начинать с 25%.

## 8. Flagger: тот же результат другой моделью

Flagger решает ту же задачу, не заменяя `Deployment`, а забирая его: при создании ресурса `Canary` оператор делает копию-`primary`, переводит на неё весь трафик, а исходный Deployment масштабирует в ноль — «by default all traffic is routed to this version and the target deployment is scaled to zero». Дальше любое изменение исходного Deployment он трактует как заявку на релиз и гонит анализ сам.

```yaml
analysis:
  interval: 1m        # шаг расписания, по умолчанию 60s
  threshold: 5        # сколько неудачных проверок до отката
  stepWeight: 10      # на сколько увеличивать вес за шаг
  maxWeight: 50       # до какого веса дойти перед промоутом
  metrics: [{ name: request-success-rate, thresholdRange: { min: 99 }, interval: 1m }]
```

Критерий выбора между ними ровно один: **кто владеет объектом рабочей нагрузки**. Argo Rollouts требует переписать `Deployment` в `Rollout` — ваш GitOps-репозиторий меняется, зато раскатка описана явным списком шагов. Flagger оставляет `Deployment` на месте и добавляет свой ресурс рядом — но реальным владельцем подов становится оператор, а поведение задаётся параметрами, а не шагами. Первое лучше, когда шаги разные для разных сервисов; второе — когда политика одна на весь кластер и её хочется задать один раз.

A/B-режим у Flagger — это поля `iterations` и `match` (условия по заголовкам) вместо роста веса.

## 9. Когда это неправильный ответ

- **Миграция схемы, несовместимая со старой версией.** Любая из схем держит две версии кода одновременно; несовместимая миграция ломает одну из них гарантированно. Сначала совместимая миграция ([`RELEASE_STRATEGIES.md` §7](../../engineering-process/theory/RELEASE_STRATEGIES.md)), потом раскатка.
- **Мало трафика.** Ночью на 0.5 rps канарейка в 5% набирает 90 запросов за час. Автоматический анализ на таких числах — генератор случайных вердиктов.
- **Состояние в подах и липкие сессии.** Если пользователь закреплён за подом, доля трафика перестаёт быть долей пользователей, а откат выбрасывает сессии.
- **Асинхронная работа.** Потребитель очереди не получает «5% трафика» — он получает сообщения. Вес в маршруте на него не действует; долю задаёт число потребителей и их скорость.
- **Один экземпляр сервиса.** Ни одна схема не работает на `replicas: 1`: любая из них требует, чтобы две версии жили одновременно.

## 10. Шпаргалка

| Что нужно | Механизм | Чем платите |
|---|---|---|
| Просто обновить без простоя | `RollingUpdate` + пробы | нет гейта, едет до конца |
| Грубая канарейка без новых инструментов | два Deployment, один Service | шаг доли = `1/N` подов |
| Точная доля трафика | `weight` в `HTTPRoute` / VirtualService | нужен шлюз или mesh |
| Сегмент пользователей | `matches.headers` | две версии живут долго |
| Мгновенный откат | blue-green | двойной ресурс, общая схема БД |
| Шаги с паузами и анализом | Argo Rollouts | `Deployment` → `Rollout` |
| Одна политика на кластер | Flagger | подами владеет оператор |

**Дерево решений.** Нет метрики здоровья → канарейка не нужна, нужна метрика. Есть метрика, но мало трафика → blue-green с ручным переключением. Есть метрика и трафик → канарейка с анализом. Нужен сегмент, а не доля → A/B, и это не релиз, а эксперимент.

### Формулировки для собеседования

- «`RollingUpdate` управляет скоростью замены подов, а не долей трафика: остановиться на 10% и подождать он не умеет.»
- «Без управления трафиком доля канарейки равна `1/N` по числу подов — на трёх репликах минимальная канарейка это 33%.»
- «`weight` в Gateway API — это доли от суммы весов, а не проценты, и по умолчанию он равен единице.»
- «Длину шага канарейки задаёт число запросов, которое попадёт на новую версию, а не круглая цифра в минутах.»
- «Blue-green не спасает от несовместимой миграции: он гарантирует, что старая версия в этот момент жива.»
