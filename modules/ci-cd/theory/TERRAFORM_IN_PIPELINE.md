# Terraform в конвейере: почему `apply` — не такой же шаг, как раскатка

> **Какую проблему решает.** Шаг раскатки и шаг `terraform apply` выглядят в конвейере одинаково, но
> худший исход первого — нерабочая версия сервиса, а второго — удалённая база данных.
> **Кому это надо.** Тому, кто пишет задание с Terraform и должен объяснить, почему `plan` и `apply`
> живут в разных заданиях и что будет, если два конвейера инфраструктуры стартуют одновременно.
> **Когда НЕ надо.** Если ваш Terraform создаёт три файла и ничего с состоянием, вся церемония —
> накладные расходы; и ничто здесь не делает `apply` безопасным: разнесение по заданиям лишь сужает
> класс отказов «применилось не то, что смотрели».

**Границы.** Кто владеет применением, обнаружение расхождения и Ansible —
[`IAC_OWNERSHIP.md`](IAC_OWNERSHIP.md). Устройство состояния, удалённый `backend` и расхождение
(drift) как явление — [`CLOUD.md` §12](../../infrastructure/theory/CLOUD.md); права токена и доступ в
облако без хранимого ключа — [`PIPELINE_CREDENTIALS.md` §2, §4, §5](PIPELINE_CREDENTIALS.md).

Выводы команд сняты на Terraform v1.16.0, macOS 15, на учебной конфигурации с локальным провайдером.

---

## 1. Почему `apply` из конвейера страшнее раскатки приложения

Откат есть у обоих шагов, но разница не в скорости, а в том, **что физически остаётся после отката**.

| Что откатываем | Где лежит прежнее состояние | Цена |
|---|---|---|
| Раскатка приложения | образ в реестре по дайджесту — неизменяем | 29,9 с в Swarm ([`DEPLOY_SWARM.md` §2](DEPLOY_SWARM.md)) |
| `apply`, меняющий ресурс на месте | прежнее значение атрибута в конфигурации | как у прямого применения |
| `apply`, пересоздающий ресурс | **нигде**: данные исчезли вместе с объектом | невосстановимо |

Третья строка появляется не по вашей воле. Terraform выбирает одно из четырёх действий — create,
destroy, update in-place и «destroy and re-create resources … which cannot be updated in-place **due
to remote API limitations**», — и решает последнее удалённый API провайдера, а не вы. Поэтому правка
одной строки может означать «обновить поле», а может — «удалить объект и создать заново»; для
экземпляра базы данных второе значит, что данные исчезли, а откат конфигурации воссоздаст ресурс с
тем же именем и пустым.

Симметрия теряется в одном месте: у раскатки предыдущее состояние **хранится отдельно от команды
раскатки** (образ в реестре, ревизия в Kubernetes, стек в Swarm), а у `apply` внешнего хранилища
содержимого нет — Terraform помнит описание ресурса и идентификаторы, но не то, что внутри лежало.
**Обратимо описание, а не содержимое.** Вторая асимметрия — права: шагу раскатки хватает одного
пространства имён, `apply` создаёт и удаляет ресурсы в аккаунте
([`PIPELINE_CREDENTIALS.md` §4](PIPELINE_CREDENTIALS.md)).

**Правило.** Спрашивайте не «как быстро шаг откатывается», а «что останется после отката».
Механическая часть пишется в конфигурации: с `lifecycle { prevent_destroy = true }` «Terraform
rejects plans that would destroy the infrastructure object … and returns an error», причём при
построении плана — проверка стоит в коде, а не в инструкции для дежурного.

## 2. `plan` как артефакт ревью

Ревьюер читает дифф конфигурации, после слияния задание выполняет `terraform apply -auto-approve`.
Ломается это дважды, и оба раза молча. Первое: дифф конфигурации не является предсказанием —
результат `apply` есть функция трёх входов (конфигурация, переменные, фактическое состояние), а
ревьюер видел первый. Terraform предупреждает об этом сам:

```
Note: You didn't use the -out option to save this plan, so Terraform can't
guarantee to take exactly these actions if you run "terraform apply" now.
```

Второе: `apply` в отдельном задании — отдельный процесс, а задания не делят состояние
([`PIPELINE_MODEL.md` §2](PIPELINE_MODEL.md)), поэтому без артефакта второе задание строит свой план.
На учебной конфигурации (`manifest_path` — её единственный ресурс, он показывает, какое окружение
фактически выделено):

```
$ terraform plan  -var-file=dev.tfvars       →  + manifest_path = "./out/dev.json"
$ terraform apply -var-file=staging.tfvars   →  manifest_path = "./out/staging.json"
$ ls out/                                    →  staging.json
```

**Ревьюер утвердил план на dev — применился staging.** Ни ошибки, ни предупреждения, ни отличия в
коде возврата: `apply` без сохранённого плана считает план заново по входам момента применения, а
роль `-var-file` в конвейере играет что угодно — переменная окружения, значение из хранилища
секретов, ветка ручного запуска. `-out` превращает план в файл, и `apply` становится исполнением
чужого решения:

```yaml
plan:  { script: [terraform plan -out=tfplan -var-file=$ENV.tfvars],
         artifacts: { paths: [tfplan] } }   # артефакт, не кэш: нет плана — apply не стартует
apply: { needs: [plan], when: manual,       # ворота здесь, а не внутри terraform
         script: [terraform apply tfplan] } # ни -var-file, ни -auto-approve: вход один
```

Разница артефакта и кэша принципиальна ([`PIPELINE_CACHE_AND_CONCURRENCY.md` §2](PIPELINE_CACHE_AND_CONCURRENCY.md)):
нет кэша — замедление, нет артефакта — отказ. Безопасным план делает **одноразовость**: `Error: Saved
plan is stale … the state was changed by another operation`. План — не сценарий, а утверждение «при
**вот этом** состоянии сделать вот это»: состояние изменилось — утверждение неверно, и потому план
годится предметом ревью. Двух вещей он не даёт — гарантии, что мир не изменился между `plan` и
`apply` («always re-check the final non-speculative plan before applying»), и секретности: значения
«will be saved in cleartext in the plan file … **even if obscured in Terraform's terminal output**»,
а артефакт задания скачает любой, у кого есть доступ к репозиторию
([`PIPELINE_CREDENTIALS.md` §3](PIPELINE_CREDENTIALS.md)).

**Правило.** Разносить `plan` и `apply` по заданиям имеет смысл только с `-out`: без него одобряют
один текст, применяется другой, и несовпадение ничем не проявится.

## 3. Конвейер приложения против конвейера инфраструктуры

Код и конфигурация лежат в одном репозитории, и соблазн — один конвейер на всё. Не совпадают две
величины. **Каданс:** приложение меняется на каждый push (допущение модуля — 24 прогона в день,
[`PIPELINE_MODEL.md` §7](PIPELINE_MODEL.md)), инфраструктура — единицы раз в месяц, поэтому задание
Terraform либо выполняет `plan` на каждом из 24 прогонов, требуя прав читать состояние, либо
пропускается по условию — и это условие и есть граница, записанная неявно. **Планка одобрения:**
`apply` стоит за ручными воротами ([`PIPELINE_CREDENTIALS.md` §5](PIPELINE_CREDENTIALS.md)), так
что в одном графе либо правка текста ждёт человека с кнопкой, либо ворота ослабляют для всех.

Граница проходит не по репозиториям: разделять надо **триггер и права токена**. Один репозиторий
вполне несёт два конвейера — по каталогу с кодом и по каталогу с конфигурацией
([`PIPELINE_THROUGHPUT.md` §3](PIPELINE_THROUGHPUT.md)), причём первому не нужен доступ в облако, а
второму — к реестру образов. Более жёсткий довод — **направление зависимости**: приложению нужен
экземпляр базы, чтобы запуститься, базе приложение не нужно, поэтому конвейер, где `apply` стоит
после раскатки, описывает обратный порядок.

**Правило.** Один конвейер законен, только когда обе величины совпали — так бывает у окружений,
живущих вместе с пулл-реквестом
([`ENVIRONMENT_ANATOMY.md` §3](ENVIRONMENT_ANATOMY.md)).

## 4. Окружения: workspaces против отдельных директорий

Три окружения с почти одинаковой конфигурацией раскладывают в один каталог и три `workspace`:
дублирования ноль, добавление окружения — одна команда. Это буквально конструкция из §2, в которой
применился не тот стенд: какое окружение затронуто, определяют два изменяемых входа (`workspace` и
файл переменных), а конфигурация физически одна, так что ошибка не поймается ничем — файлы те же,
команда та же, каталог тот же.

Документация предупреждает дважды: «CLI workspaces within a working directory use the same backend,
so they are **not a suitable isolation mechanism**» и они «not appropriate for … deployments requiring
separate credentials and access controls». «Тот же `backend`» и есть вся суть: один `backend` —
одни креденшелы и одни права, поэтому задание, способное применить в dev, **технически способно
применить в staging**, и разница между исходами есть значение переменной, а не разрешение. Отдельные
директории дают цепочку «своя директория → свой `backend` → своя роль в облаке» и убирают скрытое
состояние ценой дублирования корневой конфигурации, снижаемого выносом общей части в модуль.

| Что должно быть правдой | Что из этого следует |
|---|---|
| Окружения различаются кругом лиц с доступом | Отдельные директории: разные `backend` — разные креденшелы |
| Экземпляры одинаковы по правам и создаются пачками | Workspaces: нужна изоляция состояния, изоляция прав — нет |
| Ошибочный `apply` не в то окружение должен быть **невозможен**, а не «маловероятен» | Отдельные директории |
| Нужно быстро завести четвёртое одинаковое окружение | Workspaces: дешевле; но проверьте первую строку |

**Правило.** `workspace` изолирует состояние и ничего больше; как только между окружениями появляется
граница по правам — а между staging и dev она появляется всегда, — разделяйте конфигурации, а не
имена `workspace`.

## 5. Блокировка состояния и два конвейера, стартовавших одновременно

Два пулл-реквеста слиты с разницей в двадцать секунд, оба конвейера дошли до `apply`. Ответ «второй
увидит результат первого» неверен: чтение и запись состояния разнесены на всю длительность
применения. Без блокировки оба прочитали `S`; первый записал `S + A`; второй, не зная про `A`,
записал `S + B` **поверх**. Ресурс `A` существует и оплачивается, но в состоянии его нет — и дальше
хуже: следующий `plan` предложит создать `A` заново и упрётся в занятое имя либо создаст второй
экземпляр. Порча проявляется не сразу, а через несколько дней.

Блокировка превращает «прочитал — применил — записал» в критическую секцию: «state locking happens
automatically on all operations that could write state», и «if state locking fails, Terraform does
not continue» — второй `apply` не портит состояние, а ждёт или падает с явной ошибкой: отказ виден
сразу, повторный запуск задания решает вопрос. Это свойство **`backend`**, не самого Terraform
([`CLOUD.md` §12](../../infrastructure/theory/CLOUD.md)), а отключающий его флаг `-lock=false`
документация сопровождает прямым «we do not recommend it» — он безобиден ровно до первого дня, когда
сливают два пулл-реквеста подряд.

**Чего блокировка не делает — и это спрашивают.** Она **сериализует**, но не **согласовывает**: два
конвейера с расходящимися намерениями применятся один за другим, и выиграет последний; состояние
останется целым, а инфраструктура — не той, которую ожидал автор первого изменения. Второй слой даёт
сохранённый план из §2: построенный до применения первого, он отвергается как stale. **Блокировка
защищает файл состояния, `-out` защищает смысл изменения.** Бывает и блокировка процесса: Atlantis
держит директорию занятой «until the pull request is merged or closed», чтобы предмет ревью не
устаревал на глазах.

**Правило.** Удалённый `backend` с блокировкой — не «хорошая практика», а условие, при котором
`apply` вообще можно запускать из конвейера: тот по построению умеет запускать себя параллельно сам с
собой; ограничение конкурентности конвейера
([`PIPELINE_CACHE_AND_CONCURRENCY.md` §4](PIPELINE_CACHE_AND_CONCURRENCY.md)) его дополняет, но не заменяет.

## 6. Шпаргалка

| Симптом | Что на самом деле сломано |
|---|---|
| «Утвердили план на dev, применилось в staging» | `apply` без `-out`: план считается заново на входах момента применения (§2) |
| «Второй `apply` того же файла отвергнут: Saved plan is stale» | Так и задумано: план — утверждение о состоянии, одноразовое (§2, §5) |
| «`plan` предлагает создать то, что уже есть» | Состояние перезаписано параллельным применением — не было блокировки (§5) |
| «Ошиблись переменной — тронули не то окружение» | Одна конфигурация на все окружения: `workspace` изолирует состояние, не права (§4) |
| «Правка кода ждёт человека с кнопкой» | Конвейер приложения слит с конвейером инфраструктуры (§3) |

**Как разложить окружения (§4).** Окружения различаются кругом лиц с доступом? → отдельные директории
и отдельные `backend`. Экземпляры одинаковы и создаются пачками? → `workspace`.

### Формулировки для собеседования

- «`apply` необратим не по времени отката, а физически: откат конфигурации воссоздаёт описание
  ресурса, но не его содержимое».
- «Сохранённый план — не сценарий, а утверждение «при вот этом состоянии сделать вот это»; поэтому он
  одноразовый, и поэтому его можно утверждать на ревью».
- «Блокировка защищает файл состояния, `-out` защищает смысл изменения; нужны оба».
- «`workspace` изолирует состояние и ничего больше — общий `backend` означает общие права».
