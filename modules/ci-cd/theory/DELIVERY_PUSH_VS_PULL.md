# Доставка толчком и вытягиванием: кто применяет изменение в кластере

> **Какую проблему решает.** У задания `deploy-staging` в переменных лежит `kubeconfig` с правами на запись в прод, а через полгода никто не скажет, что сейчас развёрнуто на staging: «у кого ключи» и «где истина» решает один разворот направления доставки.
> **Кому это надо.** Тому, кто настраивает раскатку в Kubernetes и должен объяснить безопаснику, почему у конвейера нет доступа в кластер.
> **Когда НЕ надо.** Вытягивание требует декларативного состояния: раскатка-последовательность действий в манифест не превращается, а один сервис в одном кластере не окупает второй репозиторий и бот-коммиты.

**Границы.** Устройство репозитория конфигурации, продвижение пулл-реквестом и откат через `git revert` — [`GITOPS_REPOSITORIES.md`](GITOPS_REPOSITORIES.md). Механика применения и ожидание готовности — [`DEPLOY_TO_K8S.md`](DEPLOY_TO_K8S.md); что продвигается между окружениями — [`ENVIRONMENTS_AND_PROMOTION.md` §1, §4](ENVIRONMENTS_AND_PROMOTION.md). Постоянные креденшелы и OIDC-федерация — [`PIPELINE_CREDENTIALS.md` §1, §2](PIPELINE_CREDENTIALS.md); согласование как механизм контроллеров — [`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md).

## 1. Конвейер с креденшелами кластера против агента внутри кластера

Конвейер собрал образ и знает дайджест. Осталось применить новое в кластере — и самый частый ответ на «кто это делает» звучит «конвейер сам»:

```yaml
      - run: helm upgrade --install payments ./payments -f ./payments/values-qa.yaml
               --set image.digest="${{ needs.image.outputs.digest }}"
```

Это **доставка толчком (push)**: внешняя система пишет в целевую среду. Она понятна и отлаживается по журналу одного прогона, но ломается в двух местах — и не сразу.

*Учётные данные.* Чтобы `helm upgrade` сработал, у задания нужны права на запись в кластер, а хранить их можно только в секретах системы сборки — право менять прод оказывается **снаружи прода**, в системе, исполняющей чужой код из репозитория. Долгоживущий ключ в переменных конвейера — инцидент, а не настройка: добраться до него можно и без прав на слияние, через инъекцию в контекст события ([`PIPELINE_CREDENTIALS.md` §1](PIPELINE_CREDENTIALS.md), [`SUPPLY_CHAIN_ATTACKS.md` §1](SUPPLY_CHAIN_ATTACKS.md)).

*Направление соединения.* Толчок требует, чтобы API-сервер кластера был достижим с исполнителя — для управляемого это сервер, открытый в интернет, с адресов, которые вы не контролируете. Кластер, не отвечающий снаружи, толчком с чужой машины не раскатать.

**Разворот направления.** Внутри кластера работает агент, который сам читает желаемое состояние и приводит к нему живое — **доставка вытягиванием (pull)**:

> «Pulled Automatically: Software agents automatically pull the desired state declarations from the source.» «Continuously Reconciled: Software agents continuously observe actual system state and attempt to apply the desired state.»
>
> — OpenGitOps, принципы v1.0.0

> «Target state: The desired state of an application, as represented by files in a Git repository.» «Live state: The live state of that application. What pods etc are deployed.» «Sync: The process of making an application move to its target state.»
>
> — Argo CD docs, «Core Concepts»

Ключевое слово — target state: желаемое состояние это **файлы в репозитории**, а не команда, которую кто-то выполнил.

**Что меняется в правах.** Вытягивание не «убирает секрет» — оно его переносит и ослабляет:

| | Доставка толчком | Доставка вытягиванием |
|---|---|---|
| У конвейера есть | запись в кластер | запись в репозиторий конфигурации |
| У кластера есть | — | чтение репозитория, чтение реестра |
| Соединение инициирует | исполнитель снаружи → API-сервер | агент изнутри → Git и реестр |
| API-сервер доступен снаружи | да | нет |
| При компрометации системы сборки | злоумышленник меняет прод напрямую | злоумышленник делает коммит, видимый и ревьюируемый |

Последняя строка — главная: право писать в Git не равно праву менять прод — между ними стоят история, ревью и откат. Защита не абсолютна: коммит в основную ветку агент применит, — но это разница между «изменение произошло» и «изменение зафиксировано и обратимо одной командой».

**Чего это не делает.** Агент имеет права на всё в своей области видимости — компрометация репозитория конфигурации равна компрометации `kubeconfig`. Раскатку разворот не ускоряет, а добавляет задержку на обнаружение изменения (§2).

**Правило.** Выбор между толчком и вытягиванием — ответ на «где лежит креденшел, дающий право менять прод». Толчок кладёт его снаружи, требуя, чтобы кластер отвечал внешнему миру; вытягивание оставляет право внутри кластера и отдаёт наружу только запись в Git.

## 2. Согласование и расхождение: почему «истина в Git» — про восстановимость

Кластер staging потерян целиком. Восстановить его вчерашним «повторим последний зелёный прогон `deploy-staging`» не выйдет: журнал не вечен — прогон мог быть удалён по сроку хранения; команда не самодостаточна — `--set image.digest="${{ needs.image.outputs.digest }}"` ссылается на выход задания, которого больше нет; между раскатками кто-то правил `kubectl edit` руками, и последняя команда этого не отражает; а повторить пять `helm upgrade` в верном порядке — задача археологическая.

В модели вытягивания желаемое состояние — не последовательность команд, а **содержимое репозитория на ревизии**: восстановление — поднять пустой кластер, поставить агента, показать репозиторий. Дальше работает **согласование (reconciliation)** — сравнение живого состояния с желаемым; отличие называется **расхождением (drift)**. Та же форма, что у контроллеров Kubernetes ([`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md)), уровнем выше: контроллер приводит поды к `Deployment`, агент — объекты кластера к Git.

> «Sync status: Whether or not the live state matches the target state.» «Refresh: Compare the latest code in Git with the live state. Figure out what is different.»
>
> — Argo CD docs, «Core Concepts»

**«Истина в Git» — не лозунг, а конъюнкция двух настроек, и по умолчанию обе выключены:**

> «By default, automated sync will not delete resources when Argo CD detects the resource is no longer defined in Git.» «By default, changes that are made to the live cluster will not trigger automated sync» — устраняет расхождение только `selfHeal`.
>
> — Argo CD docs, «Automated Sync Policy»

Без `prune` удаление из Git не удаляет из кластера — Git описывает то, что **есть**, но не то, чего **нет**. Без `selfHeal` ручная правка живёт неограниченно долго: расхождение видно как `OutOfSync`, но не устраняется.

| Окружение | `prune` | `selfHeal` | Что это значит |
|---|---|---|---|
| dev | `true` | `true` | Git — полное описание; правка живёт до следующего цикла |
| qa | `true` | `false` | удаления работают; ручная правка сохраняется, видна |
| staging | блока `automated` нет | | Git — цель, но применяет её человек |

Средняя строка не недоделка: тестировщик может временно поменять что-то руками, и `selfHeal` откатил бы правку посреди проверки — расхождение остаётся видимым, просто не устраняется молча.

**Правило.** «Истина в Git» окупается в одном сценарии — когда состояние надо **восстановить**. Держится это на двух настройках, а не на факте наличия репозитория; выключив любую, вы меняете «Git описывает окружение» на «Git описывает часть окружения».

## 3. Argo CD против Flux

Сравнивать агентов по списку функций бессмысленно — такая таблица устаревает за квартал. Содержательная разница — **единица описания**: какой объект вы заводите, когда хотите что-то развернуть.

У Argo CD единица — одно приложение, один ресурс:

> «Application: A group of Kubernetes resources as defined by a manifest. This is a Custom Resource Definition (CRD).»
>
> — Argo CD docs, «Core Concepts»

Источник (`repoURL`, `targetRevision`, `path`), назначение (`server`, `namespace`) и политика согласования (`syncPolicy`) собраны в одном манифесте: одно приложение — один объект — один экран.

У Flux единица мельче, и объектов несколько:

> «Flux is constructed with the GitOps Toolkit components… The APIs comprise Kubernetes custom resources, which can be created and updated by a cluster user, or by other automation tooling.»
>
> — Flux docs, «Components»

Документация перечисляет контроллеры: source-controller, kustomize-controller, helm-controller, notification-controller, автоматизация образов. «Откуда брать» и «что делать» — **разные ресурсы**, связанные ссылкой; один источник обслуживает нескольких потребителей.

| Что должно быть правдой | Что из этого следует |
|---|---|
| нужен один экран, где видно приложение целиком | Argo CD: приложение — один объект со своим интерфейсом |
| один источник обслуживает много потребителей | Flux: источник и применение — отдельные ресурсы |
| управление должно идти только через Kubernetes API | Flux: отдельного интерфейса среди компонентов нет |
| нужно «новый образ в реестре → обновить» без бот-коммита | Flux: для этого названы отдельные контроллеры автоматизации образов |

**Оговорка важнее сравнения.** Направление доставки, согласование, разделение репозиториев, продвижение и откат через `git revert` ([`GITOPS_REPOSITORIES.md`](GITOPS_REPOSITORIES.md)) от этого выбора **не зависят** — модель одна, различается форма записи. «Argo CD или Flux» стоит в списке решений последним и дёшево; «толчок или вытягивание» — первым и дорого.

**Правило.** Сравнивайте не набор функций, а границу объекта: у Argo CD приложение — один ресурс, у Flux оно собрано из нескольких контроллеров.

## 4. Чего GitOps не решает

Модель ровно настолько широка, насколько широко определение: агент приводит **набор объектов кластера** к тому, что записано декларативно. Четыре вещи в это не помещаются.

*Миграции схемы.* База — не объект кластера, а у конвейера нет доступа к ней (§1): из трёх мест для миграции ([`ENVIRONMENTS_AND_PROMOTION.md` §7](ENVIRONMENTS_AND_PROMOTION.md)) первое недоступно — выбор сужается до init-контейнера или хука жизненного цикла. «Выполни раньше того» тоже не свойство согласования: агент приводит объекты к состоянию, а не выполняет сценарий.

*Секреты.* Структурный конфликт: модель требует желаемое состояние в Git, секрет — часть этого состояния, а класть его в Git открытым текстом нельзя. Кодирование `Secret` — не шифрование ([`SECRETS.md`](../../infrastructure/theory/SECRETS.md)). Секреты вынесены наружу — «восстановление = Git плюс агент» (§2) уже неточно: нужны **два** источника.

*Порядок между сервисами.* Согласование — сходимость, а не последовательность: каждый объект приводится к состоянию независимо и в произвольном порядке, «A раньше B» модель выразить не может. Правильная реакция — убрать зависимость от порядка: сервис, не переживающий отсутствие соседа при старте, сломается и без GitOps ([`FAILURE_ISOLATION.md`](../../microservices/theory/FAILURE_ISOLATION.md)).

*«Синхронизировано» не значит «работает».* `Sync status` отвечает на «совпадает ли с Git», а не «отвечает ли сервис» и не «растёт ли число ошибок». Манифест с образом-дефектом даёт `Synced` при полностью неработающем сервисе — сигналом успеха должны быть здоровье нагрузки и метрики приложения ([`KUBERNETES.md` §10](../../infrastructure/theory/KUBERNETES.md)).

**Правило.** GitOps решает одну задачу — где записано желаемое состояние набора объектов и кто его применяет. Не выполняет миграции, не хранит секреты, не задаёт порядок между сервисами, не отвечает «работает ли» и не ускоряет раскатку.

## 5. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Что на самом деле выбирается | не инструмент, а место, где лежит право менять прод |
| Что нужно конвейеру при толчке | учётные данные на запись в кластер и доступный снаружи API-сервер |
| Что нужно конвейеру при вытягивании | право записи в репозиторий конфигурации, и больше ничего |
| Кто инициирует соединение при вытягивании | агент изнутри кластера — наружу, к Git и реестру |
| На чём держится «истина в Git» | на `prune` и `selfHeal`; по умолчанию оба выключены |
| Что значит `prune: false` | Git описывает то, что есть, но не то, чего быть не должно |
| Что значит отсутствие блока `automated` | Git — цель, но применяет её человек: точка согласования |
| Модельная разница Argo CD и Flux | одно приложение — один ресурс против набора отдельных контроллеров |
| Что `Synced` не означает | что сервис работает: статус про совпадение с Git, а не про здоровье |

### Формулировки для собеседования

- «Толчок означает, что учётные данные прода лежат снаружи прода — в системе, исполняющей код из репозитория; вытягивание оставляет их внутри кластера и отдаёт наружу только запись в Git».
- «"Истина в Git" — это не факт наличия репозитория, а две настройки: без `prune` удаления не работают, без `selfHeal` ручная правка живёт вечно».
- «Argo CD и Flux реализуют один принцип; разница — в единице описания: ресурс-приложение целиком против источника и потребителя как отдельных объектов».
- «GitOps не выполняет миграции, не хранит секреты, не задаёт порядок между сервисами и не отвечает на вопрос "работает ли" — `Synced` говорит только о совпадении с Git».
