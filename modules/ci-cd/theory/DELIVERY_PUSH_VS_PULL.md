# Доставка толчком и вытягиванием: кто применяет изменение в кластере

> **Какую проблему решает.** У задания `deploy-staging` в переменных конвейера лежит `kubeconfig` с
> правами на запись в кластер. Это работает — и означает, что учётные данные вашего прода живут
> снаружи прода, в системе сборки, куда пишет код каждый разработчик. Вторая половина той же
> проблемы: полгода спустя никто не может сказать, что именно сейчас развёрнуто на staging, потому
> что поверх раскаток конвейера кто-то трижды правил ресурсы руками, а `helm upgrade` из журнала
> прогона трёхмесячной давности не воспроизводит текущее состояние. Оба вопроса — «у кого ключи» и
> «где записано истинное состояние» — решаются одним разворотом направления доставки.
> **Кому это надо.** Тому, кто настраивает раскатку в Kubernetes и должен объяснить безопаснику,
> почему у конвейера нет доступа в кластер; тому, кого спросят «что такое GitOps и что конкретно
> оно вам дало, кроме нового инструмента».
> **Когда НЕ надо.** Доставка вытягиванием (pull) требует, чтобы желаемое состояние было
> **декларативным**.
> Раскатка, которая по существу является последовательностью действий — прогреть кэш, переключить
> запись, дождаться дренажа очереди, потом переключить чтение, — в манифест не превращается, и
> агент согласования её не выразит. Отдельно: один сервис в одном кластере не окупает агента,
> второго репозитория и бот-коммитов; здесь `helm upgrade` из конвейера честнее.

**Границы с соседними файлами.** Правило «собрать один раз, продвигать тот же артефакт», три
окружения и место миграции схемы — в
[`ENVIRONMENTS_AND_PROMOTION.md` §1, §4, §7](ENVIRONMENTS_AND_PROMOTION.md); этот файл отвечает не
на «что продвигается», а на «кто физически применяет». **Механика применения** —
`kubectl apply` против `helm upgrade --atomic` против синхронизации Argo CD, ожидание готовности и
откат в каждом из трёх способов — в [`DEPLOY_K8S_AND_SWARM.md`](DEPLOY_K8S_AND_SWARM.md); здесь
разбирается только направление и то, у кого при этом права. Почему у конвейера не должно быть
постоянных креденшелов и что такое OIDC-федерация — в
[`SUPPLY_CHAIN_SECURITY.md` §1, §2](SUPPLY_CHAIN_SECURITY.md). Устройство чарта и шаблонизация —
[`HELM.md` §2, §3](../../infrastructure/theory/HELM.md); цикл согласования как общий механизм
контроллеров Kubernetes — [`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md): термин
здесь используется, а не переопределяется. Хранение секретов вне Git —
[`SECRETS.md`](../../infrastructure/theory/SECRETS.md). Откат против наката и совместимые миграции —
[`RELEASE_STRATEGIES.md` §6, §7](../../engineering-process/theory/RELEASE_STRATEGIES.md).

**Сквозной пример.** Сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, пик
40 запросов в секунду. Учебная конфигурация окружений — `pipelines/kustomize/` (база и три
overlay), учебные манифесты агента — `pipelines/argocd/payments-dev.yaml`, `payments-qa.yaml`,
`payments-staging.yaml`. Три последних различаются **ровно моделью согласования** и потому служат
основной иллюстрацией файла.

Вывод в блоках — настоящий, из прогона 8 журнала модуля: `kubectl kustomize` со встроенным
kustomize, macOS 15 (Darwin 25.6.0). Ничего в кластер не применялось: прогон только рендерит
манифесты. Поэтому всё, что касается **поведения** Argo CD, подпёрто цитатой документации, а не
прогоном, — и это отмечено в тексте.

## 1. Конвейер с креденшелами кластера против агента внутри кластера

**Задача.** Конвейер собрал образ и знает его дайджест
([`ENVIRONMENTS_AND_PROMOTION.md` §1](ENVIRONMENTS_AND_PROMOTION.md)). Осталось, чтобы в кластере
поехало новое. Кто выполняет само действие?

**Наивное решение — и оно же самое распространённое.** Конвейер сам. Ровно так устроено задание
`deploy-qa` в `pipelines/github/ci.yml`:

```yaml
      - run: |
          helm upgrade --install payments ./modules/ci-cd/pipelines/helm/payments \
            -f ./modules/ci-cd/pipelines/helm/payments/values-qa.yaml \
            --set image.digest="${{ needs.image.outputs.digest }}"
```

Это **доставка толчком (push)**: внешняя система выполняет запись в целевую среду. Она понятна,
отлаживается по журналу одного прогона и не требует ничего, кроме того, что уже есть.

**Где ломается.** Не в том, что не работает, — работает. Ломается в двух местах, и оба вылезают не
сразу.

*Первое: чтобы `helm upgrade` сработал, у задания должны быть учётные данные на запись в кластер.*
Хранить их можно только в секретах системы сборки. Это переворачивает картину прав наизнанку:
самый ценный доступ в организации — право менять прод — лежит **снаружи прода**, в системе, которая
по своему назначению исполняет код из репозитория. Насколько это опасно, разобрано в
[`SUPPLY_CHAIN_SECURITY.md` §1, §5](SUPPLY_CHAIN_SECURITY.md): долгоживущий ключ в переменных
конвейера — инцидент, а не настройка, и добраться до него можно, не имея прав на слияние.

*Второе: направление сетевого соединения.* Толчок требует, чтобы API-сервер кластера был достижим с
исполнителя. Для управляемого исполнителя это означает API-сервер, открытый в интернет: список
адресов, с которых придёт задание, вы не контролируете. Кластер, который никому снаружи не отвечает,
раскатать толчком с чужой машины нельзя в принципе.

**Механизм — развернуть направление.** Вместо того чтобы внешняя система писала в кластер, внутри
кластера работает агент, который сам читает желаемое состояние и приводит к нему живое. Это
**доставка вытягиванием (pull)**, и она сформулирована как принцип:

> «Pulled Automatically: Software agents automatically pull the desired state declarations from the
> source.»
> «Continuously Reconciled: Software agents continuously observe actual system state and attempt to
> apply the desired state.»
>
> — OpenGitOps, принципы v1.0.0

Что при этом становится объектами модели, видно из словаря Argo CD:

> «Target state: The desired state of an application, as represented by files in a Git repository.»
> «Live state: The live state of that application. What pods etc are deployed.»
> «Sync: The process of making an application move to its target state.»
>
> — Argo CD docs, «Core Concepts»

Обратите внимание на формулировку target state: желаемое состояние — это **файлы в репозитории**, а
не команда, которую кто-то выполнил. Отсюда всё остальное в этом файле.

**Что меняется в правах.** Соблазнительно сказать, что доставка вытягиванием «убирает секрет». Нет —
она его **переносит и ослабляет**:

| | Доставка толчком | Доставка вытягиванием |
|---|---|---|
| У конвейера есть | запись в кластер | запись в репозиторий конфигурации |
| У кластера есть | — | чтение репозитория, чтение реестра |
| Соединение инициирует | исполнитель снаружи → API-сервер | агент изнутри → Git и реестр |
| API-сервер должен быть доступен снаружи | да | нет |
| При компрометации системы сборки | злоумышленник меняет прод напрямую | злоумышленник делает коммит, который виден и ревьюируем |

Последняя строка — главная. Право писать в Git не эквивалентно праву менять прод: между коммитом и
кластером стоит история, ревью и возможность отката. Это не абсолютная защита (коммит в основную
ветку конфигурации агент применит), но это разница между «изменение произошло» и «изменение
произошло, зафиксировано, подписано автором и может быть отменено одной командой».

В учебном манифесте модуля граница названа прямо:

```yaml
# Конвейер приложения сюда не ходит вообще — он останавливается на том, что
# записал новый дайджест в overlays/dev репозитория конфигурации. Дальше Argo CD
# сам замечает расхождение между Git и кластером и устраняет его.
# Креденшелов кластера у конвейера при этом нет — в этом весь смысл модели.
```

(`pipelines/argocd/payments-dev.yaml`)

**Чего этого не делает.** Разворот направления не отменяет необходимости доверять кому-то: агент
внутри кластера имеет права на изменение всего, что описано в его области видимости, и компрометация
репозитория конфигурации даёт ровно то же, что компрометация `kubeconfig`. Он также не делает
раскатку быстрее — наоборот, добавляет задержку на обнаружение изменения (§2). Выигрыш здесь не в
скорости и не в безопасности «вообще», а в том, **где именно проходит граница доверия**.

**Правило.** Выбор между толчком и вытягиванием — это не выбор инструмента, а ответ на вопрос
«где должен лежать креденшел, дающий право менять прод». Толчок кладёт его снаружи и требует, чтобы
кластер отвечал внешнему миру; вытягивание оставляет право внутри кластера, а наружу отдаёт только
запись в Git.

## 2. Согласование и расхождение: почему «истина в Git» про восстановимость

**Задача.** Кластер staging потерян целиком: ошибочно удалили пространство имён, отвалился регион,
неважно. Восстановите его в том виде, в каком он был вчера.

**Наивное решение.** У нас есть журналы конвейера. Найдём последний зелёный прогон `deploy-staging`,
посмотрим, какая команда `helm upgrade` выполнялась, и повторим её.

**Где ломается — четырьмя способами, и все четыре обнаруживаются в худший момент.**

*Журнал не вечен.* Прогоны и их артефакты хранятся ограниченный срок; «последний зелёный» мог быть
три месяца назад и уже удалён вместе с выходами заданий.

*Команда не самодостаточна.* В строке стоит
`--set image.digest="${{ needs.image.outputs.digest }}"` — ссылка на выход задания, которого больше
нет. Значение подставлялось в момент исполнения и нигде не сохранилось.

*Последняя команда — не текущее состояние.* Между раскатками кто-то дважды выполнил `kubectl edit`
(увеличил лимит памяти в инциденте), а кто-то поставил рядом секрет руками. В журнале конвейера
этого нет вообще: журнал знает, что конвейер делал, и ничего не знает о том, что делали помимо него.

*Порядок не восстанавливается.* Повторить пять команд `helm upgrade` разных релизов в правильном
порядке и с правильными параметрами — задача археологическая, а не инженерная.

**Механизм.** В модели доставки вытягиванием желаемое состояние — это не последовательность команд,
а **содержимое репозитория на определённой ревизии**. Восстановление сводится к трём шагам: поднять
пустой кластер, поставить агента, показать ему репозиторий. Дальше работает согласование:

> «Continuously Reconciled: Software agents continuously observe actual system state and attempt to
> apply the desired state.»
>
> — OpenGitOps, принципы v1.0.0

Это ровно та же форма, что у контроллеров самого Kubernetes
([`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md)), поднятая на уровень выше:
контроллер приводит поды к тому, что записано в `Deployment`; агент приводит набор объектов кластера
к тому, что записано в Git. Термин тот же, и это не совпадение.

Отсюда два рабочих понятия. **Согласование (reconciliation)** — непрерывное сравнение живого
состояния с желаемым и приведение к нему. **Расхождение (drift)** — зафиксированное отличие живого
состояния от записанного. В словаре Argo CD это выражено через статус:

> «Sync status: Whether or not the live state matches the target state. Is the deployed application
> the same as Git says it should be?»
> «Refresh: Compare the latest code in Git with the live state. Figure out what is different.»
>
> — Argo CD docs, «Core Concepts»

**«Истина в Git» — не лозунг, а конъюнкция двух настроек.** Здесь легко обмануться: сам факт, что
манифесты лежат в Git, ничего не гарантирует. Гарантию дают два поведения агента, и **по умолчанию
оба выключены**:

> «By default (and as a safety mechanism), automated sync will not delete resources when Argo CD
> detects the resource is no longer defined in Git.»
> «By default, changes that are made to the live cluster will not trigger automated sync. To enable
> automatic sync when the live cluster's state deviates from the state defined in Git» — включается
> `selfHeal`.
>
> — Argo CD docs, «Automated Sync Policy»

Читается это так. Без `prune` удаление из Git не приводит к удалению из кластера — значит, Git
описывает то, что **есть**, но не то, чего **нет**, и полным описанием окружения не является. Без
`selfHeal` ручная правка в кластере живёт неограниченно долго: расхождение будет видно как
`OutOfSync`, но устранено не будет.

Именно эти две строки и различают три учебных манифеста модуля:

| Манифест | `prune` | `selfHeal` | Что это значит про «истину в Git» |
|---|---|---|---|
| `payments-dev.yaml` | `true` | `true` | Git — полное описание; ручная правка живёт до следующего цикла |
| `payments-qa.yaml` | `true` | `false` | удаления работают; ручная правка тестировщика сохраняется, расхождение видно |
| `payments-staging.yaml` | блока `automated` нет | | Git — цель, но применяет её человек |

Комментарий в `pipelines/argocd/payments-qa.yaml` объясняет, почему средняя строка не является
недоделкой:

```yaml
# Отличие от dev — одна строка, и она про людей, а не про технику: на qa тестировщик
# может временно поменять что-то руками, и selfHeal откатил бы правку посреди
# проверки. Расхождение при этом остаётся видимым в интерфейсе Argo CD
# (состояние OutOfSync) — его не прячут, его просто не устраняют молча.
```

**Оговорка о проверке.** Всё в этом разделе, что касается поведения Argo CD, подпёрто документацией,
а не прогоном: журнал модуля рендерит манифесты, но ничего не применяет в кластер. Считайте это
описанием документированного контракта, а не наблюдением.

**Правило.** «Истина в Git» окупается ровно в одном сценарии — когда состояние надо **восстановить**:
после потери кластера, при заведении второго региона, при расследовании «когда это изменилось».
И держится она на двух настройках, а не на факте наличия репозитория; выключая любую из них, вы
осознанно меняете утверждение «Git описывает окружение» на «Git описывает часть окружения».

## 3. Репозиторий приложения против репозитория конфигурации

**Задача.** Конвейер собрал образ, знает дайджест и в кластер не ходит (§1). Куда он тогда девает
дайджест — и откуда агент узнаёт, что появилась новая версия?

**Наивное решение.** Положить манифесты рядом с кодом, в тот же репозиторий, и направить агента
туда. Всё в одном месте: изменил код — изменил манифест — один пулл-реквест, одна история.

**Где ломается.** Тремя разными способами, и они не про вкус.

*Конвейер начинает запускать сам себя.* Чтобы записать новый дайджест, конвейер делает коммит. Этот
коммит — событие в том же репозитории, значит, он запускает конвейер, который соберёт образ и
сделает ещё один коммит. Лечится это пометками вроде `[skip ci]` и фильтрами по автору, то есть
конструкцией, которая держится на строке в сообщении коммита. Забыли фильтр в одном месте — получили
бесконечный цикл сборок; сделали фильтр слишком широким — перестали собираться настоящие изменения.

*История кода перестаёт читаться.* Каждая раскатка на каждое из трёх окружений — коммит. Через
полгода `git log` сервиса наполовину состоит из строк «chore: bump payments digest to sha256:…», и
`git bisect` по нему ведёт себя соответственно
([`BRANCHING_AND_CODE_FLOW.md` §5](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md)).

*Правила защиты у кода и у раскатки разные, а ветка одна.* Изменение кода ревьюит команда сервиса.
Изменение того, что работает на staging, может требовать другого согласующего — и уж точно другого
момента (`ENVIRONMENTS_AND_PROMOTION.md` §6). В одном репозитории с одной основной веткой эти два
потока получают одни и те же правила, то есть либо код ревьюится избыточно, либо продвижение —
недостаточно.

Есть и четвёртая причина, менее очевидная: **окружение — это не один сервис.** Вопрос «что сейчас
на staging» относится ко всему набору, а если конфигурация каждого сервиса лежит в его собственном
репозитории, ответ снова размазан по десяти местам — ровно та беда, от которой уходили в §2.

**Механизм — два репозитория с разными свойствами.**

| | Репозиторий приложения | Репозиторий конфигурации |
|---|---|---|
| Что описывает | как сервис работает | что развёрнуто и где |
| Кто меняет | разработчики | конвейер (бот) и тот, кто продвигает |
| Частота | каждая задача | каждая раскатка и каждое продвижение |
| Что означает коммит в основную ветку | «код изменился» | «состояние окружения должно измениться» |

Конвейер приложения заканчивается не раскаткой, а **бот-коммитом**: он записывает новый дайджест в
конфигурацию окружения dev. Этот коммит и есть точка перехода: всё до него — доставка толчком
(конвейер что-то делает), всё после — доставка вытягиванием (агент что-то забирает). Учебный
манифест называет обе стороны границы явно:

```yaml
  source:
    # Репозиторий КОНФИГУРАЦИИ, а не репозиторий приложения: у них разный
    # темп изменений и разный круг ревьюеров.
    repoURL: https://github.com/example/payments-config.git
    targetRevision: main
    path: kustomize/overlays/dev
```

(`pipelines/argocd/payments-dev.yaml`). Три поля — адрес, ревизия, путь — и есть полный ответ на
вопрос «где записано желаемое состояние»: репозиторий, ветка, каталог.

Заодно это ответ на вопрос про креденшелы из §1. Токен, который остался у конвейера, даёт запись в
`payments-config` и больше ничего. Он не открывает кластер, не открывает реестр и не позволяет
изменить код сервиса.

**Цена, о которой обычно молчат.** Обратная связь рвётся ровно по этой границе. Конвейер приложения
завершается зелёным сразу после бот-коммита — а сервис в этот момент ещё не развёрнут, и был ли
он развёрнут успешно, в прогоне не видно **никогда**. Разработчик, привыкший к «зелёный прогон =
поехало», получает зелёный прогон и неработающий dev. Восстанавливать эту связь приходится отдельно:
уведомлениями агента, статусом синхронизации на пулл-реквесте, эндпоинтом `/version`
(`ENVIRONMENTS_AND_PROMOTION.md` §3), который прямо отвечает, какой дайджест сейчас работает.

**Когда это неправильный ответ.** Два репозитория не обязаны быть двумя репозиториями. Если у
организации монорепозиторий, то же разделение делается каталогом с собственными правилами защиты и
собственным списком владельцев. Критерий не в числе репозиториев, а в том, **различаются ли у двух
потоков изменений частота, ревьюеры и триггер**. Если не различаются — разделение добавит бот-коммит
и не купит ничего.

**Правило.** Разделяются не файлы, а два разных утверждения: «код изменился» и «состояние окружения
должно измениться». Смешав их в одной истории, вы получаете конвейер, запускающий сам себя, и
`git log`, по которому нельзя ни читать код, ни узнать, что развёрнуто.

## 4. Продвижение как пулл-реквест между overlay окружений

**Задача.** Артефакт проверен на qa. Продвинуть его на staging. В модели доставки толчком это запуск
задания `deploy-staging`. Что это физически в модели вытягивания?

**Наивное решение.** Открыть интерфейс агента, выбрать приложение `payments-staging` и нажать
«синхронизировать».

**Где ломается.** Синхронизация ничего не продвигает. Она приводит staging к тому, что **записано
для staging**, а записана там прежняя версия. Нажатие даст `Synced` и ровно ту же самую старую
версию, что была. В модели вытягивания у агента нет и не может быть понятия «взять то, что стоит на
соседнем окружении»: он знает только свой каталог в репозитории.

**Механизм — продвижение есть изменение данных.** Конфигурация окружений модуля построена как база
плюс три overlay: `pipelines/kustomize/base/` описывает сервис без единого признака окружения,
`overlays/dev`, `overlays/qa`, `overlays/staging` добавляют то, что различается. Прогон 8 журнала
рендерит каждый overlay командой `kubectl kustomize` и даёт следующее (значимая часть вывода для
qa):

```
      containers:
      - env:
        - name: PAYMENTS_ENVIRONMENT
          value: qa
        - name: PAYMENTS_BUILD_DIGEST
          value: sha256:1111111111111111111111111111111111111111111111111111111111111111
        image: registry.example.com/payments@sha256:1111111111111111111111111111111111111111111111111111111111111111
```

Сводка по трём окружениям:

| overlay | namespace | replicas | дайджест в образе | requests.cpu |
|---|---|---|---|---|
| dev | payments-dev | 1 | `sha256:1111…1111` | 100m |
| qa | payments-qa | 2 | `sha256:1111…1111` | 250m |
| staging | payments-staging | 3 | `sha256:0000…0000` | 500m |

Прочитайте столбец с дайджестом: dev и qa несут **один и тот же**, staging — отстающий. Это и есть
снимок «артефакт прошёл dev и qa, но ещё не продвинут на staging», выраженный не статусом в чьей-то
базе, а содержимым файлов. Продвижение на staging — правка одной строки в
`overlays/staging/kustomization.yaml` так, чтобы дайджест совпал с qa. Ничего больше.

Отсюда три следствия, каждое из которых в модели толчка приходится строить отдельно:

- **Ревью.** Правка приезжает пулл-реквестом, значит, у неё есть автор, обязательный согласующий и
  обсуждение — тем же механизмом, что у кода. Отдельного механизма одобрения раскатки не нужно.
- **Аудит.** Вопрос «кто, когда и почему поставил на staging именно эту версию» отвечается
  `git log` по одному файлу, а не поиском по журналам прогонов с ограниченным сроком хранения.
- **Диффабельность.** Различие между окружениями — это буквально `diff` двух каталогов. Вопрос
  «чем qa отличается от staging» перестаёт быть исследованием.

**Цена, которую видно в том же прогоне.** У kustomize нет вычисляемых значений, поэтому дайджест
приходится записывать **дважды**: в преобразователе `images` и в патче, выставляющем переменную
`PAYMENTS_BUILD_DIGEST`. Прогон 8 фиксирует это отдельным пунктом: сослаться на первое значение из
второго места средствами kustomize нельзя — такой возможности нет. В чарте Helm то же самое
записывается один раз как `.Values.image.digest`
([`ENVIRONMENTS_AND_PROMOTION.md` §3](ENVIRONMENTS_AND_PROMOTION.md)). Комментарий в
`overlays/dev/kustomization.yaml` называет это прямо:

```yaml
  # Дайджест приходится писать второй раз: у kustomize нет вычисляемых значений,
  # поэтому значение из блока images в переменную окружения само не попадёт.
```

Практический вывод не «kustomize плохой», а «продвижение здесь меняет два места, значит, его должен
делать бот, а не человек»: два поля, которые обязаны совпадать, рано или поздно разъедутся, если их
синхронизирует внимательность.

**Правило.** В модели вытягивания продвижение — это изменение данных, а не запуск действия. Из
одного этого свойства бесплатно получаются ревью, аудит и откат (§5); плата за него — ровно та, что
видна в прогоне 8: конфигурацию окружения теперь надо уметь редактировать машинно.

## 5. Откат как `git revert` и когда это не работает

**Задача.** Продвинули на staging, через десять минут пошли ошибки. Вернуть предыдущую версию.

**Наивное решение — и в этот раз оно правильное, но не полностью.** Откатить коммит продвижения:

```
git revert <коммит с новым дайджестом>
```

Дальше ничего делать не надо: в конфигурации снова стоит прежний дайджест, агент видит расхождение
и приводит кластер обратно. В модели вытягивания откат действительно является операцией над
историей, а не отдельной процедурой, — и это одно из главных её приобретений.

**Первое условие, о котором забывают.** Прежний образ должен ещё существовать в реестре. Дайджест
адресует содержимое, но не удерживает его: если политика удержания реестра успела вычистить старые
образы, откатывать некуда. Именно поэтому политика удержания проектируется от политики отката, а не
от размера диска ([`IMAGE_BUILD_AND_REGISTRY.md` §7](IMAGE_BUILD_AND_REGISTRY.md)).

**Отдельная деталь: кнопка «откатить» в агенте — не то же самое.** У Argo CD откат интерфейсом
прямо запрещён при включённом автоматическом согласовании:

> «Rollback cannot be performed against an application with automated sync enabled.»
>
> — Argo CD docs, «Automated Sync Policy»

И это не ограничение, а следствие модели: агент, которому велено непрерывно приводить кластер к Git,
через цикл согласования отменит любой откат, сделанный мимо Git. **Откат в модели вытягивания
делается только через Git** — других согласованных с моделью способов нет.

**Где `git revert` не работает — три случая.**

*Случай первый: миграция схемы уже выполнилась.* Новая версия при раскатке добавила колонку и
переименовала другую. `git revert` вернёт манифест — и старый код встретит новую схему. Ревертится
описание желаемого состояния кластера; база в это описание не входит вообще. Отсюда и требование к
самой миграции: она обязана быть совместима с обеими версиями кода, иначе откат кода невозможен в
принципе. Это отдельная техника (expand/contract), и разбирается она во владеющем файле —
[`RELEASE_STRATEGIES.md` §7](../../engineering-process/theory/RELEASE_STRATEGIES.md); где эта
миграция физически выполняется в конвейере — в
[`ENVIRONMENTS_AND_PROMOTION.md` §7](ENVIRONMENTS_AND_PROMOTION.md).

*Случай второй: наружу уже ушли необратимые эффекты.* За десять минут работы новая версия успела
отправить платежи, разослать письма, записать сообщения в топик и вызвать сторонние API. Откат
манифеста возвращает код; он не отменяет то, что этот код сделал. Хуже того, старая версия может не
уметь читать то, что новая успела записать: сообщения нового формата в топике, записи с новой
структурой в кэше. Согласование по определению работает с состоянием кластера, а не с состоянием
мира (компенсация уже совершённого действия — предмет
[`DISTRIBUTED_TRANSACTIONS.md`](../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md), владение
данными между сервисами — [`DATA_OWNERSHIP.md`](../../microservices/theory/DATA_OWNERSHIP.md)).

*Случай третий: состояние, не описанное в Git.* Всё, что создано мимо агента, откатом не
затрагивается: ресурс, добавленный руками в инциденте, объект в другом пространстве имён, запись во
внешней системе. Если `prune` выключен (§2), сюда же попадает и всё, что новая версия успела
создать: `revert` уберёт объект из Git, а из кластера его не уберёт никто.

**Есть и четвёртая, процессная поломка.** `git revert` — это коммит, а коммит в защищённую ветку —
это пулл-реквест с обязательным согласующим. В три часа ночи это означает: разбудить второго
человека ради откатывающей правки в одну строку. Модель здесь не виновата — виновато отсутствие
заранее согласованного аварийного пути. Он должен быть спроектирован до инцидента: отдельное правило
для откатывающих коммитов, дежурный с правом слияния, заранее описанная процедура. Выбор же между
откатом и накатом исправления — вообще не техническое решение:
[`RELEASE_STRATEGIES.md` §6](../../engineering-process/theory/RELEASE_STRATEGIES.md).

**Что здесь дороже, чем в модели толчка.** `helm rollback` выполняется за секунды и не требует
ничьего согласия. Откат через Git проходит через ревью, слияние и цикл согласования агента —
минуты вместо секунд. Это честная цена за то, что в §2 названо восстановимостью: состояние всегда
описано, и «откатили и забыли» невозможно — откат остаётся в истории как отдельное событие.

**Правило.** В модели вытягивания откат — это `git revert`, и других способов быть не должно, иначе
согласование отменит вашу правку. Работает он ровно настолько, насколько раскатка была **чистой
сменой описания**: всё, что успело выйти за пределы кластера — изменённая схема, отправленные
сообщения, созданные мимо агента объекты, — откатывается отдельно и вручную, и планировать это надо
до раскатки, а не во время инцидента.

## 6. Argo CD против Flux

**Задача.** Модель выбрана — доставка вытягиванием. Осталось выбрать агента.

**Наивное решение.** Сравнить по списку функций: у одного есть интерфейс, у другого мультиарендность,
у третьего что-то ещё. Составить таблицу из двадцати строк и выбрать по числу галочек.

**Где ломается.** Такая таблица устаревает за квартал и ничего не объясняет: обе системы
реализуют один и тот же принцип и обе его реализуют. Содержательная разница между ними —
**единица описания**, то есть какой объект вы заводите, когда хотите что-то развернуть.

**Механизм.** У Argo CD единица — одно приложение, выраженное одним ресурсом:

> «Application: A group of Kubernetes resources as defined by a manifest. This is a Custom Resource
> Definition (CRD).»
>
> — Argo CD docs, «Core Concepts»

Это ровно то, что видно в манифестах модуля: в одном файле `payments-dev.yaml` собраны источник
(`repoURL`, `targetRevision`, `path`), назначение (`server`, `namespace`) и политика согласования
(`syncPolicy`). Одно приложение — один объект — один экран.

У Flux единица мельче, и объектов несколько:

> «Flux is constructed with the GitOps Toolkit components, which is a set of specialized tools and
> Flux Controllers, composable APIs, reusable Go packages for GitOps under the fluxcd GitHub
> organisation for building Continuous Delivery on top of Kubernetes.»
> «The APIs comprise Kubernetes custom resources, which can be created and updated by a cluster
> user, or by other automation tooling.»
>
> — Flux docs, «Components»

Документация перечисляет контроллеры: source-controller, kustomize-controller, helm-controller,
notification-controller и контроллеры автоматизации образов. Разделение здесь не косметическое:
«откуда брать» и «что с этим делать» — **разные ресурсы**, связанные ссылкой. Один источник могут
использовать несколько потребителей, а ставить можно только те контроллеры, которые нужны, — это и
означает слово «composable» в цитате.

**Что из этого следует практически.**

| Что должно быть правдой | Что из этого следует |
|---|---|
| нужен один экран, где видно приложение целиком, и смотреть туда будут не только те, кто живёт в `kubectl` | Argo CD: приложение — один объект, и у него есть свой интерфейс |
| один источник обслуживает много потребителей; хочется ставить только нужные части | Flux: источник и применение — отдельные ресурсы |
| всё управление должно идти через Kubernetes API и обычные манифесты | Flux: среди перечисленных документацией компонентов интерфейса нет вовсе |
| нужна автоматика «появился новый образ в реестре — обновить» без бот-коммита конвейера | Flux: документация называет для этого отдельные контроллеры автоматизации образов |

**Оговорка, которая важнее самого сравнения.** Всё, разобранное в §1–§5, — направление доставки,
согласование и расхождение, разделение репозиториев, продвижение пулл-реквестом, откат через
`git revert` — от этого выбора **не зависит**. Модель одна; различается форма записи. Поэтому в
списке решений, которые вы принимаете, «Argo CD или Flux» стоит последним и стоит дёшево, а
«толчок или вытягивание» — первым и стоит дорого.

**Правило.** Сравнивайте не наборы функций, а границу объекта: у Argo CD приложение — один ресурс,
у Flux оно собрано из нескольких. Из этого выводится и то, как выглядит наблюдение за системой, и
то, насколько её части переиспользуемы, — а всё остальное в сравнении обычно означает «сегодня
реализовано, а завтра будет у обоих».

## 7. Чего GitOps не решает

**Задача.** Агент поставлен, конвейер больше не ходит в кластер, история продвижений есть, откат —
`git revert`. Что осталось нерешённым — и что придётся строить отдельно?

**Наивное решение.** Считать, что GitOps закрывает раскатку целиком: раз желаемое состояние в Git,
значит, в Git всё.

**Где ломается.** Модель ровно настолько широка, насколько широко определение: агент приводит
**набор объектов кластера** к тому, что записано декларативно. Четыре вещи в это определение не
помещаются, и каждая из них — отдельная работа.

*Первое: миграции схемы.* База данных — не объект кластера, и её состояние в Git не описано.
Дальше хуже: в модели вытягивания у конвейера нет доступа к базе (§1), значит, из трёх мест для
миграции, разобранных в
[`ENVIRONMENTS_AND_PROMOTION.md` §7](ENVIRONMENTS_AND_PROMOTION.md), первое — отдельное задание
конвейера — просто недоступно, и выбор сужается до init-контейнера или хука жизненного цикла.
Отдельно стоит отметить, что «выполни это раньше того» не является свойством согласования: агент
приводит объекты к желаемому состоянию, а не выполняет сценарий. Средства упорядочивания есть у
каждого инструмента под своим именем — но это надстройка, а не следствие модели.

*Второе: секреты.* Здесь структурный конфликт, а не недоработка. Модель требует, чтобы желаемое
состояние было в Git; секрет — часть желаемого состояния; положить секрет в Git открытым текстом
нельзя. Не помогает и то, что объект `Secret` в Kubernetes выглядит закодированным: кодирование —
не шифрование ([`SECRETS.md`](../../infrastructure/theory/SECRETS.md) — разбор там, включая то,
чем это лечится). Важное следствие именно для этого файла: как только секреты вынесены наружу,
утверждение §2 «восстановление кластера = Git плюс агент» перестаёт быть точным. Восстановление
требует **двух** источников — репозитория и хранилища секретов, — и второй обязан быть в плане
восстановления так же явно, как первый.

*Третье: порядок между сервисами.* Согласование по природе — сходимость, а не последовательность.
Каждый объект приводится к желаемому состоянию независимо и в неопределённом порядке, поэтому
утверждение «сервис A должен подняться раньше сервиса B» модель не выражает и выразить не может.
Наивная реакция — искать в агенте механизм упорядочивания. Правильная — убрать зависимость от
порядка: сервис, который не переживает отсутствие соседа при старте, сломается и без GitOps —
при перезапуске узла, при масштабировании, при сетевой ошибке
([`FAILURE_ISOLATION.md`](../../microservices/theory/FAILURE_ISOLATION.md)). GitOps здесь не
создаёт проблему, а делает её видимой.

*Четвёртое, самое коварное: «синхронизировано» не значит «работает».* Смотрим на определение:

> «Sync status: Whether or not the live state matches the target state. Is the deployed application
> the same as Git says it should be?»
>
> — Argo CD docs, «Core Concepts»

Вопрос, на который отвечает этот статус, — «совпадает ли с Git». Не «отвечает ли сервис», не
«проходят ли пробы», не «выросло ли число ошибок». Манифест, который применён успешно и описывает
образ с дефектом, даёт `Synced` при полностью неработающем сервисе. Отсюда практическое следствие:
статус синхронизации нельзя использовать как сигнал успешной раскатки — для этого нужны состояние
здоровья рабочей нагрузки и метрики приложения
([`KUBERNETES.md` §10](../../infrastructure/theory/KUBERNETES.md) — пробы состояния).

**Чего GitOps не делает — одним списком.** Не выполняет миграции. Не хранит секреты. Не задаёт
порядок между сервисами. Не отвечает на вопрос «работает ли». Не делает раскатку быстрее — наоборот,
добавляет к ней задержку обнаружения и ревью (§5). И не отменяет необходимости решить, **что именно**
вы катите и когда: правило продвижения артефакта, три окружения и точка согласования живут в
[`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md) и от выбора модели доставки не
зависят.

**Правило.** GitOps решает ровно одну задачу — **где записано желаемое состояние набора объектов и
кто его применяет**. Всё, что не выражается как желаемое состояние объектов, остаётся вашей работой,
и первым делом стоит выписать эти четыре пункта явно: инструмент, поставленный с ожиданием, что он
закроет раскатку целиком, вернёт эти четыре задачи по одной и в самый неудобный момент.

## 8. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Что на самом деле выбирается | не инструмент, а место, где лежит право менять прод |
| Что нужно конвейеру при доставке толчком | учётные данные на запись в кластер и доступный снаружи API-сервер |
| Что нужно конвейеру при доставке вытягиванием | право записи в репозиторий конфигурации, и больше ничего |
| Кто инициирует соединение при вытягивании | агент изнутри кластера — наружу, к Git и реестру |
| На чём держится «истина в Git» | на `prune` и `selfHeal`; по умолчанию оба выключены |
| Что значит `prune: false` | Git описывает то, что есть, но не то, чего быть не должно |
| Что значит отсутствие блока `automated` | Git — цель, но применяет её человек: точка согласования |
| Чем разделены два репозитория | утверждениями «код изменился» и «состояние окружения должно измениться» |
| Где рвётся обратная связь | конвейер зелёный после бот-коммита, раскатки в нём не видно |
| Что такое продвижение при вытягивании | правка одной строки в overlay целевого окружения |
| Цена kustomize без шаблонизатора | дайджест записан дважды; синхронизировать их должен бот |
| Как делается откат | только `git revert`: кнопка мимо Git будет отменена согласованием |
| Когда откат не работает | выполненная миграция · необратимые внешние эффекты · состояние вне Git |
| Модельная разница Argo CD и Flux | одно приложение — один ресурс против набора отдельных контроллеров |
| Что `Synced` не означает | что сервис работает: статус про совпадение с Git, а не про здоровье |

**Дерево решения:** кластер должен быть закрыт снаружи или креденшелы кластера в CI недопустимы →
вытягивание. Раскатка по существу является последовательностью действий → толчок. Один сервис, один
кластер, нет второго репозитория → толчок, вытягивание не окупится. Выбрали вытягивание — тогда
`prune` и `selfHeal` включаются осознанно, по окружению, а не «как у всех».

### Формулировки для собеседования

- «Толчок означает, что учётные данные прода лежат снаружи прода — в системе, которая исполняет код
  из репозитория; вытягивание оставляет их внутри кластера, а наружу отдаёт только запись в Git».
- «"Истина в Git" — это не факт наличия репозитория, а две настройки: без `prune` удаления не
  работают, без `selfHeal` ручная правка живёт вечно».
- «Продвижение в GitOps — изменение данных, а не запуск действия: из этого бесплатно получаются
  ревью, аудит и откат, а платим мы задержкой и тем, что конфигурацию должен править бот».
- «Откат — это `git revert`, и другого способа быть не должно: агент с автоматическим согласованием
  отменит любую правку мимо Git».
- «GitOps не выполняет миграции, не хранит секреты, не задаёт порядок между сервисами и не отвечает
  на вопрос "работает ли" — `Synced` говорит только о совпадении с Git».
