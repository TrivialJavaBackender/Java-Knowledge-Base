# Доставка толчком и вытягиванием: кто применяет изменение в кластере

> **Какую проблему решает.** У задания `deploy-staging` в переменных конвейера лежит `kubeconfig` с правами на запись в прод, а полгода спустя никто не может сказать, что именно сейчас развёрнуто на staging: «у кого ключи» и «где записано истинное состояние» решаются одним разворотом направления доставки.
> **Кому это надо.** Тому, кто настраивает раскатку в Kubernetes и должен объяснить безопаснику, почему у конвейера нет доступа в кластер; тому, кого спросят «что такое GitOps и что конкретно оно вам дало».
> **Когда НЕ надо.** Вытягивание требует, чтобы желаемое состояние было **декларативным**: раскатка, которая по существу является последовательностью действий (прогреть кэш, переключить запись, дождаться дренажа очереди), в манифест не превращается. И один сервис в одном кластере не окупает агента, второго репозитория и бот-коммитов.

**Границы.** Что продвигается между окружениями и где место миграции схемы — [`ENVIRONMENTS_AND_PROMOTION.md` §1, §4, §7](ENVIRONMENTS_AND_PROMOTION.md); этот файл отвечает не на «что продвигается», а на «кто физически применяет».
Механика применения (`kubectl apply` против `helm upgrade --atomic` против синхронизации Argo CD), ожидание готовности и откат — [`DEPLOY_K8S_AND_SWARM.md`](DEPLOY_K8S_AND_SWARM.md); почему у конвейера не должно быть постоянных креденшелов и что такое OIDC-федерация — [`SUPPLY_CHAIN_SECURITY.md` §1, §2](SUPPLY_CHAIN_SECURITY.md).
Цикл согласования как общий механизм контроллеров — [`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md); хранение секретов вне Git — [`SECRETS.md`](../../infrastructure/theory/SECRETS.md); откат против наката — [`RELEASE_STRATEGIES.md` §6, §7](../../engineering-process/theory/RELEASE_STRATEGIES.md).

Сквозной пример модуля — сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, пик 40 запросов в секунду. Вывод в блоках получен рендером манифестов (`kubectl kustomize`, macOS 15); в кластер ничего не применялось, поэтому всё, что касается **поведения** Argo CD, подпёрто цитатой документации, а не прогоном.

## 1. Конвейер с креденшелами кластера против агента внутри кластера

Конвейер собрал образ и знает дайджест. Осталось, чтобы в кластере поехало новое, — и самый распространённый ответ на вопрос «кто выполняет действие» звучит «конвейер сам»:

```yaml
      - run: helm upgrade --install payments ./payments -f ./payments/values-qa.yaml
               --set image.digest="${{ needs.image.outputs.digest }}"
```

Это **доставка толчком (push)**: внешняя система выполняет запись в целевую среду. Она понятна, отлаживается по журналу одного прогона и не требует ничего нового. Ломается она не в том, что не работает, а в двух местах, и оба вылезают не сразу.

*Чтобы `helm upgrade` сработал, у задания должны быть учётные данные на запись в кластер.* Хранить их можно только в секретах системы сборки, а это переворачивает картину прав наизнанку: самый ценный доступ в организации — право менять прод — лежит **снаружи прода**, в системе, которая по назначению исполняет код из репозитория. Долгоживущий ключ в переменных конвейера — инцидент, а не настройка, и добраться до него можно, не имея прав на слияние ([`SUPPLY_CHAIN_SECURITY.md` §1, §5](SUPPLY_CHAIN_SECURITY.md)).

*Направление сетевого соединения.* Толчок требует, чтобы API-сервер кластера был достижим с исполнителя. Для управляемого исполнителя это означает API-сервер, открытый в интернет: список адресов, с которых придёт задание, вы не контролируете. Кластер, который никому снаружи не отвечает, раскатать толчком с чужой машины нельзя в принципе.

**Разворот направления.** Вместо того чтобы внешняя система писала в кластер, внутри кластера работает агент, который сам читает желаемое состояние и приводит к нему живое. Это **доставка вытягиванием (pull)**, и она сформулирована как принцип:

> «Pulled Automatically: Software agents automatically pull the desired state declarations from the source.» «Continuously Reconciled: Software agents continuously observe actual system state and attempt to apply the desired state.»
>
> — OpenGitOps, принципы v1.0.0

> «Target state: The desired state of an application, as represented by files in a Git repository.» «Live state: The live state of that application. What pods etc are deployed.» «Sync: The process of making an application move to its target state.»
>
> — Argo CD docs, «Core Concepts»

Обратите внимание на формулировку target state: желаемое состояние — это **файлы в репозитории**, а не команда, которую кто-то выполнил. Отсюда всё остальное в этом файле.

**Что меняется в правах.** Соблазнительно сказать, что вытягивание «убирает секрет». Нет — оно его **переносит и ослабляет**:

| | Доставка толчком | Доставка вытягиванием |
|---|---|---|
| У конвейера есть | запись в кластер | запись в репозиторий конфигурации |
| У кластера есть | — | чтение репозитория, чтение реестра |
| Соединение инициирует | исполнитель снаружи → API-сервер | агент изнутри → Git и реестр |
| API-сервер доступен снаружи | да | нет |
| При компрометации системы сборки | злоумышленник меняет прод напрямую | злоумышленник делает коммит, который виден и ревьюируем |

Последняя строка — главная. Право писать в Git не эквивалентно праву менять прод: между коммитом и кластером стоит история, ревью и возможность отката. Это не абсолютная защита — коммит в основную ветку конфигурации агент применит, — но это разница между «изменение произошло» и «изменение произошло, зафиксировано, подписано автором и может быть отменено одной командой».

**Чего это не делает.** Разворот направления не отменяет необходимости кому-то доверять: агент имеет права на изменение всего, что описано в его области видимости, и компрометация репозитория конфигурации даёт ровно то же, что компрометация `kubeconfig`. Раскатку он не ускоряет — наоборот, добавляет задержку на обнаружение изменения (§2).

**Правило.** Выбор между толчком и вытягиванием — ответ на вопрос «где должен лежать креденшел, дающий право менять прод». Толчок кладёт его снаружи и требует, чтобы кластер отвечал внешнему миру; вытягивание оставляет право внутри кластера, а наружу отдаёт только запись в Git.

## 2. Согласование и расхождение: почему «истина в Git» про восстановимость

Кластер staging потерян целиком: ошибочно удалили пространство имён, отвалился регион. Восстановите его в том виде, в каком он был вчера. Ответ «найдём последний зелёный прогон `deploy-staging` и повторим его команду» не работает четырьмя способами, и все четыре обнаруживаются в худший момент.

*Журнал не вечен.* Прогоны и их артефакты хранятся ограниченный срок; «последний зелёный» мог быть три месяца назад и уже удалён.

*Команда не самодостаточна.* В строке стоит `--set image.digest="${{ needs.image.outputs.digest }}"` — ссылка на выход задания, которого больше нет. Значение подставлялось в момент исполнения и нигде не сохранилось.

*Последняя команда — не текущее состояние.* Между раскатками кто-то дважды выполнил `kubectl edit` в инциденте, а кто-то поставил рядом секрет руками. Журнал знает, что делал конвейер, и ничего не знает о том, что делали помимо него.

*Порядок не восстанавливается.* Повторить пять команд `helm upgrade` разных релизов в правильном порядке и с правильными параметрами — задача археологическая.

В модели вытягивания желаемое состояние — не последовательность команд, а **содержимое репозитория на определённой ревизии**, и восстановление сводится к трём шагам: поднять пустой кластер, поставить агента, показать ему репозиторий. Дальше работает **согласование (reconciliation)** — непрерывное сравнение живого состояния с желаемым и приведение к нему; зафиксированное отличие живого от записанного называется **расхождением (drift)**. Это ровно та же форма, что у контроллеров самого Kubernetes ([`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md)), поднятая на уровень выше: контроллер приводит поды к тому, что записано в `Deployment`; агент приводит набор объектов кластера к тому, что записано в Git.

> «Sync status: Whether or not the live state matches the target state. Is the deployed application the same as Git says it should be?» «Refresh: Compare the latest code in Git with the live state. Figure out what is different.»
>
> — Argo CD docs, «Core Concepts»

**«Истина в Git» — не лозунг, а конъюнкция двух настроек.** Сам факт, что манифесты лежат в Git, не гарантирует ничего. Гарантию дают два поведения агента, и **по умолчанию оба выключены**:

> «By default (and as a safety mechanism), automated sync will not delete resources when Argo CD detects the resource is no longer defined in Git.» «By default, changes that are made to the live cluster will not trigger automated sync» — устраняет расхождение только `selfHeal`.
>
> — Argo CD docs, «Automated Sync Policy»

Без `prune` удаление из Git не приводит к удалению из кластера — значит, Git описывает то, что **есть**, но не то, чего **нет**, и полным описанием окружения не является. Без `selfHeal` ручная правка в кластере живёт неограниченно долго: расхождение видно как `OutOfSync`, но не устраняется.

| Окружение | `prune` | `selfHeal` | Что это значит про «истину в Git» |
|---|---|---|---|
| dev | `true` | `true` | Git — полное описание; ручная правка живёт до следующего цикла |
| qa | `true` | `false` | удаления работают; ручная правка тестировщика сохраняется, расхождение видно |
| staging | блока `automated` нет | | Git — цель, но применяет её человек |

Средняя строка — не недоделка: на qa тестировщик может временно поменять что-то руками, и `selfHeal` откатил бы правку посреди проверки. Расхождение при этом остаётся видимым (`OutOfSync`) — его не прячут, его просто не устраняют молча.

**Правило.** «Истина в Git» окупается ровно в одном сценарии — когда состояние надо **восстановить**: после потери кластера, при заведении второго региона, при расследовании «когда это изменилось». Держится она на двух настройках, а не на факте наличия репозитория; выключая любую, вы меняете утверждение «Git описывает окружение» на «Git описывает часть окружения».

## 3. Репозиторий приложения против репозитория конфигурации

Конвейер собрал образ, знает дайджест и в кластер не ходит (§1). Соблазн — положить манифесты рядом с кодом и направить агента туда: всё в одном месте, один пулл-реквест, одна история. Ломается это тремя разными способами, и они не про вкус.

*Конвейер начинает запускать сам себя.* Чтобы записать новый дайджест, конвейер делает коммит. Этот коммит — событие в том же репозитории, значит, он запускает конвейер, который соберёт образ и сделает ещё один коммит. Лечится это пометками вроде `[skip ci]` и фильтрами по автору — конструкцией, которая держится на строке в сообщении коммита. Забыли фильтр в одном месте — получили бесконечный цикл сборок; сделали слишком широким — перестали собираться настоящие изменения.

*История кода перестаёт читаться.* Каждая раскатка на каждое из трёх окружений — коммит. Через полгода `git log` сервиса наполовину состоит из строк «chore: bump payments digest to sha256:…», и `git bisect` по нему ведёт себя соответственно ([`BRANCHING_AND_CODE_FLOW.md` §5](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md)).

*Правила защиты у кода и у раскатки разные, а ветка одна.* Изменение кода ревьюит команда сервиса; изменение того, что работает на staging, может требовать другого согласующего и уж точно другого момента ([`ENVIRONMENTS_AND_PROMOTION.md` §6](ENVIRONMENTS_AND_PROMOTION.md)). В одном репозитории с одной основной веткой оба потока получают одни правила: либо код ревьюится избыточно, либо продвижение — недостаточно.

Есть и четвёртая причина, менее очевидная: **окружение — это не один сервис.** Вопрос «что сейчас на staging» относится ко всему набору, а если конфигурация каждого сервиса лежит в его собственном репозитории, ответ снова размазан по десяти местам — ровно та беда, от которой уходили в §2.

| | Репозиторий приложения | Репозиторий конфигурации |
|---|---|---|
| Что описывает | как сервис работает | что развёрнуто и где |
| Кто меняет | разработчики | конвейер (бот) и тот, кто продвигает |
| Частота | каждая задача | каждая раскатка и каждое продвижение |
| Что означает коммит в основную ветку | «код изменился» | «состояние окружения должно измениться» |

Конвейер приложения заканчивается не раскаткой, а **бот-коммитом**: он записывает новый дайджест в конфигурацию окружения dev. Этот коммит и есть точка перехода: всё до него — доставка толчком, всё после — вытягивание. Готовый сквозной конвейер такого вида разобран в [`RELEASE_PIPELINE_RECIPES.md` §3](RELEASE_PIPELINE_RECIPES.md). В манифесте агента граница выражена тремя полями:

```yaml
  source:
    # Репозиторий КОНФИГУРАЦИИ, а не репозиторий приложения: у них разный
    # темп изменений и разный круг ревьюеров.
    repoURL: https://github.com/example/payments-config.git
    targetRevision: main
    path: kustomize/overlays/dev
```

Адрес, ревизия, путь — полный ответ на вопрос «где записано желаемое состояние». Заодно это ответ на вопрос про креденшелы из §1: токен, оставшийся у конвейера, даёт запись в `payments-config` и больше ничего — он не открывает ни кластер, ни реестр и не позволяет изменить код сервиса.

**Цена, о которой обычно молчат.** Обратная связь рвётся ровно по этой границе. Конвейер приложения завершается зелёным сразу после бот-коммита — а сервис в этот момент ещё не развёрнут, и был ли он развёрнут успешно, в прогоне не видно **никогда**. Разработчик, привыкший к «зелёный прогон = поехало», получает зелёный прогон и неработающий dev. Связь восстанавливают отдельно: уведомлениями агента, статусом синхронизации на пулл-реквесте, эндпоинтом `/version` ([`ENVIRONMENTS_AND_PROMOTION.md` §3](ENVIRONMENTS_AND_PROMOTION.md)).

**Когда это неправильный ответ.** Два репозитория не обязаны быть двумя репозиториями: в монорепозитории то же разделение делается каталогом с собственными правилами защиты и собственным списком владельцев. Критерий не в числе репозиториев, а в том, **различаются ли у двух потоков изменений частота, ревьюеры и триггер**. Не различаются — разделение добавит бот-коммит и не купит ничего.

**Правило.** Разделяются не файлы, а два разных утверждения: «код изменился» и «состояние окружения должно измениться». Смешав их в одной истории, вы получаете конвейер, запускающий сам себя, и `git log`, по которому нельзя ни читать код, ни узнать, что развёрнуто.

## 4. Продвижение как пулл-реквест между overlay окружений

Артефакт проверен на qa, надо продвинуть его на staging. В модели толчка это запуск задания `deploy-staging`. Открыть интерфейс агента и нажать «синхронизировать» — не то же самое: синхронизация ничего не продвигает, она приводит staging к тому, что **записано для staging**, а записана там прежняя версия. Нажатие даст `Synced` и ту же самую старую версию. У агента нет и не может быть понятия «взять то, что стоит на соседнем окружении»: он знает только свой каталог в репозитории.

**Продвижение есть изменение данных.** Конфигурация строится как база плюс три overlay: база описывает сервис без единого признака окружения, overlay добавляют то, что различается. Рендер каждого overlay командой `kubectl kustomize` даёт (значимая часть вывода для qa):

```
      containers:
      - env:
        - name: PAYMENTS_ENVIRONMENT
          value: qa
        - name: PAYMENTS_BUILD_DIGEST
          value: sha256:1111111111111111111111111111111111111111111111111111111111111111
        image: registry.example.com/payments@sha256:11111111111111111111111111111111…
```

| overlay | namespace | replicas | дайджест в образе | requests.cpu |
|---|---|---|---|---|
| dev | payments-dev | 1 | `sha256:1111…1111` | 100m |
| qa | payments-qa | 2 | `sha256:1111…1111` | 250m |
| staging | payments-staging | 3 | `sha256:0000…0000` | 500m |

Прочитайте столбец с дайджестом: dev и qa несут **один и тот же**, staging — отстающий. Это и есть снимок «артефакт прошёл dev и qa, но ещё не продвинут на staging», выраженный не статусом в чьей-то базе, а содержимым файлов. Продвижение — правка одной строки в overlay staging так, чтобы дайджест совпал с qa. Ничего больше. Отсюда три следствия, каждое из которых в модели толчка приходится строить отдельно:

- **Ревью.** Правка приезжает пулл-реквестом, значит, у неё есть автор, обязательный согласующий и обсуждение — тем же механизмом, что у кода. Отдельного механизма одобрения раскатки не нужно.
- **Аудит.** «Кто, когда и почему поставил на staging именно эту версию» отвечается `git log` по одному файлу, а не поиском по журналам прогонов с ограниченным сроком хранения.
- **Диффабельность.** Различие между окружениями — буквально `diff` двух каталогов; вопрос «чем qa отличается от staging» перестаёт быть исследованием.

**Цена видна в том же выводе.** У kustomize нет вычисляемых значений, поэтому дайджест приходится записывать **дважды**: в преобразователе `images` и в патче, выставляющем переменную `PAYMENTS_BUILD_DIGEST`. Сослаться на первое значение из второго места средствами kustomize нельзя — такой возможности нет; в чарте Helm то же самое записывается один раз как `.Values.image.digest`. Вывод не «kustomize плохой», а «продвижение здесь меняет два места, значит, его должен делать бот»: два поля, которые обязаны совпадать, рано или поздно разъедутся, если их синхронизирует внимательность.

**Правило.** В модели вытягивания продвижение — это изменение данных, а не запуск действия. Из одного этого свойства бесплатно получаются ревью, аудит и откат (§5); плата — конфигурацию окружения теперь надо уметь редактировать машинно.

## 5. Откат как `git revert` и когда это не работает

Продвинули на staging, через десять минут пошли ошибки. Откат — это `git revert <коммит с новым дайджестом>`, и больше ничего: в конфигурации снова стоит прежний дайджест, агент видит расхождение и приводит кластер обратно. В модели вытягивания откат действительно является операцией над историей, а не отдельной процедурой.

**Первое условие, о котором забывают.** Прежний образ должен ещё существовать в реестре: дайджест адресует содержимое, но не удерживает его. Если политика удержания реестра успела вычистить старые образы, откатывать некуда — поэтому политика удержания проектируется от политики отката, а не от размера диска ([`IMAGE_BUILD_AND_REGISTRY.md` §7](IMAGE_BUILD_AND_REGISTRY.md)).

**Кнопка «откатить» в агенте — не то же самое.** У Argo CD откат интерфейсом прямо запрещён при включённом автоматическом согласовании:

> «Rollback cannot be performed against an application with automated sync enabled.»
>
> — Argo CD docs, «Automated Sync Policy»

Это не ограничение, а следствие модели: агент, которому велено непрерывно приводить кластер к Git, через цикл согласования отменит любой откат, сделанный мимо Git. **Откат делается только через Git** — других согласованных с моделью способов нет.

*Случай первый, где `git revert` не работает: миграция схемы уже выполнилась.* Новая версия добавила колонку и переименовала другую. `git revert` вернёт манифест — и старый код встретит новую схему: ревертится описание желаемого состояния кластера, база в это описание не входит вообще. Отсюда требование к самой миграции: она обязана быть совместима с обеими версиями кода, иначе откат кода невозможен в принципе ([`RELEASE_STRATEGIES.md` §7](../../engineering-process/theory/RELEASE_STRATEGIES.md); где миграция физически выполняется — [`ENVIRONMENTS_AND_PROMOTION.md` §7](ENVIRONMENTS_AND_PROMOTION.md)).

*Случай второй: наружу ушли необратимые эффекты.* За десять минут новая версия успела отправить платежи, разослать письма, записать сообщения в топик и вызвать сторонние API. Откат манифеста возвращает код; он не отменяет то, что этот код сделал. Хуже того, старая версия может не уметь читать записанное новой: сообщения нового формата в топике, записи с новой структурой в кэше. Согласование по определению работает с состоянием кластера, а не с состоянием мира (компенсация совершённого действия — [`DISTRIBUTED_TRANSACTIONS.md`](../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md)).

*Случай третий: состояние, не описанное в Git.* Всё, что создано мимо агента, откатом не затрагивается: ресурс, добавленный руками в инциденте, объект в другом пространстве имён, запись во внешней системе. Если `prune` выключен (§2), сюда же попадает всё, что новая версия успела создать: `revert` уберёт объект из Git, а из кластера его не уберёт никто.

**Четвёртая, процессная поломка.** `git revert` — это коммит, а коммит в защищённую ветку — пулл-реквест с обязательным согласующим. В три часа ночи это означает разбудить второго человека ради правки в одну строку. Модель здесь не виновата — виновато отсутствие заранее согласованного аварийного пути: отдельное правило для откатывающих коммитов, дежурный с правом слияния, описанная процедура. Выбор между откатом и накатом исправления — вообще не техническое решение ([`RELEASE_STRATEGIES.md` §6](../../engineering-process/theory/RELEASE_STRATEGIES.md)).

**Что здесь дороже, чем при толчке.** `helm rollback` выполняется за секунды и не требует ничьего согласия; откат через Git проходит ревью, слияние и цикл согласования — минуты вместо секунд. Это честная цена за восстановимость из §2: состояние всегда описано, и «откатили и забыли» невозможно.

**Правило.** Откат работает ровно настолько, насколько раскатка была **чистой сменой описания**: всё, что успело выйти за пределы кластера — изменённая схема, отправленные сообщения, созданные мимо агента объекты, — откатывается отдельно и вручную, и планировать это надо до раскатки, а не во время инцидента.

## 6. Argo CD против Flux

Сравнивать агентов по списку функций бессмысленно: такая таблица устаревает за квартал и ничего не объясняет — обе системы реализуют один и тот же принцип и обе его реализуют. Содержательная разница — **единица описания**, то есть какой объект вы заводите, когда хотите что-то развернуть.

У Argo CD единица — одно приложение, выраженное одним ресурсом:

> «Application: A group of Kubernetes resources as defined by a manifest. This is a Custom Resource Definition (CRD).»
>
> — Argo CD docs, «Core Concepts»

В одном манифесте собраны источник (`repoURL`, `targetRevision`, `path`), назначение (`server`, `namespace`) и политика согласования (`syncPolicy`). Одно приложение — один объект — один экран.

У Flux единица мельче, и объектов несколько:

> «Flux is constructed with the GitOps Toolkit components, which is a set of specialized tools and Flux Controllers, composable APIs, reusable Go packages for GitOps… The APIs comprise Kubernetes custom resources, which can be created and updated by a cluster user, or by other automation tooling.»
>
> — Flux docs, «Components»

Документация перечисляет контроллеры: source-controller, kustomize-controller, helm-controller, notification-controller и контроллеры автоматизации образов. Разделение не косметическое: «откуда брать» и «что с этим делать» — **разные ресурсы**, связанные ссылкой. Один источник могут использовать несколько потребителей, а ставить можно только нужные контроллеры — это и означает слово «composable».

| Что должно быть правдой | Что из этого следует |
|---|---|
| нужен один экран, где видно приложение целиком, и смотреть туда будут не только те, кто живёт в `kubectl` | Argo CD: приложение — один объект, и у него есть свой интерфейс |
| один источник обслуживает много потребителей; хочется ставить только нужные части | Flux: источник и применение — отдельные ресурсы |
| всё управление должно идти через Kubernetes API и обычные манифесты | Flux: среди перечисленных документацией компонентов интерфейса нет вовсе |
| нужна автоматика «появился новый образ в реестре — обновить» без бот-коммита конвейера | Flux: документация называет для этого отдельные контроллеры автоматизации образов |

**Оговорка, которая важнее самого сравнения.** Всё из §1–§5 — направление доставки, согласование и расхождение, разделение репозиториев, продвижение пулл-реквестом, откат через `git revert` — от этого выбора **не зависит**. Модель одна; различается форма записи. Поэтому «Argo CD или Flux» в списке ваших решений стоит последним и стоит дёшево, а «толчок или вытягивание» — первым и стоит дорого.

**Правило.** Сравнивайте не наборы функций, а границу объекта: у Argo CD приложение — один ресурс, у Flux оно собрано из нескольких. Из этого выводится и форма наблюдения за системой, и переиспользуемость её частей; всё остальное в сравнении обычно означает «сегодня реализовано, а завтра будет у обоих».

## 7. Чего GitOps не решает

Модель ровно настолько широка, насколько широко определение: агент приводит **набор объектов кластера** к тому, что записано декларативно. Четыре вещи в это определение не помещаются, и каждая — отдельная работа.

*Миграции схемы.* База данных — не объект кластера, и её состояние в Git не описано. Дальше хуже: у конвейера нет доступа к базе (§1), значит, из трёх мест для миграции ([`ENVIRONMENTS_AND_PROMOTION.md` §7](ENVIRONMENTS_AND_PROMOTION.md)) первое — отдельное задание конвейера — просто недоступно, и выбор сужается до init-контейнера или хука жизненного цикла. Отдельно: «выполни это раньше того» не является свойством согласования — агент приводит объекты к желаемому состоянию, а не выполняет сценарий. Средства упорядочивания есть у каждого инструмента под своим именем, но это надстройка, а не следствие модели.

*Секреты.* Здесь структурный конфликт, а не недоработка: модель требует, чтобы желаемое состояние было в Git, секрет — часть желаемого состояния, а положить секрет в Git открытым текстом нельзя. Не помогает и то, что объект `Secret` выглядит закодированным: кодирование — не шифрование ([`SECRETS.md`](../../infrastructure/theory/SECRETS.md)). Следствие именно для этого файла: как только секреты вынесены наружу, утверждение §2 «восстановление кластера = Git плюс агент» перестаёт быть точным — восстановление требует **двух** источников, и второй обязан быть в плане восстановления так же явно, как первый.

*Порядок между сервисами.* Согласование по природе — сходимость, а не последовательность: каждый объект приводится к желаемому состоянию независимо и в неопределённом порядке, поэтому «сервис A должен подняться раньше сервиса B» модель выразить не может. Наивная реакция — искать в агенте механизм упорядочивания; правильная — убрать зависимость от порядка: сервис, который не переживает отсутствие соседа при старте, сломается и без GitOps — при перезапуске узла, при масштабировании, при сетевой ошибке ([`FAILURE_ISOLATION.md`](../../microservices/theory/FAILURE_ISOLATION.md)). GitOps здесь не создаёт проблему, а делает её видимой.

*Самое коварное: «синхронизировано» не значит «работает».* Статус `Sync status` отвечает на вопрос «совпадает ли с Git» — не «отвечает ли сервис», не «проходят ли пробы», не «выросло ли число ошибок». Манифест, применённый успешно и описывающий образ с дефектом, даёт `Synced` при полностью неработающем сервисе. Значит, статус синхронизации нельзя использовать как сигнал успешной раскатки: для этого нужны состояние здоровья рабочей нагрузки и метрики приложения ([`KUBERNETES.md` §10](../../infrastructure/theory/KUBERNETES.md)).

**Правило.** GitOps решает ровно одну задачу — **где записано желаемое состояние набора объектов и кто его применяет**. Не выполняет миграции, не хранит секреты, не задаёт порядок между сервисами, не отвечает на вопрос «работает ли» и не делает раскатку быстрее. Инструмент, поставленный с ожиданием, что он закроет раскатку целиком, вернёт эти четыре задачи по одной и в самый неудобный момент.

## 8. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Что на самом деле выбирается | не инструмент, а место, где лежит право менять прод |
| Что нужно конвейеру при доставке толчком | учётные данные на запись в кластер и доступный снаружи API-сервер |
| Что нужно конвейеру при доставке вытягиванием | право записи в репозиторий конфигурации, и больше ничего |
| Кто инициирует соединение при вытягивании | агент изнутри кластера — наружу, к Git и реестру |
| На чём держится «истина в Git» | на `prune` и `selfHeal`; по умолчанию оба выключены |
| Что значит `prune: false` | Git описывает то, что есть, но не то, чего быть не должно |
| Что значит отсутствие блока `automated` | Git — цель, но применяет её человек: точка согласования |
| Чем разделены два репозитория | утверждениями «код изменился» и «состояние окружения должно измениться» |
| Где рвётся обратная связь | конвейер зелёный после бот-коммита, раскатки в нём не видно |
| Что такое продвижение при вытягивании | правка одной строки в overlay целевого окружения |
| Цена kustomize без шаблонизатора | дайджест записан дважды; синхронизировать их должен бот |
| Как делается откат | только `git revert`: кнопка мимо Git будет отменена согласованием |
| Когда откат не работает | выполненная миграция · необратимые внешние эффекты · состояние вне Git |
| Модельная разница Argo CD и Flux | одно приложение — один ресурс против набора отдельных контроллеров |
| Что `Synced` не означает | что сервис работает: статус про совпадение с Git, а не про здоровье |

**Дерево решения:** кластер должен быть закрыт снаружи или креденшелы кластера в CI недопустимы → вытягивание. Раскатка по существу является последовательностью действий → толчок. Один сервис, один кластер, нет второго репозитория → толчок, вытягивание не окупится. Выбрали вытягивание — тогда `prune` и `selfHeal` включаются осознанно, по окружению, а не «как у всех».

### Формулировки для собеседования

- «Толчок означает, что учётные данные прода лежат снаружи прода — в системе, которая исполняет код из репозитория; вытягивание оставляет их внутри кластера, а наружу отдаёт только запись в Git».
- «"Истина в Git" — это не факт наличия репозитория, а две настройки: без `prune` удаления не работают, без `selfHeal` ручная правка живёт вечно».
- «Продвижение в GitOps — изменение данных, а не запуск действия: из этого бесплатно получаются ревью, аудит и откат, а платим мы задержкой и тем, что конфигурацию должен править бот».
- «Откат — это `git revert`, и другого способа быть не должно: агент с автоматическим согласованием отменит любую правку мимо Git».
- «GitOps не выполняет миграции, не хранит секреты, не задаёт порядок между сервисами и не отвечает на вопрос "работает ли" — `Synced` говорит только о совпадении с Git».
