# Образ и реестр: как конвейер собирает контейнер и чем адресует результат

> **Какую проблему решает.** Задание конвейера само выполняется в контейнере, а ему нужно собрать
> контейнер — и первый же способ, который приходит в голову, отдаёт этому заданию root на хосте.
> Дальше: собранный образ отправляется в реестр под тегом `dev`, через час тот же тег указывает уже
> на другое содержимое, и никто этого не замечает. Обе беды — про одно: между `mvn package` и
> работающим подом лежит артефакт, который надо **изготовить, не открыв дверь**, и **назвать так,
> чтобы имя не переставало значить то же самое**.
> **Кому это надо.** Тому, кто пишет `Dockerfile` для сервиса и шаг сборки образа в конвейере; тому,
> кого спросят «а почему у вас образ адресуется дайджестом, а не тегом» и «зачем вам вообще Kaniko,
> если есть `docker build`».
> **Когда НЕ надо.** Ни одна техника отсюда не ускоряет сборку сама по себе. Кэш слоёв через реестр
> имеет смысл, когда слои действительно переиспользуются: если `Dockerfile` начинается с `COPY . .`,
> кэшировать нечего — правка любого файла инвалидирует всё, и внешний кэш добавит только время на
> его выгрузку. Сначала порядок слоёв, потом их кэширование.

**Границы с соседними файлами.** Что такое слой, как устроен `Dockerfile` и что реестр хранит внутри
себя — в [`DOCKER.md` §3, §9](../../infrastructure/theory/DOCKER.md); здесь не пересказывается ничего
из этого, берётся как известное. Эфемерность исполнителя как модель — в
[`PIPELINE_MODEL.md` §5](PIPELINE_MODEL.md), механика кэша конвейера вообще (ключ, промах,
отравление) — в [`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md). Layered jar со стороны
Maven и воспроизводимость сборки — в [`JAVA_BUILD_IN_CI.md` §7](JAVA_BUILD_IN_CI.md); здесь тот же
layered jar разбирается со стороны слоёв образа. Правило «собрать один раз, продвигать тот же
артефакт» и то, как дайджест попадает в манифесты окружения, — в
[`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md); здесь только механизм, из которого
это правило следует. Кража учётных данных реестра, подпись образа и происхождение — в
[`SUPPLY_CHAIN_SECURITY.md`](SUPPLY_CHAIN_SECURITY.md). Во что кэш обходится в минутах и когда он
окупается — в [`PIPELINE_ECONOMICS.md`](PIPELINE_ECONOMICS.md).

**Сквозной пример.** Сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, пик
40 запросов в секунду, базовая сборка 12 минут. Образ описан в `Dockerfile` в корне модуля, шаг
сборки образа — в `pipelines/github/ci.yml` (задание `image`).

Числа в блоках прогонов сняты на Apple Silicon, macOS 15 (Darwin 25.6.0): Docker 29.4.3,
buildx v0.33.0, Temurin 21.0.9. Это не бенчмарк — порядок величин.

## 1. Почему `docker build` внутри контейнера конвейера — проблема

**Задача.** В `pipelines/github/ci.yml` задание `image` делает ровно одну содержательную вещь:

```yaml
      - id: push
        run: |
          docker buildx build --push -t "$IMAGE:${{ github.sha }}" .
```

На управляемом исполнителе GitHub это работает без единой настройки: там задание выполняется прямо
на виртуальной машине, где демон Docker уже стоит. Переносим тот же конвейер на собственный
исполнитель контейнерного типа ([`RUNNERS_AND_EXECUTION.md` §2](RUNNERS_AND_EXECUTION.md)) — и шаг
падает: `Cannot connect to the Docker daemon`.

**Наивное решение.** «В образе задания нет Docker — добавим». Ставим пакет `docker-cli`, получаем то
же самое сообщение. Причина в разделении, которое видно из архитектуры Docker
([`DOCKER.md` §11](../../infrastructure/theory/DOCKER.md)): `docker` — это клиент, отправляющий
запросы по HTTP демону; сборку выполняет демон. Установить клиент внутрь контейнера легко, а демона
внутри контейнера по-прежнему нет. Отсюда ровно два способа дать заданию собирать образы: принести
демон внутрь (DinD) или дать доступ к чужому демону снаружи (сокет хоста).

**Где ломается — оба способа платят одним и тем же.**

*Сокет хоста.* Пробрасываем `/var/run/docker.sock` внутрь контейнера задания. Формально мы дали
одному процессу право обратиться к одному сокету. Фактически:

> «When you share the Docker daemon, you effectively disable the container's security mechanisms and
> expose your host to privilege escalation.»
> «This can cause container breakout. For example, if you run `docker rm -f $(docker ps -a -q)` in a
> project, it removes the GitLab Runner containers.»
>
> — GitLab docs, «Use Docker to build Docker images», раздел «Known issues with Docker socket binding»

*Docker-in-Docker.* Поднимаем рядом с заданием отдельный демон — тот самый `services: docker:dind`
из `pipelines/gitlab/.gitlab-ci.yml`. Демон внутри контейнера должен создавать пространства имён,
монтировать файловые системы и управлять cgroups, а обычному контейнеру этого не разрешено, поэтому
условие у документации одно:

> «Use this approach when your runner supports `privileged` mode.»
>
> — GitLab docs, «Use Docker to build Docker images», раздел «Use Docker-in-Docker»

**Механизм — почему это не «настройка безопасности», а свойство конструкции.** У API демона нет
модели прав: он не различает «этому клиенту можно собрать образ, а вон тому нельзя». Клиент, который
дотянулся до демона, может запустить любой контейнер с любыми параметрами — и один из параметров
закрывает вопрос:

> «Docker allows you to share a directory between the Docker host and a guest container; and it
> allows you to do so without limiting the access rights of the container. This means that you can
> start a container where the `/host` directory is the `/` directory on your host; and the container
> can alter your host filesystem without any restriction.»
> «First of all, only trusted users should be allowed to control your Docker daemon.»
>
> — Docker docs, «Docker Engine security», раздел «Docker daemon attack surface»

Цепочка из трёх шагов, каждый из которых легален: задание говорит с демоном → просит контейнер с
корнем хоста внутри → пишет в него. Дополнительный множитель — сам демон:

> «Running containers (and applications) with Docker implies running the Docker daemon. This daemon
> requires `root` privileges unless you opt-in to Rootless mode»
>
> — там же

Отсюда вывод, который стоит уметь произнести целиком: **доступ к демону Docker эквивалентен root на
машине, где этот демон работает.** Не «почти», не «при неудачном стечении обстоятельств» — это
прямое следствие того, что демон умеет и чего он не проверяет. Разница между сокетом и DinD в этом
свете чисто топологическая: в первом случае вы отдаёте хост, во втором — только контейнер сборщика,
но отдаёте его с привилегиями, которых у остальных контейнеров нет.

**Отдельно — цена DinD, не связанная с безопасностью.** Демон, поднятый на время задания, стартует с
пустым хранилищем образов: базовые слои `maven:3.9-eclipse-temurin-21` и `eclipse-temurin:21-jre-alpine`
он скачивает заново каждый раз, потому что кэш хоста ему не принадлежит. Это тот же счёт, что и в
§3, только выставленный не за слои сборки, а за базовые образы. Testcontainers формулируют итог
прямо: «While Docker-in-Docker (DinD) is generally considered an instrument of last resort, it is
necessary for some CI environments» (Testcontainers docs, разбор — в
[`JAVA_BUILD_IN_CI.md` §5](JAVA_BUILD_IN_CI.md)).

**Когда это всё-таки нормальный ответ.** Три условия одновременно: код, который собирается,
доверенный (никаких пулл-реквестов из форков —
[`RUNNERS_AND_EXECUTION.md` §9](RUNNERS_AND_EXECUTION.md)); машина исполнителя эфемерна и умирает
вместе с заданием; на этой машине нет ничего чужого — ни другого задания, ни секретов соседней
команды. При выполнении всех трёх «отдать root» означает «отдать одноразовую пустую машину», и цена
приемлема. Именно поэтому управляемые исполнители GitHub позволяют себе просто держать демон на
машине задания.

**Правило.** Прежде чем выбирать инструмент сборки образа, ответьте на один вопрос: **чей код я
запускаю и что ещё стоит на этой машине.** Если ответ «свой, и ничего» — `docker build` на
исполнителе годится, и усложнять нечего. Если хотя бы одна половина ответа другая — доступ к демону
давать нельзя, и дальше выбор идёт среди сборщиков, которым демон не нужен (§2).

## 2. Kaniko, Buildah, BuildKit — три разных ответа

**Задача.** Демон давать нельзя (§1), а образ собирать надо. Дальше в любой статье встречаются три
имени — Kaniko, Buildah, BuildKit — и ощущение, что это конкуренты, из которых надо выбрать.

**Наивное решение.** «Возьмём любой, они делают одно и то же». Ошибка в том, что они отвечают на
разные вопросы, и только два из трёх вообще про отсутствие демона.

**Механизм — что именно каждый убирает.**

*BuildKit демон не убирает.* Это не альтернатива Docker, а его собственный движок сборки:

> «BuildKit is the builder backend used by Docker.»
> «BuildKit is the default builder for Docker Desktop and Docker Engine users.»
>
> — Docker docs, «BuildKit»

Вызывая `docker build` на современном Docker, вы уже вызываете BuildKit. Он отвечает на вопрос «как
собирать быстро», а не «как обойтись без демона»: строит граф шагов и параллелит независимые
(«Parallelize building independent build stages»), пропускает этапы, чей результат никому не нужен
(«Detect and skip executing unused build stages»), передаёт из контекста сборки только изменившиеся
файлы («Incrementally transfer only the changed files in your build context between builds» — там
же). Именно из-за графа трёхэтапный `Dockerfile` модуля не обходится дороже одноэтапного: этап
`extract` зависит от `build`, а не наоборот, и лишнего не делается. Кроме того, сборщик BuildKit не
обязан жить внутри вашего демона: в прогоне 3 он поднят драйвером `docker-container`, то есть
отдельным контейнером со своим сетевым пространством имён (§3 — про то, чем это оборачивается).

*Kaniko убирает демон целиком.*

> «kaniko is a tool to build container images from a Dockerfile, inside a container or Kubernetes
> cluster.»
> «kaniko doesn't depend on a Docker daemon and executes each command within a Dockerfile completely
> in userspace.»
>
> — Kaniko README (GoogleContainerTools)

Ключевое слово — **userspace**. Каждая инструкция `RUN` выполняется процессом самого Kaniko, который
сам распаковывает базовый образ в свою файловую систему, сам исполняет команду и сам вычисляет
получившийся слой. Ничего привилегированного для этого не нужно, поэтому Kaniko запускается обычным
подом в кластере — это и есть его ниша: сборка образа там, где кластер есть, а демона нет и не будет.

*Buildah убирает демон и заодно `Dockerfile` как обязательную форму.* Он описывает себя как «a tool
that facilitates building OCI container images» и позиционируется для тех, кому нужно собирать
образы «without a full container runtime or daemon installed» (buildah.io). Его отличие не в
отсутствии демона — этим он совпадает с Kaniko, — а в императивности: слои создаются отдельными
командами, поэтому образ можно собрать скриптом, из пакетов дистрибутива, вообще без `Dockerfile`.
Оборотная сторона очевидна: то, что у `Dockerfile` описано декларативно и потому кэшируется и
воспроизводится, здесь становится вашим скриптом со всеми последствиями.

**Критерий выбора — не «что лучше», а что у вас должно быть правдой.**

| Что должно быть правдой | Что из этого следует |
|---|---|
| Демон есть, он ваш, машина одноразовая; нужен быстрый кэш и параллельный граф | `docker buildx` (то есть BuildKit) — усложнять нечего |
| Демона нет и не будет: сборка идёт подом в кластере, `Dockerfile` уже написан | Kaniko |
| Образ собирается не из `Dockerfile`, а скриптом или из пакетов; нужна сборка без привилегий на обычной машине | Buildah |
| Демон есть, но он **чужой** — общий на несколько команд | ни один из трёх не спасает: проблема в §1, а не в инструменте |

**Чего эти инструменты не делают.** Ни один из них не превращает недоверенную сборку в безопасную.
Kaniko говорит это про себя открытым текстом:

> «kaniko by itself **does not** make it safe to run untrusted builds inside your cluster, or
> anywhere else.»
>
> — Kaniko README

Разница между «сборка не требует привилегий» и «сборку можно доверить чужому коду» — это разница
между тем, что инструмент **просит** у среды, и тем, что среда ему **позволяет**. Отсутствие
привилегий убирает один путь эскалации; всё остальное — сеть, доступ к секретам смонтированным в
под, доступ к сервису метаданных облака — остаётся ровно там же, где было.

**Правило.** Вопрос «Kaniko или BuildKit» почти всегда задан не с той стороны. Начинайте с «есть ли
у задания право говорить с демоном и чей код оно собирает» — ответ на него выбирает инструмент сам,
а список из трёх имён нужен только чтобы этот ответ было чем реализовать.

## 3. Кэш слоёв, который не переживает исполнителя

**Задача.** Образ `payments` собирается из трёхэтапного `Dockerfile`: Maven тянет зависимости,
пакует jar, `jarmode=tools` разбирает его на слои. На стенде полная сборка без кэша — **95,66 с**;
в настоящем конвейере с полусотней зависимостей это минуты. Между двумя коммитами меняется
несколько строк в `src/`, всё остальное идентично. Хочется платить только за изменившееся.

**Наивное решение.** «Docker же кэширует слои — вторая сборка будет быстрой». На ноутбуке так и
происходит. В конвейере — нет, и причина не в Docker.

**Где ломается.** Кэш слоёв — это содержимое файловой системы сборщика. Исполнитель эфемерен
([`PIPELINE_MODEL.md` §5](PIPELINE_MODEL.md)): машина создаётся под задание и уничтожается вместе с
ним, а вместе с машиной уходит и кэш. Каждая сборка в конвейере — первая сборка. Проверяется это
одной командой: `docker buildx prune -af` стирает кэш сборщика целиком (в прогоне 3 освободилось
1,438 ГБ) — ровно то состояние, в котором эфемерный исполнитель видит проект впервые.

**Механизм.** Раз кэш обязан пережить машину, он должен лежать не на машине. Внешнее хранилище,
которое у конвейера уже есть, — реестр образов, и BuildKit умеет писать кэш туда же, где лежат
образы, но отдельным артефактом:

> «Allows for separating the cache and resulting image artifacts so that you can distribute your
> final image without the cache inside.»
> «It can efficiently cache multi-stage builds in `max` mode, instead of only the final stage.»
>
> — Docker docs, «Registry cache backend»

Вторая фраза важна для нашего `Dockerfile`: у него три этапа, и без `mode=max` во внешний кэш попал
бы только последний — то есть самое дешёвое, а долгий Maven-этап пересобирался бы каждый раз.
Сборка становится двусторонней: `--cache-to` в конце выгружает кэш в реестр, `--cache-from` в начале
подтягивает его обратно.

**Замер (прогон 3).** Кэш записан в реестр, затем локальный кэш стёрт целиком — эмуляция нового
исполнителя:

| Сборка | Реальное время | Шагов взято из кэша |
|---|---|---|
| `--cache-from type=registry` после полной очистки | **3,74 с** | **13** |
| без кэша вовсе | **95,66 с** | 0 |

Отношение ≈ 26×. Это и есть содержательный ответ на вопрос «как кэш переживает эфемерность»:
никак — его каждый раз приносят заново, просто принести 13 готовых слоёв дешевле, чем их построить.

### Ловушка, которая дороже самого замера

Первая попытка снять этот замер дала ложный успех, и разбирать его стоит внимательнее, чем итоговые
цифры. Сборщик был создан обычным способом, кэш направлен в локальный `registry:2` на хосте:

```bash
docker buildx create --name cicdbuilder --driver docker-container --use
docker buildx build --builder cicdbuilder -t localhost:5001/payments:v1 \
  --cache-to type=registry,ref=localhost:5001/payments:buildcache,mode=max --push .
```

Команда отработала 251 секунду и завершилась **с кодом 0**. Реестр при этом оказался пуст:

```
$ curl -s http://localhost:5001/v2/payments/tags/list
{"errors":[{"code":"NAME_UNKNOWN","message":"repository name not known to registry",
 "detail":{"name":"payments"}}]}
```

Следующая сборка с `--cache-from` взяла из кэша **0 шагов**.

**Причина — та же, что в §1, только с другой стороны.** Драйвер `docker-container` запускает сборщик
отдельным контейнером со своим сетевым пространством имён. `localhost:5001` внутри этого контейнера
означает сам контейнер сборщика, а не хост, где слушает реестр. Лечится тем, что сборщику отдают
сеть хоста:

```bash
docker buildx create --name cicdhost --driver docker-container --driver-opt network=host --use
```

**Второй урок, отдельный и более общий: `--cache-to`, который не смог записать кэш, не роняет
сборку.** И это не недосмотр, а следствие того, чем кэш является: он не входит в результат. Образ,
собранный без кэша, побайтово тот же самый, что собранный с кэшем, — значит, у сборки нет причины
падать оттого, что оптимизация не сработала. Конвейер остаётся зелёным, отчёт красивым, а поведение
неотличимо от «кэш настроили, но он почему-то не окупается». В действительности его никогда не было.

**Как это ловить.** Код возврата про кэш не говорит ничего, поэтому смотреть надо на два других
признака, и оба видны сразу:

- **есть ли кэш в реестре** — после первой сборки `curl .../v2/<репозиторий>/tags/list` должен
  показать тег кэша рядом с тегом образа (в починенном прогоне —
  `{"name":"payments","tags":["v1","buildcache"]}`);
- **сколько шагов пришло из кэша** — в логе следующей сборки. Ноль после «успешной» выгрузки кэша
  означает, что выгрузки не было.

Это тот же класс проблемы, что «отравленный кэш» в
[`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md): кэш — единственная часть конвейера,
которая **молча** меняет только время, и потому единственная, чью работоспособность приходится
проверять специально, а не по результату сборки.

**Правило.** Кэш слоёв через реестр включается не флагом, а тремя действиями: направить
`--cache-to ... ,mode=max` в реестр, убедиться, что кэш там появился, и один раз проверить сборку
после полной очистки локального кэша. Пропуск любого из трёх даёт конвейер, который выглядит
кэширующим и им не является. Во что кэш обходится в минутах и когда он окупается на реальной
частоте сборок — [`PIPELINE_ECONOMICS.md`](PIPELINE_ECONOMICS.md); как реестр хранит слои и почему
он вообще годится под кэш — [`DOCKER.md` §3, §9](../../infrastructure/theory/DOCKER.md).

## 4. Layered jar, Jib, buildpacks: что экономит каждый

**Задача.** `payments` собирается в исполняемый jar Spring Boot: внутри классы приложения и все
зависимости, порядка 40 МБ. Разработчик правит одну строку в контроллере. Что должно уехать в реестр?

**Наивное решение.** Одна строка `Dockerfile`:

```dockerfile
COPY target/*.jar app.jar
```

**Где ломается.** Слой образа адресуется дайджестом своего содержимого
([`DOCKER.md` §3](../../infrastructure/theory/DOCKER.md)). Правка одной строки кода делает jar другим
файлом целиком — а значит, другим слоем целиком. Реестр обязан принять все 40 МБ заново, и каждый
узел кластера обязан их заново скачать, хотя не изменился ни один байт зависимостей. Документация
Spring Boot называет это прямо:

> «The other issue is that putting your application's code and all its dependencies in one layer in
> the Docker image is not optimal.»
> «Since you probably recompile your code more often than you upgrade the version of Spring Boot you
> use, it's often better to separate things a bit more. If you put jar files in the layer before your
> application classes, Docker often only needs to change the very bottom layer and can pick others
> up from its cache.»
>
> — Spring Boot docs, «Efficient container images»

Обратите внимание, чего в этой цене **нет**: время сборки. Сборка не стала дольше — стала дороже
доставка. Это разные счета, и второй легко не заметить, потому что он выставляется не конвейеру, а
сети и реестру.

**Механизм.** Разложить содержимое jar по слоям так, чтобы граница слоя совпала с границей частоты
изменений. Spring Boot делает это разбиением на четыре части — `dependencies`, `spring-boot-loader`,
`snapshot-dependencies`, `application`, — и объясняет порядок:

> «This layering is designed to separate code based on how likely it is to change between application
> builds. Library code is less likely to change between builds, so it is placed in its own layers to
> allow tooling to re-use the layers from cache. Application code is more likely to change between
> builds so it is isolated in a separate layer.»
>
> — там же

В `Dockerfile` модуля это отдельный этап и четыре `COPY` в порядке возрастания изменчивости:

```dockerfile
RUN java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted
...
COPY --from=extract --chown=app:app /app/extracted/dependencies/ ./
COPY --from=extract --chown=app:app /app/extracted/spring-boot-loader/ ./
COPY --from=extract --chown=app:app /app/extracted/snapshot-dependencies/ ./
COPY --from=extract --chown=app:app /app/extracted/application/ ./
```

Порядок здесь не косметика: слой инвалидирует все слои выше себя, поэтому редко меняющееся кладут
первым. После правки контроллера пересобирается и передаётся только последний слой — классы
приложения, единицы мегабайт вместо сорока.

**Побочный эффект, который стоил модулю красной сборки.** Разбор на слои меняет форму артефакта
внутри образа. Документация Spring Boot показывает `extract --layers` без `--launcher` и завершает
`Dockerfile` строкой `ENTRYPOINT ["java", "-jar", "application.jar"]`. Наш `Dockerfile` извлекает
**с** `--launcher` — и тогда никакого `application.jar` в образе нет, есть распакованное дерево
`BOOT-INF/`, `META-INF/`, `org/`. Первая версия образа падала с `non-zero exit (1)` во всех репликах
(прогон 6), пока точку входа не взяли из манифеста:

```
$ grep -a "Main-Class\|Start-Class" /app/META-INF/MANIFEST.MF
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: by.pavel.payments.PaymentsApplication
```

Отсюда `ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]`. Урок общий:
слои — это не «та же программа, разложенная по полкам»; после разбора запускается другой артефакт
другим способом, и проверять это надо запуском, а не чтением.

**Jib и buildpacks решают ту же задачу, убирая `Dockerfile`.** Jib:

> «Jib builds optimized Docker and OCI images for your Java applications without a Docker daemon -
> and without deep mastery of Docker best-practices.»
> «Jib separates your application into multiple layers, splitting dependencies from classes.»
>
> — Jib README (GoogleContainerTools)

Формулировка «without a Docker daemon» ставит Jib в один ряд с §2: он не просто удобнее, он снимает
ту же проблему доступа к демону, только на уровне сборочного плагина. Buildpacks через
`spring-boot:build-image` — противоположный случай, и это надо знать до того, как ставить их в
конвейер:

> «This means you can just type a single command and quickly get a sensible image into your locally
> running Docker daemon.»
>
> — Spring Boot docs, «Cloud Native Buildpacks»

«Locally running Docker daemon» — то самое, чего у задания в контейнере нет. Удобство на ноутбуке
здесь не переносится в конвейер бесплатно.

**Критерий выбора.**

| Что должно быть правдой | Что из этого следует |
|---|---|
| Нужен контроль над базовым образом, пользователем, точкой входа; `Dockerfile` команда готова вести | `Dockerfile` + `jarmode=tools extract --layers` — вариант модуля |
| Демона нет, лишнего файла в репозитории не хочется, образ нужен «просто из сборки» | Jib |
| Единый способ собирать образы для десятка сервисов, базовый образ — забота платформы | buildpacks, но проверьте, откуда возьмётся демон |

**Правило.** Вопрос не «как уменьшить образ», а **«что в нём меняется от коммита к коммиту»**.
Уменьшение общего размера почти ничего не даёт, если единственный слой переписывается целиком;
разделение по частоте изменений даёт выигрыш даже при том же суммарном размере. Считайте не
мегабайты образа, а мегабайты дельты.

## 5. Тег против дайджеста

**Задача.** Образ `payments` собран, отправлен в реестр под тегом `dev`, раскатан на dev-окружение,
проверен. Теперь его надо продвинуть на qa — там должно поехать **то же самое**, иначе проверка на
dev не значила ничего.

**Наивное решение.** «Тег и есть имя образа: раскатали `payments:dev` на dev, потом на qa — значит,
раскатали одно и то же».

**Где ломается — прогон 4.** Тот же тег до и после пересборки того же исходного дерева:

```
$ docker buildx imagetools inspect localhost:5001/payments:v1
Name:      localhost:5001/payments:v1
Digest:    sha256:25a00689dd771dfcbdaaa524ab9739c6ebbcbb5a4c4ac179c4ee030a2e5bb52b

# ... пересборка и push под тем же тегом ...

$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:81fc786d34ef4d8957ce99f13ac108aa8692ead54a4a151e39e7e74b57bab132
```

Тег `v1` продолжает существовать и указывает уже на другое содержимое. **Никакой ошибки при этом не
возникает** — ни в реестре, ни в конвейере, ни в кластере. Это не сбой и не злоупотребление: это
штатное поведение, ради которого теги и придуманы.

**Механизм.** У образа две принципиально разные формы адресации, и спецификация разрешает обе:

> «the digest of the manifest or (b) a tag. The `<tag-or-digest>` MUST NOT be in any other format.»
>
> — OCI Distribution Spec, раздел «Pulling Manifests»

Разница между ними — не в длине строки, а в том, откуда берётся связь «имя → содержимое».

*Тег — это запись в реестре.* Отношение «тег `v1` указывает на манифест X» хранится реестром и
меняется операцией `push`. Ничего в самом образе про его теги не записано, и ничто не мешает
переставить тег на другой манифест.

*Дайджест — это функция от содержимого.*

> «**Digest**: a unique identifier created from a cryptographic hash of a Blob's content.»
>
> — OCI Distribution Spec, раздел «Definitions»

> «The _digest_ property of a Descriptor acts as a content identifier, enabling content
> addressability.»
> «It uniquely identifies content by taking a collision-resistant hash of the bytes.»
> «If the _digest_ can be communicated in a secure manner, one can verify content from an insecure
> source by recalculating the digest independently, ensuring the content has not been modified.»
>
> — OCI Image Spec, раздел «Digests»

Отсюда вся асимметрия одной фразой: **тег можно переставить, потому что он хранится; дайджест
переставить нельзя, потому что он вычисляется.** Чтобы «подменить» дайджест, нужно не право на `push`,
а коллизия SHA-256.

**Три следствия, которые видны сразу.**

*Первое: «тот же тег» не значит «тот же образ» — ни между окружениями, ни между узлами.* Kubernetes
формулирует это в тех же терминах:

> «When using image tags, if the image registry were to change the code that the tag on that image
> represents, you might end up with a mix of Pods running the old and new code. An image digest
> uniquely identifies a specific version of the image, so Kubernetes runs the same code every time
> it starts a container with that image name and digest specified.»
>
> — Kubernetes docs, «Images», раздел «Image pull policy»

Слово «mix» здесь ключевое: расходятся не окружения целиком, а отдельные поды — те, что стартовали
до перестановки тега, и те, что после. Усиливается это политикой `IfNotPresent`, при которой «the
image is pulled only if it is not already present locally» (там же): узел, у которого образ уже
лежит, новый вообще не заберёт.

*Второе: откат по тегу — не откат.* «Вернём `v1.2.3`» имеет смысл, только если `v1.2.3` всё ещё те
же байты, что были в проде неделю назад. Проверить это можно ровно одним способом — сравнив
дайджесты.

*Третье: `latest` — крайний случай того же самого, а не отдельная беда.* Рекомендация Kubernetes
формулируется без ссылки на безопасность:

> «You should avoid using the `:latest` tag when deploying containers in production as it is harder
> to track which version of the image is running and more difficult to roll back properly.»
>
> — там же

`dev`, `staging`, `stable` ничем не лучше `latest`: любой тег, который переставляют, — это `latest`
под другим именем.

**Как это выглядит в конвейере модуля.** Задание `image` в `pipelines/github/ci.yml` отдаёт вниз по
графу не тег, а дайджест:

```yaml
    outputs:
      digest: ${{ steps.push.outputs.digest }}
```

Тег `${{ github.sha }}` при этом остаётся — он нужен человеку, чтобы найти образ глазами. Роли
разделены: **тег адресует образ для людей, дайджест — для машин.**

**Чего дайджест не делает.** Он идентифицирует содержимое, но ничего не говорит о происхождении:
дайджест не отвечает на вопрос «этот образ собрал наш конвейер из нашего коммита» — он отвечает
только «это ровно те байты, что и были». Образ, подложенный тем, у кого есть право `push`, имеет такой
же честный дайджест. Происхождение закрывается подписью и утверждением о сборке —
[`SUPPLY_CHAIN_SECURITY.md` §9](SUPPLY_CHAIN_SECURITY.md).

**Правило.** Всё, на чём держится гарантия «на следующем окружении поедет проверенное», адресуется
дайджестом: манифест раскатки, откат, отчёт о том, что сейчас в проде. Тег — подпись под фотографией,
удобная и необязательная. Как дайджест доезжает до манифестов окружений и почему один и тот же
артефакт вообще должен проходить всю цепочку — в
[`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md).

## 6. Аутентификация конвейера в реестре

**Задача.** Задание `image` собирает образ и делает `push`. Реестр — не файловая шара: он должен
понять, кто пришёл и что этому кому-то разрешено.

**Наивное решение** — то, что записано в `pipelines/github/ci.yml` буквально:

```yaml
      - run: echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login registry.example.com -u "${{ secrets.REGISTRY_USER }}" --password-stdin
```

Работает с первой попытки, и в учебном конвейере стоит именно оно.

**Где ломается.** У этого решения три свойства, каждое из которых само по себе терпимо, а вместе они
дают знакомый инцидент. Пароль **долгоживущий** — он не истекает и после утечки полезен
злоумышленнику неограниченно долго. Он **широкий** — если это учётная запись, которой пользуются
люди, у неё права на весь реестр, а не на один репозиторий образа. И он **доступен любому заданию**
репозитория, которое умеет читать секреты, — включая то, которое написали не вы. Разбор этого класса
целиком — [`SUPPLY_CHAIN_SECURITY.md` §1](SUPPLY_CHAIN_SECURITY.md).

**Механизм — три способа, отличающиеся тем, сколько живёт учётная запись.**

*Robot-аккаунт.* Отдельная учётная запись, созданная под конвейер, с правом `push` только в
`payments`. Секрет по-прежнему долгоживущий, но радиус поражения сузился с реестра до одного
репозитория образа. Это минимум, ниже которого опускаться незачем.

*Токен, который платформа выдаёт самому заданию.* Реестр, живущий внутри той же платформы, что и
конвейер, может не требовать никакого хранимого секрета: токен создаётся под запуск и умирает вместе
с ним, а права объявляются в конвейере явно:

```yaml
    permissions:
      contents: read
      packages: write
```

> «The token's permissions are limited to the repository that contains your workflow.»
>
> — GitHub docs, «Publishing and installing a package with GitHub Actions»

*Федерация без хранимого секрета.* Для облачных реестров (ECR, Artifact Registry) конвейер
предъявляет короткоживущий подписанный токен, который облако обменивает на временные учётные данные.
Красть заранее нечего: секрета не существует. Механика — [`SUPPLY_CHAIN_SECURITY.md`
§2](SUPPLY_CHAIN_SECURITY.md).

**Отдельно — вторая учётная запись, про которую забывают.** `push` делает конвейер, `pull` делает
кластер, и это разные субъекты с разными правами: кластеру нужен только `pull`, и только на те
репозитории, которые он запускает. Одна общая учётка «для образов» превращает компрометацию узла
кластера в право переписать образ.

**Правило.** Про доступ в реестр из конвейера задают два вопроса: **сколько эта учётная запись живёт**
и **что она может, кроме `push` в один конкретный репозиторий образа**. Правильные ответы — «минуты»
и «ничего»; чем дальше ваши ответы от этих, тем больше вы храните, а не настраиваете.

## 7. Хранение и сборка мусора в реестре

**Задача.** Конвейер `payments` собирает образ на каждый коммит в `main`. Двадцать слияний в день —
двадцать образов в день, около пяти тысяч за рабочий год. И это один сервис из двадцати.

**Наивное решение.** «Место кончится — удалим старые теги». Удаляем — место не освобождается.

**Механизм — почему удаление и освобождение это два разных события.** Реестр хранит манифесты и
блобы отдельно: манифест ссылается на слои, слои разделяются между образами. Удаление манифеста
только снимает ссылку; собственно освобождение делает отдельный проход:

> «Garbage collection runs in two phases. First, in the "mark" phase, the process scans all the
> manifests in the registry… Secondly, in the "sweep" phase, the process scans all the blobs and if
> a blob's content address digest is not in the mark set, the process deletes it.»
> «As long as a layer is referenced by one manifest, it cannot be garbage collected.»
>
> — Docker Registry docs, «Garbage collection»

Отсюда два следствия, оба контринтуитивные.

*Удаление одного образа обычно освобождает почти ничего.* Базовый `eclipse-temurin:21-jre-alpine` и
слой `dependencies` (§4) общие для всех сборок `payments`: пока жива хоть одна, они не уйдут. Реально
удаляется только верхний слой с классами приложения — единицы мегабайт из сорока. Разделение слоёв,
которое экономило трафик, ровно так же экономит и хранение: пять тысяч сборок занимают не пять тысяч
образов, а один набор общих слоёв плюс пять тысяч маленьких верхушек.

*Сборка мусора — операционное окно, а не фоновая задача.*

> «You should ensure that the registry is in read-only mode or not running at all. If you were to
> upload an image while garbage collection is running, there is the risk that the image's layers are
> mistakenly deleted leading to a corrupted image.»
>
> — там же

Причина видна из «mark»: набор живых блобов вычисляется по снимку манифестов, и образ, появившийся
после снимка, в него не попал — его слои будут признаны мусором. Для управляемого реестра это скрыто
провайдером, для своего — прямое требование к расписанию: чистка не совмещается со сборками.

**Что делает политику удержания политикой.** Правило удержания описывается критерием «что оставить»,
а не «что удалить»:

> «When you set a rule, any tags in a repository that are not identified as being eligible for
> retention are discarded.»
> «Retention is matched at the tag level but retention / deletion is carried out at the artifact
> level.»
>
> — Harbor docs, «Configure tag retention rules»

Вторая фраза объясняет ходовой сюрприз: правило пишут про теги, а удаляется артефакт целиком — со
всеми остальными своими тегами. Образ, который вы оставили как `v1.4.0`, исчезнет вместе с ним, если
критерий удержания смотрел на тег `dev`. Отдельно решается судьба артефактов без тегов вовсе — это
результат перестановки тега из §5: старый манифест никуда не делся, просто на него больше никто не
ссылается по имени.

**Где это ломается по-настоящему.** Критерии удержания вида «последние N сборок» считают от **ветки
сборки**, а не от того, что работает в проде. Прод, отставший на два релиза, легко оказывается за
пределами последних N — и первый же откат упирается в «manifest unknown». Это не сбой реестра: это
несогласованность двух политик, написанных разными людьми.

**Правило.** Политика удержания проектируется от политики отката, а не от размера диска: сначала
ответ на «на сколько версий назад мы обязаны уметь откатиться», потом критерий, который гарантированно
удерживает всё, на что ссылается живое развёртывание, и только потом — сколько остального оставлять
про запас. И держите в голове второй счёт: реестр вырастет не от числа сборок, а от числа **разных**
слоёв, — поэтому смена базового образа стоит дороже, чем тысяча коммитов.

## 8. Образы под несколько архитектур

**Задача.** Разработчики `payments` сидят на Apple Silicon (arm64), прод исторически на amd64, а
инфраструктура присматривается к arm-инстансам ради цены. Образ должен запускаться на обеих
архитектурах.

**Наивное решение.** Дописать в команду сборки одну строку: `--platform linux/amd64,linux/arm64`.
Формально это работает; результат — не два образа, а один составной:

> «Multi-platform images contain a manifest list, pointing to multiple manifests, each of which
> points to a different configuration and set of layers.»
>
> — Docker docs, «Multi-platform builds»

**Где ломается.** Исполнитель конвейера имеет ровно одну архитектуру. Всё, что собирается под
другую, исполняется через эмуляцию, и документация не смягчает формулировку:

> «Emulation with QEMU can be much slower than native builds, especially for compute-heavy tasks
> like compilation and compression or decompression.»
>
> — там же, раздел «QEMU»

Слова «compilation and compression» указывают прямо на наш `Dockerfile`: первый его этап — Maven,
который компилирует; второй — распаковка jar. То есть под эмуляцию попадает не какая-то маргинальная
часть сборки, а самая дорогая.

**Механизм — три стратегии, и выбор между ними определяется одним вопросом.**

> «You can build multi-platform images using three different strategies, depending on your use case:
> 1. Using emulation, via QEMU 2. Use a builder with multiple native nodes 3. Use cross-compilation
> with multi-stage builds»
>
> — там же, раздел «Strategies»

Вопрос такой: **что именно в вашей сборке зависит от целевой архитектуры.** Для Java ответ приятный —
почти ничего. Байткод в class-файлах архитектурно нейтрален по определению формата, поэтому jar,
собранный на amd64, побайтово годится для arm64; от архитектуры зависит только базовый образ с JRE.
Значит, компилировать под каждую платформу незачем — компилировать надо один раз, нативно, а
различать только последний этап. Это и есть третья стратегия:

> «You can leverage multi-stage builds to build binaries for target platforms from the native
> architecture of the builder.»
> «The `FROM` instruction is pinned to the native platform of the builder (using the
> `--platform=$BUILDPLATFORM` option) to prevent emulation from kicking in.»
>
> — там же, раздел «Cross-compilation»

Применительно к `Dockerfile` модуля это означает `FROM --platform=$BUILDPLATFORM
maven:3.9-eclipse-temurin-21 AS build` — этап сборки остаётся нативным, а под эмуляцию (или под
нативный узел) уходит только финальный этап, который всего лишь копирует готовые каталоги.

**Когда стратегия 3 не спасает.** Как только в сборке появляется что-то, что действительно
компилируется под целевую архитектуру, — нативная библиотека, JNI, GraalVM Native Image — цена
возвращается целиком, и остаётся выбор между медленной эмуляцией и нативными узлами:

> «Using multiple native nodes provide better support for more complicated cases that QEMU can't
> handle, and also provides better performance.»
>
> — там же, раздел «Multiple native nodes»

Нативные узлы — это два исполнителя вместо одного, то есть та же матрица сборки со всеми её
издержками ([`RUNNERS_AND_EXECUTION.md` §6](RUNNERS_AND_EXECUTION.md)): парк машин под каждую
архитектуру, две очереди, два набора кэша.

**Когда это неправильный ответ.** Собирать под две архитектуры «на всякий случай» — чистый расход.
Мультиархитектурный образ нужен, когда обе архитектуры действительно исполняются: прод на одной,
ноутбуки на другой, или идёт переезд. Если прод один и переезда не планируется, вторая платформа
покупает удобство локального запуска ценой каждой сборки конвейера — размен, который стоит делать
осознанно, а не по умолчанию.

**Правило.** Прежде чем добавлять вторую платформу, разделите сборку на «что зависит от архитектуры»
и «что не зависит». Для типового Java-сервиса первая часть — только базовый образ, и тогда вторая
платформа почти бесплатна. Если же первая часть непустая, честная оценка звучит так: вы удваиваете
не размер артефакта, а самое дорогое место конвейера.

## 9. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Что на самом деле выбирает способ сборки образа | чей код собирается и что ещё стоит на этой машине |
| Чему равен доступ к сокету демона | root на хосте, где работает демон |
| Что убирает BuildKit | не демон, а лишнюю работу: граф, параллелизм, инкрементальный контекст |
| Что убирает Kaniko и Buildah | демон; но не опасность недоверенной сборки |
| Почему кэш слоёв не работает в конвейере сам собой | он лежит на исполнителе, а исполнитель умирает |
| Как понять, что внешний кэш реально работает | тег кэша появился в реестре, и следующая сборка взяла из него шаги |
| Худший режим отказа кэша | `--cache-to` не записал, сборка зелёная — «кэш не окупается» вместо «кэша нет» |
| Что экономит layered jar | не размер образа, а размер дельты между сборками |
| Чем тег отличается от дайджеста | тег хранится и переставляется, дайджест вычисляется из содержимого |
| Что дайджест не гарантирует | происхождение: чем и из какого кода собран образ |
| Почему удаление образа не освобождает место | слои общие; освобождает отдельный проход mark-and-sweep |
| От чего проектируется политика удержания | от политики отката, не от размера диска |
| Что для Java зависит от целевой архитектуры | только базовый образ с JRE; байткод — нет |

**Дерево решения по сборке образа:** демон доступен и машина одноразовая → `docker buildx`. Демона
нет, есть кластер → Kaniko. Нужна сборка не из `Dockerfile` → Buildah. Демон общий с чужими
заданиями → задача не про инструмент, а про изоляцию (§1).

### Формулировки для собеседования

- «Дать заданию доступ к демону Docker — это дать ему root на хосте: API демона позволяет запустить
  контейнер с корнем хоста внутри, и никаких прав он при этом не проверяет».
- «Кэш слоёв в конвейере не переживает исполнителя, поэтому его выносят в реестр; и главное — если
  выгрузка кэша не удалась, сборка остаётся зелёной, поэтому проверять надо не код возврата, а
  наличие кэша».
- «Тег хранится в реестре и переставляется операцией `push`, дайджест вычисляется из содержимого; всё,
  на чём держится продвижение и откат, адресуется дайджестом».
- «Layered jar экономит не размер образа, а размер того, что меняется между сборками: граница слоя
  ставится по частоте изменений».

- Docker docs, «Docker Engine security» — раздел «Docker daemon attack surface» (демон требует root;
  «only trusted users should be allowed to control your Docker daemon»; монтирование корня хоста).
- GitLab docs, «Use Docker to build Docker images» — разделы «Use Docker-in-Docker» (требование
  `privileged`) и «Known issues with Docker socket binding» (отключение механизмов безопасности
  контейнера, container breakout).
- Kaniko README, GoogleContainerTools — сборка из `Dockerfile` внутри контейнера, «completely in
  userspace»; оговорка «does not make it safe to run untrusted builds».
- buildah.io — сборка OCI-образов без демона и полного runtime; сборка скриптом; rootless.
- Docker docs, «BuildKit» — движок сборки по умолчанию; пропуск неиспользуемых этапов, параллелизм,
  инкрементальная передача контекста.
- Docker docs, «Registry cache backend» — отделение кэша от образа, `mode=max` для многоэтапных
  сборок, требования к драйверу.
- Spring Boot docs, «Efficient container images» и «Dockerfiles» — почему один слой не оптимален;
  четыре слоя и порядок по частоте изменений; `-Djarmode=tools … extract --layers`.
- Spring Boot docs, «Cloud Native Buildpacks» — образ собирается «into your locally running Docker
  daemon».
- Jib README, GoogleContainerTools — сборка без демона, разделение зависимостей и классов по слоям.
- OCI Distribution Spec — «Pulling Manifests» (ссылка на манифест: дайджест или тег), «Definitions»
  (определение дайджеста).
- OCI Image Spec, «Digests» — дайджест как content identifier; проверка пересчётом хеша.
- Kubernetes docs, «Images» — дайджест против тега («mix of Pods running the old and new code»),
  `IfNotPresent`, рекомендация не использовать `:latest` в проде.
- Docker Registry docs, «Garbage collection» — фазы mark и sweep, требование read-only, разделяемые
  слои.
- Harbor docs, «Configure tag retention rules» — правило удержания, критерии, «matched at the tag
  level but … carried out at the artifact level».
- Docker docs, «Multi-platform builds» — манифест-список, три стратегии, «much slower than native»,
  `--platform=$BUILDPLATFORM`.
- Журнал прогонов модуля `.build/verified/_RUNS.notes.md` — прогон 3 (кэш слоёв через реестр и
  ловушка сети сборщика), прогон 4 (тег против дайджеста), прогон 6 (точка входа после разбора jar).
