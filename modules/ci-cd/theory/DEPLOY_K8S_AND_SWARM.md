# Раскатка в кластер: Kubernetes и Docker Swarm как цель конвейера

> **Какую проблему решает.** Шаг `deploy-qa` отработал за восемь секунд, конвейер зелёный — а сервис лежит: новые поды в `CrashLoopBackOff`, старых уже нет. Вторая половина той же проблемы — слово «откат»: под ним прячутся три разные операции с тремя разными хранилищами предыдущей версии.
> **Кому это надо.** Тому, кто пишет шаг раскатки и должен ответить, почему выбрал `helm upgrade`, а не `kubectl apply`; тому, кого спросят «как в Docker Swarm выглядит откат» и «зачем вам Kubernetes, если Swarm умеет то же самое».
> **Когда НЕ надо.** Ничего из этого файла не поможет без пробы готовности: все три механизма ожидания спрашивают кластер «готово?», а кластер отвечает по пробам — без них ожидание вырождается в «контейнер запустился».

**Границы.** **Кто** применяет изменение и откат как `git revert` — [`DELIVERY_PUSH_VS_PULL.md` §1, §5](DELIVERY_PUSH_VS_PULL.md); здесь — **чем** физически применяет. Продвижение артефакта и место миграции схемы — [`ENVIRONMENTS_AND_PROMOTION.md` §1, §7](ENVIRONMENTS_AND_PROMOTION.md).
Объекты Kubernetes, механика `RollingUpdate` и пробы готовности — [`KUBERNETES.md` §5, §10](../../infrastructure/theory/KUBERNETES.md); устройство чарта и хуки — [`HELM.md` §2, §4, §5](../../infrastructure/theory/HELM.md); управляемые платформы вне Kubernetes — [`DEPLOY_CLOUD_PLATFORMS.md`](DEPLOY_CLOUD_PLATFORMS.md).
Канарейка, blue-green и A/B как механизмы — [`PROGRESSIVE_DELIVERY_K8S.md`](PROGRESSIVE_DELIVERY_K8S.md); готовые сквозные конвейеры релиза — [`RELEASE_PIPELINE_RECIPES.md`](RELEASE_PIPELINE_RECIPES.md); выбор между откатом и накатом — [`RELEASE_STRATEGIES.md` §6](../../engineering-process/theory/RELEASE_STRATEGIES.md).

Сквозной пример модуля — сервис `payments`: Spring Boot 3.3.4, Java 21, PostgreSQL, пик 40 запросов в секунду, три реплики. Вывод в блоках Swarm снят на Apple Silicon, macOS 15 (Darwin 25.6.0), Docker 29.4.3, Helm v4.2.4 — порядок величин; раскатка в Kubernetes на этом стенде не прогонялась, и всё, что её касается, подпёрто документацией.

## 1. `kubectl apply`, `helm upgrade` и синхронизация Argo CD: чем платит каждый

Вариантов, чем написать шаг раскатки, ровно три, и отличаются они не синтаксисом, а тем, **где хранится предыдущее состояние всего набора ресурсов**.

*`kubectl apply -f k8s/`: нигде.* На одном Deployment это лучший ответ. Но `payments` — не один объект: Deployment, Service, ConfigMap, Secret, Ingress, HPA, PodDisruptionBudget. `apply` обрабатывает объекты **по одному** и вычисляет разницу для каждого отдельно — он «sets fields that appear in the configuration file in the live configuration». Если пятый манифест не прошёл валидацию, первые четыре **уже применены**, и команда завершится с ошибкой, оставив кластер в состоянии, которого нет ни в одном файле. Предыдущая конфигурация каждого объекта живёт в его собственной аннотации `kubectl.kubernetes.io/last-applied-configuration`, история ревизий есть только у Deployment и только про его поды (§8); набор как целое не отслеживается никем.

*`helm upgrade`: в самом Helm.* Helm хранит **релиз** — набор ресурсов чарта плюс номер ревизии ([`HELM.md` §4](../../infrastructure/theory/HELM.md)). Отсюда то, чего не может `kubectl`: обновление становится транзакцией.

> «`--rollback-on-failure` — if set, Helm will rollback the upgrade to previous success release upon failure. The `--wait` flag will be defaulted to "watcher" if `--rollback-on-failure` is set»
>
> — Helm docs, `helm upgrade`

**Осторожно с названием флага на собеседовании.** До Helm 4 он назывался `--atomic`, и именно эта форма ходит по статьям. В Helm 4 переименование зафиксировано: «`--atomic → --rollback-on-failure`», причём «the existing flags remain, but emit a deprecated warning». На стенде (Helm v4.2.4+g3900f43):

```
$ helm upgrade --help | grep -c atomic
0
$ helm upgrade payments ./payments --atomic --dry-run …
Flag --atomic has been deprecated, use --rollback-on-failure instead
```

В справке флага **уже нет** — ни у `upgrade`, ни у `install`, — но разбор аргументов его по-прежнему принимает. Вариант «у одной команды работает, у другой падает с unknown flag» проверку не проходит. Практический вывод для конвейера: скрипт 2022 года продолжает работать, предупреждение теряется в общем логе, и момент, когда флаг перестанут принимать совсем, вы пропустите.

*Синхронизация Argo CD: в Git, и применяет её не конвейер.* Шага раскатки в конвейере нет вовсе: конвейер коммитит новый дайджест в репозиторий конфигурации, агент внутри кластера замечает расхождение и устраняет его ([`DELIVERY_PUSH_VS_PULL.md` §1](DELIVERY_PUSH_VS_PULL.md)). Механически важно, что цикл согласования не мгновенный:

> «The automatic sync interval is determined by the `timeout.reconciliation` value in the `argocd-cm` ConfigMap, which defaults to `120s` with added jitter of `60s` for a maximum period of 3 minutes.»
>
> — Argo CD docs, «Automated Sync Policy»

| Способ | Что значит «шаг успешен» | Где предыдущее состояние набора | Кто откатывает | Чем платите |
|---|---|---|---|---|
| `kubectl apply -f` | API-сервер принял манифесты | нигде: только в Git ваших манифестов | вы, руками | частичное применение при ошибке в середине |
| `helm upgrade --rollback-on-failure` | Helm дождался готовности и зафиксировал ревизию | в истории релиза Helm | Helm сам | неудачный прогон удлиняется на ожидание + откат |
| синхронизация Argo CD | коммит записан в репозиторий конфигурации | в истории Git | согласование, после `git revert` | конвейер теряет обратную связь о раскатке |

Третья строка — самая недооценённая: переход на доставку вытягиванием **не убирает** проблему, а переносит её. «Зелёный конвейер» теперь означает лишь «коммит записан», и узнать из него, поднялся ли сервис, невозможно в принципе; если обратная связь нужна, её возвращают отдельным шагом (`argocd app wait`, §2) — и тогда конвейеру снова нужен доступ, уже не к кластеру, а к Argo CD.

Вторая строка платит временем, и платит именно тогда, когда болит: пока всё хорошо, `--rollback-on-failure` не стоит ничего, а при неудаче шаг сначала ждёт готовности до таймаута, потом откатывает и ждёт снова — самый быстрый возможный сигнал «сломано» превращается в самый медленный шаг конвейера. Это осознанный размен: кластер остаётся рабочим без участия человека.

**Правило.** Выбирайте не команду, а ответ на вопрос: **где хранится предыдущее состояние всего набора ресурсов и кто обязан вернуть его без человека.** Всё остальное — синтаксис.

## 2. Ожидание готовности: почему конвейер зелёный, а под падает

Задание `deploy-qa` завершилось успешно. Доказано этим ровно одно: API-сервер принял YAML. Типичный шаг выглядит так:

```yaml
      - run: helm upgrade --install payments ./payments -f ./payments/values-qa.yaml
               --set image.digest="${{ needs.image.outputs.digest }}"
```

Ни `--wait`, ни `--rollback-on-failure`. По документации Helm 4 это означает вот что:

> «`--wait WaitStrategy[=watcher]` — wait until resources are ready (up to `--timeout`). Use '`--wait`' alone for 'watcher' strategy, or specify one of: 'watcher', 'hookOnly', 'legacy'. **Default when flag is omitted: 'hookOnly'.**»
>
> — Helm docs, `helm upgrade`

Без флага Helm дожидается только хуков ([`HELM.md` §5](../../infrastructure/theory/HELM.md)), а готовности подов — нет: шаг зеленеет в момент записи ревизии релиза, за секунды. Что случится с подами дальше — образ не скачается, приложение упадёт на старте, проба готовности не пройдёт, — конвейер уже не увидит. С `kubectl apply -f` то же самое и ещё нагляднее.

Это не дефект инструментов, а следствие модели: запись желаемого состояния и приведение фактического — **два разных события во времени**, разнесённые циклом согласования ([`KUBERNETES.md` §2](../../infrastructure/theory/KUBERNETES.md)). Команда записи физически не может сообщить исход согласования: в момент её возврата согласование ещё не началось. Значит, у кластера надо спросить **второй раз** и другим вопросом — «готово?».

| Чем применили | Чем дожидаетесь |
|---|---|
| `kubectl apply -f` | `kubectl rollout status deployment/payments --timeout=5m` |
| `helm upgrade` | `--wait` (или `--rollback-on-failure`, который включает `--wait=watcher` сам) |
| коммит в репозиторий конфигурации | `argocd app wait payments-qa --health --sync --timeout 300` |

Первая форма описывает себя прямо: «By default '`rollout status`' will watch the status of the latest rollout until it's done». Третья — столь же коротко: «Wait for an application to reach a synced and healthy state».

**Как ожидание кончается неудачей — и что Kubernetes при этом НЕ делает.** У Deployment есть срок, за который он обязан продвинуться: `progressDeadlineSeconds` — «the maximum time in seconds for a deployment to make progress before it is considered to be failed… a condition with a `ProgressDeadlineExceeded` reason will be surfaced in the deployment status. **Defaults to 600s.**» И сразу за этим — предложение, которое стоит выучить дословно:

> «Kubernetes takes no action on a stalled Deployment other than to report a status condition with `reason: ProgressDeadlineExceeded`.»
>
> — Kubernetes docs, «Deployment», раздел «Failed Deployment»

Kubernetes **не откатывает** застрявшую раскатку: он выставляет условие и продолжает пытаться, старые поды при `RollingUpdate` остаются живы, новые крутятся в отказе. Красным конвейер делает не кластер, а `kubectl rollout status`, который на этом условии завершается ненулевым кодом. Уберите ожидание — и единственный, кто вообще замечает провал, исчезает из картины.

**Чего ожидание готовности не делает.** Оно проверяет ровно то, что проверяет проба готовности, и ни на йоту больше. Проба `httpGet` на `/actuator/health/readiness` означает «Spring поднял контекст и Actuator отвечает» — не «сервис умеет обрабатывать платежи» ([`KUBERNETES.md` §10](../../infrastructure/theory/KUBERNETES.md)). Смоук-проверка после раскатки — отдельный шаг конвейера.

**Правило.** Шаг раскатки состоит из **двух** команд, а не из одной: «примени» и «дождись». Уберите у сервиса пробу готовности — и все три способа ожидания продолжат отчитываться об успехе, потому что спрашивать им станет не о чем.

## 3. Docker Swarm: разворачивание стека и постепенная замена

Swarm mode — переключение того же демона Docker в режим, где у сервиса появляется **желаемое состояние** и кто-то, кто его поддерживает: «Docker Engine uses a declarative approach to let you define the desired state of the various services» / «At rollout time you can apply service updates to nodes incrementally» (Docker docs, «Swarm mode overview»). `docker stack deploy -c stack.yml payments` применяет compose-файл как желаемое состояние стека — тот же декларативный жест, что `kubectl apply`, только единица не объект, а стек целиком. Постепенная замена настраивается в `deploy.update_config`:

```yaml
      update_config:
        parallelism: 1        # сколько задач меняем за раз
        delay: 10s            # пауза между группами
        order: start-first    # новая задача поднимается до остановки старой
        failure_action: rollback
        monitor: 20s          # окно наблюдения за только что запущенной задачей
```

**Значения по умолчанию выбраны не в вашу пользу** — по той же спецификации `order` по умолчанию `stop-first`, а `failure_action` — `pause`: без явной настройки Swarm сначала гасит старую задачу (на трёх репликах это минус треть ёмкости в каждый момент замены), а при неудаче **замирает на середине**, и никто ничего не откатывает. Прогон `docker service update --image payments:v2 payments_api` на трёх репликах, опрос `docker service ls` раз в 5 секунд:

```
t+ 5s  3/3 payments:v1
t+10s  3/3 payments:v2      ← колонка образа = объявленная спецификация, а не факт
t+30s  4/3 payments:v2      ← вот здесь виден start-first
t+45s  4/3 payments:v2
t+60s  3/3 payments:v2      verify: Service payments_api converged   (всего 59,4 с)
```

Строка `t+10s` — тот же обман, что в §2: колонка показывает **объявленную** спецификацию сервиса, а не то, что выполняется. Строка `4/3` — `start-first` в чистом виде: реплик заказано три, живёт четыре, ёмкость не просела ни на секунду, и заплачено за это пиковым потреблением (на забитом кластере четвёртая задача просто не найдёт себе места). Минута на три реплики — не накладные расходы Swarm, а ваши собственные паузы: `delay` и `monitor` куплены за наблюдаемость, и убрать их можно одним числом — тогда сломанная версия доедет до всех трёх реплик раньше, чем кто-нибудь это заметит.

**Правило.** Постепенная замена в Swarm настраивается теми же двумя решениями, что и в Kubernetes, — сколько задач меняем за раз и в каком порядке относительно старых; разница в том, что умолчания (`stop-first`, `pause`) описывают одиночный контейнер, а не сервис из трёх реплик.

## 4. Docker Swarm: откат на практике

`v2` уехала на все три реплики, пошли ошибки. Обратное обновление `docker service update --image payments:v1` ломается втройне: надо помнить, что предыдущей была именно `v1`; назад поедет **только образ**, а изменённые тем же обновлением переменные и лимиты останутся от `v2` — получится третья, никогда не существовавшая конфигурация; и пойдёт оно по `update_config`, то есть медленно, ровно когда медленно нельзя.

Swarm хранит предыдущую спецификацию сам: `docker service rollback` возвращает сервис к «the configuration that was in place before the most recent `docker service update` command» — **конфигурацию целиком**, а не образ. У отката своя, отдельная от обновления политика:

```yaml
      rollback_config:
        parallelism: 0        # «if set to 0, all containers rollback simultaneously»
        order: stop-first
```

```
t+ 4s  3/3 payments:v2
t+12s  0/3 payments:v1      ← полный простой
t+16s  3/3 payments:v1      verify: converged   (всего 29,9 с)
```

Две настройки **одного и того же сервиса** дают противоположный размен: обновление — 59,4 с и ёмкость не ниже 3/3 (в момент замены 4/3); откат — 29,9 с и несколько секунд на **0/3**. Это осознанный выбор: **при откате вы уже знаете, что текущая версия сломана**, и тридцать лишних секунд её работы дороже пяти секунд честного простоя.

**Чего этот откат не делает.** Он живёт целиком внутри Swarm и ничего не знает про Git: после него `stack.yml` в репозитории описывает `v2`, а кластер выполняет `v1`, и следующий `docker stack deploy` молча вернёт сломанную версию. Это тот же класс расхождения, что в [`DELIVERY_PUSH_VS_PULL.md` §2](DELIVERY_PUSH_VS_PULL.md), — только там его находит и устраняет агент согласования, а здесь не находит никто. Второе ограничение читается прямо из цитаты: откат определён относительно **последнего** обновления, глубины истории нет — вернуться на две версии назад этой командой нельзя.

**Правило.** «Откатить» в Swarm — отдельная операция с отдельной политикой, а не обновление задом наперёд. Настраивайте `rollback_config` раньше, чем он понадобится, и сразу после отката приводите в порядок описание в репозитории.

## 5. Что теряется при уходе с Kubernetes на Swarm

Сравнивать надо не возможности, а **словарь**: сколько разных вещей платформа умеет называть, и что происходит, когда нужная вам вещь в него не входит. У Swarm словарь закрыт — сервис, сеть, том, конфигурация, секрет. У Kubernetes он открыт: «A *custom resource* is an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation» / «The Operator pattern combines custom resources and custom controllers». Когда сертификат, база или внешний секрет становятся объектами API, за их жизненный цикл отвечает чужой контроллер, который вы ставите готовым; когда такой возможности нет, каждая из этих вещей превращается в ваш скрипт с вашим обработчиком ошибок и вашим дежурным. Отсюда три потери, и все три — одно следствие.

*Масштабирование остаётся ручным.* В Kubernetes есть штатный HorizontalPodAutoscaler, который «automatically updates a workload resource… with the aim of automatically scaling capacity to match demand». В Swarm число задач объявляете **вы**: «for each service, you can declare the number of tasks you want to run». Для `payments` с его 40 запросами в секунду это потеря на бумаге; для сервиса с ночным и дневным профилем — либо круглосуточно оплаченный пик, либо человек, который меняет число вручную.

*Сложные схемы раскатки нечем выразить.* Маршрутизация в Swarm описана как балансировка между контейнерами одного сервиса: «swarm manager nodes assign each service in the swarm a unique DNS name and load balance running containers». Доли трафика между двумя версиями в этой модели нет — её приходится изображать соотношением числа реплик двух отдельных сервисов, грубо и без возможности направить конкретного пользователя. Как эти схемы устроены там, где они есть, — [`PROGRESSIVE_DELIVERY_K8S.md`](PROGRESSIVE_DELIVERY_K8S.md); здесь важно лишь, что на Swarm часть из них выразить нечем.

*Экосистема пишется против API, которого у Swarm нет.* Чарты Helm, ingress-контроллеры, service mesh, cert-manager, операторы баз — расширения Kubernetes API. Сюда же попадает вся модель доставки вытягиванием: Argo CD и Flux — контроллеры Kubernetes, для Swarm готового агента согласования в том же смысле нет, и «истина в Git» остаётся дисциплиной, а не проверяемым свойством.

**Что Swarm за это получает — и это не «ничего».** Управляющий слой Kubernetes живёт отдельно от рабочих узлов и имеет собственный жизненный цикл: обновления, сертификаты, etcd, сетевой плагин ([`KUBERNETES.md` §3](../../infrastructure/theory/KUBERNETES.md)). В Swarm его роль исполняет тот же демон Docker, который уже стоит на машине. Это не «проще в использовании», а **меньше отдельных вещей, которые надо эксплуатировать**.

**Формулировка, которая хорошо звучит и неверна: «Swarm мёртв, его закрыли».** Закрыли другой продукт: «Do not confuse Docker Swarm mode with Docker Classic Swarm which is no longer actively developed». Classic Swarm — отдельный оркестратор поверх Docker, он действительно не развивается; Swarm mode — режим самого движка, и раздел документации о нём живой.

**Правило.** Разница не в списке возможностей, а в том, **открыт ли словарь**. Если всё нужное называется словом «сервис», Swarm описывает вашу задачу целиком; если хоть что-то приходится называть иначе, на Swarm это станет вашим кодом — оценивать надо именно эту работу.

## 6. Когда Swarm — правильный ответ

«Kubernetes, потому что стандарт, и потом всё равно вырастем» — не критерий, а отложенное решение, оплаченное вперёд. Платформа выбирается по тому, **что придётся эксплуатировать в понедельник**, и это три вопроса, отвечаемых до установки чего бы то ни было.

*Какие слова из словаря Kubernetes вы произнесёте в ближайшие полгода?* Если честный список — Deployment, Service, Ingress и `kubectl logs`, открытый словарь из §5 вы не используете: всё перечисленное в Swarm называется сервисом с опубликованным портом. Если в списке есть оператор базы, cert-manager, `NetworkPolicy` или собственный CRD — разговор окончен.

*Кто эксплуатирует управляющий слой?* Здесь ответ разворачивается на 180° от одной детали. Свой кластер на своих машинах — отдельная работа. Управляемый Kubernetes у облачного поставщика — та же работа, но выполняет её поставщик, и главный аргумент в пользу Swarm исчезает ([`DEPLOY_CLOUD_PLATFORMS.md` §1, §4](DEPLOY_CLOUD_PLATFORMS.md)). **Swarm выигрывает у самостоятельно поднятого Kubernetes, а не у Kubernetes вообще.**

*Что говорит профиль нагрузки?* Пик 40 запросов в секунду, три реплики покрывают его с запасом, дневной и ночной профиль различаются несущественно — автомасштабированию нечего оптимизировать, и потеря из §5 остаётся на бумаге. Ночью ноль, днём в двадцать раз больше — тот же пункт стал бы решающим.

Свои машины, три сервиса, никаких слов вне словаря, ровный профиль — Swarm описывает такую задачу целиком, и это не компромисс, а точное попадание. Поменяйте одну вводную, «машины арендуем в облаке», — и ответом становится управляемый Kubernetes, потому что второй вопрос перестал быть вашим.

**Когда Swarm — неправильный ответ, даже пройдя три вопроса.** Если в команде есть люди с опытом Kubernetes и ни одного с опытом Swarm, «простота» обернётся незнакомым инструментом. Если нужна доставка вытягиванием как проверяемое свойство — готового агента согласования нет (§5). И отдельный вопрос, на который отвечает не документация, а рынок труда: кого проще найти на замену. Это законный аргумент, но произносить его надо как аргумент, а не как технический факт.

## 7. Декларативный `apply` против императивных команд в конвейере

Конвейер знает дайджест, и поменять надо одно поле — соблазн написать одну строку без манифеста и шаблонизатора очень велик:

```bash
kubectl set image deployment/payments payments="registry.example.com/payments@$DIGEST"
```

Через две недели кто-то запускает `kubectl apply -f k8s/`, чтобы добавить переменную окружения, — и образ откатывается на записанный в файле. Ошибки не произойдёт: `apply` «sets fields that appear in the configuration file in the live configuration», поле `image` в файле есть, значит `apply` его выставит. Императивная команда изменила живой объект, но не изменила ни файл, ни аннотацию `kubectl.kubernetes.io/last-applied-configuration`, которую `apply` использует как память о прошлом применении. Для декларативного управления вашего изменения просто не было.

Это не «плохой стиль», а прямо описанное поведение:

> «A Kubernetes object should be managed using only one technique. Mixing and matching techniques for the same object results in undefined behavior.» / «Commands do not integrate with change review processes.» «Commands do not provide an audit trail associated with changes.» «Commands do not provide a source of records except for what is live.»
>
> — Kubernetes docs, «Kubernetes Object Management»

Последняя фраза и есть корень: **единственная запись о том, что развёрнуто, — сам кластер.** Вопрос «что сейчас на qa» перестаёт иметь ответ где-либо, кроме `kubectl get`, — а значит, исчезает и возможность сравнить желаемое с фактическим, на которой держится модель из [`DELIVERY_PUSH_VS_PULL.md` §2](DELIVERY_PUSH_VS_PULL.md).

**Тот же механизм даёт неочевидное следствие про `replicas`.** Включённый HorizontalPodAutoscaler меняет `replicas` живого объекта, то есть выступает ровно в роли императивной команды. Держите `replicas: 3` в манифесте — и каждый `apply` будет возвращать три, отменяя решение автомасштабирования до следующего его срабатывания. Отсюда общее правило: **поле, которым управляет другой контроллер, не должно присутствовать в вашем манифесте** — у каждого поля ровно один владелец.

**Когда императивная команда — правильный ответ.** Когда она сознательно одноразова и её результат не должен пережить следующую раскатку: `kubectl scale` под всплеск нагрузки, `kubectl delete pod` для проверки восстановления, `kubectl rollout undo` в инциденте (§8). Разница не в команде, а в намерении: одноразовое действие человека против повторяемого шага конвейера.

**Правило.** В конвейере — только декларативное применение: конвейер выполняется много раз, и каждый прогон обязан приводить кластер к состоянию, записанному **в репозитории**, а не складываться с предыдущими прогонами. После императивной команды в файл вносится то же изменение, иначе оно исчезнет при первом же `apply`.

## 8. Что технически «откатывается» в kubectl, Helm и Argo CD

«Мы откатили раскатку» — не ответ, пока не сказано, что именно откатилось: под одним словом живут три операции с разным охватом и тремя разными хранилищами предыдущей версии.

*`kubectl rollout undo` — переключение на старый ReplicaSet.* Хранилище — сам Kubernetes, в виде старых ReplicaSet: `revisionHistoryLimit` — «the number of old ReplicaSets to retain to allow rollback… **Defaults to 10**»; `--to-revision` по умолчанию 0, то есть предыдущая ревизия. Охват точный: откатывается **только этот Deployment и только его шаблон пода**. ConfigMap, Secret, Ingress, HPA в ревизию не входят — они отдельные объекты, и если новая версия приехала вместе с новым ConfigMap, `rollout undo` вернёт старые поды с новой конфигурацией, то есть соберёт сочетание, которое никогда не тестировалось. Отдельная ловушка: `revisionHistoryLimit: 0` — законное значение, которое часто ставят «чтобы не мусорить»; после него откатывать нечем.

*`helm rollback` — возврат сохранённой ревизии релиза.* «The first argument of the rollback command is the name of a release, and the second is a revision (version) number. If this argument is omitted or set to 0, it will roll back to the previous release.» Охват шире ровно на то, чего не хватало первому: назад едет **весь набор ресурсов чарта**, включая ConfigMap и Ingress, потому что единицей истории здесь является релиз. Граница тоже есть: Helm не знает об объектах, которые создал не он, и не отменяет **последствия** хуков — отработавшее перед обновлением задание миграции откатом релиза не отменяется никак ([`HELM.md` §5](../../infrastructure/theory/HELM.md)).

*`git revert` — возврат желаемого состояния.* Хранилище — Git, исполнитель — цикл согласования; разбор целиком, вместе со случаями, когда это не работает, — [`DELIVERY_PUSH_VS_PULL.md` §5](DELIVERY_PUSH_VS_PULL.md). Здесь важен запрет, который делает модель непротиворечивой: «Rollback cannot be performed against an application with automated sync enabled».

| Операция | Где предыдущая версия | Что откатывается | Что НЕ откатывается |
|---|---|---|---|
| `kubectl rollout undo` | старые ReplicaSet, по умолчанию 10 | шаблон пода одного Deployment | ConfigMap, Secret, Ingress, всё остальное |
| `helm rollback` | история ревизий релиза Helm | все ресурсы чарта | объекты вне чарта, последствия хуков |
| `git revert` | история Git | всё, что описано в репозитории конфигурации | всё, что вышло за пределы кластера |

Правая колонка — самое ценное в таблице, и в ней есть строка, общая для всех трёх: **база данных не откатывается ни одним из механизмов**. Схема, изменённая миграцией, лежит вне охвата всех трёх историй — отсюда требование совместимости миграции с обеими версиями кода ([`RELEASE_STRATEGIES.md` §7](../../engineering-process/theory/RELEASE_STRATEGIES.md)).

**Отдельная ошибка: откатывать не тем механизмом, которым раскатывали.** Раскатка шла через `helm upgrade`, а откат сделали `kubectl rollout undo` — живой Deployment вернулся к старым подам, но Helm по-прежнему считает текущей записанную им ревизию со сломанным образом. Что случится при следующем `helm upgrade`, зависит от того, как Helm сольёт файл, свою запись и живой объект, — ровно тот случай, который Kubernetes называет undefined behavior для смешанного управления (§7). Надёжен один вывод: две истории разошлись, и приводить их в согласие придётся руками, посреди инцидента.

**Правило.** Откатывайте **тем же инструментом, которым раскатывали**: `helm upgrade` → `helm rollback`, коммит в конфигурацию → `git revert`, `kubectl apply` → применение манифестов предыдущего коммита. И до инцидента ответьте на вопрос, который в инциденте задавать поздно: сколько предыдущих версий у вас вообще сохранено и где.

## 9. Шпаргалка

**Значения по умолчанию, о которых чаще всего узнают на инциденте.**

| Что | По умолчанию | Последствие |
|---|---|---|
| `helm upgrade` без `--wait` | стратегия `hookOnly` | шаг зелёный до готовности подов |
| `--rollback-on-failure` | выключен; включает `--wait=watcher` | без него Helm ничего не откатывает |
| `.spec.progressDeadlineSeconds` | 600 с | после — только условие, откат не делается |
| `.spec.revisionHistoryLimit` | 10 | при `0` откатывать нечем |
| согласование Argo CD | 120 с + джиттер 60 с | коммит ≠ мгновенная раскатка |
| Swarm `update_config.order` | `stop-first` | треть ёмкости минус на трёх репликах |
| Swarm `update_config.failure_action` | `pause` | замирает на полпути, половина реплик новые |
| Swarm `rollback_config.parallelism: 0` | «все сразу» | быстро, но через полный простой |

**Дерево решений.**

- Один объект, один человек → `kubectl apply` + `kubectl rollout status`.
- Набор ресурсов как единый релиз, нужен автоматический откат → `helm upgrade --rollback-on-failure` и готовность к тому, что неудачный прогон станет самым долгим.
- Не хотите отдавать конвейеру ключи от кластера → коммит в конфигурацию, ожидание — `argocd app wait --health`, откат — `git revert`.
- Свои машины, закрытый словарь (сервис, сеть, том, секрет), ровный профиль нагрузки → Swarm.

### Формулировки для собеседования

- «Зелёный шаг раскатки доказывает, что API-сервер принял манифест, и больше ничего: ждать готовности надо отдельной командой, и ждёт она ровно то, что описывает проба готовности.»
- «Kubernetes не откатывает застрявшую раскатку — он выставляет `ProgressDeadlineExceeded` и продолжает пытаться; красным конвейер делает `kubectl rollout status`, а не кластер.»
- «Три разных отката: ReplicaSet помнит поды, Helm помнит релиз, Git помнит всё описанное; базу не помнит никто.»
- «В Swarm обновление и откат настраиваются раздельно, потому что при откате уже известно, что текущая версия сломана: там платят простоем за скорость, здесь скоростью за плавность.»
- «Разница Swarm и Kubernetes не в возможностях, а в том, открыт ли словарь: всё, что нельзя назвать сервисом, на Swarm становится вашим кодом.»
