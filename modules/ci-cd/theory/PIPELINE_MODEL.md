# Конвейер как модель исполнения: что происходит между `git push` и работающим сервисом

> **Какую проблему решает.** Вопрос «расскажите, что происходит после `git push`» проваливают не
> потому, что не знают инструментов, а потому, что держат в голове список слов («сборка, тесты,
> деплой») вместо модели: где рождается артефакт, чем он адресуется, что его двигает вперёд и что
> случится, если один узел упадёт.
> **Кому это надо.** Тому, кто пишет сервис и получает красный конвейер вместо зелёного; тому, кто
> проектирует конвейер и должен решить, что разнести по заданиям, а что оставить вместе.
> **Когда НЕ надо.** Модель конвейера ничего не говорит о том, **что** проверять. Состав гейта,
> ненадёжные тесты и глубина проверок — предмет
> [`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md)
> модуля engineering-process, а не этого файла.

**Границы с соседними файлами.** Здесь — модель: из чего конвейер собран и по каким правилам
исполняется. Кто именно исполняет задания и что переживает границу задания — в
[`RUNNERS_AND_EXECUTION.md`](RUNNERS_AND_EXECUTION.md). Как одна и та же модель записывается на
трёх разных языках — в [`TOOLS_COMPARED.md`](TOOLS_COMPARED.md). Из чего складываются 12 минут
сборки и как их сокращать — в [`PIPELINE_ECONOMICS.md`](PIPELINE_ECONOMICS.md).

**Сквозной пример.** Сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, пик
40 запросов в секунду. Исходники — `src/main/java/by/pavel/payments/`, образ — `Dockerfile`,
чарт и манифесты — `pipelines/`. Базовая сборка идёт 12 минут.

Числа в блоках прогонов сняты на Apple Silicon, macOS 15 (Darwin 25.6.0): Temurin 21.0.9,
Maven 3.9.14, Docker 29.4.3, buildx v0.33.0-desktop.1, Helm v4.2.4. Это не бенчмарк — порядок
величин.

## 1. От `git push` до работающего сервиса — по шагам

**Задача.** Разработчик `payments` выполнил `git push` в `main`. Через двенадцать минут на staging
крутится новая версия. Что произошло за эти двенадцать минут — не «в общих чертах», а так, чтобы
можно было ответить на встречный вопрос: **откуда именно взялся тот файл, который сейчас
работает**.

**Наивный ответ.** «CI собрал, прогнал тесты и задеплоил». Формально верно и бесполезно: из него не
следует ни где живёт артефакт, ни чем он адресуется, ни что случится при отказе. Проверьте себя
одним вопросом: если staging сейчас перезапустить, откуда возьмётся код — из репозитория, из
реестра образов или с диска узла? Ответ «из репозитория» неверен, и именно эта ошибка стоит за
привычкой «пересобрать под каждое окружение».

**Механизм — восемь шагов, у каждого свой вход и выход.**

| Шаг | Вход | Выход | Где это в `payments` |
|---|---|---|---|
| 1. Событие | новое состояние ветки на сервере | запуск конвейера | push в `main` |
| 2. Планирование | запуск | занятый исполнитель | свободная машина из пула |
| 3. Получение кода | коммит | дерево исходников | `git checkout <sha>` в пустой директории |
| 4. Сборка | исходники + зависимости | `target/*.jar` | `mvn -B -ntp package` |
| 5. Проверки | jar + тесты | «красный/зелёный» | surefire (`*Test`), failsafe (`*IT`) |
| 6. Упаковка в образ | jar + базовый образ | слои образа | `Dockerfile`, три этапа |
| 7. Публикация | слои | **дайджест** `sha256:…` | ответ реестра образов на `push` |
| 8. Раскатка | дайджест + конфигурация окружения | работающие поды | `helm upgrade` с `image.digest` |

Терминология шага 1 задана прямо в документации: «An **event** is a specific activity in a
repository that triggers a **workflow** run» (GitHub Actions, «Understanding GitHub Actions»).
Разработчик делает ровно одно действие — порождает событие; всё остальное конвейер делает сам.

Ключевое свойство цепочки: **артефакт рождается один раз, на шаге 4, и дальше только меняет
упаковку.** jar заворачивается в слои образа, образ получает дайджест, дайджест подставляется в
манифест. Пересборки по пути нет ни на одном шаге. Из этого следует правило продвижения одного и
того же артефакта по окружениям — оно разбирается в
[`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md), здесь важно только то, что
модель конвейера это уже предопределяет.

**Почему выход шага 7 — дайджест, а не тег.** Прогон из журнала модуля: тот же тег `v1`
пересобран и опубликован повторно.

```
$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:25a00689dd771dfcbdaaa524ab9739c6ebbcbb5a4c4ac179c4ee030a2e5bb52b

# ... пересборка и push под тем же тегом ...

$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:81fc786d34ef4d8957ce99f13ac108aa8692ead54a4a151e39e7e74b57bab132
```

Тег — изменяемая метка, и подмена содержимого под ней не вызывает никакой ошибки. Дайджест —
функция от содержимого манифеста. Поэтому шаг 8 адресует образ дайджестом; механика реестра
образов — в [`IMAGE_BUILD_AND_REGISTRY.md`](IMAGE_BUILD_AND_REGISTRY.md), устройство слоёв и OCI —
в [`DOCKER.md` §3, §9](../../infrastructure/theory/DOCKER.md) модуля infrastructure.

**Шаг 8 не заканчивается словом «задеплоили».** У `payments` есть эндпоинт, существующий ровно
ради этого шага:

```java
// src/main/java/by/pavel/payments/PaymentsController.java
@GetMapping("/version")
public Map<String, String> version() {
    return Map.of("environment", environment, "digest", buildDigest);
}
```

Оба значения приходят снаружи, из переменных окружения (`PAYMENTS_ENVIRONMENT`,
`PAYMENTS_BUILD_DIGEST`), а не зашиты в образ. Значит, ответ `/version` — это проверяемое
утверждение «на staging работает вот этот дайджест», а не надежда на то, что раскатка прошла.

**Правило.** Рассказывая цепочку, называйте для каждого шага вход и выход, а не действие. Тогда
сразу видны две вещи, из-за которых конвейеры и ломаются: где именно артефакт становится
неизменяемым (шаг 7) и где в него впервые попадает информация об окружении (шаг 8, снаружи, а не
внутри образа).

## 2. Событие, задание, шаг: три уровня и одна граница, которая всё решает

**Задача.** В `pom.xml` сервиса `payments` тесты намеренно разделены на два вида: surefire гоняет
быстрые модульные (`*Test`), failsafe — медленные интеграционные (`*IT`). Разделение сделано ради
конвейера: хочется, чтобы красный модульный тест был виден через сорок секунд, а не через девять
минут. Куда положить эти два прогона — в одно задание двумя шагами или в два задания?

**Наивное решение.** В одно задание: «это же обе проверки, логически одно целое». Формулировка
звучит разумно, потому что подменяет вопрос — вместо «что должно уметь падать и стартовать
независимо» отвечает на «что похоже по смыслу».

**Где ломается.** Внутри одного задания шаги идут строго по очереди на одной машине. Значит:

- параллельности нет — время задания равно сумме шагов, и сорок секунд превращаются в девять минут
  плюс сорок секунд;
- отказ модульных тестов останавливает задание, и вы не узнаете, красные ли интеграционные, —
  следующий прогон покажет их только после починки первых;
- если интеграционным тестам нужна другая среда (например, поднятый PostgreSQL), эта среда
  оказывается навязана и быстрому прогону тоже.

Разнести на два задания — тоже не бесплатно: второе задание не найдёт `target/*.jar`, собранный
первым. Понять, почему, — и значит понять границу.

**Механизм.** Три уровня определены в документации буквально:

> **Event.** «An **event** is a specific activity in a repository that triggers a **workflow** run.»
> **Job.** «A **job** is a set of **steps** in a workflow that is executed on the same **runner**.»
> **Step.** «Each step is either a shell script that will be executed, or an **action** that will be
> run.»
> «Since each step is executed on the same runner, you can share data from one step to another.»
> «By default, jobs have no dependencies and run in parallel.»
>
> — GitHub Actions docs, «Understanding GitHub Actions»

Всё, что важно, следует из одной фразы: **задание целиком исполняется на одном исполнителе.**
Отсюда граница задания одновременно является:

- границей машины — у другого задания другая файловая система, и `target/` первого там просто нет;
- границей параллелизма — параллельно могут идти задания, а не шаги;
- границей изоляции отказа — падение задания не трогает соседнее (см. §4);
- границей выбора окружения — операционная система и образ выбираются на задание, не на шаг.

**Обещание надо читать точно.** Документация обещает, что шаги делят **данные** («share data»), —
и это про файловую систему. Обещания «шаги выполняются в одном процессе» там нет, и оно неверно:
`export FOO=bar` в одном шаге не виден в следующем, потому что следующий шаг — новый запуск
оболочки. Именно поэтому у каждого инструмента есть отдельный механизм передачи значений между
шагами (запись в файл окружения задания); синтаксис — в
[`TOOLS_COMPARED.md`](TOOLS_COMPARED.md). Общий диск между шагами есть, общей памяти нет.

**Критерий выбора, а не список.**

| Что вам нужно | На какой границе это решается |
|---|---|
| Две проверки идут одновременно | разные задания |
| Одна проверка падает, вторая всё равно отчитывается | разные задания |
| Второй команде нужен `target/` первой без явной передачи | одно задание, два шага |
| Разные ОС, версии JDK или образы | разные задания |
| Отдельная сворачиваемая секция в логе | шаг |
| Значение из первой команды нужно во второй | шаги + файл окружения, не `export` |

**Правило.** Дробление на задания покупает параллельность и изоляцию, а платит явной передачей
состояния — артефактами (см. [`RUNNERS_AND_EXECUTION.md` §5](RUNNERS_AND_EXECUTION.md)).
Объединение в одно задание покупает бесплатный общий диск, а платит сериализацией. Решая, где
провести границу, спрашивайте не «это одно и то же по смыслу», а «должно ли это падать и
стартовать независимо».

## 3. Конвейер — граф зависимостей, а не список этапов

**Задача.** У `payments` шесть заданий: сборка, модульные тесты, статический анализ, интеграционные
тесты, сборка образа, публикация и раскатка на dev. Надо получить «красный/зелёный» и рабочий dev
как можно раньше.

**Наивное решение.** Выстроить их в линию: сборка → анализ → модульные → интеграционные → образ →
раскатка. Так рисуют на доске, так проще объяснить, и большинство конвейеров именно так и
начинаются.

**Где ломается — арифметика.** Возьмём разложение 12 минут по заданиям как **допущение**, чтобы
показать счёт (настоящий разбор, куда уходят эти минуты, — в
[`PIPELINE_ECONOMICS.md` §1](PIPELINE_ECONOMICS.md)):

```
сборка          3 мин      интеграционные тесты   6 мин
модульные       1 мин      сборка образа          2 мин
статический     2 мин      публикация + раскатка  1 мин
анализ
```

- **Линейно:** 3 + 1 + 2 + 6 + 2 + 1 = **15 минут**. Каждое задание ждёт предыдущее, хотя
  статический анализ не нуждается ни в чьём результате, кроме исходников.
- **По зависимостям данных.** После сборки три ветки независимы: модульные (1), анализ (2),
  интеграционные (6) — и сборка образа (2), которой нужен только jar. Публикация ждёт всех.
  Критический путь: 3 + 6 + 1 = **10 минут**.
- **Как это чаще всего устроено на самом деле:** образ ставят *после* тестов — «зачем собирать
  образ, если тесты красные». Критический путь становится 3 + 6 + 2 + 1 = **12 минут**. Те самые
  двенадцать.

Обратите внимание на природу лишних двух минут. Ребро «образ после тестов» — не зависимость по
данным (образу нужен jar, а не результат тестов), а **зависимость по политике**. Она стоит две
минуты на каждом прогоне, включая все зелёные. Осознанный это размен или случайно нарисованная
стрелка — вопрос, который стоит задать своему конвейеру.

**Механизм.** Ни один из ходовых инструментов не исполняет список — все исполняют направленный
ациклический граф, различаются только значения по умолчанию.

> «By default, jobs have no dependencies and run in parallel.»
> «Use `jobs.<job_id>.needs` to identify any jobs that must complete successfully before this job
> will run.»
>
> — GitHub Actions docs, «Understanding GitHub Actions» и «Workflow syntax»

> «The staged structure, where all steps in a stage must complete before the first job in the next
> stage begins, causes waits that slow things down.»
> «When GitLab knows the dependencies between your jobs, jobs can run as fast as possible, even
> starting earlier than other jobs in the same stage.»
>
> — GitLab docs, «Pipeline architectures»

Значения по умолчанию противоположны: в Actions задания параллельны, пока вы не объявили ребро;
в GitLab по умолчанию действует барьер этапа, и `needs` его снимает. Модель при этом одна.
Сравнение того, как каждый инструмент это записывает, — в [`TOOLS_COMPARED.md`](TOOLS_COMPARED.md).

**Этап — не третий уровень модели, а сахар.** Этап выражается через рёбра: «каждое задание этапа N
зависит от всех заданий этапа N−1». Обратное неверно — граф через этапы точно не выражается. В
нашем примере это видно прямо: чтобы образ собирался параллельно тестам, но публикация ждала обоих,
нужны рёбра, а не полосы. Поэтому GitLab и добавил `needs` поверх этапов, а Actions обошёлся без
этапов вовсе.

**Что из этого нельзя вывести.** Граф даёт параллельность только при наличии свободных
исполнителей. Три ветки, стартующие одновременно, требуют трёх машин; если исполнитель один,
критический путь снова превращается в сумму. Очередь и ограничение конкурентности разобраны в
[`RUNNERS_AND_EXECUTION.md` §7](RUNNERS_AND_EXECUTION.md).

**Правило.** Длительность конвейера — не сумма заданий, а длина самого длинного пути по графу.
Отсюда два следствия, которые экономят больше всего времени: ускорять имеет смысл только задания на
критическом пути (минута, отыгранная у статического анализа в нашем примере, не даёт ничего), а
перед тем как ускорять — посмотреть, нет ли на этом пути рёбер, которых по данным быть не должно.

## 4. Один узел упал: что происходит с остальными

**Задача.** Тот же граф из §3. На седьмой минуте падают интеграционные тесты. Статический анализ в
этот момент ещё идёт, сборка образа — тоже. Что произойдёт с ними и с публикацией?

**Наивные ответы — оба неверны.** Первый: «конвейер остановится». Второй: «конвейер доедет до
конца, просто отметит задание красным». Первое неверно, потому что уже стартовавшие соседи никто не
трогает; второе — потому что потомки упавшего узла не выполнятся.

**Механизм.** Отказ распространяется **по рёбрам графа, а не по времени**.

> «If a job fails, all jobs that need that job are skipped unless the job uses a conditional
> statement that causes the job to continue.»
>
> — GitHub Actions docs, `jobs.<job_id>.needs`

Ключевое слово — **skipped**, а не failed. Пропущенное задание не выполнялось вовсе: у него нет
логов, нет длительности и нет причины отказа. Отсюда самая частая ошибка при разборе красного
конвейера: человек открывает последний красный узел и ищет там причину, а искать надо в корне
поддерева — единственном узле, который действительно упал; всё остальное красное ниже него просто
не запускалось.

Для нашего графа это значит:

| Задание | Что с ним будет | Почему |
|---|---|---|
| Статический анализ (идёт) | доработает до конца | ребра к упавшему узлу нет |
| Сборка образа (идёт) | доработает до конца | зависит от сборки, не от тестов |
| Публикация | пропущена | зависит от тестов по ребру |
| Раскатка на dev | пропущена | зависит от публикации |

Соседние ветки доработают и потратят свои минуты. Если такая ветка дорогая — например, сборка
образа под вторую архитектуру, — ребро политики «образ после тестов» из §3 внезапно окупается: две
минуты на каждом зелёном прогоне против впустую потраченных минут на каждом красном.

**Поведение настраивается, и это выбор, а не мелочь.** Двумя противоположными способами:

> «Use `allow_failure` to determine whether a pipeline should continue running when a job fails.»
> — GitLab CI/CD YAML reference

Это ослабление: узел красный, но конвейер продолжается и потомки выполняются. Осмысленно ровно
тогда, когда проверка **информирует**, а не запирает: свежезаведённый линтер, который вы ещё не
успели починить везде, отчёт о лицензиях, замер размера образа.

> «When set to `true`, GitHub cancels all in-progress jobs if any matrix job fails. Default: `true`»
> — GitHub Actions docs, `jobs.<job_id>.strategy.fail-fast`

А это ужесточение, причём включённое по умолчанию: одна упавшая ячейка матрицы отменяет соседние.
Обратите внимание, чем вы платите. Матрица «Java 17 / Java 21» заводится ровно затем, чтобы
узнать, ломается ли код на одной версии или на обеих. Значение по умолчанию гарантирует, что
на этот вопрос вы не ответите: соседняя ячейка будет отменена, и следующий прогон вы потратите на
то, чтобы узнать то, что можно было узнать в этом.

**Когда это неправильный ответ.** Ослаблять запирающие проверки, чтобы «конвейер не мешал», —
самый быстрый способ превратить гейт в информационную панель, которую никто не читает. Ненадёжный
тест, падающий раз в пять прогонов, тоже не лечится ослаблением. Что обязано запирать слияние и
что делать с ненадёжными тестами — в
[`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

**Правило.** Каждому ребру задайте вопрос «это зависимость по данным или по политике», каждому
узлу — «его отказ обязан запирать или информировать». Оба ответа должны быть записаны явно:
значения по умолчанию у инструментов разные и местами противоположные, и полагаться на них — значит
получить поведение, которого вы не выбирали.

## 5. Эфемерность исполнителя и всё, что из неё следует

**Задача.** Сборка `payments` в пустом локальном репозитории Maven против сборки в уже заполненном.
Замер из журнала модуля (репозиторий вынесен в отдельную директорию, `clean` в обоих случаях —
иначе второй прогон переиспользовал бы `target/`):

```bash
mvn -B -ntp -Dmaven.repo.local=/tmp/m2-cold clean package -DskipTests
```

```
холодный репозиторий (пусто)   25,97 с      скачано 68 МБ
тёплый (тот же репозиторий)     1,53 с
тёплый, повтор                  1,59 с
```

Отношение ≈ 17×. Оговорка обязательна: у `payments` всего два стартера Spring Boot; на сервисе с
40–60 зависимостями холодный прогон измеряется минутами. Отношение сохраняется, абсолютные числа —
нет.

**Наивное решение.** «Пусть репозиторий остаётся на машине — один раз скачали, дальше быстро». Так
и работает свой сервер сборки, и именно эту картинку человек приносит с собой в CI.

**Где ломается.** Машины «своей» нет:

> «With the exception of single-CPU runners, each GitHub-hosted runner is a new virtual machine (VM)
> hosted by GitHub.» … «When the job has finished, the container is automatically decommissioned.»
>
> — GitHub Actions docs, «GitHub-hosted runners»

Свежая машина выдаётся под задание и уходит вместе с ним. Значит, **26 секунд — это не разовая
плата, а плата на каждом прогоне**, если ничего не предпринять.

**Механизм и его следствия.** Эфемерность — не свойство какого-то ключа конфигурации, а базовое
допущение модели, из которого выводится почти вся остальная механика:

1. **Ничто не переживает границу задания само по себе** — ни `~/.m2`, ни `target/`, ни пакет,
   поставленный из репозитория дистрибутива, ни переменная оболочки.
2. Поэтому **кэш и артефакт — явные механизмы**, а не «файл, оставшийся с прошлого раза». Кэш
   адресуется ключом, артефакт передаётся между заданиями по имени; механика обоих — в
   [`RUNNERS_AND_EXECUTION.md` §4 и §5](RUNNERS_AND_EXECUTION.md).
3. **Слои образа — тот же случай.** Прогон из журнала модуля: локальный кэш сборщика стёрт целиком
   (`docker buildx prune -af`, освобождено 1,438 ГБ) — это эмуляция нового исполнителя, который
   видит машину впервые.

   | Сборка образа `payments` | Реальное время | Шагов из кэша |
   |---|---|---|
   | `--cache-from type=registry` после полной очистки | **3,74 с** | **13** |
   | без кэша вовсе | **95,66 с** | 0 |

   Эфемерность лечится не «сохраните машину», а «сделайте состояние адресуемым снаружи»: кэш,
   лежащий в реестре образов, доступен машине, которая ничего о прошлых сборках не знает.
4. **Обратная сторона — это гарантия, а не только неудобство.** Зелёная сборка на свежей машине
   доказывает, что она не зависит от того, что кто-то поставил руками полгода назад. Долгоживущий
   собственный исполнитель эту гарантию теряет — см.
   [`RUNNERS_AND_EXECUTION.md` §1 и §3](RUNNERS_AND_EXECUTION.md).

**Чего эфемерность не делает.** Она не делает сборку воспроизводимой. Свежая машина гарантирует
отсутствие следов прошлого прогона — и ничего не говорит о том, что два прогона одного коммита
дадут одинаковые байты. Прогон из журнала, две сборки подряд одного и того же дерева исходников:

```
без project.build.outputTimestamp     сборка 1: 1935ad70b5bbad69b941ef55a505a8ea…
                                      сборка 2: 546701dcc3c1cad09f49e0833a21cb86…   → РАЗНЫЕ
с project.build.outputTimestamp       сборка 1: 9fc5925cf3e7c4b0f44b68fc3bc568a5…
                                      сборка 2: 9fc5925cf3e7c4b0f44b68fc3bc568a5…   → ОДИНАКОВЫ
```

В записи архива попадает время сборки, и без явно зафиксированного времени jar перестаёт быть
функцией только от входа. Свойство `<project.build.outputTimestamp>` есть в `pom.xml` модуля; зачем
оно нужно и что ещё ломает воспроизводимость — в
[`JAVA_BUILD_IN_CI.md`](JAVA_BUILD_IN_CI.md).

**Правило.** Любое состояние, которое должно пережить границу задания, назовите явно и дайте ему
имя — ключ кэша или имя артефакта. Формулировка «оно же там лежит» механизмом не является. Верный
признак нарушенного правила: сборка проходит только со второго раза или только на «прогретой»
машине. Это не сборка, это привычка конкретной машины.

## 6. CI, continuous delivery, continuous deployment — три разных обещания

**Задача.** Вопрос на собеседовании: «У вас continuous deployment?» За ним стоит проверка, а не
любопытство: понимаете ли вы, что аббревиатура CD скрывает два разных термина, а связка «CI/CD» —
три разные практики, и умеете ли назвать, где именно в вашем процессе стоит человек.

**Наивный ответ.** «Да, у нас настроен CI/CD, всё автоматизировано». Он не переживает встречного
вопроса: «то есть коммит в `main` через двенадцать минут оказывается в проде без участия человека?»
Если после этого приходится сказать «ну, там есть кнопка», значит, вы описали не то, что назвали.

**Механизм — три обещания, у каждого свой проверочный вопрос.**

| Практика | Обещание | Вопрос, которым это проверяется | В `payments` |
|---|---|---|---|
| Continuous integration | изменения попадают в общую ветку часто, и каждое автоматически собирается и проверяется | «сколько живёт ветка до слияния и что запускается при слиянии?» | push в `main` запускает весь конвейер |
| Continuous delivery | любой прошедший проверки коммит **может быть** выпущен нажатием кнопки | «сколько ручных шагов между зелёной сборкой и продом и какие именно?» | до staging — ноль шагов |
| Continuous deployment | каждый прошедший проверки коммит **выпускается** | «когда человек последний раз нажимал кнопку выпуска?» | нет: в прод — решение человека |

Различие delivery и deployment сформулировано автором термина:

> «Continuous deployment is the practice of releasing every good build to users.»
> «Continuous delivery is about putting the release schedule in the hands of the business, not in
> the hands of IT.» … «any build could *potentially* be released to users at the touch of a button
> using a fully automated process.»
>
> — Jez Humble, «Continuous Delivery vs Continuous Deployment», continuousdelivery.com, 2010

Отсюда то, что чаще всего понимают наоборот: **continuous delivery — про способность, а не про
частоту.** Команда, выпускающая релиз раз в квартал, потому что так решил бизнес, практикует
continuous delivery, если выпуск занимает одно нажатие. Команда, выпускающая каждый день, но
руками и по чек-листу из тридцати пунктов, — не практикует, сколько бы раз в день она это ни
делала.

**Второе, что путают: CI — не про инструмент.** «У нас есть Jenkins» не означает continuous
integration. Практика — в том, что изменения вливаются в общую ветку часто, короткими порциями;
конвейер лишь делает это проверяемым. Долгоживущая ветка с двухнедельным слиянием остаётся
долгоживущей веткой, даже если на каждый её коммит запускается сборка. Тема ветвления и частоты
интеграции принадлежит
[`BRANCHING_AND_CODE_FLOW.md`](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

**Третье: continuous deployment не означает, что пользователь сразу видит изменение.** Код может
приехать в прод выключенным, а включиться позже и отдельным решением. Это разделение — предмет
[`RELEASE_STRATEGIES.md` §4](../../engineering-process/theory/RELEASE_STRATEGIES.md); там же выбор
схемы раскатки (§8) и решение «откат или накат исправления» (§6). Здесь важно только одно: если
раскатка и выпуск функциональности разделены, вопрос «у вас continuous deployment» перестаёт быть
страшным — автоматически едет код, а не изменение поведения для пользователя.

**Когда continuous deployment — неправильный ответ.** Он требует, чтобы обнаружение отказа было
автоматическим и укладывалось в промежуток до следующей раскатки. Если о поломке узнают из
обращения в поддержку через час, автоматическая раскатка — это автоматизация распространения
дефекта: за час туда уедет ещё несколько изменений, и первопричину придётся искать среди них.
Второе ограничение — внешнее: там, где требуется зафиксированное одобрение выпуска, ручной шаг
существует не из-за незрелости процесса, а по требованию. Чем измеряется скорость и надёжность
доставки — [`DELIVERY_METRICS.md`](../../engineering-process/theory/DELIVERY_METRICS.md).

**Правило.** Отвечая на вопрос, называйте не практику, а расположение человека в цепочке:
«до staging — полностью автоматически, в прод — одно нажатие релиз-менеджера, потому что <причина>»
сообщает о вашем процессе больше, чем «у нас CI/CD», и снимает половину встречных вопросов.

## 7. Чем платит конвейер: длина цикла обратной связи

**Задача.** Конвейер `payments` идёт двенадцать минут. Вопрос: это много или нормально — и как
такой ответ вообще обосновывают?

**Наивный ответ.** «Двенадцать минут — ерунда, я пока займусь другим». Он неверен не потому, что
двенадцать минут долго, а потому, что считает не то: измеряется ожидание, а платится за другое.

**Где ломается — три счёта по явно названным допущениям.**

*Счёт первый, машинный.* Команда из шести человек, четыре push в день на человека (нормальная
частота при короткоживущих ветках): 6 × 4 = 24 прогона в день × 12 мин = **288 минут машинного
времени в сутки**. Это уже деньги; из чего они складываются и что с этим делать — в
[`PIPELINE_ECONOMICS.md` §1](PIPELINE_ECONOMICS.md).

*Счёт второй, человеческий.* Двенадцать минут — не средняя, а **нижняя граница** цикла. Сверху
ложится ожидание свободного исполнителя (см.
[`RUNNERS_AND_EXECUTION.md` §7](RUNNERS_AND_EXECUTION.md)) и повторные прогоны. Допустим,
ненадёжный тест роняет прогон в одном случае из пяти, а падения независимы: ожидаемое число
прогонов до зелёного равно 1 / 0,8 = 1,25, то есть **ожидаемое время до зелёного — 15 минут**,
а не 12. Один ненадёжный тест стоит четверти длительности конвейера; что с ним делать — в
[`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

*Счёт третий, тот, ради которого раздел написан.* Длина цикла определяет **размер порции
изменений**. Когда проверка стоит двенадцать минут, человек перестаёт отправлять по одному
изменению и начинает копить — «отправлю всё разом, чтобы один прогон». Порции растут, ревью
становится тяжелее, отказ дороже, а причину красного приходится искать уже среди нескольких
изменений сразу. Это положительная обратная связь: длинный конвейер делает изменения крупнее, а
крупные изменения делают каждый отказ дороже. Связь размера пулл-реквеста с потоком разобрана в
[`BRANCHING_AND_CODE_FLOW.md` §6](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

**Механизм.** Время до сигнала об ошибке — это не длительность конвейера, а **длина пути по графу
от корня до того задания, которое эту ошибку ловит** (§3). Ошибка, которую ловят модульные тесты,
обнаруживается: в графе — через 3 + 1 = **4 минуты**; в линейном списке, где перед ними стоит
статический анализ, — через 3 + 2 + 1 = **6 минут**; а если модульные тесты по недосмотру
поставлены после интеграционных и сборки образа — через 3 + 6 + 2 + 1 = **12 минут**, то есть
в самом конце. Код один и тот же, ошибка одна и та же, разница только в положении узла в графе.

Отсюда содержание принципа **fail fast**: он не про «падать почаще», а про порядок — дешёвая и
часто срабатывающая проверка ставится ближе к корню графа, дорогая и редко срабатывающая — дальше.
Компиляция ловит больше ошибок, чем сканер лицензий, и стоит меньше; значит, её место первое, а не
«где-то в проверках».

**Что отсюда не следует.** Не следует, что надо сокращать конвейер целиком. Конвейер, который
отвечает «красный» за девяносто секунд и полностью завершается за двадцать минут, лучше
двенадцатиминутного монолита, отвечающего только в конце: разработчик получает сигнал за полторы
минуты, а остальное происходит без него. Длительность конвейера и длина цикла обратной связи — две
разные величины, и оптимизируют вторую.

**Правило.** Измеряйте не «сколько идёт конвейер», а сколько проходит от `git push` до первого
достоверного «красный/зелёный». Эта величина входит слагаемым в lead time for changes — метрику,
разобранную в
[`DELIVERY_METRICS.md`](../../engineering-process/theory/DELIVERY_METRICS.md), — и именно она, а не
общая длительность, определяет, насколько крупными кусками команда работает.

## Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Где рождается артефакт | на шаге сборки, один раз; дальше меняется только упаковка |
| Чем адресуется образ | дайджестом `sha256:…`; тег — изменяемая метка и гарантией не является |
| Что даёт граница задания | другую машину, другой диск, параллельность, изоляцию отказа |
| Что переживает границу задания | только названное явно: артефакт (обязателен) и кэш (необязателен) |
| Чему равна длительность конвейера | длине самого длинного пути по графу, не сумме заданий |
| Что будет с потомками упавшего узла | пропущены (skipped) — они не выполнялись, причину искать не в них |
| Что будет с соседями | доработают до конца, если уже стартовали |
| Куда ставить дешёвые проверки | ближе к корню графа — это и есть fail fast |
| Что измерять | время от `git push` до первого достоверного «красный/зелёный» |
| Как отличить delivery от deployment | посчитать ручные шаги между зелёной сборкой и продом |

### Формулировки для собеседования

- «Артефакт собирается один раз и дальше только продвигается: пересборка под окружение — это потеря
  гарантии, а не оптимизация.»
- «Граница задания — это граница машины; всё, что должно её пережить, обязано иметь имя.»
- «Отказ распространяется по рёбрам графа, а не по времени: потомки пропускаются, соседи
  доработывают.»
- «Длительность конвейера — длина критического пути, поэтому сначала смотрят на рёбра, а потом на
  скорость заданий.»
- «Continuous delivery — про способность выпустить в любой момент; continuous deployment — про то,
  что выпускается каждый прошедший проверки коммит.»
