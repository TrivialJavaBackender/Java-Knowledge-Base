# Конвейер как модель исполнения: что происходит между `git push` и работающим сервисом

> **Какую проблему решает.** «Расскажите, что происходит после `git push`» проваливают не из-за незнания инструментов, а из-за отсутствия модели: где рождается артефакт, чем он адресуется и что будет, если один узел упадёт.
> **Кому это надо.** Тому, кто получает красный конвейер вместо зелёного, и тому, кто решает, что разнести по заданиям, а что оставить вместе.
> **Когда НЕ надо.** Модель ничего не говорит о том, **что** проверять: состав гейта и ненадёжные тесты — предмет [`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

**Границы.** Что конвейер обещает и чем платит — [`PIPELINE_GUARANTEES.md`](PIPELINE_GUARANTEES.md). Кто исполняет задания — [`RUNNERS.md` §1](RUNNERS.md); что переживает границу задания — [`PIPELINE_CACHE_AND_CONCURRENCY.md` §1, §2](PIPELINE_CACHE_AND_CONCURRENCY.md). Та же модель на трёх языках — [`TOOLS_COMPARED.md` §1](TOOLS_COMPARED.md).

Сквозной пример модуля — сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, базовая сборка 12 минут. Замеры сняты на Apple Silicon, macOS 15 (Temurin 21.0.9, Maven 3.9.14, Docker 29.4.3) — порядок величин, не бенчмарк.

---

## 1. От `git push` до работающего сервиса — по шагам

«CI собрал, прогнал тесты и задеплоил» — ответ формально верный и бесполезный. Проверьте себя: если staging сейчас перезапустить, откуда возьмётся код — из репозитория, из реестра образов или с диска узла? «Из репозитория» неверно, и за этой ошибкой стоит привычка пересобирать под каждое окружение.

| Шаг | Вход | Выход | Где это в `payments` |
|---|---|---|---|
| 1. Событие | новое состояние ветки на сервере | запуск конвейера | push в `main` |
| 2. Планирование | запуск | занятый исполнитель | свободная машина из пула |
| 3. Получение кода | коммит | дерево исходников | `git checkout <sha>` в пустой папке |
| 4. Сборка | исходники + зависимости | `target/*.jar` | `mvn -B -ntp package` |
| 5. Проверки | jar + тесты | «красный/зелёный» | surefire (`*Test`), failsafe (`*IT`) |
| 6. Упаковка в образ | jar + базовый образ | слои образа | многоэтапный `Dockerfile` |
| 7. Публикация | слои | **дайджест** `sha256:…` | ответ реестра образов на `push` |
| 8. Раскатка | дайджест + конфигурация окружения | работающие поды | `helm upgrade` с `image.digest` |

**Артефакт рождается один раз, на шаге 4, и дальше только меняет упаковку:** jar заворачивается в слои, образ получает дайджест, дайджест подставляется в манифест. Пересборки нет ни на одном шаге — отсюда правило продвижения одного артефакта по окружениям ([`ENVIRONMENTS_AND_PROMOTION.md` §1](ENVIRONMENTS_AND_PROMOTION.md)).

Выход шага 7 — дайджест, а не тег. Тот же тег `v1`, пересобранный и опубликованный повторно:

```
$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:25a00689dd771dfcbdaaa524ab9739c6ebbcbb5a4c4ac179c4ee030a2e5bb52b
# ... пересборка и push под тем же тегом ...
Digest:    sha256:81fc786d34ef4d8957ce99f13ac108aa8692ead54a4a151e39e7e74b57bab132
```

Подмена содержимого под тегом не вызвала ошибки: тег — изменяемая метка, дайджест — функция от манифеста ([`IMAGE_REGISTRY_AND_TAGS.md` §1](IMAGE_REGISTRY_AND_TAGS.md)).

Шаг 8 не заканчивается словом «задеплоили». У `payments` эндпоинт `/version` отдаёт пару `environment` + `digest`, и оба значения приходят из переменных окружения, а не зашиты в образ. Поэтому его ответ — проверяемое утверждение «на staging работает вот этот дайджест», а не надежда, что раскатка прошла.

**Правило.** Называйте для каждого шага вход и выход, а не действие: тогда видно, где артефакт становится неизменяемым (шаг 7) и где в него впервые попадает информация об окружении (шаг 8, снаружи, а не внутри образа).

## 2. Событие, задание, шаг: три уровня и одна граница, которая всё решает

В `payments` surefire гоняет быстрые модульные тесты (`*Test`), failsafe — медленные интеграционные (`*IT`). Наивное решение — положить оба прогона в одно задание двумя шагами, «это же обе проверки». Но шаги задания идут по очереди на одной машине: сорок секунд до красного модульного теста превращаются в девять минут плюс сорок, отказ первого прогона скрывает результат второго, а поднятый PostgreSQL навязан и быстрому. Разнести на два задания тоже не бесплатно: второе не найдёт `target/*.jar`, собранный первым.

> **Event.** «An **event** is a specific activity in a repository that triggers a **workflow** run.»
> **Job.** «A **job** is a set of **steps** in a workflow that is executed on the same **runner**.»
> «Since each step is executed on the same runner, you can share data from one step to another.»
> «By default, jobs have no dependencies and run in parallel.»

Всё следует из одной фразы: **задание целиком исполняется на одном исполнителе.** Поэтому граница задания — одновременно граница машины (у соседа другая файловая система, и `target/` первого там нет), граница параллелизма (параллельны задания, а не шаги), граница изоляции отказа (§4) и граница выбора окружения (ОС и образ задаются на задание).

Обещание читают точно: шаги делят **данные** («share data»), то есть файловую систему. Обещания «шаги выполняются в одном процессе» там нет, и оно неверно — `export FOO=bar` в следующем шаге не виден, потому что это новый запуск оболочки. Общий диск есть, общей памяти нет: значения передают через файл окружения задания ([`TOOLS_COMPARED.md` §1](TOOLS_COMPARED.md)).

| Что вам нужно | На какой границе это решается |
|---|---|
| Две проверки идут одновременно | разные задания |
| Одна проверка падает, вторая всё равно отчитывается | разные задания |
| Второй команде нужен `target/` первой без явной передачи | одно задание, два шага |
| Разные ОС, версии JDK или образы | разные задания |
| Значение из первой команды нужно во второй | шаги + файл окружения, не `export` |

**Правило.** Дробление на задания покупает параллельность и изоляцию, а платит явной передачей состояния — артефактами ([`PIPELINE_CACHE_AND_CONCURRENCY.md` §2](PIPELINE_CACHE_AND_CONCURRENCY.md)); объединение покупает общий диск даром, а платит сериализацией.

## 3. Конвейер — граф зависимостей, а не список этапов

У `payments` шесть заданий, и наивное решение — выстроить их в линию. Считаем на разложении 12 минут, взятом как **допущение** (настоящий разбор — [`PIPELINE_DURATION.md` §1](PIPELINE_DURATION.md)): сборка 3 мин, модульные тесты 1, статический анализ 2, интеграционные тесты 6, сборка образа 2, публикация с раскаткой 1.

- **Линейно:** 3 + 1 + 2 + 6 + 2 + 1 = **15 минут**, хотя статическому анализу не нужен ничей результат, кроме исходников.
- **По зависимостям данных.** После сборки независимы четыре ветки: модульные (1), анализ (2), интеграционные (6) и сборка образа (2), которой нужен только jar; публикация ждёт всех. Критический путь 3 + 6 + 1 = **10 минут**.
- **Как это чаще всего устроено:** образ ставят *после* тестов — «зачем собирать его, если тесты красные». Путь 3 + 6 + 2 + 1 = **12 минут**. Те самые двенадцать.

Природа лишних двух минут важнее цифры: ребро «образ после тестов» — не зависимость по данным (образу нужен jar, а не результат тестов), а **зависимость по политике**, и стоит она две минуты на каждом прогоне, включая зелёные. При этом ни один ходовой инструмент не исполняет список — все исполняют направленный ациклический граф и различаются лишь умолчаниями.

> «Use `jobs.<job_id>.needs` to identify any jobs that must complete successfully before this job will run.»

> «The staged structure, where all steps in a stage must complete before the first job in the next stage begins, causes waits that slow things down.»

Умолчания противоположны: в Actions задания параллельны, пока вы не объявили ребро; в GitLab действует барьер этапа, и `needs` его снимает. Модель при этом одна, а **этап — не третий уровень модели, а сахар:** он выражается через рёбра («задание этапа N зависит от всех заданий этапа N−1»), обратное же неверно — чтобы образ собирался параллельно тестам, но публикация ждала обоих, нужны рёбра, а не полосы.

**Правило.** Ускоряют только задания критического пути, а перед этим проверяют, нет ли на нём рёбер, которых по данным быть не должно. И параллельность граф даёт лишь при свободных исполнителях: на одном критический путь снова становится суммой ([`PIPELINE_CACHE_AND_CONCURRENCY.md` §4](PIPELINE_CACHE_AND_CONCURRENCY.md)).

## 4. Один узел упал: что происходит с остальными

Тот же граф. На седьмой минуте падают интеграционные тесты; статический анализ и сборка образа ещё идут. Оба ходовых ответа неверны: «конвейер остановится» — стартовавших соседей никто не трогает; «доедет до конца, отметив задание красным» — потомки упавшего узла не выполнятся. Отказ распространяется **по рёбрам графа, а не по времени**.

> «If a job fails, all jobs that need that job are skipped unless the job uses a conditional statement that causes the job to continue.»

Ключевое слово — **skipped**, а не failed: пропущенное задание не выполнялось вовсе, у него нет ни логов, ни причины отказа. Отсюда частая ошибка при разборе — открыть последний красный узел, тогда как искать надо в корне поддерева, единственном узле, который действительно упал.

| Задание | Что с ним будет | Почему |
|---|---|---|
| Статический анализ (идёт) | доработает до конца | ребра к упавшему узлу нет |
| Сборка образа (идёт) | доработает до конца | зависит от сборки, не от тестов |
| Публикация | пропущена | зависит от тестов по ребру |
| Раскатка на dev | пропущена | зависит от публикации |

Соседние ветки доработают и потратят свои минуты, поэтому дорогая ветка (сборка образа под вторую архитектуру) оправдывает ребро политики из §3: две минуты на каждом зелёном прогоне против впустую потраченных на каждом красном.

> «Use `allow_failure` to determine whether a pipeline should continue running when a job fails.»
> «When set to `true`, GitHub cancels all in-progress jobs if any matrix job fails. Default: `true`»

Первое — ослабление: узел красный, конвейер продолжается, потомки выполняются; осмысленно ровно тогда, когда проверка **информирует**, а не запирает (свежий линтер, отчёт о лицензиях). Второе — ужесточение по умолчанию: упавшая ячейка матрицы отменяет соседние, и матрица «Java 17 / Java 21», заведённая ради ответа «на одной версии или на обеих», этого ответа не даёт.

**Когда это неправильный ответ.** Ослабить запирающую проверку, чтобы «конвейер не мешал», — быстрый способ превратить гейт в панель, которую никто не читает; ненадёжный тест этим тоже не лечится ([`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md)).

**Правило.** Каждому ребру задайте вопрос «зависимость по данным или по политике», каждому узлу — «отказ обязан запирать или информировать», и записывайте ответ явно: умолчания у инструментов местами противоположные.

## 5. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Где рождается артефакт | на шаге сборки, один раз; дальше меняется только упаковка |
| Чем адресуется образ | дайджестом `sha256:…`; тег — изменяемая метка и гарантией не является |
| Что даёт граница задания | другую машину, другой диск, параллельность, изоляцию отказа |
| Чему равна длительность конвейера | длине самого длинного пути по графу, не сумме заданий |
| Откуда лишние минуты на критическом пути | из рёбер политики: ребро есть, зависимости по данным нет |
| Что такое этап | сахар над рёбрами: этапы через граф выражаются, граф через этапы — нет |
| Что будет с потомками упавшего узла | пропущены (skipped): не выполнялись, причину искать не в них |

**Дерево решения:** нужна параллельность или изоляция отказа → разные задания; нужен общий диск даром → одно задание, два шага; надо ускорить → сначала рёбра, потом узлы.

### Формулировки для собеседования

- «Артефакт собирается один раз и дальше только продвигается: пересборка под окружение — потеря гарантии, а не оптимизация.»
- «Граница задания — это граница машины; всё, что должно её пережить, обязано иметь имя.»
- «Отказ распространяется по рёбрам графа, а не по времени: потомки пропускаются, соседи доработывают.»
- «Длительность конвейера — длина критического пути, поэтому сначала смотрят на рёбра, потом на скорость заданий.»
