# Сборка Java в конвейере: от `mvn -B` до воспроизводимого артефакта

> **Какую проблему решает.** Сборка не описана как функция от входа: зависимости качаются заново,
> jar из одного коммита состоит из разных байтов, версия `1.0-SNAPSHOT` не говорит, что внутри.
> **Кому это надо.** Тому, кто настраивает конвейер Java-сервиса и должен объяснить в нём каждый флаг `mvn`.
> **Когда НЕ надо.** Пока конвейер идёт списком там, где мог бы идти графом, экономия секунд на Maven ничего не меняет.

- Кэш вообще (ключ, промах, отравление) — [`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md); граф заданий — [`PIPELINE_MODEL.md` §3](PIPELINE_MODEL.md).
- Образ и адресация дайджестом — [`IMAGE_BUILD_AND_REGISTRY.md` §5](IMAGE_BUILD_AND_REGISTRY.md); продвижение артефакта — [`ENVIRONMENTS_AND_PROMOTION.md` §1](ENVIRONMENTS_AND_PROMOTION.md).
- Состав гейта перед слиянием — [`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md); что вообще тестировать — [`TESTING.md`](../../software-engineering/theory/TESTING.md).

## 1. `-B -ntp` и почему интерактивные флаги ломают лог конвейера

За обоими флагами стоит один принцип: **у задания в конвейере нет человека** — ни терминала, ни
клавиатуры, ни глаз, следящих за прогрессом. Maven по умолчанию считает, что человек есть.

> `-B,--batch-mode` — «Run in non-interactive (batch) mode (disables output color)»
> `-ntp,--no-transfer-progress` — «Do not display transfer progress when downloading or uploading»
> — Maven docs, «Maven CLI Options Reference»

В первой формулировке обе половины. *Non-interactive*: плагин, задающий вопрос (архетипы, релизные
плагины), получает пустой стандартный ввод и либо ждёт, пока задание не прибьют по таймауту, либо
падает через десять минут вместо секунды; задание не «зависло» — оно честно ждёт ответа, которого не
будет. *Disables output color*: цвет — escape-последовательности ANSI, в текстовом логе они
становятся мусором вокруг каждой строки, по которому нельзя ни искать, ни читать.

Прогресс загрузки рассчитан на терминал, перерисовывающий одну строку; у файла-лога такой
возможности нет, и каждое обновление становится новой строкой. Холодная сборка `payments` тянет
68 МБ — на сервисе с полусотней зависимостей это тысячи строк, среди которых предстоит искать
настоящую ошибку.

**Чего эти флаги не делают.** На состав сборки и на результат они не влияют: jar получится тем же.
`-B` меняет режим общения, `-ntp` — объём лога; ускорения от них ждать не стоит, кроме случая, когда
конвейер писал сотню тысяч строк и упирался в лимит.

**Правило.** Любую команду в конвейере проверяйте вопросом «что она сделает, если ей некому ответить
и некуда рисовать?». Прямая проверка — `mvn ... < /dev/null > log.txt`. Тот же принцип шире Maven:
`--no-progress` у загрузчиков, `-y` у пакетных менеджеров, `--non-interactive` у клиентов облаков.

## 2. Кэш `~/.m2`: сколько экономит и когда травит сборку

Исполнитель эфемерен, локальный репозиторий Maven на нём пуст, и цена этого — порядок величины, а не
проценты. Замер на сквозном примере модуля (сервис `payments`, Spring Boot, Java 21, PostgreSQL):
Apple Silicon, macOS 15, Temurin 21.0.9, Maven 3.9.14; не бенчмарк, порядок величин. Локальный
репозиторий вынесен отдельно, `clean` в обоих случаях — иначе второй прогон мерил бы заодно
инкрементальную компиляцию:

```bash
mvn -B -ntp -Dmaven.repo.local=/tmp/m2-cold clean package -DskipTests
```
```
холодный репозиторий (пусто)   25,97 с      скачано 68 МБ
тёплый (тот же репозиторий)     1,53 с
тёплый, повтор                  1,59 с
```

Отношение ≈ 17×. **Оговорка обязательна:** у `payments` всего два стартера Spring Boot, на сервисе
с 40–60 зависимостями холодная сборка измеряется минутами. Отношение сохраняется, абсолютные числа —
нет, поэтому честный ответ на «насколько кэш ускоряет сборку» звучит как «во столько-то раз на
такой-то сборке», а не «на N секунд».

**Где ломается — и это не про скорость.** В `~/.m2` попадают вещи разной природы, а кэшируются
одинаково. Релизная версия `spring-boot-starter-web:3.3.4` — неизменяемая координата, кэшировать её
безопасно. SNAPSHOT — нет: «Unlike release versions, snapshot artifacts can and do change over
time» (Maven docs, «Guide to naming conventions»), а частота проверок задаётся политикой
репозитория — «can be `always,` `daily` (default), `interval:XXX` (in minutes) or `never` (only if
it doesn't exist locally)» (POM Reference, `repository/snapshots/updatePolicy`).

Умолчание — раз в сутки. Чтобы такая политика пережила завершение процесса, отметка о последней
проверке должна где-то храниться, а переживает процесс только сам локальный репозиторий: кэш
конвейера восстанавливает вместе с артефактами состояние «сегодня уже проверяли». Maven, честно
соблюдая политику, не проверяет повторно — и конвейер собирает сервис против вчерашней версии общей
библиотеки при зелёных тестах и без единой ошибки. Отсюда назначение `-U` («Forces a check for
missing releases and updated snapshots on remote repositories»): он снимает именно эту политику, а
не «обновляет кэш вообще».

Третий случай — то, чего в кэше не должно было быть: артефакт, положенный в `~/.m2` командой
`mvn install` из соседнего проекта, живёт там наравне со скачанными, и сборка находит зависимость,
которую в Nexus никто не публиковал ([`RUNNERS_AND_EXECUTION.md` §3](RUNNERS_AND_EXECUTION.md)).

**Правило.** Локальный репозиторий Maven — не кэш загрузок, а хранилище с собственными правилами
актуальности, и кэш конвейера сохраняет его вместе с этими правилами и их состоянием. Кэшировать
нужно — семнадцатикратная разница того стоит, но на условии, что в сборке нет SNAPSHOT-зависимостей
(§3): иначе кэш и политика обновлений противоречат друг другу, и лечится это устранением SNAPSHOT.
Проверка здоровья: `mvn -o` на восстановленном кэше должен собрать проект целиком.

## 3. SNAPSHOT против неизменяемой версии

Почти каждый проект заводится с `<version>1.0-SNAPSHOT</version>`. Конвейер собрал
`ci-cd-payments-1.0-SNAPSHOT.jar`, проверил на dev, через час его надо поставить на qa — и соблазн
взять артефакт с той же координатой. Координата содержимое не идентифицирует:

> «`SNAPSHOT`s are artifacts built in between releases.» «They may be built from a particular commit
> or from code that isn't even committed to the source repository.» «Unlike release versions,
> snapshot artifacts can and do change over time.»
> — Maven docs, «Guide to naming conventions on groupId, artifactId, and version»

Три предложения — три поломки. *Can and do change*: за час соседняя ветка успела перезалить
`1.0-SNAPSHOT`, на qa поедет непроверенное, и сигнала не будет — имя файла совпало. *From code that
isn't even committed*: вопрос «из какого исходного кода собрано то, что работает на qa» может не
иметь ответа, а это первый вопрос любого разбора инцидента. И следствие для откатов: «то, что
работало раньше», не адресуемо, потому что по координате лежит уже другое.

**Механизм тот же, что у тега образа** — не аналогия, а одна ошибка на разных слоях: тот же тег `v1`
до и после пересборки того же дерева исходников указывает на разные дайджесты.

```
$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:25a00689dd771dfcbdaaa524ab9739c6ebbcbb5a4c4ac179c4ee030a2e5bb52b
# ... пересборка и push под тем же тегом ...
Digest:    sha256:81fc786d34ef4d8957ce99f13ac108aa8692ead54a4a151e39e7e74b57bab132
```

**Чего SNAPSHOT не делает и в чём его смысл.** Он не «плохая практика» сам по себе: несколько команд
разрабатывают связанные библиотеки параллельно, и потребитель подхватывает свежее, не выпуская релиз
на каждое изменение. Это осмысленно **внутри разработки** и бессмысленно на границе конвейера, где
нужен ответ на вопрос «что именно сейчас работает».

**Правило.** До сборки SNAPSHOT допустим, после — нет: в репозиторий артефактов, в реестр образов и
на окружения уходит только неизменяемый идентификатор. Проверка вопросом, а не инструментом: *«если
я через месяц назову этот идентификатор, я получу те же байты?»*

## 4. surefire против failsafe

У `payments` два вида тестов: модульные (40 секунд) и интеграционные с поднятым PostgreSQL
(9 минут). Соблазн — один прогон `mvn test`. Ломается это дважды, и вторая поломка интереснее.

*Обратная связь.* Опечатка ловится модульным тестом за 40 секунд, но при общем прогоне разработчик
узнаёт о ней через девять с половиной минут: порядок исполнения общий, и где упадёт, не предскажешь.
Разделение даёт fail fast — дешёвая проверка падает раньше дорогой, и дорогая при красной дешёвой не
запускается вовсе (задание `integration-test` объявляется зависящим от `build`).

*Уборка после падения.* Она и есть причина, по которой Failsafe — отдельный плагин, а не настройка:

> «If you use the Surefire Plugin for running tests, then when you have a test failure, the build
> will stop at the `integration-test` phase and your integration test environment will not have been
> torn down correctly.» «The Failsafe Plugin will not fail the build during the `integration-test`
> phase, thus enabling the `post-integration-test` phase to execute.»
> — Maven Failsafe Plugin docs

Жизненный цикл содержит три фазы подряд: `pre-integration-test` (поднять окружение),
`integration-test` (прогнать тесты), `post-integration-test` (погасить окружение). Surefire, встретив
падение, роняет сборку сразу, и до уборки дело не доходит; Failsafe падение запоминает, а отказ
объявляет позже — поэтому цели `integration-test` и `verify` подключают вместе, вторая без первой
бессмысленна: именно она превращает запомненное падение в красную сборку. Практическое следствие:
под Surefire упавший интеграционный тест оставляет поднятые контейнеры и занятые порты, и следующее
задание на том же исполнителе падает по причине, к коду отношения не имеющей. На долгоживущем агенте
([`TOOLS_COMPARED.md` §5](TOOLS_COMPARED.md)) это превращается в накопление мусора.

**Как плагины делят тесты.** Не по расположению и не по настройке, а по имени класса: умолчания
Surefire — `**/Test*.java`, `**/*Test.java`, `**/*Tests.java`, `**/*TestCase.java` (параметр
`includes` цели `surefire:test`), Failsafe забирает классы `*IT`. Отсюда единственное требование к
коду: назвать интеграционный тест `PaymentsFlowIT`, а не `PaymentsFlowTest` — ошибка в имени тихо
переводит девятиминутный тест в сорокасекундный этап.

**Оговорка про пропуск тестов.** Свойство `skipTests` общее для обоих плагинов («Set this to "true"
to skip running tests, but still compile them», Surefire docs), поэтому «прогнать только
интеграционные, пропустив модульные» им не выражается: задание `integration-test` честно выполняет
`mvn -B -ntp verify` и прогоняет модульные второй раз. Сорок секунд — приемлемая цена за задание,
которое собирается из чистого клона и ни от чего не зависит.

**Правило.** Разделение — не про аккуратность, а про два измеримых свойства: быстрый гейт падает
первым, медленный гарантированно убирает за собой.

## 5. Testcontainers в конвейере

Интеграционные тесты `payments` поднимают настоящий PostgreSQL и на ноутбуке работают без единой
настройки, а в конвейере падают до первого запроса к базе. Диагноз «в CI нет Docker» неполный:
Docker там обычно есть — его нет **у задания**.

> «To run Testcontainers-based tests, you need a Docker-API compatible container runtime, such as
> using Testcontainers Cloud or installing Docker locally.»
> — Testcontainers docs, «Supported container runtimes»

Ключевое слово — **API**: вопрос не «стоит ли Docker на машине», а «достижим ли его API из процесса,
где идёт `mvn verify`». Отсюда три случая с одним корнем.

*Случай 1: задание само выполняется в контейнере, API снаружи.* Это умолчание для исполнителя с
контейнерным типом ([`RUNNERS_AND_EXECUTION.md` §2](RUNNERS_AND_EXECUTION.md)).

> «The docker socket must be available via a volume mount» «Testcontainers will automatically detect
> if it's inside a container and instead of 'localhost' will use the default gateway's IP.» «While
> Docker-in-Docker (DinD) is generally considered an instrument of last resort, it is necessary for
> some CI environments.»
> — Testcontainers docs, «Patterns for running tests inside a docker container»

Проброшенный сокет делает поднятые Testcontainers контейнеры **соседними** на том же хосте. DinD —
отдельный демон рядом (в GitLab это `services: docker:27-dind` и переменная `DOCKER_HOST`);
«instrument of last resort» — их формулировка, и она про цену: привилегированный режим и
непереиспользуемый кэш образов хоста.

*Случай 2: API достижим, но адреса не те.* **`localhost` внутри контейнера — это сам контейнер.** Та
же ловушка ловит и сборщик образов: запущенный в контейнере, он писал кэш на `localhost:5001` и
молча писал его в себя, а не в реестр на хосте. Тест, который после старта контейнера с базой идёт
на `localhost:5432`, работает на ноутбуке и не работает в задании: адрес и порт надо спрашивать у
Testcontainers, а не предполагать.

*Случай 3: за заданием остаётся мусор.* Задание прибили по таймауту, JVM умерла, поднятые ею
контейнеры остались. Для этого поднимается служебный контейнер:

> «The resource reaper is responsible for container removal and automatic cleanup of dead containers
> at JVM shutdown» «Note that Testcontainers will continue doing the cleanup at JVM's shutdown,
> unless you `kill -9` your JVM process.» «If your environment already implements automatic cleanup
> of containers after the execution, but does not allow starting privileged containers, you can turn
> off the Ryuk container by setting `TESTCONTAINERS_RYUK_DISABLED` **environment variable** to
> `true`.»
> — Testcontainers docs, «Custom configuration»

Условие в цитате составное: среда **уже** убирает за собой **и** не разрешает привилегированные
контейнеры. Первая половина выполняется на эфемерном исполнителе — машина уходит целиком; на
долгоживущем агенте выключение `ryuk` означает отказ от единственной уборки, переживающей `kill -9`,
и порты с памятью кончаются к концу недели.

**Правило.** Три вопроса в этом порядке: достижим ли API среды исполнения контейнеров из процесса
тестов (конфигурация исполнителя); какие адреса видит тест, если сам выполняется в контейнере (код
теста); кто уберёт контейнеры, если задание убьют (тип исполнителя). Сборка образа в контейнере —
та же болезнь, другая задача: [`IMAGE_BUILD_AND_REGISTRY.md` §1](IMAGE_BUILD_AND_REGISTRY.md).

## 6. Гейт покрытия: почему порог — плохая метрика

Фраза «покрытие показывает, какая доля кода протестирована» неверна буквально: покрытие показывает
не «протестирована», а «исполнена» — «a source line is considered executed when at least one
instruction that is assigned to this line has been executed» (JaCoCo docs, «Coverage Counters»).
Требования проверить результат в определении нет, отсюда контрпример на две строки:

```java
@Test
void charge() {
    service.charge(new Order("A-1", 100));   // ни одного assert
}
```

Метод исполнен целиком, все его строки засчитаны, покрытие выросло, порог 80 % выполнен. Проверено
ноль: тест зелёный при любом возвращаемом значении и упадёт только на исключении.

Вторая половина проблемы — покрытие грубее, чем кажется, даже как метрика исполнения:

> «JaCoCo also calculates branch coverage for all `if` and `switch` statements. This metric counts
> the total number of such branches in a method and determines the number of executed or missed
> branches.» — JaCoCo docs, «Coverage Counters»

Строка `if (amount > limit && account.isActive())` считается покрытой, если исполнена **хотя бы
одна** ведущая к ней инструкция. На вопрос «а второй вариант условия кто-нибудь проверял» отвечает
отдельный счётчик — покрытие ветвей, а в отчётах чаще смотрят на первое число.

**Почему порог именно как гейт ведёт себя плохо.** Метрика становится целью, и способ достичь числа
дешевле способа достичь смысла: тест без проверок пишется быстрее, чем разбирается непокрытая ветка,
а число оба двигают одинаково. Отдельно вредна асимметрия — порог наказывает того, кто добавил код,
и надёжнее всего останавливает не плохие изменения, а мелкие правки в давно нетронутом классе.

**Когда покрытие полезно — и это не гейт.** Как диагностический инструмент отчёт показывает, какие
ветки не исполняются ни одним тестом, и это точное проверяемое знание. Полезен и порог не на
абсолютную величину, а на **изменение**: «покрытие не должно падать» ловит настоящий случай
(добавили код без тестов), не требуя догонять исторический долг. Покрытие — карта того, что тесты
**трогают**, а не того, что они **проверяют**.

## 7. Воспроизводимая сборка

Jar — это zip-архив, а формат zip хранит для каждой записи время её создания, и по умолчанию туда
попадает момент упаковки. Значит, jar является функцией не только от входа, но и от часов: две
сборки одного дерева исходников с `sleep 2` между ними (`mvn -B -ntp clean package -DskipTests`,
затем `shasum -a 256 target/*.jar`; в выводе первые 32 символа) дают разные байты.

```
без project.build.outputTimestamp     сборка 1: 1935ad70b5bbad69b941ef55a505a8ea…
                                      сборка 2: 546701dcc3c1cad09f49e0833a21cb86…   → РАЗНЫЕ
с project.build.outputTimestamp       сборка 1: 9fc5925cf3e7c4b0f44b68fc3bc568a5…
                                      сборка 2: 9fc5925cf3e7c4b0f44b68fc3bc568a5…   → ОДИНАКОВЫ
```

Свойство подменяет время в записях архива фиксированным значением:

> «Timestamp for reproducible output archive entries, either formatted as ISO 8601 extended offset
> date-time (e.g. in UTC such as '2011-12-03T10:15:30Z' or with an offset '2019-10-05T20:37:42+06:00'),
> or as an int representing seconds since the epoch (like SOURCE_DATE_EPOCH).»
> — Maven JAR Plugin docs, цель `jar:jar`, параметр `outputTimestamp`

Брать значение надо от даты последнего коммита: оно должно быть **функцией от входа**, а не
константой на все времена. Без него «пересобрать из того же коммита» и «взять тот же артефакт» —
разные операции с разными контрольными суммами; с ним пересборка становится допустимой запасной
дорогой, а основной остаётся продвижение одного артефакта. Одно свойство закрывает самый частый
источник расхождения, но не единственный — порядок файлов, абсолютные пути в манифесте, генерация
кода с временными метками ломают воспроизводимость так же; проверка одна и дешёвая: собрать дважды
и сравнить `sha256`.

## 8. Публикация в Nexus/Artifactory

У `payments` есть модуль `payments-api` — классы запросов и ответов, нужные трём другим сервисам.
Образом с ними не поделишься: образ запускают, а не подключают зависимостью. Собирать `payments` у
каждого потребителя из исходников работает, пока сервисов трое, и разваливается на четвёртом: у всех
своя копия чужого кода и своя версия, а сборка зависит от того, что лежит в чужом репозитории
**сейчас**.

> «The deploy plugin is primarily used during the deploy phase, to add your artifact(s) to a remote
> repository for sharing with other developers and projects.» «As a repository contains more than the
> artifacts (POMs, the metadata, MD5 and SHA1 hash files...), deploying means not only copying the
> artifacts, but making sure all this information is correctly updated.»
> — Maven Deploy Plugin docs

Вторая цитата объясняет, почему это не «положить файл на сервер»: репозиторий хранит ещё и `pom` с
описанием транзитивных зависимостей, метаданные версий и контрольные суммы. Nexus и Artifactory —
серверные реализации этой модели: содержимое адресуется координатой `groupId:artifactId:version`, и
сборка потребителя разрешает зависимости по ней, а не по чьей-то рабочей директории.

| | Менеджер артефактов | Реестр образов |
|---|---|---|
| Что хранит | библиотеку — то, что **подключают** | образ — то, что **запускают** |
| Адресация | координата `groupId:artifactId:version` | тег и дайджест |
| Кто потребитель | сборка другого сервиса | среда исполнения (Kubernetes, Swarm) |
| Когда нужен | у вас есть код, общий для нескольких сервисов | у вас есть сервис, который надо запустить |

**Правило.** `mvn deploy` оправдан ровно тогда, когда у артефакта есть потребитель, который
**подключает** его как зависимость; если такой потребитель один и это вы сами, у вас не библиотека,
а преждевременно вынесенный модуль. Сервису, не отдающему наружу ни одной библиотеки, публикация
добавляет этап, версионную дисциплину и хранилище, которое надо чистить, не давая взамен ничего.
И требование к версии из §3: публиковать наружу можно только неизменяемую — иначе потребитель на
пустом кэше и потребитель на прогретом соберутся против разного кода.

## 9. Чем модель Gradle отличается от Maven для CI

Разница не в синтаксисе сборочного файла — он к длительности конвейера отношения не имеет, — а в
единице выполнения и в том, что считается «уже сделанным». У Maven единица — фаза жизненного цикла,
и `mvn package` проходит фазы подряд от начала; экономия возможна ровно одна, из §2 — не скачивать
заново зависимости, а компиляция и упаковка выполняются каждый раз. У Gradle единица — задача с
объявленными входами и выходами: «Gradle tests whether any of the task inputs or outputs has changed
**since the last build**. If they haven't, Gradle can consider the task up to date and therefore
skip executing its actions» (Gradle docs, «Incremental Build»; в консоли это отметка `UP-TO-DATE`).

«Since the last build» — сравнение с предыдущей сборкой **на этой машине**. На ноутбуке это выигрыш;
на эфемерном исполнителе предыдущей сборки не было никогда, так что сама инкрементальность к
конвейеру отношения не имеет. Имеет — второй механизм:

> «The build cache works by storing (locally or remotely) build outputs and allowing builds to fetch
> these outputs from the cache when it is determined that inputs have not changed, avoiding the
> expensive work of regenerating them.» «When using a shared build cache for task output caching this
> even works across developer machines and build agents.»
> — Gradle docs, «Build Cache»

Слово «кэш» одинаковое, природа разная: кэш локального репозитория Maven хранит **входы** сборки —
чужие библиотеки, которые не надо скачивать заново; кэш сборки Gradle хранит **выходы** — если входы
те же, результат берётся готовым и задача не выполняется вовсе. Второе сильнее: не переиспользовать
загрузку, а не делать работу.

**Где ломается.** Механизм держится на том, что входы задачи объявлены полно и точно. Задача,
читающая что-то вне списка входов — переменную окружения, текущее время, файл вне проекта, — будет
признана актуальной там, где результат изменился. Расплата такая же, как у неверного ключа кэша
([`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md)): не медленно, а неверно. Общий на всю
компанию кэш выходов эту цену умножает — ошибочная запись достаётся всем.

| Что должно быть правдой | Что из этого следует |
|---|---|
| Сборка идёт минуты, модулей много, между прогонами меняется малая часть | кэш выходов Gradle окупается: платите за инфраструктуру кэша, экономите работу |
| Один модуль, сборка секунды, зависимости — главная статья расходов | достаточно кэша локального репозитория; модель Maven ничем не хуже |
| Тесты зависят от внешнего состояния, входы задач объявлены не полностью | общий кэш выходов опасен: включать после того, как это починено, а не до |

Выбор системы сборки скоростью конвейера не измеряется: Gradle даёт более сильный механизм экономии
и вместе с ним более сильный способ получить неверный результат. Это размен, а не рейтинг.

## 10. Шпаргалка

| Что спрашивают | Одна фраза |
|---|---|
| Зачем `-B -ntp` | У задания нет человека: некому отвечать на вопросы и негде рисовать прогресс |
| Сколько экономит кэш `~/.m2` | 25,97 с → 1,53 с на `payments` (≈17×); абсолютные числа зависят от числа зависимостей, отношение — нет |
| Когда кэш `~/.m2` вредит | Есть SNAPSHOT-зависимости: политика обновления «раз в сутки» восстанавливается вместе с кэшем |
| Почему SNAPSHOT нельзя продвигать | Изменяемый указатель: «snapshot artifacts can and do change over time» |
| Граница SNAPSHOT | До сборки допустим, после — нет: наружу уходит только неизменяемый идентификатор |
| Зачем failsafe | Быстрый гейт падает первым; failsafe не роняет сборку в `integration-test`, чтобы отработала уборка в `post-integration-test` |
| Как делятся тесты | По имени класса: `*Test` → surefire, `*IT` → failsafe |
| Что нужно Testcontainers | Достижимый API среды исполнения контейнеров; проброшенный сокет предпочтительнее DinD |
| Зачем `ryuk` | Убирает контейнеры после смерти JVM; выключать только там, где среда убирает сама |
| Порог покрытия | Измеряет исполнение строк, а не проверку поведения: тест без `assert` поднимает число |
| Как чинить невоспроизводимый jar | `project.build.outputTimestamp` = дата коммита; проверка — собрать дважды и сравнить `sha256` |
| Когда нужен `mvn deploy` | Только если у артефакта есть потребитель, подключающий его зависимостью |
| Модель Gradle против Maven | Gradle кэширует **выходы** задач (в том числе удалённо), Maven — только **входы** сборки |

### Формулировки для собеседования

- «Кэш локального репозитория экономит примерно семнадцатикратно, но это сборка с двумя стартерами:
  честный ответ всегда во столько-то раз на такой-то сборке, а не в секундах.»
- «SNAPSHOT — не версия, а изменяемый указатель. Ровно та же ошибка, что адресовать образ тегом:
  имя то же, содержимое другое, и никакой ошибки при подмене не возникает.»
- «Surefire роняет сборку прямо в фазе `integration-test`, и до уборки окружения дело не доходит, —
  ради этого failsafe и существует.»
- «Покрытие — карта того, что тесты трогают, а не того, что они проверяют. Как гейт годится только
  в форме "не падает".»
- «Без `project.build.outputTimestamp` "пересобрать из того же коммита" и "взять тот же артефакт" —
  разные операции с разными контрольными суммами.»
