# Сборка Java в конвейере: от `mvn -B` до воспроизводимого артефакта

> **Какую проблему решает.** Сборка не описана как функция от входа: зависимости качаются заново, jar из одного коммита состоит из разных байтов, версия `1.0-SNAPSHOT` не говорит, что внутри.
> **Кому это надо.** Тому, кто настраивает конвейер Java-сервиса и должен объяснить в нём каждый флаг `mvn`.
> **Когда НЕ надо.** Пока конвейер идёт списком там, где мог бы идти графом, экономия секунд на Maven ничего не меняет.

Соседнее: кэш конвейера — [`PIPELINE_CACHE_AND_CONCURRENCY.md` §1](PIPELINE_CACHE_AND_CONCURRENCY.md), тег и дайджест — [`IMAGE_REGISTRY_AND_TAGS.md` §1](IMAGE_REGISTRY_AND_TAGS.md), продвижение — [`ENVIRONMENTS_AND_PROMOTION.md` §1](ENVIRONMENTS_AND_PROMOTION.md), что тестировать — [`TESTING.md`](../../software-engineering/theory/TESTING.md).

## 1. `-B -ntp` и почему интерактивные флаги ломают лог конвейера

**У задания в конвейере нет человека** — ни терминала, ни клавиатуры, ни глаз. Maven по умолчанию
считает иначе: `-B` — «run in non-interactive (batch) mode (disables output color)», `-ntp` — «do not
display transfer progress» (Maven CLI Options). Без первого плагин, задающий вопрос, получает пустой
стандартный ввод и ждёт до таймаута задания, а ANSI-цвет становится мусором вокруг каждой строки. Без
второго прогресс загрузки, рассчитанный на перерисовку одной строки, пишет новую строку на каждое
обновление: холодная сборка тянет 68 МБ, и на полусотне зависимостей это тысячи строк вокруг настоящей
ошибки. На результат флаги не влияют — jar тот же. **Правило:** проверяйте команду вопросом «что она
сделает, если некому ответить и некуда рисовать?» — `mvn ... < /dev/null > log.txt`.

## 2. Кэш `~/.m2`: сколько экономит и когда травит сборку

Исполнитель эфемерен, локальный репозиторий Maven пуст, и цена этого — порядок величины (`payments`
на Spring Boot и Java 21; Apple Silicon, macOS 15, Temurin 21.0.9, Maven 3.9.14, не бенчмарк):

```
$ mvn -B -ntp -Dmaven.repo.local=/tmp/m2-cold clean package -DskipTests
холодный репозиторий (пусто)   25,97 с      скачано 68 МБ
тёплый (тот же репозиторий)     1,53 с
тёплый, повтор                  1,59 с
```

Отношение ≈ 17×, но у `payments` два стартера Spring Boot: на 40–60 зависимостях холодная сборка идёт
минутами: отношение устойчиво, абсолютные числа нет.

Ломается кэш не на скорости: SNAPSHOT — изменяемая координата, а частота его проверок задаётся
политикой репозитория, по умолчанию `daily` (POM Reference, `snapshots/updatePolicy`). Отметка о
последней проверке переживает процесс только внутри самого репозитория, поэтому кэш восстанавливает
вместе с артефактами состояние «сегодня уже проверяли» — и сборка идёт против вчерашней версии общей
библиотеки при зелёных тестах; `-U` снимает именно эту политику. Отдельный случай — артефакт,
положенный в `~/.m2` командой `mvn install` из соседнего проекта: сборка находит зависимость, которой в
Nexus нет ([`RUNNERS.md` §3](RUNNERS.md)).

**Правило.** Локальный репозиторий — не кэш загрузок, а хранилище со своими правилами актуальности;
кэшировать нужно при условии, что SNAPSHOT в сборке нет (§3), а проверка — `mvn -o` на восстановленном
кэше собирает проект целиком.

## 3. SNAPSHOT против неизменяемой версии

Координата `1.0-SNAPSHOT` не идентифицирует содержимое: «they may be built from a particular commit or
from code that isn't even committed to the source repository», «unlike release versions, snapshot
artifacts can and do change over time» (Maven docs, «Guide to naming conventions»). Отсюда три поломки:
соседняя ветка успевает перезалить ту же координату, и на qa едет непроверенное без сигнала; «из какого
кода собрано то, что работает на qa» может не иметь ответа; откат недоступен, потому что «то, что
работало раньше», не адресуемо. Та же ошибка, что адресовать образ тегом
([`IMAGE_REGISTRY_AND_TAGS.md` §1](IMAGE_REGISTRY_AND_TAGS.md)). Сам по себе SNAPSHOT решает задачу
параллельной разработки связанных библиотек — потребитель подхватывает свежее без релиза на каждое
изменение. **Правило:** до сборки допустим, после — нет; проверка вопросом «назову этот идентификатор
через месяц — получу те же байты?».

## 4. surefire против failsafe

Модульные тесты `payments` идут 40 секунд, интеграционные с поднятым PostgreSQL — 9 минут, и общий
прогон `mvn test` ломается дважды. Первое — обратная связь: об опечатке, которую ловит модульный тест,
разработчик узнаёт через девять с половиной минут. Второе — уборка, и она же причина, по которой
Failsafe отдельный плагин:

Делят тесты плагины по имени класса: Surefire берёт `Test*`, `*Test`, `*Tests`, `*TestCase`, Failsafe —
`*IT`, и ошибка в имени тихо переводит девятиминутный тест в сорокасекундный этап. **Правило:** быстрый
гейт падает первым, медленный гарантированно убирает за собой.

## 5. Testcontainers в конвейере

«В CI нет Docker» — неполный диагноз: Docker там обычно есть, его нет **у задания**. Требование —
«a Docker-API compatible container runtime» (Testcontainers docs), и ключевое слово здесь API: вопрос
не «стоит ли Docker на машине», а «достижим ли его API из процесса `mvn verify`».

| Случай | Что делать |
|---|---|
| Задание в контейнере, API снаружи | «the docker socket must be available via a volume mount» — контейнеры станут соседними на хосте; DinD документация зовёт «an instrument of last resort» |
| **`localhost` внутри контейнера — это сам контейнер** | Testcontainers «will use the default gateway's IP»; адрес и порт спрашивают у него, а не предполагают |
| JVM убили, контейнеры остались | служебный контейнер убирает их «at JVM shutdown, unless you `kill -9` your JVM process» |

Выключать `ryuk` (`TESTCONTAINERS_RYUK_DISABLED`) документация разрешает при составном условии: среда
**уже** убирает за собой **и** не разрешает привилегированные контейнеры. Первая половина верна для
эфемерного исполнителя; на долгоживущем агенте это отказ от единственной уборки, переживающей
`kill -9`.

## 6. Гейт покрытия: почему порог — плохая метрика

Покрытие показывает не «протестирована», а «исполнена»: «a source line is considered executed when at
least one instruction that is assigned to this line has been executed» (JaCoCo docs). Требования
проверить результат в определении нет:

```java
@Test
void charge() {
    service.charge(new Order("A-1", 100));   // ни одного assert
}
```

Метод исполнен целиком, строки засчитаны, порог 80 % выполнен, проверено ноль. Строка
`if (amount > limit && account.isActive())` покрыта, если исполнена хотя бы одна ведущая к ней
инструкция; на «а второй вариант условия проверял кто-нибудь» отвечает отдельный счётчик — покрытие
ветвей, а в отчётах смотрят на первое число. Как гейт порог плох, потому что метрика становится целью:
тест без проверок пишется быстрее, чем разбирается непокрытая ветка. **Правило:** как гейт годится
только порог на изменение («не должно падать»).

## 7. Воспроизводимая сборка

Zip хранит для каждой записи время создания, и по умолчанию туда попадает момент упаковки: jar
оказывается функцией не только от входа, но и от часов. Две сборки одного дерева с `sleep 2` между
ними (`mvn -B -ntp clean package -DskipTests`, затем `shasum -a 256 target/*.jar`, первые 32 символа):

```
без project.build.outputTimestamp     сборка 1: 1935ad70b5bbad69b941ef55a505a8ea…
                                      сборка 2: 546701dcc3c1cad09f49e0833a21cb86…   → РАЗНЫЕ
с project.build.outputTimestamp       сборка 1: 9fc5925cf3e7c4b0f44b68fc3bc568a5…
                                      сборка 2: 9fc5925cf3e7c4b0f44b68fc3bc568a5…   → ОДИНАКОВЫ
```

Свойство подменяет это время фиксированным — «timestamp for reproducible output archive entries»
(Maven JAR Plugin, `jar:jar`), — и брать его надо от даты последнего коммита, чтобы значение было
функцией от входа. Оно закрывает самый частый источник расхождения, но не единственный: порядок файлов,
абсолютные пути в манифесте, генерация кода с метками времени ломают его так же — **проверка одна:
собрать дважды и сравнить `sha256`.**

## 8. Публикация в Nexus/Artifactory

Модуль `payments-api` — классы запросов и ответов, нужные трём другим сервисам; образом с ними не
поделишься, образ запускают, а не подключают зависимостью, а сборка у каждого потребителя из исходников
разваливается на четвёртом сервисе. Публикация — не «положить файл на сервер»: «a repository contains
more than the artifacts (POMs, the metadata, MD5 and SHA1 hash files...), deploying means… making sure
all this information is correctly updated» (Deploy Plugin).

| | Менеджер артефактов | Реестр образов |
|---|---|---|
| Что хранит | библиотеку — то, что **подключают** | образ — то, что **запускают** |
| Адресация | `groupId:artifactId:version` | тег и дайджест |
| Кто потребитель | сборка другого сервиса | среда исполнения (Kubernetes, Swarm) |

**Правило.** `mvn deploy` оправдан, когда у артефакта есть потребитель, который **подключает** его как
зависимость; наружу публикуется только неизменяемая версия (§3).

## 9. Чем модель Gradle отличается от Maven для CI

Разница в единице выполнения. У Maven единица — фаза жизненного цикла, и экономия возможна ровно одна,
из §2: не скачивать заново зависимости. У Gradle единица — задача с объявленными входами и выходами,
она пропускается, если ничего не изменилось «since the last build» (в консоли — `UP-TO-DATE`), но
сравнение идёт с предыдущей сборкой **на этой машине**, которой на эфемерном исполнителе не было.
К конвейеру относится кэш сборки, который «stores (locally or remotely) build outputs» и «even works
across developer machines and build agents» (Gradle docs): кэш репозитория Maven хранит **входы**
сборки, кэш Gradle — **выходы**. Держится это на полноте объявленных входов — задача, читающая
переменную окружения или файл вне проекта, будет признана актуальной там, где результат изменился.

| Что должно быть правдой | Что из этого следует |
|---|---|
| Сборка идёт минуты, модулей много, меняется малая часть | кэш выходов Gradle окупается |
| Один модуль, секунды, главная статья — зависимости | достаточно кэша репозитория, Maven не хуже |
| Входы задач объявлены не полностью | общий кэш выходов опасен: сначала починить |

Gradle даёт более сильный механизм экономии и более сильный способ получить неверный результат:
размен, а не рейтинг.

## 10. Шпаргалка

| Что спрашивают | Одна фраза |
|---|---|
| Зачем `-B -ntp` | У задания нет человека: некому отвечать и негде рисовать прогресс |
| Сколько экономит кэш `~/.m2` | 25,97 с → 1,53 с (≈17×); отношение устойчиво, абсолютные числа нет |
| Когда кэш `~/.m2` вредит | Есть SNAPSHOT: политика «раз в сутки» восстанавливается вместе с кэшем |
| Почему SNAPSHOT нельзя продвигать | Изменяемый указатель: «can and do change over time» |
| Граница SNAPSHOT | До сборки допустим, после — нет |
| Зачем failsafe | Не роняет сборку в `integration-test`, чтобы отработала уборка в `post-integration-test` |
| Как делятся тесты | По имени класса: `*Test` → surefire, `*IT` → failsafe |
| Что нужно Testcontainers | Достижимый API среды контейнеров; сокет предпочтительнее DinD |
| Зачем `ryuk` | Убирает контейнеры после смерти JVM; выключать там, где среда убирает сама |
| Порог покрытия | Меряет исполнение строк, а не проверку: тест без `assert` поднимает число |
| Невоспроизводимый jar | `outputTimestamp` = дата коммита; собрать дважды и сравнить `sha256` |
| Когда нужен `mvn deploy` | Только если артефакт кто-то подключает зависимостью |
| Gradle против Maven | Gradle кэширует **выходы** задач, Maven — только **входы** |

### Формулировки для собеседования

- «Кэш репозитория экономит семнадцатикратно, но это сборка с двумя стартерами: честный ответ — во столько-то раз на такой-то сборке, а не в секундах.»
- «SNAPSHOT — не версия, а изменяемый указатель: та же ошибка, что адресовать образ тегом.»
- «Surefire роняет сборку прямо в фазе `integration-test`, и до уборки окружения дело не доходит, — ради этого failsafe и существует.»
- «Покрытие — карта того, что тесты трогают, а не того, что они проверяют.»
- «Без `outputTimestamp` "пересобрать из того же коммита" и "взять тот же артефакт" — разные операции с разными суммами.»
