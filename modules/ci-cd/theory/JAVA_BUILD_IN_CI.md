# Сборка Java в конвейере: от `mvn -B` до воспроизводимого артефакта

> **Какую проблему решает.** Сборка `payments` идёт 12 минут, из которых заметная часть — заново
> скачанные зависимости; jar, собранный дважды из одного коммита, состоит из разных байтов; версия
> артефакта `1.0-SNAPSHOT` не говорит ничего о том, что внутри. Всё это не «особенности Maven», а
> следствия одного пробела: сборка не описана как функция от входа, поэтому её результат не
> идентифицируется и продвигать по окружениям, строго говоря, нечего.
> **Кому это надо.** Тому, кто настраивает конвейер для Java-сервиса и должен объяснить каждую
> строчку `mvn` в нём; тому, у кого спросят «а почему у вас в CI именно `-B -ntp`» и «зачем вам
> failsafe, если есть surefire».
> **Когда НЕ надо.** Ускорение сборки — не первый шаг. Пока конвейер идёт последовательно там, где
> мог бы идти графом, и перезапускается из-за ненадёжных тестов, экономия секунд на Maven ничего не
> меняет: сначала граф ([`PIPELINE_MODEL.md` §3](PIPELINE_MODEL.md)), потом содержание заданий.

**Границы с соседними файлами.** Механика кэша вообще — ключ как утверждение, промах, отравление —
в [`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md); здесь только Maven-специфичный случай.
Как один и тот же путь сборки записывается тремя инструментами — в
[`TOOLS_COMPARED.md` §1](TOOLS_COMPARED.md). Сборка образа, слои и адресация дайджестом — в
[`IMAGE_BUILD_AND_REGISTRY.md`](IMAGE_BUILD_AND_REGISTRY.md); правило «собрать один раз, продвигать
тот же артефакт» — в [`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md). Что должно
входить в гейт перед слиянием и что делать с ненадёжными тестами — в
[`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md);
пирамида тестирования и что мокать — в
[`TESTING.md`](../../software-engineering/theory/TESTING.md).

**Сквозной пример.** Сервис `payments`: Spring Boot 3.3.4, Java 21, Maven, PostgreSQL, пик
40 запросов в секунду, базовая сборка 12 минут. `pom.xml` и `Dockerfile` — в корне модуля, учебные
конвейеры — в `pipelines/`.

Числа в блоках прогонов сняты на Apple Silicon, macOS 15 (Darwin 25.6.0): Temurin 21.0.9,
Maven 3.9.14, Docker 29.4.3. Это не бенчмарк — порядок величин.

## 1. `-B -ntp` и почему интерактивные флаги ломают лог конвейера

**Задача.** В `pipelines/github/ci.yml` стоит `mvn -B -ntp clean package`. На собеседовании
спрашивают, зачем два флага, которых нет в команде на ноутбуке.

**Наивный ответ.** «Так принято». Ответ плохой не потому, что неправдив, а потому, что за флагами
стоит один принцип, из которого выводятся оба: **у задания в конвейере нет человека**. Ни терминала,
ни клавиатуры, ни глаз, которые следят за прогрессом.

**Где ломается без `-B`.** Maven по умолчанию считает, что перед ним человек:

> `-B,--batch-mode` — «Run in non-interactive (batch) mode (disables output color)»
>
> — Maven docs, «Maven CLI Options Reference»

Из формулировки видны обе половины. *Non-interactive*: плагин, который в интерактивном режиме
задаёт вопрос (архетипы, релизные плагины), в конвейере получает пустой стандартный ввод и либо
ждёт, пока задание не прибьют по таймауту, либо падает через десять минут вместо секунды. Задание
при этом не «зависло» — оно честно ждёт ответа, которого не будет. *Disables output color*: цвет —
это escape-последовательности ANSI, и в текстовом логе они превращаются в мусор вокруг каждой
строки, по которому потом невозможно ни искать, ни разбирать глазами.

**Где ломается без `-ntp`.**

> `-ntp,--no-transfer-progress` — «Do not display transfer progress when downloading or uploading»
>
> — Maven docs, «Maven CLI Options Reference»

Прогресс загрузки рассчитан на терминал, который перерисовывает одну строку. Файла-лога такой
возможности нет: каждое обновление становится новой строкой. Масштаб понятен из прогона 1 журнала —
холодная сборка `payments` тянет 68 МБ; на сервисе с полусотней зависимостей это сотни файлов и
тысячи строк, среди которых предстоит искать настоящую ошибку.

**Механизм.** Оба флага — не оптимизация, а приведение поведения инструмента в соответствие со
средой: нет человека — нет вопросов и нет анимации. Тот же принцип действует шире, чем Maven:
`--no-progress` у загрузчиков, `-y` у пакетных менеджеров, `--non-interactive` у клиентов
облаков — все они про одно и то же.

**Правило.** Любую команду в конвейере проверяйте одним вопросом: «что она сделает, если ей некому
ответить и некуда рисовать?» Прямая проверка — прогнать её с перенаправленным выводом и закрытым
стандартным вводом (`mvn ... < /dev/null > log.txt`). Если после этого команда ждёт или лог
нечитаем, флаги нужны.

**Чего эти флаги не делают.** Они не влияют ни на состав сборки, ни на результат: jar получится
тем же. `-B` меняет только режим общения, `-ntp` — только объём лога. Ускорения от них ждать не
стоит, кроме одного случая — когда конвейер писал в лог сотню тысяч строк и упирался в лимит.

## 2. Кэш `~/.m2`: сколько экономит и когда травит сборку

**Задача.** Исполнитель эфемерен, локальный репозиторий Maven на нём пуст. Насколько это дорого и
что делать?

**Замер — прогон 1 журнала модуля.** Локальный репозиторий вынесен в отдельную директорию, чтобы не
трогать рабочий; `clean` в обоих случаях, иначе второй прогон переиспользовал бы `target/` и мерил
бы заодно инкрементальную компиляцию:

```bash
mvn -B -ntp -Dmaven.repo.local=/tmp/m2-cold clean package -DskipTests
```

```
холодный репозиторий (пусто)   25,97 с      скачано 68 МБ
тёплый (тот же репозиторий)     1,53 с
тёплый, повтор                  1,59 с
```

Отношение ≈ 17×. **Оговорка обязательна:** у `payments` всего два стартера Spring Boot. На сервисе
с 40–60 зависимостями холодная сборка измеряется минутами; отношение сохраняется, абсолютные числа —
нет. Именно поэтому на вопрос «насколько кэш ускоряет сборку» единственный честный ответ — «во
столько-то раз на такой-то сборке», а не «на N секунд».

**Наивное решение.** Закэшировать `~/.m2` целиком и никогда не инвалидировать: содержимое
аддитивно, лишнего не бывает. Механика ключа, промаха и того, почему вечно совпадающий ключ убивает
запись в кэш, разобрана в [`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md) и здесь не
повторяется. Здесь — то, что специфично для Maven и что этой механикой не ловится.

**Где ломается — и это не про скорость.** В `~/.m2` попадают две вещи разной природы, а кэшируются
они одинаково.

*Первое: релизные версии.* `spring-boot-starter-web:3.3.4` — неизменяемая координата. Кэшировать
её безопасно: содержимое по этому адресу не меняется никогда, старый кэш просто экономит загрузку.

*Второе: SNAPSHOT-зависимости.* Вот здесь кэш перестаёт быть ускорением и становится источником
неверного результата, потому что содержимое по координате меняется:

> «Unlike release versions, snapshot artifacts can and do change over time.»
>
> — Maven docs, «Guide to naming conventions on groupId, artifactId, and version»

Насколько часто Maven проверяет, не изменились ли они, задаётся политикой репозитория:

> «The frequency for downloading updates - can be `always,` `daily` (default), `interval:XXX`
> (in minutes) or `never` (only if it doesn't exist locally).»
>
> — Maven docs, POM Reference, `repository/snapshots/updatePolicy`

Умолчание — раз в сутки. Дальше рассуждение, которое из этой формулировки следует само: чтобы
политика «раз в сутки» пережила завершение процесса, отметка о времени последней проверки должна
где-то храниться, а единственное, что переживает процесс, — сам локальный репозиторий. Значит, кэш
конвейера восстанавливает вместе с артефактами и состояние «сегодня уже проверяли». Maven, честно
соблюдая политику, повторно не проверяет — и конвейер собирает сервис против вчерашней версии общей
библиотеки. Тесты зелёные, ошибки нет нигде: каждый участник ведёт себя строго по документации.

Отсюда назначение `-U` («Forces a check for missing releases and updated snapshots on remote
repositories» — там же, CLI Options): он снимает именно эту политику, а не «обновляет кэш вообще».

*Третье, самое неприятное — то, чего в кэше не должно было быть.* Артефакт, попавший в `~/.m2`
командой `mvn install` из соседнего проекта, живёт там наравне со скачанными. Закэшировали такой
репозиторий — и сборка находит зависимость, которую в Nexus никто не публиковал. Этот случай уже
разобран с другой стороны в [`RUNNERS_AND_EXECUTION.md` §3](RUNNERS_AND_EXECUTION.md) как источник
расхождения «локально работает».

**Механизм в одну строку.** Локальный репозиторий Maven — не кэш загрузок, а **хранилище с
собственными правилами актуальности**. Кэш конвейера сохраняет и восстанавливает его как обычную
директорию, вместе с этими правилами и с их состоянием.

**Правило.** Кэшировать `~/.m2` нужно — семнадцатикратная разница того стоит. Но кэшируется он на
условии: в сборке нет SNAPSHOT-зависимостей (§3). Если они есть, кэш и политика обновлений начинают
противоречить друг другу, и лечится это не настройкой кэша, а устранением SNAPSHOT. Проверка
здоровья простая: `mvn -o` (offline) на восстановленном кэше должен собрать проект целиком. Если
не собирает — вы кэшируете не то, что думаете.

## 3. SNAPSHOT против неизменяемой версии

**Задача.** В `pom.xml` модуля стоит `<version>1.0-SNAPSHOT</version>` (`pom.xml:16`) — так
заводится почти каждый проект. Конвейер собрал `ci-cd-payments-1.0-SNAPSHOT.jar`, проверил его на
dev, и через час его надо поставить на qa. Что именно ставить?

**Наивное решение.** «Тот же артефакт»: взять `ci-cd-payments-1.0-SNAPSHOT.jar` из репозитория
артефактов и поставить на qa. Координата та же, значит, и содержимое то же.

**Где ломается.** Координата не идентифицирует содержимое:

> «`SNAPSHOT`s are artifacts built in between releases.»
> «They may be built from a particular commit or from code that isn't even committed to the source
> repository.»
> «Unlike release versions, snapshot artifacts can and do change over time.»
>
> — Maven docs, «Guide to naming conventions on groupId, artifactId, and version»

Три предложения — три отдельные поломки, и ни одна не про удобство.

*«Can and do change over time».* За час между dev и qa соседняя ветка успела собраться и перезалить
`1.0-SNAPSHOT`. На qa поедет то, что никто не проверял, и никакого сигнала об этом не будет: имя
файла совпало.

*«From code that isn't even committed».* SNAPSHOT не обязан соответствовать никакому коммиту вообще.
Значит, вопрос «из какого исходного кода собран артефакт, который сейчас работает на qa» может не
иметь ответа — а это первый вопрос любого разбора инцидента.

*И следствие для откатов.* Откатиться — значит поставить то, что работало раньше. Если
идентификатор указывает на изменяемое содержимое, «то, что работало раньше», не адресуемо: по
координате `1.0-SNAPSHOT` лежит что-то другое.

**Механизм — тот же, что у тега образа.** Это не совпадение и не аналогия, а одна и та же ошибка
на разных слоях. Прогон 4 журнала модуля: тот же тег `v1` до и после пересборки того же дерева
исходников указывает на разные дайджесты:

```
$ docker buildx imagetools inspect localhost:5001/payments:v1
Digest:    sha256:25a00689dd771dfcbdaaa524ab9739c6ebbcbb5a4c4ac179c4ee030a2e5bb52b

# ... пересборка и push под тем же тегом ...
Digest:    sha256:81fc786d34ef4d8957ce99f13ac108aa8692ead54a4a151e39e7e74b57bab132
```

Тег образа и версия SNAPSHOT — **изменяемые указатели**. Продвижение артефакта требует
неизменяемого идентификатора, то есть такого, у которого содержимое по адресу не меняется никогда.
Механика продвижения и то, как окружения адресуют один и тот же артефакт, — в
[`ENVIRONMENTS_AND_PROMOTION.md`](ENVIRONMENTS_AND_PROMOTION.md); адресация образа дайджестом — в
[`IMAGE_BUILD_AND_REGISTRY.md`](IMAGE_BUILD_AND_REGISTRY.md).

**Чего SNAPSHOT не делает и в чём его смысл.** Он не «плохая практика» сам по себе — он решает
ровно ту задачу, для которой сделан: несколько команд разрабатывают связанные библиотеки
параллельно, и потребитель хочет автоматически подхватывать свежее, не выпуская релиз на каждое
изменение. Это осмысленно **внутри разработки** и бессмысленно на границе конвейера, где нужен
ответ на вопрос «что именно сейчас работает».

**Правило.** В конвейере действует граница: до сборки SNAPSHOT допустим, после — нет. Всё, что
уходит дальше сборки — в репозиторий артефактов, в реестр образов, на окружения, — должно
адресоваться идентификатором, содержимое по которому не меняется. Проверка вопросом, а не
инструментом: *«если я через месяц назову этот идентификатор, я получу те же байты?»* Для
`1.0-SNAPSHOT` ответ «не обязательно», и этого достаточно, чтобы его туда не пускать.

## 4. surefire против failsafe

**Задача.** У `payments` два вида тестов: быстрые модульные (40 секунд) и медленные
интеграционные с поднятым PostgreSQL (9 минут — цифры из комментария в `pom.xml:58-62`). Зачем в
`pom.xml` подключён `maven-failsafe-plugin`, если `mvn test` уже прогоняет тесты?

**Наивное решение.** Один прогон `mvn test`, все тесты вместе. Меньше плагинов, меньше конфигурации,
один отчёт.

**Где ломается — две разные поломки, и вторая интереснее.**

*Первая, очевидная: обратная связь.* Опечатка в коде ловится модульным тестом за 40 секунд, но при
общем прогоне разработчик узнаёт о ней через девять с половиной минут — потому что порядок
исполнения общий и предсказать, где именно упадёт, нельзя. Разделение даёт `fail fast`: дешёвая
проверка падает раньше дорогой, и дорогая при красной дешёвой просто не запускается. Именно так
устроен граф в учебных конвейерах модуля: `integration-test` объявлен зависящим от `build`.

*Вторая, неочевидная: уборка после падения.* Она и есть настоящая причина, по которой Failsafe —
отдельный плагин, а не настройка Surefire:

> «The Failsafe Plugin is designed to run integration tests while the Surefire Plugin is designed to
> run unit tests.»
> «If you use the Surefire Plugin for running tests, then when you have a test failure, the build
> will stop at the `integration-test` phase and your integration test environment will not have been
> torn down correctly.»
> «The Failsafe Plugin is used during the `integration-test` and `verify` phases of the build
> lifecycle to execute the integration tests of an application. The Failsafe Plugin will not fail
> the build during the `integration-test` phase, thus enabling the `post-integration-test` phase to
> execute.»
>
> — Maven Failsafe Plugin docs

Разберём это по шагам, потому что формулировка плотная. Жизненный цикл Maven содержит три фазы
подряд: `pre-integration-test` (поднять окружение), `integration-test` (прогнать тесты),
`post-integration-test` (погасить окружение). Surefire, встретив падение, роняет сборку **сразу** —
и до фазы уборки дело не доходит. Failsafe падение запоминает, но сборку в этой фазе не роняет:
уборка отрабатывает, а отказ объявляется позже, в `verify`. Отсюда и связка целей в `pom.xml`
модуля (`pom.xml:63-74`): `integration-test` и `verify` подключены вместе — вторая без первой
бессмысленна, потому что именно она превращает запомненное падение в красную сборку.

Практическое следствие: под Surefire упавший интеграционный тест оставляет за собой поднятые
контейнеры и занятые порты, и следующее задание на том же исполнителе падает по причине, к коду
отношения не имеющей. На долгоживущем агенте ([`TOOLS_COMPARED.md` §5](TOOLS_COMPARED.md)) это
превращается в накопление мусора.

**Как плагины делят тесты между собой.** Не по расположению и не по настройке, а по имени класса.
Умолчания Surefire — `**/Test*.java`, `**/*Test.java`, `**/*Tests.java`, `**/*TestCase.java`
(Maven Surefire Plugin docs, `surefire:test`, параметр `includes`); Failsafe забирает классы `*IT`.
Отсюда единственное, что нужно сделать в коде: назвать интеграционный тест `PaymentsFlowIT`, а не
`PaymentsFlowTest`. Ошибка в имени тихо переводит девятиминутный тест в сорокасекундный этап.

**Оговорка про пропуск тестов.** Свойство `skipTests` — общее для обоих плагинов («Set this to
"true" to skip running tests, but still compile them», Surefire docs), поэтому «прогнать только
интеграционные, пропустив модульные» им не выражается. В учебном конвейере
(`pipelines/github/ci.yml`) задание `integration-test` честно выполняет `mvn -B -ntp verify` и
прогоняет модульные тесты второй раз: сорок секунд — приемлемая цена за задание, которое собирается
из чистого клона и ни от чего не зависит.

**Правило.** Разделение — не про аккуратность, а про два измеримых свойства: быстрый гейт падает
первым, а медленный гарантированно убирает за собой. Что должно попадать в каждую категорию и
зачем интеграционные тесты нужны вообще — вопрос не конвейера, а
[`TESTING.md`](../../software-engineering/theory/TESTING.md).

## 5. Testcontainers в конвейере

**Задача.** Интеграционные тесты `payments` поднимают настоящий PostgreSQL через Testcontainers.
На ноутбуке это работает без единой настройки. В конвейере — падает ещё до первого запроса к базе.

**Наивный ответ.** «Значит, в CI нет Docker, попросим админов поставить». Ответ неполный: Docker
там как раз обычно есть — его нет **у задания**, и это разные вещи.

**Где ломается — три случая, у всех один корень.** Требование к среде сформулировано документацией
прямо:

> «To run Testcontainers-based tests, you need a Docker-API compatible container runtime, such as
> using Testcontainers Cloud or installing Docker locally.»
>
> — Testcontainers docs, «Supported container runtimes»

Ключевое слово — **API**. Testcontainers не «использует Docker», он обращается к API среды
исполнения контейнеров и просит поднять контейнер. Значит, вопрос не «стоит ли Docker на машине», а
«достижим ли его API из процесса, где идёт `mvn verify`».

*Случай 1: задание само выполняется в контейнере, и API снаружи.* Это умолчание для исполнителя с
контейнерным типом ([`RUNNERS_AND_EXECUTION.md` §2](RUNNERS_AND_EXECUTION.md)): процесс `mvn` живёт
внутри контейнера, где никакого демона нет. Документация называет два выхода и явно предпочитает
первый:

> «The docker socket must be available via a volume mount»
> «Testcontainers will automatically detect if it's inside a container and instead of 'localhost'
> will use the default gateway's IP.»
> «While Docker-in-Docker (DinD) is generally considered an instrument of last resort, it is
> necessary for some CI environments.»
>
> — Testcontainers docs, «Patterns for running tests inside a docker container»

Первый способ — пробросить сокет: контейнеры, которые поднимет Testcontainers, окажутся
не «внутри» задания, а **соседними** контейнерами на том же хосте. Второй — поднять отдельный демон
рядом (DinD); именно так сделано в `pipelines/gitlab/.gitlab-ci.yml`, где задание объявляет
`services: docker:27-dind` и `DOCKER_HOST`. «Instrument of last resort» — их формулировка, и она
про цену: отдельный демон требует привилегированного режима и не переиспользует кэш образов хоста.

*Случай 2: API достижим, но адреса не те.* Фраза «instead of 'localhost' will use the default
gateway's IP» описывает ровно ту ловушку, на которую наткнулся журнал модуля в прогоне 3, только с
другим инструментом: сборщик образов в отдельном контейнере писал кэш на `localhost:5001` и молча
писал его в себя, а не в реестр на хосте. Правило общее: **`localhost` внутри контейнера — это сам
контейнер**. Тест, который после старта контейнера с базой ходит на `localhost:5432`, работает на
ноутбуке и не работает в задании; адрес и порт надо спрашивать у Testcontainers, а не предполагать.

*Случай 3: за заданием остаётся мусор.* Задание прибили по таймауту, процесс JVM умер, поднятые им
контейнеры остались. На эфемерном исполнителе это никого не волнует — машина уходит целиком; на
долгоживущем агенте порты и память кончаются к концу недели. Для этого Testcontainers поднимает
служебный контейнер:

> «The resource reaper is responsible for container removal and automatic cleanup of dead containers
> at JVM shutdown»
> «Note that Testcontainers will continue doing the cleanup at JVM's shutdown, unless you `kill -9`
> your JVM process.»
> «If your environment already implements automatic cleanup of containers after the execution, but
> does not allow starting privileged containers, you can turn off the Ryuk container by setting
> `TESTCONTAINERS_RYUK_DISABLED` **environment variable** to `true`.»
>
> — Testcontainers docs, «Custom configuration»

Отсюда видно и когда `ryuk` действительно можно выключить, и когда это ошибка. Условие в цитате
составное: среда **уже** убирает за собой **и** не разрешает привилегированные контейнеры. Первая
половина выполняется на эфемерном исполнителе; на долгоживущем агенте выключение `ryuk` — это
отказ от единственной уборки, которая переживает `kill -9`.

**Правило.** Прежде чем чинить Testcontainers в конвейере, ответьте на три вопроса в этом порядке:
достижим ли API среды исполнения контейнеров из процесса тестов; какие адреса видит тест, если сам
он выполняется в контейнере; кто уберёт контейнеры, если задание убьют. Первый вопрос — про
конфигурацию исполнителя, второй — про код теста, третий — про тип исполнителя. Механика самой
сборки образа в контейнере (DinD против сборки без демона) — та же болезнь, но другая задача, она
в [`IMAGE_BUILD_AND_REGISTRY.md`](IMAGE_BUILD_AND_REGISTRY.md).

## 6. Гейт покрытия: почему порог — плохая метрика

**Задача.** В конвейер `payments` предлагают добавить гейт: сборка красная, если покрытие строк
ниже 80 %. Звучит разумно — что здесь не так?

**Наивное обоснование.** «Покрытие показывает, какая доля кода протестирована». Именно эта фраза и
неверна, причём буквально: покрытие показывает не «протестирована», а «исполнена».

> «A source line is considered executed when at least one instruction that is assigned to this line
> has been executed.»
>
> — JaCoCo docs, «Coverage Counters»

Слово «executed» тут единственное, и никакого требования проверить результат в определении нет.

**Где ломается — контрпример на две строки.** Возьмём метод `PaymentService.charge()` и напишем
такой тест:

```java
@Test
void charge() {
    service.charge(new Order("A-1", 100));   // ни одного assert
}
```

Метод исполнен целиком, все его строки засчитаны как покрытые, покрытие выросло. Проверено при этом
ноль: тест зелёный при любом возвращаемом значении и упадёт только на исключении. Порог 80 %
выполняется формально и без единой проверки поведения — а значит, гейт, который его сторожит,
измеряет не то, что собирался.

Вторая половина проблемы — что покрытие даже как метрика исполнения грубее, чем кажется:

> «JaCoCo also calculates branch coverage for all `if` and `switch` statements. This metric counts
> the total number of such branches in a method and determines the number of executed or missed
> branches.»
>
> — JaCoCo docs, «Coverage Counters»

Строка `if (amount > limit && account.isActive())` считается покрытой, если исполнена **хотя бы
одна** ведущая к ней инструкция. Покрытие ветвей — отдельный счётчик, и именно оно отвечает на
вопрос «а второй вариант условия кто-нибудь проверял». В отчётах чаще смотрят на первое число.

**Механизм — почему порог именно как гейт ведёт себя плохо.** Метрика становится целью, и дальше
работает известный эффект: способ достичь числа дешевле, чем способ достичь смысла. Написать тест
без проверок быстрее, чем разобраться, почему ветка не тестируется, и оба действия одинаково
двигают число вверх. Отдельно вредна асимметрия: порог наказывает того, кто добавил код, — и
надёжнее всего он останавливает не плохие изменения, а мелкие правки в давно нетронутом классе с
низким покрытием.

**Когда покрытие полезно — и это не гейт.** Как **диагностический инструмент** оно работает
отлично: отчёт показывает, какие ветки не исполняются ни одним тестом, и это точное, проверяемое
знание. Полезен и другой порог — не на абсолютную величину, а на **изменение**: «покрытие не должно
падать» ловит настоящий случай (добавили код без тестов), не требуя догонять исторический долг.

**Правило.** Покрытие — это карта того, что тесты **трогают**, а не того, что они **проверяют**.
Как карту его стоит читать на каждом пулл-реквесте; как гейт — только в форме «не падает», и
никогда как единственную проверку качества. Из чего вообще должен состоять гейт перед слиянием и
почему ненадёжный тест дороже низкого покрытия — в
[`BRANCHING_AND_CODE_FLOW.md` §7](../../engineering-process/theory/BRANCHING_AND_CODE_FLOW.md).

## 7. Воспроизводимая сборка

**Задача.** Артефакт `payments` потерялся: срок хранения в конвейере истёк, а на qa его надо
поставить снова. Решение очевидное — пересобрать из того же коммита. Получим ли мы тот же артефакт?

**Наивный ответ.** Разумеется: тот же исходный код, та же команда, та же версия JDK. Откуда взяться
разнице?

**Где ломается — прогон 2 журнала модуля.** Две сборки подряд одного и того же дерева исходников,
между ними `sleep 2`; команда `mvn -B -ntp clean package -DskipTests`, затем
`shasum -a 256 target/*.jar` (в выводе — первые 32 символа):

```
без project.build.outputTimestamp     сборка 1: 1935ad70b5bbad69b941ef55a505a8ea…
                                      сборка 2: 546701dcc3c1cad09f49e0833a21cb86…   → РАЗНЫЕ
с project.build.outputTimestamp       сборка 1: 9fc5925cf3e7c4b0f44b68fc3bc568a5…
                                      сборка 2: 9fc5925cf3e7c4b0f44b68fc3bc568a5…   → ОДИНАКОВЫ
```

Обратите внимание на то, что здесь **не менялось**: ни строки исходников, ни версия JDK, ни
команда, ни машина. Разница между первыми двумя строками — две секунды.

**Механизм.** Jar — это zip-архив, а формат zip хранит для каждой записи время её создания. По
умолчанию туда попадает момент упаковки, то есть текущее время сборки. Значит, jar является функцией
не только от входа, но и от часов: два прогона в разные секунды дают разные байты при полностью
одинаковом коде. Свойство `project.build.outputTimestamp` подменяет это значение фиксированной
датой — параметр, который его читает, документирован у плагина, собирающего архив:

> «Timestamp for reproducible output archive entries, either formatted as ISO 8601 extended offset
> date-time (e.g. in UTC such as '2011-12-03T10:15:30Z' or with an offset '2019-10-05T20:37:42+06:00'),
> or as an int representing seconds since the epoch (like SOURCE_DATE_EPOCH).»
>
> — Maven JAR Plugin docs, цель `jar:jar`, параметр `outputTimestamp`

В `pom.xml` модуля свойство выставлено явно (`pom.xml:32`), и комментарий рядом с ним говорит, что
в конвейере его переопределяют датой последнего коммита. Это и есть содержательная часть: значение
должно быть **функцией от входа**, а не константой на все времена. Дата коммита подходит идеально —
она меняется тогда и только тогда, когда меняется код.

**Что мы получаем — и это больше, чем аккуратность.**

> «A build is **reproducible** if given the same source code, build environment and build
> instructions, any party can recreate **bit-by-bit** identical copies of all specified artifacts.»
>
> — Maven docs, «Guide to Configuring for Reproducible Builds»

До этого свойства фразы «пересобрать из того же коммита» и «взять тот же артефакт» были **разными**
операциями с разным результатом, и это не философия — это две разные контрольные суммы в выводе
выше. После — они совпадают, и появляется проверяемое утверждение: «то, что работает на qa, собрано
вот из этого коммита», причём проверяется оно пересборкой и сравнением хэша, а не доверием к
конвейеру.

**Чего это не даёт.** Три ограничения, каждое стоит помнить.

*Первое.* Воспроизводимость не заменяет продвижение артефакта. Она делает пересборку **допустимой
запасной** дорогой, а не основной: собирать заново на каждом окружении по-прежнему не надо — уже
хотя бы потому, что это лишние минуты и лишний шанс, что среда сборки успела измениться.

*Второе.* Эфемерность исполнителя воспроизводимости не даёт — она гарантирует отсутствие следов
прошлого прогона и молчит про байты; это разобрано в
[`PIPELINE_MODEL.md` §5](PIPELINE_MODEL.md).

*Третье.* Одно свойство не делает воспроизводимой всю сборку. Оно закрывает время в записях
архива — самый частый источник расхождения, но не единственный: порядок файлов, абсолютные пути,
попавшие в манифест, генерация кода с временными метками ломают её точно так же. Проверка ровно
одна и она дешёвая — собрать дважды и сравнить хэш; именно так и получен вывод выше. Тот же принцип
для слоёв образа — в [`IMAGE_BUILD_AND_REGISTRY.md`](IMAGE_BUILD_AND_REGISTRY.md).

**Правило.** Свойство `project.build.outputTimestamp` со значением из даты коммита ставится один
раз и стоит копейки, а даёт способность ответить на вопрос «из чего это собрано» проверкой, а не
рассуждением. Ставьте его в новый проект сразу — задним числом оно добавляется в тот момент, когда
ответ уже срочно нужен.

## 8. Публикация в Nexus/Artifactory

**Задача.** У `payments` есть модуль `payments-api` — классы запросов и ответов, которые нужны
трём другим сервисам. Образ с ними не поделишься: образ запускают, а не подключают зависимостью.
Куда конвейер их кладёт?

**Наивное решение.** Пусть каждый потребитель собирает `payments` сам из исходников. Работает,
пока сервисов трое, и разваливается на четвёртом: у всех появляется своя копия чужого кода и своя
версия, а сборка потребителя начинает зависеть от того, что лежит в чужом репозитории **сейчас**.

**Механизм.** Публикация в менеджер артефактов — отдельная фаза жизненного цикла, у которой одна
задача:

> «The deploy plugin is primarily used during the deploy phase, to add your artifact(s) to a remote
> repository for sharing with other developers and projects.»
> «As a repository contains more than the artifacts (POMs, the metadata, MD5 and SHA1 hash
> files...), deploying means not only copying the artifacts, but making sure all this information
> is correctly updated.»
>
> — Maven Deploy Plugin docs

Вторая цитата объясняет, почему это не «положить файл на сервер»: репозиторий хранит ещё и `pom` с
описанием транзитивных зависимостей, и метаданные версий, и контрольные суммы. Nexus и Artifactory —
серверные реализации именно этой модели: содержимое адресуется координатой
`groupId:artifactId:version`, и сборка потребителя разрешает зависимости по ней, а не по чьей-то
рабочей директории.

**Почему это отдельный слой от реестра образов.** Разница не в технологии хранения, а в том, кто
потребитель и что является единицей:

| | Менеджер артефактов | Реестр образов |
|---|---|---|
| Что хранит | библиотеку — то, что **подключают** | образ — то, что **запускают** |
| Адресация | координата `groupId:artifactId:version` | тег и дайджест |
| Кто потребитель | сборка другого сервиса | среда исполнения (Kubernetes, Swarm) |
| Когда нужен | у вас есть код, общий для нескольких сервисов | у вас есть сервис, который надо запустить |

Отсюда практический вывод, который экономит время: сервису, не отдающему наружу ни одной
библиотеки, `mvn deploy` не нужен вовсе — его артефакт целиком уезжает внутрь образа. Публикация в
Nexus «на всякий случай» добавляет к конвейеру этап, версионную дисциплину и хранилище, которое
надо чистить, не давая взамен ничего.

**Правило.** `mvn deploy` в конвейере оправдан ровно тогда, когда у артефакта есть потребитель,
который **подключает** его как зависимость. Если такой потребитель один и это вы сами, у вас не
библиотека, а преждевременно вынесенный модуль. И одно требование к версии, следующее из §3:
публиковать наружу можно только неизменяемую версию — иначе потребитель на пустом кэше и потребитель
на прогретом соберутся против разного кода.

## 9. Чем модель Gradle отличается от Maven для CI

**Задача.** Соседняя команда собирает свой сервис на Gradle и утверждает, что её конвейер быстрее
не из-за железа. Что именно у них устроено иначе — при том, что задача та же: скомпилировать,
прогнать тесты, упаковать?

**Наивный ответ.** «Другой синтаксис сборочного файла». Синтаксис к длительности конвейера
отношения не имеет. Различие — в единице выполнения и в том, что считается «уже сделанным».

**Механизм: Maven исполняет фазы, Gradle исполняет граф задач.** У Maven единица — фаза жизненного
цикла, и `mvn package` проходит их подряд от начала. Экономия в конвейере возможна ровно одна и
разобрана в §2: не скачивать заново зависимости. Сама компиляция и упаковка выполняются каждый раз.

У Gradle единица — задача с объявленными входами и выходами, и это меняет вопрос:

> «As part of incremental build, Gradle tests whether any of the task inputs or outputs has changed
> since the last build. If they haven't, Gradle can consider the task up to date and therefore skip
> executing its actions.»
> «When you run a task and the task is marked with `UP-TO-DATE` in the console output, this means
> incremental build is at work.»
>
> — Gradle docs, «Incremental Build»

Обратите внимание на «since the last build»: сравнение идёт с **предыдущей сборкой на этой машине**.
На ноутбуке это выигрыш; на эфемерном исполнителе предыдущей сборки не было никогда, и
инкрементальность не даёт ничего. Поэтому сама по себе она к конвейеру отношения не имеет — и вот
второй механизм, который имеет:

> «The build cache works by storing (locally or remotely) build outputs and allowing builds to fetch
> these outputs from the cache when it is determined that inputs have not changed, avoiding the
> expensive work of regenerating them.»
> «When using a shared build cache for task output caching this even works across developer machines
> and build agents.»
> «We have focused on the use case where users have an organization-wide remote build cache that is
> populated regularly by continuous integration builds.»
>
> — Gradle docs, «Build Cache»

Разница с кэшем `~/.m2` принципиальная, и её стоит проговорить, потому что слово «кэш» одинаковое.
Кэш локального репозитория Maven хранит **входы** сборки — чужие библиотеки, которые не надо
скачивать заново. Кэш сборки Gradle хранит **выходы** — результат выполнения задачи: если входы те
же, результат берётся готовым и задача не выполняется вовсе. Второе сильнее: не переиспользовать
загрузку, а не делать работу.

**Где это ломается — и почему не бесплатно.** Механизм держится на том, что входы задачи объявлены
полно и точно. Задача, читающая что-то, чего нет в списке входов — переменную окружения, текущее
время, файл вне проекта, — будет признана актуальной там, где результат на самом деле изменился.
Расплата ровно такая же, как у неверного ключа кэша
([`RUNNERS_AND_EXECUTION.md` §4](RUNNERS_AND_EXECUTION.md)): не медленно, а неверно. Общий на всю
компанию кэш выходов эту цену умножает — ошибочная запись достаётся всем.

**Правило и границы применимости.**

| Что должно быть правдой | Что из этого следует |
|---|---|
| Сборка идёт минуты, модулей много, между прогонами меняется малая часть | кэш выходов Gradle окупается: платите за инфраструктуру кэша, экономите работу |
| Один модуль, сборка секунды, зависимости — главная статья расходов | достаточно кэша локального репозитория; модель Maven ничем не хуже |
| Тесты зависят от внешнего состояния, входы задач объявлены не полностью | общий кэш выходов опасен: включать после того, как это починено, а не до |

И оговорка, снимающая ложное впечатление: выбор системы сборки не измеряется скоростью конвейера.
Gradle даёт более сильный механизм экономии и вместе с ним более сильный способ получить неверный
результат. Maven даёт меньше экономии и меньше способов ошибиться. Это размен, а не рейтинг.

## 10. Шпаргалка

| Что спрашивают | Одна фраза |
|---|---|
| Зачем `-B -ntp` | У задания нет человека: некому отвечать на вопросы и негде рисовать прогресс |
| Сколько экономит кэш `~/.m2` | 25,97 с → 1,53 с на `payments` (≈17×); абсолютные числа зависят от числа зависимостей, отношение — нет |
| Когда кэш `~/.m2` вредит | Есть SNAPSHOT-зависимости: политика обновления «раз в сутки» восстанавливается вместе с кэшем |
| Почему SNAPSHOT нельзя продвигать | Изменяемый указатель: «snapshot artifacts can and do change over time» |
| Граница SNAPSHOT | До сборки допустим, после — нет: наружу уходит только неизменяемый идентификатор |
| Зачем failsafe | Быстрый гейт падает первым; failsafe не роняет сборку в `integration-test`, чтобы отработала уборка в `post-integration-test` |
| Как делятся тесты | По имени класса: `*Test` → surefire, `*IT` → failsafe |
| Что нужно Testcontainers | Достижимый API среды исполнения контейнеров; проброшенный сокет предпочтительнее DinD |
| Зачем `ryuk` | Убирает контейнеры после смерти JVM; выключать только там, где среда убирает сама |
| Порог покрытия | Измеряет исполнение строк, а не проверку поведения: тест без `assert` поднимает число |
| Как чинить невоспроизводимый jar | `project.build.outputTimestamp` = дата коммита; проверка — собрать дважды и сравнить `sha256` |
| Когда нужен `mvn deploy` | Только если у артефакта есть потребитель, подключающий его зависимостью |
| Модель Gradle против Maven | Gradle кэширует **выходы** задач (в том числе удалённо), Maven — только **входы** сборки |

### Формулировки для собеседования

- «Кэш локального репозитория экономит на `payments` примерно семнадцатикратно, но это сборка с
  двумя стартерами — честный ответ всегда во столько-то раз на такой-то сборке, а не в секундах.»
- «SNAPSHOT — не версия, а изменяемый указатель. Ровно та же ошибка, что адресовать образ тегом:
  имя то же, содержимое другое, и никакой ошибки при подмене не возникает.»
- «Failsafe существует не ради красоты отчётов: Surefire роняет сборку прямо в фазе
  `integration-test`, и до уборки окружения дело не доходит.»
- «Покрытие — карта того, что тесты трогают, а не того, что они проверяют. Как гейт годится только
  в форме "не падает".»
- «Без `project.build.outputTimestamp` фразы "пересобрать из того же коммита" и "взять тот же
  артефакт" — разные операции с разными контрольными суммами.»
