# Terraform в конвейере: почему `apply` — не такой же шаг, как раскатка

> **Какую проблему решает.** Шаг раскатки и шаг `terraform apply` выглядят в конвейере одинаково, но
> худший исход первого — нерабочая версия сервиса, а второго — удалённая база данных.
> **Кому это надо.** Тому, кто должен объяснить, кто и где нажимает `apply`, и ответить, что будет,
> если два конвейера инфраструктуры запустятся параллельно.
> **Когда НЕ надо.** Если ваш Terraform создаёт три файла и ничего с состоянием, вся церемония —
> накладные расходы; и ничто здесь не делает `apply` безопасным, разнесение по заданиям лишь сужает
> класс отказов «применилось не то, что смотрели».

**Границы.** Состояние, удалённый `backend` и расхождение (drift) —
[`CLOUD.md` §12](../../infrastructure/theory/CLOUD.md); права токена —
[`SUPPLY_CHAIN_SECURITY.md` §2, §4, §6](SUPPLY_CHAIN_SECURITY.md). Выводы команд сняты на Terraform
v1.16.0, macOS 15, на учебной конфигурации с локальным провайдером.

---

## 1. Почему `apply` из конвейера страшнее раскатки приложения

Откат есть у обоих шагов, но разница не в скорости, а в том, **что физически остаётся после отката**.

| Что откатываем | Где лежит прежнее состояние | Цена |
|---|---|---|
| Раскатка приложения | образ в реестре по дайджесту — неизменяем | 29,9 с в Swarm ([`DEPLOY_K8S_AND_SWARM.md` §4](DEPLOY_K8S_AND_SWARM.md)) |
| `apply`, меняющий ресурс на месте | прежнее значение атрибута в конфигурации | как у прямого применения |
| `apply`, пересоздающий ресурс | **нигде**: данные исчезли вместе с объектом | невосстановимо |

Третья строка появляется не по вашей воле: Terraform сам выбирает между update in-place и «destroy
and re-create resources … which cannot be updated in-place **due to remote API limitations**» —
решает удалённый API провайдера. Поэтому правка одной строки может означать «удалить объект и
создать заново», а откат воссоздаст ресурс с тем же именем и пустым: **обратимо описание, а не
содержимое**. Вторая асимметрия — права: шагу раскатки хватает пространства имён, `apply` создаёт и
удаляет ресурсы в аккаунте ([`SUPPLY_CHAIN_SECURITY.md` §4](SUPPLY_CHAIN_SECURITY.md)).

**Правило.** Спрашивайте не «как быстро шаг откатывается», а «что останется после отката»;
`lifecycle { prevent_destroy = true }` — «Terraform rejects plans that would destroy the
infrastructure object» — отказывает при построении плана, то есть проверка стоит в коде.

## 2. `plan` как артефакт ревью

Ревьюер читает дифф конфигурации, после слияния задание выполняет `apply -auto-approve`. Ломается это
дважды. Первое: результат `apply` — функция трёх входов (конфигурация, переменные, фактическое
состояние), а ревьюер видел первый; несохранённый план сам это и печатает — «Terraform can't
guarantee to take exactly these actions if you run "terraform apply" now». Второе: задания не делят
состояние ([`PIPELINE_MODEL.md` §2](PIPELINE_MODEL.md)) — нет артефакта, значит второе задание строит
свой план, а не применяет чужой:

```
$ terraform plan  -var-file=dev.tfvars       →  + manifest_path = "./out/dev.json"
$ terraform apply -var-file=staging.tfvars   →  manifest_path = "./out/staging.json"
$ ls out/                                    →  staging.json
```

**Ревьюер утвердил план на dev — применился staging**, без ошибки и без отличия в коде возврата: план
считается заново по входам момента применения, а роль `-var-file` в конвейере играет что угодно —
переменная окружения, значение из хранилища секретов, ветка ручного запуска.

```yaml
plan:  { script: [terraform plan -out=tfplan -var-file=$ENV.tfvars],
         artifacts: { paths: [tfplan] } }   # артефакт, не кэш: нет плана — apply не стартует
apply: { needs: [plan], when: manual,       # ворота здесь, а не внутри terraform
         script: [terraform apply tfplan] } # ни -var-file, ни -auto-approve: вход один
```

Безопасным план делает одноразовость: повторное применение того же файла даёт `Error: Saved plan is
stale … the state was changed by another operation`. План — не сценарий, а утверждение «при **вот
этом** состоянии сделать вот это», поэтому одобренное применяется байт в байт либо не применяется
вовсе. Двух вещей он не даёт: гарантии, что мир не изменился между `plan` и `apply`, и секретности —
значения «will be saved in cleartext in the plan file … **even if obscured in Terraform's terminal
output**».

**Правило.** Разносить `plan` и `apply` по заданиям имеет смысл только с `-out`: без него одобряют
один текст, применяется другой.

## 3. Конвейер приложения против конвейера инфраструктуры

Соблазн — один конвейер на всё, но не совпадают две величины: приложение меняется на каждый push
(допущение модуля — 24 прогона в день, [`PIPELINE_MODEL.md` §7](PIPELINE_MODEL.md)), инфраструктура —
единицы раз в месяц, и `apply` стоит за ручными воротами
([`SUPPLY_CHAIN_SECURITY.md` §6](SUPPLY_CHAIN_SECURITY.md)). В одном графе это значит либо `plan` на
каждом из 24 прогонов с правами читать состояние, либо пропуск по условию — и условие и есть граница,
записанная неявно; а правка текста либо ждёт человека с кнопкой, либо ворота ослабляют для всех.

Разделять надо не файлы, а **триггер и права токена**: два конвейера в одном репозитории — по
каталогу с кодом и по каталогу с конфигурацией
([`PIPELINE_ECONOMICS.md` §6](PIPELINE_ECONOMICS.md)), и первому не нужен доступ в облако, а второму
— к реестру образов. То же говорит направление зависимости: приложению нужна база, чтобы
запуститься, базе приложение — нет.

**Правило.** Один конвейер законен, только когда обе величины совпали: так бывает у окружений,
живущих вместе с пулл-реквестом
([`ENVIRONMENTS_AND_PROMOTION.md` §5](ENVIRONMENTS_AND_PROMOTION.md)).

## 4. Окружения: workspaces против отдельных директорий

Три окружения с почти одинаковой конфигурацией раскладывают в один каталог и три `workspace` — это
буквально конструкция из §2: окружение определяют два изменяемых входа, а конфигурация физически
одна, так что ошибка не поймается ничем. Документация прямо говорит, что «CLI workspaces within a
working directory use the same backend, so they are **not a suitable isolation mechanism**»: один
`backend` — одни креденшелы, поэтому задание, способное применить в dev, **технически способно
применить в staging**. Отдельные директории дают цепочку «своя директория → свой `backend` → своя
роль в облаке» ценой дублирования корневой конфигурации, снижаемого выносом общего в модуль.

| Что должно быть правдой | Что из этого следует |
|---|---|
| Окружения различаются кругом лиц с доступом | Отдельные директории: разные `backend` — разные креденшелы |
| Экземпляры одинаковы по правам и создаются пачками | Workspaces: нужна изоляция состояния, не прав |
| Ошибочный `apply` не в то окружение должен быть **невозможен** | Отдельные директории |
| Нужно быстро завести четвёртое одинаковое окружение | Workspaces: дешевле; но проверьте первую строку |

**Правило.** `workspace` изолирует состояние и ничего больше; появилась граница по правам —
разделяйте конфигурации, а не имена `workspace`.

## 5. Блокировка состояния и два конвейера, стартовавших одновременно

Два пулл-реквеста слиты с разницей в двадцать секунд, оба конвейера дошли до `apply`. Чтение и запись
состояния разнесены на всю длительность применения: оба прочитали `S`, первый записал `S + A`,
второй — `S + B` **поверх**. Ресурс `A` существует и оплачивается, но в состоянии его нет, и
следующий `plan` предложит создать его заново — проявится это через несколько дней.

Блокировка превращает «прочитал — применил — записал» в критическую секцию: «state locking happens
automatically on all operations that could write state», а при неудаче Terraform не продолжает. Это
свойство **`backend`**, не самого Terraform
([`CLOUD.md` §12](../../infrastructure/theory/CLOUD.md)); отключающий флаг `-lock=false` документация
сопровождает прямым «we do not recommend it».

**Чего блокировка не делает.** Она **сериализует**, но не **согласовывает**: два конвейера с
расходящимися намерениями применятся один за другим, и выиграет последний. Второй слой даёт план из
§2 — построенный до применения первого, он отвергается как stale. **Блокировка защищает файл
состояния, `-out` защищает смысл изменения.** Atlantis добавляет третий уровень, держа директорию
занятой «until the pull request is merged or closed».

**Правило.** Удалённый `backend` с блокировкой — условие, при котором `apply` вообще можно запускать
из конвейера: конвейер по построению умеет запускать себя параллельно сам с собой.

## 6. Задание обнаружения расхождения

Ночью дежурный расширил через консоль правило доступа к базе; через неделю кто-то слил изменение
тегов, конвейер применил — и правило исчезло. Конфигурация источник истины **в момент применения**;
плохо не то, что Terraform привёл ресурс к конфигурации (это §1), а то, что **момент, когда это
произойдёт, никем не выбран**. Детектор — задание по расписанию, строящее план и ничего не
применяющее; о непустом плане Terraform сообщает кодом возврата, а не текстом:

```bash
terraform plan -detailed-exitcode -var-file=staging.tfvars   # 0 — нет изменений,
                                                             # 1 — ошибка, 2 — расхождение
```

| Что показывает план | Что произошло | Что делать |
|---|---|---|
| Изменение атрибута, которого нет в диффе кода | Кто-то поправил руками | Узаконить правку в коде или снести её |
| Изменения ровно те, что в свежем коммите `main` | Слито, но не применено | Применить обычным порядком через §2 |
| Ресурс изменился «сам» | Провайдер поменял представление, автомасштабирование сдвинуло узлы | Исключить поле из сравнения |

Для первой строки есть `-refresh-only` — план, «whose goal is only to update the Terraform state … to
match changes made to remote objects outside of Terraform», и документация прямо называет сценарий:
«while responding to an incident». Применять непустой план по расписанию нельзя: он может содержать
удаляющее действие, а это `apply` без ревьюера и ночью — в доставке вытягиванием у того же детектора
исполнитель есть ([`DELIVERY_PUSH_VS_PULL.md` §2](DELIVERY_PUSH_VS_PULL.md)) именно потому, что там
объект обратим.

**Правило.** Обнаружение расхождения — детектор, а не исполнитель: его выход идёт туда же, куда
инциденты.

## 7. Кто владеет `apply`

За вопросом «кто нажимает `apply`» стоят три других: где фиксируется факт применения, откуда берутся
права и чем гарантировано, что применилось ровно одобренное. «Разработчик с ноутбука» проваливает все
три — следа нет, совпадение с Git не гарантировано, права это долгоживущий ключ в домашнем каталоге
([`SUPPLY_CHAIN_SECURITY.md` §1](SUPPLY_CHAIN_SECURITY.md)) — по одной общей причине: применение
произошло там, где его никто не наблюдает. Моделей три, и две встраивают правило §2 в инструмент.

| Что должно быть правдой | Что из этого следует |
|---|---|
| Конвейер есть, окружения защищены, OIDC настроен | Ручные ворота на `apply`: права на время задания ([`SUPPLY_CHAIN_SECURITY.md` §2, §6](SUPPLY_CHAIN_SECURITY.md)), но план читают в логе и после слияния |
| Ревьюер обязан видеть план **до** слияния | Atlantis: «running `terraform apply plan.tfplan`, any Terraform options that would change the `plan` are ignored» |
| Нужны политики, единая очередь и история по всем командам | HCP Terraform: «always plans first, then uses that plan's output for the apply», workspace «maintains its own queue of runs» |
| Три файла, правка раз в квартал, команда из двух человек | Ручной `apply`, но не с долгоживущим ключом |

**Правило.** «Кто нажимает `apply`» — не про человека, а про место, умеющее ответить: кто одобрил, что
применилось и откуда права. Правильный ли план — не гарантирует ни одна модель.

## 8. Ansible: настройка машины против выделения ресурсов

«Terraform декларативный, Ansible императивный» — бесполезное разделение: плейбук тоже описывает
желаемое состояние. Граница в том, что является объектом и **помнится ли он**. У Terraform объект —
ресурс у API провайдера, и состояние помнит, какие объекты он создал; отсюда действие, без памяти
невозможное: удалить то, что исчезло из конфигурации. У Ansible объект — машина из инвентаря,
состояния нет, каждый прогон доводит фактическое положение дел до описанного («Ansible does not
change anything, even if the playbook runs multiple times»), и платой идёт то, чего без памяти не
бывает: **убрав из плейбука задачу «поставить пакет», вы не удалите пакет**.

| Свойство | Terraform | Ansible |
|---|---|---|
| Что означает «применить» | Привести набор ресурсов к конфигурации | Привести перечисленные машины к описанию |
| Нужна ли блокировка состояния (§5) | Да: состояние общее и перезаписываемое | Нет общего состояния; конкурируют за машину |
| Что происходит с удалённой из кода строкой | Ресурс удаляется | Ничего: сделанное остаётся |
| Что подаётся на вход | Переменные и состояние | Инвентарь: список хостов |

Отсюда связка из двух заданий: `terraform apply` создаёт машины и отдаёт адреса выводом, задание
Ansible получает вывод артефактом и превращает в инвентарь — зависимость по данным, не по политике.

**Правило.** Спрашивайте не «какой инструмент лучше», а «должен ли кто-то помнить, что объект был
создан». На контейнерной платформе слоя «настроить машину» нет вовсе: содержимое описано в
`Dockerfile` ([`IMAGE_BUILD_AND_REGISTRY.md` §4](IMAGE_BUILD_AND_REGISTRY.md)).

## Шпаргалка

| Симптом | Что на самом деле сломано |
|---|---|
| «Утвердили план на dev, применилось в staging» | `apply` без `-out`: план считается заново на входах момента применения (§2) |
| «Второй `apply` того же файла отвергнут: Saved plan is stale» | Так и задумано: план — утверждение о состоянии, одноразовое (§2, §5) |
| «`plan` предлагает создать то, что уже есть» | Состояние перезаписано параллельным применением — не было блокировки (§5) |
| «Правило, поставленное ночью руками, исчезло через неделю» | Штатное приведение к конфигурации; не было задания обнаружения расхождения (§6) |
| «Ошиблись переменной — тронули не то окружение» | Одна конфигурация на все окружения: `workspace` изолирует состояние, не права (§4) |
| «Правка кода ждёт человека с кнопкой» | Конвейер приложения слит с конвейером инфраструктуры (§3) |

**Как разложить окружения (§4).** Различаются кругом лиц с доступом? → отдельные директории и
`backend`. Экземпляры одинаковы и создаются пачками? → `workspace`.

**Кто применяет (§7).** План нужен до слияния? → Atlantis. Есть конвейер с защищёнными окружениями и
OIDC? → ручные ворота. Нужны политики и общая очередь? → управляемый сервис.

### Формулировки для собеседования

- «`apply` необратим не по времени отката, а физически: откат конфигурации воссоздаёт описание
  ресурса, но не его содержимое».
- «Сохранённый план — не сценарий, а утверждение «при вот этом состоянии сделать вот это»; поэтому он
  одноразовый, и поэтому его можно утверждать на ревью».
- «Блокировка защищает файл состояния, `-out` защищает смысл изменения; нужны оба».
- «`workspace` изолирует состояние и ничего больше — общий `backend` означает общие права».
- «Задание обнаружения расхождения — детектор, а не исполнитель».
