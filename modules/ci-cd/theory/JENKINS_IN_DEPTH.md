# Jenkins изнутри: Declarative, Scripted и цена долгоживущего агента

> **Какую проблему решает.** `Jenkinsfile` выглядит как декларативный список стадий, но неочевидно, где кончается описание и начинается программа на Groovy; общий для тридцати сервисов кусок конвейера либо копируют в тридцать файлов, либо выносят в код, который исполняется на всех конвейерах компании сразу; агент, который не пересоздаётся месяцами, превращает зелёную сборку в доказательство того, что она работает только на этой машине.
> **Кому это надо.** Тому, кто пишет `Jenkinsfile` и выбирает между Declarative и Scripted не по мощности, а по тому, известна ли структура конвейера до запуска, и тому, кто отвечает за парк агентов и получает необъяснимые падения через раз.
> **Когда НЕ надо.** Сравнение Jenkins с GitHub Actions и GitLab CI и критерий выбора между инструментами — не здесь, это [`TOOLS_COMPARED.md`](TOOLS_COMPARED.md).

**Границы.** Модель графа заданий, три модели композиции и сквозной пример `payments` — [`TOOLS_COMPARED.md`](TOOLS_COMPARED.md), файл-близнец. Исполнители и три класса расхождения «локально работает, в CI нет» — [`RUNNERS.md`](RUNNERS.md). Передача файла между заданиями — [`PIPELINE_CACHE_AND_CONCURRENCY.md` §2](PIPELINE_CACHE_AND_CONCURRENCY.md); эфемерность исполнителя как источник гарантий — [`PIPELINE_GUARANTEES.md` §1](PIPELINE_GUARANTEES.md).

## 1. Declarative против Scripted: известна ли структура до запуска

Требование: прогонять интеграционные тесты на трёх версиях PostgreSQL, а список версий брать не из файла, а из ответа внутреннего сервиса, который команда платформы меняет сама. Наивный ответ «добавить цикл по списку и внутри него стадию» ломается: в Declarative Pipeline нет места для такого цикла.

> «Declarative Pipeline presents a more simplified and opinionated syntax on top of the Pipeline sub-systems.» «All valid Declarative Pipelines must be enclosed within a `pipeline` block.» «Declarative limits what is available to the user with a more strict and pre-defined structure.»

«Limits» здесь описательное, а не оценочное: `stages` содержит `stage`, `stage` содержит `steps`, список стадий записан в файле буквально, и стадию, которой в тексте нет, породить нечем. Второй режим того же движка это ограничение снимает:

> «Scripted Pipeline is effectively a general-purpose DSL built with Groovy.» «Scripted Pipeline is serially executed from the top of a `Jenkinsfile` downwards, like most traditional scripts in Groovy.» «Scripted provides very few limits, insofar that the only limits on structure and syntax tend to be defined by Groovy itself.»

«Serially executed from the top downwards» — ключевое отличие, и оно не про синтаксис. Declarative — **описание**: движок знает состав конвейера до первой выполненной команды, отсюда валидация файла, отображение стадий в интерфейсе и блок `post`, способный выполниться после падения. Scripted — **программа**: конвейер строится по ходу исполнения, и стадии, которые породит цикл, до запуска не существуют.

Для точечных вычислений в Declarative есть шов — блок `script`, например чтобы положить результат шага в переменную конвейера:

```groovy
script {
    env.DIGEST = sh(script: '...imagetools inspect... | awk ...', returnStdout: true).trim()
}
```

Критерий выбора — не «что мощнее», а известна ли структура конвейера до запуска:

| Что должно быть правдой | Что брать |
|---|---|
| Список стадий фиксирован; нужна валидация файла и понятная картинка в интерфейсе | Declarative |
| Нужно вычислить значение и передать его дальше | Declarative + точечный блок `script` |
| Число и состав стадий определяются данными, доступными только в момент запуска | Scripted |

Начинают с Declarative, переходят на `script` там, где упёрлись, и уходят в Scripted, только когда структура перестала быть известной заранее: «напишем сразу на Groovy, так гибче» заканчивается конвейером, который кроме автора никто не читает.

**Чего Declarative не делает.** Он не запрещает Groovy — он ограничивает место, где тот разрешён. Разница между «`Jenkinsfile` на Declarative» и «на Declarative, у которого каждая стадия состоит из одного блока `script`» — только в самообмане: второй давно Scripted.

## 2. Shared library: как выносят общую логику

Общая для тридцати сервисов компании логика — собрать образ, посчитать дайджест, приложить SBOM, отправить в реестр ([`TOOLS_COMPARED.md` §2](TOOLS_COMPARED.md)) — в Jenkins не решается готовым компонентом: маркетплейса нет, а плагин под вашу внутреннюю схему тегирования никто не написал. Скопировать блок `stage('image')` в тридцать `Jenkinsfile` — значит через полгода, когда сменится адрес реестра, разослать тридцать пулл-реквестов, из которых доедут двадцать восемь.

> «As Pipeline is adopted for more and more projects in an organization, common patterns are likely to emerge. Oftentimes it is useful to share parts of Pipelines between various projects to reduce redundancies and keep code "DRY".» «Pipeline has support for creating "Shared Libraries" which can be defined in external source control repositories and loaded into existing Pipelines.»

После этого `Jenkinsfile` сервиса содержит не двадцать строк, а одну — вызов шага из библиотеки; двадцать строк живут в одном месте, версионируются в Git и правятся один раз. Shared library — не особенность Jenkins, а его ответ на ту же потребность, которую два других инструмента закрывают своими средствами:

| Инструмент | Чем выносят общую логику | Что при этом переиспользуется |
|---|---|---|
| GitHub Actions | своё или чужое действие; переиспользуемый конвейер целиком | код компонента |
| GitLab CI | `include` из другого файла или репозитория | текст конфигурации |
| Jenkins | shared library | ваш Groovy-код |

Столбец «что переиспользуется» объясняет разницу в ощущениях. Конфигурация не умеет ветвиться и считать — зато её видно целиком. Код умеет всё — зато конвейер сервиса становится вызовом функции, и чтобы понять, что он делает, надо открыть другой репозиторий.

Заводить shared library имеет смысл ровно тогда, когда один и тот же кусок конвейера уже скопирован в третий репозиторий: два — совпадение, три — общая логика. Оговорка, которую проще принять сразу: библиотека — это код, исполняемый на всех конвейерах компании, и её изменение раскатывается на тридцать сервисов мгновенно. Поэтому подключают её по имени ветки или тега, а не «последнюю» — ровно по той же причине, по которой не подключают чужое действие подвижной меткой ([`TOOLS_COMPARED.md` §4](TOOLS_COMPARED.md)).

## 3. Чем платит долгоживущий агент

Классический Jenkins-агент не эфемерный, и на первый взгляд это к лучшему: локальный репозиторий Maven прогрет, слои образа на месте, `git fetch` тянет дельту вместо полного клона. Ускорение реально — и оно же ломает три вещи, которые эфемерность ([`PIPELINE_GUARANTEES.md` §1](PIPELINE_GUARANTEES.md)) давала бесплатно.

*Первое: зелёная сборка перестаёт быть доказательством.* На эфемерной машине зелёный прогон доказывает, что сборка не зависит ни от чего, поставленного руками. На агенте, живущем шестой месяц, он доказывает только то, что она работает **на этом агенте**. Классическая форма — не объявленный в конфигурации инструмент: `docker buildx`, `helm`, нужная минорная версия JDK, — их поставил дежурный полгода назад, чтобы починить конвейер ночью. Всё зелёное — до дня, когда агент пересоздают.

*Второе: агенты расходятся между собой.* Jenkins документирует агент как машину, а не как одноразовую сущность: «An agent is typically a machine, or container, which connects to a Jenkins controller and executes tasks when directed by the controller». Пять агентов с меткой `linux && docker` — это пять историй установок: задание попадает на любой из них, сборка падает через раз, а честный ответ на «что изменилось» — «ничего, просто задание поехало на другой агент». Диагностика по тем же трём классам, что для «локально работает, в CI нет» ([`RUNNERS.md` §3](RUNNERS.md)), только состояние здесь копится не в образе исполнителя, а вручную.

*Третье: рабочая директория переживает сборку.* Отсюда `cleanWs()` в `post { always { … } }` — на эфемерном исполнителе такой строки не бывает, чистить нечего. Пока директория не почищена, `target/` остаётся с прошлого прогона, и `mvn package` без `clean` может собрать jar из классов, которых в текущем коммите уже нет.

*И отдельно — поверхность атаки.* Секрет, попавший на диск агента, остаётся там и виден следующему заданию, в том числе задания другой команды; на эфемерном исполнителе такой передачи нет вовсе — машина уходит вместе с секретом ([`PIPELINE_GUARANTEES.md` §1](PIPELINE_GUARANTEES.md)).

**Правило.** Долгоживущий агент — это размен «сборка не зависит от истории машины» на «сборка быстрее». Он бывает оправдан (большой кэш, дорогое железо, лицензия) при одном условии: агент должен создаваться из описания, а не настраиваться руками. Вопрос к такому парку не «что стоит на агенте», а «сколько времени займёт собрать этот агент с нуля» — нет ответа, значит, это не парк агентов, а несколько уникальных машин.

## 4. Шпаргалка

| Вопрос | Ответ одной строкой |
|---|---|
| Критерий Declarative или Scripted | структура известна до запуска → Declarative; зависит от данных, доступных только в момент запуска → Scripted |
| Шов для вычислений в Declarative | блок `script` |
| Когда заводить shared library | кусок конвейера уже скопирован в третий репозиторий: два — совпадение, три — общая логика |
| Что переиспользует shared library | ваш Groovy-код, а не конфигурацию (GitLab) и не чужой компонент (Actions) |
| Почему агент — «machine», а не сущность | пять агентов с одной меткой — пять разных историй установки |
| Первое, чем платит долгоживущий агент | зелёная сборка доказывает работу только на этом агенте |
| Что снимает риск долгоживущего агента | агент создаётся из описания, а не настраивается руками |

### Формулировки для собеседования

- «Declarative и Scripted — не два уровня мощности одного языка, а ответ на вопрос, известна ли структура конвейера до запуска; шов между ними — блок `script`.»
- «Shared library — это код, который выполняется на всех конвейерах компании сразу; подключать его "последней" версией так же опасно, как чужое действие подвижной меткой.»
- «Долгоживущий агент меняет "сборка не зависит от истории машины" на скорость: зелёный конвейер доказывает не отсутствие скрытых зависимостей, а то, что агент уже успел их накопить.»
