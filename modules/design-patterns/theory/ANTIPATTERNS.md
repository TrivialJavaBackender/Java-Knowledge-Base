# Design Patterns — Антипаттерны и code smells

Паттерны отвечают на вопрос «как правильно», антипаттерны — «как повторяют одну и ту же
ошибку». Антипаттерн — это устойчивое, на первый взгляд разумное, но систематически вредное
решение типовой проблемы; запах кода (code smell) — поверхностный симптом, намекающий на
более глубокий изъян дизайна. На собеседовании ценится умение назвать симптом, объяснить,
чем он вреден, и указать конкретный рефакторинг или паттерн-лекарство.

## Запах кода против антипаттерна

- **Запах кода (code smell)** — локальный признак: длинный метод, дублирование, длинный
  список параметров. Сам по себе не баг, но повод присмотреться.
- **Антипаттерн** — уже принятое ошибочное архитектурное решение (God Object, анемичная
  модель). Лечится не косметикой, а перепроектированием.
- **Рефакторинг** — дисциплинированное изменение структуры без изменения поведения; мост
  от «плохо» к «хорошо». Каждый запах имеет каноническое лечение по Фаулеру.

Связь запахов с принципами проектирования (нарушение SRP → большой класс, нарушение OCP →
расходящиеся изменения, нарушение LSP → отказ от наследства) канонично раскрыта в модуле
software-engineering: [SOLID_OOP.md](../../software-engineering/theory/SOLID_OOP.md).

## Over-engineering: «паттерн ради паттерна» (patternitis)

Критерий уместности паттерна введён в [INTRO.md](INTRO.md) («Когда паттерн уместен»); здесь —
разбор обратной крайности. **Избыточное проектирование (over-engineering)**, оно же
«паттерномания» (patternitis) — введение косвенности без реальной оси изменчивости.

- **Симптом.** Интерфейс с единственной реализацией, которая никогда не поменяется;
  «фабрика фабрик»; абстракция, добавленная «на будущее»; конфигурируемость, которой никто
  не пользуется.
- **Почему плохо.** Каждый лишний уровень косвенности — это налог на чтение: чтобы понять
  один вызов, приходится прыгать через интерфейсы и обёртки. Гибкость, за которую заплачено,
  не окупается, а сложность реальна.
- **Как лечить.** YAGNI («вам это не понадобится»), KISS, DRY и **правило трёх** — обобщать
  после третьего повторения, а не первого. Убрать абстракцию с одной реализацией (обратный
  рефакторинг «Встраивание класса», Inline Class), вернуть прямой вызов.

```java
// Плохо: три уровня косвенности ради создания одной строки
new GreetingFactoryProvider()
    .getFactory("en")
    .createGreetingBuilder()
    .withName("Bob").build();

// Хорошо: столько косвенности, сколько требует задача
String greeting = "Hello, Bob";
```

Родственный антипаттерн — **golden hammer (золотой молоток)**: «у кого молоток, тому всё
кажется гвоздём». Один любимый инструмент (или паттерн) применяют ко всем задачам подряд.
Лекарство то же — выбирать решение по проблеме, а не по привычке.

## OOP- и дизайн-антипаттерны

### God Object / God Class (божественный объект)

- **Симптом.** Один класс на тысячи строк знает и делает всё: загрузку, валидацию, расчёт,
  сохранение, форматирование. Остальные классы — анемичные держатели данных вокруг него.
- **Почему плохо.** Нарушает SRP: у класса десятки причин для изменения, он становится узким
  местом слияний, его невозможно протестировать или переиспользовать по частям.
- **Как лечить.** «Выделение класса» (Extract Class) по осям ответственности; вынести
  вариативное поведение в Strategy ([BEHAVIORAL_1.md](BEHAVIORAL_1.md)); скоординировать
  подсистемы через **Facade** ([STRUCTURAL.md](STRUCTURAL.md)). Важно: Facade **делегирует**
  работу подсистеме, а не выполняет её сам, — фасад поверх God Object проблему не лечит, а
  лишь прячет.

### Анемичная модель предметной области (anemic domain model)

- **Симптом.** Сущности — это структуры из полей с геттерами и сеттерами, вся бизнес-логика
  вынесена в «сервисы», которые дёргают чужие данные.
- **Почему плохо.** Данные и правила их изменения разнесены: инварианты некому защищать,
  логика дублируется по сервисам, теряется инкапсуляция (по Фаулеру и Эвансу — антипаттерн
  в объектно-ориентированной и DDD-модели).
- **Как лечить.** Перенести поведение к данным по GRASP «Информационный эксперт»
  («Перемещение метода», Move Method) — получить насыщенную модель. **Нюанс для собеседования:**
  в гексагональной или функциональной архитектуре разделение данных и поведения бывает
  осознанным выбором, — это не всегда антипаттерн, важен контекст.

### Poltergeist (полтергейст) — объекты-однодневки

- **Симптом.** Классы-«пустышки» с короткой жизнью, единственная роль которых — вызвать метод
  другого объекта и исчезнуть (`XxxManager`, `XxxController`, который лишь переадресует).
- **Почему плохо.** Лишние прыжки в цепочке вызовов без добавленной ценности; загромождают
  граф объектов и диаграмму последовательности.
- **Как лечить.** Удалить посредника, вызвать целевой объект напрямую; если координация
  реально нужна — оформить её как Mediator ([BEHAVIORAL_2.md](BEHAVIORAL_2.md)), а не как
  «объект на один вызов».

### Преждевременная абстракция (premature abstraction)

- **Симптом.** Обобщённый каркас, параметры типов и точки расширения созданы до того, как
  появился второй-третий реальный случай использования.
- **Почему плохо.** Абстракция, выведенная из одного примера, почти всегда «не та»: она
  фиксирует случайные детали и мешает, когда приходит настоящий второй случай.
- **Как лечить.** Правило трёх и YAGNI: сначала три конкретных случая, потом обобщение.
  «Дублирование дешевле неправильной абстракции».

### Спагетти-код против лазанья-кода

- **Спагетти-код (spaghetti code).** Симптом: запутанный поток управления без слоёв, глобальное
  состояние, всё связано со всем. Почему плохо: любое изменение непредсказуемо. Лечение —
  выделение методов и классов, слои, инкапсуляция изменяемого.
- **Лазанья-код (lasagna code).** Обратная крайность: слоёв так много, что простой вызов
  проходит через десять уровней делегирования. Почему плохо: over-engineering «в высоту».
  Лечение — «Свёртывание иерархии» (Collapse Hierarchy), убрать слои без ответственности.

### Проблема йо-йо (yo-yo problem)

- **Симптом.** Чтобы понять поведение, приходится «кататься» вверх-вниз по глубокой иерархии
  наследования: метод определён в прадеде, переопределён в деде, вызывает шаблонный метод из
  внука.
- **Почему плохо.** Логику невозможно прочитать в одном месте; хрупкий базовый класс —
  изменение вверху ломает потомков.
- **Как лечить.** «Предпочитай композицию наследованию»: заменить наследование делегированием
  (Strategy вместо переопределяемого шага), выпрямить иерархию. Разбор компромисса
  наследование/композиция — в [INTRO.md](INTRO.md).

## Singleton как глобальное изменяемое состояние

Singleton часто вырождается в замаскированную глобальную переменную. Это **не** про
потокобезопасность и корректную инициализацию (holder idiom / `enum` / double-checked locking
с `volatile`) — эта тема принадлежит [CREATIONAL.md](CREATIONAL.md) и, на уровне модели памяти,
[../../concurrency/theory/THREADS_BASICS.md](../../concurrency/theory/THREADS_BASICS.md).
Здесь — только про антипаттерн «глобальное изменяемое состояние».

- **Симптом.** `SomeService.getInstance()` разбросан по коду; глобальный изменяемый реестр,
  к которому пишут откуда угодно.
- **Почему плохо.**
  - *Скрытые зависимости.* По сигнатуре класса не видно, что он тянет глобальный Singleton, —
    связи не отражены в конструкторе.
  - *Тестируемость.* Жёсткий `getInstance()` невозможно подменить mock-объектом; тесты
    начинают влиять друг на друга через общее изменяемое состояние.
  - *Переиспользование и параллелизм.* Один глобальный экземпляр мешает иметь два конфига,
    две конфигурации, изолированные окружения.
- **Как лечить.** Внедрять единственный экземпляр через DI-контейнер (Spring bean scope
  `singleton` — это один экземпляр *на контейнер*, управляемый и подменяемый, а не JVM-глобаль).
  Зависимость объявлять в конструкторе — тогда она видима и подменяема. Про инверсию создания и
  внедрение зависимостей — [../../spring-frameworks/theory/SPRING_CORE_DI.md](../../spring-frameworks/theory/SPRING_CORE_DI.md).

## Code smells по Фаулеру

Каждый запах имеет каноническое лечение — рефакторинг, часто ведущий к конкретному паттерну.

| Запах | Симптом | Почему плохо | Рефакторинг → целевой паттерн |
|-------|---------|--------------|-------------------------------|
| **Long Method** (длинный метод) | метод на десятки строк, много уровней вложенности | нечитаем, невозможно переиспользовать фрагменты | «Выделение метода»; «Замена условного оператора полиморфизмом» → **Strategy/State** ([BEHAVIORAL_1.md](BEHAVIORAL_1.md)) |
| **Large Class** (большой класс) | слишком много полей и методов (см. God Object) | нарушен SRP, низкая связность | «Выделение класса»/«подкласса»; координация через **Facade** ([STRUCTURAL.md](STRUCTURAL.md)) |
| **Feature Envy** (завистливость метода) | метод обращается к данным чужого объекта чаще, чем к своим | поведение оторвано от данных | «Перемещение метода» к владельцу данных (GRASP «Информационный эксперт») |
| **Data Clumps** (скопления данных) | одни и те же поля кочуют группой (`x, y`, `from, to, currency`) | дублирование, легко перепутать порядок | «Введение объекта-параметра»/«Выделение класса» → Value Object; сборка через **Builder** ([CREATIONAL.md](CREATIONAL.md)) |
| **Primitive Obsession** (одержимость примитивами) | `String email`, `int money`, коды-константы вместо типов | нет валидации и типобезопасности, логика размазана | «Замена примитива объектом»; «Замена кода типа классом/состоянием» → **State/Strategy** |
| **Shotgun Surgery** (стрельба дробью) | одно изменение требует мелких правок во многих классах | размазанная ответственность, легко забыть место | «Перемещение метода/поля», собрать логику вместе; централизация через **Facade/Mediator** |
| **Divergent Change** (расходящиеся изменения) | один класс меняют по разным, не связанным причинам | смешаны несколько осей изменчивости | «Выделение класса» по осям; разделение осей → **Bridge** ([STRUCTURAL.md](STRUCTURAL.md)) |
| **Refused Bequest** (отказ от наследства) | подкласс не использует или переопределяет-в-пустую унаследованное | нарушение LSP, ложная иерархия «is-a» | «Замена наследования делегированием» → **Strategy**; ссылка на LSP в [SOLID_OOP.md](../../software-engineering/theory/SOLID_OOP.md) |

**Divergent Change против Shotgun Surgery** (частый вопрос): при расходящихся изменениях
*один* класс правят по разным поводам — лечим разделением класса; при стрельбе дробью *одна*
причина заставляет править *много* классов — лечим сведением логики в один. Это зеркальные
запахи.

### Primitive Obsession — «плохо/хорошо»

```java
// Плохо: примитивы без смысла и защиты инвариантов
void transfer(long amountCents, String currency, String toEmail) { … }
// вызов легко перепутать: transfer(100, "bob@x.io", "USD") скомпилируется

// Хорошо: типы-значения инкапсулируют валидацию и правила
void transfer(Money amount, Email to) { … }   // порядок не перепутать, валидация внутри
```

### Feature Envy — «плохо/хорошо»

```java
// Плохо: метод Order завидует данным Address и лезет в его внутренности
class Order {
    double shippingCost(Address a) {
        return a.getCountry().equals("US") ? a.getZone() * 1.5 : a.getZone() * 2.0;
    }
}

// Хорошо: расчёт переезжает туда, где живут данные (Информационный эксперт)
class Address {
    double shippingCost() { … }   // Order лишь делегирует: address.shippingCost()
}
```

## Смежные домены: не путать

Три антипаттерна часто всплывают рядом, но принадлежат другим доменам — здесь только ссылки.

- **log-and-throw** (залогировать и перебросить исключение) — антипаттерн логирования, а не
  дизайна объектов. Канонический владелец —
  [../../infrastructure/theory/LOGGING.md](../../infrastructure/theory/LOGGING.md).
- **Кэш-антипаттерны** — захлёст кэша (cache stampede), пробой, лавина, проникновение. Это
  проблемы поведения кэша под нагрузкой, **а не OOP-смеллы**; отдельный домен —
  [../../caching-deep-dive/theory/ANTI_PATTERNS.md](../../caching-deep-dive/theory/ANTI_PATTERNS.md).
- **Связь запахов с SOLID** — большинство смеллов есть нарушение одного из пяти принципов;
  канонические формулировки — [../../software-engineering/theory/SOLID_OOP.md](../../software-engineering/theory/SOLID_OOP.md).
