# Interview Questions — System Design

~90 вопросов по полной карте модуля (см. [ROADMAP.md](ROADMAP.md)): основы → методология собеседования → распределённые примитивы → микросервисы → надёжность → алгоритмы → коммуникация → безопасность → потоковая обработка и современное → проектные задачи.

Источники: «Designing Data-Intensive Applications» (DDIA) — Kleppmann; «System Design Interview» — Alex Xu; канонические статьи (Raft/Paxos, Spanner, Dynamo, Tail at Scale).

## 1. Основы (Q1–Q15)

### Q1: В чём разница между вертикальным и горизонтальным масштабированием и где потолок вертикального?
**A:** Вертикальное масштабирование (scale-up) — наращивать ресурсы одной машины (CPU, RAM, диск). Простота: код не меняется, нет распределённой сложности. Потолок: физические лимиты железа, нелинейный рост цены (топовые серверы в 10× дороже без 10× производительности), единая точка отказа. Горизонтальное масштабирование (scale-out) — добавлять машины; почти линейный рост ёмкости (с учётом USL — см. Q5), но требует сервисов без состояния, балансировщика нагрузки, шардирования для слоя с состоянием. На практике связка: вертикально до разумного предела (8–32 ядра), затем горизонтально.

### Q2: Опиши типичный путь масштабирования веб-приложения с нуля до миллионов пользователей.
**A:** (1) Один сервер: приложение + БД на одной машине. (2) Разделить БД и сервер приложения. (3) Поставить балансировщик нагрузки + несколько экземпляров приложения (без состояния). (4) Добавить реплики БД для чтения (90% нагрузки — чтение). (5) Кэш (Redis/Memcached) перед БД. (6) CDN для статики. (7) Шардирование БД, когда нагрузка на запись не помещается на одну первичную реплику. (8) Разделить монолит на сервисы по доменным границам (микросервисы). (9) Multi-region для глобальной задержки и DR. Каждый шаг — реакция на конкретное узкое место, а не «делаем потому что модно».

### Q3: Оценка ёмкости (capacity estimation) — как считать на собеседовании?
**A:** Шаги: (1) **DAU** (daily active users); (2) **действий на пользователя в день** для каждой операции; (3) **отношение чтений к записям** (часто 100:1); (4) **пиковый коэффициент** = 2–10× от среднего (учёт суточного пика); (5) **хранилище** = DAU × действия × размер полезной нагрузки × срок хранения × фактор репликации; (6) **пропускная способность канала** = QPS × размер полезной нагрузки. Используй степени двойки: 1M ≈ 2²⁰, 1B ≈ 2³⁰. Бюджет задержки сравни с числами Джеффа Дина — если требуется < 10 мс, а только сетевой round-trip внутри ЦОД — 1 мс, остальное распределяй между БД и кэшем.

### Q4: Назови ключевые числа задержки (Jeff Dean) и зачем их помнить.
**A:** Опорный набор: L1 cache 1 нс, L2 ~4 нс, branch misprediction 5 нс, mutex lock/unlock 25 нс, основная память 100 нс, сжатие 1 КБ ~10 мкс, случайное чтение 4 КБ на SSD ~10 мкс (раньше 150 мкс для HDD), round-trip внутри ЦОД 500 мкс, сеть 1 Гбит/с — 10 мс на МБ, disk seek HDD 10 мс, между регионами 50–150 мс. Полезны на собеседовании для прикидочной оценки: «если задержка чтения должна быть p95 < 20 мс, две сетевые операции уже съели 1 мс — оставшиеся 19 мс на диск/CPU». Шкала разрядов важнее точных цифр.
> Jeff Dean — «Numbers Every Programmer Should Know»

### Q5: Что такое Universal Scalability Law (USL) и почему линейный scale-out — миф?
**A:** USL — модель Нила Гюнтера: пропускная способность при N узлах = `N / (1 + α(N-1) + βN(N-1))`, где α — конкуренция (сериализация), β — когерентность (синхронизация между узлами). При α=0, β=0 — идеальный линейный рост; на практике с ростом N сначала рост сублинейный, затем плато, затем спад (отрицательная масштабируемость при β>0). Практический вывод: не верить «удвоим узлы — удвоим RPS», измерять реальный коэффициент масштабирования; чаще всего узкое место — общий ресурс (БД, сервис блокировок) с большим α.
> Neil Gunther — «Guerrilla Capacity Planning»

### Q6: Типы DNS-записей и зачем нужен компромисс по TTL.
**A:** Основные записи: **A** (IPv4), **AAAA** (IPv6), **CNAME** (псевдоним на другое DNS-имя — нельзя на корне домена), **MX** (почтовый сервер), **NS** (делегирование), **TXT** (произвольный текст: SPF/DKIM/verification), **SOA** (zone authority). TTL — сколько резолверы кэшируют запись. Низкий TTL (30–60 с) даёт быстрое переключение на резерв, но повышает QPS на authoritative DNS и задержку для пользователей (промах кэша каждые 60 с). Высокий TTL (часы) — наоборот: дешевле и быстрее, но при инциденте смена IP займёт часы. Прод: 60–300 с для динамических сервисов, 1 ч для статики.

### Q7: GeoDNS и маршрутизация по задержке против anycast — в чём разница?
**A:** **GeoDNS** возвращает разные IP в зависимости от географии запрашивающего (расположение DNS-резолвера, не реального клиента — отсюда часть неточности). **Маршрутизация по задержке** (AWS Route 53, Cloudflare) — измеряет реальную задержку и направляет к ближайшему по сети региону. **Anycast** — один и тот же IP анонсируется из множества POP через BGP, и пакет приходит на ближайший по сети узел; работает на L3 без участия DNS. Anycast мгновенный (TCP-соединение к ближайшему POP), GeoDNS даёт более гибкую логику маршрутизации (например, по комплаенсу — данные ЕС → только франкфуртский регион).

### Q8: CDN: push против pull, и почему версионированные URL обычно лучше очистки кэша?
**A:** **Pull CDN** (Cloudflare, Fastly) — клиент запрашивает у пограничного узла; при промахе кэша узел тянет с источника и кэширует. **Push CDN** — публикатор сам загружает контент на пограничный узел (Amazon CloudFront для S3 — гибрид). Pull проще: не надо думать о синхронизации; push даёт предсказуемое наполнение для редких ресурсов. **Очистка кэша (purge)** требует прохода по всем POP (минуты, иногда часы у крупных CDN), а **версионированные URL** (`/static/app.v42.js` или хэш в пути) — мгновенная инвалидация на стороне клиента: новая ссылка автоматически — промах кэша. Прод: статика — всегда версионированные URL (immutable + `Cache-Control: max-age=31536000`), очистка — только для редких аварийных случаев.

### Q9: Cache-Control, ETag, Vary — что делает каждый в контексте CDN?
**A:** **`Cache-Control`** — главный директор кэширования: `public`/`private`, `max-age`, `s-maxage` (только для общего кэша), `no-store`, `stale-while-revalidate`, `must-revalidate`. **`ETag`** — версионный отпечаток ресурса; при `If-None-Match` сервер возвращает 304 без тела, если ETag совпал. **`Vary`** — указывает CDN, по каким заголовкам запроса разделять ключ кэша (`Vary: Accept-Encoding` — отдельные кэш-записи для gzip/br). Подводный камень: `Vary: Cookie` или `User-Agent` фрагментирует кэш до бесполезности — каждый пользователь получает свою копию. Подробнее — `caching-deep-dive/theory/HTTP_CDN_CACHE.md`.

### Q10: Балансировщик L4 против L7 — когда какой нужен?
**A:** **L4** (TCP/UDP, IP+порт) — балансирует на уровне сокетов: NAT/DSR, низкая задержка (~мкс), не видит содержимое, поэтому не может маршрутизировать по пути/заголовку. Подходит для произвольных протоколов (gRPC, postgres) и максимального RPS. **L7** (HTTP/HTTPS) — терминирует TLS, разбирает запрос, маршрутизирует по пути/хосту/заголовку, поддерживает rewrite, повтор, A/B, WAF. Дороже по CPU, но необходим для HTTP-маршрутизации. Прод: часто связка — L4 (anycast/ELB) на входе, за ним L7 (Envoy/Nginx/HAProxy) для маршрутизации к сервисам.

### Q11: Алгоритмы балансировки нагрузки и где какой использовать.
**A:**
- **Round-robin** — простой, справедливый при одинаковых бэкендах; плох при неравных машинах или длинных запросах.
- **Least connections** — выбирает бэкенд с минимумом активных соединений; хорошо для долгих сессий (WebSocket, БД).
- **IP-hash / consistent hash** — фиксирует клиента/ключ за бэкендом; нужен для «липкого» поведения без cookies или для кэш-узлов.
- **Weighted round-robin / least conn** — учитывает разные мощности машин.
- **Power-of-two-choices** — выбираем 2 случайных, шлём на менее загруженный; почти как least-conn без глобального состояния, хорошо масштабируется.
- **EWMA / response-time** (Envoy) — учитывает реальную задержку, естественно отжимает слабые поды.

### Q12: Привязка сессии против отсутствия состояния — компромиссы.
**A:** **Привязка сессии (sticky session)** (через cookie или IP hash) — простой путь сделать приложение с состоянием горизонтально масштабируемым: каждый пользователь всегда попадает на тот же сервер, который хранит состояние сессии в памяти. Минусы: при выпадении этого сервера пользователь теряет сессию; неравномерная нагрузка; rolling deploy сложен. **Без состояния (stateless)** — состояние в Redis / БД / JWT; любой экземпляр обслужит любого пользователя; горизонтальное масштабирование и rolling deploy без потерь. Прод: почти всегда без состояния для веб-серверов; привязка только для специфичных случаев (WebSocket с локальным in-memory pub/sub, GPU-сессии для ML-инференса).

### Q13: Что такое anycast и как один IP может обслуживаться разными POP?
**A:** Anycast — один и тот же IP-префикс анонсируется из множества физических локаций через BGP. Маршрутизаторы интернета сами выбирают «ближайший» по BGP-метрикам путь к этому IP, поэтому пакет от пользователя приходит на ближайший POP без участия DNS или приложения. Используется для: корпоративных DNS (8.8.8.8, 1.1.1.1), поглощения DDoS (атака размывается по сотням POP), CDN на L3. Подводный камень: anycast подходит для UDP без состояния (DNS, QUIC) и коротких TCP-сессий; для длинных TCP-сессий перестроение маршрута (route flap) может перебросить трафик на другой POP, и соединение разорвётся (поэтому крупные CDN держат сессии с состоянием на пограничных узлах и тянут к источнику внутренне).

### Q14: Обратный прокси против балансировщика нагрузки — где граница?
**A:** Граница размытая; на практике это часто **один и тот же продукт** (Nginx, HAProxy, Envoy) в разных режимах. **Обратный прокси (reverse proxy)** — единая точка входа, терминирует TLS, кэширует ответы, добавляет заголовки, проксирует на 1+ бэкенд; даже на одном бэкенде имеет смысл (разгрузка TLS, безопасность на границе). **Балансировщик нагрузки** — конкретно функция распределения нагрузки между несколькими бэкендами по алгоритму. Любой современный обратный прокси умеет балансировать, любой L7-балансировщик умеет проксировать. Различение полезно концептуально: обратный прокси — «фасад», балансировщик — «диспетчер»; коммерческие устройства вроде F5 BIG-IP делают акцент на балансировке, а Cloudflare — на пограничном прокси.

### Q15: HTTP/1.1 против HTTP/2 против HTTP/3+QUIC — ключевые различия.
**A:** **HTTP/1.1** — текстовый, один запрос/ответ на TCP-соединение (keep-alive переиспользует, но без мультиплексирования → блокировка очереди (head-of-line blocking), костыли вроде domain sharding и конкатенации). **HTTP/2** — бинарный, мультиплексирование множества потоков в одном TCP, HPACK-сжатие заголовков, server push (на практике мёртв). Блокировка очереди устранена на уровне HTTP, но остаётся на уровне TCP: потеря одного пакета блокирует все потоки. **HTTP/3** — поверх QUIC (на UDP), TLS 1.3 встроен, мультиплексирование на уровне транспорта (каждый поток независим — нет TCP HOL), миграция соединения (смена сети без потери соединения). TLS 1.3 0-RTT — повторные подключения без round-trip рукопожатия. Прод: HTTP/3 заметно ускоряет мобильных клиентов в плохих сетях.

## 2. Методология собеседования (Q16–Q18)

### Q16: Как структурировать первые 5 минут собеседования по System Design (уточнение требований)?
**A:** Цель — превратить размытую тему в конкретный охват. (1) **Функциональные требования**: какие сценарии в охвате, какие вне (например, «Twitter: лента + пост + подписка; обмен сообщениями — вне охвата»). (2) **Нефункциональные**: цели задержки p95/p99, доступность (99,9% или 99,99%), согласованность (строгая / read-your-writes / итоговая), живучесть. (3) **Масштаб**: DAU, пиковый QPS, размер полезной нагрузки, географическое распределение. (4) **Ограничения**: бюджет, регулятор (GDPR/HIPAA), существующий технологический стек. Завершить кратким резюме: «итого: 100M DAU, 100K QPS чтения / 5K записи, p95 < 200 мс, итоговая согласованность, multi-region, GDPR». Это рамка остальной дискуссии.

### Q17: Оценка ёмкости на собеседовании — шаблон на 5 минут.
**A:** На доске последовательно: (1) DAU → MAU/30 или из контекста; (2) действия/пользователя/день × DAU = операций/день; (3) операций/день / 86400 ≈ средний QPS; (4) пик = 2–10× от среднего; (5) хранилище = операции × размер полезной нагрузки × срок хранения × фактор репликации; (6) пропускная способность канала = QPS × размер полезной нагрузки × множитель. Округлять степенями двойки: 1M ≈ 10⁶ ≈ 2²⁰. Делать sanity-check: «100 ПБ хранилища — это ~10K серверов с 10 ТБ каждый» — соответствует ли это размеру компании? Главное — продемонстрировать процесс рассуждения, точные цифры не критичны.

### Q18: Как защищать выбор архитектуры на вопросах о компромиссах?
**A:** Структура: **«я выбрал X, потому что A, B, C; альтернатива Y хороша когда Z, но не подходит здесь потому что W»**. Опорные оси: задержка против согласованности (PACELC), живучесть против стоимости, простота против гибкости, скорость разработки против операционной сложности. Не давать «лучшее решение» — давать **обоснованный выбор с явными компромиссами**. Конкретно: на вопрос «PostgreSQL или Cassandra» — не «Cassandra, она быстрее», а «Cassandra если нужна multi-region запись без выделенного лидера и устроит итоговая согласованность; PostgreSQL если нужны транзакции и сложные джоины. Для нашего случая с финансовой бухгалтерской книгой — PostgreSQL, потому что ACID критичен». Интервьюеру важна именно логика выбора.

## 3. Распределённые примитивы (Q19–Q34)

### Q19: Что такое теорема CAP и её ограничения?
**A:** При сетевом разделении (Partition) распределённая система вынуждена выбирать между **согласованностью** (все узлы видят одинаковые данные) и **доступностью** (система отвечает на все запросы). CP-системы (ZooKeeper, etcd, Spanner) — при разделе становятся недоступными в меньшинстве. AP-системы (Cassandra, DynamoDB при `R=W=1`) — отвечают данными, которые могут быть устаревшими. Ограничения: «согласованность» в CAP = **строгая согласованность (linearizability)** (узкий смысл), не обычная ACID-согласованность; в нормальной работе доступны оба свойства. Поэтому в обиходе используют PACELC — см. Q20.
> Eric Brewer — «CAP Twelve Years Later»

### Q20: PACELC — почему «честнее» CAP?
**A:** **PACELC** (Daniel Abadi): если есть разделение (P), выбирай между доступностью (A) и согласованностью (C); иначе (E) — выбирай между задержкой (L) и согласованностью (C). CAP описывает только редкий случай раздела; PACELC отражает постоянный компромисс: синхронная репликация даёт согласованность, но платит задержкой на каждом запросе. Классификация: **PostgreSQL = PC/EC** (единая первичная реплика, строгая согласованность, неоптимально по задержке); **Cassandra = PA/EL** (под нагрузкой можно нагнетать итоговую согласованность); **DynamoDB = PA/EL** (с опциональным строго согласованным чтением); **Spanner = PC/EC** (CP даже под нагрузкой, но компенсирует TrueTime).
> Daniel Abadi — «Consistency Tradeoffs in Modern Distributed Database System Design»

### Q21: Кворум (R+W>N) — что это даёт и где подводные камни?
**A:** В системах без выделенного лидера с N репликами: записываем на W узлов, читаем с R узлов; если **R+W > N** — кворумы чтения и записи пересекаются хотя бы в одном узле, значит чтение увидит последнюю запись. Конкретно `N=3, W=2, R=2` — стандарт; `W=N=3, R=1` — быстрое чтение, медленная запись; `W=1, R=1` — best effort, итоговая согласованность. Подводный камень: кворум гарантирует пересечение, но не порядок — нужны **векторные часы (vector clock)** или **last-write-wins с синхронизированными часами** для разрешения конфликтов. Нестрогий кворум с подсказанной передачей (sloppy quorum + hinted handoff, Dynamo) допускает запись при отсутствии первичных узлов — кратко: если положенный узел недоступен, запись идёт на ближайший доступный, а тот хранит «подсказку», кому передать данные после восстановления. Это нарушает строгую кворумную гарантию ради высокой доступности.
> Dynamo paper (Amazon, 2007)

### Q22: Строгая (linearizable), последовательная, причинная и итоговая согласованность.
**A:** Спектр от сильной к слабой:
- **Строгая (linearizable)**: операции выполняются в некотором глобальном порядке, согласующемся с реальным временем; «как один сервер». Дорого: требует консенсуса или единого лидера.
- **Последовательная**: глобальный порядок есть, но не обязан совпадать с wall-clock временем; операции одного клиента — в программном порядке.
- **Причинная**: если A причинно предшествует B (через `happens-before`), все наблюдатели видят A раньше B; независимые операции могут разойтись (векторные часы).
- **Read-your-writes / monotonic reads / writes-follow-reads**: сессионные гарантии — слабее причинной, но достаточно для UX (пользователь видит свой только что отправленный пост).
- **Итоговая**: «когда-нибудь сходимся»; конкретики о времени и порядке нет.

### Q23: Lamport clock против векторных часов — какие конфликты ловят?
**A:** **Lamport timestamp** — счётчик, который монотонно увеличивается при send/receive. Даёт полный порядок (с разрешением ничьей по идентификатору узла), но **не отличает причинную связь от конкурентности**: для двух событий A и B с разными метками времени мы не знаем, было ли A→B или они конкурентны. **Векторные часы (vector clock)** — массив `[c1, c2, ..., cN]` по одному счётчику на узел; событие A→B тогда и только тогда, когда `VC(A) ≤ VC(B)` поэлементно и не равны. Если ни `VC(A) ≤ VC(B)`, ни `VC(B) ≤ VC(A)` — они конкурентны (параллельны). Векторные часы дороже (O(N) накладных расходов) и нужны для систем, где важен причинный порядок (Riak, обнаружение конфликтов в Dynamo).
> Lamport — «Time, Clocks, and the Ordering of Events»

### Q24: Ключи идемпотентности — почему обязательны для безопасных повторов?
**A:** При повторе неидемпотентной операции (создание заказа, списание с карты) есть риск выполнить её дважды, если первый запрос всё-таки дошёл, но ответ потерялся. Ключ идемпотентности — UUID, генерируемый клиентом до первого запроса; сервер хранит `(key → response)` с TTL (например, 24 ч) и при повторе с тем же ключом возвращает тот же кэшированный ответ. Реализация: отдельная таблица в БД с уникальным индексом по ключу + транзакционная запись результата. Без ключа идемпотентности любая логика повторов становится небезопасной для операций с побочными эффектами.
> Stripe API — Idempotency Keys

### Q25: Raft — основные идеи и свойства безопасности.
**A:** Raft — алгоритм консенсуса для реплицированного автомата состояний. Состояния узла: **Follower** (ведомый) / **Candidate** (кандидат) / **Leader** (лидер). Время разбито на **термы (terms)** (монотонная нумерация); в каждом терме избран не более одного лидера. **Выборы лидера**: при таймауте ведомый становится кандидатом, запрашивает голоса; кто соберёт большинство — лидер. **Репликация журнала**: клиент → лидер → AppendEntries к ведомым; запись зафиксирована после реплики на большинстве. Свойства безопасности: (1) безопасность выборов — один лидер на терм; (2) лидер пишет только в конец — не перезаписывает свой журнал; (3) совпадение журнала — если две записи имеют одинаковые `(term, index)`, всё предыдущее тоже совпадает; (4) полнота лидера — зафиксированные записи присутствуют у всех будущих лидеров; (5) безопасность автомата состояний — две команды применяются в одинаковом порядке всеми автоматами.
> Diego Ongaro & John Ousterhout — «In Search of an Understandable Consensus Algorithm»

### Q26: Paxos против Raft — почему Raft победил в индустрии?
**A:** Корректность одинаковая (Paxos формально доказан старше), но Raft проще для понимания и реализации. Различия: (1) **Single-decree Paxos** решает один консенсус; для реплицированного журнала нужен Multi-Paxos с нетривиальной оптимизацией. Raft — журнало-центричный с самого начала. (2) Раздел проблемы: Raft чётко разделяет выборы лидера, репликацию журнала, безопасность; в Paxos они переплетены. (3) Raft требует **сильного лидера** (вся запись через лидера) — это упрощает рассуждения, но снижает доступность записи при переключении на резерв. (4) Изменение состава: Raft предлагает совместный консенсус (joint consensus) как стандартный механизм — кратко: при смене набора узлов на короткое время действует пересечение старого и нового кворумов, потом — только новый, что исключает разделение голосов. Этимология: после статьи Ongaro (2014) Raft взяли etcd, Consul, CockroachDB, TiKV, KRaft; Paxos остался в Google (Chubby, Spanner) и ZooKeeper (ZAB — вариация Paxos).

### Q27: ZAB (ZooKeeper Atomic Broadcast) — чем отличается от Raft?
**A:** ZAB предшествует Raft, тоже основан на едином лидере + репликация журнала, но: (1) фокусируется на **атомарной рассылке (atomic broadcast)** (порядок сообщений), не на репликации автомата состояний явно; (2) использует **двухфазное восстановление** при выборах (синхронизация журнала лидера с большинством перед началом работы) — это даёт более строгие гарантии при разделе, но усложняет код; (3) zxid — 64-битный идентификатор (epoch + counter) вместо отдельных терма и индекса. На практике ZAB и Raft эквивалентны по гарантиям. ZAB остался специфичным для ZooKeeper; индустрия пошла по пути Raft из-за читаемости спецификации.

### Q28: Выборы лидера — Bully, Raft, эфемерные znode в ZK и временная аренда (lease).
**A:**
- **Bully**: узел с самым большим ID побеждает. Узел заметил, что лидер умер → отправляет ELECTION узлам с большим номером; если никто не ответил — он лидер; иначе ждёт от победителя. Прост, но генерирует O(N²) сообщений и требует знания всех узлов.
- **На основе Raft**: см. Q25; голосование большинства со случайным таймаутом для предотвращения разделения голосов.
- **Эфемерные znode в ZK**: каждый кандидат создаёт `/leader-XXX` (sequential ephemeral); владелец znode с минимальным номером — лидер. При смерти узла znode исчезает (по таймауту сессии), следующий по списку забирает лидерство.
- **Через временную аренду (lease) + токен ограждения (fencing token)**: лидер получает аренду (lease) на T секунд от сервиса блокировок; каждое действие сопровождается монотонно растущим токеном ограждения. Если старый лидер «воскрес» с протухшей арендой и пытается записать — нижестоящий сервис отказывает (токен старее последнего виденного). Защищает от расщепления кластера (split-brain) без консенсуса.

### Q29: Расщепление кластера (split-brain) — причина и способы защиты.
**A:** Расщепление возникает, когда при сетевом разделении обе половины кластера считают себя первичными и принимают записи → конфликтующие данные на сторонах раздела. Способы защиты: (1) **Кворум** — записи только при большинстве узлов в живых; меньшинство отказывает в записи (CP); (2) **Токен ограждения (fencing token)** — каждое действие нумеруется; нижестоящий сервис отвергает действия с устаревшим токеном (Martin Kleppmann: «How to do distributed locking»); (3) **STONITH** (Shoot The Other Node In The Head) — изолированный watchdog физически отключает «зомби»-узлы; (4) **Свидетель / арбитр** для разрешения ничьей (топология 2+1). Без токена ограждения распределённый замок сам по себе не защищает от расщепления.

### Q30: Gossip-протокол — push, pull и push-pull, что такое SWIM?
**A:** Gossip — децентрализованное распространение информации: каждый узел периодически выбирает случайных N соседей и обменивается состоянием. **Push**: я отдаю своё состояние соседу. **Pull**: я прошу состояние у соседа. **Push-pull**: обмен в обе стороны (быстрее сходится). Распространение информации — O(log N) раундов. **SWIM** (Scalable Weakly-consistent Infection-style Membership) — конкретный gossip для обнаружения сбоев: периодический ping + косвенный ping через k случайных свидетелей перед объявлением узла мёртвым (уменьшает ложные срабатывания). Используется в Consul, Memberlist (Serf), Cassandra.
> SWIM paper — Das, Gupta, Motivala (2002)

### Q31: CRDT — основные типы и где применять.
**A:** **CRDT** (Conflict-free Replicated Data Types) — структуры, для которых слияние двух реплик математически коммутативно, ассоциативно, идемпотентно, поэтому конфликты разрешаются без координации. Базовые типы:
- **G-Counter** — счётчик только-на-увеличение (массив счётчиков по узлам, слияние = поэлементный max).
- **PN-Counter** — пара G-Counter (положительный и отрицательный).
- **G-Set / 2P-Set / OR-Set** — множества с разной семантикой удалений; OR-Set различает повторные добавления и удаления через уникальные метки.
- **LWW-Register** — Last-Write-Wins по метке времени; теряет конкурентные записи.
Применение: совместное редактирование (Yjs, Automerge), корзина покупок в Dynamo, edge-реплицированные счётчики (Riak).
> Marc Shapiro et al. — «Conflict-free Replicated Data Types»

### Q32: Op-based против state-based CRDT — компромиссы.
**A:** **State-based** (CvRDT) — каждый узел шлёт полное состояние, слияние — полурешётка слияния (join semilattice), т. е. операция, которая ассоциативна, коммутативна и идемпотентна. Просто: можно использовать обычный gossip; слияние идемпотентно, дубликаты неопасны. Минус: размер сообщений растёт со временем (хотя delta-state CRDT уменьшает). **Op-based** (CmRDT) — узлы шлют только операции; требует надёжной доставки **exactly-once в причинном порядке** (через векторные часы). Сообщения маленькие, но транспорт сложнее. На практике обычно используют delta-state или гибрид: реплика хранит состояние, шлёт компактные дельты.

### Q33: Multi-region active-active против active-passive — компромисс RTO/RPO.
**A:** **Active-passive** — первичный регион принимает записи, вторичный — асинхронная реплика. RTO (время восстановления) — минуты-десятки минут (сценарий переключения + смена DNS); RPO (точка восстановления) — секунды-минуты (задержка репликации). Проще операционно. **Active-active** — оба региона принимают записи; нужно решать разрешение конфликтов (LWW, CRDT, слияние на уровне приложения) или использовать lead-per-key (Cosmos DB, владение партиций). RTO ~0, RPO ~0 (если синхронная реплика; иначе ~секунды), но дороже в инфраструктуре и сложнее в коде. Выбор: банкинг с ACID — active-passive в одной зоне + cross-region cold standby; глобальный соцпродукт — active-active с итогово-согласованными данными.

### Q34: Как Spanner достигает глобальной строгой согласованности через TrueTime?
**A:** Spanner предоставляет **внешне согласованные** транзакции глобально — в общем случае невозможно, но Google использует **TrueTime API**: GPS и атомарные часы дают ограниченную неопределённость `[earliest, latest]` (обычно ±7 мс). Алгоритм для read-write транзакций: (1) выбрать `commit_timestamp = TT.now().latest`; (2) **commit wait** — ждать пока `TT.now().earliest > commit_timestamp` (т. е. реальное время точно прошло этот момент); (3) только потом сделать запись видимой. Это гарантирует: если T1 фиксируется до начала T2 (по wall-clock), то T2 видит T1. Цена: каждая запись платит ~7 мс задержки commit-wait. Доступно как Cloud Spanner.
> Spanner paper — Corbett et al. (OSDI 2012)

## 4. Шаблоны микросервисов и Kafka (Q35–Q47)

### Q35: Когда оправдан переход от монолита к микросервисам?
**A:** Не из-за масштаба (вертикально и в монолите можно), а из-за **организационной масштабируемости**: когда команд > 5–8 и они блокируют друг друга на одном репозитории/выкатке. Признаки готовности: (1) разные части системы имеют разный нефункциональный профиль (одни — строгая задержка, другие — пакетная обработка); (2) частота развёртывания страдает из-за связности; (3) разные команды хотят разный технологический стек; (4) есть зрелая платформа (CI/CD, наблюдаемость, секреты, service mesh) — иначе операционная сложность убьёт продуктивность. Анти-шаблон: «модульный монолит → микросервисы потому что модно». Если границы доменов нечёткие — разбиение только закрепит хаос в виде распределённого монолита.

### Q36: Шаблон Saga — хореография против оркестрации.
**A:** Saga разбивает длинную транзакцию на цепочку локальных транзакций, каждая публикует событие или вызывает следующий шаг; при сбое — **компенсирующие транзакции** в обратном порядке. **Хореография**: сервисы реагируют на события друг друга (event-driven, слабая связность). Минусы: нет центрального представления, отладка сложна — нужно по трассировке склеивать поток; легко создать циклы. **Оркестрация**: центральный координатор (Camunda, Temporal, AWS Step Functions) хранит состояние saga и явно вызывает шаги. Плюсы: видимость, легче изменить порядок, тесты проще. Минусы: координатор — единая точка эволюции/отказа. Прод: оркестрация для критичных бизнес-процессов (платежи, заказы), хореография — для слабосвязанных интеграций.
> Chris Richardson — «Microservices Patterns»

### Q37: Outbox-шаблон — зачем нужен и как реализовать с CDC.
**A:** Проблема: нельзя атомарно записать в БД (например, создать заказ) и опубликовать событие в Kafka — две разных системы, распределённая транзакция (XA) дорого и хрупко. **Outbox**: в одной транзакции пишем в бизнес-таблицу И в таблицу `outbox` (в той же БД). Отдельный публикатор читает outbox и шлёт в Kafka, помечая записи как отправленные. Гарантирует at-least-once доставку без 2PC. **Опрос**: публикатор делает `SELECT FROM outbox WHERE NOT sent LIMIT 100` — просто, но даёт задержку и нагрузку на БД. **CDC** (Debezium → WAL/binlog → Kafka Connect) — публикация в реальном времени на основе репликационного потока БД, без опроса. Подводные камни: эволюция схемы в outbox-таблице, удаление обработанных записей (TTL или мягкое удаление).

### Q38: CQRS — когда оправдан и когда избыточен?
**A:** CQRS (Command Query Responsibility Segregation) — разделение модели на write-side (команды, нормализованная) и read-side (запросы, денормализованная) с отдельными хранилищами. Оправдан когда: (1) чтение и запись имеют радикально разную нагрузку или шаблоны (чтение 1000:1 запись, сложные джоины на больших данных); (2) разные read-модели для разных UI; (3) чтение должно быть глобально доступно (итогово-согласованный поисковый индекс, кэш). Избыточен для CRUD-приложений с простой моделью — добавляет сложность (проекция событий, итоговая согласованность, разные модели данных) ради абстрактных преимуществ. Часто путают с Event Sourcing — это разные шаблоны, CQRS не требует ES (и наоборот).

### Q39: Event Sourcing — append-only журнал как источник истины.
**A:** Вместо хранения текущего состояния в таблицах храним последовательность событий: `OrderPlaced`, `ItemAdded`, `OrderShipped`. Текущее состояние = свёртка по событиям. Преимущества: (1) **полный журнал аудита** бесплатно; (2) **путешествие во времени** — состояние на любой момент; (3) **проекции** — несколько read-моделей из одного потока; (4) **событийно-ориентированная архитектура** естественна. Сложности: версионирование событий (см. Q40), идемпотентность проекций (применять смещение для exactly-once-effect), снапшоты для производительности (Q41), GDPR (удаление события из append-only журнала — нетривиально, обычно крипто-стирание ключа).

### Q40: Обратная и прямая совместимость и апкастинг в Event Sourcing.
**A:** **Обратная совместимость**: новый код читает старые события — поля добавлять только необязательные со значениями по умолчанию, не удалять обязательные, не переименовывать. **Прямая**: старый код читает новые события — игнорировать неизвестные поля (Jackson: `@JsonIgnoreProperties(ignoreUnknown = true)`). **Полная** = пересечение. **Апкастинг** — преобразование сырого старого события до десериализации: заполнить новое поле значением по умолчанию, разбить, склеить. Применяется когда строго типизированные события и Avro/Protobuf schema resolution недостаточны. Альтернативы: версионирование событий (`OrderCreatedV1`, `OrderCreatedV2` как отдельные классы), параллельные поля с `@Deprecated`. Confluent Schema Registry поддерживает режимы `BACKWARD`, `FORWARD`, `FULL` и `_TRANSITIVE`.
> Greg Young — «Versioning in an Event Sourced System»

### Q41: Снапшоты в Event Sourcing — зачем и как организовать.
**A:** Восстановление состояния агрегата = переигрывание всех его событий с начала. При тысячах событий на агрегат переигрывание становится медленным (линейное сканирование). **Снапшот** — материализованное состояние агрегата после N-ного события, хранится в отдельном хранилище (отдельная таблица или KV). Восстановление = загрузка последнего снапшота + переигрывание хвоста после снапшота. Компромисс: дополнительное место + инвалидация снапшотов при изменении структуры события vs скорость восстановления. Стратегия: снапшот каждые 100–1000 событий или по weighted-replay-time (если переигрывание > 100 мс — взять снапшот). Версионирование снапшотов важно: при изменении схемы либо мигрировать снапшоты, либо инвалидировать и пересчитать.

### Q42: Стратегии развёртывания: Blue/Green, Rolling, Canary, A/B.
**A:**
- **Rolling**: постепенная замена экземпляров по N штук; простое (по умолчанию в k8s), без простоя, но смешан старый/новый код во время раскатки.
- **Blue/Green**: параллельные окружения (blue — текущее, green — новое); переключение трафика мгновенно (переключение балансировщика). Лёгкий откат (откатить трафик обратно). Дорого по инфраструктуре (2× мощности на время раскатки), сложно для систем с состоянием (миграции БД).
- **Canary (канареечная)**: новый код на маленькой доле трафика (1% → 10% → 100%), мониторинг ошибок и задержки. Самый безопасный для рискованных изменений; нужна надёжная наблюдаемость и флаги функциональности (feature flag) для срочного отката.
- **A/B-тестирование**: не стратегия развёртывания, а способ проверки бизнес-метрик на сегменте пользователей. Часто реализуется через флаги функциональности поверх любой стратегии развёртывания.

### Q43: Партиционирование Kafka и гарантии порядка.
**A:** Kafka даёт **порядок в пределах партиции**: внутри одной партиции сообщения упорядочены по смещению; между партициями порядка нет. Ключ партиционирования (хэш) определяет, в какую партицию попадёт сообщение — `hash(key) % num_partitions`. Поэтому: чтобы события одной сущности (user_id, order_id) обрабатывались по порядку — использовать её ID как ключ партиционирования. Подводный камень: **изменение `num_partitions` ломает hash-маршрутизацию** — старые ключи разъедутся по новым партициям, и порядок для них нарушится; в проде num_partitions фиксируют заранее с запасом. Пользовательский partitioner — для сложной логики (например, weighted by tenant size).

### Q44: At-most / at-least / exactly-once в Kafka — что реально гарантируется?
**A:** Семантики:
- **At-most-once**: `acks=0`, без повторов — просто, потери возможны.
- **At-least-once**: `acks=all` + повторы — стандарт; потребитель должен быть идемпотентным, дубликаты возможны при повторе.
- **Exactly-once**: идемпотентный producer (`enable.idempotence=true` — producer id + sequence, брокер дедуплицирует) + транзакции (`transactional.id` + `initTransactions` + `beginTransaction/commitTransaction`). Потребитель читает с `isolation.level=read_committed`. Уточнение: exactly-once в Kafka работает только внутри экосистемы Kafka (consume → process → produce); если внутри транзакции вызывается внешний HTTP API — exactly-once на этот вызов **не** распространяется. Побочные эффекты вне Kafka требуют ключей идемпотентности.

### Q45: Перебалансировка consumer group — что происходит и как минимизировать паузу.
**A:** Когда потребитель присоединяется или уходит из группы, координатор группы (один из брокеров) запускает **перебалансировку**: вычисляет новое распределение партиция → потребитель и шлёт каждому. Старый алгоритм (eager) — **stop-the-world**: все потребители отдают партиции, ждут нового назначения, затем стартуют. Это паузы 1–10 с. **Кооперативная перебалансировка** (KIP-429, Kafka 2.4+) — инкрементальная: только меняющиеся назначения отзываются, остальные продолжают работать; паузы намного короче. **Статическое членство** (`group.instance.id`) — потребитель переподключается с тем же ID после рестарта без перебалансировки, если успел до session timeout. Sticky assignor минимизирует перемещение партиций при перебалансировке.

### Q46: ISR, acks=all, min.insync.replicas — что реально означает «живучесть»?
**A:** **ISR** (In-Sync Replicas) — реплики, которые в данный момент не отстают от лидера больше `replica.lag.time.max.ms`. **`acks=all`** заставляет producer ждать подтверждения от **всех ISR** (не от всех реплик). Если `min.insync.replicas=2` и реплик 3 — производство требует, чтобы хотя бы 2 (включая лидера) были в ISR; иначе producer получает `NotEnoughReplicasException` и запись не примется. Тонкость: `acks=all` без `min.insync.replicas` не даёт живучести — если ISR сжалась до одного лидера, и он умирает, данные потеряны. Boilerplate-настройка для живучего producer: `acks=all`, `min.insync.replicas=2` (при `replication.factor=3`), `enable.idempotence=true`.

### Q47: KRaft против ZooKeeper — почему Kafka отказалась от ZK?
**A:** ZooKeeper был отдельным кластером с операционными накладными расходами (отдельное развёртывание, отдельная модель авторизации, лимит ~200K партиций из-за хранения метаданных в куче ZK). **KRaft** (KIP-500) выносит метаданные в встроенный Raft-журнал внутри брокеров Kafka — единое развёртывание, единая модель безопасности, миллионы партиций. Контроллер всегда один (лидер Raft-кворума метаданных), при переключении на резерв новый избирается за ~10 с. Готово к проду с Kafka 3.3 (2022), поддержка ZK удалена в Kafka 4.0.
> KIP-500: Replace ZooKeeper with a Self-Managed Metadata Quorum

## 5. Шаблоны надёжности (Q48–Q53)

### Q48: Повторы с экспоненциальной задержкой и разбросом — почему именно full jitter?
**A:** Базовая экспоненциальная задержка: `delay = base * 2^attempt` (с потолком сверху). Без разброса все клиенты падают одновременно → повторяют одновременно → новая волна нагрузки → каскад. **Full jitter** (AWS): `delay = random(0, base * 2^attempt)` — равномерно распределяет повторы во времени, минимизирует наложение. **Equal jitter**: `delay = half + random(0, half)` — гарантирует минимальную задержку, чуть лучше для очень коротких повторов. **Decorrelated jitter** (`delay = random(base, prev_delay * 3)`) — хорош для долгих сценариев с длинным хвостом. AWS Architecture Blog статистически показал: full jitter даёт минимальное время завершения и минимальную нагрузку на нижестоящий сервис.
> AWS Architecture Blog — «Exponential Backoff and Jitter» (Marc Brooker)

### Q49: Circuit Breaker — зачем, состояния, когда открывается, что такое CCB и адаптивная конкурентность.
**A:** Защищает от каскадных сбоев: при недоступности нижестоящего сервиса быстро возвращаем ошибку вместо ожидания таймаута. Состояния: **CLOSED** → **OPEN** (при >K сбоев или >K% за окно) → **HALF-OPEN** (после охлаждения, пробный запрос) → CLOSED или снова OPEN. **CCB** (Concurrency-Limited Circuit Breaker) считает не только сбои, но и активные in-flight вызовы; при concurrency > limit (нижестоящий сервис медленный — pending-запросы накапливаются) — OPEN. **Adaptive concurrency-limits** (Netflix concurrency-limits, Envoy adaptive): динамически вычисляет оптимальную конкурентность через алгоритм типа TCP Vegas (задержка растёт → уменьшать конкурентность), не требует ручной настройки. Resilience4j, Hystrix (устарел), Polly.

### Q50: Bulkhead — что это и где границы изоляции.
**A:** Bulkhead — изоляция ресурсов между нижестоящими сервисами, чтобы сбой одного не утопил все. Уровни изоляции: (1) **Изоляция пула потоков** — отдельный пул потоков на каждый нижестоящий сервис; пул medium-downstream насыщается, но critical-downstream остаётся отзывчивым; (2) **Изоляция пула соединений** — отдельный JDBC/HTTP-пул на каждую зависимость; (3) **Изоляция процесса / контейнера** — отдельный sidecar или сервис; самая дорогая, но самая надёжная. Компромисс: больше изоляция = больше ресурсов. Hystrix исторически использовал пул потоков на команду; современные подходы (Resilience4j) предпочитают семафор (легче) + адаптивный concurrency-limit.

### Q51: Hedged requests — как уменьшить задержку хвоста.
**A:** Идея: дублировать запрос после `p95` оригинала; ответ берём от того, кто ответил первым. Задержка хвоста p99 уменьшается в 5–10 раз. Цена: дополнительная нагрузка ~5% (только запросы, превышающие p95, дублируются), плюс побочный эффект: hedged-запросы должны быть идемпотентными или отменяемыми (Google использует отмену `read-after-write`). Развитие: **tied requests** — дубликат шлётся одновременно на нескольких бэкендах, но с tied-протоколом — кто первый принимает в обработку, остальные отменяются. Применяется в Google Bigtable, Spanner; экспериментально в gRPC.
> Dean & Barroso — «The Tail at Scale» (CACM 2013)

### Q52: Сброс нагрузки и плавная деградация — как пережить перегрузку.
**A:** **Сброс нагрузки (load shedding)**: при перегрузке (задержка p99 растёт, очередь растёт) сознательно отбрасывать часть запросов — лучше отказать 10% сразу, чем медленно отвечать всем (нарастание задержки, каскад нарушенных дедлайнов). Реализация: очередь с ограниченным размером + 429/503 при переполнении; адаптивный сброс по утилизации (Google CoDel). **Плавная деградация**: вернуть **меньше**, но что-то полезное. Примеры: (1) **устаревший кэш** — отдать просроченные данные, если БД медленная; (2) **значения по умолчанию** — рекомендации = top-trending вместо персонализированных; (3) **режим только чтения** — отключить записи под нагрузкой, чтения работают; (4) **флаги функциональности** — выключить тяжёлые фичи (полный поиск → поиск по ключевым словам). Принцип: «не уронить весь продукт ради одной фичи».

### Q53: Очередь недоставленных сообщений (DLQ) — когда сообщение туда попадает и как восстанавливать.
**A:** **DLQ** — отдельная очередь, куда отправляются сообщения, которые потребитель не смог обработать после N попыток. Триггеры: (1) ошибка разбора (несовпадение схемы); (2) нарушение бизнес-правила (некорректные данные); (3) нижестоящий сервис сломан окончательно; (4) превышен `max_retries`. Что хранить вместе с сообщением: исходную полезную нагрузку, последнее исключение, число попыток, метки времени, причину. Восстановление: (1) **инструмент переигрывания** — после исправления бага потребителя переложить из DLQ обратно в основную очередь; (2) **ручной разбор** для бизнес-проблем; (3) **алерты** — размер DLQ > порога → page. DLQ без процесса разгребания становится «кладбищем»; должен быть владелец и SLO на разгребание (например, < 100 сообщений за 24 ч).

## 6. Алгоритмы для System Design (Q54–Q62)

### Q54: Bloom filter — математика, гарантии, сценарии.
**A:** Битовый массив размера `m` + `k` независимых хэш-функций. Вставка: установить `k` бит. Проверка принадлежности: проверить `k` бит — если все 1, элемент возможно во множестве; если хоть один 0, точно нет. **Ложных отрицательных нет**; доля ложных положительных `p ≈ (1 - e^(-kn/m))^k`. Оптимальное `k = (m/n) * ln(2)`. На практике: **~10 бит на ключ даёт ~1% ложных срабатываний**, ~14 бит → 0,1%. Сценарии: проникновение в кэш (проверить «может ли быть в БД» до запроса), фильтр на каждую SSTable в LSM-tree (LevelDB/RocksDB) для пропуска SSTable без чтения с диска, дедупликация веб-краулера, распределённый join (Bloom join — узлы шлют Bloom вместо полных ключей).

### Q55: Count-Min Sketch против HyperLogLog — разные задачи.
**A:** **Count-Min Sketch (CMS)** — приближённая оценка частоты: «сколько раз встречался ключ X». Матрица `d × w` счётчиков с `d` независимыми хэш-функциями; инкремент — увеличить `d` ячеек; запрос — взять минимум. **Завышает** (никогда не занижает). Применение: top-K на потоке (heavy hitters), ограничение скорости без точных счётчиков. **HyperLogLog (HLL)** — приближённый подсчёт уникальных: «сколько уникальных значений в потоке». Использует max leading zeros в хэше как индикатор мощности + гармоническое среднее по корзинам. ~12 КБ даёт погрешность ~2% на миллиардах уникальных. Применение: уникальные посетители сайта, уникальные IP, BigQuery `APPROX_COUNT_DISTINCT`. CMS отвечает «сколько раз», HLL — «сколько разных»; путают часто.

### Q56: HyperLogLog — почему гармоническое среднее и какая память.
**A:** HLL делит хэш на (корзина, максимум ведущих нулей): первые `b` бит — индекс корзины (`m = 2^b` корзин), остальные — счётчик максимума ведущих нулей в этой корзине (чем больше нулей подряд, тем более «уникальный» хэш попал в эту корзину — это и есть индикатор большой мощности). Оценка: `E = α_m * m² / Σ(1 / 2^M[i])` — гармоническое среднее чувствительно к малым значениям, что снижает влияние выбросов в корзинах. Стандартная ошибка ≈ `1.04 / √m`. При `m = 16384` (b=14) — ~12 КБ и погрешность ~0,81%. Дополнительно для малых мощностей используется linear counting (sparse-представление в Redis HLL). Главное: память **константная**, не зависит от мощности — это бьёт `HashSet`, который растёт линейно.
> Flajolet et al. — «HyperLogLog: the analysis of a near-optimal cardinality estimation algorithm»

### Q57: Geohash против S2, H3, Quadtree, R-tree — когда что выбрать.
**A:**
- **Geohash**: 2D → 1D через кривую Z-order (чередование битов lat/lng); префикс = большая ячейка, длиннее = меньше. Простой, есть в Redis (`GEOADD`). Минус: соседние ячейки могут иметь сильно разные префиксы (скачок на границах) → нужно проверять 8 соседей.
- **S2** (Google): 2D на сферу Земли → ячейки через кривую Гильберта. 30 уровней, точность от глобуса до 1 см². Лучше учитывает кривизну; используется в Google Maps, Foursquare.
- **H3** (Uber): шестиугольная сетка, 16 уровней. Преимущество шестиугольников: одинаковое расстояние до всех 6 соседей (у квадратов 4 + 4 диагональных разной длины) → точнее для близости и кластеризации. Используется Uber, Hexagon.
- **Quadtree**: рекурсивное деление 2D-пространства на 4. Хорош для адаптивной плотности (мегаполис делится мельче), in-memory структура; ElasticSearch GeoPoint.
- **R-tree**: индекс для bounding box произвольных объектов (не точек); PostGIS `GIST`, MongoDB 2dsphere. Универсален для геометрии.

### Q58: Почему Uber выбрал H3 (шестиугольную сетку)?
**A:** Шестиугольники дают равноудалённость 6 соседей (у квадратов диагональные дальше прямых на √2); это критично для **близостных** запросов: динамическая надбавка к цене (surge), сопоставление водитель-пассажир, ETA. На квадратной сетке артефакты — водитель чуть за углом квадрата выглядит «далеко» из-за смены ячейки. Шестиугольники также дают более плавные «контуры» зон. H3 — иерархическая (parent/child cells), 16 уровней (от ~1 100 км до ~1 м²), быстрая геометрия: `latLngToCell`, `cellToBoundary`, `gridDisk(k)` для соседей в радиусе. Open source (Uber, 2018).

### Q59: Trie для автодополнения с предвычисленным top-K.
**A:** Trie — префиксное дерево, каждый узел — символ; путь от корня — префикс. Поиск всех слов с префиксом — O(длина префикса). Для автодополнения нужны **top-K** подсказок, а не все — наивно: на каждый запрос обходить поддерево (дорого при популярных префиксах). Оптимизация: в каждом узле хранить **предвычисленный top-K** (полный список + частоты, обновляемый офлайн). Запрос: O(префикс) + копия top-K. При вставке или обновлении частот — поднимать изменения вверх по цепочке. Для огромных словарей (веб-поиск, миллионы+) — компактнее: Aho-Corasick для multi-pattern, FST (term dictionary в Lucene) или DAWG (направленный ациклический граф слов). Дополнительные фичи автодополнения: ранжирование по истории пользователя, нечёткое совпадение (расстояние редактирования), trending boost.

### Q60: Инвертированный индекс — структура и ранжирование TF-IDF против BM25.
**A:** **Инвертированный индекс** — `term → posting list` (список doc_id, где встречается term, плюс позиции и частоты). Запрос «red car» → пересечение posting lists `red` и `car`. **TF-IDF**: `score = TF(t,d) * IDF(t)`; TF — частота терма в документе (часто `log(1 + tf)`, чтобы избежать линейного масштаба), IDF — `log(N / df)` (редкие термы важнее). **BM25** — модернизация TF-IDF: насыщение терма (`TF / (TF + k1)` — добавление 10-го вхождения даёт меньше, чем 2-го) и нормализация по длине документа (короткий документ с термом релевантнее длинного с тем же TF). `k1 = 1.2..2`, `b = 0.75` — стандартные параметры. BM25 — ранжирование по умолчанию в Elasticsearch / OpenSearch / Lucene с 2016.
> Robertson & Zaragoza — «The Probabilistic Relevance Framework: BM25 and Beyond»

### Q61: Merkle tree для anti-entropy между репликами.
**A:** Merkle tree — бинарное дерево хэшей: листья = хэши блоков данных, внутренние узлы = хэш конкатенации детей. Корневой хэш суммирует всё содержимое. Для anti-entropy между репликами: (1) каждая реплика строит Merkle tree своих данных по диапазонам ключей; (2) реплики обмениваются корневым хэшем; (3) если совпало — данные идентичны, синхронизация не нужна; (4) если различаются — рекурсивно сравнивают детей, доходят до конкретных diff-блоков, синхронизируют **только их**. Стоимость передачи — O(log N) вместо O(N) полной синхронизации. Используется в Dynamo, Cassandra, Riak; также в Git (хранение объектов), Bitcoin (SPV-доказательства), синхронизация файлов (rsync — частично похожая идея).

### Q62: Bloom filter в LSM-tree — зачем на каждую SSTable и как ускоряет?
**A:** LSM-tree: записи → MemTable → flush → SSTables на диске. На чтение нужно проверить MemTable и **все** SSTables от новых к старым до попадания. Если ключа в БД нет — пришлось бы прочитать все SSTables (несколько disk seek). **Bloom filter на каждую SSTable**: при чтении сначала спросить BF — «есть ли ключ?»; если BF говорит «нет» — пропускаем SSTable без чтения с диска. Маленькая доля ложных срабатываний (1%) — иногда зря читаем SSTable, но в среднем 99% чтений получают точный ответ без I/O. Размер: ~10 бит/ключ → ~12 МБ на миллиард ключей. Применяется в LevelDB, RocksDB, Cassandra, ScyllaDB. Аналогично — partition summary file для range-запросов.

## 7. Коммуникация (Q63–Q67)

### Q63: Короткий опрос / длинный опрос / SSE / WebSocket / потоковая передача gRPC — матрица выбора.
**A:**
| Шаблон | Направление | Постоянное соединение | Задержка | Сценарии |
|---|---|---|---|---|
| Короткий опрос | Клиент → сервер | Нет | Интервал опроса | Простые обновления, RSS, панели |
| Длинный опрос | Клиент ↔ сервер (отложенный ответ) | Во время ожидания | ~миллисекунды | Реальное время без инфраструктуры WebSocket |
| **SSE** | Сервер → клиент (односторонний) | Да (HTTP) | Реальное время | Уведомления, ленты, логи, отправляемые сервером |
| **WebSocket** | Двунаправленное | Да | Реальное время | Чат, игры, совместное редактирование |
| **Потоковая передача gRPC** | Двунаправленное (потоки HTTP/2) | Да | Реальное время | Внутренние сервисы с типизированными контрактами |

Эволюция: короткий опрос → длинный опрос → SSE → WebSocket → потоковая передача gRPC (по мере роста требований к задержке, пропускной способности и инструментам).

### Q64: SSE против WebSocket — почему SSE проще для одностороннего канала?
**A:** **SSE** (Server-Sent Events) — обычный HTTP-ответ с `Content-Type: text/event-stream`, который сервер держит открытым и шлёт сообщения построчно. Преимущества: (1) работает через любой HTTP-прокси и межсетевой экран (это просто долгий HTTP-ответ); (2) автоматическое переподключение и курсор (`Last-Event-ID`) встроены в браузер; (3) только текст, проще отлаживать. **WebSocket** требует upgrade-рукопожатие, бинарный фрейминг, отдельный код для переподключения; зато двунаправленный и бинарный. Для односторонней отправки (уведомления, цены в реальном времени, потоковая передача логов) SSE достаточен и проще. WebSocket нужен, когда требуется клиент → сервер по тому же каналу (чат, игры). Подводный камень SSE: некоторые старые прокси буферизуют ответы и ломают потоковую передачу (надо `X-Accel-Buffering: no` для Nginx).

### Q65: Обратное давление (backpressure) — как защитить нижестоящий сервис от перегрузки.
**A:** **Обратное давление** — механизм, при котором потребитель контролирует темп получения данных от производителя; производитель тормозит или буферизует, не утопит потребителя. Реализации: (1) **Reactive Streams** (Project Reactor, RxJava, потоковая передача gRPC) — `request(n)` явно запрашивает n элементов; производитель не шлёт больше; (2) **очереди с ограниченным размером** — если очередь переполнена, производитель блокируется или роняет; (3) **TCP flow control** — встроено в транспорт (sliding window). Анти-шаблон: неограниченная очередь в middleware (Kafka может казаться бездонной, но память producer ограничена). На уровне сервисов обратное давление часто заменяется **сбросом нагрузки** (см. Q52) — отказать вместо тормозить.

### Q66: Webhooks — HMAC-подпись, идемпотентность, политика повторов.
**A:** Webhook — отправитель шлёт HTTP POST на URL получателя при событии. Безопасность: (1) **HMAC-подпись** — отправитель шлёт `X-Signature: sha256=...` с подписью полезной нагрузки секретом; получатель проверяет до обработки (защита от подделки); (2) **метка времени** + допустимое окно (5 мин) — защита от **повторной атаки (replay)** (Q67); (3) HTTPS обязателен. **Идемпотентность** на получателе: отправитель гарантирует at-least-once доставку (см. Stripe — повтор 3 суток с экспоненциальной задержкой), получатель должен дедуплицировать по `idempotency_key` или `event_id`. **Политика повторов**: клиент отвечает 2xx — успех; 4xx — постоянный сбой, не повторять; 5xx или таймаут — повтор с экспоненциальной задержкой; после N попыток — DLQ + алерт.
> Stripe Webhooks docs

### Q67: Атака повтора (replay) на webhook — как защититься.
**A:** Атака: злоумышленник перехватывает настоящий webhook-запрос (HMAC валидный!) и повторно отправляет его позже — получатель принимает за свежий, дублирует побочный эффект. Защита: (1) **метка времени в полезной нагрузке** + отправитель включает её в HMAC; получатель проверяет `|now - timestamp| < tolerance` (например, 5 мин); устаревшие отбрасывает. (2) **nonce / event_id** — получатель хранит виденные event ID на 24 ч (Redis), отвергает дубликаты. (3) Комбинированно: метка времени + nonce. Stripe использует обе: `Stripe-Signature: t=timestamp,v1=signature`. HTTPS обязателен — без него повтор тривиален, а MITM подменит полезную нагрузку (HMAC останется валидным, потому что злоумышленник знает секрет, если он утёк).

## 8. Безопасность и идентификация (Q68–Q72)

### Q68: JWT — структура, почему подпись не шифрование, ротация JWKS.
**A:** JWT = `header.payload.signature` (base64url). **Header**: алгоритм (`alg: RS256`) и `kid` (key id). **Payload**: claims (`sub`, `iss`, `aud`, `exp`, `iat`, пользовательские). **Signature**: HMAC (HS256) или асимметричная (RS256/ES256). **Подписан, не зашифрован** — полезная нагрузка читается всеми (base64 не шифр); для шифрования — JWE (редко). **JWKS** (JSON Web Key Set): IdP публикует `https://issuer/.well-known/jwks.json` с публичными ключами; потребитель кэширует ключи и проверяет подпись по `kid` из header. **Ротация**: IdP добавляет новый ключ с новым `kid`, шлёт новые токены, подписанные новым ключом; старый ключ остаётся в JWKS, пока живые токены не истекут. Подводный камень: `alg: none` — известный эксплойт (если потребитель не проверяет белый список alg, злоумышленник шлёт неподписанный JWT и его принимают за валидный).

### Q69: Отзыв JWT — стратегии и компромиссы.
**A:** JWT по дизайну без состояния → отзыв сложен. Стратегии:
- **Короткий TTL + refresh-токены**: access-токен 5–15 мин, refresh-токен живёт долго, проверяется на сервере (в БД). Отзыв = удалить refresh-токен. Просто, по умолчанию в OIDC.
- **Чёрный список (deny-list)**: хранить отозванные `jti` (JWT ID) в Redis с TTL = оставшийся срок действия. Каждый запрос проверяет deny-list. Компрометирует природу без состояния, но контроль точный.
- **Белый список / session ID внутри JWT**: JWT содержит session_id, который проверяется в Redis (фактически — обычная сессия, JWT просто как контейнер). Преимуществ без состояния — ноль.
- **Ротация ключей**: отзыв массово через смену ключа подписи (все токены становятся невалидны). Грубо, но эффективно при крупном инциденте.

Прод: короткий TTL + ротация refresh-токенов как база, deny-list для срочных отзывов (выход с устройства, force logout).

### Q70: Flows OAuth2 — Authorization Code+PKCE, Client Credentials, ротация Refresh.
**A:**
- **Authorization Code + PKCE**: для пользовательских flow (веб, мобильные, SPA). Клиент делает `code_challenge = SHA256(code_verifier)`, шлёт IdP. После согласия IdP редиректит с `code`. Клиент обменивает `code` + `code_verifier` на access/refresh-токены. PKCE защищает от перехвата кода (для SPA — обязателен, секрет клиента хранить негде).
- **Client Credentials**: для machine-to-machine. Клиент шлёт `client_id` + `client_secret` → access-токен. Контекста пользователя нет.
- **Ротация refresh-токена**: каждый refresh выпускает новый refresh-токен и инвалидирует старый. Если злоумышленник украл refresh и использовал — следующий refresh настоящего пользователя свалится, можно автоматически отозвать. OAuth 2.1 предписывает ротацию для публичных клиентов.
- Устарели: **Implicit flow** (выдавал токен прямо в URL, легко утекал в логи/историю), **Resource Owner Password Credentials** (пользователь даёт пароль клиенту — анти-шаблон).

### Q71: OIDC и SAML — где разница и где какой использовать.
**A:** **OIDC** (OpenID Connect) — слой идентичности поверх OAuth2: добавляет `id_token` (JWT с claims о пользователе: `sub`, `email`, `name`, `picture`). Современный, JSON, легковесный, удобен для веба/мобильных/API. Все потребительские IdP (Google, Auth0, Okta) → OIDC. **SAML 2.0** — XML, корпоративный SSO-стандарт. IdP → SP через browser POST с подписанным SAML Assertion (XML). Тяжёлый, сложный (XML-подписи, namespaces), но **обязателен** в энтерпрайзе (Active Directory Federation Services, Workday, Salesforce). Прод: OIDC для приложений к пользователям; SAML — для энтерпрайз B2B SSO. Многие IdP (Keycloak, Okta) поддерживают оба; Keycloak умеет identity brokering: SAML → внутренний OIDC, чтобы приложение говорило только OIDC.

### Q72: Защита от DDoS — слои.
**A:** Защита от DDoS — стек, ни один уровень не закрывает всё.
1. **Anycast + поглощение CDN** (Cloudflare, CloudFront): атака размывается по сотням POP; CDN отбрасывает мусор до источника.
2. **L3/L4 фильтрация**: SYN cookies против SYN flood; ограничение скорости на IP/ASN; uRPF против spoofed-источников.
3. **Ограничение скорости на L7**: token bucket на пользователя/IP/API key; многоуровневые лимиты.
4. **WAF** (Web Application Firewall) с OWASP CRS: блокировка SQLi, XSS, path traversal, известных сигнатур ботов.
5. **Управление ботами** (Cloudflare Bot Fight Mode, Akamai Bot Manager): JS-проверки, поведенческий анализ, скоринг на основе ML.
6. **Адаптивное ограничение на уровне приложения**: при росте задержки p99 включается сброс нагрузки (Q52).
7. **Captcha / proof-of-work** как последняя мера для подозрительного трафика.

Дополнительно: **Zero Trust / BeyondCorp** — внутренние сервисы не доступны из сети без mTLS + идентичности; убирает «защищённый периметр» как концепцию.

## 9. Потоковая обработка и современное (Q73–Q80)

### Q73: MapReduce → Spark → Flink — эволюция и где какая система.
**A:** **MapReduce** (Google 2004, Hadoop): пакетная обработка, map → shuffle → reduce, всё через HDFS между стадиями (медленно, но restart-friendly). **Spark** (2009): RDD (Resilient Distributed Dataset) + ленивое выполнение DAG; данные в памяти между стадиями → в 10–100 раз быстрее MR на итеративных задачах (ML, графы). Поддерживает потоковую передачу через **микропакеты** (Spark Streaming) — задержка секунды. **Flink** (2014): настоящая потоковая обработка с семантикой event-time, **водяные знаки**, **exactly-once** через распределённые снапшоты (Chandy-Lamport), задержка миллисекунды; пакет — частный случай потока. Прод: Spark для аналитики/ML в пакете и почти реального времени; Flink для настоящей потоковой обработки (обнаружение мошенничества, ценообразование в реальном времени); MapReduce — унаследованный стек.

### Q74: Архитектура Lambda против Kappa.
**A:** **Lambda** (Nathan Marz, 2011): два параллельных пайплайна — **пакетный слой** (Hadoop, точные результаты, задержка часы) и **скоростной слой** (Storm/Spark Streaming, приблизительные, задержка секунды); обслуживающий слой объединяет. Минус: две кодовых базы, две логики — дублирование и сложность поддержки. **Kappa** (Jay Kreps, 2014): только потоковый слой; переобработка = переигрывание с начала журнала Kafka с новой версией кода. Возможна благодаря хранению Kafka (могут быть дни/недели) и быстрому Flink/Spark. Прод: индустрия сместилась к Kappa-like (один пайплайн на Flink), где пакет — это сценарий переигрывания, не отдельная система.

### Q75: Event-time против processing-time и водяные знаки — что они дают.
**A:** **Время обработки**: время обработки события в системе (wall clock машины). Простое, но недетерминировано: тот же стрим — разные результаты при переигрывании. **Время события**: время реального события (метка в полезной нагрузке). Детерминировано, но требует обработки **неупорядоченных** событий (лагающие мобильные клиенты могут приходить с опозданием на минуты). **Водяной знак** — нижняя граница времени события, гарантирующая «события старше этого времени уже не придут (с высокой вероятностью)». Когда водяной знак пересекает конец окна — окно закрывается, результат отдаётся. Опоздавшие события (после водяного знака) либо игнорируются, либо обновляют результат (allowed lateness). Flink даёт первоклассную поддержку водяных знаков; Kafka Streams тоже; Spark Structured Streaming — позже.

### Q76: Развёртывание ML-моделей — онлайн против пакетного инференса и роль feature store.
**A:** **Пакетный инференс**: предсказания для всех (или большой когорты) пользователей офлайн, результат пишется в KV/БД, веб подаёт просто через выборку по ключу. Дёшево, подходит для медленно меняющихся предсказаний (рекомендации на завтра, риск оттока). **Онлайн-инференс**: модель живёт постоянно, делает предсказание на каждый запрос (обнаружение мошенничества в реальном времени, динамическое ценообразование, ранжирование выдачи). Требует низкозадержечного обслуживания (< 50 мс p99), выборки признаков в горячем хранилище (Redis, DynamoDB), часто GPU. **Feature store** (Feast, Tecton): центральный реестр признаков с двумя хранилищами — офлайн (BigQuery/S3 для обучения) и онлайн (Redis для инференса). Решает train/serve skew: одна логика расчёта признаков. **Реестр моделей** (MLflow, Weights & Biases) — версионирование моделей: какая версия в продакшене, происхождение от обучающих данных.

### Q77: Теневое развёртывание / canary для ML-моделей.
**A:** ML-модели требуют дополнительной осторожности: «готово к проду» по тестам не гарантирует качество на реальном трафике. Подходы:
- **Теневое развёртывание**: новая модель получает копию продакшен-трафика, но её предсказания **не возвращаются** пользователю — только логируются и сравниваются с прод-моделью офлайн. Задержка и качество данных оцениваются без риска для бизнес-метрик.
- **Канареечное** (как обычно): 1% → 10% → 100% реального трафика; мониторинг бизнес-метрик (CTR, конверсия, не только задержка и доля ошибок).
- **A/B-тестирование**: статистически значимое сравнение моделей на сегментах, бизнес-метрики решают.
- **Champion-Challenger**: прод-модель = champion, новые предлагаются как challenger; авто-продвижение, если challenger лучше N дней подряд.

Подводный камень: дрейф модели — модель деградирует со временем (сдвиг распределения входных данных); нужна непрерывная оценка и пайплайн переобучения, не только при развёртывании.

### Q78: Векторные БД — компромиссы HNSW, IVF, PQ.
**A:** Индексы приближённых ближайших соседей (ANN):
- **HNSW** (Hierarchical Navigable Small World): многослойный граф; на верхних слоях редкие узлы дают быстрый «прыжок» близко к цели, нижние — точная навигация. Полнота (recall) 95–99% при суб-10 мс на миллионах векторов. Тяжёлая память (граф в RAM), быстрая вставка, плохо сжимается. По умолчанию в Pinecone, Weaviate, pgvector с 0.6+.
- **IVF** (Inverted File): кластеризация векторов на K центроидов; запрос сравнивается только с N ближайшими центроидами и их членами. Меньше памяти, хуже полнота (~80–90%), нужно перестроение индекса при больших изменениях.
- **PQ** (Product Quantization): разбить вектор на subvectors, каждый кодировать индексом в codebook (например, 8 байт вместо 1024 float). Радикально снижает память (в 10–50 раз), теряет точность. Часто IVF + PQ в комбинации (FAISS).

Прод: HNSW по умолчанию; IVF/PQ, если миллиарды векторов и память дорогая.
> Malkov & Yashunin — HNSW paper (2016)

### Q79: RAG — нарезание на сегменты, переранжирование, защита от галлюцинаций.
**A:** RAG (Retrieval-Augmented Generation): пользовательский запрос → эмбеддинг → ANN-поиск → top-K документов → передать LLM как контекст → сгенерировать ответ. Качество зависит от:
- **Нарезание на сегменты**: разбиение документов на куски. Слишком крупные (5K токенов) — теряется точность извлечения; слишком мелкие (100 токенов) — теряется контекст. Sweet spot ~500–1500 токенов с перекрытием 10–20%.
- **Гибридное извлечение**: векторный поиск + BM25 (по ключевым словам) скомбинированы через reciprocal rank fusion. Ловит точное совпадение терминов, которые эмбеддинг теряет.
- **Переранжирование**: после извлечения top-100 — пропускать через cross-encoder (более точная, но дорогая модель) для точного top-K. Cohere Rerank, BGE-reranker.
- **Защита от галлюцинаций**: (1) явный промпт «отвечай только из контекста; если нет — скажи «не знаю»»; (2) ссылки на источники в ответе с возможностью проверки; (3) скоринг уверенности через порог сходства извлечения; (4) ограничители (Nemo Guardrails) для фильтра выходов.

### Q80: pgvector против Pinecone против Weaviate — когда какой?
**A:**
- **pgvector** (расширение PostgreSQL): векторный индекс в обычном Postgres; идеален, когда у вас уже PG, ANN — побочная фича. Джоины с реляционными данными, транзакции, не нужен отдельный сервис. Лимит: миллионы векторов (десятки миллионов — граница); HNSW добавлен в pgvector 0.5.
- **Pinecone**: managed векторная БД, полностью serverless; высокий QPS, авто-масштабирование; закрытый исходник, привязка к вендору. Для прода, когда не хотите ops.
- **Weaviate / Qdrant / Milvus**: self-hosted open source; больше гибкости, гибридный поиск встроен (Weaviate), фильтрация по метаданным. Операционные накладные расходы есть.
- **Elasticsearch / OpenSearch с dense_vector**: если у вас уже ES для полнотекстового поиска, вектор добавляется естественно; гибрид (BM25 + вектор) из коробки.

Решение по масштабу + зрелости против операционной стоимости: < 10M векторов — pgvector почти всегда хватит; 100M+ или строгий SLA по задержке — выделенная векторная БД.

## 10. Инсайты по проектным задачам (Q81–Q90)

### Q81: Сокращатель URL — base62 против UUID против сервиса генерации ключей?
**A:** Цель — короткий, уникальный, неперебираемый по порядку (приватность). **Counter + base62**: просто, 7 символов покрывают `62^7 ≈ 3,5 × 10^12`, но требует единого счётчика (lock contention) или партиционированных счётчиков (Twitter Snowflake). **UUID**: легко генерируется, но 128 бит → 22+ символов после base62 — слишком длинно для сокращателя URL. **Hash(URL)**: предсказуемо, легко дедуплицировать одинаковые URL, но коллизии нужно ловить. **Сервис генерации ключей (KGS)**: отдельный сервис пакетно генерирует ID и раздаёт батчами; каждый сервер приложения резервирует блок из 1000, выдаёт локально, забирает следующий при истощении. Защита от двойной выдачи: KGS помечает блок как использованный при выдаче. Прод: KGS + base62 — стандарт.

### Q82: Лента новостей — fan-out на запись против чтения и проблема знаменитостей.
**A:** **Fan-out на запись (push)**: при посте автор пишет в feed-table каждого подписчика. Чтение — простой `SELECT FROM feed WHERE user=X ORDER BY time` (быстро). Минус: для знаменитостей (100M подписчиков) каждый пост = 100M записей; **проблема знаменитостей**. **Fan-out на чтение (pull)**: лента формируется при запросе: `SELECT FROM posts WHERE author IN (followees) ORDER BY time`. Чтение дорого, запись дёшево. Минус: для активных пользователей с 1K подписок — поиск по большому набору. **Гибрид push-pull**: обычные авторы → push (fan-out на запись); знаменитости → pull (читатель сам подмешивает их посты в свою ленту). Порог: автор с >10K подписчиков переключается на режим pull. Twitter, Instagram используют гибрид.

### Q83: Мессенджер — at-least-once доставка + идемпотентность + присутствие.
**A:** **Доставка**: клиент → брокер (Kafka) → получатель. At-least-once с повторами; получатель дедуплицирует по `message_id` (UUID, сгенерированный клиентом). Постоянное хранение: хранить сообщения в БД (Cassandra, HBase) с partition key = conversation_id, sort key = метка времени. **Присутствие**: heartbeat от клиента каждые 30 с в Redis с TTL 60 с; сервис подписан на keyspace-уведомления Redis для обновлений присутствия. Альтернатива: эфемерные узлы ZooKeeper (как WhatsApp исторически). **WebSocket** для отправки в реальном времени, запасной вариант — длинный опрос / push-уведомления (APNS, FCM) для офлайн-клиентов. **Сквозное шифрование (E2E)** (Signal Protocol): X3DH + Double Ratchet, ключи на устройстве, сервер только пересылает зашифрованное. Подводный камень: групповые чаты с E2E — каждое сообщение шифруется N раз для N участников (или sender keys).

### Q84: Поездки на заказ — почему H3 hex и как работает надбавка (surge).
**A:** H3 (см. Q58) даёт равноудалённость 6 соседей — критично для близости. Диспетчеризация: новая поездка → найти водителей в радиусе через `gridDisk(rider_cell, k)` (например, k=2 → 19 шестиугольников); сортировка по ETA, не по евклиду (реальная дорожная дистанция). **Надбавка к цене (surge)**: для каждой ячейки в реальном времени считаем отношение `спрос/предложение` (Kafka-события: ride_requested, driver_available); при отношении выше порога поднимаем коэффициент. Надбавка динамична (обновление каждые 30–60 с), но плавная (сглаживание, иначе пользователи видят прыжки $5 → $25). Алгоритм должен бороться с положительной обратной связью (повысили надбавку → водители съезжаются → отношение падает → дроп надбавки → водители уезжают → надбавка снова растёт). Решения: гистерезис, усреднение по временному окну, минимальное время в режиме надбавки.

### Q85: Видеостриминг — адаптивный битрейт и стратегия CDN.
**A:** **Адаптивный битрейт** (HLS / DASH): видео закодировано в 5–7 качествах (240p–4K), нарезано на сегменты по 2–10 с. Манифест (m3u8 для HLS, mpd для DASH) — список сегментов на каждом качестве. Плеер оценивает полосу (по скорости загрузки предыдущих сегментов), выбирает оптимальное качество для следующего; перестраивается каждый сегмент. **Стратегия CDN**: горячие видео заранее закачиваются на пограничные узлы (push); long-tail-контент по pull-кэшу. Чувствительные к задержке (живой стрим): low-latency HLS (LL-HLS) с 1-секундными сегментами. Оптимизация стоимости: многоуровневое хранилище (горячее — SSD на пограничном узле, тёплое — источник, холодное — S3 Glacier для legacy). Пайплайн кодирования (см. Q85 в DESIGN_05): загрузка → S3 → Kafka-событие → обработчики кодирования (Spark / выделенные) → транскодированные версии → CDN.

### Q86: Распределённый кэш — consistent hashing + виртуальные узлы + горячий ключ.
**A:** **Consistent hashing**: хэш-кольцо, ключи и узлы на нём; ключ → ближайший по часовой стрелке узел. Добавление/удаление узла двигает только `1/N` ключей (против `(N-1)/N` для наивного `hash % N`). **Виртуальные узлы**: каждый физический узел представлен 100–500 точками на кольце → равномерное распределение, плавная перебалансировка при добавлении. **Rendezvous hashing** (HRW) — альтернатива: для ключа выбрать узел с максимумом `hash(key + node)`; не нужно кольцо, но O(N) на ключ (на практике быстро для N до тысяч). **Горячий ключ**: один ключ перегружает один узел. Способы защиты: (1) **реплицировать горячие ключи** на K узлов, клиент читает случайный (запись — на все); (2) **клиентский кэш** для самых горячих ключей; (3) **шардировать горячий ключ** через суффикс (Redis Cluster `{key}:1, {key}:2`); (4) обнаруживать через мониторинг top-K на cache-сервере.

### Q87: Система уведомлений — маршрутизация по каналам, повторы с DLQ, расписание.
**A:** Архитектура: продюсер публикует `Notification(user_id, type, payload)` → сервис настроек выбирает каналы (push / email / SMS) на основе предпочтений пользователя → веерная рассылка в Kafka-топик на канал → обработчик канала (FCM/APNS для push, SendGrid/SES для email, Twilio для SMS). У каждого обработчика своя политика повторов: push 3 раза за 1 час, email — 5 раз за 24 часа, SMS — 2 раза за 30 мин (SMS дорогой, не молотим). **DLQ** на канал — сообщения после исчерпания повторов для ручного разбора / переигрывания. **Расписание**: отложенные уведомления через очереди с временными корзинами (TimerWheel) или Kafka с producer-set timestamp (потребитель спит до часа N). **Ограничение скорости на пользователя**: никто не любит 50 push-уведомлений в день — лимит на пользователя через Redis sliding window. **Дедупликация**: ключ идемпотентности для предотвращения дублей при повторе продюсера.

### Q88: Веб-краулер — вежливость, очередь URL, дедупликация через Bloom.
**A:** **Очередь URL (frontier)**: приоритетная очередь URL к обходу; разделена на домены для **вежливости** (не более 1 запроса на домен в N секунд, иначе похоже на DDoS). Реализация — распределённые Redis-очереди, партиционированные по хэшу домена. **robots.txt**: разбирается, кэшируется (TTL на домен 24 ч); запрещённые пути не обходятся. **Дедупликация**: уже посещённые URL в Bloom filter (~миллиарды URL × 10 бит/ключ ≈ ТБ RAM кластерно). Доля ложных срабатываний до 1% — несколько повторных обходов, не критично. **Дедупликация содержимого**: hash(content) для определения дубликатов страниц с разных URL (зеркала, варианты query-string). **Бюджет обхода**: приоритизация по PageRank-подобному скору + свежесть (свежесть против охвата). Распределённые краулеры через consistent hashing по домену — каждый обработчик отвечает за свой набор доменов.

### Q89: KV-хранилище в стиле Dynamo — vnodes, кворум, sloppy quorum + hinted handoff, anti-entropy через Merkle.
**A:** Архитектура Dynamo (и потомков — Cassandra, Riak): (1) **Consistent hashing + vnodes** — равномерное распределение и плавная перебалансировка; (2) **N реплик** (обычно 3); (3) **Кворум на чтение и запись** R+W>N для строгой согласованности; R=W=1 — итоговая; (4) **Sloppy quorum + hinted handoff**: если одна из N реплик недоступна, запись идёт на следующий доступный узел с `hint` — кому передать, когда оригинал восстановится. Даёт высокую доступность записи в разделе, ценой временного нарушения инварианта R+W>N; (5) **Anti-entropy**: периодический обмен Merkle tree между репликами для нагона пропущенных записей (см. Q61); (6) **Read repair**: при кворумном чтении обнаружены расходящиеся версии → последняя записывается всем репликам в фоне; (7) **Векторные часы** для обнаружения конфликтов между конкурентными записями; разрешение — логика приложения (Riak) или LWW (Cassandra).
> Dynamo paper — DeCandia et al. (SOSP 2007)

### Q90: Платёжная бухгалтерская книга — double-entry, идемпотентность, Saga, требования к хранению.
**A:** **Double-entry accounting**: каждая транзакция — 2+ записи (дебет одного счёта, кредит другого), сумма по всем счетам всегда 0. Невозможно «потерять» деньги: периодический `SUM(balance)` должен сходиться. **Идемпотентность** обязательна: клиент шлёт `idempotency_key` для каждого списания; повтор с тем же ключом возвращает кэшированный результат (см. Q24). **Saga** для составных переводов (USD → EUR через промежуточный счёт): шаги hold_source → debit_source → credit_dest → release_hold; компенсация в обратном порядке при сбое. **Итоговая согласованность** недопустима — итоговый баланс должен быть точным; используется PostgreSQL/MySQL с serializable isolation для критичных записей, append-only журнал для аудита (часто event sourcing). **Требования к хранению**: PCI DSS — не хранить полную карту в БД (токенизация через Stripe/Adyen); SOX — храним audit trail минимум 7 лет; GDPR — конфликт между «правом на забвение» и хранением для аудита решается через крипто-стирание (удалить ключ → данные нечитаемы) или анонимизацию.
