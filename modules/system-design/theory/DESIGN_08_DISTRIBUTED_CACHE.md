# Проектная задача: распределённый кэш (Memcached / Redis Cluster)

Общий кэш на N экземпляров приложений. Главные сложности: распределение данных (consistent hashing), репликация для высокой доступности, инвалидация.

> **Область:** уровень дизайна. Шаблоны кэширования, алгоритмы вытеснения, Caffeine/Redis в глубину — в [`caching-deep-dive/`](../../../caching-deep-dive/).

---

## 1. Требования

### Функциональные
- GET key → value;
- PUT key value [TTL];
- DELETE key;
- (опционально) счётчики (INCR), структуры (Hash, List, Set, ZSet).

### Нефункциональные
- **Низкая задержка** — p99 < 10 мс;
- **Высокая пропускная способность** — 100K–1M операций/с;
- **Масштабируемость** — добавление узлов для ёмкости;
- **Высокая доступность** — отказ узла не теряет все данные;
- **Допустима итоговая согласованность** — кэш «приближение», источник истины — БД.

---

## 2. Оценка

```
1B элементов в кэше, в среднем 1 КБ → рабочий набор 1 ТБ
Пик 1M операций/с по кластеру

Один Redis-узел:
  - 100K–1M операций/с (упирается в сеть > 1 Гбит/с)
  - ~100 ГБ RAM практический предел

→ Нужно 10–20 шардов на 1 ТБ / 1M операций
```

---

## 3. Архитектура

```
Клиент (умный, знает топологию)
  ↓
  ├── Узел 1 (шард 0, первичный)
  ├── Узел 2 (шард 1, первичный)
  ├── Узел 3 (шард 2, первичный)
  ├── Реплика узла 1 (шард 0, реплика)
  ├── Реплика узла 2 (шард 1, реплика)
  └── Реплика узла 3 (шард 2, реплика)

Чтения → первичный (или реплика для масштабирования чтений)
Записи → первичный
Асинхронная репликация первичный → реплика
```

---

## 4. Распределение — consistent hashing

Сопоставление key → шард через consistent hashing.

Теория — в [`SHARDING.md` (databases)](../../databases/theory/SHARDING.md#consistent-hashing) и [`caching-deep-dive/DISTRIBUTED_CACHING.md`](../../../caching-deep-dive/theory/DISTRIBUTED_CACHING.md).

```python
ring = ConsistentHashRing(virtual_nodes_per_real=200)
ring.add_node("node1")
ring.add_node("node2")
ring.add_node("node3")

shard = ring.get_node(key)  # hash(key) → проходим кольцо → находим узел
```

**При добавлении узла:** перемещается только `1/N` ключей.

**Подход Redis Cluster:** 16384 хэш-слота, статически распределённых по узлам. Перенос слота → онлайн-миграция ключей.

---

## 5. Маршрутизация: на клиенте vs на сервере

### На клиенте (стиль Memcached)

Клиент сам вычисляет шард, подключается напрямую к нужному узлу.

- ✓ Самый быстрый (1 hop);
- ✗ Клиент обязан знать топологию и переживать изменения членства.

### Через прокси (Twemproxy, mcrouter)

Клиент шлёт на прокси, прокси маршрутизирует.

- ✓ Простой клиент;
- ✗ Дополнительный hop, прокси добавляет задержку.

### Кластер на стороне сервера (Redis Cluster, в стиле mongos)

Любой узел принимает запрос, при необходимости делает редирект («MOVED slot to nodeX»).

- ✓ Клиенту достаточно начального списка узлов;
- ✗ Возможен дополнительный hop.

---

## 6. Репликация

### Синхронная vs асинхронная

- **Синхронная** — запись завершается после подтверждения от реплики. Медленнее, нет потери при сбое первичного узла.
- **Асинхронная** — запись возвращается сразу. Быстрее, могут потеряться последние записи при переключении на резерв.

Кэш обычно: **асинхронная** (потеря кэша переживается, перезаливается из БД).

### Количество реплик

- 1 реплика — переживает падение одного узла, без масштабирования чтений;
- 2+ реплик — нагрузка чтения распределяется, выше отказоустойчивость.

Компромисс: затраты на хранилище × (N+1).

---

## 7. Обработка сбоев

### Узел упал

- реплика повышается до первичного;
- клиент (или кластер) обновляет топологию;
- когда узел возвращается — реплицируется с нового первичного.

### Целый шард упал

- все данные шарда потеряны (для кэша — ок);
- либо восстанавливается из снапшота;
- во время восстановления: промахи кэша, всплеск нагрузки на БД.

### Сетевое разделение

- меньшинство перестаёт принимать записи (защита от расщепления кластера);
- кластер переконфигурируется после восстановления.

## 8. Инвалидация кэша

Теория — в [`caching-deep-dive/CONSISTENCY.md`](../../../caching-deep-dive/theory/CONSISTENCY.md).

### Шаблоны

- **Только TTL** — записи автоматически истекают; итоговая согласованность;
- **Write-through инвалидация** — приложение пишет в кэш + БД атомарно (с определённым порядком: сначала БД, потом кэш; либо CAS);
- **На основе CDC** — Debezium передаёт изменения БД потоком → инвалидирует кэш (менее жёсткая связанность);
- **Версионированные ключи** — добавлять версию к ключу (`user:123:v5`), новые данные → новый ключ, старый протухает.

### Что обычно используют

1. Cache-aside (ленивое наполнение): промах чтения → БД → пишем в кэш;
2. TTL для границы свежести;
3. Активная инвалидация только для критичного (изменение цен и т. п.).

---

## 9. Проблема горячего ключа

Один ключ получает непропорциональную нагрузку.

### Способы защиты

- **Репликация** — реплицировать горячий ключ на несколько / все узлы;
- **Разбиение ключа** — `user:bieber:tweets:0..9`, рандомизируем на запись/чтение;
- **Локальный кэш** — приложения кэшируют горячие ключи в памяти процесса;
- **Многоуровневое кэширование** — L1 in-process, L2 распределённый.

Подробнее — в [`caching-deep-dive/ANTI_PATTERNS.md`](../../../caching-deep-dive/theory/ANTI_PATTERNS.md#hot-key).

---

## 10. Персистентность (опционально)

Чистый кэш — только в RAM. Иногда нужна персистентность:

- **Redis RDB** — периодический снапшот;
- **Redis AOF** — append-only журнал;
- **Компромисс:** персистентность добавляет задержку и стоимость. Большинство дизайнов кэша обходятся без неё.

См. [`caching-deep-dive/REDIS.md`](../../../caching-deep-dive/theory/REDIS.md).

---

## 11. Политики вытеснения

Когда кэш переполнен — нужно вытеснять.

- **LRU** — Least Recently Used. Стандарт, подходит для большинства нагрузок.
- **LFU** — Least Frequently Used. Лучше при стабильном горячем наборе.
- **TTL** — фиксированное время жизни.
- **FIFO** — просто, но часто хуже LRU.
- **W-TinyLFU** (по умолчанию в Caffeine) — современный лидер по бенчмаркам.
- **Allkeys-random** — опция Redis (когда все ключи одинаково важны).

См. [`caching-deep-dive/EVICTION_POLICIES.md`](../../../caching-deep-dive/theory/EVICTION_POLICIES.md).

---

## 12. Мониторинг

Ключевые метрики:
- **доля попаданий (hit ratio)** (цель > 90%);
- **задержка** p50/p99;
- **использование памяти** на шард;
- **скорость вытеснения** — высокая = кэш слишком маленький;
- **горячие ключи** — периодическое сканирование top-N.

Перекос между шардами — индикатор плохого распределения ключей.

---

## 13. Компромиссы

### Memcached против Redis

| | Memcached | Redis |
|---|---|---|
| Типы данных | Только string | String, Hash, List, Set, ZSet, Stream, … |
| Персистентность | Нет | RDB / AOF |
| Репликация | Через клиент (сторонние) | Встроенная |
| Кластер | mcrouter / Twemproxy | Redis Cluster |
| Потоки | Multi-threaded | Single-threaded на шард |
| Сценарии | Чистый кэш | Кэш + структуры данных + pub/sub + Lua |

Сейчас Redis доминирует. Memcached — у унаследованных систем или там, где нужен только чистый кэш.

### Централизованный против near-cache

- **Централизованный** (этот дизайн) — один кэш, все приложения работают с ним;
- **Near-cache** (per-app L1 + общий L2) — быстрее локальный поиск, сложнее инвалидация;
- **Реплицированный** — все данные на всех узлах (только небольшие датасеты).

Hazelcast и Apache Ignite поддерживают near-cache.

---

## 14. Анти-шаблоны

- **Кэш как основное хранилище** — без БД под ним потеря кэша = потеря данных;
- **Огромный одиночный ключ (big key)** — блокирует event loop; см. `caching-deep-dive/ANTI_PATTERNS.md`;
- **Нет TTL на пользовательских ключах** — потенциальная утечка памяти;
- **Синхронная инвалидация на критическом пути** — добавляет задержку к записям.
