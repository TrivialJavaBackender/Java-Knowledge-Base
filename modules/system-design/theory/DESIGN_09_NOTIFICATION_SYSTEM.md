# Проектная задача: система уведомлений

Отправка уведомлений по нескольким каналам (email, SMS, push, in-app) миллионам пользователей. Веерная рассылка, дедупликация, повторы, пользовательские настройки.

---

## 1. Требования

### Функциональные
- отправка уведомлений по каналам: email, SMS, мобильные push (APNs / FCM), in-app, web push;
- пользовательские настройки (отключение по каналу);
- шаблоны (i18n, персонализация);
- запланированные уведомления (отправить завтра в 8:00);
- пакетная и массовая рассылка (кампании);
- подтверждения доставки (отправлено / открыто / кликнуто).

### Нефункциональные
- **Надёжность** — доставка at-least-once;
- **Пропускная способность** — миллионы уведомлений в час для маркетинговых кампаний;
- **Задержка** — транзакционные (сброс пароля) < 5 с;
- **Экономия** — SMS дорогие (центы за штуку), использовать аккуратно.

---

## 2. Оценка

```
100M MAU, в среднем 30 уведомлений на пользователя в день
  → 3B уведомлений/день = 35K/с в среднем
  → Пик ×10 = 350K/с (маркетинговый всплеск, breaking news)

Типичное распределение по каналам:
  Push: 60%
  Email: 30%
  In-app: 8%
  SMS: 2% (дорогой)
```

## 3. API

```http
POST /api/v1/notifications
Body: {
  templateId: "order_shipped",
  recipientUserId: 123,
  channels: ["push", "email"],
  data: { orderId: "...", trackingUrl: "..." },
  scheduledAt?: "2024-12-25T08:00:00Z"
}
→ 202 Accepted { notificationId }

GET /api/v1/notifications/:id
→ { status, deliveryAttempts, ... }
```

## 4. Архитектура

```
Сервисы-клиенты (Order, Auth, Marketing) → публикуют события
  ↓
Notification Service (API)
  ↓ (постановка в очередь)
Kafka topic: notifications
  ↓ (потребитель)
Обработчики каналов (по одному типу на канал)
  ├── Push Worker → APNs / FCM
  ├── Email Worker → SES / SendGrid / Mailgun
  ├── SMS Worker → Twilio
  └── In-App Worker → пишем в БД, отправляем через WebSocket, если пользователь в сети

Сбоку:
  - User Service (настройки, контакты, токены устройств)
  - Template Service (рендеринг шаблонов)
  - Delivery DB (журнал аудита)
```

---

## 5. Поток обработки

```
1. Order service: «order shipped, notify user»
2. → POST /api/v1/notifications
3. Notification Service:
   a. Валидирует запрос
   b. Берёт настройки пользователя (кэшированные): «push включён, email включён»
   c. Берёт шаблон (из кэша) и рендерит с данными
   d. Применяет ограничение скорости на пользователя (не более 10 уведомлений/час ради UX)
   e. Публикует событие в Kafka-топик соответствующего канала
4. Обработчики каналов читают:
   a. Push Worker:
      - Достаёт токены устройств из User Service
      - Шлёт в APNs / FCM
      - Логирует попытку
      - Помечает «доставлено» (или повтор при сбое)
```

---

## 6. Специфика каналов

### Email (SES / SendGrid)

- Обработка возвратов (bounce) (hard / soft) → помечаем email невалидным;
- жалобы на спам → отписка пользователя;
- шаблоны: MJML или Handlebars;
- встроенное отслеживание (open pixel, click-redirect).

### SMS (Twilio)

- Дорого (в 10 раз дороже email);
- используем аккуратно (security-коды, срочное);
- гео-ограничения;
- глобальное ограничение скорости (на уровне аккаунта Twilio).

### Push (APNs / FCM)

- APNs (iOS) — HTTP/2 API Apple;
- FCM (Android + Web) — Google;
- управление токенами устройств — токены протухают, нужна ротация;
- тихий push (silent push) — без UI-уведомления, только обновление данных.

### In-app

- хранятся в БД (таблица `notifications`);
- отправляются через WebSocket, если пользователь в сети;
- помечаются прочитанными, когда пользователь открыл.

## 7. Пользовательские настройки

```sql
CREATE TABLE user_preferences (
    user_id BIGINT,
    channel ENUM('push', 'email', 'sms', 'in_app'),
    category ENUM('marketing', 'transactional', 'system'),
    opted_in BOOLEAN,
    PRIMARY KEY (user_id, channel, category)
);
```

Правила:
- транзакционные (сброс пароля) — обычно нельзя отключить;
- маркетинговые — должна быть возможность отписки (GDPR, CAN-SPAM Act).

## 9. Надёжность

### At-least-once доставка

Гарантии Kafka + повторы обработчиков. Возможны дубликаты → потребитель должен дедуплицировать (ключ идемпотентности на уведомление).

### Политика повторов

```
Channel Worker:
  попытка = 1
  отправить уведомление
  если упало:
    временная ошибка (5xx, сеть): повтор с экспоненциальной задержкой
    постоянная (невалидный токен устройства): помечаем устройство, не повторяем
    исчерпан лимит попыток: DLQ
```

Стандартная задержка (экспоненциальный рост): 1 мин, 5 мин, 30 мин, 2 ч, 12 ч.

### DLQ (очередь недоставленных)

Окончательно упавшие уведомления → DLQ-топик. Ручной разбор и поддержка.

---

## 10. Ограничение скорости

### На пользователя

Чтобы не спамить уведомлениями.
```
не более 10 уведомлений / час / пользователь (по умолчанию; для системных можно повышать)
```

Корзина: отслеживаем число уведомлений на пользователя в окне. Превысили — новые пропускаем.

### На канал (глобально)

- SMS — ограничение скорости на уровне аккаунта Twilio;
- APNs — лимит push на устройство;
- email — репутация отправляющего домена (новые домены — медленный разгон).

---

## 11. Запланированные уведомления

```
уведомление с scheduledAt = будущая метка времени
  → кладём в очередь с задержкой (SQS DelaySeconds, Redis sorted set со score=timestamp)
  → в назначенное время переносим в основную очередь

Варианты реализации:
  - Cron-задача каждую минуту: сканируем ближайшие → публикуем
  - Redis ZSET с ZPOPMIN по score <= now
  - Отдельный сервис-планировщик (Quartz, Temporal)
```

---

## 12. Кампании (массовая рассылка)

Маркетинговая кампания: «Отправить всем 10M пользователей».

```
Campaign Service:
  - Валидирует конфиг
  - Материализует список получателей (запрос к сегментам)
  - Режет список на батчи (по 10K)
  - Публикует пакетные задачи в Kafka
  - Обработчики обрабатывают батчи и публикуют отдельные уведомления
```

Регулирование: рассылка идёт постепенно (например, 1M в час), чтобы избегать жалоб на спам и всплесков нагрузки.

---

## 13. Подтверждения доставки

По каждому уведомлению трекаем:
- `sent_at` — сервер совершил попытку отправки;
- `delivered_at` — канал подтвердил доставку (событие email-сервиса, подтверждение push);
- `opened_at` — пользователь открыл (open-pixel в письме, push открыт в приложении);
- `clicked_at` — клик по ссылке.

События пишутся в Kafka → агрегируются в аналитическую БД.

---

## 14. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Email-сервис недоступен (SendGrid) | Повтор, затем запасной провайдер (SES) |
| Токен устройства невалиден | Помечаем, перестаём слать до обновления |
| Пользователь отписался | Проверяем настройки до отправки, тихо пропускаем |
| Шторм уведомлений (баг шлёт ×1000) | Лимит на пользователя срезает, алерт оператору |
| Обработчик упал | Смещение в Kafka осталось, его подхватит другой обработчик |

## 15. Компромиссы

### Синхронный против асинхронного API

- **Синхронный** — вызывающий ждёт подтверждения доставки. Медленно (mailbox-провайдер может секунды ждать);
- **Асинхронный (этот дизайн)** — вызывающий сразу получает ответ, статус трекается отдельно.

По умолчанию асинхронный; синхронный — редко, для высокоприоритетного (код аутентификации).

### Отдельный обработчик на канал против универсального

- Отдельные обработчики на канал — специализированы, масштабируются независимо;
- универсальный обработчик — проще, но один сбойный канал блокирует остальные.
