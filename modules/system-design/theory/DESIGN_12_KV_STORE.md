# Проектная задача: распределённое key-value хранилище (Dynamo-style)

Распределённое KV-хранилище — DynamoDB, Cassandra, Riak. Главные компоненты: consistent hashing, репликация, кворумы, итоговая согласованность, anti-entropy (фоновая синхронизация для устранения расхождений между репликами).

---

## 1. Требования

### Функциональные
- PUT key value;
- GET key;
- DELETE key;
- range-запросы? Обычно нет (чистый NoSQL KV);
- TTL?

### Нефункциональные
- **Масштаб** — добавляем узлы, ёмкость растёт;
- **Высокая доступность** — переживает падение узлов (AP в CAP);
- **Низкая задержка** — p99 чтений < 10 мс;
- **Итоговая согласованность** допустима;
- **Живучесть** — переживает диск, сбой региона.

---

## 2. Оценка

```
1B элементов, в среднем 1 КБ = 1 ТБ
Пик: 100K чтений/с, 10K записей/с
RF = 3 → 3 ТБ суммарного реплицированного хранилища
~10–20 узлов по 200 ГБ
```

---

## 3. Архитектура

Стиль Dynamo: **нет лидера, все узлы равноправны**.

```
Клиент (умный клиент со знанием топологии)
  ↓
Координатор (любой узел) →
Реплики для ключа:
  Узел A (реплика 1)
  Узел B (реплика 2)
  Узел C (реплика 3)

Gossip-протокол для членства в кластере
```

---

## 4. Consistent Hashing

```
Кольцо хэш-значений [0, 2^64)
У каждого узла несколько **виртуальных узлов (vnodes)** — 100–200 на физический узел

PUT(key, value):
  partition_key = hash(key)
  replicas = следующие N узлов по часовой стрелке
  пишем во все N реплик
```

Детали — в [`SHARDING.md` (databases)](../../databases/theory/SHARDING.md#consistent-hashing).

Добавление и удаление узла перемещает только `1/N` ключей.

---

## 5. Репликация

**N реплик** на ключ — соседние узлы на кольце.

```
N = 3 типично
Реплики: следующие 3 уникальных физических узла после partition_key
```

### Нестрогий кворум (sloppy quorum)

Если реплика недоступна — запись принимается на «соседний» узел с подсказкой. Когда реплика оживает — подсказанная передача (hinted handoff).

```
Если первичная реплика недоступна:
  Координатор выбирает следующий доступный узел
  Метит запись как подсказку: «это для оригинальной реплики X»
  Когда X восстановится — получает все накопленные подсказанные записи
```

---

## 6. Кворум чтения и записи (R + W > N)

```
N = 3, W = 2, R = 2 → строгая согласованность
  PUT ждёт подтверждения от 2 из 3 реплик
  GET читает 2 из 3, берёт более свежую (по метке времени)
  Оба пересекаются хотя бы по 1 реплике → чтение видит последнюю запись

N = 3, W = 1, R = 1 → итоговая согласованность, низкая задержка, высокая доступность
  Каждая операция работает с одной репликой
  Может вернуть устаревшие данные
```

Настраивается на операцию — приложения сами выбирают строго (финансовое) против мягко (как кэш).

---

## 7. Read repair (восстановление при чтении)

Когда GET возвращает противоречивые версии (у реплик разные значения):

```
GET key →
  реплика A: value=X, timestamp=t1
  реплика B: value=Y, timestamp=t2 > t1
  реплика C: value=X, timestamp=t1

Координатор возвращает Y (свежее).
**Read repair:** в фоне обновляет A и C на Y.
```

Обеспечивает итоговую сходимость без отдельного процесса anti-entropy.

---

## 8. Anti-Entropy (Merkle trees)

Периодическая фоновая синхронизация между репликами. Эффективное обнаружение расхождений.

Подробнее — в [`MERKLE_TREE.md`](MERKLE_TREE.md) и [`databases/REPLICATION.md`](../../databases/theory/REPLICATION.md#anti-entropy--merkle-trees).

```
Каждая реплика строит Merkle tree своих данных:
  Сравниваются корневые хэши.
  Различаются → рекурсивно спускаемся по дереву, находим различия.
  Синхронизируем только их.
```

`nodetool repair` в Cassandra запускает именно это.

---

## 9. Разрешение конфликтов

Конкурентные записи → конфликты. Подходы:

### Last-Write-Wins (LWW) — по умолчанию в Cassandra

Метка времени на каждой записи. Победил тот, у кого метка больше.

- ✓ просто;
- ✗ расхождение часов → тихая потеря данных;
- ✗ конкурентные обновления теряются.

### Векторные часы (Riak, оригинальный Dynamo)

У каждой версии — векторные часы. Конфликтующие версии возвращаются приложению — приложение само резолвит.

- ✓ без потери данных;
- ✗ сложно для приложения;
- см. [`distributed_systems.md`](distributed_systems.md#lamport-timestamps--vector-clocks).

### CRDT

См. [`CRDT.md`](CRDT.md). Математически гарантированное слияние. Riak поддерживает CRDT-типы.

## 10. Gossip-протокол

Членство в кластере без центрального координатора. См. [`GOSSIP_PROTOCOL.md`](GOSSIP_PROTOCOL.md).

```
Каждый узел периодически (раз в секунду):
  Выбирает случайного соседа
  Обменивается состоянием кластера: кто жив, версия схемы, кому принадлежат токены
  Все узлы постепенно сходятся

Обнаружение сбоев: phi accrual detector (подозрительность копится с пропущенными heartbeat)
```

---

## 11. Модель данных

### Чистый KV

```
PUT key value [TTL]
GET key → value
DELETE key
```

### Wide-column (Cassandra, HBase)

Разрешает несколько колонок в строке, time-series-запросы:

```
PUT key column1 value1 [TS1]
PUT key column2 value2 [TS2]
GET key column1
GET key columns BETWEEN c1 AND c5
```

Полезно, когда у строк много значений с метками времени (например, user_id → metric_name → time-series).

## 12. Движок хранения

Большинство в стиле Dynamo используют **LSM-tree** для нагрузок с большим числом записей.

См. [`databases/STORAGE_ENGINES.md`](../../databases/theory/STORAGE_ENGINES.md#lsm-tree-storage-engines).

- Memtable + SSTable;
- стратегии уплотнения (LCS, STCS, TWCS);
- Bloom filter на каждую SSTable.

## 13. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Узел упал | Реплики обслуживают; подсказанная передача проигрывается на восстановлении |
| Сетевое разделение | Нестрогий кворум продолжает работать, если R/W достижимы; конвергенция позже |
| Полный сбой ЦОДа | Реплики в другом ЦОДе обслуживают (multi-DC репликация) |
| Постоянная потеря узла | Стримим данные на замещающий узел с других реплик |
| Конфликт при разделе | CRDT автоматически разрешает, или приложение читает несколько версий и выбирает |

## 14. Настраиваемая согласованность

```
Уровни согласованности в Cassandra:
  ANY: запись принята любым узлом (или подсказкой)
  ONE: подтверждение от 1 реплики
  QUORUM: большинство (например, 2 из 3)
  ALL: все реплики

Шаблон:
  CL_READ + CL_WRITE > RF → строгая согласованность
  Меньший CL → выше доступность, ниже задержка, возможны устаревшие данные
```

---

## 15. Multi-DC

Асинхронная репликация в удалённый ЦОД. См. [`databases/REPLICATION.md`](../../databases/theory/REPLICATION.md#multi-leader-replication).

```
Локальный ЦОД: RF=3, строгие чтения/записи
Удалённый ЦОД: RF=3, асинхронная реплика
Локальность чтения: предпочитаем локальные реплики
Cross-DC чтения (для проверки согласованности): по требованию
```

---

## 16. Компромиссы

### Строгая против итоговой

- **Строгая (R+W>N)** — медленнее, ниже доступность при сбоях;
- **Итоговая** — быстрее, доступнее, может вернуть устаревшие данные.

На операцию в Cassandra: «сессионные чтения — строгие, аналитика — слабые».

### Задержка против живучести

- синхронная репликация на N реплик — медленно, но надёжно;
- асинхронная — быстро, но возможна потеря на переключении на резерв.

### Wide-column против чистого KV

- wide-column добавляет выразительность запросов;
- чистый KV проще и быстрее.
