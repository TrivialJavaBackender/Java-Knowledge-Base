# Проектная задача: автодополнение поиска (typeahead)

Подсказывать запросы по мере набора. Google search box, поиск товаров на Amazon, упоминания в Twitter. Критично по задержке (50–100 мс на нажатие клавиши), ранжирование по популярности.

> **Область:** уровень дизайна. Теория Trie — в [`TRIE.md`](TRIE.md).

---

## 1. Требования

### Функциональные
- подсказывать top-K продолжений запроса для префикса;
- обновлять подсказки на каждом нажатии клавиши;
- ранжирование по популярности (чаще искали — выше);
- персонализация (опционально);
- обновление в реальном времени (новые трендовые запросы появляются).

### Нефункциональные
- **Ответ за 100 мс** — в идеале < 50 мс;
- **Высокая пропускная способность** — каждое нажатие = запрос × миллионы пользователей;
- **Масштаб** — миллиарды поисковых запросов в истории.

---

## 2. Оценка

```
500M поисков в день
В среднем 4 нажатия клавиш на запрос = 2B запросов автодополнения в день
  = ~25K QPS в среднем, пик 100K QPS

Уникальных запросов: ~100M (длинный хвост)
Top 1M покрывает ~95% (распределение Zipf)

Размер Trie:
  100M запросов × в среднем 20 символов × 1 байт = 2 ГБ сырых символов
  С деревом и top-K на каждом узле: ~20 ГБ
  → Влезет в RAM (один узел 64 ГБ)
```

## 3. API

```http
GET /api/v1/autocomplete?q=brown+f&limit=10
→ 200 [
  { suggestion: "brown fox", count: 12345 },
  { suggestion: "brown furniture", count: 8901 },
  { suggestion: "brown fox jumps over", count: 5432 },
  ...
]
```

## 4. Архитектура

```
Пользователь печатает → дросселирование (debounce 50–100 мс между нажатиями)
  ↓
Балансировщик → Autocomplete Service (read-реплики)
  ↓
In-memory Trie + кэш top-K
  ↓ (периодическое обновление)
Trie Builder (пакетная задача)
  ↑
Query Log Aggregator → счётчики по запросу за день
  ↑
Сырые поисковые логи (Kafka)
```

---

## 5. Trie с предвычисленным top-K

Базовая теория — в [`TRIE.md`](TRIE.md).

Каждый узел Trie хранит **top-K подсказок** для своего префикса:

```python
class TrieNode:
    children: dict
    top_k_suggestions: list[(string, score)]  # отсортированы по score
```

Запрос `"app"`:
- доходим до узла для "app";
- возвращаем `node.top_k_suggestions` (мгновенно).

**Компромиссы:**
- ✓ время запроса O(L) + возврат K — очень быстро;
- ✗ память: кэш top-K на узел;
- ✗ обновление: смена score может требовать обновления в нескольких предках.

---

## 6. Пайплайн построения Trie

### Офлайн (пакетно)

```
Ежедневная Spark-задача:
  Сырые поисковые логи → агрегация:
    query → count за последние 30 дней
  Строим Trie:
    вставляем каждый (query, count) → обновляем top-K в предках
  Сериализуем Trie → S3
```

### Онлайн-обновление

```
Autocomplete-сервис:
  При старте: скачиваем свежий Trie из S3, загружаем в память
  Периодически: проверяем обновления, перезагружаем (blue/green, чтобы избежать простоя)
```

### Частичные обновления в реальном времени

Для трендов (например, термов из новостей вроде «Earthquake») чисто офлайн-подход отстаёт.

```
Свежие запросы (за последний час) → потоковая агрегация (Flink) →
  Обновления в «горячем» Trie (отдельный in-memory) →
  При запросе сливаем результаты офлайн + горячего Trie
```

---

## 7. Хранение

### Trie (in-memory)

- один сериализованный бинарный формат;
- на каждом экземпляре приложения тот же блоб;
- ~20 ГБ на 100M запросов → влезает в инстанс 64 ГБ.

### Персистентность (холодная)

- блоб в S3 — перестраивается ежедневно;
- меньшая БД запросов (PostgreSQL / Cassandra) для аналитики с детализацией.

### Поисковые логи

- Kafka-топик с хранением (например, 30 дней);
- архив в S3 + колоночный формат (Parquet) для аналитики.

---

## 8. Распределённое обслуживание

### Шардирование по префиксу

Если Trie не помещается на одном узле — шардируем по префиксу:

```
Шард 0: префикс a–d
Шард 1: префикс e–h
Шард 2: префикс i–l
...

Маршрутизатор отправляет запрос на нужный шард по первому символу
```

Если подсказка пересекает шарды — нужно сливать.

### Реплики только для чтения

Trie неизменяем в рамках одного обновления. Много реплик только для чтения для высокой пропускной способности.

```
N реплик, каждая загружает один и тот же Trie
Round-robin запросов
Обновление: blue/green-выкатка, новые реплики поднимаются с новым Trie
```

## 9. Персонализация

Добавляем подсказки по пользователю поверх глобально популярных.

```
На запросе:
  global_suggestions = trie.top_k(prefix, K=15)
  user_history = redis.lrange(f"history:{user_id}", 0, -1)  # недавние поиски
  user_matching = filter(lambda s: s.startswith(prefix), user_history)

  слияние: предпочитаем user_matching, остаток добиваем из global
```

Либо ML-модель с признаками (локация, время суток, язык, недавняя активность).

---

## 10. Анти-шаблоны и плохой контент

- фильтрация явных / вредных запросов;
- блокировка злоупотреблений товарными знаками (Coca-Cola не разрешит подсказку «Pepsi»);
- скрытие запросов с очень низким count (спам / опечатки).

---

## 11. Слой кэширования

Топ-префиксы («a», «am», «ama», «amaz») получают миллионы QPS.

```
Кэш на уровне приложения (Caffeine LRU) на каждом экземпляре
TTL: 5 минут (баланс свежести vs доли попаданий)

Топ 1000 префиксов покрывают → 90% запросов отдаются из кэша без обхода Trie
```

## 12. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Перестроение Trie упало | Используем вчерашний; алерт оператору |
| Перегрузка горячего префикса | Масштабирование реплик; гео-CDN на пограничных узлах только для чтения |
| Свежий трендовый терм отсутствует в Trie | Горячий Trie (потоковый) его подхватывает; слияние результатов |
| Пользователь ввёл emoji / unicode | Нормализуем при загрузке и на запросе |

## 13. Компромиссы

### Предвычисленный top-K против ранжирования на запросе

- **Предвычисленный** — быстро, но устаревает (пересборка раз в день); агрессивно персонализировать сложно;
- **На запросе** — медленнее, но в реальном времени + возможна персонализация.

Гибрид: предвычисленный + позднее переранжирование под пользователя.

### Trie против поискового движка

- **Trie** — идеален для поиска по префиксу, ручное ранжирование;
- **Elasticsearch / Solr** — нечёткий поиск, edge n-gram tokenizer; готовые возможности;
- **DAWG** (Directed Acyclic Word Graph) — ещё компактнее, но сложно обновлять.

Сейчас широко используют Elasticsearch Completion Suggester (на базе FST). Чистый Trie остаётся там, где нужен точный контроль.

## 14. Примеры из продакшена

- **Google search autocomplete** — самописный Trie + ML + персонализация;
- **Amazon search** — Trie по каталогу + усиление по категориям;
- **Twitter mentions** — особый случай (user handles);
- **LinkedIn typeahead** — Cleo (выложен в open source);
- **Elasticsearch Completion Suggester** — на базе FST, используется многими небольшими сервисами.
