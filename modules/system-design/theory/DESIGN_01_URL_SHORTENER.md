# Проектная задача: сокращатель URL (TinyURL / bit.ly)

Сервис принимает длинный URL → возвращает короткий (`bit.ly/abc123`). Клик по короткому → редирект на длинный. Классическая «лёгкая» SD-задача — фокус на генерации ID, задержке редиректа и аналитике.

---

## 1. Требования

### Функциональные
- POST длинного URL → короткий URL (`bit.ly/<6-символьный код>`);
- GET по короткому URL → 301/302 редирект на длинный;
- (опционально) пользовательский алиас (`bit.ly/my-link`);
- (опционально) истечение (TTL);
- (опционально) аналитика кликов.

### Нефункциональные
- **Преобладание чтения** (обычно 10:1 чтения/запись);
- **Низкая задержка редиректа** — p99 < 100 мс;
- **Высокая доступность** — 99,99% (битый редирект никто не повторит);
- **Непредсказуемый код** — нельзя угадать `abc124`, зная `abc123` (нужен случайный или хэш, не последовательный);
- **Уникальность** — каждый длинный URL → один короткий (или допустить дубли — обсудить с интервьюером).

---

## 2. Оценка

```
100M URL создаётся в год, отношение чтения/записи 10:1

Записи: 100M / год / 31,5M с = ~3 записи/с в среднем
        Пик: 30 записей/с
Чтения: 1B чтений / год / 31,5M = ~30 чтений/с в среднем
        Пик: 300 чтений/с
→ QPS тривиальный, хватит и одного сервера

Хранилище: на URL ~500 байт (long_url + short_code + метаданные)
           10 лет × 100M × 500 байт = 500 ГБ → влезет в один PostgreSQL

Кэш: 20% горячих URL × 500 байт = 10 ГБ рабочего набора → один Redis-узел

Пространство ID: base62 (a-zA-Z0-9) на 6 символов = 62^6 = 56B URL (хватит на годы)
                7 символов = 3,5T (на «вечность»)
```

---

## 3. API

```http
POST /api/v1/shorten
Body: { url: "https://example.com/very/long/path", expiresIn?: 86400 }
→ 201 { shortCode: "abc123", shortUrl: "https://bit.ly/abc123" }

GET /:shortCode
→ 301 Location: <long_url>
   (или 302, если нужна аналитика — 301 кэшируется браузером, повторный GET до сервера не дойдёт)

GET /api/v1/links/:shortCode/stats
→ { clicks: 12345, byCountry: {...}, byHour: {...} }
```

---

## 4. Высокоуровневая архитектура

```
Клиент → CDN (опционально кэширует горячие редиректы) →
       → балансировщик → API-серверы →
                ├ Кэш (Redis) — code → long_url
                ├ Сервис генерации ID
                └ БД (PostgreSQL, шардирована по short_code) — устойчивое хранилище

       → Аналитика: асинхронно (Kafka → пакетная обработка)
```

---

## 5. Генерация ID — главное архитектурное решение

### Вариант A: последовательный ID + base62

Autoincrement в БД → целое число → кодирование в base62.

```
id=1 → "1"
id=62 → "10"
id=1000000 → "4c92"
```

- ✓ просто, монотонно;
- ✗ **последовательность предсказуема** — скрейпер может пройти `abc1`, `abc2`, …;
- ✗ единая точка (autoincrement БД) — узкое место на масштабе.

### Вариант B: случайные 6 символов

```python
import secrets
shortCode = secrets.token_urlsafe(4)[:6]  # base64 → 6 символов
```

- ✓ непредсказуемо;
- ✗ **коллизии** — парадокс дней рождения: 62^6 = 56B; при 10M существующих URL ~1 на 5,6M сокращений → изредка коллизия → повтор;
- защита: `INSERT ... ON CONFLICT DO NOTHING`, повтор при конфликте.

### Вариант C: хэш от длинного URL

`shortCode = base62(MD5(long_url))[:6]`

- ✓ бесплатная дедупликация (один и тот же URL → один и тот же короткий код);
- ✗ коллизии всё равно возможны; их нужно обрабатывать;
- ✗ пользователь не может иметь несколько коротких ссылок на один длинный URL (часто нужно для аналитики).

### Вариант D: Сервис генерации ключей (KGS)

Заранее сгенерировать пачку уникальных кодов и хранить в БД. Приложение берёт из пула.

```
Пул KGS: 1M предгенерированных неиспользованных кодов
Приложение: GET /kgs/next-code → "abc123" (помечается как использованный)
```

- ✓ нет коллизий во время работы;
- ✓ непредсказуемо;
- ✓ масштабируется: несколько экземпляров KGS, у каждого свой диапазон;
- ✗ дополнительный сервис в эксплуатации.

### Вариант E: ID в стиле Snowflake

64-битный ID = `метка времени (41 бит) | machine_id (10 бит) | sequence (12 бит)`. Кодируется в base62.

- ✓ распределённо, без центрального координатора;
- ✓ сортируется по времени;
- ✗ предсказуемо (внутри лежит метка времени).

**Рекомендация:** KGS для прода; случайные 6–7 символов с повтором — для меньших масштабов.

## 6. Модель данных

```sql
CREATE TABLE urls (
    short_code   VARCHAR(8) PRIMARY KEY,
    long_url     TEXT NOT NULL,
    user_id      BIGINT,
    created_at   TIMESTAMPTZ DEFAULT now(),
    expires_at   TIMESTAMPTZ,
    click_count  BIGINT DEFAULT 0  -- денормализовано; или отдельная таблица аналитики
);

CREATE INDEX idx_expires ON urls(expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX idx_user ON urls(user_id);
```

**Шардирование:** по хэшу `short_code`. Поскольку чтение и запись — по ключу (short_code), шардирование тривиально.

---

## 7. Путь редиректа — критичный путь

Горячий путь: `GET /:shortCode → редирект`. Бюджет задержки < 100 мс.

```
1. Приложение принимает запрос
2. Чтение Redis-кэша (1 мс): попадание → 301
3. Промах → запрос в БД (1–5 мс): кладём в кэш, → 301
4. Асинхронно: пишем событие аналитики в Kafka
5. Возвращаем 301 с заголовком Location
```

**Стратегия кэша:**
- LRU-кэш, TTL = 1 час (или дольше для неизменяемых кодов);
- горячий набор (20%) → доля попаданий 95%+;
- защита от захлёста кэша (cache stampede): single-flight при промахе.

**Нюанс CDN:** можно кэшировать сами 301-ответы на пограничных узлах для виральных ссылок. Компромисс: устаревшие ссылки при обновлении или удалении; обычно норм, потому что короткие коды неизменяемы.

---

## 8. Аналитика

```
На клик: отправляем событие в Kafka-топик
  { shortCode, timestamp, ip, userAgent, referer, country }

Асинхронный потребитель:
  Пакетная обработка раз в минуту → агрегаты по (shortCode, hour, country)
  Хранение в БД аналитики (ClickHouse, BigQuery) — колоночная для агрегаций
```

Денормализованный счётчик в `urls.click_count` обновляется итогово согласованно (раз в N секунд).

---

## 9. Соображения масштаба

### ×10 (1B URL, 10K чтений в секунду)

- больше узлов кэша (Redis Cluster);
- шардирование БД по `short_code`;
- несколько аналитических потребителей.

### ×100 (100B URL)

- гео-реплицированная БД (multi-region);
- пограничный кэш для виральных ссылок (CDN).

### Горячая ссылка / контент знаменитости

«bit.ly/xyz» виралится → 1M запросов/с на один shortCode.

- CDN поглощает большую часть;
- реплицируем горячие ключи на несколько узлов кэша;
- ограничение скорости на пользователя (но сам редирект должен работать для всех — лимит ставится только на создание / злоупотребления).

---

## 10. Компромиссы

### 301 vs 302

- **301 Permanent Redirect** — кэшируется браузером, меньше нагрузки на сервер, **аналитика теряется на повторных визитах**;
- **302 Temporary Redirect** — каждый визит долетает до нас, **аналитика полная**.

Выбрать 302, если аналитика важна (по умолчанию у bit.ly); 301 — если это просто редирект как сервис.

### Пользовательский алиас

```
POST /api/v1/shorten
Body: { url: "...", alias: "my-link" }
→ "bit.ly/my-link"

Если алиас занят → 409 Conflict
```

В БД — UNIQUE-ограничение на `alias`. Либо предварительная проверка, либо опираться на ошибку при INSERT.

### Истечение / мягкое удаление

Колонка `expires_at`; пакетная задача для очистки. Либо флаг `is_active` (полное удаление редко делают).

---

## 11. Защита от злоупотреблений

- **Ограничение скорости на создание** — 100 URL в час на IP;
- **валидация URL** — отвергать невалидные, внутренние IP (SSRF), известные плохие домены (фишинг-список);
- **спам-ссылки** — периодическая перепроверка назначения, блокировка редиректа, если URL стал вредоносным.
