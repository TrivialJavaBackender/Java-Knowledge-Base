# Проектная задача: лента новостей (Twitter / Instagram)

Пользователь публикует пост → подписчики видят его в своей ленте. Главная задача — **веерная рассылка (fan-out)**: отправка подписчикам (нагрузка на запись) против подтягивания на чтение (вычисление по запросу). Проблема знаменитостей.

---

## 1. Требования

### Функциональные
- опубликовать твит (текст + опционально медиа);
- подписка и отписка;
- просмотр домашней ленты (по времени или по релевантности);
- лайк, ретвит, ответ;
- (опционально) поиск, хэштеги, тренды.

### Нефункциональные
- **Преобладание чтения** (~1000:1 чтения/запись в масштабе Twitter);
- **Низкая задержка ленты** — p99 < 500 мс;
- **Итоговая согласованность допустима** — пост может появиться у подписчиков с задержкой 1–10 с;
- **Масштабируемость** — 300M+ DAU, миллиарды связей подписки.

---

## 2. Оценка

```
300M DAU, в среднем 100 чтений + 1 пост на пользователя в день (постят ~10%)

ЗАПИСИ (посты):
  300M × 1 × 10% = 30M постов/день = ~350 записей/с в среднем, пик ~700

ЧТЕНИЯ (лента):
  300M × 100 = 30B чтений/день = ~350K чтений/с в среднем, пик ~700K

Отношение чтения/записи: 1000:1 — сильный перекос на чтение

ХРАНИЛИЩЕ:
  Посты: 30M × 500 байт = 15 ГБ/день = 5,5 ТБ/год
  10 лет: 55 ТБ сырого, × 3 репликации = 165 ТБ

Стоимость веерной рассылки (если push):
  В среднем у пользователя ~200 подписчиков
  Знаменитость: 100M подписчиков
  Всего записей рассылки в секунду = 700 × 200 (среднее) = 140K записей/с
  Знаменитости: 700 × 100M подписчиков = 70B записей (если все «выстрелят» одновременно — невозможно)
```

## 4. Три подхода к генерации ленты

### A. Веерная рассылка при записи (Push)

При публикации — пишем твит в кэш ленты **каждого подписчика**.

```
Пользователь постит →
  вставляем твит в таблицу posts →
  для каждого подписчика:
    LPUSH timeline:{follower_id} tweet_id
```

- ✓ **Задержка чтения низкая** — лента уже подготовлена;
- ✗ **Усиление записей** — знаменитость (100M подписчиков) = 100M записей в кэш;
- ✗ неактивные подписчики — холостая работа;
- ✗ новая подписка требует backfill.

### B. Веерное чтение (Pull)

На чтение — подтягиваем посты от всех подписок в реальном времени.

```
Пользователь открывает ленту →
  followed = SELECT user_id FROM follows WHERE follower = user
  tweets = SELECT * FROM tweets WHERE user_id IN (followed) ORDER BY time DESC LIMIT 50
```

- ✓ **Нет усиления записей**;
- ✗ **Задержка чтения высокая** — много джоинов и сортировка;
- ✗ худший случай: подписан на 10K — запрос огромный.

### C. Гибрид (реальный подход Twitter)

**Push для обычных пользователей, pull для знаменитостей.**

```
Пользователь постит:
  if user.followers > 100K (знаменитость):
    не отправляем — подписчики сами подтянут
  else:
    отправка во все ленты подписчиков

Пользователь читает ленту:
  base_timeline = заранее подготовлен (через push)
  + celebrities_tweets = подтягивание свежих постов знаменитостей, на которых подписан пользователь
  слияние с сортировкой по времени
  return
```

- ✓ лучшее из двух миров;
- ✗ сложность реализации;
- нужен тюнинг порога.

## 6. Модель данных

```sql
-- Tweets (шардированы по user_id)
CREATE TABLE tweets (
    id BIGINT PRIMARY KEY,  -- Snowflake ID (сортируем по времени)
    user_id BIGINT,
    text TEXT,
    media_urls TEXT[],
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_user_time ON tweets(user_id, created_at DESC);

-- Follows (шардированы по follower)
CREATE TABLE follows (
    follower_id BIGINT,
    followee_id BIGINT,
    created_at TIMESTAMPTZ,
    PRIMARY KEY (follower_id, followee_id)
);
CREATE INDEX idx_followee ON follows(followee_id);  -- для обратного поиска

-- Timeline cache (Redis sorted set на пользователя)
ZADD timeline:{user_id} {timestamp} {tweet_id}
-- Храним последние ~1000 tweets на пользователя (LRU evict старее)
```

## 7. Поток веерной рассылки

```
1. Пользователь публикует твит → API-сервис пишет в Post DB
2. API публикует событие в Kafka topic `tweet-posted`
3. Обработчик веерной рассылки читает событие:
   a. Берёт список подписчиков из Follow DB
   b. Если знаменитость (>100K) → веерную рассылку пропускаем (будет pull при чтении)
   c. Иначе: на каждого подписчика → ZADD timeline:{follower} (tweet_id, timestamp)
4. Ленты подписчиков обновляются в течение 1–10 с
```

**Параллелизм обработчиков:** партиционирование Kafka по user_id → много обработчиков работают параллельно.

**Обработка сбоев:**
- DLQ для постоянных сбоев;
- повтор с экспоненциальной задержкой;
- идемпотентный ZADD (повторное добавление того же твита — no-op).

---

## 8. Путь чтения

```
1. API получает GET /timeline
2. Берём ID из Redis: ZREVRANGE timeline:{user_id} 0 49
3. Берём tweets параллельно: MGET posts:{id1} posts:{id2} ...
   если промах → достаём из БД, кэшируем
4. Если пользователь подписан на знаменитостей:
   для каждой знаменитости → берём свежие посты из celebrity_timeline:{celeb_id}
   сливаем в базовую ленту, сортируем по времени
5. Возвращаем топ-50
```

Задержка: обычно 10–50 мс (всё в кэше).

## 9. Проблема знаменитостей (глубже)

Горячие пользователи (Justin Bieber с 100M+ подписчиков).

### Почему веерная рассылка не работает

- 100M записей в кэш на каждый твит → 700 мс – 7 с;
- если знаменитость постит 10 раз в день → 1B записей в день на знаменитость;
- холостая работа: большинство подписчиков неактивны.

### Стратегия

- **Кэш ленты знаменитости** — отдельный Redis-ключ `celebrity_timeline:{id}` с последними N твитами;
- **на чтение**: объединение обычной ленты + подтягивание свежих постов знаменитостей.

### Тюнинг порога

Порог «знаменитость»:
- просто число (>100K) — самый простой вариант;
- с учётом активности (подписчики × активность);
- на основе стоимости: стоимость веерной рассылки против стоимости подтягивания для конкретной сети пользователя.

## 10. Масштабирование хранилища

### Tweets — шардирование по user_id

- ~5,5 ТБ/год → один PostgreSQL-primary справится, шардирование — по мере роста;
- в реальности Twitter использует Manhattan (самописный NoSQL).

### Кэш ленты — Redis Cluster

- 300M пользователей × ~1000 ID твитов × ~8 байт = ~2 ТБ рабочего набора;
- Redis Cluster на 50+ шардов;
- LRU-вытеснение «холодных» пользователей — пересчитывать по запросу (лениво).

### Follows — шардирование по follower_id

- прямой запрос «на кого я подписан» — быстро (тот же шард);
- обратный «кто подписан на меня» — нужен `idx_followee`, может потребоваться сбор с разных шардов;
- для знаменитостей — храним count подписчиков заранее, отдельно.

## 11. Компромиссы и варианты

### Ранжирование против хронологии

Старый Twitter — хронология. Новый Twitter, Facebook, Instagram — с ранжированием (ML).

В ранжируемой ленте формирование становится задачей скоринга: заранее готовим набор кандидатов, на чтении делаем переранжирование ML-моделью.

### Правки и удаления

Tombstones (маркеры удаления) для твитов, событие через Kafka, удаление из кэшей ленты.

### Приватность (закрытые аккаунты)

При публикации проверяем, что подписчик подтверждён. Добавляет задержку в веерную рассылку.

### Треды и ответы

Поле `parent_tweet_id`. Чтение треда — рекурсивная выборка с ограничением по глубине.

### Медиа

Загрузка в S3 напрямую по подписанному URL. Доставка через CDN. В таблице tweets — только URL.

---

## 12. Защита от злоупотреблений

- ограничение скорости на пользователя (300 твитов в день);
- детектирование спама (ML по тексту и поведению);
- очередь жалоб на контент для ручного разбора.
