# Проектная задача: облачное хранилище файлов (Dropbox / Google Drive)

Облачное хранилище с синхронизацией между устройствами, нарезанием на чанки, дедупликацией и разрешением конфликтов. Главные сложности: работа с большими файлами, эффективная синхронизация, согласованность между устройствами.

---

## 1. Требования

### Функциональные
- загрузка файлов (любого размера до лимита, например 50 ГБ);
- скачивание;
- синхронизация между устройствами (десктоп, мобильный, веб);
- шеринг файлов (ссылка, права);
- история версий;
- (опционально) совместное редактирование в реальном времени (как Google Docs).

### Нефункциональные
- **Надёжность** — никогда не терять файлы (живучесть 99,999999999% — как у S3);
- **Эффективная синхронизация** — передаём только дельту, не файл целиком;
- **Доступность** — 99,99%;
- **Экономия трафика** — для мобильных и медленных сетей;
- **Согласованность между устройствами** — изменение на телефоне → видно на ноутбуке за секунды.

## 2. Оценка

```
500M пользователей, 100M DAU
В среднем хранят 50 ГБ → всего 25 ЭБ (экзабайт!)
Со сжатием и дедупликацией → ~5 ЭБ уникальных данных

Ежедневные загрузки: 100M × ~10 файлов × 5 МБ = 5 ПБ/день
Ежедневные скачивания: ×5 = 25 ПБ/день

Пиковая пропускная способность: обслуживание ~10M одновременных соединений глобально
```

## 3. API

```http
POST /api/v1/files
Body: { name, parentId, size }
→ { fileId, uploadSessionId }

PUT /api/v1/files/:fileId/chunks/:index
Body: <binary chunk>
→ { chunkHash, index }

POST /api/v1/files/:fileId/finalize
Body: { chunks: [...] }
→ { fileId, version, downloadUrl }

GET /api/v1/files/:fileId
→ { metadata, downloadUrl }

GET /api/v1/files/sync?cursor=...
→ { changes: [...], nextCursor }   # изменения с последней синхронизации
```

## 4. Высокоуровневая архитектура

```
Клиент (десктоп, мобильный, веб)
  ↓
Балансировщик → API Gateway
  ↓
  ├── Metadata Service (иерархия файлов и папок, версии)
  ├── Block Service (загрузка и получение чанков)
  ├── Sync Service (поток изменений для клиентов)
  ├── Share Service (права, ссылки)
  ↓
Хранилище:
  - БД метаданных (PostgreSQL / Cassandra) — дерево файлов, владение, права, версии
  - Хранилище блоков (S3 / самописное) — собственно чанки
  - Индекс хэшей блоков (Redis / DynamoDB) — для дедупликации
```

## 5. Нарезание на чанки — главный шаблон дизайна

Большие файлы (1 ГБ+) разбиваются на **чанки фиксированного размера** (обычно 4 МБ).

### Зачем чанки

- **Параллельная загрузка** — N чанков одновременно;
- **Возобновляемая загрузка** — обрыв соединения → продолжаем с конкретного чанка;
- **Дедупликация** — одинаковые чанки переиспользуются между файлами и пользователями;
- **Эффективная синхронизация** — изменился один чанк → отправляем только его.

### Идентификация чанка

У каждого чанка есть **хэш** (SHA-256). Хэш служит одновременно идентификатором и проверкой целостности.

```
файл F = [chunk1_hash, chunk2_hash, chunk3_hash, ...]

Протокол загрузки:
  Клиент режет файл
  Для каждого чанка:
    hash = SHA256(chunk_data)
    Спрашиваем API: «у вас есть hash X?»
      Да → пропускаем загрузку (уже есть, сервер переиспользует)
      Нет → загружаем чанк
  Финализация: шлём серверу список хэшей
```

### Дедупликация

Кросс-пользовательская дедупликация: если 1M пользователей хранят одинаковый файл (популярный документ, дистрибутив библиотеки), физически он лежит один раз.

```
chunk_hash → (storage_location, refcount)

На загрузку: инкремент refcount или создаём новый
На удаление: декремент; если refcount==0 → помечаем для GC
```

Нюанс приватности: кросс-пользовательская дедупликация может выдавать существование файла. **Дедупликация в рамках одного пользователя** сохраняет приватность.

### Нарезание по содержимому (CDC)

У фиксированного размера чанков есть проблема: вставка 1 байта в начало → все чанки сдвигаются, дедупликация ломается.

CDC: использовать **скользящий хэш** (Rabin fingerprint) для определения границ чанков по содержимому. Вставили байт → изменился только соседний чанк.

Используют: rsync, Restic, BorgBackup, Dropbox.

## 6. Модель данных

```sql
-- Файлы и папки (шард по user_id)
CREATE TABLE files (
    id UUID PRIMARY KEY,
    user_id BIGINT NOT NULL,
    parent_id UUID,           -- NULL для корня
    name TEXT,
    type ENUM('file', 'folder'),
    size BIGINT,              -- в байтах
    current_version BIGINT,
    created_at TIMESTAMPTZ,
    deleted_at TIMESTAMPTZ
);

-- Версии
CREATE TABLE file_versions (
    file_id UUID,
    version BIGINT,
    chunks UUID[],            -- упорядоченный список хэшей чанков
    size BIGINT,
    created_by BIGINT,
    created_at TIMESTAMPTZ,
    PRIMARY KEY (file_id, version)
);

-- Индекс чанков (высокая пропускная способность KV)
CREATE TABLE chunks (
    hash CHAR(64) PRIMARY KEY, -- SHA256 в hex
    storage_path TEXT,         -- путь в S3
    size INT,
    refcount BIGINT
);
```

## 7. Протокол синхронизации

Клиент держит локальный **курсор** (последнее состояние синхронизации). При переподключении подтягивает изменения с этого курсора.

```
Клиент → GET /sync?cursor=last_known_position
Сервер → список изменений с курсора:
  [
    { event: "file_created", id, name, parent, chunks: [...] },
    { event: "file_updated", id, version, chunks: [...] },
    { event: "file_deleted", id },
    ...
  ]
  + новый курсор

Клиент применяет изменения:
  - Новый файл: качаем чанки (параллельно)
  - Обновлён файл: качаем ТОЛЬКО новые чанки (дельта)
  - Удалён: убираем локально
```

### Отправка в реальном времени (альтернатива)

Для мгновенной синхронизации сервер отправляет события через WebSocket / длинный опрос. Гибрид: отправка при подключённом клиенте, запасной вариант — подтягивание при переподключении.

## 8. Разрешение конфликтов

Два устройства редактируют файл оффлайн. Оба приходят онлайн с разными изменениями.

### Last-Write-Wins (простой вариант)

Кто первым залил — победил; второй получает уведомление о конфликте.

```
Устройство A: загружает v5 (parent = v3)
Устройство B: пытается v5 (тоже parent = v3) → сервер видит «v5 уже существует»
  Сервер сохраняет версию B как «file (B's conflict).docx» (стиль Dropbox)
  Пользователь сливает вручную
```

### На основе CRDT (Google Docs / совместное редактирование)

Редактирование текста в реальном времени через CRDT (Yjs / Automerge). См. [`CRDT.md`](CRDT.md).

```
Каждое редактирование = операция CRDT
Все операции рассылаются всем участникам
Итоговая сходимость
```

Не подходит для произвольных типов файлов — только для структурированных (текст, JSON и т. п.).

## 9. Шеринг

### Ссылка для шеринга

Генерируем уникальный токен на файл:
```
fileId + shareToken → уникальный URL
```

Права:
- публичный (любой по ссылке);
- конкретные пользователи (по email);
- только чтение vs запись.

### БД прав

```sql
CREATE TABLE share_permissions (
    file_id UUID,
    user_id BIGINT,        -- или NULL для публичной ссылки
    permission ENUM('read', 'write', 'admin'),
    expires_at TIMESTAMPTZ
);
```

Проверка ACL на каждом доступе (кэшируется).

## 10. Бэкенд хранилища

### S3-совместимое объектное хранилище

Большинство облаков используют объектное хранилище (S3, GCS, Azure Blob) под собственно чанки.

```
хэш чанка → ключ объекта S3 (например, bucket/chunks/ab/cd/abcd1234...)
Используем 2–3-символьный префикс как ключ шардирования (защита от горячих партиций S3)
```

### Многоуровневое хранилище

- **Горячий уровень** — недавно использованные чанки, S3 Standard или локальный SSD-кэш;
- **Холодный уровень** — старые, редко используемые, S3 Glacier / Deep Archive;
- перенос — через lifecycle policies (автоматически).

### Репликация

S3 даёт живучесть «11 девяток» — потери из-за падения одного ЦОДа исключены.

## 11. Стратегия кэширования

### Пограничный кэш

Для расшаренных и публичных файлов — отправка в CDN.

```
Файл → пограничный кэш CDN (подписанный URL)
Другие пользователи в регионе получают файл с пограничного узла.
```

### Недавние файлы

Горячий кэш на пользователя в приложении: недавно использованные метаданные + чанки.

## 12. Оптимизация трафика

### Дельта-синхронизация (загрузка только различий)

Используем подход rsync:
- сервер вычисляет хэши уже хранимых чанков;
- клиент при редактировании считает скользящий хэш → находит совпадающие чанки → шлёт только новые.

### Сжатие

Сжимаем текстовые файлы (txt, html, json) перед загрузкой. Бинарные (картинки, видео) уже сжаты.

### Лимиты трафика

Настраиваются в клиенте («пауза синхронизации на мобильной сети», «ограничить до 1 МБ/с»).

## 13. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Загрузка оборвалась | Продолжаем с последнего успешного чанка |
| Несовпадение хэша на скачивании | Перекачиваем чанк (повреждение) |
| Превышена квота | Отвергаем загрузку, уведомляем пользователя |
| Конфликт синхронизации | Сохраняем как «file (conflict).ext», пользователь сливает |
| Ошибка сервера на финализации | Клиент повторяет; идемпотентно — те же чанки распознаются |
| Сбой блочного хранилища | Запасной вариант — вторичный регион; загрузки в очередь |

## 14. Компромиссы

### Размер чанка

- **Меньше** (1 МБ) — лучше дедупликация, гранулярная синхронизация, но больше оверхеда на метаданные;
- **Больше** (16 МБ) — меньше метаданных, но хуже дедупликация; правки требуют перезагрузки всего чанка.

Типично: 4 МБ (Dropbox).

### Дедупликация: на пользователя vs кросс-пользовательская

- **На пользователя** — приватность сохранена, но затраты на хранилище ×N (каждый пользователь отдельно);
- **Кросс-пользовательская** — огромная экономия места, но теоретическая утечка приватности (можно определить наличие файла).

Dropbox делает кросс-пользовательскую дедупликацию; часть конкурентов — на пользователя (с упором на приватность).

### Стратегия синхронизации

- **Выборочная синхронизация** — пользователь выбирает папки для синхронизации (ограниченное место на ноутбуке);
- **Поточный доступ к файлам** — Files On-Demand (стиль Windows OneDrive): заглушка, скачивание при открытии;
- **Полная синхронизация** — всё везде (тяжело).
