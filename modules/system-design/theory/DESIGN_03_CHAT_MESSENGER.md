# Проектная задача: мессенджер (WhatsApp / Slack)

Обмен сообщениями в реальном времени для миллиардов пользователей. Групповые чаты, присутствие, push-уведомления, потенциально сквозное шифрование (E2E).

---

## 1. Требования

### Функциональные
- 1:1 и групповые чаты;
- отправка и получение сообщений (текст, медиа);
- статус «в сети» (last seen);
- статусы доставки (отправлено, доставлено, прочитано);
- push-уведомления, когда пользователь не в сети;
- история сообщений (поиск).

### Нефункциональные
- **Реальное время** — p99 доставки < 500 мс;
- **Высокая доступность** — 99,99%;
- **Масштаб** — 2B пользователей (масштаб WhatsApp);
- **Постоянные соединения** — миллионы одновременных WebSocket-соединений;
- **Сохранение порядка сообщений в рамках чата**.

---

## 2. Оценка

```
2B зарегистрированных, 500M DAU
Каждый шлёт ~50 сообщений в день → 25B сообщений/день = ~300K сообщений/с в среднем, пик ~1M

Одновременных соединений: 100M+ (активные пользователи)

Хранилище:
  На сообщение ~100 байт (без медиа)
  25B × 100 байт = 2,5 ТБ/день = 1 ПБ/год (со сжатием)
  Медиа — отдельно (S3)
```

---

## 3. API

```http
POST /api/v1/messages
Body: { conversationId, text, mediaUrl? }
→ 201 { messageId, sentAt }

GET /api/v1/conversations/:id/messages?cursor=...&limit=50
→ 200 { messages: [...], nextCursor }

WebSocket /ws
  → сервер шлёт новые сообщения и обновления присутствия
```

---

## 4. Высокоуровневая архитектура

```
Клиент (WS) ↔ балансировщик (L4 passthrough или L7 со стики-сессией) → Connection Service (с состоянием)
                                                                              ↑↓
                                                                      Pub/Sub-слой (Redis / Kafka)
                                                                              ↑↓
                              Message Service ←→ Message DB (Cassandra, шард по conversationId)
                                                                              ↓
                                                                      Push Notification Service (APNs/FCM)
                                                                      для пользователей не в сети
```

---

## 5. Connection Service

**Главная сложность:** миллионы одновременных постоянных соединений.

### Реализация

- **WebSocket** (или MQTT для мобильных — экономнее по батарее);
- **С состоянием** — каждый пользователь привязан к узлу Connection Service;
- **Реестр соединений** — `user_id → conn_service_node_id` (Redis hash).

```
Вход пользователя:
  WS handshake к балансировщику → попадает на узел Connection Service X
  Conn Service: registry[user_id] = nodeX
  Поддерживается heartbeat

Выход / разрыв соединения:
  registry[user_id] = null
  Либо просто протухает heartbeat
```

### Масштабирование

- Каждый узел держит 1M+ одновременных соединений (Erlang/Elixir, Go, Rust);
- горизонтальное добавление узлов;
- **L4-балансировщик** (NLB) либо **anycast** для распределения;
- стики-сессия не нужна, если реестр внешний.

## 6. Доставка сообщений

```
Alice → POST сообщение {conversationId: chat:bob, text: "hi"}
  ↓
Message Service:
  1. Сохранить в БД (Cassandra) — по ключу conversationId
  2. Найти получателей (Bob)
  3. Поднять узел соединения Bob из Redis: nodeY
  4. Отправить на nodeY через внутренний pub/sub (Redis pub/sub или Kafka)
  5. nodeY отправляет сообщение в WebSocket Bob
  6. Если Bob не в сети → push-уведомление (APNs/FCM)
  7. Подтверждение Alice «доставлено»
```

### Pub/Sub-слой

Когда у нас 1000 узлов соединений, сообщение от Alice к Bob — на какой узел слать?

Вариант 1: **прямая маршрутизация** — смотрим узел Bob, шлём TCP-сообщение туда. Точечно.

Вариант 2: **широковещание через pub/sub** — публикуем сообщение по user_id в pub/sub. Каждый узел подписан на тех user_id, что к нему подключены.

WhatsApp использует подход 1 (точная маршрутизация).

---

## 7. Групповой чат (1000+ участников)

Прямая веерная рассылка ×1000 становится дорогой.

### Стратегия

**Веерная рассылка на сервере по группе:**
```
Alice шлёт в group:xyz →
  Message Service:
    Сохраняет одно сообщение в БД (conversationId = group:xyz)
    Берёт список участников (кэшированный)
    Для каждого узла, на котором есть участник → шлёт через pub/sub
    Участники не в сети → push-уведомление
```

**Масштабируемость:** список участников кэширован, сообщение сохраняется один раз, рассылка идёт параллельно.

### Очень большие группы (100K+ участников)

Каналы Slack, серверы Discord — другой шаблон: **подтягивание на чтение**, не отправка на каждого.

```
Участники подписываются на канал группы (Redis pub/sub по channel ID)
Conn service пересылает сообщения подписчикам
```

Discord использует Erlang/Elixir с процессами на канал (миллионы одновременных).

## 8. Модель данных

### Сообщения (Cassandra)

```
TABLE messages (
    conversation_id TEXT,
    sent_at TIMEUUID,
    sender_id BIGINT,
    text TEXT,
    media_url TEXT,
    PRIMARY KEY (conversation_id, sent_at)
) WITH CLUSTERING ORDER BY (sent_at DESC);
```

Ключ шардирования = `conversation_id` → все сообщения чата на одной партиции.

Чтение: «последние 50 сообщений в чате X» → запрос одной партиции, очень быстро.

### Беседы и участники

```
TABLE conversations (id, type, created_at, last_message_at, ...)
TABLE conversation_members (conversation_id, user_id, joined_at, role)
```

Хранится в PostgreSQL (реляционная, меньший масштаб).

### Индексы

- Чтобы пользователь X видел список своих чатов — индекс `(user_id) → conversation_ids` (либо кэш в Redis).

---

## 9. Статусы доставки

```
отправлено → сервер получил, сохранил
доставлено → устройство получателя получило (отправка по WS или подтягивание)
прочитано  → получатель пометил прочитанным
```

Отслеживается через отдельный поток событий или колонку метаданных в сообщении.

С учётом приватности: статус «прочитано» может быть отключаемым.

---

## 10. Присутствие (статус «в сети»)

```
На подключение: HSET presence user:123 online "true" lastSeen now()
На отключение: HSET presence user:123 online "false"
Периодический heartbeat обновляет TTL

Друзья могут читать: HGETALL friend:user_id presence
```

Нюанс масштабирования: «last seen» обновляется при каждом открытии приложения → высокая частота записей. Ограничивать до ~1 обновления в минуту.

Приватность: возможность скрыть last seen и статус «в сети».

---

## 11. Не в сети и push-уведомления

Если получатель не в сети (нет активной WS-сессии):
- шлём push через APNs (iOS), FCM (Android);
- сохраняем сообщение в БД;
- при переподключении клиент дотягивает пропущенные сообщения.

Полезная нагрузка push должна быть маленькой: «У вас новое сообщение от Alice» — без содержимого (для приватности).

## 12. Сквозное шифрование (E2E)

Шаблон WhatsApp (Signal Protocol):
- каждое устройство генерирует ключевую пару;
- открытый ключ загружается на сервер;
- отправитель шифрует сообщение открытым ключом получателя;
- сервер хранит **зашифрованный блоб** и не может прочитать содержимое;
- получатель расшифровывает закрытым ключом.

**Следствия для архитектуры:**
- сервер не может искать по содержимому;
- управление ключами в группах сложно (повторное генерирование ключей при изменении состава);
- резервное копирование сложно (зашифрованный бэкап требует отдельного ключа);
- поиск по истории нельзя предложить из коробки (только клиентский индекс).

---

## 13. Синхронизация между устройствами

У пользователя телефон + ноутбук + планшет. Сообщение, отправленное с телефона, должно появиться на ноутбуке за секунды.

```
У каждого пользователя несколько соединений (одно на устройство)
Сообщения хранятся централизованно
При подключении устройство подтягивает пропущенные сообщения с сервера
Состояние синхронизации: отслеживаем, какое устройство получило какое сообщение
```

## 14. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Падает узел соединений | Клиенты переподключаются (балансировщик перенаправит), состояние в БД |
| Запись в БД упала | Повтор, ошибка отправителю; возможен дубль, если повтор дойдёт обоими путями |
| Разделение в pub/sub | Часть сообщений не доходит до помеченных как не в сети; отправитель видит «отправлено», получатель догонит при переподключении |
| Push-уведомление упало | Повтор через push-сервис; подтягивание в приложении при следующем открытии |
| Получатель удалил аккаунт | Отправитель видит «доставлено», сообщение хранится, но прочитать некому |

## 15. Компромиссы

### Подтягивание vs отправка сервером

- **Отправка через WebSocket (текущий дизайн)** — реальное время, но с состоянием, дорогая инфраструктура;
- **Длинный опрос как запасной вариант** — для клиентов за фаерволом;
- **Чистый опрос** — плохая задержка, использовалось исторически (ранний Skype).

### Централизованно vs P2P

- Централизованно — сервер посередине;
- P2P (WebRTC) — напрямую между устройствами, сервер только для сигнализации.

WhatsApp и Signal — централизованные (со сквозным шифрованием). Skype изначально был P2P, перешёл на централизованный.

### Хранить вечно vs временно

WhatsApp исторически: сообщения хранятся до доставки и удаляются с сервера. Сейчас многие хранят бессрочно в БД.

Snapchat / Telegram Secret Chats — временные, удаляются после прочтения.
