# Развёртывание ML-моделей

Внедрение ML-моделей в продакшен: онлайн-инференс (в реальном времени) против пакетного, реестр моделей, feature store, A/B-тестирование моделей. В 2024–2026 — стандартная тема на собеседовании senior backend / ML platform engineer.

> **Область:** инфраструктура инференса. Векторные БД и RAG — отдельно в [`VECTOR_DBS_RAG.md`](VECTOR_DBS_RAG.md).

## Онлайн против пакетного инференса

### Онлайн-инференс

Запрос-ответ в реальном времени: пользователь совершает действие → модель делает предсказание → возвращается результат.

```
Пользователь → API Gateway → Inference Service → Модель
                                                  ↓
                                            Предсказание (~10–100 мс)
                  ← Ответ с персонализированным результатом
```

**Сценарии:** рекомендации на странице, обнаружение мошенничества по транзакции, ранжирование выдачи поиска, таргетинг рекламы.

**Требования к задержке:** обычно < 100 мс p99. Иногда < 10 мс (высокочастотная торговля, биржи рекламных аукционов).

**Сложности:**
- низкая задержка = небольшая модель или инференс на GPU;
- высокая пропускная способность = батчинг запросов на сервере инференса;
- свежесть признаков — данные должны лежать в памяти или быстром хранилище.

### Пакетный инференс

Предсказания считаются периодически (каждый час / каждую ночь) для всех пользователей или объектов и сохраняются для быстрого извлечения.

```
Расписание: ночью
  → загружаем всех пользователей из БД
  → прогоняем модель (Spark / Flink)
  → записываем предсказания в БД / кэш
  → на запрос — извлечение по ключу

Запрос пользователя → выборка из БД → кэшированное предсказание (< 1 мс)
```

**Сценарии:** «что показать на главной» (предсказания закэшированы на каждого пользователя), email-кампании, предсказание оттока.

**Компромиссы:**
- ✓ низкая задержка запроса (выборка по ключу);
- ✓ можно использовать тяжёлые модели (нет жёсткого бюджета задержки);
- ✗ устаревшие предсказания (не учитывают текущую сессию);
- ✗ затраты на хранение (предсказания для всех пользователей × всех объектов × N вариантов).

### Гибрид

Предварительно считаем кандидатов (пакетно), переранжируем в реальном времени (онлайн).

YouTube: пакетно заранее считает 100–1000 кандидатов на пользователя; онлайн-модель переранжирует с учётом текущей сессии и контекста.

## Архитектура инференса

### Сервер моделей

Специализированные серверы для обслуживания ML-моделей:

- **TensorFlow Serving** — оригинал, gRPC + REST API;
- **TorchServe** — для PyTorch;
- **NVIDIA Triton Inference Server** — мультифреймворковый, оптимизация под GPU, батчинг;
- **Seldon Core / KServe (на Kubernetes)** — оркестрация;
- **BentoML** — Python-native, простое развёртывание.

### Оптимизация

- **Квантование (quantization)** — fp32 → int8/fp16. Меньше, быстрее, небольшая потеря точности.
- **Прунинг** — выкидывание малозначимых весов.
- **Дистилляция** — обучение маленькой «student»-модели имитировать большую «teacher».
- **Компиляция** — TensorRT (NVIDIA), ONNX Runtime, OpenVINO (Intel).
- **Батчинг** — несколько запросов обрабатываются одним батчем (эффективнее на GPU).
- **Кэширование** — частые входы → кэшированные предсказания.

### Железо

- **CPU** — небольшие модели, низкая нагрузка.
- **GPU** — большие модели (CNN, трансформеры), пакетный инференс. Доминирует NVIDIA.
- **TPU** — собственный AI-чип Google.
- **Ускорители** — AWS Inferentia, Apple Neural Engine, Tenstorrent.

## Feature Store

В продакшен-ML нужны **одни и те же признаки** для обучения и инференса (проблема расхождения обучения и инференса — training-serving skew).

### Зоны ответственности feature store

- **Единый источник истины** для признаков.
- **Онлайн-хранилище** — быстрое извлечение в инференсе (Redis, DynamoDB).
- **Офлайн-хранилище** — исторические признаки для обучения (S3, Parquet, BigQuery).
- **Инженерия признаков** — пайплайны вычислений (Flink, Spark).
- **Версионирование** — версии схем признаков.
- **Корректность по моменту времени (point-in-time correctness)** — при обучении достаём значения признаков **на момент** timestamp T.

### Реализации

- **Feast** (open source) — Python-native;
- **Tecton** — managed-вариант, по сути коммерческий Feast;
- **AWS SageMaker Feature Store**;
- **Databricks Feature Store**;
- **Hopsworks**;
- **Самописные** (Uber Michelangelo, Airbnb Zipline, LinkedIn Feathr).

## Шаблоны развёртывания

### Теневое развёртывание (shadow deployment)

Новая модель работает параллельно со старой; предсказания сравниваются. Клиенту возвращается только результат старой модели.

```
Запрос → Старая модель (предсказание → пользователю)
       → Новая модель (предсказание логируется, не возвращается)

Сравнение: распределение различий, задержка, ошибки
```

- ✓ Безопасный тест на реальном трафике
- ✗ Удваивает затраты на вычисления

### A/B-тестирование

Разделить трафик между моделями, сравнить бизнес-метрики.

```
50% → Модель A (текущая prod)
50% → Модель B (challenger)

Метрики: click-through, конверсия, задержка
```

Проверять статистическую значимость; многорукий бандит — для адаптивного распределения трафика.

### Канареечная раскатка

Постепенный выкат: 1% → 10% → 50% → 100%. Мониторим метрики на каждом шаге, откатываемся при ухудшении.

### Мультимодельность

Разные модели для разных сегментов или контекстов.

```
if user.tier == "premium":
    use heavy_model
elif user.country == "US":
    use us_specific_model
else:
    use default_model
```

## Мониторинг

ML-системы деградируют в продакшене без мониторинга.

### Что мониторим

- **Дрейф входных данных (input data drift)** — распределение входных признаков меняется (новое поведение пользователей).
- **Дрейф концепции (concept drift)** — меняется связь вход → выход (рецессия меняет шаблоны покупок).
- **Распределение предсказаний** — выходы сдвинулись.
- **Метрики качества** — если доступна реальная разметка (клики, конверсии).

### Инструменты

- **Evidently AI** — open source;
- **Arize, Fiddler, WhyLabs** — managed-варианты;
- **Кастомные дашборды** — Grafana + Prometheus.

### Триггеры на переобучение

- По расписанию (раз в неделю или месяц).
- По порогу (метрика упала ниже X).
- Непрерывно (поток новых данных из продакшена).

## Бюджет задержки

Для рекомендаций и поиска в реальном времени:

```
Общий бюджет: 100 мс (пользователь воспринимает как мгновенно)

Распределение:
  Сеть (клиент ↔ пограничный узел):  30 мс
  Логика приложения:                 10 мс
  Извлечение признаков:               5 мс (Redis, горячие данные)
  Инференс модели:                   20 мс (батч на GPU)
  Переранжирование + постобработка:  10 мс
  Запас:                             25 мс
```

**Вывод:** задержка самой модели — лишь часть. Извлечение признаков может занимать столько же или дольше.

## Делать самим или брать готовое

| | Делать самим | Брать готовое (managed) |
|---|---|---|
| Стартовые затраты | Высокие (инженерное время) | Низкие (подписка) |
| Затраты на масштабе | Ниже на запрос | Выше |
| Кастомизация | Полная | Ограниченная |
| Размер команды | Нужна команда ML-платформы | Меньше |
| Примеры | Uber Michelangelo, Airbnb Zipline | SageMaker, Vertex AI |

Большинство компаний с менее чем 1000 ML-моделей — берут готовое. FAANG-масштаб — делают сами.

## Анти-шаблоны

- **Расхождение обучения и инференса (training-serving skew)** — разные пайплайны признаков для обучения и инференса → использовать feature store.
- **Нет мониторинга** — модель тихо деградирует, бизнес-метрики падают.
- **Задержка измеряется неполно** — только модель, без извлечения признаков, сети и т. п.
- **Переобучение без проверки** — новая модель выкатывается без офлайн- и онлайн-оценки → регрессия качества.
- **Нет плана отката** — плохая модель ломает продакшен, и нечем откатиться.
- **Чрезмерная инженерия** — сложный пайплайн под простой случай. Часто простая модель + хорошие данные побеждают.
