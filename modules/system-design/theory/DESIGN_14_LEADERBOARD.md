# Проектная задача: таблица лидеров (leaderboard)

Подсчёт очков и ранжирование в реальном времени — игровая индустрия (топ игроков по очкам), фитнес-приложения, e-commerce («топ продавцов»). Главные сложности: высокая пропускная способность записи, разрешение ничьей, запросы по процентилям, масштабирование.

---

## 1. Требования

### Функциональные
- обновление очков игрока (на каждое действие или событие);
- топ-K таблица лидеров (топ-100 глобально, только друзья, по регионам);
- ранг игрока: «Ты #1234 из 10M»;
- история очков (график во времени).

### Нефункциональные
- **Низкая задержка чтения** — топ-K < 100 мс;
- **Обновления в реальном времени** — изменение очков видно за секунды;
- **Высокая пропускная способность записи** — миллионы обновлений в минуту;
- **Согласованность** — итоговая для отображения; точный ранг — по запросу.

---

## 2. Оценка

```
10M MAU, пик 1M одновременно
Обновления очков: 10 событий / игрок / час = ~30K обновлений/с в среднем, пик 100K

Чтения: 100M запросов таблицы лидеров/день = ~1500 чтений/с
Запросы ранга: тот же масштаб

Хранилище:
  10M игроков × 100 байт (id, очки, метаданные) = 1 ГБ
  Компактно, влезает в память
```

## 3. API

```http
POST /api/v1/scores
Body: { playerId, scoreDelta, gameMode? }
→ 204

GET /api/v1/leaderboard/global?limit=100
→ [{ playerId, score, rank }, ...]

```

## 4. Архитектура — Redis Sorted Set (ZSET)

Redis ZSET идеален: упорядоченное множество со значением очков на участника.

```redis
# Обновление очков игрока
ZADD leaderboard 9500 player:123
# (если инкремент, а не замена: ZINCRBY leaderboard +50 player:123)

# Топ-100
ZREVRANGE leaderboard 0 99 WITHSCORES

# Ранг игрока (0-индексирован)
ZREVRANK leaderboard player:123

# Игроки в диапазоне очков
ZRANGEBYSCORE leaderboard 1000 2000
```

**Производительность:**
- вставка / обновление / удаление: O(log N);
- range-запросы: O(log N + M), где M — число возвращаемых элементов;
- поиск ранга: O(log N).

Один Redis-узел держит 100K–1M операций/с.

---

## 5. Масштаб за пределы одного узла

Один ZSET ограничен памятью (десятки ГБ) и тем, что Redis однопоточный.

### Шардированная таблица лидеров

Несколько Redis-узлов, у каждого подмножество. Топ-K — запросы ко всем, потом слияние.

```
Шардирование по hash(player_id) → какой узел держит очки игрока
У каждого узла частичная таблица лидеров

Для глобального топ-K:
  Запрашиваем топ-K с каждого шарда параллельно
  Слияние: собираем топ-K с каждого (M шардов × K элементов), сортируем, возвращаем топ-K
```

Стоимость: топ-K = M × K элементов на сбор + сортировка = O(M × K log(MK)).

При K=100, M=10 шардов: 1000 элементов на слияние. Тривиально.

### Приближённый топ-K и процентиль

Для очень больших N точный ранг дорогой. Используем приближение:

```
Поддерживаем count-min sketch / структуры для квантилей
Топ-K из приближённых очков
Показываем «приближённый ранг» (например, «топ 1%»)
```

Менее точно, но память — константная.

## 6. Разрешение ничьей

Игроки с одинаковыми очками — как упорядочить?

```
Совпавшие очки:
  - Alice: 9500
  - Bob: 9500
  - Carol: 9500
```

Варианты:
- **Лексикографически по имени** — сортируем по player ID или username (детерминированно, но произвольно);
- **Кто раньше дошёл** — кто первым набрал 9500 (по времени);
- **Составной счёт** — `score × 1B + (max_timestamp - their_timestamp)` → вторичная сортировка.

Redis ZSET: участники с одним score по умолчанию сортируются лексикографически. Настройка — через составное кодирование score.

## 7. Таблицы лидеров с временным окном

«Топ игроков за неделю / день / месяц».

### Наивно: храним каждую таблицу лидеров отдельно

```
leaderboard:all-time → ZADD ...
leaderboard:weekly:2024-W42 → ZADD ...
leaderboard:daily:2024-10-15 → ZADD ...
```

Хранилище: ×N временных окон.

### Умно: отслеживание событий + фильтрация

События с очками хранятся с меткой времени. Агрегируются на чтении по окну.

```
events: (player, points, timestamp)
Дневная таблица лидеров: SUM(points) WHERE date = today, GROUP BY player, ORDER BY sum DESC
```

Cassandra / ClickHouse — эффективны для агрегаций.

### Гибрид

Предагрегация периодически (раз в минуту) для свежих окон; холодные диапазоны — по запросу.

---

## 8. Таблица лидеров среди друзей

Показать только среди друзей пользователя.

```
Для пользователя X:
  достать список друзей (User Service): friends = [Y, Z, W]
  для каждого → достать очки из таблицы лидеров
  отсортировать, вернуть
```

Друзей обычно мало (< 1000), задача тривиальна.

Для больших списков (Facebook gaming) — предвычисленные таблицы лидеров среди друзей.

## 9. Multi-region

```
Глобальная таблица лидеров: cross-region, итогово согласованная
Таблица лидеров по региону: низкая локальная задержка

Реализация:
  Локальный Redis в каждом регионе
  Асинхронная репликация в глобальный Redis
  Запросы «глобальный ранг» идут в global; «ранг в моём регионе» — в local
```

## 10. Защита от читерства

Для соревновательных игр — защита от инъекции очков.

- **Обновление очков только из авторитетного состояния на сервере** — клиент предлагает, сервер валидирует;
- **Детектирование аномалий** — резкий скачок очков, невозможные темпы;
- **Проверка по реплею** — для топ-результата запросить видео / реплей;
- **Сервисы защиты от читерства** (Easy Anti-Cheat, BattlEye).

---

## 11. Проблема горячего ключа

«Топ-10» читают все — горячий путь.

Способы защиты:
- **Пограничный кэш CDN** — топ-K с TTL 30 с (небольшое отставание норм);
- **Кэш на уровне приложения** (Caffeine LRU) — каждый экземпляр кэширует топ-K;
- **Чтение с реплик** — несколько Redis-реплик, round-robin;
- **Предвычисленные представления** — материализованный топ-K, обновляется периодически.

---

## 12. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Redis упал | Реплика повышается; обновления последней секунды могут потеряться (интервал RDB-снапшота) |
| Обновление очков упало | Повтор с идемпотентностью; если стабильно фейлится → DLQ |
| Баг раздувает очки | Детектирование: алерты на аномалии; откат событий за последние N часов |
| Гонка на ZINCRBY | Redis однопоточный — атомарно по умолчанию |

## 13. Компромиссы

### Реальное время против пакетной обработки

- **Реальное время** (ZSET на каждое событие) — мгновенное обновление, дорого на масштабе;
- **Пакетная** (агрегация раз в минуту) — дешевле, небольшое отставание.

Большинство игр: реальное время, опираясь на эффективность Redis.

### Точный против приближённого ранга

При N=10M точный ранг требует полного скана сверху. Приближение (процентиль) допустимо.

- Показывать «#1234», если N < 10K;
- показывать «Топ 5%», если N > 1M.

### Персистентность

Redis ZSET в RAM (временный). При сбое недавние обновления теряются.
- AOF (каждую секунду) — ~1 секунда потерь;
- RDB (периодический снапшот) — больше потерь;
- источник истины — БД событий (переигрывание журнала Kafka, если Redis умрёт).

## 14. Жизненный цикл данных

Старые очки со временем менее интересны. Архивируем / сжимаем.

```
Дневные таблицы лидеров: храним 30 дней, архивируем в S3
Недельные: 1 год
Месячные: вечно
Все времена: не архивируем (один ZSET, небольшой)
```

## 16. Вариант: рейтинг ELO

Не сырые очки, а **относительная сила** между игроками.

```
Игрок A (ELO 1500) против игрока B (ELO 1400):
  A ожидаемо выигрывает в 64% случаев.
  Если A победил → получает мало очков (ожидаемо); B теряет мало.
  Если B победил (неожиданно) → получает много; A теряет много.
```

Применяется: шахматы, онлайн-игры, dating-приложения.

Реализация:
- та же структура таблицы лидеров (ZSET с ELO как очки);
- обновления очков по формуле ELO после каждого матча.
