# Проектная задача: видеостриминг (Netflix / YouTube)

Доставлять видео миллионам пользователей с низкой задержкой и адаптивным качеством. Главные компоненты: **пайплайн кодирования видео**, **раздача через CDN**, **адаптивный битрейт (HLS/DASH)**.

---

## 1. Требования

### Функциональные
- загрузка видео (автор);
- просмотр видео в реальном времени (зритель);
- адаптивное качество (мобильный 3G → 4K);
- поиск, рекомендации;
- комментарии, лайки (специфика YouTube).

### Нефункциональные
- **Плавное воспроизведение** — без буферизации при приемлемой полосе;
- **Низкая задержка старта** — < 2 с от клика до первого кадра;
- **Высокая доступность** — 99,99%;
- **Глобальный масштаб** — миллиарды пользователей;
- **Хранилище** — экзабайты видео.

---

## 2. Оценка

```
100M DAU, в среднем 30 мин/день
1 час 1080p ≈ 3 ГБ
1 час 4K ≈ 7 ГБ

Пиковая пропускная способность: 100M пользователей × в среднем 2 Мбит/с = 200 Тбит/с
  → обслуживается пограничными узлами CDN, не источником

Хранилище:
  1B видео × в среднем 10 мин × 7 уровней качества × ~100 МБ на кодирование
  = ~700 ПБ (растёт)

Вычисления на кодирование:
  1M новых видео/день × в среднем 30 мин × 7 качеств
  = серьёзная нагрузка (50K+ обработчиков кодирования)
```

---

## 3. API

```http
POST /api/v1/videos/upload
Body (multipart): { title, description, file }
→ { videoId, uploadUrl } # presigned S3 URL для самой загрузки

GET /api/v1/videos/:id
→ { id, title, description, manifestUrl, thumbnails }

GET /api/v1/videos/:id/manifest.m3u8   # манифест HLS
→ плейлисты по качествам
```

## 4. Пайплайн загрузки и кодирования

```
Автор загружает оригинал →
  S3 (raw-бакет)
  ↓ Событие создания объекта (S3 → SNS → SQS)
  ↓
Обработчики кодирования (Spark / потребители Kafka):
  1. Скачать оригинал
  2. Перекодировать в несколько качеств (240p, 360p, 480p, 720p, 1080p, 4K)
  3. Нарезать на сегменты по 2–10 с: HLS/DASH
  4. Сгенерировать превью (каждые 5 с)
  5. Загрузить закодированные файлы в origin-бакет CDN
  6. Сгенерировать манифест (.m3u8 / .mpd)
  7. Пометить видео как «опубликовано» в БД

Автор получает уведомление: видео готово
```

**Стоимость перекодирования:** очень тяжело по CPU/GPU. Используют специализированные ускорители (NVIDIA NVENC, AWS MediaConvert).

**Параллелизация:** видео разбивается на сегменты, кодирование идёт параллельно, потом склейка.

## 5. Адаптивный битрейт (HLS / MPEG-DASH)

### Концепт

Видео кодируется в **несколько уровней качества**. Плеер выбирает качество по текущей полосе и динамически адаптируется.

### Структура HLS

```
master.m3u8                    # Главный плейлист
├── 240p.m3u8                  # Плейлист для 240p
│   ├── seg_001.ts             # 6-секундные сегменты
│   ├── seg_002.ts
│   └── ...
├── 720p.m3u8
│   ├── seg_001.ts
│   └── ...
└── 1080p.m3u8
    └── ...
```

```
# master.m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=400000,RESOLUTION=426x240
240p.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1500000,RESOLUTION=1280x720
720p.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p.m3u8
```

### Поведение плеера

```
Плеер забирает master.m3u8
Начинает с самого низкого качества (или оценивает по speed test)
Скачивает первый сегмент, замеряет время загрузки
  - Быстро → следующий запрос на манифест более высокого качества
  - Медленно / буферизация → понижаем качество
Непрерывно адаптируется
```

### HLS vs DASH

| | HLS | DASH |
|---|---|---|
| Автор | Apple | ISO-стандарт |
| Формат | TS (transport stream) / fragmented MP4 | MP4 |
| Манифест | .m3u8 | .mpd (XML) |
| Браузеры | Safari нативно, остальные через библиотеки | Большинство современных |
| Устройства | iOS нативно | Android, web и т. п. |

Сейчас обычно отдают оба или используют **CMAF** (Common Media Application Format) — единый mp4 + варианты манифеста.

## 6. Раздача через CDN

Пограничный кэш + защита источника (origin shielding) обязательны на масштабе.

```
Пользователь в Tokyo запрашивает сегмент видео →
  Пограничный узел CDN (POP в Tokyo) — попадание? Отдаём сегмент.
  Промах → запрос к региональному «щиту» (Asia) → источник (S3 в основном регионе)
  Кэшируем для следующих пользователей.
```

**Целевая доля попаданий в кэш:** 95%+. Иначе источник захлёбывается.

**Умное предзаполнение:** популярные видео заранее загружаются на пограничные узлы (Netflix предсказывает шаблоны просмотра по регионам ML-моделями и заранее кэширует).

**Собственная CDN:** Netflix Open Connect — CDN, развёрнутая прямо внутри сетей ISP для очень низкой задержки.

## 7. Хранилище

### Оригинал (raw upload)

S3 Standard или Glacier (после кодирования обращаются редко).

### Закодированные сегменты

- Горячие (популярные): S3 + CDN;
- холодные (старые, редкие): S3 Glacier.

На видео: ~700 МБ суммарно по качествам (10-минутное HD-видео).
1B видео × 700 МБ = 700 ПБ (согласуется с оценкой выше).

### БД метаданных

PostgreSQL / Cassandra — метаданные видео, комментарии, лайки (отдельная агрегация).

## 8. Прямой эфир (live streaming) — расширение

Отличия от VOD (Video on Demand):
- источник: непрерывный кодировщик шлёт сегменты на источник;
- манифест обновляется непрерывно (`#EXT-X-MEDIA-SEQUENCE` инкрементится);
- бюджет задержки жёстче — зрители хотят «прямо сейчас»;
- Low Latency HLS (LL-HLS) → < 5 с от глазка до экрана (против 30+ с у классического HLS);
- WebRTC для интерактива (суб-секунды, видеозвонки).

**Пайплайн:**
```
Камера → RTMP → Сервер приёма → Перекодирование (в реальном времени, несколько качеств) →
  Хранилище сегментов → CDN → Плеер зрителя
```

## 9. Рекомендации и персонализация

### Предвычисления (пакетно)

Ежедневная Spark-задача:
- коллаборативная фильтрация (matrix factorization);
- матрица оценок «пользователь × видео»;
- топ-N на пользователя — в Redis / DynamoDB.

### Переранжирование в реальном времени

При открытии приложения:
- достаём предвычисленных кандидатов (топ-1000);
- переранжируем с учётом контекста: недавние просмотры, устройство, время суток;
- онлайн-инференс ML-моделью.

**A/B-тестирование** — разные модели ранжирования работают на разных корзинах пользователей.

## 10. Комментарии и лайки (специфика YouTube)

### Лайки — счётчик

PostgreSQL / Redis HINCRBY как счётчик. Асинхронная агрегация для отображения:

```
Пользователь нажал «нравится»:
  моментально: визуальный +1 (оптимистичный UI)
  асинхронно: инкремент счётчика в Redis
  пакетно: раз в 60 с, сохраняем Redis → DB
```

### Комментарии

Cassandra, партиционирование по videoId. Постраничный вывод по метке времени.

```
TABLE comments (
  video_id BIGINT,
  comment_id TIMEUUID,
  user_id BIGINT,
  text TEXT,
  PRIMARY KEY (video_id, comment_id)
) WITH CLUSTERING ORDER BY (comment_id DESC);
```

### Ответы и треды

Ссылка `parent_comment_id`. Рекурсивный запрос с ограничением по глубине.

## 11. Защита от пиратства / DRM

Для платного контента (оригиналы Netflix, премиум):
- **DRM (Digital Rights Management)** — Widevine (Google), FairPlay (Apple), PlayReady (Microsoft);
- зашифрованные сегменты идут через CDN;
- плеер договаривается с DRM-сервером о лицензии;
- ключи дешифрования выдаются только на валидные устройства.

Бесплатный уровень (базовый YouTube):
- без DRM;
- водяные знаки для контента автора;
- ручной разбор и удаление по жалобам на нарушение авторских прав.

## 12. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Пограничный узел CDN тормозит → буферизация | Плеер переключается на качество ниже |
| Origin-бакет упал | Multi-region репликация, переключение на резерв |
| Пайплайн кодирования в очереди | Увеличиваем число обработчиков; зритель получает 240p до готовности остальных |
| Live-кодировщик упал | Резервный кодировщик подхватывает (active-active) |
| Рекомендации недоступны | Запасной вариант — список популярных видео (предкэшированный) |

## 13. Компромиссы

### Стоимость хранения против числа качеств

7 качеств × 1B видео — дорого. Компромисс:
- меньше качеств (3–4 вместо 7) — меньше хранилища, меньше выбора;
- кодирование по требованию для холодных видео — высокая задержка первого запроса;
- гибрид: больше качеств только для популярных видео.

### Pull против push в CDN

- **Pull** (по умолчанию) — первый пользователь вызывает промах кэша;
- **Push** — Netflix заранее размещает видео на пограничных узлах по ML-прогнозам.

### Прямой эфир: задержка против надёжности

- 1 с (WebRTC) — интерактивно, нет буфера на сбои сети;
- 5 с (LL-HLS) — есть буфер на «икоту» сети;
- 30 с (классический HLS) — надёжно, поздний догон.
