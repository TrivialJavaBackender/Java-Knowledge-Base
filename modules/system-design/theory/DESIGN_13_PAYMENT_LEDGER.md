# Проектная задача: платежи / бухгалтерская книга

Финансовые транзакции — двойная запись (double-entry bookkeeping), идемпотентность, согласованность, аудит. PayPal, Stripe, любые финтех.

---

## 1. Требования

### Функциональные
- переводы денег между счетами;
- учёт балансов;
- история транзакций / журнал аудита;
- откаты и возвраты;
- мультивалютность.

### Нефункциональные
- **Строгая согласованность** — деньги не дублируются и не теряются;
- **Идемпотентность** — безопасно для повторов (двойное списание категорически недопустимо);
- **Журнал аудита** — каждая транзакция отслеживаема;
- **Регуляторные требования** (PCI-DSS, SOX);
- **Высокая доступность** — 99,99%+.

## 3. Двойная запись (double-entry bookkeeping)

Каждая транзакция = **2 записи в журнале** (дебет + кредит). Баланс всегда = сумма записей.

```
Alice отправляет Bob $100:

ledger_entries:
  txn_id=tx-1, account=Alice, amount=-100, ts=now
  txn_id=tx-1, account=Bob, amount=+100, ts=now

Инвариант: SUM(amount) по обеим записям = 0 (деньги не создаются и не теряются)
```

Баланс не хранится денормализованно — вычисляется (или материализуется).

### Зачем двойная запись

- **Самокорректирующаяся** — сумма должна быть 0; любой дисбаланс = баг;
- **Удобна для аудита** — у каждой операции есть пара записей;
- стандарт в бухгалтерии с XV века.

---

## 4. Модель данных

```sql
-- Источник истины — append-only
CREATE TABLE ledger_entries (
    id BIGSERIAL PRIMARY KEY,
    transaction_id UUID,            -- группирует пару дебет/кредит
    account_id BIGINT,
    amount BIGINT,                  -- В МАЛЫХ ЕДИНИЦАХ (центы); никогда не float!
    currency CHAR(3),
    type ENUM('debit', 'credit'),
    created_at TIMESTAMPTZ DEFAULT now(),
    metadata JSONB                  -- описание, reference и т. п.
);

CREATE INDEX idx_account_time ON ledger_entries(account_id, created_at DESC);
CREATE INDEX idx_txn_id ON ledger_entries(transaction_id);

-- Материализованный баланс (для быстрых чтений)
CREATE TABLE account_balances (
    account_id BIGINT PRIMARY KEY,
    balance BIGINT,
    currency CHAR(3),
    updated_at TIMESTAMPTZ,
    version BIGINT                  -- оптимистическая блокировка
);

-- Идемпотентность
CREATE TABLE idempotency_keys (
    key VARCHAR(64) PRIMARY KEY,
    transaction_id UUID,
    response_body JSONB,
    created_at TIMESTAMPTZ,
    expires_at TIMESTAMPTZ
);
```

**Критично:** деньги — **целые числа** (центы), не float. `0.1 + 0.2 != 0.3` в float-арифметике.

## 5. Поток транзакции

```
POST /api/v1/transfers
Headers: Idempotency-Key: abc-123
Body: { fromAccount, toAccount, amount, currency, description }

Сервер:
  1. Проверить Idempotency-Key
     если есть → вернуть кэшированный ответ (не обрабатываем повторно)

  2. Открыть транзакцию (БД)
     a. Заблокировать оба счёта (SELECT FOR UPDATE, либо оптимистично с version)
     b. Проверить from.balance >= amount
     c. Вставить ledger entries (txn_id=tx_xyz):
        (from, -amount, debit)
        (to, +amount, credit)
     d. Обновить account_balances (уменьшить from, увеличить to)
     e. Сохранить ответ в idempotency_keys
     f. Commit

  3. Асинхронные события в Kafka:
     transaction_completed → уведомить обоих пользователей, аналитика

  4. Return 200 { transactionId, status: "completed", balanceAfter }
```

## 6. Идемпотентность

Критично для предотвращения двойных списаний.

```
Клиент генерирует UUID на каждый запрос, шлёт как Idempotency-Key

Сервер:
  если redis.get(key): возвращаем кэш

  Иначе:
    обрабатываем транзакцию
    Кэшируем результат в Redis (TTL 24 ч) + БД (постоянно)

Если клиент повторил тот же запрос с тем же ключом → тот же результат.
```

См. базу — в [`distributed_systems.md`](distributed_systems.md#idempotency-key).

---

## 7. Модель согласованности

**ОБЯЗАТЕЛЬНО строгая** для финансового состояния. Не итоговая.

Реализация:
- **Транзакции по одной строке** для обновления баланса (PostgreSQL);
- **2PC или Saga** для cross-shard / cross-service;
- **Строгие (linearizable) чтения** для критичного (показ текущего баланса).

Никакого нестрогого кворума. Никаких асинхронных обновлений баланса.

## 8. Шардирование

На масштабе — шардируем по `account_id`.

**Проблема:** перевод задействует два счёта. Часто **разные шарды**.

Решения:

### A. Совместное размещение через диапазон хэшей

Если счета связаны (например, у одного пользователя несколько счетов) — шардируем по `user_id`, а не по `account_id`.

### B. Двухфазная фиксация (2PC)

```
Координатор → Шард A: "приготовиться списать $100 у Alice"
                       → A блокирует, отвечает "готов"
Координатор → Шард B: "приготовиться зачислить $100 Bob"
                       → B блокирует, отвечает "готов"
Координатор: "коммитим оба"
Оба шарда коммитят, отпускают блокировки.
```

- ✓ строгая согласованность;
- ✗ медленно (несколько round-trip), координатор — единая точка отказа, блокирующее поведение.

### C. Saga (событийная)

См. [`../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md`](../../microservices/theory/DISTRIBUTED_TRANSACTIONS.md).

```
1. Списать с Alice (Шард A): Alice -= 100. Публикация события.
2. Зачислить Bob (Шард B): Bob += 100. Публикация события.
3. Если шаг 2 упал: компенсирующая транзакция — зачисляем Alice обратно.
```

- ✓ выше доступность, нет распределённых блокировок;
- ✗ итогово согласованно в короткое окно (Alice -100, Bob ещё не +100);
- распространено в современных финтех.

### D. Записи в одну БД, чтения с шардов

Если масштаб небольшой (< 10K TPS), оставляем записи в одном PostgreSQL primary, масштабируем чтения через реплики.

## 9. Журнал аудита

Каждая операция неизменяема, append-only. Никогда не делать UPDATE/DELETE записей журнала.

```
Даже возврат:
  reverse_txn (зачисление Bob, списание Alice) — отдельные записи
  Ссылка на оригинальную транзакцию в metadata
```

БД аудита обычно только для чтения после записи; через какое-то время может уезжать на более дешёвое хранилище (S3 Parquet).

## 10. Внешние платёжные процессоры

Для платежей по картам — интеграция со Stripe / Adyen / Braintree / PayPal.

```
Клиент вводит карту →
  Клиент токенизирует через Stripe.js (данные карты никогда не попадают к вам — PCI scope)
  Токен идёт на ваш сервер
  Ваш сервер: POST в API Stripe с токеном + суммой
  Stripe: списывает, возвращает успех / ошибку
  Вы: пишете в ваш журнал
```

**PCI-DSS:** если вы прикасаетесь к сырым номерам карт, охват аудита взрывается (аудиты, шифрование, ограничения). Аутсорсим через токенизацию.

## 11. Валюты

### Мультивалютные счета

```
ledger_entries.currency : USD, EUR, GBP
account_balances: отдельный баланс на (account, currency)
```

### Конвертация

При переводе между валютами:
```
Alice (USD) → Bob (EUR)
$100 USD → списываем у Alice
×exchange_rate → €92 EUR → зачисляем Bob
Бухгалтерия: отдельная FX-запись для отслеживания

Курс — у FX-провайдера (Forex API), фиксируется на момент транзакции.
```

Конвертация валют может приводить к округлению — внимательно (округлять единообразно, например всегда вниз для комиссии).

## 12. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Сетевое разделение во время перевода | 2PC блокируется (CP); Saga компенсирует; идемпотентность предотвращает дубликаты на повторе |
| Сервер упал после списания, до зачисления | Компенсация Saga откатывает списание; 2PC ждёт восстановления координатора |
| Гонка: два перевода с одного счёта | Пессимистичная блокировка (SELECT FOR UPDATE) — последовательно |
| Stripe отклонил карту | Помечаем транзакцию как сбойную, записи журнала не пишем |
| Двойное списание | Idempotency-Key ловит (возвращает кэш) |
| Баг переплачивает | Детектируется: SUM(ledger_entries) ≠ 0; алерт, ручной разбор |

## 13. Сверка (reconciliation)

Ежедневная / ежечасная задача проверяет:
- сумма записей журнала = 0 (инвариант);
- материализованный баланс = сумме записей счёта;
- внешне: баланс совпадает со Stripe / банковской выпиской.

Алерты на любое расхождение — расследование сразу.

---

## 14. Компромиссы

### Saga против 2PC

- Saga — для высокой пропускной способности, допускает короткую несогласованность;
- 2PC — для строгих инвариантов, в ущерб пропускной способности.

Современные финтех предпочитают Saga + компенсации + сверка.

### Синхронные против асинхронных события

- синхронно: вызывающий ждёт полного распространения;
- асинхронно: быстрый ответ API, побочные эффекты с задержкой (уведомления, аналитика).

Критическое состояние (баланс) — синхронно. Побочное (email-подтверждение) — асинхронно.

## 15. Регуляторные требования

- **PCI-DSS** — обработка данных карт;
- **SOX** — внутренние финансовые контроли;
- **GDPR / CCPA** — приватность пользовательских данных;
- **KYC / AML** — знай своего клиента, противодействие отмыванию денег;
- **Налоговая отчётность** — форма 1099 в США.

Каждый стандарт добавляет требований (журнал аудита, шифрование, контроль доступа).
