# Проектная задача: веб-краулер

Периодически качает веб-страницы для индексации (поисковая система), мониторинга (отслеживание цен), архивации (Wayback Machine). Главные сложности: масштаб, вежливость (не «дудосить» сайты), дедупликация, извлечение контента.

---

## 1. Требования

### Функциональные
- старт со стартовых URL;
- обход страниц, извлечение текста и исходящих ссылок;
- переход по ссылкам (BFS / DFS);
- периодический повторный обход (свежесть);
- уважение robots.txt;
- хранение скачанного контента для дальнейшей обработки.

### Нефункциональные
- **Вежливость** — не перегружать целевые серверы (ограничение скорости на домен);
- **Масштаб** — миллиарды страниц;
- **Свежесть** — популярные страницы повторно обходятся за дни;
- **Устойчивость** — обработка ошибок, динамический контент, редиректы.

---

## 2. Оценка

```
Веб: ~50B уникальных страниц (грубо)
Повторный обход: топ-1B ежедневно, остальные раз в неделю/месяц
  → ~10K–100K скачиваний в секунду в среднем

Хранилище на страницу (HTML + извлечённый текст):
  В среднем 100 КБ сырого, 20 КБ извлечённого
  10B страниц × 100 КБ = 1 ПБ сырого + 200 ТБ извлечённого

Полоса: 10K запросов/с × 100 КБ = 1 ГБ/с входящего трафика
```

---

## 3. Архитектура

```
Стартовые URL →
URL Frontier (приоритетная очередь на домен)
  ↓
Селектор URL (политика, robots.txt) →
DNS Resolver (кэшированный) →
HTTP Fetcher (пул обходчиков, асинхронный I/O)
  ↓
Ответ →
Парсер контента (извлечение текста и ссылок)
  ↓
  ├── Новые URL → URL Frontier (обратно в очередь)
  ├── Извлечённый контент → Content Store (S3 / HDFS)
  ├── Проверка дедупликации → Bloom Filter / БД хэшей содержимого
  └── БД метаданных (PostgreSQL / Cassandra)

Дальше:
  - Индексатор → инвертированный индекс (Elasticsearch)
  - Аналитика
```

---

## 4. URL Frontier

Приоритетная очередь для предстоящих URL.

### Вежливость — главное ограничение

Не более 1–2 соединений или запросов на домен в секунду.

```
Frontier:
  Очередь на домен: URL example.com все в одной подочереди
  Планировщик вежливости: максимум N одновременных обходчиков на домен
  Между доменами: параллельно
```

Реализация:
- Redis sorted set на домен: `domain:example.com` со score=enqueue_time;
- N обработчиков, каждый берёт URL из разных доменов (round-robin);
- задержки по политике (например, минимум 1 с между запросами к одному домену).

### Приоритеты

Не все URL равны:
- популярные сайты — высокий приоритет (обновлять чаще);
- новые обнаруженные URL — средний;
- длинный хвост / низкий PageRank — низкий.

Многоуровневая приоритетная очередь: уровни по приоритетам. Верхние уровни обходим чаще.

### Дедупликация в очереди

URL уже обходился или в очереди? Bloom filter (быстрая проверка «вероятно да») + просмотр в БД для подтверждения.

```python
if not bloom.contains(url):
    bloom.add(url)
    enqueue(url)
elif not db.exists(url):  # проверка ложного срабатывания bloom
    bloom.add(url)
    enqueue(url)
# иначе: пропускаем дубль
```

## 5. DNS Resolver

DNS на каждый URL добавляет задержку. Кэшируем:

```
DNS-кэш:
  domain → (ip, ttl)
  Попадание: пропускаем DNS-запрос
  Промах: резолвим, кэшируем на TTL

Локальный DNS-сервер (bind, unbound) делает рекурсию + кэширование.
```

Без кэша: каждый обход = DNS-запрос = 10–100 мс оверхеда.

## 6. HTTP Fetcher

Асинхронный I/O (Java NIO, Go goroutines, Python asyncio) для массовой конкурентности на одной машине.

```python
# Псевдо-асинхронно
async def crawl(url):
    response = await http.get(url, timeout=10, follow_redirects=True)
    if response.status == 200:
        return response.text
    elif response.status in (301, 302):
        new_url = response.headers['Location']
        return await crawl(new_url)
    elif response.status == 429:  # Rate limited
        sleep_and_retry(url)
    elif response.status >= 500:
        retry_with_backoff(url)
    else:
        log_failure(url, response.status)
```

**Пул соединений** — переиспользуем TCP/TLS-соединения.

**Лимит конкурентности на хост** — максимум 5 соединений на хост.

## 7. Robots.txt

Сайт может задать правила для краулеров:

```
example.com/robots.txt:
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 10
```

```python
robots = fetch(f"{domain}/robots.txt")
for url in domain_urls:
    if not robots.allowed(crawler_user_agent, url.path):
        skip(url)
    sleep(robots.crawl_delay or 1)
```

Кэшируем robots.txt на домен (TTL 24 часа).

## 8. Извлечение контента

### Парсинг HTML

Извлекаем:
- title, meta-теги;
- текст body (без HTML);
- исходящие ссылки (`<a href>`);
- канонический URL (`<link rel="canonical">`).

Библиотеки: BeautifulSoup, jsoup (Java), readability.js.

### Определение языка

Для мультиязычной индексации — детектирование языка (cld3, langdetect).

### Поиск дубликатов

Один и тот же контент на разных URL:
- хэш содержимого (SHA-256) — точное совпадение;
- SimHash / MinHash — обнаружение почти-дубликатов (небольшие отличия).

```
content_hash = SHA256(extracted_text)
если есть в Bloom + БД → помечаем как дубль канонического URL
иначе → сохраняем
```

### Извлечение структурированных данных

- JSON-LD, microdata, Open Graph;
- данные о товарах, цены, отзывы (семантика).

## 9. Хранилище

### Сырой HTML

S3 / HDFS, партиционирование по дате и домену.

```
s3://crawler-raw/2024/01/15/example.com/<url-hash>.html.gz
```

Сжатие gzip — текст ужимается в 5–10 раз.

### Извлечённый текст

Меньше, запрашивается чаще. Cassandra или Parquet на S3.

### Метаданные

PostgreSQL — URL, статус, дата обхода, хэш содержимого, ссылки.

```sql
CREATE TABLE pages (
    url TEXT PRIMARY KEY,
    domain TEXT,
    last_crawled_at TIMESTAMPTZ,
    status INT,
    content_hash CHAR(64),
    raw_storage_path TEXT
);
CREATE INDEX idx_domain ON pages(domain);
CREATE INDEX idx_last_crawled ON pages(last_crawled_at);
```

## 10. Стратегия повторного обхода

URL обходятся повторно с разной частотой на основе:
- **частоты обновлений** (новостной сайт — ежечасно vs статический блог — раз в месяц);
- **PageRank / важности** — популярные страницы чаще;
- **заголовка Last-Modified** — подсказка сайта.

```
re_crawl_interval = base_interval × importance_factor × update_frequency_factor

Топ-1M страниц → ежедневно
Следующие 100M → еженедельно
Остальные → ежемесячно
```

Планирование: каждая обойдённая страница ставится обратно в очередь с будущей меткой времени.

## 11. Распределённые краулеры

Одна машина — 10K–100K запросов/с максимум (упирается в сеть). Для 1B+ страниц в день — несколько машин.

### Стратегия шардирования

Партиционирование по **хэшу домена** — все URL одного домена обрабатываются одним обработчиком (сохраняем вежливость).

```
crawler_id = hash(domain) % N_crawlers
```

Сам URL Frontier тоже распределён — Redis Cluster шардирует по домену.

### Координация

- новые URL найдены обработчиком A → публикация в очередь (Kafka);
- другие обработчики читают свои партиции.

## 12. Сценарии сбоев

| Сценарий | Обработка |
|----------|-----------|
| Краулер упал | URL остались в очереди, другой обработчик подхватывает |
| Сайт отвечает 503 | Экспоненциальная задержка, повтор позже (не долбим) |
| Бесконечный цикл (календарь-ловушка для пауков) | Лимит глубины на домен, дедупликация URL |
| Битые SSL-сертификаты | Пропустить или принять по политике |
| Медленный сайт | Таймаут (10 с), повтор с экспоненциальной задержкой |
| Robots.txt недоступен | По умолчанию = «всё разрешено»? Или «по умолчанию запретить»? (выбор политики) |

## 13. Анти-шаблоны / защита от обнаружения

Часть сайтов активно блокирует краулеров:
- **Идентификация User-Agent** — представляться (Googlebot/2.1 и т. д.);
- **Ограничение скорости** — уважать 429;
- **Рендеринг JavaScript** — современные SPA требуют headless-браузер (Puppeteer, Playwright);
- **CAPTCHA** — обычно такие страницы пропускаем;
- **Honeypot-ссылки** — скрытые ссылки, переход по которым → пометка «бот».

## 14. Компромиссы

### BFS vs DFS

- **BFS** (по умолчанию) — обходит по расстоянию от стартовых URL, сбалансированно;
- **DFS** — глубоко в одну ветку, может застрять на большом сайте.

Большинство краулеров — похожи на BFS (приоритетная очередь перетягивает порядок).

### Вежливость против пропускной способности

Строгая вежливость (1 запрос/с на домен) — медленно на множестве маленьких сайтов, узкое место на больших.
Агрессивный краулер — риск IP-банов, вред сайтам.

Настраивать на домен по времени ответа и `Crawl-delay`.

### Реальное время против пакетной обработки

Поисковые движки: в реальном времени (непрерывно).
Архивы (Wayback): пакетно (полный обход периодически).

## 15. В продакшене

- **Googlebot** — самый продвинутый краулер, миллиарды страниц проиндексированы;
