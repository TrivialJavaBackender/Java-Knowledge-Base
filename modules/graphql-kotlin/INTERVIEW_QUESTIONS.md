## 1. Основы GraphQL

### Q1: В чём ключевые отличия GraphQL от REST? Когда GraphQL уместнее?

**A:** GraphQL — это типизированный query-язык с одним endpoint’ом и единой схемой. Клиент сам выбирает поля → нет over-fetching и under-fetching. Версионирование — через эволюцию схемы и `@deprecated`, не через `/v2`. Поддерживает один запрос с произвольной глубиной связей и подписки. REST же опирается на множество URL’ов, фиксированную форму ответа и HTTP-кэш «из коробки».

GraphQL уместен, когда:
- много клиентов с разными нуждами (mobile vs web), каждый берёт нужный набор полей;
- модель домена графовая (User → Posts → Comments → User), и клиент часто хочет всё сразу;
- продукт быстро эволюционирует, и хочется добавлять поля без `/v2`.

REST остаётся проще, когда: ресурсы плоские, нужна агрессивная HTTP-кэширование, нет команды чтобы поддерживать схему/кодген.

> theory/BASICS.md §1

### Q2: Расскажи про модель типов GraphQL. Какие категории?

**A:** Шесть категорий:
1. **Scalar** — `Int`, `Float`, `String`, `Boolean`, `ID` плюс custom (`DateTime`, `UUID`).
2. **Object** — `type User { … }`, поля имеют резолверы.
3. **Interface** — общий контракт; объекты-имплементации указывают `implements`.
4. **Union** — «одно из»: `union SearchResult = User | Post`.
5. **Input** — типы для аргументов мутаций; не могут содержать резолверы или ссылки на Object.
6. **Enum** — замкнутый набор значений.

Модификаторы: `!` — non-null, `[T!]!` — non-null список non-null элементов. Корневые типы — `Query`, `Mutation`, `Subscription`.

> theory/BASICS.md §2

---

### Q3: Чем отличаются Query, Mutation и Subscription?

**A:**
- **Query** — чтение, идемпотентно. Поля одного запроса исполнитель **может выполнять параллельно**.
- **Mutation** — запись с побочными эффектами. Поля одного блока выполняются **последовательно** (по спецификации) — иначе порядок мутаций был бы недетерминирован.
- **Subscription** — long-lived поток, обычно поверх WebSocket (`graphql-ws` протокол). На стороне graphql-kotlin реализуется как `Flow<T>`. Канонично — один root-field на одну подписку.

> theory/BASICS.md §2

### Q4: Что такое fragments, aliases, variables?

**A:**
- **Fragment** — переиспользуемый набор полей: `fragment UserCard on User { id name email }`. Помогает не дублировать селекшен-сеты.
- **Alias** — переименование поля в ответе: `me: user(id: "1") { name }`. Нужно когда одно поле запрашивается несколько раз с разными аргументами.
- **Variable** — параметр вне текста запроса: `query GetUser($id: ID!) { user(id: $id) }`, значения `{"id":"42"}` передаются отдельно. Важно для безопасности (переменные не подмешиваются в строку запроса) и кэширования (кэш — по тексту запроса + переменным).

Бонус: **inline fragment** — `... on User { … }` для union/interface, чтобы выбрать поля конкретного варианта.

> theory/BASICS.md §4

### Q5: Как устроен ответ и обработка ошибок?

**A:** Ответ — JSON c полями `data`, `errors`, `extensions`:

```json
{ "data": { "user": null }, "errors": [{ "message": "...", "path": ["user","posts"], "extensions": {"code":"NOT_FOUND"} }] }
```

Ключевые свойства:
- **Partial response**: ошибки в одном поле не валят весь запрос.
- **Error propagation**: если non-null поле зарезолвилось null или с ошибкой, null «всплывает» к ближайшему nullable родителю; в крайнем случае `data: null`.
- `errors` — массив; у каждой `message`, `path`, опционально `locations` и `extensions` (свободное место для `code`, `requestId`, и т.п.).
- В graphql-kotlin кастомизация — через `DataFetcherExceptionHandler`.

> theory/BASICS.md §5

### Q16: Почему обход дерева резолверов начинается с root-резолвера (`Query.user`), а не может пойти в произвольном порядке?

**A:** Каждый резолвер получает `parent` одним из своих аргументов `(parent, args, context, info)`, а для полей объекта `parent` — это уже готовое значение родителя. `User.posts(parent: User)` не может выполниться, пока не готов сам `User`, возвращённый `Query.user`. Поэтому исполнение обязано идти сверху вниз: root-резолвер сначала возвращает объект, затем для каждого его поля вызывается резолвер уже с этим объектом как `parent`, и так до листьев дерева. Тривиальные резолверы (взять поле из parent) graphql-kotlin генерирует автоматически для data class; кастомные — там, где нужен доп. запрос (БД/сервис), и именно на этом уровне («по вызову на каждый экземпляр родителя») рождается N+1.

> theory/BASICS.md §3

---

### Q17: Почему сервер валидирует AST запроса против схемы отдельным этапом до исполнения резолверов, а не проверяет типы по ходу исполнения?

**A:** Жизненный цикл строго разбит на стадии: Parser (текст → AST) → Validator (AST против схемы: существуют ли поля, совпадают ли типы аргументов, корректны ли фрагменты) → Executor (обход дерева, вызовы резолверов). Если бы проверка происходила по ходу исполнения, часть резолверов — в том числе мутации с побочными эффектами — успела бы отработать до того, как ошибка в другой части того же запроса обнаружится, и клиент получил бы частично применённые изменения без внятного объяснения. Отдельный этап валидации гарантирует: либо запрос целиком соответствует контракту схемы и только тогда передаётся в Executor, либо клиент сразу получает ошибку валидации без единого вызова резолвера и без единого побочного эффекта.

> theory/BASICS.md §6

## 2. graphql-kotlin & Spring Boot

### Q6: Чем code-first отличается от schema-first и почему graphql-kotlin — code-first?

**A:**
- **Schema-first**: SDL — источник правды. Резолверы пишутся отдельно и вручную мапятся на поля (как в graphql-java + RuntimeWiring).
- **Code-first**: схема выводится из кода (типы и функции). Преимущество — refactor-safe (компилятор переименует), DRY, ближе к остальному Kotlin-коду. Недостаток — сложнее посмотреть SDL не запуская приложение (хотя `graphql-kotlin` экспортирует через `/sdl`).

graphql-kotlin полностью code-first: ты пишешь `class FooQueries : Query { fun bar(): Int = 42 }`, schema generator через рефлексию строит SDL.

> theory/GRAPHQL_KOTLIN_SPRING.md §1

---

### Q7: Как работает schema generator в graphql-kotlin? Какие подводные камни?

**A:** При старте `toSchema(config, queries, mutations, subscriptions)` (или Spring autoconfigure) проходит по всем `TopLevelObject` через рефлексию: берёт public-функции и свойства, мапит Kotlin-типы на GraphQL-типы (с учётом nullability и generics), регистрирует типы в схеме. Поведение настраивается через `SchemaGeneratorHooks` (custom scalars, фильтры).

Подводные камни:
- `graphql.packages` обязательно указать в `application.yml`, иначе типы не находятся.
- Резолвер должен быть **Spring-бином** (`@Component`) — иначе autoconfigure его не подхватит.
- Internal/private не попадают в схему по умолчанию.
- Generic с erased типом в коллекциях (`List<*>`) не сгенерится.
- Subscription — обязан возвращать `Flow<T>` (или `Publisher<T>`), не `suspend`.

> theory/GRAPHQL_KOTLIN_SPRING.md §9

---

### Q8: Как graphql-kotlin поддерживает suspend-резолверы?

**A:** При генерации schema for `suspend fun foo(): Bar` создаётся специальный DataFetcher, который вызывает функцию через корутинный bridge `kotlinx-coroutines-jdk8.future { … }`, возвращающий `CompletableFuture<Bar>`. graphql-java executor умеет ждать CF естественно.

Контекст корутины наследуется от `Dispatchers.Default`; при необходимости можно сделать кастомный `CoroutineContext` через DataLoader registry и `GraphQLContext`. Главное — не вызывать `runBlocking` внутри (заблокирует executor-поток).

> theory/GRAPHQL_KOTLIN_SPRING.md §5

---

### Q9: Что такое GraphQLContext и зачем он?

**A:** `GraphQLContext` — request-scoped мап, доступный в каждом резолвере через `DataFetchingEnvironment.graphQlContext`. Туда кладут: текущего `UserPrincipal`, `requestId`, локаль, `DataLoader`-регистри. Создаётся на каждый запрос через бин `GraphQLContextFactory<ServerRequest>`.

Альтернатива — `localContext` (передаётся от parent резолвера к children). Глобальное состояние (`@Component`) — для request-зависимых данных не подходит, потому что нет thread-locality (резолверы могут гулять по разным потокам в reactor).

> theory/GRAPHQL_KOTLIN_SPRING.md §6

---

### Q18: Почему в graphql-kotlin достаточно реализовать пустой интерфейс `Query`, чтобы public-функции класса стали полями схемы — что делает саму работу, если не интерфейс?

**A:** `Query`/`Mutation`/`Subscription` в graphql-kotlin — это пустые маркерные интерфейсы, у них самих нет ни одного метода. Всю работу делает schema generator при старте приложения: он ищет Spring-бины, реализующие эти маркеры, и через рефлексию проходит по их public-функциям — каждая становится полем соответствующего root-типа в SDL. Интерфейс здесь нужен исключительно как сигнал автоконфигурации, где искать корневые операции, иначе пришлось бы явно перечислять список классов вручную. Отсюда и характерный подводный камень: класс без маркера или не являющийся Spring-бином (`@Component`) в схему не попадёт, даже если по сигнатуре он выглядит как резолвер.

> theory/GRAPHQL_KOTLIN_SPRING.md §2

---

### Q19: Зачем для `DateTime`/`UUID` в graphql-kotlin нужен собственный `GraphQLScalarType` с `Coercing`, если `Int`/`String`/`Boolean` работают из коробки?

**A:** Стандартные scalar'ы (`Int`, `Float`, `String`, `Boolean`, `ID`) — часть спецификации, и graphql-java знает правило их сериализации/парсинга сам. Для доменных типов вроде `OffsetDateTime` такого готового правила нет — нужно явно объяснить исполнителю, как превратить объект в JSON-значение при ответе (`serialize`) и как превратить обратно значение из **переменной** (`parseValue`, сырое значение) или из **литерала прямо в тексте запроса** (`parseLiteral`, принимает AST-узел вроде `StringValue`) в объект. Без этой пары runtime не знает, что делать с полем такого типа — оно не Object и не входит в стандартные Scalar. В graphql-kotlin эта пара регистрируется через `SchemaGeneratorHooks.willGenerateGraphQLType`, которая подставляет кастомный `GraphQLScalarType` вместо попытки развернуть тип как обычный Kotlin-класс.

> theory/GRAPHQL_KOTLIN_SPRING.md §7

## 3. DataLoader & N+1

### Q10: Что такое N+1 в GraphQL и почему он практически неизбежен?

**A:** Запрос `{ posts { author { name } } }` получает 100 постов одним SQL и затем для каждого вызывает резолвер `Post.author` отдельно → 100 SQL’ей плюс первый = 101.

В REST такого нет, потому что разработчик заранее решает форму ответа и пишет `JOIN`. В GraphQL клиент сам выбирает поля — сервер не знает заранее, нужен ли `author`. Тривиальная имплементация резолверов (по полю на вызов) даёт N+1 как побочный эффект гибкости.

> theory/DATALOADER_NPLUS1.md §1

---

### Q11: Как DataLoader решает N+1? Опиши его жизненный цикл.

**A:** DataLoader — отложенный батч + per-request кэш.
1. Резолвер вызывает `loader.load(key)` — получает `CompletableFuture<V>`, ничего сразу не загружается.
2. Все `load()` одного execution tick’а копятся в очередь.
3. graphql-java вызывает `loader.dispatch()` после того, как все резолверы текущего уровня выдали свои CF.
4. DataLoader дедуплицирует ключи и вызывает `batchLoadFunction(keys: List<K>) -> List<V>`.
5. Полученные значения раздаются обратно в CF в **том же порядке, что ключи**.

Кэш — двухуровневый: promise cache (CF на ключ) и value cache (после resolve). Per-request, чтобы не утекать данные между пользователями. Размер батча ограничен `setMaxBatchSize` (для дружбы с БД).

> theory/DATALOADER_NPLUS1.md §2

---

### Q12: Какие есть подводные камни DataLoader?

**A:**
- **Order matters**: batch function обязана вернуть значения в порядке ключей; если значение отсутствует — `null` на этой позиции.
- **Длина списка должна совпадать** с длиной ключей; иначе DataLoader падает с `BatchLoaderError`.
- **Не работает в Subscription** «из коробки» — там нет request scope в классическом смысле.
- **Глобальный shared cache** легко даёт cross-tenant утечки и stale data; обычно лучше per-request.
- **Mutations**: после изменения данных `loader.clear(id)` — иначе тот же запрос увидит старые данные в последующих полях.
- **Размер батча** без лимита бьёт по `IN (...)`-параметру БД и портит план запроса.

> theory/DATALOADER_NPLUS1.md §7

---

### Q20: Почему `batchLoadFunction` обязан вернуть список значений, выровненный по позициям со списком ключей, а не `Map<K, V>`?

**A:** Контракт DataLoader требует, чтобы `batchLoadFunction(keys: List<K>): List<V>` вернул результат строго в том же порядке, что и входные ключи — в реализации `UserDataLoader` это явно видно по комментарию «важен порядок!» рядом с `keys.map { byId[it] }`. DataLoader раздаёт результаты обратно по тем же позициям во внутренние `CompletableFuture`, созданные для каждого `load(key)`; если бы batch-функция возвращала `Map<K, V>` без гарантии порядка и полноты, DataLoader не смог бы надёжно сопоставить, какое значение относится к какому из накопленных вызовов — особенно когда часть ключей не нашлась и для них нужно вернуть `null` именно на своей позиции, а не выбросить их из ответа.

> theory/DATALOADER_NPLUS1.md §3

---

### Q21: Почему DataLoader не отправляет батч сразу по первому `load()`, а ждёт конца execution tick'а?

**A:** graphql-java исполняет поля одного уровня дерева параллельно: на уровне `Post.author()` резолвер вызывается для всех постов практически одновременно, каждый раз просто выдавая `CompletableFuture` без немедленного значения. `dispatch tick` — момент, в который диспетчер приходит только после того, как **все** резолверы текущего уровня успели вызвать `load()` и вернуть свои CF. Если бы DataLoader слал батч сразу по первому вызову, он поймал бы только один ключ и превратил бы батчинг обратно в N+1 (просто асинхронный, по одному запросу на ключ). Ожидание конца тика — единственный момент, когда гарантированно собраны все ключи этого уровня, поэтому именно тогда вызывается `dispatch()` и уходит настоящий батч `WHERE id IN (...)`.

> theory/DATALOADER_NPLUS1.md §4

---

### Q22: Почему DataLoader обязан кэшировать результаты на уровне одного запроса, а не быть общим синглтоном на всё приложение?

**A:** Кэш DataLoader (promise cache + value cache) пересоздаётся заново для каждого GraphQL-запроса — обычно через `KotlinDataLoaderRegistryFactory`, привязанный к `GraphQLContext` конкретного запроса. Если сделать его глобальным shared-кэшем на уровне приложения (например, через `Caffeine`), в кэше окажутся значения, загруженные в контексте одного пользователя, и следующий запрос от другого пользователя может получить их из кэша в обход своих прав доступа — это утечка данных между пользователями (cross-tenant), плюс такой кэш никогда не узнаёт, что данные в БД изменились между запросами (stale data). Per-request scope устраняет оба риска ценой того, что кэш не переиспользуется между разными запросами вообще.

> theory/DATALOADER_NPLUS1.md §5

---

### Q23: DataLoader уже дедуплицирует ключи — зачем тогда дополнительно ограничивать `maxBatchSize`?

**A:** Дедупликация убирает повторы одного и того же ключа (`authorId=10`, запрошенный дважды), но не ограничивает количество **уникальных** ключей в одном батче. Если в ответе, скажем, 10 000 постов с разными авторами, DataLoader соберёт все 10 000 уникальных `authorId` в один вызов `batchLoadFunction`, а тот — в один SQL с `WHERE id IN (10000 значений)`. Такой запрос упирается в лимит параметров БД и портит план выполнения. `setMaxBatchSize(100)` заставляет DataLoader разбить один большой батч на несколько последовательных чанков — несколько SQL вместо одного, но каждый в разумных для БД пределах.

> theory/DATALOADER_NPLUS1.md §6

## 4. Federation

### Q13: Зачем нужна Apollo Federation, и из каких частей она состоит?

**A:** Federation — стандарт композиции нескольких GraphQL-сервисов в один граф. Решает: (1) разделение по командам/доменам, (2) единый endpoint для клиента, (3) типобезопасный кросс-сервис join.

Компоненты:
- **Subgraph** — обычный graphql-сервис плюс federation-директивы (`@key`, `@external`, и т.д.) и обязательные служебные поля `_service { sdl }` и `_entities`.
- **Supergraph** — композит схема, собранная из subgraph-схем (статически через `rover compose` или динамически через managed federation в Apollo Studio).
- **Router/Gateway** — Apollo Router (Rust) или Apollo Gateway (Node), который принимает клиентские запросы, строит query plan и распределяет работу по subgraphs, склеивая результаты через `_entities`.

> theory/FEDERATION.md §2

---

### Q14: Что делают директивы `@key` и `@external`?

**A:**
- `@key(fields: "id")` — объявляет, что у типа есть «первичный ключ» по этим полям; через них тип может быть найден в этом subgraph и расширен в других.
- `@external` — помечает поле как «определено в чужом subgraph». Внутри текущего subgraph такое поле не резолвится.

Каноничный паттерн расширения:
```graphql
# users-service: type User @key(fields: "id") { id name email }
# reviews-service:
type User @key(fields: "id") @extends {
  id: ID! @external
  reviews: [Review!]!
}
```

Router при запросе `User.reviews` приходит к reviews-service с `representations: [{__typename: "User", id: "..."}]`, и subgraph должен вернуть `User`-объект (через **entity resolver**), у которого затем будет вызван `reviews()`.

> theory/FEDERATION.md §3

---

### Q15: Чем gateway/router отличается от schema stitching и когда federation не нужна?

**A:** **Schema stitching** (legacy) — gateway знает все subgraph-схемы и **вручную** настраивает делегирование/линковку типов. Federation формализует этот процесс через директивы и стандартный протокол `_entities`/`_service`, делает его типобезопасным и пригодным для managed композиции.

**Router (Apollo Router)** — более новый компонент на Rust, заточен под federation v2; **gateway (Apollo Gateway)** — старая Node-реализация. Технически взаимозаменяемы для большинства простых случаев.

Federation **не нужна**, когда:
- < 5 GraphQL-сервисов и одна команда — overhead избыточен;
- сервисы пишут на разных стеках, но домены не пересекаются — лучше отдельные эндпоинты;
- большая часть данных в одной БД — стичь схемы будет искусственно.

Альтернатива в этих случаях — единый graphql-kotlin сервис как **BFF** поверх REST/gRPC бэкендов (см. `../microservices/theory/EDGE_AND_MESH.md`).

> theory/FEDERATION.md §8

### Q24: Почему schema stitching считается устаревшим подходом, а Federation — его стандартизацией, а не просто другим названием того же самого?

**A:** Stitching и Federation решают одну и ту же задачу — собрать несколько GraphQL-сервисов в один граф — но по-разному распределяют знание о типах. При stitching gateway должен **вручную** знать все схемы участников и настраивать делегирование/связывание типов кодом — любое изменение subgraph-схемы требует правки gateway, то есть жёсткая связанность. Federation переносит это знание в сами subgraphs: они декларируют себя через директивы (`@key`, `@external` и т.п.) и отдают `_service { sdl }`, а gateway/router лишь компонует эти декларации в supergraph и строит query plan — ему не нужно заранее знать, как связаны типы, это выводится из директив. Поэтому Federation — не «другой gateway», а протокол, снимающий ручную работу и связанность, свойственные stitching.

> theory/FEDERATION.md §1

### Q25: Что именно происходит между тем, как router получает запрос `User.reviews`, и тем, как `reviews-service` возвращает готовый объект `User`?

**A:** Router видит, что поле `reviews` определено в `reviews-service`, но у него есть только `id` пользователя из `users-service`. Он посылает в `reviews-service` служебный запрос `_entities(representations: $repr)`, где `representations` — список вида `{__typename: "User", id: "..."}`. Внутри subgraph за это отвечает **entity resolver** — в graphql-kotlin-federation это бин `FederatedTypeResolver<User>`, чей метод `resolve(env, repr)` по списку representations строит список объектов `User` без похода в БД за уже известными полями, только по ключу. После этого обычный резолвер `User.reviews()` вызывается уже на этом восстановленном объекте, как на любом другом `parent`.

> theory/FEDERATION.md §4

### Q26: Почему совместимость типов между subgraphs обязана проверяться на этапе composition, а не в рантайме на живом трафике?

**A:** Composition (статический `rover supergraph compose` или managed-режим через Apollo Studio) собирает supergraph SDL из отдельных subgraph-схем и на этом шаге валидирует, что один и тот же тип (например `User`) определён во всех subgraphs согласованно: те же поля, совместимые сигнатуры, корректные `@key`. Если бы эта проверка откладывалась до рантайма, несовместимость — например, разные типы одного поля в двух subgraphs или отсутствие `@key` там, где тип расширяется — проявлялась бы как ошибка `_entities` посреди обслуживания реального клиентского запроса. Проверка на этапе сборки supergraph превращает потенциальную рантайм-ошибку в ошибку CI/деплоя, которую разработчик увидит до раскатки.

> theory/FEDERATION.md §6

### Q27: Работает ли DataLoader между разными subgraphs — и кто в Federation отвечает за батчинг на уровне нескольких сервисов?

**A:** Нет — DataLoader как паттерн работает внутри одного subgraph, батчит вызовы к своей БД/сервису в пределах своего процесса. Между subgraphs батчинга через DataLoader нет и быть не может, потому что каждый subgraph — отдельный процесс со своим execution tick'ом. Вместо этого router сам батчит **entity-запросы**: если ему нужно у одного subgraph'а зарезолвить одинаковый `__typename` для нескольких сущностей сразу (например, `reviews` для 50 разных `User`), он соберёт все их representations в один `_entities`-запрос, а не будет слать 50 отдельных.
