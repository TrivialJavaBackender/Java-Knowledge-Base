# Релизные стратегии: как код из основной ветки становится работающей функциональностью

> **Какую проблему решает.** Код слит в основную ветку — пользователь его не видит. Между этими
> двумя состояниями лежит набор решений: что именно уезжает в этот релиз, под каким номером,
> когда, на скольких пользователей сразу, что делать со схемой БД и как вернуться назад, если
> списания пошли дважды. Каждое из решений можно принять неправильно, и цена ошибки в платёжном
> сервисе измеряется не в часах простоя, а в чужих деньгах.
> **Кому это надо.** Тому, кого на собеседовании спрашивают «как вы катите в прод» — это проверка
> не на знание слова canary, а на то, понимаете ли вы, что откат кода не откатывает данные. И тому,
> кто первый раз оказался дежурным в ночь после релиза.
> **Когда НЕ надо.** Когда у вас один инструмент вместо ответа: «мы всё катим канареечно» —
> такой же плохой ответ, как «мы катим руками в пятницу». Выбор здесь выводится из двух чисел
> (цена ошибки и время до обнаружения), а не из моды. И когда релиз ещё не проблема: пока
> развёртывание раз в квартал делает один человек за полчаса, механика важнее, чем стратегия.

Путь кода до основной ветки — ветвление, слияния, код-ревью, CI-гейт — в
[`BRANCHING_AND_CODE_FLOW.md`](BRANCHING_AND_CODE_FLOW.md); здесь всё начинается с момента, когда
код уже в основной ветке. Что делают, когда релиз уронил прод, — [`INCIDENTS_AND_POSTMORTEM.md`](INCIDENTS_AND_POSTMORTEM.md);
метрики доставки как отчётность — [`DELIVERY_METRICS.md`](DELIVERY_METRICS.md); вечные feature flags
как статья долга — [`TECH_DEBT.md`](TECH_DEBT.md); сценарий «релиз в пятницу» —
[`DECISION_SCENARIOS.md`](DECISION_SCENARIOS.md). Техника развёртывания в Kubernetes —
[`KUBERNETES.md` в модуле infrastructure](../../infrastructure/theory/KUBERNETES.md), GitOps и Argo CD —
[`HELM.md`](../../infrastructure/theory/HELM.md) §7.2, теги образов и почему `:latest` в проде
запрещён — [`DOCKER.md`](../../infrastructure/theory/DOCKER.md) §4.4.

**Сквозной пример.** Платёжный сервис продуктовой компании: пять инженеров, Product Owner, QA,
разделяемый SRE. Спринт две недели, историческая пропускная способность около восьми задач. В
бэклоге на спринт двенадцать единиц работы, из них для этого файла важны четыре: интеграция нового
провайдера платежей, требование комплаенса с законодательным сроком, действие по итогам
сентябрьского инцидента и миграция схемы БД — в таблице `payments` сумма лежит в колонке `amount`,
её надо разделить на `amount_minor` и `currency`.

**Прогоны.** Все выводы `git` в этом файле сняты на macOS 15, `git version 2.50.1 (Apple Git-155)`.
Формулировки подсказок и имена автоматических коммитов зависят от версии git и от настроек
(`advice.*`, `merge.conflictStyle`, `core.editor`); хеши коммитов у вас будут другие. Рецепт
воспроизведения с нуля — в §5.

## 1. Три способа резать релиз: что именно вы фиксируете

**Задача.** Конец спринта. Из двенадцати взятых задач готовы семь: комплаенс, баг из поддержки,
техдолг и четыре мелких. Интеграция провайдера готова наполовину — код в основной ветке, но
включать нельзя. Миграция схемы не начата. Вопрос: что такое «релиз» в этот четверг и как его
получить.

**Наивное решение: релиз — это когда всё готово.** Ломается сразу же: «всё» не бывает готово
одновременно никогда. Ждать интеграцию провайдера — значит задержать комплаенс с законодательным
сроком. Второй вариант наивного решения — «катим то, что в основной ветке сейчас» — ломается на
том, что в основной ветке лежит наполовину готовая интеграция.

**Механизм.** Релиз — это **зафиксированное подмножество истории**, к которому вы умеете
возвращаться. Всё остальное — производные вопросы. Способов зафиксировать ровно три, и они
отличаются тем, **что именно фиксируется и на какой срок**.

*Способ 1 — срез релизной ветки.* От основной ветки в момент готовности отрезается ветка, которая
дальше живёт своей жизнью: в неё принимают только исправления, в основную продолжают вливать новое.

```
$ git switch -c release/1.4
Switched to a new branch 'release/1.4'
$ git tag -a v1.4.0 -m "релиз 1.4.0"
$ git describe --tags
v1.4.0
```

Основная ветка тем временем уходит вперёд:

```
$ git switch main
$ git commit -am "provider: второй провайдер платежей"
$ git describe --tags
v1.4.0-1-gb1a0492
```

Формат вывода `git describe` — `<ближайший тег>-<сколько коммитов после него>-g<сокращённый хеш>`.
Это и есть **машинный способ получить версию артефакта из истории**: на теге вывод равен ровно
`v1.4.0`, на любом коммите после — тег плюс расстояние. Отсюда правило сборки: если
`git describe --tags` вернул чистый тег — это релизная сборка, если с суффиксом — это сборка «между
релизами», и её нельзя публиковать под номером релиза.

*Способ 2 — тег на основной ветке.* Ветку не режут вовсе: релиз — это тег, поставленный на коммит
основной ветки. Тег в git — не метка на ветке, а самостоятельный объект:

```
$ git tag v0.9.0                       # lightweight
$ git tag -a v1.0.0 -m "релиз 1.0.0"   # annotated
$ git cat-file -t v0.9.0
commit
$ git cat-file -t v1.0.0
tag
```

Lightweight-тег — просто ещё одно имя для коммита; annotated-тег — отдельный объект с автором,
датой и сообщением. Разница не косметическая: `git describe` по умолчанию видит **только**
annotated-теги.

```
$ git describe
fatal: No annotated tags can describe '99aaf4a878331b7ad3917ed2ccebc8b940067ae8'.
However, there were unannotated tags: try --tags.
```

**Правило: релизные теги ставят только через `git tag -a`.** Иначе в один прекрасный день CI не
сможет назвать версию, а вы не узнаете, кто и когда поставил тег.

*Способ 3 — непрерывное развёртывание.* Релизом становится каждый коммит основной ветки, прошедший
CI-гейт: слияние — сборка — автоматическое развёртывание в прод. Ветки нет, а тег ставится
автоматически на то, что уехало.

**Что каждый способ оптимизирует и чем платит.**

| | Релизная ветка | Тег на основной | Непрерывное развёртывание |
|---|---|---|---|
| Что фиксируется | подмножество истории + место, куда принимают исправления | точка истории | ничего: релиз = состояние ветки |
| Что оптимизирует | возможность стабилизировать релиз, не блокируя разработку | простоту истории | время от коммита до пользователя |
| Чем платит | двумя живыми линиями кода: любое исправление надо перенести дважды | нельзя «доработать релиз», не забрав всё, что влилось после | требует, чтобы основная ветка была всегда готова к проду |
| Что обязано быть | дисциплина переноса (§5) | trunk-based development | автотесты, feature flags, наблюдаемость, быстрый откат |
| Хотфикс | из релизной ветки, обратно cherry-pick | новая ветка от тега или накат исправления | накат исправления следующим коммитом |

**Критерий выбора — один вопрос: «сколько времени проходит между тем, что уже в основной ветке, и
тем, что видит пользователь?»**

```
Сколько живёт релиз в проде до следующего?
├── недели и больше (мобильное приложение, коробка, регламентированный контур)
│   └── релизная ветка: нужен адрес, куда класть исправления к уже уехавшей версии
├── дни (наш платёжный сервис: релиз в конце двухнедельного спринта)
│   ├── основная ветка всегда зелёная и незаконченное скрыто флагами → тег на основной
│   └── иначе → релизная ветка, срезанная за 1–2 дня до релиза («окно стабилизации»)
└── часы и меньше
    └── непрерывное развёртывание; релизной ветки нет, откат — это следующий коммит
```

В сквозном примере ответ — тег на основной ветке. Релиз живёт две недели, но исправлять уехавшее
приходится редко и быстро, а поддерживать две линии кода впятером — дорого. Незаконченная интеграция
провайдера не мешает: она скрыта флагом (§4). Релизную ветку режут только тогда, когда исправление
к уехавшей версии нельзя отдать вместе со всем, что успело влиться в основную.

**Чего этот выбор не делает.** Он не отвечает, **когда** релиз происходит (§3), **на скольких
пользователей** (§8) и **включена ли функциональность** (§4). Три способа резать релиз отвечают
ровно на один вопрос — как назвать и как найти то, что уехало.

## 2. Semver: три цифры, у каждой свой адресат

**Задача.** Релиз готов, надо назвать его номером. В прошлый раз назвали `1.3.7`, потому что
предыдущий был `1.3.6`. Возник спор: интеграция нового провайдера меняет ответ `/charge` — там
появилось поле `provider`. Это `1.4.0` или `2.0.0`?

**Наивное решение: увеличивать последнюю цифру, пока не надоест.** Ломается в тот день, когда
номером версии начинает пользоваться кто-то, кроме вас: клиентская библиотека с диапазоном
`^1.3.0`, зеркальный сервис, который проверяет версию контрагента, или отдел, у которого написано
«мажорные обновления — через комитет по изменениям».

**Механизм.** Semantic Versioning 2.0.0 — спецификация с пронумерованными пунктами
([semver.org](https://semver.org/)), формулировки в терминах RFC 2119 (`MUST`, `SHOULD`, `MAY`).
Ключевое здесь — пункт 1: *Software using Semantic Versioning MUST declare a public API.* Номер
версии — это утверждение **о совместимости объявленного публичного API**, и без объявленного API
он не значит ничего.

Дальше три пункта задают всю арифметику:

| Пункт | Цифра | Когда увеличивают | Кому адресовано |
|---|---|---|---|
| 6 | PATCH (`x.y.Z`) | *only backward compatible bug fixes*; исправление — «внутреннее изменение, которое чинит неверное поведение» | обновляйся не глядя |
| 7 | MINOR (`x.Y.z`) | добавлена обратно совместимая функциональность; **обязательно** и тогда, когда что-то в публичном API помечено устаревшим; MINOR *MAY* увеличиться и от крупных внутренних изменений | обновляйся, ничего не сломается, но появилось новое |
| 8 | MAJOR (`X.y.z`) | введено любое обратно несовместимое изменение публичного API | читай список изменений, планируй работу |

При увеличении MINOR патч сбрасывается в ноль, при увеличении MAJOR — сбрасываются и MINOR, и PATCH
(пункты 7 и 8). Пункт 3 добавляет то, о чём забывают: *Once a versioned package has been released,
the contents of that version MUST NOT be modified.* Тег `v1.4.0`, переставленный на другой коммит, —
не «поправили релиз», а нарушение спецификации: у двух разных артефактов один номер.

**Что считается ломающим изменением.** Спецификация формулирует критерий, а не список: ломает то,
что заставляет **существующего** клиента поменять код. Отсюда практическая проверка — «сломается ли
клиент, который сегодня работает, если не тронуть его код»:

| Изменение в `/charge` | Цифра | Почему |
|---|---|---|
| Добавили в ответ поле `provider` | MINOR | старый клиент читает свои поля и не замечает нового |
| Сделали параметр `currency` обязательным | MAJOR | запрос, который работал вчера, сегодня отвергается |
| Сузили `amount` с 64 бит до 32 | MAJOR | часть входа, которая принималась, перестала приниматься |
| Переименовали `card_token` в `token` | MAJOR | это удаление поля плюс добавление, и удаление ломает |
| Починили округление комиссии | PATCH или MAJOR | если клиент строил расчёты на старом поведении — MAJOR, см. ниже |
| Пометили `POST /v1/charge` устаревшим | MINOR | пункт 7 предписывает MINOR именно на пометку |
| Обновили внутреннюю библиотеку, API не тронут | PATCH или MINOR | по FAQ: зависит от того, чинили баг или добавляли функциональность |

Последняя строка первой таблицы — не выдумка: FAQ спецификации прямо разбирает случай, когда
исправление формально «патч», а по воздействию на клиентов — ломающее, и советует руководствоваться
воздействием на пользователей, потому что смысл semver — сообщать смысл изменением номера.

**Отдельно про `v`.** FAQ отвечает недвусмысленно: `v1.2.3` — **не** семантическая версия; это
принятое обозначение номера версии, и в примере FAQ приведён ровно наш случай —
`git tag v1.2.3 -m "Release version 1.2.3"`, где `v1.2.3` — имя тега, а семантическая версия — это
`1.2.3`. Практический вывод: тег в git пишут с `v`, а в номере артефакта, в `pom.xml` и в заголовке
ответа `v` быть не должно.

**Когда правило нарушают осознанно — три случая.**

1. **`0.y.z`.** Пункт 4 отдаёт всю ветку `0.y.z` под начальную разработку: *Anything MAY change at
   any time. The public API SHOULD NOT be considered stable.* То есть `0.x` — не «недоделанный
   semver», а предусмотренный спецификацией режим, где обещаний нет вообще. FAQ добавляет критерий
   выхода: если софт используется в проде — он, вероятно, уже должен быть `1.0.0`. Ловушка обратная:
   команды годами сидят на `0.x`, чтобы не брать на себя обязательство совместимости, — но клиенты
   к этому моменту уже зависят от поведения, и отсутствие мажорной цифры их не защищает, а лишает
   сигнала.
2. **Внутренний сервис, у которого нет внешних клиентов.** Наш платёжный сервис вызывается тремя
   сервисами той же компании, обновляются они синхронно, версию никто не парсит. Semver здесь
   выполняет ровно ноль работы: у номера нет адресата. Тратить на него споры («это MINOR или
   MAJOR?») — чистые накладные расходы. Осмысленная замена — календарное версионирование
   (CalVer): `2026.03.17`, `2026.03.17-2`. Номер отвечает на вопрос, который в этом контексте
   реально задают, — «это когда собрано». Обратная сторона: из номера больше нельзя узнать, ломает
   ли обновление совместимость, — а значит, для публичного API CalVer не годится.
3. **Мажорная цифра как маркетинг.** Переход `1.x → 2.0` без единого ломающего изменения нарушает
   пункт 8. Это осознанное нарушение: цифру берут для анонса. Цена — номер перестаёт быть машинным
   сигналом, и клиенты начинают читать список изменений вместо диапазона версий. Если так делают —
   про это должно быть написано в документации, иначе автоматическое обновление у клиентов встанет
   на пустом месте.

**Правило.** Прежде чем спорить о цифре, ответьте на пункт 1: **что здесь публичный API и кто по
номеру принимает решение**. Есть внешний клиент, читающий номер, — semver обязателен и спор о
цифре содержателен. Клиента нет — semver не нужен, номер должен отвечать на вопрос «что за сборка»,
а не «совместима ли».

## 3. Release train: расписание вместо переговоров о сроках

**Задача.** До релиза два дня. Интеграция провайдера «почти готова, нужен ещё день». Комплаенс
готов, но у него законодательный срок в конце месяца. Product Owner просит подождать интеграцию:
«следующий релиз только через две недели, клиент ждёт».

**Наивное решение: подождать день.** Ломается по механике, а не по морали. Ждать день —
значит: релиз уезжает в пятницу вместо среды; QA-прогон сдвигается на день, когда QA занят;
готовый комплаенс лежит непроверенным ещё сутки; и главное — прецедент. Со следующего релиза «ещё
один день» просят все, потому что это сработало. Через три спринта дата релиза перестаёт что-либо
значить, и каждый релиз становится переговорами.

**Механизм.** Release train переворачивает вопрос. Дата релиза фиксирована и не обсуждается —
обсуждается только состав. Не готово к отправлению — едет следующим поездом; готово раньше — ждёт
на платформе. Три следствия, ради которых это делают:

1. **Стоимость опоздания становится известной и маленькой.** «Не успел» перестаёт означать
   «неизвестно когда» и начинает означать ровно один интервал. При двухнедельном поезде опоздание
   стоит две недели — это можно посчитать и сравнить с ценой спешки
   ([`PRIORITIZATION.md`](PRIORITIZATION.md), cost of delay).
2. **Давление переносится с даты на объём.** Единственная переменная, которой можно управлять,
   — состав поезда. Разговор «успеем ли к четвергу» превращается в «что режем, чтобы уехать в
   четверг», а это разговор с ответом.
3. **Уменьшается размер партии.** Чем чаще ходит поезд, тем меньше изменений в каждом релизе, тем
   короче список подозреваемых при разборе поломки. Обратная зависимость тоже работает: релиз раз в
   квартал делает каждый релиз событием, к которому копят изменения, — и его страшно катить именно
   потому, что он большой.

**Что release train делает с давлением на команду — и чего не делает.** Он снимает давление на
дату и **усиливает** давление на объём: не успеваешь — режь. Это честнее, но не бесплатно. Два
известных способа сломать поезд:

- **Поезд, который ждёт.** Одно исключение («ну этот раз подождём комплаенс») — и механизма больше
  нет: следующий, кто попросит, сошлётся на прецедент. Расписание работает ровно до первого
  исключения.
- **Поезд, в который грузят недоделанное.** Раз дата не двигается, появляется соблазн уехать с
  наполовину готовой функциональностью и «дожать в проде». Это не ускорение, а перенос риска на
  дежурного. Ровно от этого нужны feature flags (§4): уехать можно с чем угодно, **включать**
  можно только готовое.

**Правило.** Release train — обмен: команда отдаёт возможность сдвинуть дату и получает право
резать объём. Если отдали, но не получили — это не release train, а фиксированный срок с
фиксированным объёмом, то есть срезанное качество. В сквозном примере комплаенс со сроком в конце
месяца попадает в поезд за две недели до срока — тогда опоздание на один поезд ещё не является
нарушением закона. Это и есть содержательное планирование по расписанию: **срок клиента должен
отстоять от даты поезда минимум на один интервал.**

## 4. Deploy ≠ release: код в проде и функциональность у пользователя — два события

Это главное различие файла. Всё остальное — следствия.

**Задача.** Интеграция нового провайдера готова на 70 %. До релиза два дня, дописать не успеваем.
Комплаенс со сроком уехать обязан.

**Наивное решение: держать интеграцию в отдельной ветке, пока не доделаем.** Ломается тем, что
описано в [`BRANCHING_AND_CODE_FLOW.md`](BRANCHING_AND_CODE_FLOW.md): ветка живёт спринт, основная
ветка уходит вперёд, слияние становится отдельной задачей с собственными багами. И тем, что
интеграция всё это время не проверена ни на одном настоящем запросе.

**Механизм.** Развёртывание (выкатка кода в прод) и релиз (включение функциональности для
пользователя) — два разных события, и разводит их условный переход в коде, состояние которого
задаётся снаружи: флаг функциональности (feature flag). Код интеграции уезжает в прод в выключенном
состоянии, живёт там как неисполняемая ветка, и включается отдельным действием — когда готов, когда
разрешил Product Owner, когда прошла маркетинговая рассылка.

Отсюда — три вещи, которые получаются только так:

- **Незаконченное можно интегрировать.** Основа trunk-based development: ветка живёт часы, потому
  что незаконченность прячется не в ветке, а во флаге.
- **Включение отделяется от развёртывания во времени.** Выкатили в среду, включили в понедельник
  утром, когда дежурный на месте, а не в пятницу вечером.
- **Выключение не требует развёртывания.** Сломалось — сняли флаг за секунды, вместо отката за
  минуты (§6).

**Типы флагов — по первоисточнику.** Классификацию дал Pete Hodgson в статье *Feature Toggles (aka
Feature Flags)* на martinfowler.com. Её постоянно пересказывают неверно, поэтому важны две оси, по
которым он их разводит: **сколько флаг живёт** и **насколько динамично принимается решение**.

| Тип (по Hodgson) | Срок жизни | Динамичность решения | Зачем |
|---|---|---|---|
| Release Toggle | «обычно не дольше недели-двух» | **очень статичное**: решение одинаково для всей версии | довезти незаконченный код до прода |
| Experiment Toggle | часы или недели — пока не наберётся значимость | очень динамичное: решение на каждый запрос, по когорте пользователя | A/B-тест |
| Ops Toggle | обычно короткий; **небольшое число живёт почти бессрочно** | должно меняться очень быстро — иначе бесполезен | отключить или деградировать функциональность под нагрузкой |
| Permissioning Toggle | **годы, и это нормально** | всегда на запрос: решение зависит от пользователя | премиум-функциональность, альфа/бета-доступ |

Три вещи, которые чаще всего перевирают в пересказах:

1. **Release Toggle — статичный, а не динамичный.** Hodgson пишет прямо: решение для данной версии
   одно и то же, и выкатить новую версию с изменённой конфигурацией флага обычно вполне приемлемо.
   Из этого следует практический вывод, который выглядит контринтуитивно: **для релизных флагов
   конфигурацию в системе управления версиями предпочитают динамическому сервису флагов.** Аргумент
   Hodgson: конфигурация едет по тому же конвейеру, что и код, состояние флага в прошлых релизах
   видно в истории, и — главное — резко падает нагрузка на тестирование, потому что состояние
   «зашито» в релиз и не поменяется под ногами.
2. **Не всякий долгоживущий флаг — долг.** Permissioning Toggle живёт годами **по своей природе**:
   премиум-функциональность не «дораскатывается» никогда. Долг — это **Release Toggle, переживший
   свой релиз**: он обещал жить неделю, а живёт год.
3. **Аварийный выключатель (kill switch) — это долгоживущий Ops Toggle**, а не отдельная сущность.
   Hodgson описывает его как размыкатель цепи (circuit breaker) с ручным управлением. Как паттерн
   надёжности — в [`RELIABILITY_PATTERNS.md` в модуле system-design](../../system-design/theory/RELIABILITY_PATTERNS.md);
   здесь важно процессное следствие: действие по итогам сентябрьского инцидента «добавить выключатель
   на вызов провайдера» — это не временный флаг, у него нет даты удаления, и он обязан иметь
   владельца, тест и упоминание в инструкции дежурного. Флаг, который никто не проверял полгода, в
   момент инцидента не работает.

**Чем платят за флаги.** Hodgson называет флаги инвентарём с расходами на хранение, и расходы
конкретны:

- **Комбинаторика при тестировании.** Артефакт с флагом надо проверять в обоих состояниях: на
  момент прохождения конвейера неизвестно, каким он будет в проде. С несколькими флагами число
  комбинаций растёт экспоненциально. Смягчение по Hodgson: проверять текущую конфигурацию прода
  плюс те флаги, которые собираетесь включить, и отдельно — запасной вариант с ними же выключенными.
  Работает это только при соглашении **«выключено — старое поведение, включено — новое»**.
- **Разветвление кода.** Каждый флаг — условный переход, и они расползаются по кодовой базе.
- **Мёртвый код за выключенным флагом.** Самая дорогая статья, и её цена измерена.

**Что бывает, когда флаг переиспользуют — измеренный случай.** 1 августа 2012 года Knight Capital
за 45 минут потеряла более 460 миллионов долларов. Механика по материалам SEC (административное
производство, Release No. 34-70694 от 16 октября 2013 г., пп. 13–16): функциональность Power Peg не
использовалась много лет, но код **оставался на месте и вызываемым**; новый код повторно
использовал флаг, которым раньше включался Power Peg; при поэтапной выкатке с 27 июля инженер не
скопировал новый код на один из восьми серверов, а процедуры второй проверки развёртывания у
компании не было. 1 августа семь серверов обработали заказы правильно, а заказы с переиспользованным
флагом, попавшие на восьмой, включили старый Power Peg.

Отсюда три правила, каждое из которых прямо следует из механики:

1. **Имя флага не переиспользуют никогда.** Смысл флага — не в его имени, а в коде, который на него
   смотрит; старый код, оставшийся в артефакте, смотрит на то же имя.
2. **Удаление флага — это удаление старой ветки кода**, а не «поставить `true` по умолчанию».
   Пока мёртвая ветка вызываема, флаг остаётся заряженным.
3. **Частичная выкатка обязана быть проверяемой.** «На скольких инстансах какая версия» должно быть
   видно, а не выясняться в момент отказа. Технически это заслуга механизма развёртывания
   ([`KUBERNETES.md`](../../infrastructure/theory/KUBERNETES.md)), процессно — обязанность того, кто
   катит.

**Правило.** Флаг заводят вместе с датой и способом его смерти. Практики, которые для этого
работают: задача на удаление в бэклоге в момент создания флага; срок годности в самом флаге; тест,
падающий после этого срока; лимит на общее число флагов в системе — хочешь новый, удали старый.
Флаг без даты удаления — либо Permissioning/Ops по природе (и тогда у него есть владелец и тест),
либо технический долг ([`TECH_DEBT.md`](TECH_DEBT.md)).

## 5. Хотфикс: срез от тега и дорога обратно

**Задача.** Уехал `v1.4.0`. Через три дня поддержка приносит: комиссия считается неверно на нулевой
сумме. За эти три дня в основную ветку влилась половина интеграции провайдера — она не готова.
Исправление нужно в проде сегодня.

**Наивное решение: починить в основной ветке и выкатить её.** Ломается на том, что вместе с
однострочным исправлением в прод уедет всё, что влилось за три дня, включая незаконченную
интеграцию. Вы меняете известную проблему на неизвестную.

**Механизм.** Исправление делают там, где стоит релиз: ветка от тега `v1.4.0` (или релизная ветка,
если она есть), исправление, новый тег `v1.4.1`, выкатка. Потом — и это та часть, которую забывают,
— исправление переносят в основную ветку, иначе следующий релиз вернёт баг.

**Рецепт воспроизведения.** Всё ниже повторяется на пустом каталоге:

```bash
git init -b main payments && cd payments
# три коммита с любым содержимым, дальше:
git switch -c release/1.4
git tag -a v1.4.0 -m "релиз 1.4.0"
git switch main && git commit -am "provider: второй провайдер платежей"
```

Хотфикс и перенос:

```
$ git switch release/1.4
$ git commit -am "fix: комиссия на нулевой сумме"
$ git tag -a v1.4.1 -m "хотфикс 1.4.1"
$ git describe --tags
v1.4.1
$ git switch main
$ git cherry-pick f3f6965
[main 790ae9c] fix: комиссия на нулевой сумме
 Date: Mon Mar 9 14:00:00 2026 +0300
 1 file changed, 2 insertions(+)
```

Обратите внимание на хеши: `f3f6965` в релизной ветке и `790ae9c` в основной. **Перенос отдельного
коммита (cherry-pick) не переносит коммит — он создаёт новый коммит с тем же изменением.** Отсюда
все дальнейшие сложности.

**Случай, ради которого этот раздел написан: cherry-pick конфликтует.** Второй хотфикс — списание
не должно приниматься на неположительную сумму. Правится `provider.py` — тот самый файл, который в
основной ветке уже переписан под второго провайдера:

```
$ git cherry-pick 6ecb264
Auto-merging provider.py
CONFLICT (content): Merge conflict in provider.py
error: could not apply 6ecb264... fix: отклонять списание на неположительную сумму
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git cherry-pick --continue".
hint: You can instead skip this commit with "git cherry-pick --skip".
hint: To abort and get back to the state before "git cherry-pick",
hint: run "git cherry-pick --abort".
```

```
$ git status --short
UU provider.py
$ cat provider.py
<<<<<<< HEAD
PROVIDERS = {"acme": 1, "globex": 2}

def charge(card, amount_cents, provider="acme"):
    return {"card": card, "amount": amount_cents, "provider": provider, "ok": True}
=======
def charge(card, amount_cents):
    if amount_cents <= 0:
        raise ValueError("amount must be positive")
    return {"card": card, "amount": amount_cents, "ok": True}
>>>>>>> 6ecb264 (fix: отклонять списание на неположительную сумму)
```

Конфликт здесь — не техническая помеха, а **сообщение по существу**: исправление, написанное для
старой сигнатуры, к новой не применяется. Разрешить его — значит не «выбрать сторону», а заново
реализовать ту же проверку в новом коде и заново её проверить. Это отдельная работа, и её надо
планировать: разработчик, который взял хотфикс, не закончил, пока перенос не доехал.

**Как узнать, что доехало.** У git есть встроенный ответ — и у него есть ровно одна ловушка,
которую надо знать заранее. `git cherry` сравнивает две ветки по содержанию патчей: `-` означает
«такое изменение в основной ветке уже есть», `+` — «нет».

```
$ git cherry -v main release/1.4
- f3f69650ae62c7675b1d5264d2a77e846fab4d09 fix: комиссия на нулевой сумме
+ 6ecb2642b25856d8f3731b685ce5709bda1926a2 fix: отклонять списание на неположительную сумму
+ fb8e5e26df281347c96b7654ffcf96855efbfd68 fix: возврат на неположительную сумму
```

Здесь первый хотфикс перенесён чисто, второй — перенесён с разрешением конфликта, третий не
перенесён вообще. Но помечены `+` и второй, и третий: **cherry-pick с разрешением конфликта
неотличим от забытого**. Причина видна на уровне механизма — `git cherry` сравнивает не коммиты, а
`patch-id`, хеш нормализованного содержимого патча:

```
$ git show f3f6965 | git patch-id --stable   # хотфикс в релизной ветке
aacf003b134bd719275e69720254091d27d35b8b f3f69650ae62c7675b1d5264d2a77e846fab4d09
$ git show 790ae9c | git patch-id --stable   # он же после чистого переноса
aacf003b134bd719275e69720254091d27d35b8b 790ae9c9daaaf1877e97f515f9ad034703f848cd

$ git show 6ecb264 | git patch-id --stable   # хотфикс с конфликтом
a9c1d94d704807b02c3f20c943ea5cb07d55f28f 6ecb2642b25856d8f3731b685ce5709bda1926a2
$ git show 881151f | git patch-id --stable   # он же после разрешения
af683babbbd4081c826b6a06005463c5218b769f 881151f81303db292e15a71df33c6a4a38b96c20
```

Первая пара — один и тот же `patch-id`, вторая — разные. **Правило: `git cherry` даёт список
кандидатов, а не ответ.** Проверять надо не «есть ли коммит», а «есть ли в основной ветке тест,
который падал бы без этого исправления». Именно поэтому к хотфиксу пишут тест — не ради покрытия, а
как машиночитаемое доказательство переноса.

**Как выглядит история релизов.**

```
$ git log --oneline --graph --all --decorate
* fb8e5e2 (release/1.4) fix: возврат на неположительную сумму
* 6ecb264 (tag: v1.4.2) fix: отклонять списание на неположительную сумму
* f3f6965 (tag: v1.4.1) fix: комиссия на нулевой сумме
| * 881151f (HEAD -> main) fix: отклонять списание на неположительную сумму
| * 790ae9c fix: комиссия на нулевой сумме
| * b1a0492 provider: второй провайдер платежей
|/
* 39db5e0 (tag: v1.4.0) provider: списание
* bd981cf refund: заявка на возврат
* ad703e1 payments: комиссия провайдера
```

Читается это так: линии разошлись на `v1.4.0`; в релизной ветке три исправления, в основной — те же
исправления **другими коммитами** плюс новая функциональность. Двойные записи одинаковых сообщений в
двух линиях — нормальная стоимость релизной ветки; отсутствие такой пары — симптом потерянного
хотфикса.

**Правило.** Хотфикс не закончен, когда он в проде. Он закончен, когда: (1) уехал под своим тегом,
(2) перенесён в основную ветку, (3) в основной ветке есть падавший бы без него тест. Пункт (3) —
единственный, который проверяется механически.

## 6. Откат или накат исправления: чем определяется выбор

**Задача.** 20:40, релиз уехал час назад. Доля ошибок на `/charge` выросла с 0,2 % до 4 %. Причина
неизвестна. Что делать: откатывать или чинить?

**Наивное решение: «всегда откатывай, разберёмся утром».** Хороший инстинкт, у которого есть ровно
одно место, где он ломается, и в платёжном сервисе оно как раз встречается: **откат кода не
откатывает данные**. За час новая версия успела записать в базу строки, которых старая не понимает,
и провести списания, которых старая не видит. Обратный вариант наивного решения — «всегда чиним
накатом» — ломается ещё проще: он требует, чтобы вы знали причину, а в 20:40 вы её не знаете.

**Механизм: что откат возвращает и что нет.**

| Что | Возвращается откатом кода? |
|---|---|
| Байты артефакта в проде | да |
| Схема БД, если миграция применена | **нет** — она осталась применённой (§7) |
| Строки, записанные новой версией | **нет** — они в базе, и старый код читает их по-старому |
| Сообщения, отправленные в очередь | **нет** — потребители их уже разобрали |
| Списание, ушедшее в банк-эквайер | **нет** — деньги списаны, отмена — отдельная операция |
| Кэш, заполненный новой версией в новом формате | нет, пока не истечёт TTL или не сбросят вручную |

Три нижние строки — причина, по которой платёжный сервис нельзя «просто откатить». Откат чинит
**поток новых запросов** и не чинит **последствия уже обработанных**. Это два разных действия, и в
инциденте нужны оба ([`INCIDENTS_AND_POSTMORTEM.md`](INCIDENTS_AND_POSTMORTEM.md)).

**Критерий выбора.** Он состоит из трёх вопросов, и порядок важен:

```
1. Есть ли выключатель, снимающий проблему без развёртывания (§4)?
   да  → снять флаг. Это и есть самый быстрый откат: секунды, ничего не разворачивается
   нет → вопрос 2

2. Есть ли необратимый след — применённая миграция, записанные новой версией данные,
   отправленные наружу события?
   нет → откат. Он быстрее, чем понимание причины, а понимание можно отложить до утра
   да  → откат вернёт код, но оставит систему в состоянии, которого не понимает
         ни одна из версий → вопрос 3

3. Знаете ли вы причину настолько, чтобы написать исправление за время меньшее,
   чем продлится ущерб?
   да  → накат исправления (roll-forward)
   нет → останавливаем ущерб чем угодно (выключить функциональность, включить
         режим только для чтения, отключить трафик на регион) и разбираемся
```

Ключевая мысль: **откат — это способ выиграть время, а не починка.** Он оптимален ровно тогда, когда
дешёв и обратим. Как только в игре появились данные, он перестаёт быть обратимым, и его цена
начинает конкурировать с ценой наката.

**Ловушка `git revert -m 1`.** Отдельно — потому что она стреляет через две недели после инцидента,
когда все уже забыли. Интеграция провайдера была влита в основную ветку слиянием (`--no-ff`), то
есть коммитом с двумя родителями. Откатить такой коммит без указания родителя git отказывается:

```
$ git revert f32b2d1
error: commit f32b2d14b53cda1a52e7d8c1cc5147e00cf2f0fa is a merge but no -m option was given.
fatal: revert failed
```

`-m 1` означает «считать первого родителя (основную ветку) правильной линией и убрать всё, что
пришло со второй»:

```
$ git revert -m 1 --no-edit f32b2d1
[main cdaf63e] Revert "merge: интеграция провайдера globex"
 Date: Fri Mar 6 10:00:00 2026 +0300
 1 file changed, 5 deletions(-)
 delete mode 100644 globex.py
```

Сработало: функциональности в проде больше нет. А теперь — цена. Через две недели ветку доработали
и слили заново.

*Случай A — ветку слили как есть:*

```
$ git merge --no-ff feature/globex
Already up to date.
```

Слияние не делает ничего. Для git ветка уже слита: коммит слияния в истории есть, и то, что его
содержимое потом отменили отдельным коммитом, для алгоритма слияния не значит ничего — он смотрит на
топологию, а не на содержимое. Функциональность не вернулась, и об этом никто не узнал: команда
ничего не забыла, просто git ответил «уже актуально».

*Случай B — в ветку добавили новый файл и слили:*

```
$ git merge --no-ff -m "merge: globex, вторая попытка" feature/globex
Merge made by the 'ort' strategy.
 globex_refund.py | 2 ++
 1 file changed, 2 insertions(+)
 create mode 100644 globex_refund.py
$ ls
globex_refund.py  provider.py
```

Слияние прошло **чисто и без предупреждений** — и принесло только новый файл. `globex.py`, то есть
собственно интеграция, в основную ветку не вернулся. Ни одного конфликта, ни одного сообщения. Это
хуже случая A: там ничего не поменялось и это заметно, здесь слияние выглядит успешным.

Причина у обоих случаев одна: **база слияния сместилась**. После первого слияния общий предок веток
— тот самый коммит слияния; git берёт разницу от него, а в ней содержимого `globex.py` уже нет.

Правильный способ вернуть — откатить откат:

```
$ git revert --no-edit cdaf63e
[main fb31fe7] Reapply "merge: интеграция провайдера globex"
 1 file changed, 5 insertions(+)
 create mode 100644 globex.py
```

(Имя `Reapply "..."` генерирует git начиная с версии 2.31; более старые версии пишут
`Revert "Revert "..."`.)

**Правило.** `git revert -m 1` на коммите слияния — законный инструмент, но у него есть неочевидное
последствие: **ветка считается слитой навсегда**. Поэтому: если функциональность планируют вернуть —
либо возвращают откатом отката, либо начинают с новой ветки от текущей основной. И общий вывод
уровнем выше: **откат в git и откат в проде — разные операции**. В проде откатывают артефакт
(предыдущий образ, предыдущий тег), и это занимает минуты; трогать историю в момент инцидента не
нужно вовсе — `git revert` делают потом, спокойно, когда решают, что функциональность не
возвращается.

## 7. Миграции схемы БД: почему код и схему нельзя выкатить одной кнопкой

Самая практичная часть файла. Здесь ломается больше релизов, чем на всём остальном вместе.

**Задача.** В таблице `payments` сумма лежит в колонке `amount`. Для второго провайдера нужна
валюта, и заодно надо явно обозначить, что сумма в минорных единицах: `amount` → `amount_minor`
плюс новая колонка `currency`.

**Наивное решение: одна задача, один релиз.** В миграции `ALTER TABLE payments RENAME COLUMN amount
TO amount_minor`, в коде — новое имя, выкатываем вместе. Ломается в трёх местах, и каждое —
отдельно:

1. **Во время самой выкатки.** Развёртывание не атомарно: пока обновляются реплики приложения, в
   проде одновременно работают старая и новая версии (§8). Миграция применяется один раз — и с этого
   момента все ещё не обновлённые инстансы выполняют `SELECT amount` по колонке, которой больше нет.
   Каждое их обращение — ошибка. Длится это столько, сколько идёт раскатка.
2. **При откате.** Что-то пошло не так, откатываем приложение на предыдущий образ. Схема осталась
   переименованной — теперь **вся** старая версия падает на каждом запросе. Откат не просто не помог:
   он превратил частичный отказ в полный.
3. **После отката.** Даже если бы схему удалось вернуть — данные, записанные новой версией в
   `amount_minor` за время работы, старой версии не видны. В платёжном сервисе это означает платежи
   с неизвестной суммой.

**Механизм: expand/contract.** Шаблон известен под двумя именами — expand and contract и parallel
change; описан Danilo Sato ([*ParallelChange*, martinfowler.com, 13.05.2014](https://martinfowler.com/bliki/ParallelChange.html))
как разбиение обратно несовместимого изменения интерфейса на три фазы: **expand → migrate →
contract**. К схеме БД он применяется буквально, потому что схема и есть интерфейс — между базой и
всеми версиями приложения, которые к ней ходят.

Идея одна: **между старым и новым состоянием вставляется период, в котором схема поддерживает оба.**
Fowler формулирует то же самое про сине-зелёное развёртывание одной фразой: сначала привести схему к
виду, поддерживающему и новую, и старую версию приложения, выкатить это, убедиться, что всё
работает, — и только тогда выкатывать новую версию приложения ([*BlueGreenDeployment*, 01.03.2010](https://martinfowler.com/bliki/BlueGreenDeployment.html)).

Наше переименование раскладывается на три релиза:

| Релиз | Схема | Код | Инвариант в конце шага |
|---|---|---|---|
| **R1 — expand** | `ADD COLUMN amount_minor`, `ADD COLUMN currency`; заполнить существующие строки | пишет в **обе** колонки, читает из `amount` | старая версия работает как раньше; новая колонка заполнена и синхронна |
| **R2 — migrate** | не меняется | читает из `amount_minor`, продолжает писать в обе | обе версии кода корректно работают на одной схеме |
| **R3 — contract** | `DROP COLUMN amount` | пишет и читает только `amount_minor` | старой колонки больше нет; откат возможен только до R2 |

Что здесь даёт каждый шаг:

- **Каждый релиз обратно совместим сам по себе.** На любом шаге можно откатить приложение на
  предыдущую версию, и оно продолжит работать на текущей схеме.
- **Двойная запись в R1–R2 — не избыточность, а страховка отката.** Именно она делает обратимым
  переход R2: если после R2 обнаружилось, что читать из новой колонки нельзя, откат к R1 находит
  `amount` актуальным, потому что в него всё это время писали.
- **R3 закрывает окно отката.** После удаления колонки вернуться к R1 нельзя. Поэтому R3 делают
  не «в том же спринте», а после того, как истёк срок, в течение которого вы реально готовы
  откатываться: у нас релиз раз в две недели — значит, R3 идёт минимум через один полный релизный
  цикл после R2, а не следующей строкой в том же скрипте миграций.

**Правило порядка — оно выводится, а не запоминается.** Схема и код никогда не выкатываются
атомарно, значит существует промежуток, в котором одно уже новое, а другое ещё старое. Порядок
выбирается так, чтобы этот промежуток был безопасным:

| Тип изменения | Порядок | Почему так |
|---|---|---|
| Добавление (колонка с `NULL`/значением по умолчанию, таблица, индекс) | **схема, потом код** | новая схема не мешает старому коду: он о ней не знает |
| Удаление или сужение (`DROP COLUMN`, `NOT NULL`, сужение типа, удаление таблицы) | **код, потом схема** | сначала код перестаёт пользоваться, и только потом объект исчезает |
| Переименование | оба сразу невозможны → **expand/contract** | переименование — это удаление плюс добавление, то есть оба случая одновременно |

Общий инвариант, из которого вытекает вся таблица: **схема версии N обязана быть совместима с кодом
версий N−1 и N+1**. N−1 — потому что на него откатываются, N+1 — потому что во время раскатки он
уже работает.

**Чего expand/contract не делает.**

- **Не делает миграцию быстрой.** Заполнение новой колонки на большой таблице — отдельная задача с
  собственной стоимостью (пакетами, с паузами, чтобы не положить репликацию;
  [`REPLICATION.md` в модуле databases](../../databases/theory/REPLICATION.md)). Шаблон говорит,
  **как разложить релизы**, а не как выполнить `UPDATE` на ста миллионах строк.
- **Не спасает от блокирующих операций DDL.** Какие именно `ALTER TABLE` берут тяжёлую блокировку
  и переписывают таблицу — свойство конкретной СУБД и её версии; проверять надо по документации
  своей версии, а не по памяти.
- **Не отменяет необходимости в переносе данных.** Между R1 и R2 существуют строки, записанные до
  R1: их заполняет отдельный процесс, и до его завершения переход к R2 делать нельзя.

**Что происходит при откате приложения после применённой миграции — по шагам.** Это тот самый
вопрос, который задают на собеседовании после «как вы катите в прод». Ответ зависит от того, на
каком шаге вы откатываетесь:

| Откат после… | Что со схемой | Что с данными | Приложение работает? |
|---|---|---|---|
| R1 (expand) | новые колонки остались | старая колонка актуальна | да, полностью |
| R2 (migrate) | без изменений | обе колонки актуальны из-за двойной записи | да, полностью |
| R3 (contract) | `amount` удалена | восстановлению из `amount_minor` подлежит, но это отдельная миграция | **нет**: старый код обращается к удалённой колонке |
| наивной миграции из «наивного решения» | `amount` переименована | часть данных только в новой колонке | **нет**: падает на каждом запросе |

Нижние две строки — ровно то, ради чего вся эта конструкция.

**Правило одной фразой.** Миграция и релиз кода — два независимых развёртывания с разными окнами
отката, и порядок между ними определяется тем, какое из двух состояний переживёт отсутствие
другого. Если для миграции нельзя назвать шаг, на который вы откатитесь, — она не готова к выкатке.

## 8. Механика раскатки: сколько пользователей увидит новое и когда мы это заметим

Механизмы развёртывания сами по себе принадлежат инфраструктуре:
[`KUBERNETES.md`](../../infrastructure/theory/KUBERNETES.md) — `Deployment`, `RollingUpdate` и
`rollout undo`; [`HELM.md`](../../infrastructure/theory/HELM.md) §7.2 — GitOps и Argo CD;
[`DOCKER.md`](../../infrastructure/theory/DOCKER.md) §4.4 — теги образов. Здесь только процессная
часть: раскатка — это способ **купить время на обнаружение**, и покупается оно по понятной цене.

**Задача.** Релиз ломает 100 % запросов, которые попадают на новую версию. Алерт срабатывает через
6 минут (пятиминутное окно по доле ошибок плюс минута на реакцию дежурного), раскатка при этом
останавливается. Сколько списаний испортится?

**Расчёт.** Параметры: 40 списаний в секунду в пике (это допущение, не измерение — подставьте свои);
обнаружение 6 минут; откат — переключение маршрутизатора за 30 секунд для сине-зелёного
развёртывания (blue-green) и канареечной раскатки (canary), 4 минуты для постепенной замены реплик
(rolling update, пять реплик, по одной каждые две минуты).

| Схема | Испорчено до обнаружения | Испорчено за время отката | Всего | Доля месячного бюджета ошибок при SLO 99,9 % |
|---|---|---|---|---|
| Сине-зелёное развёртывание | 14 400 | 600 | **15 000** | 14,5 % |
| Постепенная замена реплик | 5 760 | 2 880 | **8 640** | 8,3 % |
| Канареечная раскатка, 1 % | 144 | 6 | **150** | 0,14 % |

Месячный бюджет ошибок при SLO 99,9 % и 40 запросах в секунду — 103 680 запросов, то есть 43,2
минуты полного отказа (о бюджете ошибок как механизме —
[`OBSERVABILITY.md` в модуле infrastructure](../../infrastructure/theory/OBSERVABILITY.md)).
Числа получены арифметикой по описанным параметрам, а не замером; ценность — в отношении между
строками, а не в абсолютных значениях. Отношение при этом велико: **сине-зелёное развёртывание
стоит в сто раз дороже канареечной раскатки по испорченным запросам** — просто потому, что доля
трафика на плохой версии в момент обнаружения отличается в сто раз.

**Где эта таблица врёт — и это важнее самой таблицы.** Она предполагает, что обнаружение занимает 6
минут независимо от доли трафика. Для канареечной раскатки это неверно, и вот механизм. При 1 % от
40 запросов в секунду канарейка обслуживает 0,4 запроса в секунду:

| Доля трафика | Запросов в секунду | 1 000 запросов накопится за | 10 000 — за |
|---|---|---|---|
| 1 % | 0,4 | 42 минуты | 6,9 часа |
| 5 % | 2,0 | 8,3 минуты | 1,4 часа |
| 10 % | 4,0 | 4,2 минуты | 42 минуты |
| 25 % | 10,0 | 1,7 минуты | 17 минут |

Отсюда два следствия:

- **Грубый отказ канарейка ловит мгновенно** — если ломается 100 % запросов, хватает и десяти
  наблюдений.
- **Тонкий отказ она не ловит вообще.** Рост доли ошибок с 0,2 % до 2 % на 1 % трафика — это около
  двух лишних ошибок за пять минут при полусотне запросов. Отличить это от шума нельзя, и десяти
  минут наблюдения не хватит: чтобы набрать статистику, нужны часы. Канарейка на 1 % с окном в
  десять минут для тонких дефектов — ритуал, а не проверка.

И третье, менее очевидное: **при доле трафика 1 % плохая версия, ломающая все свои запросы, даёт
ровно 1 % глобальной доли ошибок** — то есть общий алерт, настроенный на 2 %, не сработает никогда.
Канареечная раскатка работает только там, где метрики разрезаны по версии. Без такого разреза она
не просто не помогает — она **прячет** отказ, размывая его в общем фоне.

**Критерий выбора — из двух чисел.**

```
Насколько дорога одна испорченная операция?
├── очень дорога и необратима (списание денег, отправка документа в госорган)
│   └── канареечная раскатка + метрики по версии;
│       время наблюдения — из объёма выборки, не из привычки
├── дорога, но обратима
│   └── постепенная замена реплик: компромисс по цене и по скорости
└── дёшева (внутренняя панель, отчёт)
    └── сине-зелёное развёртывание или простая замена: дешевле оперировать

Насколько быстро нужно уметь откатиться?
├── за секунды → сине-зелёное (переключение маршрутизатора) или feature flag
└── минуты приемлемы → постепенная замена
```

Обратите внимание: два вопроса дают **разные** ответы. Сине-зелёное развёртывание выигрывает по
скорости отката и проигрывает по цене окна обнаружения; канареечная — наоборот. Это и есть настоящий
размен, а не «канареечная лучше».

**Чего раскатка не делает.** Ни одна схема не уменьшает ущерб, если нет чем его заметить. Все три
строки таблицы отличаются только тем, какая доля трафика попадает на плохую версию **за время
обнаружения** — а само время обнаружения задаётся наблюдаемостью, а не схемой раскатки. Команда,
которая узнаёт о поломке от службы поддержки через сорок минут, получит одинаково плохой результат
при любой стратегии. **Сначала метрики, разрезанные по версии, потом канарейка.** Второе без
первого — театр.

И отдельно: сине-зелёное развёртывание не решает вопрос данных. Fowler в исходной заметке отмечает
это прямо: остаётся проблема транзакций, прошедших через новую среду, пока она была живой. Это тот
же §6 и §7 другими словами: переключение маршрутизатора обратимо, записанные строки — нет.

## 9. Когда это неправильный ответ

**Непрерывное развёртывание — когда его нет смысла предлагать.**

- **Развёртывание — не единственный барьер.** Медицинское устройство, авиационный софт, банковское
  ядро под регламентом: изменение требует внешней сертификации или согласования комитета по
  изменениям. Автоматизировать выкатку тут можно и нужно, а вот «каждое слияние едет в прод»
  невозможно не по технической причине.
- **Пользователь не может обновиться сам.** Мобильное приложение проходит проверку в магазине,
  коробочная поставка ставится клиентом раз в квартал. Развёртывание вы контролируете, релиз — нет;
  релизная ветка и хотфикс к уехавшей версии становятся неизбежными.
- **Нечем заметить поломку.** Непрерывное развёртывание переносит проверку из «перед выкаткой» в
  «после выкатки». Если после выкатки смотреть нечем, оно просто убирает проверку. Это не «низкий
  уровень зрелости» как ярлык — это конкретное условие, которое надо выполнить до, а не после.
- **Цена одной ошибки несопоставима с выигрышем от скорости.** Не наш случай: платёжный сервис в
  проде с телеметрией и флагами катят непрерывно многие. Но там, где выкатка запускает необратимую
  внешнюю операцию без возможности компенсации, размен другой.

**Когда feature flag хуже ветки.**

- **Изменение пронизывает всё.** Смена схемы аутентификации, переезд на другой формат
  сериализации, глобальный рефакторинг: флаг здесь означает две реализации в каждом слое и
  комбинаторику при тестировании. Ветка, живущая три дня под пристальным вниманием, дешевле
  «временного» флага в сорока местах.
- **Флаг нельзя выключить.** Если после включения система записала данные в новом формате, снятие
  флага не возвращает систему в прежнее состояние — оно возвращает **код**, который этих данных не
  понимает. Флаг, у которого выключение не обратимо, создаёт ложное чувство безопасности: кнопка
  есть, а нажимать её нельзя.
- **Флаг переживёт релиз.** Если вы уже знаете, что удалять его будет некому, вы заводите не флаг,
  а ветвление кода навсегда. Честнее либо довести функциональность, либо не начинать.
- **Флаг ставят вместо решения.** Два поведения, между которыми не могут выбрать, за флагом
  «пусть пока оба будут» — это не отложенное решение, а два поведения в проде, каждое из которых
  надо поддерживать.

**Когда откат опаснее наката.**

- **Применена необратимая миграция** — §7. Откат кода при удалённой колонке кладёт сервис
  полностью вместо частично.
- **Новая версия уже записала данные, которых старая не понимает.** Откат превращает «часть
  запросов ошибочна» в «часть данных нечитаема».
- **Причина известна, а исправление тривиально.** Однострочная правка через конвейер за восемь
  минут против отката, который вернёт и десять других изменений этого релиза, включая нужное
  комплаенсу.
- **Откатываться некуда.** Предыдущая версия несовместима с текущей схемой, или её образ уже
  удалён из хранилища. Это состояние выясняют заранее, а не в 20:40: «на какую версию мы можем
  откатиться прямо сейчас» — вопрос с проверяемым ответом, и его проверяют на учениях.

**И общий неправильный ответ.** «Мы катим канареечно с feature flags и GitOps» без ответа на «как
вы узнаёте, что стало хуже» — перечисление инструментов. Содержательный ответ начинается с того,
**что вы измеряете во время раскатки и на каком пороге останавливаетесь**.

## 10. Чего эти инструменты не делают

- **Semver не делает обновление безопасным.** Он сообщает намерение автора. Ломающее изменение,
  выпущенное как PATCH, останется ломающим; спецификация в FAQ предписывает в этом случае выпустить
  новую версию с восстановленной совместимостью и **не трогать** уже выпущенную (пункт 3).
- **Feature flag не делает код обратимым.** Он делает обратимым **исполнение**. Всё, что код успел
  записать наружу, флагом не отменяется.
- **Release train не делает команду быстрее.** Он делает срок **известным**. Пропускная способность
  задаётся ёмкостью, а не расписанием ([`FLOW_AND_WIP.md`](FLOW_AND_WIP.md) §1).
- **Канареечная раскатка не находит дефекты.** Она ограничивает долю трафика на подозреваемой
  версии. Находят дефекты метрики — и только если они разрезаны по версии (§8).
- **Откат не восстанавливает состояние.** Он восстанавливает код (§6).
- **Expand/contract не ускоряет миграцию.** Он делает каждый шаг обратимым, а суммарно —
  длиннее: три релиза вместо одного (§7).
- **`git revert` не делает ветку не слитой.** Топология остаётся, и повторное слияние либо не
  делает ничего, либо делает половину (§6).
- **CI-гейт не проверяет то, что за флагом.** Артефакт с выключенным флагом прошёл проверку в одном
  состоянии из двух (§4).

## 11. Формулировки, которые хорошо звучат

Для вопроса «как вы катите в прод»:

- «Развёртывание и релиз у нас разведены. Код едет в прод выключенным — за флагом, — и включается
  отдельным решением: когда готово, когда дежурный на месте, когда разрешил Product Owner. Поэтому
  выкатка не является событием, а включение можно назначить на удобное время».
- «Релиз по расписанию, раз в две недели, дата не двигается. Не успели — едем следующим поездом;
  переменная только одна — состав. Это делает опоздание измеримым: оно стоит ровно две недели, и
  эту цену можно сравнить с ценой спешки».
- «Схему и код мы никогда не выкатываем вместе. Сначала схема, которая поддерживает и старую, и
  новую версию, потом код. Удаление старого — отдельный релиз, после того как окно отката закрылось.
  Иначе откат приложения кладёт сервис вместо того, чтобы его спасти».
- «Раскатываем канареечно, но ценность здесь не в проценте трафика, а в том, что метрики разрезаны
  по версии. Канарейка на одном проценте без такого разреза не ловит отказ, а маскирует его».

Для вопроса «что делаете, если релиз сломал прод»:

- «Первый вопрос — есть ли выключатель, снимающий проблему без развёртывания: это секунды против
  минут. Если нет — второй вопрос: остался ли необратимый след, применённая миграция или записанные
  данные. Пока следа нет, откат дешевле, чем понимание причины, и я откатываюсь, не разобравшись».
- «Откат чинит поток новых запросов и не чинит последствия уже обработанных. В платёжном сервисе
  это два разных действия, и в инциденте нужны оба: остановить ущерб и потом разобраться со
  списаниями, которые уже ушли».
- «Накат исправления я выбираю, когда знаю причину и уверен, что напишу правку быстрее, чем длится
  ущерб. Во всех остальных случаях сначала останавливаю ущерб, а причину ищу потом».

## 12. Шпаргалка

**Три способа резать релиз**

| | Релизная ветка | Тег на основной | Непрерывное развёртывание |
|---|---|---|---|
| Когда уместно | релиз живёт недели; исправлять уехавшее надо отдельно от нового | релиз живёт дни; основная ветка всегда готова | релиз живёт часы |
| Цена | две линии кода, каждый хотфикс переносится | нельзя доработать релиз, не забрав всё, что влилось после | требует тестов, флагов, наблюдаемости, быстрого отката |
| Хотфикс | ветка → тег → cherry-pick в основную | ветка от тега | следующим коммитом |

**Semver 2.0.0 — что увеличиваем** (пункты спецификации 6/7/8; предпосылка — пункт 1: объявленный
публичный API)

| Изменение | Цифра |
|---|---|
| исправление обратно совместимо | PATCH |
| добавлена обратно совместимая функциональность **или** что-то помечено устаревшим | MINOR |
| существующий клиент обязан поменять код | MAJOR |
| режим «обещаний нет» | `0.y.z` (пункт 4) |
| у номера нет адресата (внутренний сервис) | CalVer вместо semver |

Тег в git — `v1.4.0`; семантическая версия — `1.4.0` (FAQ спецификации). Релизные теги — только
`git tag -a`: `git describe` без `--tags` видит только annotated. Выпущенную версию не переписывают
(пункт 3).

**Типы feature flags (Pete Hodgson)**

| Тип | Живёт | Решение | Долг, если… |
|---|---|---|---|
| Release | неделя-две | статичное, на версию | пережил свой релиз |
| Experiment | до статистической значимости | на запрос, по когорте | эксперимент кончился, флаг остался |
| Ops | коротко; аварийные выключатели — бессрочно | должно меняться мгновенно | нет владельца и теста |
| Permissioning | годы — это норма | на запрос, по пользователю | (не долг по своей природе) |

Соглашение, без которого не работает проверка комбинаций: **выключено — старое поведение, включено
— новое**. Имя флага не переиспользуют. Удалить флаг — значит удалить старую ветку кода.

**Хотфикс — команды и что они значат**

```bash
git switch -c hotfix/1.4.1 v1.4.0   # срез от тега
git tag -a v1.4.1 -m "хотфикс"      # только annotated
git cherry-pick <sha>               # НОВЫЙ коммит с тем же изменением
git cherry -v main release/1.4      # '+' = в основной ветке эквивалента нет
git describe --tags                 # v1.4.0-3-gabc1234 = тег + расстояние + хеш
```

`git cherry` сравнивает `patch-id`: перенос с разрешением конфликта выглядит так же, как забытый.
Доказательство переноса — тест, а не список коммитов.

**Откат или накат**

```
выключатель есть?      → снять флаг (секунды)
необратимого следа нет? → откат (минуты; причину ищем потом)
причина известна?      → накат исправления
иначе                  → остановить ущерб, потом разбираться
```

`git revert -m 1 <merge>` убирает содержимое ветки, но ветка остаётся слитой: повторное слияние даёт
`Already up to date.` либо приносит только новые коммиты, молча оставляя старые отменёнными.
Возврат — откатом отката (`Reapply "..."`).

**Порядок «схема — код»**

| Изменение | Порядок |
|---|---|
| добавление (колонка, таблица, индекс) | схема → код |
| удаление, сужение, `NOT NULL` | код → схема |
| переименование | expand → migrate → contract, три релиза |

Инвариант: **схема версии N совместима с кодом N−1 (откат) и N+1 (раскатка)**. Двойная запись
существует ради обратимости, а не ради надёжности. `contract` делают после того, как окно отката
закрылось.

**Цена окна обнаружения** (40 запросов в секунду, обнаружение 6 минут, отказ 100 %; арифметика по
допущениям, не замер)

| Схема | Испорчено всего | Доля бюджета ошибок при SLO 99,9 % |
|---|---|---|
| Сине-зелёное развёртывание | 15 000 | 14,5 % |
| Постепенная замена реплик | 8 640 | 8,3 % |
| Канареечная раскатка 1 % | 150 | 0,14 % |

Канарейка на 1 % при 40 запросах в секунду набирает 1 000 наблюдений за 42 минуты: грубый отказ
ловится сразу, тонкий не ловится вовсе. При доле трафика 1 % полностью сломанная версия даёт 1 %
глобальной доли ошибок — общий алерт не сработает. **Метрики по версии — предпосылка канареечной
раскатки, а не дополнение к ней.**

## Вопросы для самопроверки

1. `git describe --tags` вернул `v1.4.0-3-gabc1234`. Что именно означает каждая из трёх частей и
   почему сборка с таким выводом не должна публиковаться под номером релиза?
2. Почему релизные теги ставят через `git tag -a`, а не просто `git tag`? Ответ должен объяснять
   поведение `git describe`, а не апеллировать к аккуратности.
3. В ответ `/charge` добавили необязательное поле. В другом релизе сделали обязательным существующий
   параметр. Какие цифры semver меняются в каждом случае и какой один вопрос отличает эти случаи
   друг от друга?
4. Команда третий год выпускает `0.14.x`, потому что «API ещё не устоялся». Что говорит об этом
   спецификация и почему клиентам от такой позиции не легче, а тяжелее?
5. Release train снимает давление на дату. На что он это давление переносит и почему одно
   исключение («в этот раз подождём») ломает механизм целиком?
6. Hodgson называет Release Toggle статичным флагом и рекомендует для него конфигурацию в системе
   управления версиями, а не динамический сервис флагов. Приведите его аргумент и объясните, почему
   для Ops Toggle рекомендация противоположная.
7. У Knight Capital новый код переиспользовал флаг старой функциональности, а старый код остался в
   артефакте. Какие два независимых условия должны были совпасть, чтобы это выстрелило, и какое из
   них устраняется процессом релиза, а какое — работой с кодом?
8. Хотфикс перенесли в основную ветку через cherry-pick с разрешением конфликта. `git cherry`
   продолжает помечать его `+`. Объясните это через `patch-id` и скажите, что тогда служит
   доказательством переноса.
9. Cherry-pick хотфикса дал конфликт. Почему это следует считать содержательным сообщением, а не
   технической помехой, и что меняется в оценке трудоёмкости задачи?
10. `git revert -m 1` на коммите слияния отменил функциональность. Через две недели ветку слили
    заново, слияние прошло чисто, а функциональность не вернулась. Что произошло с базой слияния и
    почему случай «слияние прошло чисто» опаснее случая `Already up to date.`?
11. Миграция `RENAME COLUMN` выкачена вместе с кодом. Перечислите три момента, в которые это
    ломается, — во время раскатки, при откате и после отката — и объясните, почему откат делает
    ситуацию хуже, а не лучше.
12. Из какого рассуждения выводится правило «добавление — схема первой, удаление — код первым»?
    Ответ должен опираться на то, какие версии кода одновременно живут в проде.
13. Канареечная раскатка на 1 % трафика: сломанная версия ломает все свои запросы. Какой будет
    глобальная доля ошибок и почему из этого следует, что канарейка без метрик по версии не просто
    бесполезна, а вредна?
14. Сине-зелёное развёртывание выигрывает по скорости отката и проигрывает по цене окна
    обнаружения. Объясните, откуда берутся оба свойства, и назовите ситуацию, в которой правильный
    выбор — именно оно.
