# Go — Планировщик (GMP)

> Горутины — это потоки **пользовательского уровня**: их создаёт, останавливает и
> возобновляет не ядро ОС, а планировщик внутри рантайма Go. Тысячи и миллионы горутин
> мультиплексируются на небольшое число потоков ОС по схеме **M:N**. Понимание модели
> **GMP** объясняет, почему `go f()` стоит копейки, почему блокирующий вызов не «съедает»
> весь параллелизм и откуда берутся редкие, но реальные паузы.

Аудитория — разработчик из Java/Kotlin, видящий Go впервые. Где параллель с JVM помогает —
она проведена явно. Ключевой ориентир: **горутина в Go — это примерно то же, что виртуальный
поток (virtual thread) в Java 21**, а планировщик GMP играет роль связки carrier-потоков и
ForkJoinPool из мира JVM. Каноническая теория про M:N и виртуальные потоки — в
[../../concurrency/theory/VIRTUAL_THREADS.md](../../concurrency/theory/VIRTUAL_THREADS.md);
здесь разбирается конкретная реализация в Go, а не переопределяется общая модель.

## 1. Зачем Go свой планировщик

Поток ОС (OS thread) — дорогой ресурс. У него фиксированный (обычно ~1–8 МБ) стек, его
создание и уничтожение — это системный вызов, а переключение между потоками идёт через
ядро (сохранение/восстановление регистров, смена адресного пространства планировщиком ОС,
сброс части кешей CPU). Если бы каждая «логическая задача» в Go была потоком ОС, сервер на
сто тысяч одновременных соединений упёрся бы в память и в стоимость переключений задолго до
исчерпания CPU.

Решение — **двухуровневая модель**. Рантайм Go держит небольшой пул потоков ОС (по числу
ядер) и раскладывает по ним множество лёгких горутин **сам, в пользовательском пространстве**,
без участия ядра на каждое переключение.

| Свойство | Поток ОС | Горутина |
|---|---|---|
| Кто создаёт/планирует | ядро ОС | рантайм Go (user-space) |
| Начальный стек | ~1–8 МБ, фиксированный | ~2 КБ, растёт по необходимости |
| Стоимость создания | системный вызов | аллокация в куче, десятки нс |
| Стоимость переключения | вход в ядро, ~1–2 мкс | смена нескольких регистров, ~десятки нс |
| Сколько реально держать | тысячи | миллионы |

Прямая аналогия из JVM: **платформенный поток (platform thread) ≈ поток ОС**, а
**горутина ≈ виртуальный поток (virtual thread)**. Java до 21 не имела встроенного M:N и
отображала потоки 1:1 на ОС; Go же M:N-планировщик имел с самого начала. Это разбирается в
[../../concurrency/theory/VIRTUAL_THREADS.md](../../concurrency/theory/VIRTUAL_THREADS.md) —
сравнение с Go вынесено в раздел 9 ниже.

## 2. Модель GMP: три буквы

Планировщик оперирует тремя сущностями. Их инициалы дали модели имя.

### G — Goroutine

`G` — структура, описывающая **одну горутину**: её стек, указатель инструкции (где
возобновить выполнение), статус, ссылка на функцию. Это не поток — это «задача» вместе со
своим сохранённым контекстом. Создаётся при `go f()`, живёт в куче, переиспользуется через
свободный список (`gFree`), когда горутина завершилась.

### M — Machine (поток ОС)

`M` — это **поток ОС** (буква от «Machine»). Только `M` реально исполняет код на ядре CPU.
Сам по себе `M` не знает, какую горутину запускать, — для этого ему нужен `P`. Число `M`
не фиксировано: рантайм создаёт новые потоки, когда существующие застряли в блокирующих
системных вызовах (раздел 4). Жёсткий потолок задаётся переменной окружения
`GOMAXTHREADS` (по умолчанию 10000) — защита от неконтролируемого роста.

### P — Processor (логический процессор, контекст планирования)

`P` (буква от «Processor») — это **контекст, дающий право исполнять код Go**. `P` владеет
локальной очередью готовых горутин, кешем памяти для аллокаций (`mcache`) и прочим
состоянием планировщика. Чтобы исполнять горутины, поток `M` обязан сначала **захватить
`P`**. Нет свободного `P` — `M` исполнять код Go не может.

Число `P` фиксировано и равно **`GOMAXPROCS`** (по умолчанию — числу логических ядер). Именно
`P`, а не `M`, ограничивает **реальный параллелизм** Go-кода: одновременно исполняться может
ровно `GOMAXPROCS` горутин, потому что столько есть `P`.

```
        ┌─────────────────────────────────────────────┐
        │  Global Run Queue (общая очередь готовых G)   │
        └─────────────────────────────────────────────┘
              ▲                              ▲
   work-steal │                              │ work-steal
        ┌─────┴─────┐                  ┌─────┴─────┐
        │     P0     │                 │     P1     │      ... всего GOMAXPROCS штук P
        │ local runq │                 │ local runq │
        │ [G][G][G]  │                 │ [G]        │
        └─────┬─────┘                  └─────┬─────┘
              │ привязан                       │ привязан
        ┌─────┴─────┐                  ┌─────┴─────┐
        │    M0      │  (поток ОС)     │    M1      │  (поток ОС)
        │ исполняет  │                 │ исполняет  │
        │    Gx      │                 │    Gy      │
        └───────────┘                  └───────────┘
```

**Связка для исполнения**: `M` + `P` + `G`. Поток `M` берёт `P`, у `P` из локальной очереди
достаёт `G` и исполняет её. Один `P` в каждый момент привязан максимум к одному `M`.

Параллель с JVM: грубо `M ≈ carrier thread`, `P ≈ слот параллелизма / воркер ForkJoinPool`,
`G ≈ виртуальный поток`. Но прямой структуры «P» в JVM нет — это особенность Go, отделяющая
**право исполнять** (P) от **исполнителя** (M).

## 3. Очереди и work-stealing

Готовые к исполнению горутины (статус *runnable*) лежат в очередях:

- **Локальная очередь `P`** (local run queue) — кольцевой буфер на **256** элементов,
  привязанный к конкретному `P`. Обращение к нему почти без блокировок (lock-free для
  владельца) — это быстрый путь.
- **Глобальная очередь** (global run queue) — общая на весь рантайм, защищена мьютексом.
  Туда попадают «лишние» горутины при переполнении локальной и новые горутины при некоторых
  условиях. Доступ дороже (нужен лок), поэтому она — резерв.

### Балансировка через кражу работы

Если у `P` опустела локальная очередь, его `M` не простаивает, а **крадёт работу**
(work-stealing): берёт половину горутин из локальной очереди **случайного другого `P`**.
Прежде чем красть, проверяется глобальная очередь и сетевой poller (раздел 4). Порядок
поиска работы планировщиком примерно такой:

1. Иногда (раз в 61 такт планировщика) заглянуть в **глобальную** очередь — чтобы она не
   голодала, когда локальные всегда полны.
2. Взять `G` из **своей локальной** очереди.
3. Локальная пуста → проверить **глобальную**.
4. Глобальная пуста → опросить **netpoller** (готовые сетевые горутины).
5. И только потом — **украсть** половину у случайного `P`.

Параллель: это тот же принцип, что и **work-stealing в `ForkJoinPool`** JVM (двусторонние
деки на воркер, кража с чужого хвоста) — каноника по нему в
[../../concurrency/theory/EXECUTORS_FUTURES.md](../../concurrency/theory/EXECUTORS_FUTURES.md).
Виртуальные потоки Java как раз и планируются поверх `ForkJoinPool`; механика Go аналогична.

## 4. Жизненный цикл и состояния горутины

Горутина проходит через несколько статусов (в рантайме их больше, но рабочих — три):

| Статус | Что значит |
|---|---|
| `_Grunnable` | готова исполняться, ждёт `P`/`M`; лежит в очереди |
| `_Grunning` | прямо сейчас исполняется на каком-то `M` (привязана к `P`) |
| `_Gwaiting` | заблокирована (ждёт канал, мьютекс, таймер, сеть, syscall) — **не в очереди** |

```
   go f()
     │
     ▼
 ┌──────────┐  взяли P+M   ┌──────────┐  блокирующая операция   ┌──────────┐
 │ runnable │ ───────────► │ running  │ ──────────────────────► │ waiting  │
 │ (в очереди)│            │(исполняется)│                      │(припаркована)│
 └──────────┘  ◄───────────└──────────┘ ◄────────────────────── └──────────┘
       ▲   квант истёк / вытеснена          событие наступило
       │                                    (канал готов, лок взят,
       └────────────────────────────────────  данные пришли)
                          возобновление
```

**Парковка (park) и пробуждение (ready).** Когда горутина упирается в недоступный ресурс
(пустой канал, занятый мьютекс), рантайм её **парует**: переводит в `_Gwaiting`, отвязывает
от `M` и сохраняет контекст. Поток `M` при этом **не блокируется** — он тут же берёт из
очереди следующую `G` и продолжает крутить полезную работу. Когда ресурс становится доступен
(другая горутина отправила в канал, освободила лок), припаркованную горутину переводят
обратно в `_Grunnable` и кладут в очередь — её подхватит любой свободный `M`+`P`.

Ключевой вывод: **блокировка горутины не блокирует поток ОС**. Это и есть причина, по которой
на одном потоке ОС спокойно живут тысячи «спящих» на каналах горутин. В модели 1:1 (старая
Java) спящий поток держал бы поток ОС целиком.

## 5. Блокирующие системные вызовы и netpoller

Парковка из раздела 4 работает для блокировок **внутри рантайма** (каналы, мьютексы) — там
рантайм контролирует обе стороны. Но что с **системным вызовом**, который уходит в ядро
(чтение файла, `time.Sleep` на низком уровне, вызов C через cgo)? Поток `M`, нырнувший в
блокирующий syscall, для рантайма потерян — он застрял в ядре и не может исполнять Go-код.

### Hand-off P (передача процессора)

Если syscall затягивается, нельзя дать одному застрявшему `M` «заморозить» целый `P` (а с ним
— все горутины из его локальной очереди). Поэтому рантайм выполняет **hand-off**: отбирает `P`
у заблокированного `M` и отдаёт его другому `M` (свободному или новому). Освобождённый `P`
тут же продолжает крутить остальные горутины на другом потоке.

```
До syscall:        M0 ── P0 ── исполняет G1 (G2,G3 в очереди P0)
G1 уходит в read():
                   M0 ── (застрял в ядре с G1)
                   P0 ── переходит к ──► M1   (M1 берёт G2, G3 продолжают исполняться)
read() вернулся:
                   M0 ищет свободный P; нет — кладёт G1 в очередь и паркуется в пул
```

Когда syscall завершается, `M0` пытается снова получить `P`. Если свободного `P` нет, горутина
G1 становится `_Grunnable` и кладётся в очередь (её подхватит кто-то другой), а сам `M0`
отправляется в пул простаивающих потоков. Так число `M` может **временно превысить
`GOMAXPROCS`** — лишние потоки нужны, чтобы «прикрыть» застрявшие в syscall.

### sysmon — фоновый монитор

Решение «syscall затянулся, пора делать hand-off» принимает **sysmon** — специальный
системный поток рантайма, работающий **без `P`** и потому всегда доступный. Он периодически
просыпается (адаптивно, от ~20 мкс до 10 мс) и:

- отбирает `P` у `M`, застрявших в syscall дольше порога;
- инициирует **асинхронное вытеснение** долго бегущих горутин (раздел 6);
- опрашивает сетевой poller, если им давно никто не занимался;
- запускает форсированный сбор мусора по таймеру.

### netpoller — неблокирующий сетевой ввод-вывод

Сетевые операции (`net.Conn.Read`, HTTP, БД-драйверы поверх TCP) — отдельный, важный случай.
Если бы каждое чтение из сокета блокировало поток `M` через syscall, hand-off спасал бы, но
ценой постоянного жонглирования потоками под высокой нагрузкой. Вместо этого Go использует
**netpoller** — обёртку над механизмом мультиплексирования ОС (epoll на Linux, kqueue на
BSD/macOS, IOCP на Windows).

Когда горутина читает из сокета, в котором ещё нет данных, рантайм **не** делает блокирующий
syscall. Он:

1. Регистрирует файловый дескриптор в netpoller (epoll и т.п.).
2. **Парует** горутину (`_Gwaiting`) — как при блокировке на канале.
3. Освобождает `M`+`P` для другой работы.

Когда ОС сообщает «в сокет пришли данные», netpoller возвращает список готовых горутин,
рантайм переводит их в `_Grunnable` и ставит в очередь. **Поток ОС всё это время был занят
полезной работой**, а не висел в чтении.

Именно поэтому в Go можно писать линейный, синхронный по виду код
(`n, err := conn.Read(buf)`), который под капотом ведёт себя как высокопроизводительный
асинхронный (event-loop) сервер на epoll. В Java аналогичную «синхронную форму поверх
неблокирующего I/O» дают как раз виртуальные потоки (их блокирующие вызовы перехватываются и
переводятся в неблокирующие). До них приходилось писать колбэки/реактивщину (NIO, Netty) —
такой же event-loop вручную.

## 6. Вытеснение (preemption)

Чтобы планировщик был справедлив, ни одна горутина не должна бесконечно держать `P`. Механизм
отъёма управления — **вытеснение (preemption)**. В Go он эволюционировал.

### Кооперативное вытеснение (до 1.14)

Исторически Go вытеснял горутины только **кооперативно**: точки переключения вставлялись
компилятором в «безопасные» места — прежде всего в **прологи функций** (где проверяется ещё и
рост стека). На таких точках горутина смотрела на флаг «тебя просят уступить» и, если он
взведён, добровольно отдавала `P`.

Проблема — **«горячие циклы» без вызовов функций**:

```go
// До Go 1.14 этот цикл МОГ заблокировать свой P целиком:
func spin() {
    for {            // нет вызовов функций внутри → нет точек кооперации
        i++          // компилятору некуда вставить проверку флага preemption
    }
}
```

Такой цикл не содержит вызовов функций, значит компилятору **некуда** вставить проверку. Если
он попадал на `P`, то держал его, пока сам не закончит. В худшем случае (`GOMAXPROCS=1`) это
подвешивало вообще весь рантайм: даже сборщик мусора не мог дойти до своей фазы STW, потому
что не мог остановить такую горутину. На практике приходилось вручную вставлять
`runtime.Gosched()` (явная уступка) в подобные циклы.

### Асинхронное вытеснение (с Go 1.14)

С Go 1.14 добавлено **асинхронное вытеснение на сигналах**. Когда `sysmon` видит, что горутина
бежит дольше кванта (**~10 мс**), он шлёт потоку `M`, на котором она крутится, сигнал ОС
(`SIGURG`). Обработчик сигнала останавливает горутину **в произвольной безопасной точке**
(рантайм гарантирует, что регистры и стек в согласованном состоянии), сохраняет контекст и
возвращает управление планировщику.

Теперь «горячий цикл» из примера выше будет вытеснен принудительно — `runtime.Gosched()`
вставлять не нужно. Это критично и для сборщика мусора: фазы STW (раздел про GC в
[./MEMORY_GC.md](./MEMORY_GC.md)) теперь могут гарантированно останавливать **все** горутины,
а не ждать их доброй воли.

Параллель с JVM: точки кооперации в прологах функций — близкий аналог **safepoint** в HotSpot
(каноника — [../../java-core/theory/GARBAGE_COLLECTION.md](../../java-core/theory/GARBAGE_COLLECTION.md)):
там JIT тоже вставляет safepoint-проверки в backward-ветви и возвраты, и до недавних
loop-strip-mining-оптимизаций «горячий счётный цикл» аналогично умел задерживать выход всех
потоков на safepoint.

## 7. GOMAXPROCS, привязка и стоимость переключения

### GOMAXPROCS

`GOMAXPROCS` — число `P`, то есть **максимум одновременно исполняющегося Go-кода**. По
умолчанию равно числу логических ядер (с Go 1.5). Меняется переменной окружения или из кода:

```go
import "runtime"

n := runtime.GOMAXPROCS(0)   // 0 — только прочитать текущее значение
runtime.GOMAXPROCS(4)        // установить (редко нужно вручную)
```

```bash
GOMAXPROCS=2 ./server        # ограничить двумя P через окружение
```

**Важная ловушка в контейнерах.** Долгое время рантайм Go видел **все** ядра хоста, игнорируя
ограничения cgroup (`--cpus`). На 64-ядерной ноде в поде с лимитом «2 CPU» Go ставил
`GOMAXPROCS=64`, плодил лишние `P`, усиливал конкуренцию и троттлинг от планировщика ОС.
Лечилось библиотекой `automaxprocs` (Uber), читающей квоту cgroup. **Начиная с Go 1.25**
рантайм учитывает лимит cgroup автоматически и берёт `GOMAXPROCS` исходя из CPU-квоты, так что
внешний костыль для современных версий не нужен. (Сравните с JVM, где аналогичную проблему
решает `UseContainerSupport`/`MaxRAMPercentage` — каноника в
[../../java-core/theory/JVM_MEMORY_AREAS.md](../../java-core/theory/JVM_MEMORY_AREAS.md).)

### Привязка (нет жёсткого pinning по умолчанию)

Горутина **не привязана** к конкретному `M` или ядру: при следующем кванте её может подхватить
другой `M` на другом ядре (миграция). Это хорошо для балансировки, но теряет локальность кеша
CPU. Жёсткой привязки горутины к ядру в публичном API нет. Единственная форма «привязки» —
`runtime.LockOSThread()`: она прибивает горутину к **текущему `M`** (нужно для библиотек C/GUI,
требующих вызовов из одного и того же потока ОС, например OpenGL).

### Стоимость переключения

Переключение между горутинами **на одном `M`** — это смена нескольких регистров и указателя
стека в пользовательском пространстве, **без входа в ядро**: порядка десятков наносекунд.
Переключение потоков ОС — это вход в ядро, ~1–2 микросекунды, плюс эффекты на кеш CPU. Разница
на два порядка и есть причина, по которой Go спокойно мультиплексирует огромное число горутин:
дорогие переключения потоков ОС случаются редко (hand-off, рост числа `M`), а частые
переключения горутин — дёшевы.

## 8. Минимальный пример: иллюстрация модели

```go
package main

import (
    "fmt"
    "runtime"
    "sync"
    "time"
)

func main() {
    fmt.Println("GOMAXPROCS =", runtime.GOMAXPROCS(0)) // число P = реальный параллелизм
    fmt.Println("NumCPU     =", runtime.NumCPU())       // логических ядер

    var wg sync.WaitGroup
    for i := 0; i < 100_000; i++ { // сто тысяч горутин — на потоках ОС это немыслимо
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            time.Sleep(time.Millisecond) // паркуется: M свободен для других горутин
        }(i)
    }
    wg.Wait()
    fmt.Println("горутин сейчас:", runtime.NumGoroutine())
}
```

Сто тысяч горутин по ~2 КБ стартового стека — это порядка сотен мегабайт в пределе и обычно
сильно меньше (большинство спит на `Sleep`, их стек не растёт). Те же сто тысяч **потоков ОС**
по ~1 МБ — это ~100 ГБ и мгновенный отказ. В этом вся суть M:N.

### Полезные инструменты наблюдения

```bash
GODEBUG=schedtrace=1000 ./app        # раз в 1000 мс печатать состояние планировщика
GODEBUG=scheddetail=1,schedtrace=1000 ./app  # детально: по каждому P и M
```

`runtime.NumGoroutine()` — текущее число горутин; профиль `goroutine` в `pprof` показывает,
где они застряли (диагностика утечек горутин) — см.
[./PERFORMANCE_PROFILING.md](./PERFORMANCE_PROFILING.md).

## 9. Сравнение с JVM: виртуальные потоки и M:N

Каноника по виртуальным потокам Java — в
[../../concurrency/theory/VIRTUAL_THREADS.md](../../concurrency/theory/VIRTUAL_THREADS.md).
Здесь — только карта соответствий.

| Понятие | Go | Java (Project Loom, 21+) |
|---|---|---|
| Лёгкая задача | горутина (`G`) | виртуальный поток |
| Носитель (поток ОС) | `M` (Machine) | carrier thread |
| Контекст планирования | `P` (Processor), `GOMAXPROCS` штук | слот параллелизма `ForkJoinPool` |
| Планировщик | рантайм Go | `ForkJoinPool` (work-stealing) |
| Сохранённое состояние при блокировке | стек горутины (растущий) | continuation (стек копируется в кучу) |
| Неблокирующий I/O под капотом | netpoller (epoll/kqueue/IOCP) | перехват блокирующих вызвов → NIO selector |
| Парк потока ОС при блокировке задачи | нет (M свободен) | нет (carrier свободен) |
| Эпоха в языке | с рождения (M:N изначально) | с Java 21 (до этого только 1:1) |

**Сходства.** Обе модели — M:N: множество лёгких задач поверх немногих потоков ОС с
work-stealing-планировщиком; блокировка задачи **не** блокирует поток-носитель; синхронный по
виду код прозрачно превращается в неблокирующий I/O.

**Отличия.**

1. **Как сохраняется состояние.** Go даёт каждой горутине собственный **растущий стек** в
   куче (раздел про рост стека — в [./MEMORY_GC.md](./MEMORY_GC.md)); при блокировке этот стек
   просто остаётся. Java хранит виртуальный поток как **continuation** — при «парковке»
   фрагмент стека копируется в объект на куче, при возобновлении — обратно. Разные механизмы с
   разными издержками.
2. **`P` как явная сущность.** В Go параллелизм Go-кода прямо ограничен числом `P`
   (`GOMAXPROCS`). В Java степень параллелизма задаётся размером пула carrier-потоков; явной
   структуры «P» нет.
3. **Pinning.** В Java виртуальный поток может «прибиться» к carrier-потоку (pinning) внутри
   `synchronized`-блока или нативного вызова, временно теряя выгоду M:N (каноника — раздел про
   pinning в [../../concurrency/theory/LOCKS.md](../../concurrency/theory/LOCKS.md)). В Go
   аналогичный эффект даёт только явный `runtime.LockOSThread()`; `synchronized`-аналога,
   неявно прибивающего горутину, нет — мьютексы Go (`sync.Mutex`) горутину не пинят.
4. **Долгий CPU-bound код.** До асинхронного вытеснения (Go < 1.14) «горячий цикл» мог
   задержать планировщик Go. Виртуальные потоки Java тоже не вытесняются по таймеру внутри
   тугого CPU-цикла (Loom рассчитан на I/O-bound задачи); это родственное ограничение обеих
   моделей.

## Типичные ошибки

| Ошибка / заблуждение | Почему неверно | Как правильно |
|---|---|---|
| «`GOMAXPROCS` = число горутин» | это число `P` = параллелизм Go-кода, горутин могут быть миллионы | горутин ограничивает только память |
| «блокирующий канал блокирует поток ОС» | рантайм паркует горутину, `M` свободен | блокировка горутины дёшева и масштабируема |
| «много горутин висят в сети → много потоков» | netpoller обходится единицами потоков | синхронный код поверх epoll — это норма Go |
| «горячий цикл всегда вытесняется» (любая версия) | принудительно — только с Go 1.14+ | на старых версиях нужен `runtime.Gosched()` |
| «в контейнере Go сам ограничит CPU» | автоматически — лишь с Go 1.25 | на старых версиях — `automaxprocs` или явный `GOMAXPROCS` |
| «горутина закреплена за ядром» | по умолчанию мигрирует между `M`/ядрами | закрепление — только `runtime.LockOSThread()` |
| `sync.Mutex` «пинит» горутину как Java `synchronized` | мьютекс Go горутину не прибивает к потоку | pinning в Go — только явный `LockOSThread` |
