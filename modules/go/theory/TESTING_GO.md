# Go — Тестирование

> Инструментарий тестирования встроен в язык: тесты, бенчмарки, fuzzing и примеры-документация
> запускаются одной командой `go test` — без сторонних зависимостей, без runner-плагинов, без
> аннотаций. Файл `_test.go`, функция `TestXxx(t *testing.T)` — и всё.
> Это покрывает тестовый инструментарий Go. Пирамида тестов, философия мокинга и интеграционное
> тестирование как дисциплина — у владельца: [TESTING (software-engineering)](../../software-engineering/theory/TESTING.md).

Аудитория — разработчик из Java/Kotlin, знающий JUnit и Mockito, видящий Go-тесты впервые.
Главный сдвиг сознания: в Go нет JUnit. Нет `@Test`, нет `@BeforeEach`, нет ассерт-библиотеки в
стандартной поставке, нет встроенного Mockito. Вместо этого — одно соглашение об именах,
один пакет `testing`, и идиома «сравни вручную, при расхождении позови `t.Errorf`». Меньше
магии, больше явности — ровно как и весь язык.

## 1. Соглашения и запуск

### Файлы и имена

Тест живёт рядом с кодом, в том же каталоге (= в том же пакете), в файле с суффиксом `_test.go`.
Компилятор знает: `*_test.go` собираются только при `go test` и не попадают в обычную сборку
(`go build` их игнорирует). Тестовая функция распознаётся по сигнатуре:

```go
// файл stats.go      → пакет wordstats
// файл stats_test.go → тесты для него
package wordstats

import "testing"

func TestCount(t *testing.T) {     // имя начинается с Test + заглавная буква
    got := Count("a b c")
    if got != 3 {
        t.Errorf("Count = %d, want 3", got)
    }
}
```

Правила распознавания строгие:
- имя функции — `Test` + следующая буква в верхнем регистре (`TestCount`, `Test_count` — НЕ тест, `Testcount` — НЕ тест);
- единственный параметр — `*testing.T`;
- возвращаемого значения нет.

Аналогично: `BenchmarkXxx(b *testing.B)` — бенчмарк, `FuzzXxx(f *testing.F)` — fuzz-цель,
`ExampleXxx()` — пример-документация. Всё это собирает и запускает один и тот же `go test`.

### White-box vs black-box: пакет `foo` vs `foo_test`

Тестовый файл может объявлять один из двух пакетов:

| `package foo` | `package foo_test` |
|---|---|
| тот же пакет, что и код (**white-box**) | внешний пакет (**black-box**) |
| видит неэкспортируемые имена (`count`, `helper`) | видит только экспортируемый API (`Count`) |
| тестируете внутренности | тестируете контракт «как пользователь» |
| импорт `foo` не нужен — вы и есть `foo` | импортируете `foo` явно |

Особенность Go: **оба пакета разрешено держать в одном каталоге** — это единственное исключение
из правила «один каталог = один пакет». Идиома: основной набор пишут как `package foo_test`
(проверяет публичный контракт и заодно ловит случайные циклы импортов), а отдельные white-box
тесты внутренней логики — как `package foo` в соседнем файле. `Example`-функции почти всегда
кладут в `foo_test` — чтобы они выглядели как реальный клиентский код в документации.

### Запуск и флаги

```bash
go test ./...                 # все пакеты рекурсивно
go test ./wordstats/          # один пакет
go test -v ./wordstats/       # подробно: имя каждого теста + PASS/FAIL
go test -run TestCount        # только тесты, чьё имя матчит регулярку
go test -run 'TestCount/empty'# конкретный подтест (см. t.Run ниже)
go test -count=1 ./...        # отключить кэш результатов (форсировать перезапуск)
go test -short ./...          # «короткий режим» — см. t.Short ниже
go test -timeout 30s ./...    # таймаут на весь бинарник теста (default 10m)
go test -race ./...           # с детектором гонок
```

Две ловушки для пришедших из JUnit:
- `-run` принимает **регулярное выражение**, а не точное имя: `-run Count` запустит и `TestCount`, и `TestCountEmpty`. Для точного совпадения — `-run '^TestCount$'`.
- `go test` **кэширует** успешные результаты: если код и тесты не менялись, второй запуск мгновенно отдаст `(cached)`. Чтобы заставить перезапуститься (например, тест читает внешний ресурс) — `-count=1`.

## 2. API `testing.T`

`*testing.T` — единственный «фреймворк», который у вас есть. Ассертов нет: вы пишете обычный
`if`, а при расхождении сообщаете о провале. Ключевое различие — между «отметить провал и
продолжить» и «отметить провал и немедленно выйти».

| Метод | Действие |
|---|---|
| `t.Error(args)` / `t.Errorf(format, …)` | пометить тест проваленным, **продолжить** выполнение |
| `t.Fatal(args)` / `t.Fatalf(format, …)` | пометить проваленным и **немедленно** прервать (`runtime.Goexit`) |
| `t.Log` / `t.Logf` | вывод (печатается только при `-v` или при провале) |
| `t.Helper()` | пометить функцию как хелпер — её строка не будет в репорте |
| `t.Cleanup(func)` | зарегистрировать teardown (выполнится после теста, в LIFO-порядке) |
| `t.TempDir()` | создать временный каталог, удаляемый автоматически после теста |
| `t.Setenv(key, val)` | установить переменную окружения, восстановить после теста |
| `t.Skip` / `t.Skipf` / `t.SkipNow` | пропустить тест (статус SKIP, не FAIL) |
| `t.Parallel()` | пометить тест как параллельный (см. раздел 3) |

### Error vs Fatal — когда что

Правило: **`Fatal` — когда продолжать бессмысленно** (предусловие не выполнено, дальше всё равно
паника). **`Error` — когда хочется собрать несколько претензий за один прогон.**

```go
func TestUser(t *testing.T) {
    u, err := Load("u-1")
    if err != nil {
        t.Fatalf("Load вернул ошибку: %v", err)   // дальше u нечего проверять — Fatal
    }
    if u.Name != "Ann" {
        t.Errorf("Name = %q, want Ann", u.Name)    // одна претензия...
    }
    if u.Age != 30 {
        t.Errorf("Age = %d, want 30", u.Age)       // ...и сразу вторая — обе в репорте
    }
}
```

Критическая ловушка: **`Fatal` нельзя звать из другой горутины.** Под капотом это
`runtime.Goexit`, который завершает только ту горутину, где вызван, а тест продолжит идти и
завершится «успехом». Из горутины — только `t.Error` (а синхронизацию ждите через канал/WaitGroup),
финальную проверку делайте в основной горутине теста.

### `t.Helper` — чистые репорты

Если ассерт вынесен в общую функцию, провал по умолчанию укажет на строку внутри хелпера, а не
на место вызова. `t.Helper()` это чинит:

```go
func assertEqual(t *testing.T, got, want int) {
    t.Helper()                     // «не я виноват — смотри выше»
    if got != want {
        t.Errorf("got %d, want %d", got, want)
    }
}
```

Без `t.Helper()` все провалы покажут одну и ту же строку внутри `assertEqual` — отлаживать
невозможно. Это прямой аналог того, что в JUnit делает сам фреймворк со стеком ассертов.

### `t.Cleanup`, `t.TempDir`, `t.Setenv`

Это замена `@AfterEach`/`@TempDir`/манипуляций с системными свойствами:

```go
func TestWrite(t *testing.T) {
    dir := t.TempDir()                 // авто-удаление после теста
    t.Setenv("APP_HOME", dir)          // авто-восстановление после теста

    f := openLog(dir)
    t.Cleanup(func() { f.Close() })    // выполнится при выходе, даже после Fatal

    // ... тело теста
}
```

`t.Cleanup` важен тем, что отрабатывает **даже после `t.Fatal`** (в отличие от кода после
вызова `Fatal`, который просто не выполнится). Несколько `Cleanup` снимаются в обратном порядке
(LIFO), как `defer`. `t.Setenv` несовместим с `t.Parallel()` — рантайм паникует, если их
совместить (глобальное окружение нельзя менять из параллельных тестов).

## 3. Table-driven тесты — каноничный стиль Go

Это **главная идиома** тестирования в Go, её ждут на ревью и на собеседовании. Вместо десятка
почти одинаковых функций — срез структур-кейсов, по которому идёт цикл; каждый кейс
оборачивается в подтест через `t.Run`.

```go
func TestRomanToInt(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    int
        wantErr bool
    }{
        {"single I", "I", 1, false},
        {"additive III", "III", 3, false},
        {"subtractive IV", "IV", 4, false},
        {"mixed MCMXCIV", "MCMXCIV", 1994, false},
        {"empty is error", "", 0, true},
        {"bad letter", "IIX", 0, true},
    }

    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {     // подтест с именем
            got, err := RomanToInt(tc.in)
            if (err != nil) != tc.wantErr {
                t.Fatalf("RomanToInt(%q) err = %v, wantErr = %v", tc.in, err, tc.wantErr)
            }
            if got != tc.want {
                t.Errorf("RomanToInt(%q) = %d, want %d", tc.in, got, tc.want)
            }
        })
    }
}
```

Почему это сильнее, чем JUnit `@ParameterizedTest`:
- кейсы — обычные данные, добавить строку = добавить случай; ничего не аннотируется;
- `t.Run(name, …)` даёт каждому кейсу **отдельное имя в репорте** и позволяет запустить один: `go test -run 'TestRomanToInt/empty_is_error'` (пробелы в имени заменяются на `_`);
- провал одного подтеста не валит остальные — видно сразу все упавшие кейсы;
- стандартная привычка — в сообщении печатать **вход и ожидание**, чтобы из лога было ясно, какой кейс упал.

### Подтесты и `t.Parallel` — главная ловушка

Подтест можно сделать параллельным, вызвав `t.Parallel()` в его теле. Тогда `t.Run` для него
возвращает управление немедленно, а сам кейс встаёт в очередь и стартует после того, как
внешняя `Test`-функция дойдёт до конца цикла. Здесь подстерегает **классический баг с
переменной цикла**:

```go
// ❌ БАГ на Go ≤ 1.21: все параллельные подтесты видят последний tc
for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        got := RomanToInt(tc.in)   // tc уже = последний элемент, цикл завершился
        _ = got
    })
}

// ✅ до Go 1.22 — переобъявить переменную внутри тела цикла
for _, tc := range tests {
    tc := tc                        // создаём новую переменную на каждой итерации
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        // tc теперь захвачен корректно
    })
}
```

В **Go 1.22+** семантику `for…range` починили: переменная цикла теперь создаётся заново на
каждой итерации, и строка `tc := tc` больше не нужна. Но знать про эту ловушку обязательно —
она годами была причиной номер один «загадочно зелёных» параллельных тестов и встречается в
старом коде и на собеседованиях.

Вторая тонкость: параллельные подтесты внутри одной `Test`-функции стартуют только когда
**внешняя функция вернёт управление** — поэтому общий teardown через `defer` в родителе
отработает раньше, чем подтесты успеют поработать. Решение — `t.Cleanup` (он ждёт завершения
параллельных детей) или оборачивающий подтест-группу `t.Run("group", func…)`.

## 4. `TestMain` — глобальный setup/teardown

Если на весь пакет нужен один общий setup (поднять контейнер, открыть пул соединений), объявите
функцию `TestMain`. Когда она есть, рантайм **не запускает тесты сам** — он зовёт `TestMain`,
а та обязана вызвать `m.Run()` и пробросить код возврата:

```go
func TestMain(m *testing.M) {
    // setup: один раз на весь пакет — до всех тестов
    db := startTestDB()

    code := m.Run()             // запускает ВСЕ Test/Benchmark/Example пакета

    // teardown: один раз — после всех
    db.Close()

    os.Exit(code)               // обязательно: пробросить статус наружу
}
```

Это аналог JUnit `@BeforeAll`/`@AfterAll`, но на уровне **всего пакета**, а не класса. Важно:
после `m.Run()` нужно явно `os.Exit(code)` — иначе провалы не дойдут до `go test`. И помните,
что `os.Exit` обходит `defer`: весь teardown пишите до выхода. На пакет может быть только одна
`TestMain`.

## 5. Тест-дублёры: интерфейсы вместо Mockito

В Go **нет встроенного Mockito**. И это не пробел, а следствие дизайна: дублёры делаются через
**интерфейсы + ручные реализации**, а зависимости подменяются **внедрением через интерфейс**.
Поскольку интерфейсы в Go удовлетворяются неявно (duck typing, см. [INTERFACES](./INTERFACES.md)),
объявить fake тривиально.

```go
// Зависимость объявлена как УЗКИЙ интерфейс на стороне потребителя.
type Clock interface {
    Now() time.Time
}

type Service struct {
    clock Clock                 // внедряем интерфейс, не конкретный тип
}

func (s *Service) Stamp() string {
    return s.clock.Now().Format(time.RFC3339)
}

// --- в тесте: ручной stub, реализующий Clock ---
type fixedClock struct{ t time.Time }

func (f fixedClock) Now() time.Time { return f.t }

func TestStamp(t *testing.T) {
    fixed := time.Date(2026, 1, 2, 3, 4, 5, 0, time.UTC)
    s := &Service{clock: fixedClock{fixed}}
    if got := s.Stamp(); got != "2026-01-02T03:04:05Z" {
        t.Errorf("Stamp = %q", got)
    }
}
```

Терминология (как у владельца — [TESTING](../../software-engineering/theory/TESTING.md)):
**stub** возвращает заранее заданные ответы; **fake** — рабочая упрощённая реализация (например,
map вместо БД); **mock** проверяет, что его вызвали с нужными аргументами. В Go первые два пишут
руками за минуту. Идиома «**узкий интерфейс на стороне потребителя**» (объявляйте `Clock` с
одним методом там, где он нужен, а не тащите весь интерфейс БД) делает дублёры крошечными.

Когда руками действительно много (десятки методов или строгая проверка порядка вызовов), берут
генераторы/библиотеки: `go.uber.org/mock` (gomock, кодоген по интерфейсу), `testify/mock`
(ассерты ожиданий), `testify/assert` (привычные `assert.Equal`). Но этот модуль — stdlib-only:
в 90% случаев интерфейс + структура закрывают потребность без зависимостей.

## 6. Бенчмарки

Бенчмарк — функция `BenchmarkXxx(b *testing.B)`. Рантайм сам подбирает число итераций `b.N`
так, чтобы измерение было статистически значимым (стартует с малого и увеличивает, пока время
прогона не стабилизируется). Ваша задача — выполнить измеряемую операцию **ровно `b.N` раз** в
цикле:

```go
func BenchmarkRomanToInt(b *testing.B) {
    for i := 0; i < b.N; i++ {       // тело крутится b.N раз — число выбирает рантайм
        _, _ = RomanToInt("MCMXCIV")
    }
}
```

Запуск (бенчмарки **не** запускаются обычным `go test` — нужен флаг `-bench`):

```bash
go test -bench=.            ./wordstats/   # все бенчмарки (-bench принимает регулярку)
go test -bench=Roman        ./wordstats/   # только матчащие
go test -bench=. -benchmem  ./wordstats/   # + аллокации (B/op, allocs/op)
go test -bench=. -benchtime=2s ./...       # целиться в ~2s на бенчмарк
go test -bench=. -count=10  ./...          # 10 прогонов — для benchstat
```

Вывод читается так: `BenchmarkRomanToInt-8   5000000   243 ns/op   16 B/op   1 allocs/op` —
суффикс `-8` это `GOMAXPROCS`, дальше число итераций, наносекунды на операцию и (с `-benchmem`)
байты и аллокации на операцию.

### Полезные методы `b`

| Метод | Зачем |
|---|---|
| `b.ResetTimer()` | обнулить таймер после дорогого setup (чтобы он не попал в измерение) |
| `b.StopTimer()` / `b.StartTimer()` | пауза измерения вокруг неизмеряемых участков внутри цикла |
| `b.ReportAllocs()` | включить отчёт по аллокациям для этого бенчмарка (как `-benchmem`, но локально) |
| `b.RunParallel(func(pb *testing.PB) { for pb.Next() {…} })` | нагрузить со всех ядер — для измерения contention |

```go
func BenchmarkWithSetup(b *testing.B) {
    data := buildLargeInput()    // дорогой setup — НЕ должен попасть в измерение
    b.ResetTimer()               // обнуляем таймер ровно перед циклом
    for i := 0; i < b.N; i++ {
        _ = Process(data)
    }
}
```

### Ловушка: устранение мёртвого кода компилятором

Если результат операции никуда не идёт, компилятор вправе выкинуть весь вызов — бенчмарк
покажет фантастические `0.3 ns/op`. Лекарство — **sink-переменная** на уровне пакета: присвойте
результат ей, чтобы компилятор не мог доказать ненужность вычисления.

```go
var sink int   // пакетная переменная — «слив», который компилятор не оптимизирует

func BenchmarkSum(b *testing.B) {
    var s int
    for i := 0; i < b.N; i++ {
        s = expensiveSum(input)   // результат используется...
    }
    sink = s                      // ...и «утекает» наружу — вызов не выкинут
}
```

Сравнивать прогоны на глаз нельзя — шум измерения велик. Запускайте с `-count=10` и сводите
результаты утилитой `benchstat` (она считает медиану и говорит, статистически значима ли
разница). Глубже о профилировании, `pprof` и интерпретации `B/op` — в
[PERFORMANCE_PROFILING](./PERFORMANCE_PROFILING.md).

## 7. Fuzzing — поиск входов, ломающих код

Fuzzing встроен в `testing` начиная с Go 1.18. Цель `FuzzXxx(f *testing.F)` описывает, как
проверять **произвольно сгенерированный** вход; рантайм мутирует начальные примеры (seed corpus)
и ищет панику или нарушение инварианта.

```go
func FuzzRomanRoundTrip(f *testing.F) {
    f.Add("IV")                  // seed: начальные примеры корпуса
    f.Add("MCMXCIV")
    f.Add("")                    // граничный — пустая строка

    f.Fuzz(func(t *testing.T, s string) {
        n, err := RomanToInt(s)
        if err != nil {
            return               // невалидный вход — не наша забота, просто выходим
        }
        // инвариант: если разобрали — обратное преобразование даёт ту же строку
        if got := IntToRoman(n); got != s {
            t.Errorf("round-trip: %q -> %d -> %q", s, n, got)
        }
    })
}
```

Запуск:

```bash
go test ./...                       # fuzz-цели в обычном режиме гоняются на seed-корпусе (как тест)
go test -fuzz=FuzzRomanRoundTrip ./wordstats/   # активный фаззинг (работает, пока не Ctrl+C)
go test -fuzz=Fuzz -fuzztime=30s ./...          # фаззить ограниченное время
```

Ключевые моменты:
- без `-fuzz` цель ведёт себя как обычный тест, прогоняя только seed-примеры из `f.Add` и сохранённый корпус;
- с `-fuzz` рантайм генерирует входы бесконечно; найдя падение, он **сохраняет вход в `testdata/fuzz/<имя>/`** — этот файл становится постоянным регрессионным кейсом и проверяется при каждом обычном `go test`;
- типы аргументов `f.Fuzz` ограничены (`[]byte`, `string`, числовые, `bool`, `rune` и т. п.) и должны совпадать с типами в `f.Add`;
- идеально подходит для парсеров, кодеков, нормализаторов — там, где «странный» вход легко упускается в table-driven кейсах.

## 8. Testable examples — тест и документация в одном

`ExampleXxx()` — функция без параметров, которая одновременно **попадает в godoc как пример
использования** и **проверяется как тест**. Магия — в комментарии `// Output:`: рантайк
сравнивает то, что функция напечатала в stdout, с текстом после `// Output:`.

```go
func ExampleRomanToInt() {
    n, _ := RomanToInt("XIV")
    fmt.Println(n)
    // Output: 14
}
```

Если фактический вывод не совпадёт с `// Output:` — `go test` пометит провал. Пример без
комментария `// Output:` компилируется (godoc его покажет), но **не выполняется** как тест.

Когда порядок строк недетерминирован (например, перебор map), используйте `// Unordered output:`
— рантайм сравнит набор строк без учёта порядка:

```go
func ExampleSet_Items() {
    s := NewSet[string]()
    s.Add("a"); s.Add("b")
    for _, v := range s.Items() {
        fmt.Println(v)
    }
    // Unordered output:
    // a
    // b
}
```

Соглашения об именах задают, к чему пример прикрепится в документации: `Example` (к пакету),
`ExampleRomanToInt` (к функции), `ExampleSet_Items` (к методу `Items` типа `Set`), а суффикс
`_xxx` (`ExampleRomanToInt_negative`) даёт несколько примеров для одного API. Аналога в JUnit
нет вовсе — это уникальная для Go идея «исполняемой документации».

## 9. Покрытие и детектор гонок

### Покрытие

```bash
go test -cover ./...                          # процент покрытия в выводе
go test -coverprofile=cover.out ./wordstats/  # выгрузить профиль в файл
go tool cover -func=cover.out                 # разбивка по функциям
go tool cover -html=cover.out                 # HTML с подсветкой: что не покрыто
```

`-cover` инструментирует код счётчиками и печатает строку вида `coverage: 87.5% of statements`.
`go tool cover -html` открывает браузер с построчной подсветкой (зелёное — покрыто, красное —
нет) — лучший способ найти незатронутые ветки. Покрытие в Go меряется по операторам (statements),
а не строкам.

### Детектор гонок `-race`

```bash
go test -race ./...           # инструментирует доступ к памяти; ловит data race в рантайме
```

`-race` — встроенный ThreadSanitizer: он замедляет код в разы и увеличивает память, но в обмен
**ловит реальные гонки данных** во время выполнения теста. Правило: любой тест конкурентного
кода (горутины, общая память, каналы) гоняйте под `-race` хотя бы в CI. Подробнее о модели
памяти и гонках — в [MEMORY_GC](./MEMORY_GC.md).

## 10. `net/http/httptest` — тесты обработчиков

Стандартный пакет `net/http/httptest` тестирует HTTP-обработчики **без поднятия реального
сетевого сервера**. Два главных инструмента:

**`ResponseRecorder`** — поддельный `http.ResponseWriter`, в который обработчик пишет ответ, а
тест потом читает записанное:

```go
func TestHandler(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/hello?name=Ann", nil)
    rec := httptest.NewRecorder()        // перехватчик ответа

    HelloHandler(rec, req)               // зовём обработчик напрямую, без сети

    res := rec.Result()
    if res.StatusCode != http.StatusOK {
        t.Errorf("status = %d, want 200", res.StatusCode)
    }
    body, _ := io.ReadAll(res.Body)
    if string(body) != "Hello, Ann" {
        t.Errorf("body = %q", body)
    }
}
```

**`httptest.NewServer`** — наоборот, поднимает настоящий сервер на случайном порту: нужен, когда
тестируете **клиента**, которому требуется реальный URL для запроса:

```go
srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    fmt.Fprint(w, `{"ok":true}`)
}))
defer srv.Close()                        // обязательно закрыть

resp, _ := http.Get(srv.URL)             // srv.URL — реальный адрес вида http://127.0.0.1:PORT
// ... проверяем, как клиент обработал ответ
```

Связь с устройством обработчиков, middleware и роутинга — в [NET_HTTP](./NET_HTTP.md).

## 11. Golden files

Когда ожидаемый результат громоздкий (отрендеренный HTML, сериализованный JSON, большой
текстовый отчёт), держать его строковым литералом в тесте больно. Паттерн **golden file**:
эталон лежит в файле `testdata/`, тест сравнивает с ним фактический вывод, а флаг `-update`
позволяет перегенерировать эталон, когда поведение изменилось намеренно.

```go
var update = flag.Bool("update", false, "перезаписать golden-файлы")

func TestRender(t *testing.T) {
    got := Render(input)
    golden := filepath.Join("testdata", "render.golden")

    if *update {                                  // go test -update — обновить эталон
        os.WriteFile(golden, got, 0o644)
    }
    want, _ := os.ReadFile(golden)
    if !bytes.Equal(got, want) {
        t.Errorf("вывод не совпал с %s (запусти -update, если изменение намеренно)", golden)
    }
}
```

Каталог `testdata/` особый: инструменты Go (`go build`, `go test`) его игнорируют как исходники,
поэтому туда складывают фикстуры, golden-файлы и сохранённый fuzz-корпус.

## 12. Типичные ошибки

- **`t.Fatal` из другой горутины.** Завершит только ту горутину; тест ложно «пройдёт». Из горутины — `t.Error`, финальная проверка — в основной.
- **Захват переменной цикла в параллельном подтесте (Go ≤ 1.21).** Без `tc := tc` все кейсы видят последний элемент. На 1.22+ исправлено языком, но в старом коде встречается.
- **`-run` как точное имя.** Это регулярка: `-run Foo` зацепит и `TestFooBar`. Для точного — `-run '^TestFoo$'`.
- **Бенчмарк без sink-переменной.** Компилятор выкинет неиспользуемый результат → `~0 ns/op`. Присваивайте результат пакетной переменной.
- **Setup в цикле бенчмарка без `ResetTimer`.** Дорогой setup попадёт в измерение и исказит цифры.
- **Сравнение бенчмарков на глаз.** Шум велик; `-count=10` + `benchstat`, а не «одно число против другого».
- **`Example` без `// Output:`.** Скомпилируется и попадёт в godoc, но **не проверится** как тест — лёгкая иллюзия покрытия.
- **Забыть `os.Exit(code)` в `TestMain`.** Статус не дойдёт до `go test`, провалы «потеряются».
- **`t.Setenv` вместе с `t.Parallel`.** Паника в рантайме — глобальное окружение несовместимо с параллелизмом.
- **Не гонять конкурентные тесты под `-race`.** Гонка проявится в проде, а не в зелёном CI.
- **Сравнение структур/срезов через `==`.** Срезы и map оператором `==` не сравниваются (паника компиляции / только с nil); используйте `slices.Equal`, `maps.Equal` или `reflect.DeepEqual`.
