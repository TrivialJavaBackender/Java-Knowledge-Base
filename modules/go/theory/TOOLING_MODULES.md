# Go — Инструментарий и модули

> Как устроена сборка в Go: единый бинарь `go`, переменные окружения, система модулей (`go.mod`/`go.sum`), управление зависимостями и алгоритм выбора версий MVS.
> Это первый файл модуля — он даёт фундамент, на котором стоит весь остальной Go-инструментарий.

Аудитория — разработчик из мира Java/Kotlin, где сборкой занимаются Maven или Gradle. Ключевая мысль с самого начала: в Go нет отдельной системы сборки. Сборка, тесты, форматирование, управление зависимостями, документация — всё это подкоманды одной утилиты `go`, которая ставится вместе с компилятором. Никакого `pom.xml` с плагинами, никакого DSL на Groovy/Kotlin — конфигурация минимальна и декларативна.

## 1. Установка и проверка

Go распространяется как единый дистрибутив с официального сайта (`go.dev/dl`) или через пакетный менеджер ОС (`brew install go`, `apt`, `winget`). Внутри — компилятор, линкер, стандартная библиотека (исходники + предсобранные пакеты) и сама команда `go`.

```bash
go version
# go version go1.23.4 darwin/arm64
```

Вывод показывает версию toolchain, операционную систему и архитектуру. Это первое, что стоит проверить: многие фичи привязаны к версии (дженерики — с 1.18, новый роутинг `net/http` — с 1.22, итераторы `range`-over-func — с 1.23).

### Параллель с JVM

| | JVM-мир | Go |
|---|---|---|
| Компилятор | `javac` (отдельно от Maven) | встроен в `go` |
| Сборка | Maven / Gradle (внешний tool) | `go build` (подкоманда) |
| Управление зависимостями | Maven Central + `pom.xml` | модули + `go.mod` |
| Запуск | `java -jar app.jar` (нужна JRE) | `./app` (статический бинарь) |
| Runtime у пользователя | да (JVM) | нет (runtime влинкован в бинарь) |

Главное отличие: `go build` производит **статически слинкованный исполняемый файл**, который не требует установленного Go на целевой машине. Это упрощает развёртывание — нет аналога «нужна JRE 21».

## 2. `go env` — переменные окружения

`go env` печатает все переменные, влияющие на toolchain. Их десятки, но критичны несколько.

```bash
go env GOROOT GOPATH GOMODCACHE GOBIN GOOS GOARCH
```

| Переменная | Что это | Аналогия / комментарий |
|---|---|---|
| `GOROOT` | каталог установки самого Go (компилятор + stdlib) | как `JAVA_HOME`. Менять вручную почти никогда не нужно |
| `GOPATH` | рабочий каталог Go (по умолчанию `~/go`) | исторически — корень всего кода; сейчас в основном кэш и `GOBIN` |
| `GOMODCACHE` | кэш скачанных модулей (`$GOPATH/pkg/mod`) | как локальный репозиторий `~/.m2/repository` |
| `GOBIN` | куда `go install` кладёт бинари (по умолчанию `$GOPATH/bin`) | аналог каталога, который добавляют в `PATH` |
| `GOOS` | целевая операционная система сборки | `linux`, `darwin`, `windows` |
| `GOARCH` | целевая архитектура процессора | `amd64`, `arm64`, `386` |

Изменить переменную постоянно можно через `go env -w KEY=value` (запись в `$GOENV`, обычно `~/.config/go/env`), а сбросить — через `go env -u KEY`.

```bash
go env -w GOFLAGS=-mod=readonly      # установить значение по умолчанию
go env -u GOFLAGS                    # сбросить к дефолту
```

### Кросс-компиляция

Поскольку `GOOS`/`GOARCH` — обычные переменные окружения, собрать бинарь под другую платформу можно одной командой, без эмуляторов и тулчейнов:

```bash
GOOS=linux GOARCH=arm64 go build -o app-linux-arm64 ./cmd/server
GOOS=windows GOARCH=amd64 go build -o app.exe ./cmd/server
```

Это работает «из коробки», потому что компилятор Go умеет генерировать код под все поддерживаемые цели, а стандартная библиотека уже скомпонована под каждую из них. Список целей — `go tool dist list`. Оговорка: если в проекте используется `cgo` (вызовы C), для кросс-компиляции уже нужен C-кросс-компилятор; чистый Go от этого свободен.

## 3. Основные команды

Все команды работают относительно текущего модуля (см. раздел 4). Аргумент — путь к пакету: `.` (текущий каталог), `./...` (текущий каталог и все вложенные), либо импорт-путь.

### `go run` — скомпилировать и сразу запустить

```bash
go run .                  # запустить пакет main в текущем каталоге
go run ./cmd/server       # запустить конкретный пакет
go run main.go            # запустить один файл
```

Компилирует во временный каталог и выполняет, не оставляя бинаря. Удобно для прототипов и скриптов. В проде так не запускают — там собирают артефакт через `go build`.

### `go build` — собрать бинарь

```bash
go build ./...            # проверить, что всё компилируется (бинари не сохраняются для не-main)
go build -o bin/app ./cmd/server   # собрать исполняемый файл в bin/app
```

Для пакета `main` создаётся исполняемый файл; для библиотечных пакетов `go build` просто проверяет компиляцию. Полезные флаги: `-o` (имя выходного файла), `-race` (встроить детектор гонок данных), `-ldflags "-s -w"` (убрать таблицу символов и отладочную информацию — уменьшает размер бинаря), `-tags` (build-теги, см. ниже).

### `go install` — собрать и положить в `GOBIN`

```bash
go install ./cmd/mytool
go install golang.org/x/tools/cmd/goimports@latest   # поставить сторонний CLI-инструмент
```

Кладёт бинарь в `$GOBIN` (или `$GOPATH/bin`). Форма с `@version` — канонический способ устанавливать утилиты, написанные на Go, не добавляя их в зависимости проекта. Это замена устаревшего `go get` для бинарей.

### `go test` — тесты, бенчмарки

```bash
go test ./...                 # прогнать все тесты в модуле
go test -run TestParse ./...  # только тесты, чьё имя совпадает с регуляркой
go test -race ./...           # с детектором гонок
go test -cover ./...          # с покрытием
go test -bench=. ./...        # запустить бенчмарки
```

Тесты — это файлы `*_test.go` рядом с кодом. Подробно — в [./TESTING_GO.md](./TESTING_GO.md).

### `go vet` — статический анализ

```bash
go vet ./...
```

Встроенный линтер: ловит подозрительные конструкции, которые компилируются, но почти наверняка являются ошибкой — неправильные форматные строки `Printf`, копирование структур с мьютексом, недостижимый код, ошибки в struct-тегах. Запускается автоматически перед `go test`. Это не полноценный линтер (для строгого стиля берут `golangci-lint`), но базовая страховка.

### `gofmt` / `go fmt` — форматирование

```bash
gofmt -w .       # отформатировать все .go-файлы на месте
go fmt ./...     # то же через подкоманду go
```

В Go **единый канонический стиль форматирования**, встроенный в toolchain. Споров о расстановке скобок и отступов не бывает — `gofmt` приводит код к одному виду (табуляция для отступов, выравнивание полей структур). Это сознательное решение языка: форматирование не обсуждается. В Java/Kotlin аналог — внешние инструменты вроде `google-java-format` или `ktlint`, но в Go это часть платформы.

### `go doc` — документация из кода

```bash
go doc strings.Builder          # документация по типу
go doc net/http Server.Shutdown # по конкретному методу
```

Документация в Go — это обычные комментарии перед объявлением. `go doc` показывает их в терминале; `pkgsite` (бывший `godoc`) — в браузере. Никаких отдельных Javadoc-тегов: просто грамотный комментарий, начинающийся с имени сущности.

### `go generate` — запуск генераторов кода

```bash
go generate ./...
```

Ищет в исходниках директивы-комментарии вида `//go:generate <команда>` и выполняет их. Сам ничего не генерирует — это лишь стандартизированный способ запустить генераторы (например, `stringer` для перечислений или `mockgen` для моков). Запускается вручную, не во время сборки.

### `go clean` — очистка

```bash
go clean -cache       # очистить кэш сборки
go clean -modcache    # очистить кэш скачанных модулей (GOMODCACHE)
go clean -testcache   # сбросить кэш результатов тестов
```

## 4. Go-модули

### Что такое модуль

**Модуль** — это единица версионирования и распространения кода: дерево пакетов с общим корнем, в котором лежит файл `go.mod`. Модуль имеет имя (module path), обычно совпадающее с адресом репозитория, например `github.com/user/project`. По этому имени модуль импортируют другие.

Соотношение понятий:
- **Пакет** = один каталог с `.go`-файлами (единица компиляции и видимости).
- **Модуль** = дерево пакетов с одним `go.mod` (единица версионирования и зависимостей).

В терминах Maven: модуль ≈ артефакт (`groupId:artifactId`), а его версии ≈ теги в git.

### `go mod init`

Создание модуля:

```bash
go mod init github.com/user/project
```

Эта команда создаёт `go.mod`. Имя должно совпадать с будущим адресом репозитория — иначе другие не смогут его импортировать (Go резолвит зависимости прямо по URL, без центрального реестра вроде Maven Central).

### Файл `go.mod`

`go.mod` — манифест модуля. Минимальный пример и основные директивы:

```go
module github.com/user/project

go 1.23

require (
	github.com/google/uuid v1.6.0
	golang.org/x/sync v0.10.0
)

require (
	github.com/inconshreveable/mousetrap v1.1.0 // indirect
)

replace github.com/old/pkg => github.com/fork/pkg v1.2.3

exclude github.com/broken/dep v1.4.0

toolchain go1.23.4
```

| Директива | Назначение |
|---|---|
| `module` | имя (импорт-путь) модуля |
| `go` | минимальная версия языка/семантики, нужная модулю; влияет на поведение компилятора |
| `require` | прямые и транзитивные зависимости с версиями; `// indirect` — зависимость, не импортируемая напрямую вашим кодом |
| `replace` | подменить модуль другим (форком или локальным путём) — для отладки и временных фиксов |
| `exclude` | запретить конкретную версию зависимости (например, с известным багом) |
| `toolchain` | минимальная версия самого Go-toolchain; новее `go`-директивы, управляет автозагрузкой нужной версии Go |

`replace` особенно полезен для локальной разработки нескольких модулей сразу:

```go
replace github.com/user/lib => ../lib
```

Так модуль подключает соседний каталог вместо опубликованной версии — аналог Gradle `includeBuild` / composite builds.

### Файл `go.sum`

`go.sum` хранит криптографические хеши (контрольные суммы) каждого использованного модуля — отдельно для архива исходников и для самого `go.mod` зависимости:

```
github.com/google/uuid v1.6.0 h1:NIvaJDMOsjHA8n1jAhLSgzrAzy1Hgr+hNrb57e+94F0=
github.com/google/uuid v1.6.0/go.mod h1:TIyPZe4MgqvfeYDBFedMoGGpEw/LqOeaOT+nhxU+yHo=
```

При каждой сборке Go сверяет скачанное с этими хешами. Если содержимое версии изменилось (репозиторий подменили, MITM-атака) — сборка падает. Это защита целостности цепочки поставок, аналог lockfile с хешами. `go.sum` обязательно коммитят в репозиторий вместе с `go.mod`.

### Semantic import versioning (правило `/v2`)

Go применяет строгую трактовку семантического версионирования: **мажорная версия 2 и выше становится частью импорт-пути**. Модуль `github.com/user/lib` в версии `v2` импортируется как `github.com/user/lib/v2`:

```go
import "github.com/user/lib/v2"   // тянет именно v2.x.x
```

Зачем так. Мажорная версия по semver означает несовместимое изменение API. Делая `/v2` частью пути, Go позволяет двум мажорным версиям одного модуля **сосуществовать в одной сборке** — разные части зависимостей могут зависеть от `v1` и `v2` одновременно, и это не конфликт. В Maven такое решают через `groupId`/`artifactId` или shade/relocation; в Go это встроено в правило импорта. Версии `v0` и `v1` суффикса не требуют.

### MVS — Minimal Version Selection

Это сердце системы модулей и место, которое чаще всего удивляет приходящих из Maven/npm. **Minimal Version Selection (выбор минимальной версии)** — алгоритм, которым Go вычисляет, какую версию каждой зависимости использовать.

Правило: для каждого модуля берётся **наибольшая из минимально требуемых** версий по всему графу зависимостей.

Звучит парадоксально («наибольшая из минимальных»), поэтому разберём на примере. Пусть граф такой:
- ваш модуль требует `C >= v1.2.0` и зависимость `B`;
- `B` требует `C >= v1.4.0`.

MVS выбирает `C v1.4.0` — это максимум среди всех нижних границ (`v1.2.0` и `v1.4.0`). Не `v1.2.0` (тогда нарушится требование `B`) и **не последняя доступная** `v1.9.0`, даже если она существует.

Контраст с другими системами:
- **npm / «latest wins»**: по умолчанию подтягивается самая свежая версия, удовлетворяющая диапазону (`^1.2.0` → может стать `1.9.0`). Сборки невоспроизводимы во времени: вышла новая минорная — поведение изменилось.
- **Maven «nearest wins»**: при конфликте выбирается версия, ближайшая к корню дерева зависимостей. Результат зависит от порядка и глубины и тоже не всегда интуитивен.
- **Go MVS**: выбирается минимальная версия, которой достаточно всем. Результат **детерминирован и воспроизводим** без lockfile — он однозначно вычисляется из набора `go.mod`. Версия повышается только тогда, когда кто-то явно поднял нижнюю границу в своём `go.mod`. Это «high-fidelity builds»: сегодняшняя и завтрашняя сборка одинаковы, пока не тронули `go.mod`.

Практическое следствие: «свежую» версию вы получаете не сами по себе, а только когда осознанно выполнили `go get pkg@latest`. Это делает обновления явными и контролируемыми.

## 5. Управление зависимостями

### `go get` — добавить/обновить зависимость

```bash
go get github.com/google/uuid@v1.6.0   # конкретная версия
go get github.com/google/uuid@latest    # последняя
go get github.com/google/uuid@none      # удалить
go get -u ./...                          # обновить все до последних минорных/патч
```

`go get` правит `go.mod`/`go.sum` и скачивает модуль в кэш. Важно: начиная с Go 1.16, `go get` **больше не ставит исполняемые файлы** — для установки CLI-утилит используется `go install tool@version` (см. раздел 3).

### `go mod tidy` — привести зависимости в порядок

```bash
go mod tidy
```

Сканирует все импорты в коде и приводит `go.mod`/`go.sum` к точному соответствию: добавляет недостающие зависимости, удаляет неиспользуемые, расставляет пометки `// indirect`. Это команда, которую запускают после правок импортов и перед коммитом. Аналога-кнопки в Maven нет — там лишние зависимости нужно вычищать вручную.

### Остальные команды модулей

```bash
go mod download        # скачать все зависимости из go.mod в кэш (не меняя go.mod)
go mod verify          # проверить, что кэш модулей не подделан (сверка с go.sum)
go mod graph           # вывести полный граф зависимостей (рёбра module@ver -> module@ver)
go mod why github.com/x/y   # объяснить, зачем в сборке нужен этот модуль
```

`go mod download` часто используют в Docker — отдельным слоем, чтобы закэшировать зависимости до копирования исходников:

```bash
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go build -o /app ./cmd/server
```

### Вендоринг

```bash
go mod vendor
```

Создаёт каталог `vendor/` с копиями исходников всех зависимостей прямо в репозитории. Если `vendor/` присутствует, Go по умолчанию собирает из него, игнорируя кэш и сеть (`-mod=vendor`). Зачем это нужно: воспроизводимость сборок без доступа в сеть, аудит зависимостей в одном месте, защита от исчезновения внешнего репозитория. Минус — раздувает репозиторий. В современных проектах вендоринг применяют реже (кэш + `go.sum` дают воспроизводимость), но он жив в корпоративной среде и в самом исходнике Go.

### Переменные окружения для зависимостей

| Переменная | Назначение |
|---|---|
| `GOFLAGS` | флаги, добавляемые ко всем командам `go` (например, `-mod=readonly`) |
| `GOPROXY` | прокси для скачивания модулей; по умолчанию `https://proxy.golang.org,direct` |
| `GOSUMDB` | сервер проверки контрольных сумм (`sum.golang.org`) — глобальный журнал хешей, защита от подмены версий |
| `GOPRIVATE` | список путей (с шаблонами), которые качать напрямую из репозитория, минуя прокси и `GOSUMDB` |
| `GONOSUMCHECK` / `GONOSUMDB` | обе удалены. Отключить сверку по базе сумм — `GOSUMDB=off`; исключить пути из проверок sumdb/прокси — `GOPRIVATE`; разрешить незащищённый транспорт (HTTP) — `GOINSECURE` (три разных механизма) |

`GOPROXY` — это публичный кэширующий прокси модулей, поддерживаемый командой Go. Он ускоряет скачивание и сохраняет версии, даже если оригинальный репозиторий удалён. `GOSUMDB` — глобальный прозрачный журнал (Transparency Log) контрольных сумм: гарантирует, что все в мире видят одинаковый хеш для данной версии модуля.

Для приватных репозиториев (корпоративный GitLab) типичная настройка:

```bash
go env -w GOPRIVATE=git.company.com,github.com/company/*
```

Так Go качает эти модули напрямую по git, не светит их пути в публичном прокси и не пытается проверить их в публичном `GOSUMDB`.

## 6. `go.work` — workspace из нескольких модулей

Когда нужно одновременно разрабатывать **несколько связанных модулей** (например, библиотеку и приложение, которое её использует), правки в библиотеке хочется видеть в приложении сразу, без публикации версии и без ручного `replace` в `go.mod`. Для этого есть режим workspace (Go 1.18+).

```bash
go work init ./app ./lib       # создать go.work, включив два модуля
go work use ./another-module   # добавить ещё один
```

Создаётся файл `go.work` в общем родительском каталоге:

```go
go 1.23

use (
	./app
	./lib
)
```

Пока `go.work` действует, Go при сборке резолвит импорты этих модулей из локальных каталогов, а не из опубликованных версий. Преимущество перед `replace`: `go.work` **не коммитят** в репозиторий (его добавляют в `.gitignore`), поэтому он не влияет на потребителей и не засоряет `go.mod` временными правками. Это аналог Gradle composite build / `includeBuild`, но на уровне локальной среды разработчика.

## 7. Структура проекта

### Пакет = директория

В Go **один каталог — это ровно один пакет**. Все `.go`-файлы в каталоге обязаны иметь одинаковую директиву `package` в первой строке. Имя пакета по соглашению короткое, в нижнем регистре, без подчёркиваний (`http`, `json`, `user`), и обычно совпадает с именем каталога.

```go
// файл user/service.go
package user

func NewService() *Service { /* ... */ }
```

Импортируется по полному пути от корня модуля:

```go
import "github.com/user/project/user"   // путь-импорта
// обращение: user.NewService()         // имя-пакета (последний сегмент)
```

Видимость управляется **регистром первой буквы идентификатора**: с заглавной — экспортируется (виден из других пакетов), со строчной — приватен для пакета. Никаких `public`/`private` ключевых слов. `NewService` экспортируется, `newHelper` — нет.

### Пакет `main`

Исполняемая программа — это пакет с именем `main` и функцией `func main()`. Только сборка такого пакета даёт исполняемый файл; всё остальное — библиотеки.

```go
package main

func main() { /* точка входа */ }
```

### Конвенции каталогов

Go не навязывает раскладку каталогов жёстко (как Maven `src/main/java`), но в сообществе сложились соглашения:

| Каталог | Смысл | Статус |
|---|---|---|
| `cmd/<app>/` | пакеты `main` — по одному подкаталогу на каждый исполняемый файл | широко принят |
| `internal/` | пакеты, импортируемые только внутри этого модуля | **правило компилятора** |
| `pkg/` | «публичные» библиотечные пакеты, предназначенные для импорта извне | спорный |

**`internal/` — единственная конвенция, которую обеспечивает компилятор.** Пакет внутри `internal/` (на любой глубине) можно импортировать только из кода, чей путь имеет того же родителя, что и каталог `internal/`. Пример: `github.com/user/project/internal/auth` доступен из любого пакета под `github.com/user/project/...`, но недоступен из чужого модуля. Это языковой механизм инкапсуляции на уровне модуля — аналог «package-private», но для целого поддерева.

```
project/
├── go.mod
├── cmd/
│   └── server/
│       └── main.go          // package main
├── internal/
│   └── auth/
│       └── token.go         // виден только внутри project/...
└── user/
    └── service.go           // package user, экспортируемый наружу
```

**`pkg/` — спорная конвенция.** Идея — складывать туда код, предназначенный для внешнего использования. Критика: каталог не даёт ничего, чего не даёт сам модуль (любой неэкспортируемый-в-`internal` пакет и так публичен), добавляет лишний уровень вложенности в импорт-пути и не является официальной рекомендацией. Многие проекты (включая исходники самого Go) обходятся без `pkg/`, кладя пакеты прямо в корень модуля. Использовать его или нет — вопрос вкуса команды.

### Build constraints / build tags (кратко)

Иногда файл нужно компилировать только под определённую платформу или конфигурацию. Для этого есть два механизма:

```go
//go:build linux && amd64

package mypkg
```

Директива `//go:build` (вверху файла, до `package`) — условие компиляции: этот файл войдёт в сборку только при выполнении условия (ОС, архитектура, произвольный тег). Произвольные теги включаются флагом `go build -tags integration`. Дополнительно работает соглашение по именам файлов: `file_linux.go`, `file_amd64.go`, `file_windows_arm64.go` автоматически собираются только под соответствующую платформу — без всякой директивы. Это родной способ платформенно-зависимого кода (в Java аналогов на уровне компиляции нет — там это решают в рантайме).

## 8. Краткая эволюция: GOPATH → vgo → modules

Понимать историю полезно, потому что в старых статьях и проектах ещё встречается GOPATH-стиль.

**Эпоха GOPATH (до Go 1.11).** Весь код обязан был лежать внутри единственного каталога `$GOPATH/src`, а импорт-путь жёстко выводился из физического расположения: репозиторий `github.com/user/project` лежал ровно в `$GOPATH/src/github.com/user/project`. Проблемы были фундаментальные:
- **нет версионирования** — `go get` всегда тянул последний коммит из ветки по умолчанию; воспроизводимости сборок не было;
- **один глобальный namespace** — нельзя держать две версии одной библиотеки;
- **жёсткая привязка к каталогу** — проект нельзя было разместить где угодно на диске.

Версии прибивали внешними инструментами (`dep`, `glide`, `godep`), но единого стандарта не было.

**vgo (2018).** Russ Cox опубликовал серию предложений «vgo» (versioned Go), где и был представлен подход с `go.mod`, semantic import versioning и алгоритмом MVS. Это прототип будущей системы модулей.

**Go modules (1.11+, по умолчанию с 1.16).** Идеи vgo вошли в toolchain как `go mod`. Привязка к `$GOPATH` исчезла: проект живёт в любом каталоге, версии фиксируются в `go.mod`/`go.sum`, разные мажорные версии сосуществуют. Начиная с Go 1.16 модульный режим включён по умолчанию, а GOPATH-режим фактически выведен из эксплуатации. От `GOPATH` отказались, потому что глобальный каталог без версий не масштабировался на реальную экосистему: невозможны воспроизводимые сборки, нет сосуществования версий, неудобно для CI и монорепозиториев.

## 9. Полный пример и типичный цикл работы

Пример реального `go.mod` небольшого сервиса:

```go
module github.com/acme/orders

go 1.23

require (
	github.com/google/uuid v1.6.0
	github.com/jackc/pgx/v5 v5.7.1
	golang.org/x/sync v0.10.0
)

require (
	github.com/jackc/pgpassfile v1.0.0 // indirect
	github.com/jackc/puddle/v2 v2.2.2 // indirect
	golang.org/x/crypto v0.31.0 // indirect
	golang.org/x/text v0.21.0 // indirect
)
```

Обратите внимание: `pgx/v5` — мажорная версия 5 прямо в импорт-пути (semantic import versioning), а блок с `// indirect` — транзитивные зависимости, подтянутые библиотеками.

Типичный рабочий цикл:

```bash
# 1. Создать модуль
go mod init github.com/acme/orders

# 2. Написать код, добавить импорт сторонней библиотеки в .go-файле,
#    затем синхронизировать go.mod/go.sum
go mod tidy

# 3. Отформатировать и проверить
gofmt -w .
go vet ./...

# 4. Прогнать тесты (с детектором гонок)
go test -race ./...

# 5. Собрать бинарь под целевую платформу
GOOS=linux GOARCH=amd64 go build -o bin/orders ./cmd/orders

# 6. Обновить конкретную зависимость, когда нужно осознанно
go get github.com/google/uuid@latest
go mod tidy
```

Весь цикл — одна утилита `go`, без внешних плагинов и конфигурационного DSL. Это и есть основное впечатление, которое стоит унести: инструментарий Go минималистичен и единообразен.

## Шпаргалка

```bash
# Модуль
go mod init github.com/user/project   # создать go.mod
go mod tidy                           # синхронизировать зависимости с импортами
go mod download                       # скачать зависимости в кэш
go mod verify                         # проверить целостность кэша по go.sum
go mod why pkg                        # зачем нужна зависимость
go mod vendor                         # сложить зависимости в ./vendor

# Зависимости
go get pkg@v1.2.3                     # добавить/зафиксировать версию
go get pkg@latest                     # обновить до последней
go get pkg@none                       # удалить
go install tool@latest                # поставить CLI-инструмент в GOBIN

# Сборка / запуск / тесты
go run ./cmd/app                      # скомпилировать и выполнить
go build -o bin/app ./cmd/app         # собрать бинарь
go test -race -cover ./...            # тесты с гонками и покрытием
go vet ./...                          # статический анализ
gofmt -w .                            # форматирование

# Окружение / кросс-компиляция
go env GOPATH GOMODCACHE              # посмотреть переменные
go env -w GOPRIVATE=git.company.com/* # настроить приватные модули
GOOS=linux GOARCH=arm64 go build ./...# собрать под другую платформу

# Workspace
go work init ./app ./lib              # создать go.work для нескольких модулей
```
