# Go — Паттерны конкурентности

> Каналы и `select` дают примитивы; настоящая работа — собрать из них **надёжные паттерны**: конвейеры, пулы воркеров, ограничение параллелизма, корректную отмену. В этом файле — типовые конструкции, библиотека `sync`, `context.Context` и `errgroup`. Базовый синтаксис каналов и `select` здесь **не** переобъясняется — он в [GOROUTINES_CHANNELS](./GOROUTINES_CHANNELS.md). Гарантии видимости памяти (happens-before, детектор гонок) — в [MEMORY_GC](./MEMORY_GC.md).

Для разработчика из Java/Kotlin ключевой сдвиг: в Go нет встроенной структурированной конкурентности (как `coroutineScope` в Kotlin или `StructuredTaskScope` в Java). Дерево горутин **не** формируется автоматически — родитель не ждёт детей и не отменяет их при ошибке, если вы не построили это руками. Дисциплину обеспечивают три вещи: **канал отмены**, **`context.Context`** и **`sync.WaitGroup`**. Их и собираем.

Девиз сообщества (Rob Pike): «Не общайтесь, разделяя память; разделяйте память, общаясь». То есть передавайте данные **через каналы**, а не защищайте общий объект мьютексом — там, где это удобно. Но мьютекс не запрещён: для защиты счётчика или поля структуры он зачастую проще и быстрее канала.

## 1. Паттерны на каналах

### 1.1 Generator — функция, возвращающая канал

Горутина-источник пишет значения в канал и закрывает его, когда поток исчерпан. Вызывающий читает через `range`.

```go
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)           // закрывает ТОТ, кто пишет
        for _, n := range nums {
            out <- n
        }
    }()
    return out                     // возвращаем receive-only канал
}

for v := range gen(1, 2, 3) {
    fmt.Println(v)
}
```

Тип `<-chan int` в сигнатуре — receive-only: вызывающий физически не сможет писать в канал или закрыть его. Это документирует направление потока на уровне типов (аналога в Java нет).

### 1.2 Pipeline — стадии, соединённые каналами

Каждая стадия — функция, принимающая входной канал и возвращающая выходной. Стадии работают параллельно, данные текут сквозь них.

```go
func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            out <- n * n
        }
    }()
    return out
}

// Сборка конвейера: gen -> square -> square
for v := range square(square(gen(2, 3))) {
    fmt.Println(v)                 // 16, 81
}
```

Правило: **закрывает канал тот, кто в него пишет**, и закрывает ровно один раз. Получатель никогда не закрывает входной канал — иначе писатель упадёт с паникой «send on closed channel».

### 1.3 Fan-out / fan-in

**Fan-out (веерное распределение, fan-out)** — несколько горутин читают из одного канала, распараллеливая обработку. **Fan-in** — слияние нескольких выходных каналов в один.

```go
// fan-in: слить несколько каналов в один
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(cs))
    for _, c := range cs {
        go func(c <-chan int) {    // в Go <1.22 параметр обязателен (см. ниже)
            defer wg.Done()
            for v := range c {
                out <- v
            }
        }(c)
    }
    go func() {
        wg.Wait()                  // дождаться всех читателей
        close(out)                 // и только потом закрыть слитый канал
    }()
    return out
}

in := gen(1, 2, 3, 4, 5)
c1, c2 := square(in), square(in)   // fan-out: два воркера на одном in
for v := range merge(c1, c2) {     // fan-in
    fmt.Println(v)
}
```

`WaitGroup` нужен именно для того, чтобы закрыть `out` **после** того, как все читатели дочитали свои каналы, и ни на такт раньше.

### 1.4 Worker pool — ограничение параллелизма

Запускаем фиксированное число воркеров; они разбирают задания из общего канала `jobs` и пишут в `results`. Так число одновременно работающих горутин ограничено сверху — в отличие от наивного «горутина на каждое задание».

```go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs {          // выходит, когда jobs закрыт и опустошён
        results <- j * 2
    }
}

func main() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)

    var wg sync.WaitGroup
    for w := 1; w <= 3; w++ {      // ровно 3 воркера
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            worker(id, jobs, results)
        }(w)
    }

    for j := 1; j <= 9; j++ {
        jobs <- j
    }
    close(jobs)                    // сигнал воркерам: заданий больше не будет

    go func() {
        wg.Wait()                  // когда все воркеры вышли —
        close(results)             // закрыть results, чтобы range ниже завершился
    }()

    for r := range results {
        fmt.Println(r)
    }
}
```

Параллель с Java: это ровно `ThreadPoolExecutor` с фиксированным размером пула и ограниченной очередью. Только пул здесь не объект-исполнитель, а набор одинаковых горутин, читающих из одного канала; «очередь задач» — буфер канала `jobs`.

### 1.5 Bounded parallelism через семафор-канал

Когда заводить полноценный пул лень, а ограничить параллелизм нужно — используют **буферизованный канал как счётный семафор**. Запись в него занимает «слот», чтение — освобождает.

```go
sem := make(chan struct{}, 4)      // максимум 4 одновременно

var wg sync.WaitGroup
for _, item := range items {
    wg.Add(1)
    go func(item Item) {
        defer wg.Done()
        sem <- struct{}{}          // занять слот (блокируется, если все 4 заняты)
        defer func() { <-sem }()   // освободить слот по выходе
        process(item)
    }(item)
}
wg.Wait()
```

`struct{}` — пустая структура, занимает **0 байт**: каналу-семафору важен сам факт передачи, не значение. Это идиоматичный «сигнальный» тип в Go (аналог `Semaphore` из `java.util.concurrent`, но без отдельного объекта).

### 1.6 Done-канал и плавная остановка

Закрытый канал даёт особое свойство: **любое** чтение из закрытого канала немедленно возвращает нулевое значение, не блокируясь. Это превращает закрытие канала в широковещательный сигнал «всем стоп» для произвольного числа слушателей.

```go
func worker(done <-chan struct{}, jobs <-chan int) {
    for {
        select {
        case <-done:               // канал закрыт -> мгновенно сюда, выходим
            return
        case j, ok := <-jobs:
            if !ok {
                return             // jobs закрыт и пуст
            }
            process(j)
        }
    }
}

done := make(chan struct{})
// ... запустили N воркеров с этим done ...
close(done)                        // один close останавливает всех слушателей
```

На практике этот «голый» done-канал почти всегда заменяют на `context.Context` (раздел 2): он несёт тот же сигнал отмены плюс дедлайн и значения, и распространяется по дереву вызовов стандартным образом.

### 1.7 Poison pill — сигнал завершения через сам канал

Альтернатива отдельному done-каналу: послать в рабочий канал специальное значение-«пилюлю», увидев которое воркер завершается. В Go идиоматичнее **закрыть** канал заданий (`range`/`comma-ok` сами увидят закрытие), но poison pill применяют, когда нужно остановить **конкретное** число воркеров адресно или когда у канала несколько писателей и закрыть его безопасно нельзя (закрыть канал имеет право только один владелец-писатель).

```go
// closeпредпочтительнее; poison pill — когда close недоступен
const stop = -1
for i := 0; i < numWorkers; i++ {
    jobs <- stop                   // по одной «пилюле» на каждого воркера
}
```

## 2. `context.Context` — отмена, дедлайны, значения

`context.Context` — стандартный механизм передать вниз по дереву вызовов три вещи: **сигнал отмены**, **дедлайн/таймаут** и набор **значений уровня запроса** (request-scoped). Это «нервная система» отмены в Go: канал из раздела 1.6, обёрнутый в стандартный интерфейс плюс дедлайн.

Интерфейс (упрощённо):

```go
type Context interface {
    Done() <-chan struct{}         // канал, закрывающийся при отмене/дедлайне
    Err() error                    // почему отменён: nil, Canceled или DeadlineExceeded
    Deadline() (time.Time, bool)   // дедлайн, если задан
    Value(key any) any             // значение по ключу
}
```

### 2.1 Корни и производные контексты

| Конструктор | Назначение |
|---|---|
| `context.Background()` | корень дерева: в `main`, инициализации, тестах |
| `context.TODO()` | заглушка, когда контекст ещё не прокинут (помечает «надо доделать») |
| `context.WithCancel(parent)` | даёт `ctx` + функцию `cancel()` для ручной отмены |
| `context.WithTimeout(parent, d)` | отмена через длительность `d` |
| `context.WithDeadline(parent, t)` | отмена в момент времени `t` |
| `context.WithValue(parent, k, v)` | производный контекст с парой ключ-значение |

`WithCancel`/`WithTimeout`/`WithDeadline` возвращают **два** значения — контекст и `cancel func()`. Вызов `cancel` отменяет контекст и **освобождает связанные ресурсы** (таймер, горутину-наблюдатель). Его нужно вызвать всегда — даже если контекст отменился сам по дедлайну, поэтому идиома — `defer cancel()` сразу после создания.

```go
func fetchAll(ctx context.Context, urls []string) error {
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()                 // обязательно: иначе утечёт таймер/горутина
    // ... используем ctx в дочерних вызовах ...
    return nil
}
```

### 2.2 Реакция на отмену

Функция, выполняющая долгую работу, периодически смотрит на `ctx.Done()` через `select`:

```go
func work(ctx context.Context, jobs <-chan Job) error {
    for {
        select {
        case <-ctx.Done():         // отменён или вышел дедлайн
            return ctx.Err()       // вернуть причину (Canceled / DeadlineExceeded)
        case j, ok := <-jobs:
            if !ok {
                return nil
            }
            handle(j)
        }
    }
}
```

`ctx.Err()` возвращает:
- `nil` — пока не отменён;
- `context.Canceled` — кто-то вызвал `cancel()`;
- `context.DeadlineExceeded` — истёк дедлайн/таймаут.

### 2.3 Распространение отмены вниз по дереву

Отмена родительского контекста **каскадом** отменяет все производные от него. Это и есть аналог распространения отмены в structured concurrency — но в Go его надо **протянуть руками**, передавая `ctx` первым аргументом в каждый вызов:

```go
ctx, cancel := context.WithCancel(context.Background())
child, _ := context.WithTimeout(ctx, time.Minute)
// cancel() отменит и ctx, и child одновременно.
```

Отмена идёт только **сверху вниз** (родитель → дети). Отменить родителя из ребёнка нельзя — у ребёнка нет `cancel` родителя. Это прямой аналог семантики Kotlin: см. [STRUCTURED_CONCURRENCY](../../kotlin-coroutines/theory/STRUCTURED_CONCURRENCY.md) — там отмена scope тоже распространяется только к потомкам.

### 2.4 Правила работы с context

Соглашения, закреплённые в стандартной библиотеке и линтерах:

1. **Контекст — первый аргумент** функции, с именем `ctx`: `func Do(ctx context.Context, arg T) error`.
2. **Не хранить контекст в полях структуры** — передавать явным аргументом. Контекст привязан к одному вызову/запросу, а структура живёт дольше; спрятав его в поле, вы теряете контроль над временем жизни.
3. **Не передавать `nil`-контекст.** Если не знаете, какой передать, — `context.TODO()`.
4. **`defer cancel()`** сразу после `WithCancel`/`WithTimeout`/`WithDeadline`, даже если кажется, что отмена не нужна: иначе утечёт таймер и горутина-наблюдатель.

### 2.5 Антипаттерн: `context.Value` для обязательных параметров

`WithValue` предназначен для **request-scoped** служебных данных, проходящих сквозь много слоёв: trace ID, ID запроса, данные авторизации. Это **не** замена обычным аргументам функции.

```go
// ❌ Плохо: обязательный параметр спрятан в контекст
func process(ctx context.Context) {
    userID := ctx.Value("userID").(string)  // не виден в сигнатуре, паника при отсутствии
}

// ✅ Хорошо: обязательное — явным аргументом
func process(ctx context.Context, userID string) { ... }
```

Проблемы `Value` для бизнес-параметров: значение не видно в сигнатуре, тип не проверяется компилятором (`any` + приведение), легко получить `nil` и панику. Через `Value` передают только то, что действительно «сквозное» и опциональное. Для ключей используют **неэкспортируемый собственный тип**, а не строку, — чтобы исключить коллизии между пакетами:

```go
type ctxKey int
const userKey ctxKey = 0
ctx = context.WithValue(ctx, userKey, user)
```

## 3. Пакет `sync`

Когда передача через каналы избыточна — общую память защищают примитивами `sync`. Это прямые аналоги `java.util.concurrent`, но с важными отличиями (не реентерабельны, нельзя копировать).

### 3.1 `WaitGroup` — дождаться группы горутин

Счётчик: `Add(n)` увеличивает, `Done()` уменьшает на 1, `Wait()` блокирует до нуля. Прямой аналог `CountDownLatch`, но счётчик можно наращивать динамически.

```go
var wg sync.WaitGroup
for _, item := range items {
    wg.Add(1)                      // ДО запуска горутины, не внутри неё
    go func(item Item) {
        defer wg.Done()            // гарантированно даже при панике в process
        process(item)
    }(item)
}
wg.Wait()                          // ждём, пока все Done
```

Ловушки `WaitGroup`:

- **`Add` вызывают до `go`, а не внутри горутины.** Если сделать `Add(1)` первой строкой внутри горутины, `Wait()` может проскочить до того, как горутина успеет стартовать и увеличить счётчик, — гонка.
- **`Done` ставят через `defer`** — иначе паника в теле оставит счётчик ненулевым навсегда, и `Wait()` зависнет.
- **`WaitGroup` нельзя копировать** после первого использования (внутри лежит счётчик-указатель). Передавайте по указателю (`*sync.WaitGroup`) или захватывайте через замыкание. `go vet` это ловит.
- Уход счётчика **ниже нуля** (`Done` больше, чем `Add`) — паника.

В Go 1.25+ есть метод `WaitGroup.Go(f)`, который сам делает `Add(1)`/`Done` вокруг `f`, — но классическая ручная схема выше встречается повсеместно.

### 3.2 `Mutex` и `RWMutex`

`sync.Mutex` — взаимное исключение; `sync.RWMutex` — много читателей **или** один писатель (аналоги `ReentrantLock` и `ReentrantReadWriteLock`).

```go
type Counter struct {
    mu sync.Mutex                  // мьютекс — поле рядом с защищаемыми данными
    n  int
}
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()            // defer гарантирует разблокировку при панике
    c.n++
}
```

Критические отличия от Java:

- **Не реентерабельны.** Повторный `Lock()` тем же владельцем — **дедлок** (Go-горутины не имеют идентичности владельца). В Java `synchronized`/`ReentrantLock` пускают тот же поток повторно — в Go этого нет.
- **Нельзя копировать после использования.** `Mutex` внутри несёт состояние; копия структуры со взятым мьютексом ведёт к двум независимым «половинкам» лока. Поэтому методы, берущие лок, объявляют на **указателе-получателе** (`func (c *Counter)`), а структуры с мьютексом не передают по значению. `go vet` ловит копирование.
- `RWMutex`: `RLock`/`RUnlock` для читателей, `Lock`/`Unlock` для писателя. Выгоден при сильном перекосе в сторону чтения; иначе обычный `Mutex` проще и не медленнее.

### 3.3 `Once` — ленивая инициализация

`sync.Once.Do(f)` гарантирует, что `f` выполнится **ровно один раз** за всё время жизни программы, даже при гонке множества горутин. Аналог потокобезопасной ленивой инициализации (как holder-идиома или double-checked locking в Java, но без ручного кода).

```go
var (
    once     sync.Once
    instance *Service
)
func GetService() *Service {
    once.Do(func() {
        instance = newService()    // выполнится один раз; остальные подождут здесь
    })
    return instance
}
```

В Go 1.21+ есть удобные `sync.OnceFunc`, `OnceValue`, `OnceValues`.

### 3.4 `Cond` — условная переменная (кратко)

`sync.Cond` — условная переменная поверх мьютекса: горутины ждут (`Wait`), пока не выполнится условие, другая горутина будит их (`Signal`/`Broadcast`). Аналог `Object.wait/notify` или `Condition`. На практике в Go применяется **редко** — каналы выразительнее для большинства задач «дождаться события». `Cond` уместен в узком классе задач (например, ограниченный буфер с пробуждением многих ожидающих), когда канал неудобен. `Wait` всегда вызывают в цикле, перепроверяя условие (как и в Java — из-за spurious wakeups).

### 3.5 `sync.Map` — когда уместна

`sync.Map` — потокобезопасная map, **но не универсальная замена** обычной `map` под мьютексом. Внутри оптимизирована под два сценария:

1. ключ пишется один раз, читается много раз (cache, заполняемый редко);
2. множества ключей у разных горутин **не пересекаются**.

Для общего случая «частые записи в пересекающиеся ключи» обычная `map[K]V` + `sync.RWMutex` **быстрее и понятнее**. Правило выбора:

| Сценарий | Что брать |
|---|---|
| Read-heavy, ключи пишутся редко | `sync.Map` |
| Непересекающиеся наборы ключей по горутинам | `sync.Map` |
| Частые записи, общий набор ключей | `map` + `RWMutex` |
| Нужны типобезопасность и понятность | `map` + `Mutex` (с дженериками — типобезопасно) |

`sync.Map` не типизирована (ключи/значения — `any`), что в эпоху дженериков лишний минус для общего случая.

### 3.6 `sync.Pool` — пул переиспользуемых объектов

`sync.Pool` снижает нагрузку на GC, переиспользуя короткоживущие объекты (например, буферы). Это тема производительности — детали в [PERFORMANCE_PROFILING](./PERFORMANCE_PROFILING.md). Коротко: `Get` берёт объект из пула (или создаёт через `New`), `Put` возвращает; GC может очистить пул в любой момент, поэтому хранить в нём состояние нельзя.

## 4. `sync/atomic` — атомарные операции

`sync/atomic` даёт атомарные операции над числами и указателями **без мьютекса** — на уровне аппаратных инструкций (CAS, Compare-And-Swap). Прямой аналог `AtomicInteger`/`AtomicReference` из Java.

Современный (с Go 1.19) типобезопасный API — типы-обёртки:

```go
var ops atomic.Int64               // не копировать после использования

ops.Add(1)                         // атомарный инкремент, возвращает новое значение
v := ops.Load()                    // атомарное чтение
ops.Store(42)                      // атомарная запись
ok := ops.CompareAndSwap(42, 100)  // CAS: если значение == 42, заменить на 100
```

Доступны `atomic.Int32/Int64/Uint32/Uint64/Bool/Pointer[T]/Value`. Низкоуровневые функции (`atomic.AddInt64(&x, 1)` и т.п.) остаются, но типы-обёртки безопаснее: их нельзя случайно прочитать неатомарно.

### Atomic vs mutex — когда что

| Критерий | `atomic` | `Mutex` |
|---|---|---|
| Защищаемое | одно число/указатель/флаг | группа полей, инвариант между ними |
| Операция | одна (инкремент, swap, флаг) | составная (несколько связанных полей) |
| Стоимость | дешевле (без блокировки) | дороже, но универсальнее |
| Читаемость составной логики | плохо (легко ошибиться) | хорошо |

Правило: **одно** значение, **одна** атомарная операция (счётчик запросов, флаг готовности, последний ID) — `atomic`. Как только нужно согласованно изменить **несколько** полей или поддержать инвариант между ними — `Mutex`. Попытка собрать сложную логику из нескольких CAS — частый источник едва уловимых гонок (плюс классическая [ABA problem](../../concurrency/theory/ATOMIC_CAS.md)). Подробнее о CAS и lock-free — в модуле concurrency.

## 5. `errgroup` — структурированная группа с ошибкой и отменой

`golang.org/x/sync/errgroup` (официальный, но вне стандартной библиотеки) — то, чего не хватает «голому» `WaitGroup`: он **собирает первую ошибку** и **отменяет общий контекст** при сбое любого участника. Это ближайший к structured concurrency инструмент в Go.

```go
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, urls []string) ([]Result, error) {
    g, ctx := errgroup.WithContext(ctx)   // ctx отменится при первой ошибке
    results := make([]Result, len(urls))
    for i, url := range urls {
        i, url := i, url                  // в Go <1.22 — обязательная перепривязка
        g.Go(func() error {               // запускает горутину, копит ошибку
            r, err := fetch(ctx, url)
            if err != nil {
                return err                // первая ошибка -> отмена общего ctx
            }
            results[i] = r
            return nil
        })
    }
    if err := g.Wait(); err != nil {      // ждёт всех, возвращает первую ошибку
        return nil, err
    }
    return results, nil
}
```

Поведение:
- `g.Go(f)` запускает `f` в горутине и перехватывает её возврат-ошибку.
- При **первой** не-`nil` ошибке `errgroup` отменяет производный `ctx` (если создан через `WithContext`) — остальные горутины, которые слушают `ctx.Done()`, останавливаются.
- `g.Wait()` блокирует до завершения всех и возвращает **первую** возникшую ошибку (последующие отбрасываются).
- `g.SetLimit(n)` ограничивает число одновременно работающих горутин — встроенный bounded parallelism.

### Сравнение со structured concurrency Kotlin

| Свойство | Kotlin `coroutineScope` | Go `errgroup.WithContext` |
|---|---|---|
| Дождаться всех детей | автоматически (выход из scope) | `g.Wait()` явно |
| Отмена при ошибке одного | автоматически (fail-fast) | отменяет `ctx`, но дети **сами** обязаны слушать `ctx.Done()` |
| Распространение отмены сверху | автоматически по дереву Job | вручную: передать `ctx` в каждый вызов |
| Тип результата | возврат из лямбды | через внешние переменные/слайс |
| Поглощение лишних ошибок | первая ломает scope | возвращается только первая |

Главное отличие: в Kotlin отмена ребёнка происходит **на любой suspension point** автоматически, а в Go горутина прервётся, **только если сама проверяет** `ctx.Done()`. `errgroup` отменяет контекст — но не может насильно остановить горутину, игнорирующую отмену (в Go нет принудительного прерывания горутин, как нет `Thread.stop`). Сравните с [STRUCTURED_CONCURRENCY](../../kotlin-coroutines/theory/STRUCTURED_CONCURRENCY.md): кооперативность отмены — общая идея, но в Kotlin она встроена в runtime, а в Go держится на дисциплине проверок.

## 6. Rate limiting — ограничение частоты

### 6.1 `time.Ticker`

`time.Ticker` шлёт значение в канал через равные интервалы — простейший способ задать темп.

```go
ticker := time.NewTicker(200 * time.Millisecond)
defer ticker.Stop()               // обязательно: иначе утечёт таймер

for req := range requests {
    <-ticker.C                     // ждём очередной «тик» — не чаще 5 раз/с
    handle(req)
}
```

`Stop()` обязателен — незакрытый `Ticker` держит ресурсы и не собирается GC.

### 6.2 Token bucket на канале

Алгоритм **token bucket** (корзина токенов): в буферизованный канал-«корзину» с заданной частотой подкладывают токены; обработка запроса требует забрать токен. Канал ёмкости `N` даёт «бёрст» до `N` запросов, а фоновый `Ticker` пополняет токены с нужной частотой.

```go
tokens := make(chan struct{}, burst)   // ёмкость = максимальный всплеск
for i := 0; i < burst; i++ {
    tokens <- struct{}{}               // начальная заправка
}
go func() {
    t := time.NewTicker(rate)
    defer t.Stop()
    for range t.C {
        select {
        case tokens <- struct{}{}:     // подложить токен
        default:                       // корзина полна — пропустить тик
        }
    }
}()

// перед обработкой:
<-tokens                               // забрать токен (ждёт, если корзина пуста)
handle(req)
```

### 6.3 `golang.org/x/time/rate`

Для продакшена обычно не пишут token bucket руками, а берут готовый `golang.org/x/time/rate` — это и есть промышленная реализация token bucket с методами `Allow()` (неблокирующая проверка), `Wait(ctx)` (блокирует до доступного токена, уважает отмену контекста) и `Reserve()`. Достаточно знать, что **алгоритм под капотом — token bucket**, и что `Wait` интегрирован с `context`.

## 7. Частые ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| Захват переменной цикла в горутине (Go < 1.22) | все горутины видят последнее значение | передать параметром `go func(x){...}(x)` или `x := x`; в Go 1.22+ исправлено семантикой цикла |
| Забыт `defer cancel()` | утечка таймера и горутины-наблюдателя контекста | всегда `defer cancel()` после `WithCancel/WithTimeout/WithDeadline` |
| Копирование `WaitGroup`/`Mutex` | две «половинки» примитива, гонки/дедлоки | передавать по указателю; `go vet` ловит |
| `Add` внутри горутины | `Wait()` проскакивает до старта | `Add` до `go` |
| Закрытие канала получателем / двойное закрытие | паника «close of closed / send on closed» | закрывает один владелец-писатель, один раз |
| Горутина пишет в канал, который никто не читает после отмены | **утечка горутины** (висит на `out <-` вечно) | в `select` писать в `out` и слушать `ctx.Done()`/`done` одновременно |
| Реентерабельный `Lock()` | дедлок (мьютекс не реентерабелен) | не брать тот же лок повторно; декомпозировать |
| Переиспользование уже отменённого контекста | операции мгновенно падают с `context.Canceled` | для нового запроса — новый производный контекст |
| Игнорирование `ctx.Done()` в долгой работе | отмена/таймаут не срабатывают | периодически проверять `ctx.Done()` через `select` |

Самая частая и самая опасная категория — **гонки данных** (data race): два конкурентных доступа к одной памяти, где хотя бы один — запись, без синхронизации. В Go их ловят встроенным детектором: `go test -race ./...` и `go run -race`. Запускайте тесты конкурентного кода **только** под `-race`. Механика гонок и модель памяти (happens-before, что именно создаёт отношение синхронизации) — в [MEMORY_GC](./MEMORY_GC.md).

Вторая по частоте — **утечка горутин** (goroutine leak): горутина навсегда заблокирована на send/receive, потому что её канал никто не дочитает или отмену она не слушает. Симптом — растущее `runtime.NumGoroutine()`. Лечение: всегда давайте горутине путь к выходу (`ctx.Done()` или закрытие канала) и оформляйте send в `select` вместе с отменой.

```go
// Пул воркеров с ограничением параллелизма
jobs := make(chan Job)
var wg sync.WaitGroup
for i := 0; i < workers; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); for j := range jobs { handle(j) } }()
}
// ... писать в jobs ...
close(jobs); wg.Wait()

// Отмена/таймаут
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()
select {
case <-ctx.Done(): return ctx.Err()
case res := <-resultCh: return res, nil
}

// Группа с первой ошибкой и отменой
g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return doWork(ctx) })
err := g.Wait()

// Атомарный счётчик (вместо мьютекса для одного значения)
var n atomic.Int64
n.Add(1)
```
