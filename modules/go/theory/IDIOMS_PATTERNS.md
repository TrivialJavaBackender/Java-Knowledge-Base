# Go — Идиомы и паттерны

> Этот файл — про **вкус и стиль** Go: как код выглядит, когда он написан «по-гошному».
> Механика лежит в соседних файлах (интерфейсы, типы, ошибки) — здесь мы собираем из неё
> правила дизайна и разбираем, **почему** идиоматичный вариант лучше «как в Java».
>
> Для разработчика из Java/Kotlin главный сдвиг: в Go меньше абстракций по умолчанию.
> Нет фабрик «на всякий случай», нет интерфейса на каждый класс, нет геттеров-сеттеров вокруг
> каждого поля. Go-культура ценит **очевидность** выше «расширяемости впрок».

## 1. Соглашения об именах

Имена в Go короткие и регламентированы стилистически. Это не вкусовщина — `gofmt`,
линтеры и code review в экосистеме ожидают именно эти формы.

### 1.1 MixedCaps, а не snake_case

Составные имена пишутся `MixedCaps` или `mixedCaps` — **никогда** `snake_case` и
**никогда** `SCREAMING_CASE` (даже для констант).

```go
// ✅ принято
var maxRetries int
const defaultTimeout = 30 * time.Second
func parseConfig() {}

// ❌ не принято
var max_retries int          // подчёркивания не используются
const DEFAULT_TIMEOUT = 30   // SCREAMING_CASE — это стиль C/Java, не Go
func ParseConfig_v2() {}     // подчёркивание-разделитель чужероден
```

Регистр **первой** буквы — это не стиль, а семантика: заглавная = экспортируется, строчная =
приватно для пакета (механика — в [./BASICS.md](./BASICS.md), раздел про экспорт). То есть
`MixedCaps` и `mixedCaps` различаются по смыслу, а не по вкусу.

### 1.2 Короткие имена в малой области

Длина имени должна быть **пропорциональна размеру области видимости**. Чем уже скоуп — тем
короче имя. Это противоположно Java-привычке давать всему развёрнутое самодокументирующее имя.

```go
// ✅ idiomatic: i, r, buf — в узких областях
for i, v := range items { ... }          // индекс цикла — одна буква
func (r *Reader) Read(p []byte) {}        // receiver — 1–2 буквы (первая буква типа)
buf := new(bytes.Buffer)                  // короткоживущая локальная — короткое имя

// ❌ переусложнение
for index, value := range items { ... }   // шумно для двухстрочного цикла
func (reader *Reader) Read(...) {}         // receiver не называют полным словом
```

Правило кодревью: переменная цикла, receiver, короткоживущая локальная — 1–2 символа.
Экспортируемое имя пакетного уровня — осмысленное слово (его читают вне контекста). Имя
**не** должно повторять тип (`userMap map[string]User` — лишнее, достаточно `users`).

### 1.3 Имена пакетов

Имя пакета — короткое, в нижнем регистре, **без подчёркиваний и MixedCaps**, в
единственном числе по смыслу (`http`, `json`, `user`, `time`). Полная механика «пакет =
директория» — в [./BASICS.md](./BASICS.md) и [./TOOLING_MODULES.md](./TOOLING_MODULES.md);
здесь — стилевые запреты.

Имя пакета — это **префикс** при обращении снаружи, поэтому его учитывают вместе с именем
сущности. Не дублируйте имя пакета в именах функций:

```go
// ✅ читается как http.Get, chunk.New — пакет даёт контекст
package http
func Get(url string) (*Response, error) {}   // вызов: http.Get(...)

// ❌ заикание (stutter): пакет уже сказал "http"
package http
func HTTPGet(url string) {}                   // вызов: http.HTTPGet — масло масляное
```

**Избегайте «мусорных» имён пакетов** — `util`, `common`, `helpers`, `misc`, `base`,
`shared`. Они ничего не говорят о содержимом и со временем превращаются в свалку с
циклическими зависимостями. Пакет должен называться по тому, **что он предоставляет**, а не
«разное полезное»: вместо `util` со строковыми хелперами — пакет `strutil` или просто
функция там, где она используется.

```go
// ❌ антипаттерн: бездонная свалка
package util
func FormatDate(...) {}
func ParseJSON(...) {}
func Retry(...) {}

// ✅ пакеты по смыслу
package timeutil   // или вообще держать рядом с использованием
package retry
```

### 1.4 Геттеры без `Get`

Метод-геттер называют по **имени свойства**, без приставки `Get`. Приставка `Set` для
сеттера допустима (она снимает неоднозначность с полем), а `Get` — нет.

```go
type User struct{ name string }

func (u User) Name() string      { return u.name }   // ✅ геттер без Get
func (u *User) SetName(n string) { u.name = n }      // ✅ сеттер с Set — ок

// ❌ func (u User) GetName() string — приставка Get не идиоматична
```

Причина — в инкапсуляции по пакету (детали в [./BASICS.md](./BASICS.md)): в Go нет
культуры «геттер/сеттер вокруг каждого поля». Экспортируют само поле, если инвариант не
требует защиты, и пишут метод `Name()` только когда нужна логика или скрытие. `GetName()`
выдаёт Java-привычку и засоряет вызовы (`user.GetName()` против `user.Name()`).

### 1.5 Интерфейсы на `-er`

Интерфейс с одним методом по соглашению называют по действию + суффикс `-er`: `Reader`,
`Writer`, `Closer`, `Stringer`, `Formatter`. Имя интерфейса описывает **что объект умеет
делать**, а не «кто он».

```go
type Reader interface{ Read(p []byte) (int, error) }
type Writer interface{ Write(p []byte) (int, error) }
type Stringer interface{ String() string }

// свой интерфейс — то же правило
type Notifier interface{ Notify(msg string) error }
```

Это контраст с Java, где интерфейсы часто называют существительным-ролью (`UserService`,
`PaymentRepository`) и иногда с префиксом `I` (`IRepository`). В Go префикс `I` не
используют **никогда**, а имя стремятся свести к «-er от глагола». Если метод не сводится к
одному глаголу (интерфейс с несколькими методами), берут осмысленное существительное
(`io.ReadWriteCloser`, `http.Handler`) — но и тогда без `I`.

## 2. Go Proverbs — поговорки как руководство к дизайну

Rob Pike сформулировал набор «поговорок Go» (Go Proverbs) — коротких принципов, которые
объясняют, почему идиоматичный код выглядит именно так. Разберём ключевые.

### «Clear is better than clever» — ясно лучше, чем умно

Главный принцип. Код читают чаще, чем пишут; «умное» решение, которое надо разгадывать,
дороже простого и длинного. Go намеренно беден на синтаксический сахар (нет тернарного
оператора, нет перегрузки операторов, нет наследования) именно чтобы код одного автора
читался другим без сюрпризов.

```go
// ❌ "умно": плотно, но требует расшифровки
x := map[bool]int{true: a, false: b}[cond]

// ✅ ясно: банальный if читается мгновенно
x := b
if cond {
    x = a
}
```

### «A little copying is better than a little dependency» — лучше немного скопировать

Если ради одной маленькой функции пришлось бы тянуть целую зависимость (или связывать два
пакета), — **скопируйте функцию**. Лишняя зависимость стоит дороже двадцати строк
дублирования: её надо версионировать, обновлять, она тянет транзитивные зависимости и
связывает ваши пакеты.

```go
// Нужна одна функция max для int? До дженериков — просто впишите её,
// а не импортируйте пакет ради одной строки.
func max(a, b int) int {
    if a > b {
        return a
    }
    return b
}
```

Это прямо противоречит привычке «не повторяйся любой ценой» (DRY доведённый до абсурда). В
Go дублирование маленькой логики **дешевле** связности. Контекст: для большого
повторяющегося кода правило не действует — речь про *little* copying против *little*
dependency.

### «Errors are values» — ошибки это значения

Ошибка в Go — обычное значение типа `error`, а не выброшенное исключение, ломающее поток
управления. Значит, ошибки можно **программировать**: складывать в срез, сравнивать,
передавать, оборачивать, накапливать. Стиль обработки (ранний возврат, добавление контекста,
`errors.Is/As`) — в [./ERRORS_PANIC.md](./ERRORS_PANIC.md). Принцип же таков: раз ошибка —
значение, обращайтесь с ней как с данными, а не как с управляющей конструкцией.

```go
// "errors are values": дедупликация повторяющейся проверки через функцию-обёртку.
// Пример из статьи Rob Pike — счётчик ошибок поверх Writer.
type errWriter struct {
    w   io.Writer
    err error
}

func (ew *errWriter) write(buf []byte) {
    if ew.err != nil {
        return // однажды упав, дальше молчим
    }
    _, ew.err = ew.w.Write(buf)
}

// вызов: три записи подряд без трёх if err != nil
ew := &errWriter{w: dst}
ew.write(a)
ew.write(b)
ew.write(c)
if ew.err != nil { /* одна проверка на всю серию */ }
```

### «Don't communicate by sharing memory; share memory by communicating»

Базовый принцип конкурентности в Go: вместо «общая переменная + мьютекс» предпочитают
**передачу данных через каналы**, где владение данными переходит от горутины к горутине.
Глубоко это разобрано в [./CONCURRENCY_PATTERNS.md](./CONCURRENCY_PATTERNS.md) и
[./GOROUTINES_CHANNELS.md](./GOROUTINES_CHANNELS.md); здесь фиксируем сам принцип как
ориентир дизайна.

```go
// ✅ "share memory by communicating": результат передаётся по каналу,
//    разделяемого состояния под мьютексом нет
results := make(chan int)
go func() { results <- compute() }()
r := <-results

// мьютекс не запрещён — он уместен для защиты маленького состояния (счётчик, кэш),
// но как способ "общения" между горутинами канал часто яснее
```

Оговорка: это **не** «мьютексы — зло». Для защиты простого общего состояния `sync.Mutex`
проще и быстрее канала. Поговорка про **коммуникацию** между горутинами, а не про всякую
синхронизацию.

### «The bigger the interface, the weaker the abstraction»

Чем больше методов в интерфейсе, тем меньше типов его удовлетворяют и тем он бесполезнее как
абстракция. Сила `io.Reader` — в одном методе: его реализуют сотни типов. Каноническое место
малых интерфейсов — [./INTERFACES.md](./INTERFACES.md); как принцип дизайна это раскрыто
ниже в разделе 5.

### «Make the zero value useful» — пусть нулевое значение работает

Проектируйте тип так, чтобы его **нулевое значение** (без инициализации) уже было готово к
работе. Это устраняет необходимость в конструкторе. Подробно — раздел 6.

> Полный список — [go-proverbs.github.io](https://go-proverbs.github.io) и доклад Rob Pike
> «Go Proverbs» (Gopherfest 2015). Они не догма, а способ объяснить *вкус* языка.

## 3. Стиль обработки ошибок (как идиома)

Механика ошибок — sentinel, `%w`, `errors.Is/As`, `panic/recover` — целиком в
[./ERRORS_PANIC.md](./ERRORS_PANIC.md). Здесь — стилевая сторона, влияющая на форму **любого**
Go-кода.

### Ранний возврат, плоский happy path

Идиома: проверяй ошибку сразу и **возвращайся**, не заворачивая основную логику в `else`.
Успешный путь («happy path») идёт по левому краю, с минимальным отступом; ветки ошибок
«отстреливаются» раньше.

```go
// ✅ ранний возврат: happy path не вложен
func process(path string) (*Result, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, fmt.Errorf("open %s: %w", path, err)
    }
    defer f.Close()

    data, err := io.ReadAll(f)
    if err != nil {
        return nil, fmt.Errorf("read %s: %w", path, err)
    }
    return parse(data) // основная логика — на верхнем уровне отступа
}

// ❌ "стрелочный" код: основная логика тонет в else-вложенности
func processBad(path string) (*Result, error) {
    f, err := os.Open(path)
    if err == nil {
        data, err := io.ReadAll(f)
        if err == nil {
            return parse(data) // happy path уехал на 3 отступа вправо
        } else {
            return nil, err
        }
    } else {
        return nil, err
    }
}
```

Правило кодревью: после `if err != nil { return ... }` ветка `else` почти всегда лишняя —
её содержимое выносится на уровень функции. Это и есть «плоский» Go-стиль.

### Добавляй контекст при пересечении границы

Возвращая ошибку наверх, оборачивайте её с **контекстом** (что делали), используя `%w`,
чтобы причина осталась распознаваемой. «Оборачивай при пересечении границы пакета/слоя,
обрабатывай на верхнем уровне» — золотая середина (детали и `errors.Is/As` —
в [./ERRORS_PANIC.md](./ERRORS_PANIC.md)).

## 4. `defer` для cleanup и unlock

`defer` откладывает вызов до выхода из функции (в порядке LIFO). Его идиоматическое
применение — **освобождение ресурса рядом с его захватом**, чтобы cleanup не потерялся ни на
одном пути возврата (включая `panic`). Полная механика `defer` (момент вычисления
аргументов, named returns, стоимость) — в [./ERRORS_PANIC.md](./ERRORS_PANIC.md); здесь —
как это формирует стиль.

```go
// ✅ unlock сразу после lock — невозможно забыть на каком-то return
func (c *Cache) Get(k string) (int, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()      // выполнится при любом выходе
    v, ok := c.m[k]
    return v, ok
}

// ✅ close рядом с open
f, err := os.Open(path)
if err != nil {
    return err
}
defer f.Close()              // парный cleanup стоит у места захвата
```

Идиома «захватил ресурс → на следующей строке `defer` его освобождение» делает код устойчивым
к ранним возвратам: добавив новый `return` в середину функции, вы не рискуете «утечь»
ресурсом. Это Go-замена `try-with-resources` / `finally`.

```go
// ❌ ручное освобождение — легко пропустить на новом пути выхода
func badGet(c *Cache, k string) int {
    c.mu.Lock()
    if k == "" {
        return 0          // забыли Unlock → дедлок на следующем вызове
    }
    v := c.m[k]
    c.mu.Unlock()
    return v
}
```

## 5. Functional options — конфигурация конструктора

Это **ключевой паттерн Go** для конструкторов с множеством опциональных параметров. Должен
быть в активе на собеседовании. Разберём подробно.

### Проблема

Тип `Server` имеет один обязательный параметр (`addr`) и десяток опциональных (таймаут,
лимит соединений, логгер, TLS, retry). Как сделать конструктор?

**Вариант «телескопические конструкторы»** (как иногда в Java) — плодит перегрузки. Но в Go
**нет перегрузки функций вообще** — два `NewServer` с разной сигнатурой не скомпилируются.
Значит, этот путь закрыт на уровне языка:

```go
// ❌ невозможно в Go: перегрузки запрещены
func NewServer(addr string) *Server
func NewServer(addr string, timeout time.Duration) *Server   // не компилируется
```

**Вариант «конфиг-структура»** работает, но имеет минусы:

```go
// ⚠️ рабочий, но не лучший вариант
type Config struct {
    Addr     string
    Timeout  time.Duration
    MaxConns int
    TLS      *tls.Config
}
func NewServer(cfg Config) *Server { ... }
```

Минусы конфиг-структуры:
- **Нельзя отличить «не задано» от «задан zero value».** `Timeout: 0` — это «по умолчанию» или «ноль секунд»? Приходится вводить sentinel-значения или указатели на каждое поле.
- **Нет места для валидации и вычисляемых дефолтов** в момент применения каждой опции.
- Вызывающий **обязан** знать структуру целиком; добавление поля — потенциальный источник путаницы при позиционной инициализации.

### Решение: функциональные опции

Опция — это **функция, мутирующая внутренний конфиг**. Конструктор принимает обязательные
аргументы плюс **вариативный** список опций и применяет их поверх дефолтов.

```go
package server

import "time"

type Server struct {
    addr     string
    timeout  time.Duration
    maxConns int
    logger   Logger
}

// Option — функция, настраивающая *Server. Это и есть весь "тип опции".
type Option func(*Server)

// Конструкторы опций — экспортируемые функции с префиксом With.
func WithTimeout(d time.Duration) Option {
    return func(s *Server) { s.timeout = d }
}

func WithMaxConns(n int) Option {
    return func(s *Server) { s.maxConns = n }
}

func WithLogger(l Logger) Option {
    return func(s *Server) { s.logger = l }
}

// NewServer: обязательный addr + вариативные опции.
func NewServer(addr string, opts ...Option) *Server {
    // 1) дефолты
    s := &Server{
        addr:     addr,
        timeout:  30 * time.Second,
        maxConns: 100,
        logger:   defaultLogger,
    }
    // 2) применяем опции поверх дефолтов
    for _, opt := range opts {
        opt(s)
    }
    return s
}
```

Вызов читается как декларация намерений — заданы только нужные опции, в любом порядке:

```go
srv := server.NewServer("localhost:8080",
    server.WithTimeout(5*time.Second),
    server.WithMaxConns(500),
)
// maxConns=500, timeout=5s, logger=defaultLogger (не трогали — остался дефолт)

minimal := server.NewServer("localhost:9090") // только обязательный addr, всё прочее — дефолты
```

### Почему это лучше

| Свойство | Конфиг-структура | Functional options |
|---|---|---|
| «Не задано» vs zero value | неотличимы без указателей/sentinel | опции просто не вызваны → остаётся дефолт |
| Порядок и набор аргументов | вся структура целиком | любой поднабор, любой порядок |
| Валидация/вычисление дефолта | вручную после создания | внутри опции, в момент применения |
| Обратная совместимость API | добавление поля видно всем | новая `WithX` — старые вызовы не трогаются |
| Самодокументируемость вызова | `Config{...}` | `WithTimeout(5s)` говорит сам за себя |

### Вариации

**Опция с ошибкой** — если опция может быть невалидной, тип делают возвращающим `error`, а
конструктор — собирающим ошибки:

```go
type Option func(*Server) error

func WithMaxConns(n int) Option {
    return func(s *Server) error {
        if n <= 0 {
            return fmt.Errorf("maxConns must be positive, got %d", n)
        }
        s.maxConns = n
        return nil
    }
}

func NewServer(addr string, opts ...Option) (*Server, error) {
    s := &Server{addr: addr, maxConns: 100}
    for _, opt := range opts {
        if err := opt(s); err != nil {
            return nil, err
        }
    }
    return s, nil
}
```

**Опции как интерфейс** (вариант Дейва Чейни) — вместо `type Option func(*T)` объявляют
интерфейс с методом `apply(*T)`; это позволяет добавлять опциям поведение и группировать их.
Для большинства случаев функционального типа достаточно — он проще.

Functional options — это применение принципа «errors are values» и first-class функций:
конфигурация выражается как **данные-функции**, а не как иерархия билдеров.

## 6. «Accept interfaces, return structs» как принцип дизайна

Каноническая формулировка идиомы и её механика (structural typing, где определять интерфейс,
interface pollution) — в [./INTERFACES.md](./INTERFACES.md). Здесь — как этим пользоваться на
уровне дизайна API.

### Принимай минимальный интерфейс

Функция должна требовать **ровно те методы, которые использует**, и ни одним больше. Это
максимизирует число подходящих аргументов (включая моки в тестах) и ослабляет связность.

```go
// ✅ нужен только Read → принимаем io.Reader, а не *os.File
func countLines(r io.Reader) (int, error) { ... }

// теперь работает с файлом, сетью, bytes.Buffer, strings.Reader, gzip-ридером...
countLines(file)
countLines(strings.NewReader("a\nb\n"))   // в тесте — без файлов на диске
```

### Возвращай конкретный тип

Возвращайте `*Server`, `*bytes.Buffer` — конкретику, а не интерфейс. Вызывающий получит все
методы и сам решит, к какой абстракции их свести. Вернув интерфейс, вы **преждевременно
сужаете** доступное.

```go
// ✅ конкретный тип на возврате
func NewBuffer() *bytes.Buffer { return &bytes.Buffer{} }

// ❌ интерфейс на возврате без причины: вызывающий лишается остальных методов *Buffer
func NewBuffer() io.Writer { return &bytes.Buffer{} }
```

### Интерфейс — у потребителя, не у производителя

Из structural typing: интерфейс объявляет тот, кто его **использует**, под свои нужды.
Пакет-производитель возвращает конкретный тип; пакет-потребитель определяет у себя маленький
интерфейс с нужными методами. Это разворачивает привычную Java-стрелку «сначала интерфейс в
core-модуле, потом impl».

```go
// пакет storage — производитель, отдаёт конкретный *Postgres
package storage
func New(dsn string) *Postgres { ... }
func (p *Postgres) Get(id int) (User, error) { ... }
func (p *Postgres) Save(u User) error { ... }

// пакет service — потребитель, объявляет МИНИМАЛЬНЫЙ интерфейс У СЕБЯ
package service
type userStore interface {       // только то, что нужно сервису
    Get(id int) (User, error)
}
func NewService(s userStore) *Service { ... }   // принимает интерфейс
```

### Interface pollution — не плоди интерфейсы впрок

Не добавляйте интерфейс, пока нет **второй реализации** или реальной потребности в подмене
(тесты, граница пакета). «Один интерфейс на каждую структуру» — антипаттерн `interface
pollution`: лишняя косвенность, хуже навигация и автодополнение (детали —
[./INTERFACES.md](./INTERFACES.md)).

## 7. «Make the zero value useful» — нулевое значение как дизайн

В Go у **каждого** типа есть нулевое значение (zero value): `0` для чисел, `""` для строк,
`nil` для указателей/слайсов/map/каналов/интерфейсов, рекурсивно обнулённые поля для структур
(механика — [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md) и [./BASICS.md](./BASICS.md)).
Идиома дизайна: спроектировать тип так, чтобы **его zero value было сразу готово к работе** —
тогда конструктор не нужен.

```go
// ✅ zero value полезен — все три работают БЕЗ инициализации
var mu sync.Mutex            // готов: mu.Lock()
var buf bytes.Buffer         // готов: buf.WriteString("hi")
var b strings.Builder        // готов: b.WriteByte('x')
```

Контраст с Java, где `new StringBuilder()` обязателен, а поле-объект по умолчанию `null` и
требует инициализации. В Go zero value — часть контракта типа.

### nil-слайс полезен

Особый и частый случай — **`nil`-слайс ведёт себя как пустой**. К нему можно применять
`len`, `range`, `append` — без проверок и без инициализации:

```go
var s []int          // s == nil, но это валидный пустой слайс
fmt.Println(len(s))  // 0 — не паника
for range s {}       // 0 итераций — не паника
s = append(s, 1)     // append к nil-слайсу создаёт новый — норма
```

Поэтому **не инициализируйте слайс «на всякий случай»** через `[]int{}` — `nil`-слайс
эквивалентен и идиоматичнее как «пока пусто». (Исключение — `nil`-**map**: читать можно,
писать в `nil`-map нельзя — будет паника; её надо `make`. Детали —
[./SLICES_MAPS_STRINGS.md](./SLICES_MAPS_STRINGS.md).)

```go
// ✅ возвращаем nil-слайс как "ничего не нашли" — вызывающему всё равно
func find(...) []Item {
    var result []Item        // nil
    // ... ничего не добавили ...
    return result            // вызывающий сделает range — 0 итераций, ок
}
```

### Когда zero value спроектировать нельзя

Если для готовности нужны ресурсы (открытое соединение, скомпилированный шаблон, валидация) —
тогда пишут конструктор `NewX` (раздел 8). Цель — не отказаться от конструкторов, а **не
плодить их там, где zero value и так работает**.

## 8. Конструкторы `NewX` — когда нужны

В Go нет конструкторов на уровне языка (нет `new ClassName(...)` с логикой). Базовая
механика и `new` vs составной литерал — в [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md).
Здесь — **когда** конструктор оправдан, а когда нет.

Конструктор-функцию `NewX` пишут, **только** если выполнено хотя бы одно:

1. **Нужна валидация** входных данных при создании.
2. **Есть неочевидные дефолты**, которые нельзя выразить нулевым значением.
3. **Нужно выделить/открыть ресурс** (соединение, файл, фоновую горутину).
4. **Инвариант** требует, чтобы поля были согласованы (zero value их нарушает).

```go
func NewClient(addr string) (*Client, error) {
    if addr == "" {
        return nil, errors.New("addr is required")   // (1) валидация
    }
    return &Client{
        addr:    addr,
        timeout: 30 * time.Second,                    // (2) неочевидный дефолт
        conns:   make(chan *conn, 10),                // (3) ресурс
    }, nil
}
```

Соглашения об именах:
- Пакет с **одним** основным типом → конструктор `New` (вызов `pkg.New()`, например `list.New()`).
- Несколько типов → `NewClient`, `NewServer`.
- Возврат `error` — когда создание может не удаться; иначе только значение.
- Много опциональных параметров → **functional options** (раздел 5), а не телескопические `NewX`.

**Не пишите конструктор-«пустышку»**, который просто заполняет поля без логики, если zero
value и так пригоден или хватает составного литерала `&T{...}`:

```go
// ❌ бессмысленный конструктор: ничего не добавляет к &Point{X:1, Y:2}
func NewPoint(x, y int) *Point { return &Point{X: x, Y: y} }
```

## 9. Дизайн пакетов

Пакет — единица компиляции, видимости и переиспользования. Хороший пакет **связен** (cohesive):
содержит одну ответственность, имеет узкий внятный API. Базовая структура (`cmd/`, `internal/`,
`pkg/`) — в [./TOOLING_MODULES.md](./TOOLING_MODULES.md); здесь — принципы.

### Связность и отсутствие циклов

В Go **циклические зависимости пакетов запрещены компилятором** — если `a` импортирует `b`,
то `b` не может импортировать `a`, даже транзитивно. Это не рекомендация, а ошибка сборки.
Дисциплина вынужденная и полезная: она заставляет продумывать направление зависимостей.

Типичная причина цикла — пакет `util`/`common`, в который «стекается» всё подряд и который
все импортируют. Лечится разделением по смыслу (раздел 1.3) и правилом «интерфейс у
потребителя» (раздел 6): потребитель не импортирует производителя ради типа — он объявляет
свой интерфейс.

### `internal/` — инкапсуляция на уровне модуля

Пакет под директорией `internal/` импортируется **только** изнутри того же модуля (это
правило компилятора, единственная такая конвенция). Кладите туда всё, что не является
публичным API модуля, — тогда внешние потребители физически не смогут на это завязаться, и вы
свободны менять внутренности. Механика — [./TOOLING_MODULES.md](./TOOLING_MODULES.md).

### API-минимализм

Экспортируйте **минимум**. Каждое экспортированное имя — это обещание совместимости. Чем уже
публичная поверхность, тем свободнее рефакторинг. Начинайте с приватного (строчная буква),
экспортируйте только когда снаружи это действительно нужно. Это противоположно Java-привычке
делать `public` по умолчанию.

### Документирующие комментарии (godoc) и `doc.go`

Документация в Go — это обычные комментарии **перед** объявлением, начинающиеся с **имени
сущности** (их показывает `go doc` и pkgsite; механика — [./TOOLING_MODULES.md](./TOOLING_MODULES.md)).

```go
// Server обрабатывает входящие соединения по адресу addr.
// Нулевое значение непригодно — используйте NewServer.
type Server struct { ... }

// NewServer создаёт Server на addr и применяет опции поверх дефолтов.
func NewServer(addr string, opts ...Option) *Server { ... }
```

Документацию **самого пакета** (обзор, примеры использования) пишут в комментарии перед
`package` в любом файле. Если обзор длинный, по соглашению заводят отдельный файл **`doc.go`**
— в нём только пакетный комментарий и объявление `package`, без кода:

```go
// Package server реализует TCP-сервер с конфигурацией через functional options.
//
// Базовое использование:
//
//	srv := server.NewServer("localhost:8080", server.WithTimeout(5*time.Second))
//	srv.ListenAndServe()
package server
```

## 10. Пустая структура `struct{}` — множества и сигналы

`struct{}` занимает **0 байт** — идиоматический способ сказать «значение не важно, важен сам
факт». Базовое описание — в [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md); здесь —
как паттерн.

```go
// 1) Множество: map[T]struct{} вместо map[T]bool — ноль байт на значение
seen := make(map[string]struct{})
seen["a"] = struct{}{}             // добавить
if _, ok := seen["a"]; ok { ... }  // проверить принадлежность

// 2) Сигнальный канал: передаём событие без полезной нагрузки
done := make(chan struct{})        // chan struct{} — "только сигнал"
go func() {
    defer close(done)              // закрытие = широковещательный сигнал получателям
    work()
}()
<-done                             // ждём
```

В Java множество — это `HashSet<T>` (внутри `HashMap` с фиктивной заглушкой); Go делает то же
явно, но заглушка `struct{}{}` весит ноль. Сигнальный `chan struct{}` концептуально близок к
`CountDownLatch` на одно событие. Канал семафора/сигналов делают именно `chan struct{}`,
подчёркивая «данных нет, есть только факт».

## 11. Перечисления через `iota` и `Stringer`

В Go **нет `enum`** как отдельной конструкции (в отличие от Java). Перечисления делают как
набор констант именованного целого типа, нумеруя их через `iota` — счётчик, который растёт на
каждую строку внутри блока `const`.

```go
type State int

const (
    StateIdle    State = iota // 0
    StateRunning              // 1 — iota продолжает автоматически
    StateStopped              // 2
)
```

Свой тип (`State`, не сырой `int`) даёт типобезопасность: функция `func transition(s State)`
не примет произвольное число без явного преобразования. `iota` сбрасывается в 0 в каждом
новом блоке `const` и инкрементируется по строкам — поэтому достаточно написать `= iota` один
раз, дальше значения проставляются сами.

### Делаем перечисление печатаемым — `Stringer`

Сырое `State(1)` напечатается как `1` — неинформативно. Реализуем метод `String()` (интерфейс
`fmt.Stringer`), и значение начнёт печататься именем:

```go
func (s State) String() string {
    switch s {
    case StateIdle:
        return "Idle"
    case StateRunning:
        return "Running"
    case StateStopped:
        return "Stopped"
    default:
        return fmt.Sprintf("State(%d)", int(s))
    }
}

fmt.Println(StateRunning) // "Running" — fmt.Println зовёт String() автоматически
```

### `go generate` + `stringer` — не писать `String()` руками

Писать `switch` вручную скучно и легко рассинхронизировать при добавлении константы. Поэтому
используют генератор **`stringer`**: директива-комментарий `//go:generate` + запуск
`go generate` создаёт метод `String()` за вас (механика `go generate` и `stringer` —
в [./TOOLING_MODULES.md](./TOOLING_MODULES.md)).

```go
//go:generate stringer -type=State
type State int

const (
    StateIdle State = iota
    StateRunning
    StateStopped
)
// `go generate ./...` создаст файл state_string.go с методом String()
```

Идиома: для перечислений с несколькими значениями предпочитают сгенерированный `String()` —
он не рассинхронизируется с константами.

## 12. Композиция через встраивание для декорирования

Полная механика встраивания (promotion, shadowing, диамонд) — в
[./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md). Здесь — один прикладной паттерн:
**встраивание интерфейса для декоратора**.

Чтобы обернуть существующую реализацию и переопределить **один** метод, оставив остальные «как
есть», встраивают интерфейс в структуру и реализуют только нужный метод. Продвинутые методы
встроенного интерфейса делегируются вложенному значению автоматически.

```go
// Хотим логировать только запись, остальное io.ReadWriteCloser — как есть.
type loggingWriter struct {
    io.ReadWriteCloser            // встроенный интерфейс: Read/Write/Close продвигаются
    log Logger
}

// Переопределяем ТОЛЬКО Write — Read и Close делегируются встроенному значению.
func (w loggingWriter) Write(p []byte) (int, error) {
    w.log.Printf("writing %d bytes", len(p))
    return w.ReadWriteCloser.Write(p)   // явный вызов встроенной реализации
}

// использование: оборачиваем любой ReadWriteCloser
func wrap(rwc io.ReadWriteCloser, l Logger) io.ReadWriteCloser {
    return loggingWriter{ReadWriteCloser: rwc, log: l}
}
```

Это Go-замена паттерна Decorator без иерархии классов: не нужно реализовывать весь интерфейс
заново — встраивание «пробрасывает» непереопределённые методы. Тот же приём удобен в тестах:
встроить интерфейс и подменить один метод заглушкой.

Помните ограничение из [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md): встраивание —
это **делегирование**, не наследование. Виртуальной диспетчеризации нет; если встроенный тип
внутри себя вызывает свой метод, он вызовет **свой**, а не ваш переопределяющий.

## 13. «Don't panic» через границу пакета

Правило: **библиотека почти никогда не должна паниковать наружу** — она возвращает `error`.
Паника допустима внутри пакета (нарушенный инвариант, программистский баг), но её **ловят на
границе** через `recover` и конвертируют в `error`. Механика `panic`/`recover` и какие случаи
оправдывают панику — в [./ERRORS_PANIC.md](./ERRORS_PANIC.md).

```go
// ✅ внутренняя паника не "протекает" наружу: ловим на публичной границе
func (p *Parser) Parse(input string) (result Tree, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("parse failed: %v", r)   // паника → error для вызывающего
        }
    }()
    return p.parseInternal(input), nil                // внутри может паниковать
}
```

Почему это идиома: вызывающий ожидает `error`, а не падение всего процесса. Паника,
пересекающая границу пакета, делает API непредсказуемым и не отражённым в сигнатуре. Исключения
(когда паника наружу нормальна): инициализация пакета (`init`, `MustCompile`-семейство), где
невозможность создать объект — фатальна по контракту, и это явно отражено в имени (`Must...`).

```go
// Семейство Must...: паника наружу намеренна и видна по имени.
var re = regexp.MustCompile(`\d+`)   // паникует при невалидном regexp — но это видно из имени
```

## 14. comma-ok идиома

`comma-ok` — встроенный в язык способ отличить «есть значение / нет значения» без исключений и
паник. Второй булев результат `ok` говорит, удалась ли операция. Применяется в **трёх**
местах:

```go
// 1) Чтение из map: ключа может не быть
v, ok := m["key"]
if !ok { /* ключа нет; v == zero value */ }

// 2) Type assertion: динамический тип может не совпасть (см. ./INTERFACES.md)
s, ok := x.(string)
if !ok { /* не строка; паники нет, s == "" */ }

// 3) Приём из канала: канал может быть закрыт (та же форма и в select: case v, ok := <-ch)
v, ok := <-ch
if !ok { /* канал закрыт и пуст */ }
```
(`for v := range ch` даёт только значение, без `ok` — цикл сам завершается при закрытии канала.)

Без `comma-ok` те же операции либо паникуют (assertion без второго результата), либо
неотличимы от zero value (чтение map). Идиома: **там, где значение может отсутствовать,
используйте comma-ok**, а не однозначную форму. Это часть философии «errors are values» — на
уровне примитивов языка: отсутствие выражается данными (`ok bool`), а не исключением.

```go
// ❌ assertion без comma-ok — паника, если x не string
s := x.(string)

// ✅ безопасно
if s, ok := x.(string); ok { use(s) }
```

## Типичные ошибки (шпаргалка)

| Ошибка | Симптом / почему плохо | Идиома |
|---|---|---|
| `snake_case` / `SCREAMING_CASE` | чужеродно Go, ругаются линтеры | `MixedCaps` / `mixedCaps` |
| Длинное имя в узком скоупе | шум; имя не пропорционально области | `i`, `r`, `buf` в малой области |
| Пакет `util`/`common` | свалка, циклы зависимостей | пакет по смыслу; «немного скопировать» |
| `GetName()` геттер | Java-привычка, заикание в вызове | `Name()` без `Get` |
| Префикс `I` у интерфейса | не принято в Go | `Reader`, `Notifier` (`-er`) |
| `else` после `return err` | «стрелочный» вложенный код | ранний возврат, плоский happy path |
| Ручной `Unlock`/`Close` | забыли на новом `return` → утечка/дедлок | `defer` сразу после захвата |
| Телескопические `NewX` | перегрузки в Go запрещены | functional options |
| Конфиг-структура с zero value | «не задано» неотличимо от нуля | functional options поверх дефолтов |
| Возврат интерфейса вместо `*T` | сужает доступное вызывающему | accept interfaces, **return structs** |
| Интерфейс у производителя | лишняя косвенность, pollution | интерфейс у потребителя |
| Конструктор-пустышка | не добавляет логики к `&T{}` | zero value / составной литерал |
| `[]int{}` «на всякий случай» | `nil`-слайс и так пустой | `var s []int` |
| Паника наружу из библиотеки | непредсказуемый API | `recover` на границе → `error` |
| Assertion `x.(T)` без `ok` | паника при неверном типе | `v, ok := x.(T)` |
