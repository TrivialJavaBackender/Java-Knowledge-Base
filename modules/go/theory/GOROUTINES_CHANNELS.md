# Go — Горутины и каналы

> Конкурентность в Go строится на двух примитивах: **горутина** — дешёвая единица исполнения, и **канал** — типизированная очередь для передачи значений между горутинами. Девиз языка: **«Не общайтесь, разделяя память; разделяйте память, общаясь»** (Don't communicate by sharing memory; share memory by communicating).
>
> Для разработчика из Java аналогия близкая, но не точная: горутина похожа на виртуальный поток (Java 21+), а канал — на `BlockingQueue`. Разница в том, что в Go это не библиотека, а **часть языка**: `go`, `chan`, `select`, `close` — ключевые слова и встроенные операции, а не классы.

Эта тема покрывает сами примитивы. Устройство шедулера (как горутины мультиплексируются на потоки, GMP, preemption) вынесено в [SCHEDULER](./SCHEDULER.md); модель памяти и гарантии видимости (happens-before для каналов) — в [MEMORY_GC](./MEMORY_GC.md). Прикладные паттерны (worker pool, `context`, `sync`, `errgroup`) — в [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md).

## 1. Горутина: `go f()`

Горутина — это функция, запущенная конкурентно. Запуск — ключевое слово `go` перед вызовом:

```go
func main() {
    go say("world") // запускается конкурентно
    say("hello")    // выполняется в основной горутине
}

func say(s string) {
    for i := 0; i < 3; i++ {
        fmt.Println(s)
    }
}
```

`go f(x, y)` вычисляет `f`, `x`, `y` в **текущей** горутине, а сам вызов `f` выполняет в **новой**. Управление возвращается немедленно — `go` ничего не ждёт и ничего не возвращает (никакого аналога `Future`/`Deferred`). Если результат нужен — его передают через канал.

### Почему горутины дешёвые

Начальный стек горутины — порядка **2–8 КБ** (растёт и сжимается по мере необходимости), тогда как стек потока ОС фиксирован на ~1 МБ. Горутины не отображаются на потоки ОС один-к-одному: рантайм мультиплексирует тысячи горутин на небольшое число потоков (модель M:N). Поэтому миллион горутин — рутинная ситуация, а миллион потоков ОС невозможен. Как именно работает это мультиплексирование — см. [SCHEDULER](./SCHEDULER.md).

### Параллель с Java

| | Java platform thread | Java virtual thread (21+) | Go горутина |
|---|---|---|---|
| Начальный стек | ~1 МБ | ~КБ, растёт | ~2–8 КБ, растёт |
| Сколько можно | ~10К | миллионы | миллионы |
| Кто планирует | ОС | JVM (на carrier threads) | рантайм Go (на потоках ОС) |
| Модель | 1:1 | M:N | M:N |
| Блокирующий I/O | занимает поток ОС | unmount с carrier | паркует горутину, поток ОС свободен |
| Запуск | `new Thread()` | `Thread.ofVirtual().start()` | `go f()` |

Ближайший аналог горутины — именно **виртуальный поток** Java: обе сущности лёгкие, обе мультиплексируются на пул несущих потоков, обе паркуются на блокирующих операциях, не занимая поток ОС. Подробнее про модель M:N в Java — [VIRTUAL_THREADS](../../concurrency/theory/VIRTUAL_THREADS.md). Ключевое отличие: в Go это модель по умолчанию (другой и нет), а в Java виртуальные потоки сосуществуют с платформенными.

### Время жизни и завершение

Три факта, которые меняют привычки Java-разработчика:

1. **Горутина живёт, пока жива программа, но не наоборот.** Когда `main` возвращается, процесс завершается **немедленно** — рантайм не ждёт остальные горутины (в отличие от не-daemon потоков JVM, которые удерживают процесс живым). Незавершённые горутины просто исчезают.

```go
func main() {
    go fmt.Println("я могу не успеть напечататься")
    // main сразу завершается → процесс выходит, горутина выше может не выполниться
}
```

2. **Паника в горутине, не пойманная внутри неё, рушит весь процесс.** Раскрутка стека не пересекает границу `go`: `recover` ловит только панику своей горутины. Поэтому тело фоновой горутины оборачивают в `defer recover()` (детали — [ERRORS_PANIC](./ERRORS_PANIC.md)).

3. **Горутину нельзя «убить» извне.** Нет аналога `Thread.interrupt()` или `thread.stop()`. Единственный способ остановить горутину — **попросить** её завершиться через сигнал: закрытый канал или отмену через `context.Context` (см. [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md)). Горутина обязана сама проверять этот сигнал и выходить — это кооперативная остановка, как кооперативная отмена корутин в Kotlin.

## 2. Философия CSP: общаться, а не разделять

Go наследует модель **CSP** (Communicating Sequential Processes, Хоар, 1978) — ту же теоретическую основу, что и каналы Kotlin. Идея: вместо защиты разделяемого состояния мьютексами передавайте **владение данными** через канал. В любой момент данными «владеет» одна горутина; передав значение в канал, отправитель перестаёт его трогать, а получатель — начинает.

```go
// Вместо: общий счётчик под мьютексом
// Делаем: одна горутина-владелец, остальные шлют ей запросы через канал
```

Это не догма — `sync.Mutex` и `sync/atomic` в Go есть и уместны (например, для простого счётчика или защиты небольшого участка). Но **каналы — идиоматичный способ координации**, а мьютексы — для защиты состояния. Подробный разбор «канал vs мьютекс» — в [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md).

## 3. Каналы: создание и базовые операции

Канал — типизированный конвейер: через `chan int` передаются только `int`. Создаётся через `make`:

```go
ch := make(chan int)      // небуферизованный
buf := make(chan int, 4)  // буферизованный, ёмкость 4
```

Три операции (стрелка всегда «показывает» направление потока данных):

```go
ch <- 42        // send: отправить значение в канал
v := <-ch       // receive: получить значение
v, ok := <-ch   // receive с признаком: ok=false, если канал закрыт и пуст
```

Нулевое значение канала — `nil`; неинициализированный канал бесполезен (см. §7).

## 4. Небуферизованный vs буферизованный

Это ключевое различие, которое спрашивают на собеседовании.

### Небуферизованный — `make(chan T)`: рандеву

Ёмкость 0. Канал не хранит значений вообще. `send` **блокируется**, пока другая горутина не сделает `receive`, и наоборот. Передача — это точка синхронизации (рандеву, rendezvous): отправитель и получатель «встречаются» в один момент, и обмен значением гарантирует, что оба продолжат после встречи.

```go
ch := make(chan int)
go func() { ch <- 42 }() // зависнет здесь, пока main не прочитает
fmt.Println(<-ch)        // 42; до этой строки send не завершится
```

Аналог в Java — `SynchronousQueue` (ёмкость 0, `put` ждёт `take`).

### Буферизованный — `make(chan T, n)`: ограниченная очередь

Ёмкость `n` > 0. `send` блокируется **только когда буфер полон**; `receive` — только когда буфер пуст. Отправитель и получатель развязаны во времени, пока хватает буфера.

```go
ch := make(chan int, 2)
ch <- 1 // не блокирует (буфер: [1])
ch <- 2 // не блокирует (буфер: [1 2])
// ch <- 3 // заблокировался бы: буфер полон
```

Аналог — `ArrayBlockingQueue(n)`.

| | Небуферизованный `make(chan T)` | Буферизованный `make(chan T, n)` |
|---|---|---|
| Ёмкость | 0 | n |
| `send` блокирует | пока нет готового `receive` | пока буфер полон |
| `receive` блокирует | пока нет готового `send` | пока буфер пуст |
| Семантика | синхронная передача (рандеву) | асинхронная очередь с лимитом |
| Гарантия | получатель **получил** значение | значение **поставлено в очередь** |
| Java-аналог | `SynchronousQueue` | `ArrayBlockingQueue(n)` |

**Важный нюанс гарантий.** После успешного `send` в небуферизованный канал вы знаете: получатель действительно забрал значение. После `send` в буферизованный — только что значение попало в буфер; получатель мог ещё не дойти до него. Это влияет на корректность сигналинга: для «дождись завершения» нужен небуферизованный канал или явная синхронизация.

> Буфер — не для «ускорения», а для развязки темпа producer и consumer и сглаживания всплесков. Выбирайте ёмкость осознанно; буфер «на всякий случай побольше» маскирует проблемы и копит память — как `Channel.UNLIMITED` в Kotlin.

## 5. Закрытие канала: `close`, `range`, признак `ok`

`close(ch)` сигнализирует «значений больше не будет». Это не освобождение ресурса (канал соберёт GC), а **семантический сигнал конца потока**.

### Правило: закрывает только отправитель

Закрывать канал должна **сторона-отправитель**, и притом та, которая знает, что отправок больше не будет. Получатель закрывать не должен никогда. Причина — в семантике паники (ниже): запись или повторное закрытие после `close` рушат программу, и только отправитель в состоянии гарантировать, что этого не произойдёт. Если отправителей несколько, нужен отдельный координатор (например, `sync.WaitGroup` + одна закрывающая горутина — ровно так устроен fan-in, см. §8 и упражнение).

### Receive из закрытого канала

Из закрытого канала `receive` **не блокирует**: он немедленно отдаёт нулевое значение типа и `ok = false`.

```go
ch := make(chan int, 2)
ch <- 1
close(ch)
fmt.Println(<-ch) // 1   (оставшиеся в буфере значения вычитываются)
v, ok := <-ch     // v=0, ok=false  (буфер пуст и канал закрыт)
```

Признак `ok` — единственный надёжный способ отличить «получили настоящий ноль» от «канал закрыт». Закрытие не теряет уже отправленные значения: сначала вычитывается буфер, потом начинают приходить нули с `ok=false`.

### Идиома `for range` по каналу

Цикл `for v := range ch` получает значения, пока канал не закрыт, и **завершается автоматически** при закрытии (буфер при этом дочитывается). Это самый частый способ потребления:

```go
ch := make(chan int)
go func() {
    defer close(ch)        // закрываем по выходу — получатель увидит конец
    for i := 0; i < 5; i++ {
        ch <- i
    }
}()

for v := range ch {        // 0 1 2 3 4, затем цикл выходит сам
    fmt.Println(v)
}
```

Без `close` этот `range` **завис бы навсегда** после последнего значения — классическая взаимоблокировка/утечка.

### Паники, связанные с закрытием

Три операции над закрытым каналом — программные ошибки, и рантайм их карает паникой:

| Операция | Результат |
|---|---|
| `ch <- v` в закрытый канал | **паника** `send on closed channel` |
| `close(ch)` уже закрытого | **паника** `close of closed channel` |
| `close(ch)` для `nil`-канала | **паника** `close of nil channel` |
| `<-ch` из закрытого | нулевое значение + `ok=false` (НЕ паника) |

Отсюда и правило «закрывает только отправитель, и только один раз»: получатель не может безопасно закрывать, потому что параллельный отправитель тогда запаникует.

## 6. `select`: ожидание нескольких каналов

`select` — управляющая конструкция, как `switch`, но ветки — это операции над каналами. Он блокируется, пока **хотя бы одна** ветка не станет готова, и выполняет именно её:

```go
select {
case v := <-ch1:
    fmt.Println("из ch1:", v)
case ch2 <- x:
    fmt.Println("отправили в ch2")
case <-done:
    return
}
```

### Случайный выбор среди готовых

Если готовы **несколько** веток сразу, `select` выбирает одну **случайно** (а не по порядку записи). Это сделано намеренно — чтобы исключить голодание (starvation): ни один канал не получает систематического приоритета. Полагаться на порядок case нельзя.

### `default`: неблокирующая попытка

Ветка `default` срабатывает, **если ни одна** другая ветка не готова немедленно. С ней `select` никогда не блокируется — это неблокирующий `send`/`receive`:

```go
select {
case v := <-ch:
    process(v)
default:
    // канал пуст прямо сейчас — не ждём, делаем что-то ещё
}
```

(Аналог `tryReceive`/`trySend` в Kotlin или `poll()`/`offer()` у `BlockingQueue`.)

### Таймаут через `time.After`

`time.After(d)` возвращает канал, в который через `d` придёт одно значение. В паре с `select` это даёт таймаут:

```go
select {
case v := <-ch:
    return v, nil
case <-time.After(2 * time.Second):
    return 0, errors.New("timeout")
}
```

> Замечание: каждый вызов `time.After` создаёт таймер, который не освобождается до срабатывания. В горячем цикле это утечка; там используют `time.NewTimer` с явным `Stop()` либо `context.WithTimeout` (см. [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md)).

## 7. Nil-канал и его роль в `select`

`receive` или `send` по **nil-каналу блокируются навсегда** — никогда не готовы. На первый взгляд это бесполезный (и опасный) случай, но именно он даёт идиому **«отключить ветку select»**.

Внутри `select` ветка с nil-каналом **никогда не выбирается** (она вечно не готова). Присвоив переменной канала `nil`, мы динамически выключаем соответствующий case, не трогая остальную структуру `select`:

```go
func merge(in1, in2 <-chan int, out chan<- int) {
    for in1 != nil || in2 != nil {
        select {
        case v, ok := <-in1:
            if !ok {
                in1 = nil   // источник иссяк → выключаем эту ветку
                continue
            }
            out <- v
        case v, ok := <-in2:
            if !ok {
                in2 = nil   // выключаем вторую ветку
                continue
            }
            out <- v
        }
    }
}
```

Когда оба канала закрыты и обнулены, условие цикла `in1 != nil || in2 != nil` становится `false`, и функция корректно завершается. Без этого приёма закрытый канал в `select` отдавал бы `ok=false` в бесконечном цикле (busy-loop), сжигая CPU.

| Состояние канала | `send` | `receive` |
|---|---|---|
| nil | блокирует **навсегда** | блокирует **навсегда** |
| открыт, есть место/значение | проходит | проходит |
| открыт, нет места/значения | блокирует | блокирует |
| закрыт | **паника** | нулевое значение, `ok=false`, не блокирует |

## 8. Базовые паттерны

Здесь — минимум; полноценные worker pool, fan-in/fan-out с `context`, `errgroup` — в [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md).

### Generator — функция, возвращающая канал

Источник значений отдаёт `<-chan T` (только для чтения) и сам закрывает его, когда закончил:

```go
func count(n int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for i := 0; i < n; i++ {
            out <- i
        }
    }()
    return out
}

for v := range count(5) { // 0 1 2 3 4
    fmt.Println(v)
}
```

Возврат **направленного** канала (`<-chan int`) — хорошая практика: компилятор не даст вызывающему коду по ошибке отправить или закрыть чужой канал.

### Done-канал — сигнал остановки

Чтобы сказать горутине «завершайся», закрывают общий `done`-канал. Закрытый канал «вещает» сигнал **всем** читателям сразу (каждый `<-done` немедленно разблокируется) — это broadcast одним закрытием:

```go
func worker(done <-chan struct{}, jobs <-chan int) {
    for {
        select {
        case <-done:        // попросили остановиться
            return
        case j := <-jobs:
            process(j)
        }
    }
}

done := make(chan struct{})
// ... запускаем воркеров с этим done ...
close(done) // все воркеры увидят сигнал и выйдут
```

Тип `chan struct{}` — идиома для сигнала «без данных»: `struct{}` занимает 0 байт, значение не важно, важен сам факт. В реальном коде эту роль обычно выполняет `context.Context` (см. [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md)).

### Направленные каналы в сигнатурах

Канал можно сузить до одного направления — это документирует контракт и ловится компилятором:

```go
func producer(out chan<- int) { out <- 1 } // только отправка
func consumer(in <-chan int)  { <-in }      // только чтение
```

Внутри одной функции держат двунаправленный `chan int`, а в параметры передают суженный — `chan<- int` или `<-chan int`. Преобразование происходит неявно при передаче.

## 9. Обнаружение взаимоблокировки рантаймом

Рантайм Go умеет обнаруживать **глобальную взаимоблокировку** (deadlock): ситуацию, когда **все** горутины заблокированы и ни одна не может продвинуться. Тогда программа аварийно завершается:

```
fatal error: all goroutines are asleep - deadlock!
```

```go
func main() {
    ch := make(chan int)
    <-ch // никто никогда не отправит → все горутины (одна) спят → deadlock
}
```

### Когда срабатывает, а когда нет

Детектор реагирует только на **тотальную** взаимоблокировку — когда спят **все** горутины. Он **не** обнаруживает:

- **Частичную** блокировку: если хоть одна горутина работает (например, бесконечный цикл, ожидание сети, спит на `time.Sleep`), детектор молчит, даже если другая горутина зависла навсегда на `<-ch`. Это самый частый случай в реальном коде — **утечка горутины** (см. §10), и runtime её не ловит.
- Блокировки на примитивах вне рантайма — системные вызовы, `cgo`.

То есть детектор — грубая страховка от «программа целиком встала», а не инструмент поиска утечек. Для поиска зависших горутин используют профиль `goroutine` (pprof) и таймауты в тестах — как `withTimeout` в упражнении к этой теме.

## 10. Частые ошибки

### 10.1 Утечка горутины

Горутина, навсегда заблокированная на `send` или `receive`, никогда не завершится и не освободит память — она просто «висит». Это не ошибка времени выполнения, рантайм её не заметит (см. §9), но это утечка.

```go
func leak() {
    ch := make(chan int) // небуферизованный
    go func() {
        ch <- 42 // ❌ зависнет навсегда: никто не читает
    }()
    // функция вернулась, читателя нет → горутина выше течёт
}
```

Типичный сценарий: функция вернулась раньше (по таймауту, по ошибке), а горутина-отправитель всё ещё пытается отдать результат в небуферизованный канал, который уже никто не слушает. Лечится либо буфером ёмкости 1 (отправитель кладёт значение и выходит, даже если читателя нет), либо `select` с `done`/`context`, либо гарантией, что получатель всегда дочитает. Симметрично течёт и получатель, висящий на `range` по каналу, который забыли закрыть.

### 10.2 Запись в закрытый канал

```go
ch := make(chan int)
close(ch)
ch <- 1 // ❌ паника: send on closed channel
```

Прямое следствие правила §5. Возникает, когда несколько отправителей и нет согласованного владельца закрытия: один закрыл, другой ещё пишет. Решение — закрывает ровно одна сторона, и только когда все отправки точно завершены (координация через `WaitGroup` + отдельная закрывающая горутина).

### 10.3 Переменная цикла в горутине (поведение до и после Go 1.22)

Классическая ловушка: запустить горутины в цикле, замкнув переменную цикла.

```go
for i := 0; i < 3; i++ {
    go func() {
        fmt.Println(i)
    }()
}
```

- **До Go 1.22:** переменная `i` была **одна на весь цикл**. Все горутины захватывали один и тот же `i` по ссылке и видели его текущее (часто уже финальное) значение — типичный вывод `3 3 3`. Чинили копированием: `i := i` в начале тела или передачей аргументом `go func(i int){...}(i)`.
- **Начиная с Go 1.22:** семантика изменена — **каждая итерация создаёт новый экземпляр** переменной цикла. Теперь код выше печатает `0 1 2` (в неопределённом порядке). Явное копирование больше не нужно.

Помните о версии: на модулях с `go 1.21` и ниже (директива в `go.mod`) действует старое поведение даже на новом компиляторе. Передача аргументом `go func(x int){...}(i)` корректна при любой версии — безопасный стиль, если не уверены.

> Та же ловушка ровно так же снята и при захвате переменной цикла в обычных замыканиях (`defer`, срезы функций) — это общее изменение Go 1.22, не только про `go`.

## Шпаргалка

```go
go f()                         // запуск горутины (ничего не возвращает)

ch := make(chan T)             // небуферизованный (рандеву)
ch := make(chan T, n)          // буферизованный (очередь на n)

ch <- v                        // send
v := <-ch                      // receive
v, ok := <-ch                  // ok=false → канал закрыт и пуст
close(ch)                      // закрывает ТОЛЬКО отправитель, один раз
for v := range ch { ... }      // читать до close

func gen() <-chan T            // generator: вернуть направленный канал
func sink(c chan<- T)          // только отправка

select {                       // ждать несколько каналов
case v := <-a: ...
case b <- x: ...
case <-time.After(d): ...      // таймаут
default: ...                   // неблокирующая попытка
}

var c chan T                   // nil-канал: блокирует навсегда;
                               // в select — выключенная ветка
```

| Памятка | Суть |
|---|---|
| Закрывает отправитель | получатель — никогда; close один раз |
| send/close в закрытый | паника; receive из закрытого — `ok=false` |
| Небуф = рандеву | гарантия «получатель забрал» |
| Буф = очередь | гарантия только «поставлено в буфер» |
| nil-канал | блокирует навсегда → выключить ветку select |
| `select` среди готовых | случайный выбор (нет приоритета) |
| deadlock-детектор | ловит только тотальную блокировку, не утечку |
| паника в горутине | не пойманная — рушит процесс |
| остановка горутины | только сигналом (done/context), не извне |
