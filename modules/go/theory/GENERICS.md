# Go — Дженерики

> Дженерики появились в Go 1.18 (март 2022) — спустя более десяти лет существования языка.
> До этого Go был известен как «язык без дженериков»: код переиспользовали либо через
> `interface{}` с рефлексией (теряя проверку типов и теряя на скорости), либо генерацией кода
> по шаблону. Понимание того, что именно добавили и почему так осторожно, — ключ к идиоматичному Go.
>
> Аудитория этого файла знает дженерики Java (стирание типов, `<T extends Comparable>`, PECS).
> Поэтому объяснения идут с нуля по Go-синтаксису, но с постоянным контрастом: где Go устроен
> принципиально иначе, чем стирание в Java, — отдельная тема в
> [../../java-core/theory/GENERICS_ERASURE.md](../../java-core/theory/GENERICS_ERASURE.md).

## 1. Что было до дженериков и зачем они понадобились

До 1.18 переиспользуемый «обобщённый» код в Go писали тремя способами, и каждый плох по-своему.

**Способ 1: `interface{}` (пустой интерфейс) + приведение типа.** Пустой интерфейс удовлетворяется любым типом — это аналог `Object` в Java. Контейнер на `interface{}` принимает что угодно, но на выходе вы получаете `interface{}` и обязаны привести значение обратно вручную:

```go
type Stack struct {
    items []interface{} // в любой может лежать что угодно
}

func (s *Stack) Push(x interface{}) { s.items = append(s.items, x) }
func (s *Stack) Pop() interface{}   { /* ... */ return s.items[len(s.items)-1] }

// На месте использования — приведение типа, проверяемое только в рантайме:
s := &Stack{}
s.Push(42)
n := s.Pop().(int) // паника, если там не int
```

Минусы: нет проверки типов на этапе компиляции (можно положить `int`, а достать как `string` и упасть в рантайме); приведение типа на каждом доступе; для типов-значений — лишняя упаковка в интерфейс (аллокация и косвенность, см. [./PERFORMANCE_PROFILING.md](./PERFORMANCE_PROFILING.md)).

**Способ 2: рефлексия (`reflect`).** Для по-настоящему универсальных функций (например, копирование произвольной структуры) использовали пакет `reflect`. Это ещё медленнее, ещё многословнее и полностью обходит проверку типов.

**Способ 3: кодогенерация.** Инструменты вроде `go generate` штамповали по шаблону копию контейнера под каждый тип (`IntStack`, `StringStack`). Типобезопасно и быстро, но это внешний этап сборки, дублирование исходников и боль при сопровождении.

Дженерики закрывают всю эту нишу: типобезопасность пустого интерфейса **плюс** проверка на этапе компиляции **плюс** отсутствие приведений в коде-потребителе.

> Терминологическая заметка: в Go их официально называют **type parameters** (параметры типа), а не «generics», хотя в обиходе говорят и так. Спецификация — раздел «Type Parameters» в [go.dev/ref/spec](https://go.dev/ref/spec).

## 2. Параметры типа: синтаксис

Параметр типа объявляется в **квадратных скобках** перед обычным списком параметров функции (или после имени типа). Java использует угловые скобки `<T>`, Go — квадратные `[T]`, потому что угловые в Go-грамматике уже заняты операторами сравнения.

### 2.1 Дженерик-функция

```go
// T — параметр типа. any — его ограничение (constraint): "любой тип".
// any — это псевдоним для interface{}, добавленный в 1.18 ради читаемости.
func Map[T any, U any](s []T, f func(T) U) []U {
    r := make([]U, len(s))
    for i, v := range s {
        r[i] = f(v)
    }
    return r
}
```

Читается так: «функция `Map` параметризована двумя типами `T` и `U` (оба — `any`); принимает срез `[]T` и функцию `func(T) U`; возвращает `[]U`». Контраст с Java: `static <T, U> List<U> map(List<T> s, Function<T,U> f)` — там параметры типа стоят перед возвращаемым типом, в Go — в скобках сразу после имени.

### 2.2 Дженерик-тип

Параметризовать можно структуру, и тогда параметр типа указывается после имени типа:

```go
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(x T) { s.items = append(s.items, x) }

func (s *Stack[T]) Pop() (T, bool) {
    var zero T // нулевое значение типа T — об этом ниже
    if len(s.items) == 0 {
        return zero, false
    }
    x := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return x, true
}
```

Важная деталь о методах: метод объявляется на **`*Stack[T]`**, а не на `*Stack`. Параметр типа из объявления типа повторяется в receiver. При этом сам метод **не вводит новых** параметров типа — он лишь использует `T` из типа (см. раздел 5 про запрет параметризованных методов).

### 2.3 Нулевое значение параметра типа: `var zero T`

В Go у каждого типа есть нулевое значение: `0` для чисел, `""` для строк, `nil` для указателей/срезов/map/интерфейсов, обнулённые поля для структур. Внутри дженерик-кода конкретный тип неизвестен, поэтому «вернуть нулевое значение `T`» записывают идиомой `var zero T` (объявление без инициализатора даёт нулевое значение). Эквивалент — `*new(T)` (работает с Go 1.0), но `var zero T` остаётся каноном. Это аналог проблемы «нельзя написать `new T()` при стирании» в Java — но решается чище, без хаков с `Class<T>`.

## 3. Инстанцирование и вывод типов (type inference)

**Инстанцирование** — подстановка конкретных типов вместо параметров. Бывает явной и выведенной.

```go
// Явное инстанцирование: указываем типы в квадратных скобках.
doubled := Map[int, int]([]int{1, 2, 3}, func(x int) int { return x * 2 })

// Вывод типов: компилятор сам определяет T=int, U=string из аргументов.
labels := Map([]int{1, 2, 3}, func(x int) string { return strconv.Itoa(x) })
```

Вывод типов в Go устроен по фактическим аргументам функции (function argument type inference) и по уже известным параметрам (constraint type inference). Практическое правило: если все параметры типа встречаются в обычных аргументах, скобки можно опустить. Если параметр типа **не** выводится из аргументов (например, появляется только в возвращаемом типе), его придётся указать явно.

```go
// U встречается только в типе результата — вывести нельзя, нужно явно указать оба:
func Zero[T any, U any]() (T, U) { var t T; var u U; return t, u }
a, b := Zero[int, string]()
```

Для дженерик-**типов** вывод при инстанцировании ограничен: чаще указывают тип явно — `s := &Stack[int]{}`. Это похоже на Java до «ромба» `<>`, но Go-вывод для типов слабее, чем Java diamond operator.

## 4. Constraints (ограничения)

Параметр `any` разрешает любой тип, но тогда внутри функции с `T` почти **ничего нельзя сделать**: нельзя сложить, сравнить через `<`, нельзя даже сравнить на равенство `==`. Чтобы разрешить операции, на параметр типа накладывают **ограничение (constraint)** — оно описывает, какие типы допустимы и, как следствие, какие операции над ними разрешены.

В Go ограничение — это **интерфейс**. Но интерфейс в роли ограничения расширен: помимо набора методов он может задавать **множество типов** (type set).

### 4.1 Встроенные ограничения: `any` и `comparable`

| Ограничение | Что разрешает | Аналог в Java |
|---|---|---|
| `any` | любой тип; операций над `T` почти нет | `<T>` без bound (`T extends Object`) |
| `comparable` | типы, для которых легальны `==` и `!=` | примерно `<T>`, но в Java нет такого встроенного ограничения «сравнимо через `equals`/`==`» |

`comparable` — встроенное ограничение для типов, поддерживающих операторы `==`/`!=` (числа, строки, булевы, указатели, каналы, интерфейсы, массивы и структуры из сравнимых полей). Именно `comparable` нужен, чтобы тип годился в ключ `map` или в множество:

```go
type Set[T comparable] struct {
    m map[T]struct{} // struct{} — пустая структура, занимает 0 байт
}

func (s *Set[T]) Add(x T)      { s.m[x] = struct{}{} }
func (s *Set[T]) Contains(x T) bool { _, ok := s.m[x]; return ok }
```

Если бы тут стояло `T any`, компилятор бы отверг `map[T]...`: не любой тип сравним (например, срезы и map несравнимы), а ключ `map` обязан быть сравнимым.

### 4.2 Type sets, `~T` (underlying type) и объединения

Самая мощная часть — задание **множества типов** прямо в интерфейсе-ограничении:

```go
// Ограничение "целое число со знаком": перечисление через | (объединение, union).
type Signed interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64
}

func Sum[T Signed](s []T) T {
    var total T
    for _, v := range s {
        total += v // оператор + легален: все типы множества его поддерживают
    }
    return total
}
```

Два новых элемента синтаксиса:

- **`|` (объединение, union)** — «любой из перечисленных типов». Внутри `Sum` над `T` разрешены те операции, что общие для всего множества (для целых это `+ - * / < > == ...`).
- **`~T` (approximation, аппроксимация по underlying type)** — «любой тип, чей **базовый тип** (underlying type) равен `T`». Это критично из-за **именованных типов** (defined types) Go:

```go
type Celsius float64 // именованный тип с underlying float64

// Ограничение ~float64 принимает и сам float64, и Celsius, и любой type X float64.
// Ограничение float64 (без ~) приняло бы ТОЛЬКО ровно float64, но не Celsius.
```

В Java аналога `~T` нет вовсе: там нет «именованных типов поверх примитивов» в этом смысле, а ограничения задаются только через `extends`/`super` по иерархии классов. Go-`~` отражает другую модель: тип может иметь то же представление, но другое имя, и обобщённый код почти всегда хочет принимать **оба**. Практическое правило: пишите `~int`, а не `int`, если не уверены — иначе пользовательский `type Score int` неожиданно не подойдёт.

### 4.3 Ограничение с методами и с типами одновременно

Интерфейс-ограничение может смешивать методы и множество типов:

```go
type Number interface {
    ~int | ~int64 | ~float64
    // можно было бы добавить и методы, тогда тип обязан и входить в множество, и иметь метод
}
```

> Тонкость: интерфейс, содержащий множество типов (с `|` или `~`), можно использовать **только как ограничение**. Как обычный тип переменной (`var x Number`) он недопустим — это ограничение существует на этапе компиляции и не имеет рантайм-представления.

### 4.4 Готовые ограничения: `cmp.Ordered` и `golang.org/x/exp/constraints`

Постоянно переписывать «все упорядоченные типы» неудобно, поэтому есть готовые наборы.

Исторически их давал пакет `golang.org/x/exp/constraints` (вне стандартной библиотеки): `constraints.Ordered`, `Integer`, `Float`, `Signed`, `Unsigned`. В Go 1.21 ключевой из них **стандартизировали** в виде типа `cmp.Ordered` в стандартной библиотеке (пакет `cmp`):

```go
import "cmp"

// cmp.Ordered = все типы, поддерживающие < <= >= > (числа и строки, с ~).
func Max[T cmp.Ordered](s []T) (T, error) {
    if len(s) == 0 {
        var zero T
        return zero, errors.New("Max: empty slice")
    }
    m := s[0]
    for _, v := range s[1:] {
        if v > m {
            m = v
        }
    }
    return m, nil
}
```

`cmp.Ordered` — это в точности `~int | ~int8 | ... | ~float64 | ~string` (все упорядоченные базовые типы с тильдой). Пакет `cmp` даёт и функции `cmp.Compare`, `cmp.Less`, `cmp.Or`. Для большинства задач сегодня нужен именно стандартный `cmp.Ordered`, а `x/exp/constraints` берут лишь когда нужны более узкие наборы (`Integer`, `Unsigned`), которых в `cmp` нет.

## 5. Методы и дженерики: почему НЕТ параметризованных методов

Это один из самых частых вопросов и одна из главных асимметрий с Java. В Java метод может вводить **собственный** параметр типа независимо от класса: `<R> List<R> map(Function<T,R> f)`. В Go так **нельзя**.

**Правило: параметры типа разрешены только у функций верхнего уровня и у объявлений типов. У методов — нет.**

```go
type Container[T any] struct{ items []T }

// ✅ Разрешено: метод использует T из ТИПА Container.
func (c Container[T]) Len() int { return len(c.items) }

// ❌ ЗАПРЕЩЕНО: метод вводит СВОЙ параметр типа U.
// func (c Container[T]) Map[U any](f func(T) U) Container[U] { ... }
// compile error: methods cannot have type parameters
```

Поэтому идиоматичный «map над контейнером» в Go — это **свободная функция**, а не метод:

```go
func MapContainer[T, U any](c Container[T], f func(T) U) Container[U] { /* ... */ }
```

**Почему такой запрет (дизайн-обоснование).** Параметризованные методы плохо сочетаются со структурной типизацией интерфейсов Go. Интерфейс — это фиксированный набор сигнатур; если бы метод мог иметь свой параметр типа, проверка «реализует ли тип интерфейс» потребовала бы инстанцировать метод под бесконечное число типов — это, по сути, означало бы полную мономорфизацию во время компоновки и ломало бы возможность вызывать метод через интерфейс динамически. Авторы языка сознательно оставили методы без параметров типа, чтобы интерфейсы и method sets оставались простыми (см. обсуждение в [go.dev/blog/when-generics](https://go.dev/blog/when-generics)). Практическое следствие: проектируйте обобщённые алгоритмы как функции; типы параметризуйте для хранения данных.

## 6. Когда применять дженерики, а когда нет

Официальная рекомендация (go.dev/blog/when-generics) сводится к тезису: **«дженерики — для кода, а не для типов»** в том смысле, что начинать стоит с реальной потребности устранить дублирование над разными типами, а не вводить параметры «на будущее».

**Стоит применять, когда:**

- **Контейнеры общего назначения**: `Stack[T]`, `Set[T]`, очередь, дерево, кэш. Их форма не зависит от типа элемента.
- **Алгоритмы над срезами и map**, одинаковые для всех типов элементов: `Map`, `Filter`, `Reduce`, `Keys`, `Max`. Стандартная библиотека уже даёт это в пакетах **`slices`** и **`maps`**: `slices.Sort`, `slices.Contains`, `slices.Max`, `slices.Index` (с Go 1.21), `maps.Keys`, `maps.Values` (с Go 1.23, возвращают `iter.Seq`). Прежде чем писать свой дженерик-helper — проверьте, нет ли его там.
- Когда без дженериков остаётся только `interface{}` + приведение типа или кодогенерация.

**НЕ стоит применять, когда:**

- **Достаточно обычного интерфейса.** Если функция вызывает у аргумента лишь методы (`Read`, `String`, `Write`), берите интерфейс-параметр, а не `[T SomeInterface]`. Интерфейс уже даёт полиморфизм; дженерик тут только усложняет сигнатуру без выгоды. Это главный анти-паттерн новичков, пришедших из Java.

```go
// ❌ Лишний дженерик: T используется только ради вызова метода Read.
func ReadAll[T io.Reader](r T) ([]byte, error) { /* ... */ }

// ✅ Проще и идиоматичнее — обычный интерфейс-параметр:
func ReadAll(r io.Reader) ([]byte, error) { /* ... */ }
```

- **Когда тип ровно один.** Если реально нужен только `int`, не параметризуйте — напишите конкретный тип.
- **Ради «гибкости на будущее».** Преждевременное обобщение усложняет чтение и сигнатуры. Добавляйте параметр типа тогда, когда появилось второе-третье место с тем же кодом для другого типа.

Эвристика go.dev/blog/when-generics: дженерики уместны, когда разные конкретные реализации **выглядели бы идентично** строка в строку.

## 7. Реализация: GC shape stenciling + dictionaries (контраст с Java erasure)

Это — главный «under the hood» вопрос на собеседовании и место, где Go радикально отличается от Java.

### 7.1 Два крайних подхода и компромисс Go

Есть два классических способа компилировать дженерики:

| Подход | Кто использует | Суть | Минусы |
|---|---|---|---|
| **Полная мономорфизация** | C++ templates, Rust | компилятор генерирует **отдельную копию кода** под каждый конкретный тип | раздувание бинарника, медленная компиляция |
| **Полное стирание (erasure)** | **Java** | типы стираются до `Object`/верхней границы, генерируется **один** код, на границах вставляются приведения | значения-примитивы упаковываются (boxing); тип недоступен в рантайме (`new T()` нельзя, `instanceof T` нельзя) |

Go выбрал **средний путь — GC shape stenciling со словарями (dictionaries)**.

### 7.2 Как это работает

**GC shape (форма для сборщика мусора)** — это классификация типов по тому, как они выглядят **для сборщика мусора и аллокатора**: грубо, по размеру и по расположению указателей внутри значения. Ключевая идея: все **указательные типы** (`*int`, `*string`, любой `*T`, а также `map`, каналы, функции — то, что внутри одно машинное слово-указатель) имеют **одну и ту же GC shape**. А вот `int`, `float64`, `struct{...}`, а ещё срезы (3 слова: ptr/len/cap) и интерфейсы (2 слова: тип + данные) имеют каждый свою, отдельную форму.

Компилятор генерирует **одну копию машинного кода на каждую GC shape**, а не на каждый тип (это «stenciling» — штамповка по трафарету формы). То есть `List[*User]`, `List[*Order]`, `List[*Anything]` делят **один** скомпилированный код, потому что все указатели — одна форма. А `List[int]` и `List[float64]` получат свои копии.

**Dictionary (словарь)** — это скрытый дополнительный аргумент, который компилятор неявно передаёт в дженерик-функцию. Поскольку один код обслуживает несколько типов одной формы, ему нужна рантайм-информация о **конкретном** типе: его точный размер, как сравнивать/хешировать (для `comparable`), таблицы методов для вызовов через ограничение, какой `itab` подставить при упаковке в интерфейс. Всё это лежит в словаре. Грубая аналогия: словарь — это «виртуальная таблица для параметра типа», передаваемая сбоку.

### 7.3 Контраст с Java type erasure

Каноническая теория стирания — в [../../java-core/theory/GENERICS_ERASURE.md](../../java-core/theory/GENERICS_ERASURE.md) (там же про bridge methods, reifiable/non-reifiable, PECS). Здесь — только сравнение моделей:

| Аспект | Java (erasure) | Go (GC shape stenciling + dictionaries) |
|---|---|---|
| Сколько копий кода | одна (полное стирание до `Object`/bound) | одна **на GC shape** (не на тип, но и не одна на всё) |
| Тип в рантайме | стёрт; `new T()`, `T.class`, `T[]` недоступны | доступен через словарь; `var zero T`, размер, методы — есть |
| Значения-примитивы | **упаковываются** (autoboxing `int`→`Integer`) | **не упаковываются**: `List[int]` хранит `int` напрямую, без boxing |
| Стоимость вызова | приведения на границах, но мономорфные вызовы | косвенность через словарь для значений-типов; для указателей — один код |
| Bridge methods / синтетика | да, генерируются компилятором | нет такого механизма |
| Раздувание бинарника | нет | умеренное (копия на форму, не на тип) |

Ключевые тезисы для собеседования:
1. **В Go нет стирания до `Object`.** Параметр типа не теряется — рантайм-информация о нём доступна через словарь, поэтому работают `var zero T`, корректные размеры, методы ограничения.
2. **Но это и не полная мономорфизация, как в C++/Rust.** Типы одной GC shape (в частности, все указательные) делят код — отсюда «словарь» как способ донести отличия конкретного типа.
3. **Главный практический выигрыш над Java** — отсутствие упаковки значений: `[]int` внутри дженерик-контейнера остаётся `[]int`, без `Integer`-обёрток и лишних аллокаций.

### 7.4 Влияние на производительность

Картина неоднозначная (детали и бенчмарки — [./PERFORMANCE_PROFILING.md](./PERFORMANCE_PROFILING.md)):

- Для **типов-значений** (`int`, мелкие структуры) дженерики обычно **выигрывают** у `interface{}`: нет упаковки и нет рантайм-приведений.
- Но вызов **метода** ограничения через словарь может оказаться **не инлайнящимся** косвенным вызовом — иногда обобщённый код по `[T Stringer]` чуть медленнее, чем тот же код по конкретному типу или даже по интерфейсу, из-за словаря. Это контринтуитивно для пришедших из Java: «дженерик» не всегда быстрее «интерфейса».
- Вывод: дженерики — про типобезопасность и переиспользование; выигрыш в скорости реален для значений, но не гарантирован для всех случаев. Меряйте, не угадывайте.

## 8. Частые ошибки

### 8.1 Чрезмерные дженерики там, где хватило бы интерфейса

```go
// ❌ Параметр типа не нужен: используется только метод интерфейса.
func Print[T fmt.Stringer](x T) { fmt.Println(x.String()) }
// ✅ Обычный интерфейс-параметр:
func Print(x fmt.Stringer) { fmt.Println(x.String()) }
```
Бери дженерик только если параметр типа нужен в **нескольких** местах сигнатуры (например, `[]T` на входе и `T` на выходе) или для устранения boxing значений.

### 8.2 Попытка параметризовать метод

```go
// ❌ Не компилируется: methods cannot have type parameters.
func (c Cache[K, V]) GetOrCompute[R any](...) { }
```
Выноси в свободную функцию: `func GetOrCompute[K comparable, V, R any](c Cache[K,V], ...)`.

### 8.3 Забыли `~` в ограничении — не подходит именованный тип

```go
type Ordered interface{ int | float64 } // без тильды!
type Age int
// Sum[Age](...) // ошибка: Age НЕ входит в множество {int, float64},
//               // потому что само множество не аппроксимировано (~).
```
Правильно: `~int | ~float64`. Или используйте готовый `cmp.Ordered`, где `~` уже стоит.

### 8.4 Операция, не разрешённая ограничением

```go
func Sum[T any](s []T) T {
    var total T
    for _, v := range s {
        total += v // ❌ оператор + не определён для произвольного any
    }
    return total
}
```
`any` не гарантирует ни `+`, ни `<`, ни даже `==`. Под `+` нужно `cmp.Ordered`-подобное числовое ограничение (или `constraints.Integer | Float`); под `==` — `comparable`; под `<` — `cmp.Ordered`.

### 8.5 Сравнение `==` под `any` вместо `comparable`

```go
func Index[T any](s []T, target T) int {
    for i, v := range s {
        if v == target { // ❌ == не разрешён для any (срезы/map несравнимы)
            return i
        }
    }
    return -1
}
```
Нужно `[T comparable]`. Либо, если элементы могут быть несравнимы, принимайте функцию-предикат `eq func(T, T) bool`.

### 8.6 Интерфейс-ограничение в роли обычного типа

```go
type Number interface{ ~int | ~float64 }
var x Number // ❌ интерфейс с множеством типов нельзя использовать как тип переменной
```
Такой интерфейс существует только как ограничение в `[T Number]`.

### 8.7 Ожидание мономорфизации «как в C++»

Не закладывайтесь на то, что `Stack[*A]` и `Stack[*B]` дадут разный машинный код: у них одна GC shape, код общий, различия — через словарь. Это влияет на инлайнинг и микро-оптимизации (раздел 7.4).
