# Go — Слайсы, maps и строки

> Три структуры данных, которые встречаются в каждой программе на Go: динамический список (слайс),
> ассоциативный массив (map) и строка. Все три устроены не так, как привычные `ArrayList`,
> `HashMap` и `String` в Java — и именно эти отличия порождают самые частые ошибки новичков.
> Опираемся на [основы синтаксиса](./BASICS.md) и [типы/структуры](./TYPES_STRUCTS_METHODS.md);
> вопросы памяти и сборки мусора — в [./MEMORY_GC.md](./MEMORY_GC.md).

Аудитория — разработчик из Java/Kotlin, видящий Go впервые. Главная мысль этого файла: в Go
**слайс и map — это маленькие значения-дескрипторы (descriptor), указывающие на общую память**.
Скопировали слайс — скопировали дескриптор, но не данные за ним. Отсюда и aliasing, и сюрпризы
с `append`. Строка же, наоборот, неизменяема и измеряется в **байтах**, а не в символах. Разберём
всё «как и почему», с упором на ловушки.

## 1. Массивы: фиксированный размер — часть типа

Массив в Go — это **последовательность фиксированной длины** из элементов одного типа. Ключевое и
непривычное: **длина входит в тип**. `[3]int` и `[4]int` — это два разных, несовместимых типа.

```go
var a [3]int        // [0 0 0] — длина 3, часть типа
b := [3]int{1, 2, 3}
c := [...]int{1, 2, 3, 4}   // [...] — компилятор сам посчитает длину: тип [4]int
```

Из-за этого `[3]int` нельзя присвоить переменной типа `[4]int` — это ошибка компиляции, а не runtime.
В Java длина массива в тип не входит (`int[]` — один тип для любой длины), поэтому это поведение
удивляет.

### Значимая семантика: копирование при передаче

Массив — это **значение** (как структура из [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md)).
Присваивание и передача в функцию **копируют массив целиком**, а не ссылку на него:

```go
func zero(arr [3]int) { arr[0] = 999 }   // меняет КОПИЮ

a := [3]int{1, 2, 3}
b := a          // b — независимая копия всех трёх элементов
b[0] = 9        // a[0] по-прежнему 1
zero(a)         // a не изменился: внутри функции своя копия
```

В Java ссылка на массив передаётся **по значению** (Java strictly pass-by-value): обе ссылки указывают
на один объект-массив, поэтому `void zero(int[] arr)` меняет его элементы у вызывающего — но замена
`arr = new int[]{…}` внутри метода оригинал не затронет. В Go массив — это **значение**, а не ссылка:
чтобы менять оригинал, передают `*[3]int` (указатель). Передача большого массива по значению копирует
все байты — это и оверхед, и причина, по которой массивы в API почти не используют напрямую.

### Когда нужны массивы

В прикладном коде массивы нужны редко — почти всегда берут слайс. Массив оправдан, когда:
- размер **фиксирован и известен на этапе компиляции** и является частью контракта: ключ AES-256
  (`[32]byte`), хеш SHA-256 (`[32]byte`), IPv4-адрес (`[4]byte`);
- нужна **значимая семантика** (копирование, сравнимость через `==`, использование как ключ map);
- важно избежать аллокации на куче — фиксированный массив часто остаётся на стеке.

Массивы **сравнимы** оператором `==` (поэлементно), если сравним тип элемента, — в отличие от слайсов,
которые сравнивать через `==` нельзя вовсе.

## 2. Слайсы: дескриптор поверх массива

Слайс (срез, slice) — это **динамический вид на участок массива**. Он не хранит данные сам; данные
лежат в отдельном **backing-массиве** (англ. backing array — массив-хранилище). Слайс — это всего лишь
маленький **слайс-хедер** (slice header) из трёх полей:

```
slice header (3 машинных слова):
┌─────────────┬──────┬──────┐
│ ptr         │ len  │ cap  │
└──────┬──────┴──────┴──────┘
       │  указывает на элемент backing-массива
       ▼
backing-массив:  [ e0 │ e1 │ e2 │ e3 │ e4 │ e5 │ e6 │ e7 ]
                   ▲                   ▲                 ▲
                   ptr            ptr+len           ptr+cap
                   │◄──── len ────►│                   │
                   │◄──────────── cap ────────────────►│
```

- **`ptr`** — указатель на первый элемент видимого участка;
- **`len`** — длина: сколько элементов «видно» (индексы `0..len-1`, доступ за `len` — паника);
- **`cap`** — ёмкость: сколько элементов помещается от `ptr` до конца backing-массива.

Параллель с Java: `ArrayList` тоже держит внутри массив (`elementData`) и `size`, но он скрыт за
объектом и инкапсулирован. В Go слайс-хедер — это **значение**, которое копируется при присваивании,
а backing-массив остаётся общим. Именно отсюда растёт почти вся специфика.

> `len(s)` и `cap(s)` — встроенные функции, работают за O(1) (просто читают поля хедера). `nil`-слайс
> даёт `len == 0`, `cap == 0`.

### 2.1 Создание слайса

```go
s1 := []int{1, 2, 3}              // литерал: backing-массив [1 2 3], len=cap=3
s2 := make([]int, 5)             // len=5, cap=5, все элементы — zero value (0)
s3 := make([]int, 0, 10)         // len=0, cap=10 — пустой, но место под 10 уже выделено
var s4 []int                     // nil-слайс: ptr=nil, len=0, cap=0 (см. §2.6)

arr := [5]int{10, 20, 30, 40, 50}
s5 := arr[1:4]                   // слайс поверх массива arr: [20 30 40], len=3, cap=4
```

`make([]T, len, cap)` — основной способ заранее выделить ёмкость. Если вы знаете итоговый размер,
задавайте `cap` сразу — это избавит от лишних реаллокаций при `append` (см. §3). Это аналог
`new ArrayList<>(capacity)` в Java, только ёмкость здесь — третий аргумент.

### 2.2 Индексирование и слайсинг

```go
s := []int{0, 1, 2, 3, 4}
s[2]        // 2 — доступ по индексу
s[1:4]      // под-слайс: элементы с 1 по 3 (4 не включён) → [1 2 3]
s[:3]       // от начала → [0 1 2]
s[2:]       // до конца → [2 3 4]
s[:]        // весь слайс
```

Операция `s[a:b]` создаёт **новый слайс-хедер**, указывающий в тот же backing-массив: `ptr` сдвигается
на `a`, `len = b-a`, а `cap` тянется до конца исходного backing-массива (`cap = cap(s) - a`). **Никакого
копирования данных не происходит** — это и быстро, и опасно (см. §3.2). Полуинтервал `[a:b)` (правый конец
не включён) — та же логика, что у `String.substring` в Java.

### 2.3 Трёхиндексный слайсинг `s[a:b:c]`

Полная форма позволяет **ограничить ёмкость** результата:

```go
s := []int{0, 1, 2, 3, 4}
t := s[1:3:3]      // len = 3-1 = 2, cap = 3-1 = 2 (а не до конца!)
```

Третий индекс `c` задаёт верхнюю границу backing-массива для нового слайса: `cap = c - a`. Зачем это
нужно — главный приём защиты от aliasing: если `cap == len`, то следующий же `append` будет вынужден
**выделить новый backing-массив** и не сможет затереть чужие данные (см. §3.2). Запомните `s[a:b:b]` как
идиому «отрезать слайс так, чтобы append точно реаллоцировал».

## 3. `append` — рост и главная ловушка

`append` добавляет элементы в конец слайса и **возвращает (возможно, новый) слайс**:

```go
s := []int{1, 2, 3}
s = append(s, 4)            // обязательно присвоить результат обратно!
s = append(s, 5, 6, 7)      // можно несколько сразу
s = append(s, other...)     // ... — «распаковать» другой слайс
```

**Результат `append` ОБЯЗАТЕЛЬНО присваивают обратно.** `append` может вернуть слайс с другим `ptr`
(если была реаллокация), и старая переменная тогда указывает на устаревший backing-массив. Забыли
присвоить — потеряли добавленное (а компилятор даже предупредит: «result of append is not used»).

### 3.1 Рост ёмкости: амортизация

Когда `len < cap`, `append` просто кладёт элемент в свободную ячейку backing-массива и увеличивает `len` —
это O(1). Когда `len == cap`, места нет: рантайм **выделяет новый, больший backing-массив, копирует туда
старые элементы** и дописывает новый. Это O(n), но происходит редко.

Стратегия роста — геометрическая (как `ArrayList` в Java, но с другими множителями и порогом):
маленькие слайсы растут примерно **вдвое**, а после некоторого порога (порядка нескольких сотен/тысяч
элементов) множитель снижается в сторону **~1.25×**, чтобы не тратить память слишком расточительно.
Конкретные числа — деталь реализации рантайма и менялись между версиями; полагаться на точное значение
нельзя. Важен сам факт: за счёт геометрического роста суммарная стоимость N добавлений — **амортизированно
O(N)**, отдельный `append` — амортизированно O(1).

```go
s := make([]int, 0)
for i := 0; i < 1000; i++ {
    s = append(s, i)   // изредка реаллокация, в среднем O(1)
}
// Если 1000 известно заранее — лучше make([]int, 0, 1000): ноль реаллокаций.
```

### 3.2 Когда `append` мутирует исходный backing-массив, а когда нет — ГЛАВНАЯ ЛОВУШКА

Это самая частая и коварная ошибка в Go. Поведение `append` зависит от того, **хватило ли `cap`**:

- **`len < cap`** (место есть): `append` пишет **на месте**, в общий backing-массив. Любые другие слайсы,
  видящие ту же ячейку, **увидят изменение**. `ptr` результата не меняется.
- **`len == cap`** (места нет): `append` **аллоцирует новый** backing-массив и копирует туда. Результат
  больше **не связан** с исходным; чужие слайсы не затрагиваются.

Проблема в том, что одно и то же выражение `append` ведёт себя по-разному в зависимости от рантайм-состояния
ёмкости — и это легко проглядеть.

#### Баг: под-слайс + append затирает соседа

```go
all := []int{1, 2, 3, 4, 5}        // len=5, cap=5
head := all[:2]                    // [1 2], НО len=2, cap=5 (тянется до конца all!)

head = append(head, 99)            // len(2) < cap(5) ⇒ пишем НА МЕСТЕ в all[2]
// Теперь:
// head == [1 2 99]
// all  == [1 2 99 4 5]   ← элемент all[2] был 3, стал 99! Сосед затёрт.
```

`head` имел `cap == 5`, потому что слайсинг тянет ёмкость до конца backing-массива. Места хватило,
поэтому `append` записал `99` прямо в `all[2]`, молча испортив `all`. Если бы `head` имел `cap == 2`,
`append` реаллоцировал бы и ничего бы не затёр.

**Как защититься:**

```go
// Вариант 1: трёхиндексный слайсинг ограничивает cap ⇒ append реаллоцирует.
head := all[:2:2]                  // len=2, cap=2
head = append(head, 99)            // cap исчерпан ⇒ новый backing-массив, all цел

// Вариант 2: явная копия, если нужен полностью независимый слайс.
head := make([]int, 2)
copy(head, all[:2])
```

Тот же класс багов проявляется, когда функция принимает слайс, делает `append` и «думает», что работает
с локальной копией. Хедер-то скопирован, а backing-массив — общий. Если вызывающая сторона ещё смотрит в
тот же массив, она может увидеть чужие записи (или, наоборот, не увидеть добавленное, если случилась
реаллокация). Правило: **функция, мутирующая слайс через `append`, должна возвращать результат**, а если
ей нужна независимость — копировать вход.

### 3.3 `append` как идиома слияния

```go
merged := append([]int{}, a...)    // копия a в свежий слайс
merged = append(merged, b...)      // дописать b
```

Первая строка — частая идиома «скопировать слайс»: `append` в пустой (но не `nil` важно: можно и в `nil`)
слайс гарантированно создаёт новый backing-массив, потому что у пустого `cap == 0`.

## 4. `copy`, удаление элемента, обнуление для GC

### 4.1 `copy`

```go
n := copy(dst, src)    // копирует min(len(dst), len(src)) элементов, возвращает это число
```

`copy(dst, src)` копирует элементы из `src` в `dst` поэлементно и возвращает количество скопированных —
это `min(len(dst), len(src))`. `copy` **не** растит `dst`; он пишет только в уже существующие ячейки
(в пределах `len(dst)`). Поэтому типичный паттерн «глубокой копии» выделяет `dst` нужной длины заранее:

```go
dst := make([]int, len(src))
copy(dst, src)                 // теперь dst — независимая копия
```

`copy` корректно работает даже при перекрытии `src` и `dst` (как `memmove`), что используют идиомы сдвига.

### 4.2 Удаление элемента по индексу

В Go нет встроенного `remove(i)` — удаление выражают через слайсинг и `append`/`copy`:

```go
// Удалить элемент с индексом i, СОХРАНЯЯ порядок (сдвиг хвоста влево):
s = append(s[:i], s[i+1:]...)
```

`s[:i]` — всё до `i`; `s[i+1:]...` — всё после `i`, распакованное. `append` сдвигает хвост на место
удалённого. Работает на том же backing-массиве (cap хватает), `len` уменьшается на 1. Это O(n) из-за сдвига.

```go
// Удалить, НЕ сохраняя порядок (быстрее, O(1)): переставить последний на место i.
s[i] = s[len(s)-1]
s = s[:len(s)-1]
```

> В современных версиях (Go 1.21+) есть пакет `slices`: `slices.Delete(s, i, i+1)` делает то же,
> что вариант с сохранением порядка, но дополнительно **обнуляет освободившийся хвост** (см. §4.3).
> Подробнее о пакете — в [./STDLIB_CORE.md](./STDLIB_CORE.md).

### 4.3 Обнуление хвоста для сборки мусора

Когда слайс хранит **указатели или ссылочные типы** (`[]*User`, `[]string`, `[]error`), укорачивание
через `s = s[:len(s)-1]` оставляет старый элемент **в backing-массиве за пределами `len`**. Слайс его уже
не видит, но backing-массив всё ещё держит ссылку — объект **не будет собран сборщиком мусора** (memory
leak — утечка памяти). Поэтому при удалении ссылочных элементов их нужно явно обнулить:

```go
// Удалить последний *User, сохранив порядок, и дать GC собрать объект:
s[len(s)-1] = nil      // стереть ссылку в backing-массиве
s = s[:len(s)-1]

// При удалении из середины со сдвигом — обнулить освободившийся последний слот:
copy(s[i:], s[i+1:])
s[len(s)-1] = nil
s = s[:len(s)-1]
```

Для примитивов (`[]int`, `[]byte`) обнуление не нужно — там нет указателей, держать нечего. Детали
взаимодействия с GC — в [./MEMORY_GC.md](./MEMORY_GC.md).

## 5. Nil-слайс vs пустой слайс

Это два **разных** значения, которые ведут себя почти одинаково — и оба легитимны:

```go
var a []int            // nil-слайс:  ptr=nil, len=0, cap=0,  a == nil → true
b := []int{}           // пустой:     ptr≠nil, len=0, cap=0,  b == nil → false
c := make([]int, 0)    // пустой:     то же, что b
```

| Операция | nil-слайс (`var s []int`) | пустой (`[]int{}`) |
|---|---|---|
| `len(s)` / `cap(s)` | `0` / `0` | `0` / `0` |
| `s == nil` | `true` | `false` |
| `for range s` | 0 итераций (ок) | 0 итераций (ок) |
| `append(s, x)` | работает, создаёт backing-массив | работает |
| `s[0]` | паника (index out of range) | паника |

Практически всё работает одинаково, поэтому **по умолчанию используют `nil`-слайс** как «пустой список» —
это идиоматично и не требует аллокации. Возвращать `nil` вместо `[]T{}` — норма.

### 5.1 Разница в JSON

Единственное частое место, где разница **видна** — сериализация в JSON через `encoding/json`:

```go
type Resp struct {
    Items []int `json:"items"`
}

json.Marshal(Resp{Items: nil})      // {"items":null}
json.Marshal(Resp{Items: []int{}})  // {"items":[]}
```

`nil`-слайс кодируется как `null`, пустой — как `[]`. Для публичных API это важно: фронтенд обычно ждёт
`[]`, а не `null`. Если контракт требует пустой массив — инициализируйте `[]T{}` (или `make([]T, 0)`)
явно, не оставляйте `nil`. Подробнее о `encoding/json` — в [./STDLIB_CORE.md](./STDLIB_CORE.md).

## 6. Maps — ассоциативный массив

`map[K]V` — встроенный **ассоциативный массив** (хеш-таблица). Аналог `HashMap<K,V>` в Java, но с важными
отличиями в семантике nil, итерации и потокобезопасности.

### 6.1 Устройство (кратко)

Под капотом map — это **хеш-таблица с бакетами** (bucket — корзина). Хеш ключа разбивается на две части:
младшие биты выбирают бакет, старшие 8 бит (top-hash) ускоряют поиск внутри бакета. Каждый бакет хранит
небольшое фиксированное число пар (порядка 8); при переполнении подцепляется overflow-бакет. Когда
таблица заполняется выше порога (load factor), происходит **инкрементальный rehash** — рост числа бакетов
с постепенным переносом. Детали — деталь реализации; для собеседования достаточно знать: амортизированный
доступ/вставка/удаление — **O(1)**, ключ должен быть **сравнимым** типом (поддерживать `==`): слайс, map
и функция ключом быть не могут, а структура из сравнимых полей — может.

### 6.2 Создание, доступ, `comma-ok`, `delete`

```go
m := make(map[string]int)        // пустой непустой map (готов к записи)
m := map[string]int{"a": 1, "b": 2}   // литерал

m["c"] = 3                       // вставка/перезапись
v := m["a"]                      // чтение: 1
x := m["zzz"]                    // ОТСУТСТВУЮЩИЙ ключ → zero value (0), НЕ паника!
```

Чтение отсутствующего ключа возвращает **zero value** типа значения, а не ошибку и не панику. Это удобно,
но мешает отличить «ключа нет» от «ключ есть, но значение нулевое». Для этого — форма **`comma-ok`**:

```go
v, ok := m["a"]    // ok == true, v == 1
v, ok := m["zzz"]  // ok == false, v == 0 (zero value)

if v, ok := m[key]; ok {
    // ключ точно есть
}

delete(m, "a")     // удалить ключ; если ключа нет — no-op (не паникует)
```

В Java аналог `comma-ok` — `containsKey` + `get` или `getOrDefault`; в Go это один идиоматичный приём.

### 6.3 Случайный порядок итерации — намеренно

```go
for k, v := range m {
    fmt.Println(k, v)   // порядок ключей СЛУЧАЕН и меняется от запуска к запуску!
}
```

Порядок обхода map **не определён и намеренно рандомизирован** рантаймом: при каждом проходе стартовый
бакет выбирается случайно. Это сделано осознанно — чтобы разработчики **не закладывались** на порядок,
который у хеш-таблицы и так не гарантирован, и чтобы код не ломался при смене реализации. В Java
`HashMap` тоже не гарантирует порядок, но он стабилен в пределах запуска; в Go он плавает даже между
итерациями. Если нужен детерминированный порядок — соберите ключи в слайс и отсортируйте:

```go
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)
for _, k := range keys {
    fmt.Println(k, m[k])
}
```

### 6.4 Nil-map: чтение ок, запись паникует

```go
var m map[string]int     // nil-map (не инициализирован через make/литерал)

_ = m["x"]               // ОК: чтение из nil-map → zero value
_, ok := m["x"]          // ОК: ok == false
len(m)                   // ОК: 0
for range m { }          // ОК: 0 итераций
delete(m, "x")           // ОК: no-op

m["x"] = 1               // ПАНИКА: assignment to entry in nil map
```

Это частая ошибка: объявили `var m map[K]V`, забыли `make`, и при первой же записи — паника в рантайме.
Симметрии с nil-слайсом (куда `append` работает) тут **нет**: в nil-map писать нельзя. Всегда
инициализируйте map через `make(map[K]V)` или литерал перед записью. Поле-map в структуре по умолчанию
`nil` — его тоже нужно инициализировать (например, в конструкторе).

### 6.5 Map не потокобезопасна

Встроенный map **не потокобезопасен**. Конкурентная запись (или запись одновременно с чтением) из разных
горутин — это гонка данных (data race), и рантайм Go её **специально детектирует и аварийно завершает
программу**: `fatal error: concurrent map writes`. Это не паника, которую можно поймать через `recover`, —
это немедленный краш. Защита — внешняя синхронизация (`sync.Mutex` / `sync.RWMutex`) или специализированный
`sync.Map` для некоторых сценариев. Подробно — в [./CONCURRENCY_PATTERNS.md](./CONCURRENCY_PATTERNS.md).

### 6.6 Значение по ключу не адресуемо

Нельзя взять адрес элемента map и нельзя изменить поле структуры-значения «на месте»:

```go
type Point struct{ X, Y int }
m := map[string]Point{"a": {1, 2}}

// m["a"].X = 5     // ОШИБКА КОМПИЛЯЦИИ: cannot assign to struct field m["a"].X
// p := &m["a"]     // ОШИБКА: cannot take the address of m["a"]
```

Причина — при rehash рантайм **перемещает** значения в памяти, поэтому стабильного адреса у элемента нет.
Чтобы изменить поле, нужно достать значение, поменять копию и положить обратно — либо хранить указатели:

```go
p := m["a"]; p.X = 5; m["a"] = p     // достать → изменить → положить
// или сразу map[string]*Point:
m2 := map[string]*Point{"a": {1, 2}}
m2["a"].X = 5                        // ОК: значение — указатель, он адресует структуру на куче
```

## 7. Строки — байты, не символы

Строка в Go — **неизменяемая** последовательность **байтов** (read-only `[]byte`), физически хранящая
текст обычно в кодировке **UTF-8**. Это другой мир по сравнению с Java, где `String` — это
последовательность UTF-16 `char` и `s.length()` считает 16-битные кодовые единицы.

### 7.1 Неизменяемость

```go
s := "привет"
// s[0] = 'X'      // ОШИБКА КОМПИЛЯЦИИ: cannot assign to s[0]
```

Строку нельзя изменить на месте — как `String` в Java. Любая «модификация» создаёт новую строку.
Неизменяемость позволяет безопасно делить backing-память: слайсинг строки (`s[a:b]`) **не копирует**
данные, а возвращает новую строку, ссылающуюся на тот же массив байтов.

### 7.2 `len` — это БАЙТЫ

```go
s := "hello"
len(s)            // 5 — пять ASCII-байтов

s := "привет"
len(s)            // 12, а НЕ 6! Каждая кириллическая буква в UTF-8 — 2 байта.

s := "héllo"
len(s)            // 6: 'h','l','l','o' по 1 байту + 'é' (U+00E9) = 2 байта
```

**`len(строка)` возвращает число байтов, а не количество символов.** Это ловушка №1 при работе с
не-ASCII текстом. Индексирование `s[i]` тоже работает **по байтам** и возвращает `byte` (= `uint8`),
а не «символ»:

```go
s := "héllo"
s[1]              // НЕ 'é', а первый байт UTF-8-последовательности 'é' (0xC3)
```

Чтобы посчитать именно символы (руны), используйте `utf8.RuneCountInString(s)` или `len([]rune(s))`
(см. §7.4).

### 7.3 `byte` vs `rune`

- **`byte`** — псевдоним `uint8`, один байт. `s[i]` даёт `byte`.
- **`rune`** — псевдоним `int32`, один **кодовый пункт** Unicode (code point). Это и есть «символ»
  в смысле Unicode. Литерал в одинарных кавычках — это `rune`: `'A'` == 65, `'é'` == 233, `'世'` == 19990.

Один символ может занимать от 1 до 4 байтов в UTF-8. Поэтому «байт» и «руна» совпадают только для ASCII.

### 7.4 `[]byte` vs `[]rune` — конверсии и их стоимость

```go
s := "héllo"

b := []byte(s)    // байтовое представление: len 6 (КОПИРУЕТ байты)
r := []rune(s)    // руны: len 5 (декодирует UTF-8, КОПИРУЕТ в новый []int32)

string(b)         // обратно в строку (КОПИЯ)
string(r)         // руны → строку (кодирует обратно в UTF-8, КОПИЯ)
```

| Конверсия | Что даёт | Стоимость |
|---|---|---|
| `[]byte(s)` | байты как есть | аллокация + копирование (строка read-only, слайс — нет) |
| `[]rune(s)` | по одному `int32` на символ | аллокация + декодирование UTF-8 |
| `string(b)` | строка из байтов | аллокация + копирование |
| `string(r)` | строка из рун | аллокация + кодирование в UTF-8 |

**Все четыре конверсии копируют** — потому что строка неизменяема, а слайс изменяем; разделять память
нельзя, иначе нарушилась бы неизменяемость. Это оверхед, о котором важно помнить в горячем коде. Частная
ловушка: `string(someInt)` НЕ форматирует число, а интерпретирует `int` как код руны (`string(65)` == `"A"`).
Для «число → текст» нужен `strconv.Itoa` (см. [./STDLIB_CORE.md](./STDLIB_CORE.md)).

### 7.5 Итерация: `range` по рунам vs индекс по байтам

Это критичное различие. **`for range` по строке итерирует по РУНАМ** (декодирует UTF-8), а обычный
`for i := 0; i < len(s); i++` идёт **по БАЙТАМ**:

```go
s := "héllo"

// range: декодирует UTF-8, i — байтовый ОФФСЕТ начала руны, r — сама руна (rune):
for i, r := range s {
    fmt.Printf("%d:%c ", i, r)   // 0:h 1:é 3:l 4:l 5:o   ← оффсет перескочил с 1 на 3 (é = 2 байта)
}

// индексный цикл: по байтам, s[i] — byte (часть многобайтовой руны может «разрезаться»):
for i := 0; i < len(s); i++ {
    fmt.Printf("%d:%d ", i, s[i])   // выдаёт 6 байтов, é развалится на 0xC3 0xA9
}
```

Запомните: индекс в `range` — это **байтовый оффсет**, а не «номер символа», и он может расти не на 1.
Если нужно итерировать по символам (например, считать длину слов на кириллице) — всегда `for range` или
`[]rune`, **никогда** не `s[i]` по диапазону `len`.

### 7.6 `strings.Builder` — эффективная сборка строк (кратко)

Конкатенация в цикле через `+` плодит промежуточные строки (каждая `+` копирует — строки же неизменяемы),
это квадратичный оверхед, как `String +=` в Java. Для построения строки из многих кусков есть
`strings.Builder` — аналог `StringBuilder`:

```go
var b strings.Builder
for i := 0; i < 1000; i++ {
    b.WriteString("x")        // не копирует всю строку каждый раз
}
result := b.String()          // финальная строка — без лишнего копирования
```

`Builder` накапливает байты во внутреннем растущем `[]byte` и отдаёт строку в конце. Детали и другие
инструменты пакета `strings` — в [./STDLIB_CORE.md](./STDLIB_CORE.md).

## 8. Типичные ошибки — чек-лист

| Ошибка | Симптом | Как правильно |
|---|---|---|
| Не присвоить результат `append` | потерянные элементы; «result of append not used» | `s = append(s, x)` |
| `append` в под-слайс затирает соседа | оригинал «портится» сам собой | `s[a:b:b]` или `copy` в новый слайс |
| Полагаться, что слайс-аргумент — копия | функция видит/портит чужой backing-массив | возвращать результат или копировать вход |
| `len(s)` для подсчёта символов не-ASCII | завышенная длина (байты вместо рун) | `utf8.RuneCountInString` / `[]rune` |
| `s[i]` в цикле по не-ASCII строке | руна «разрезается» на байты | `for range s` или `[]rune(s)` |
| Запись в `nil`-map | `panic: assignment to entry in nil map` | `make(map[K]V)` перед записью |
| Расчёт на порядок итерации map | флапающие тесты, нестабильный вывод | собрать ключи в слайс и отсортировать |
| Конкурентная запись в map | `fatal error: concurrent map writes` (краш) | `sync.Mutex` / `sync.RWMutex` / `sync.Map` |
| `&m[key]` или `m[key].Field = …` | ошибка компиляции (не адресуемо) | достать → изменить → положить, или `map[K]*V` |
| Забыть обнулить ссылку при «удалении» из слайса | утечка: объект не собирается GC | `s[last] = nil` перед укорачиванием |
| `string(someInt)` для «числа в текст» | получается руна, а не цифры | `strconv.Itoa(n)` |

## Шпаргалка

```go
// Слайс: дескриптор (ptr,len,cap) поверх общего backing-массива
s := make([]T, len, cap)
s = append(s, x)                 // ВСЕГДА присваивать обратно
sub := s[a:b]                    // общий backing-массив; cap до конца
safe := s[a:b:b]                 // cap ограничен ⇒ append реаллоцирует (защита от aliasing)
dst := make([]T, len(src)); copy(dst, src)   // независимая копия

// Удаление с сохранением порядка
s = append(s[:i], s[i+1:]...)
// Удаление ссылочного элемента + защита от утечки
s[len(s)-1] = nil; s = s[:len(s)-1]

// Map
m := make(map[K]V)               // ОБЯЗАТЕЛЬНО перед записью (nil-map: запись паникует)
v, ok := m[key]                  // comma-ok: отличить отсутствие от zero value
delete(m, key)                   // no-op, если ключа нет
// порядок range случаен — сортируй ключи, если нужен детерминизм

// Строки
len(s)                           // БАЙТЫ, не символы
for i, r := range s { }          // i — байтовый оффсет, r — руна (rune)
n := utf8.RuneCountInString(s)   // число символов
[]rune(s), []byte(s)             // конверсии — КОПИРУЮТ
var b strings.Builder            // эффективная сборка строки
```
