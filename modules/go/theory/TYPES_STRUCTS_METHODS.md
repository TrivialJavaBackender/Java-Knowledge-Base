# Go — Типы, структуры и методы

> Как из примитивных типов собрать свои: структуры, методы на них, указатели и встраивание.
> Главная идея Go: **нет классов, нет наследования** — есть структуры, методы и композиция.
> Интерфейсы здесь только упоминаются — их каноническое место в [./INTERFACES.md](./INTERFACES.md).

---

## 1. Структуры (`struct`)

Структура — это именованный набор полей. Ближайший аналог из Java — класс с полями, но **без методов внутри тела** (методы объявляются отдельно, см. раздел 3) и **без наследования**.

```go
type Point struct {
    X int
    Y int
}
```

`type Point struct { ... }` объявляет новый именованный тип. Поля с заглавной буквы (`X`, `Y`) экспортируются (видны из других пакетов), со строчной — приватны для пакета. Это та же экспорт-семантика, что и для функций (см. [./BASICS.md](./BASICS.md)), только на уровне полей.

В отличие от Java, где объект всегда живёт на куче и передаётся по ссылке, **значение структуры в Go — это просто данные подряд в памяти** (как `struct` в C или как `value class` / `data class` без identity). Присваивание и передача в функцию **копируют структуру целиком**:

```go
a := Point{X: 1, Y: 2}
b := a          // b — независимая копия; b.X = 9 не трогает a
b.X = 9         // a.X по-прежнему 1
```

### 1.1 Инициализация: позиционная vs по полям

Есть два составных литерала:

```go
p1 := Point{1, 2}          // позиционная: значения в порядке объявления полей
p2 := Point{X: 1, Y: 2}    // по именам полей
p3 := Point{X: 1}          // Y получит zero value (0)
p4 := Point{}              // все поля — zero value: {0, 0}
```

**Инициализация по полям предпочтительнее** — это не стиль, а защита от поломки при эволюции типа:

| | Позиционная `Point{1, 2}` | По полям `Point{X: 1, Y: 2}` |
|---|---|---|
| Читаемость | непонятно, что есть что | поле названо явно |
| Добавили поле в `struct` | **не компилируется** (если поле не последнее) или молча сдвигает смысл | продолжает работать, новое поле = zero value |
| Можно пропустить поле | нет, нужны все | да, пропущенные = zero value |
| `go vet` | ругается на позиционные литералы вне пакета | ок |

В Go нет конструкторов как в Java (`new Point(1, 2)`), поэтому составной литерал — основной способ создать значение. Когда нужна логика при создании — пишут функцию-конструктор `NewPoint` (раздел 8).

### 1.2 Анонимные структуры

Структуру можно объявить «на месте», без `type`-имени. Полезно для разовых группировок: таблиц в тестах, временных DTO, конфигов:

```go
// частый случай — таблица для table-driven теста
tests := []struct {
    name string
    in   int
    want int
}{
    {"zero", 0, 0},
    {"one", 1, 1},
}
```

Аналога в Java нет (ближайшее — анонимный класс, но он про интерфейсы, а не про данные). Для постоянных доменных типов анонимные структуры не используют — только для локальных одноразовых.

### 1.3 Пустая структура `struct{}`

`struct{}` — структура **без полей**. Занимает **0 байт** (все её значения делят один адрес в памяти). Это идиоматический способ сказать «значение мне не важно, важен сам факт».

Два канонических применения:

```go
// 1) Множество (set): map[T]struct{} вместо map[T]bool — ноль накладных расходов на значение
seen := map[string]struct{}{}
seen["a"] = struct{}{}              // добавить
_, ok := seen["a"]                  // проверить принадлежность

// 2) Сигнальный канал: передаём «событие произошло», без полезной нагрузки
done := make(chan struct{})
go func() {
    // ... работа ...
    close(done)                     // сигнал: закрытие канала разблокирует получателей
}()
<-done                              // ждём сигнала
```

В Java для множества берут `HashSet<T>` (внутри которого `HashMap<T, Object>` с фиктивным значением-заглушкой `PRESENT`) — Go делает то же явно, но заглушка занимает 0 байт. Сигнальный канал `chan struct{}` концептуально близок к `CountDownLatch` на одно событие.

### 1.4 Сравнимость структур и структура как ключ map

Структура **сравнима оператором `==`**, если сравнимы все её поля (числа, строки, булевы, указатели, массивы сравнимых типов, другие сравнимые структуры). Сравнение поэлементное:

```go
Point{1, 2} == Point{1, 2}     // true — сравниваются все поля
```

Сравнимая структура может быть **ключом map** — никаких `equals`/`hashCode` писать не нужно, рантайм генерирует их автоматически:

```go
type Cell struct{ Row, Col int }
grid := map[Cell]string{}
grid[Cell{1, 2}] = "X"          // структура как составной ключ
```

**Несравнимы** структуры, содержащие слайсы, map или функции — попытка `==` или использования как ключа это **ошибка компиляции**:

```go
type Bad struct{ Tags []string }
// Bad{...} == Bad{...}         // не компилируется: slice can only be compared to nil
```

Контраст с Java: там `equals`/`hashCode` пишутся вручную (или генерируются `record` / Lombok / IDE), и по умолчанию сравнение — по identity (ссылке). В Go сравнение структур всегда **по значению** и встроено в язык. Для сравнения структур со слайсами/map используют `reflect.DeepEqual` (медленно, обычно только в тестах) или пишут свой метод `Equal`.

## 2. Методы на не-структурных типах

Метод в Go можно объявить **на любом именованном типе своего пакета**, не только на структуре. Часто делают именованный тип поверх примитива, чтобы навесить поведение и усилить типобезопасность:

```go
type Celsius float64
type Fahrenheit float64

func (c Celsius) ToF() Fahrenheit {
    return Fahrenheit(c*9/5 + 32)
}

func (c Celsius) String() string {            // метод String() → как toString() в Java
    return strconv.FormatFloat(float64(c), 'f', 1, 64) + "°C"
}
```

`Celsius` и `Fahrenheit` — **разные типы**, хотя оба `float64` под капотом. Случайно сложить градусы Цельсия с Фаренгейтами без явного преобразования нельзя — компилятор это запретит. Это даёт «type safety» уровнем выше, чем сырой `float64` (в Java похожего эффекта добивались бы отдельным классом-обёрткой, что дороже).

### Правило: нельзя добавлять методы к чужим типам

Метод можно объявить **только в том же пакете, где объявлен тип**. Нельзя навесить метод на `int`, на `time.Time` из чужого пакета или на `string`:

```go
// func (s string) Shout() string { ... }   // ❌ не компилируется: cannot define new methods on non-local type string
```

Это сознательное ограничение (в Kotlin есть extension-функции, в Go их **нет**). Обходной путь — объявить свой именованный тип поверх чужого и навесить метод на него:

```go
type MyString string
func (s MyString) Shout() string { return strings.ToUpper(string(s)) }
```

## 3. Методы: объявление и method set

Метод — это функция со специальным параметром-**получателем** (receiver), который пишется в скобках **перед** именем функции:

```go
type Counter struct{ n int }

func (c Counter) Value() int {     // (c Counter) — получатель; c как this/self
    return c.n
}
```

`c` — это «this», но именуется явно (идиома — короткое имя из 1–2 букв, обычно первая буква типа; имена вроде `this`/`self` не приняты).

**Method set** (набор методов) типа — это множество методов, которые можно на нём вызвать. Эта концепция ключевая для интерфейсов (см. [./INTERFACES.md](./INTERFACES.md)), но и для receiver'ов важна: method set типа `T` и method set типа `*T` различаются (см. 4.4).

## 4. Value receiver vs pointer receiver

Это **главная развилка** темы и частый вопрос на собеседовании. Получатель бывает двух видов:

```go
func (c Counter) Value() int      { return c.n }    // value receiver — работает с КОПИЕЙ
func (c *Counter) Inc()           { c.n++ }         // pointer receiver — работает с ОРИГИНАЛОМ
```

### 4.1 Value receiver — копия

При вызове метода с value receiver структура **копируется**. Внутри метода `c` — это локальная копия. Мутация её полей **не видна снаружи**:

```go
func (c Counter) BrokenInc() { c.n++ }   // ❌ инкрементит копию, оригинал не меняется

x := Counter{n: 5}
x.BrokenInc()
// x.n всё ещё 5
```

### 4.2 Pointer receiver — оригинал

При вызове метода с pointer receiver передаётся **указатель** на структуру. Мутация видна снаружи:

```go
func (c *Counter) Inc() { c.n++ }        // ✅ меняет оригинал

x := Counter{n: 5}
x.Inc()
// x.n == 6
```

### 4.3 Когда какой — правила выбора

| Бери **pointer receiver** (`*T`), если… | Бери **value receiver** (`T`), если… |
|---|---|
| метод **мутирует** получателя | тип маленький (несколько слов: числа, маленькие структуры) |
| структура большая — копировать дорого | тип неизменяемый по дизайну (`time.Time`, `Celsius`) |
| тип содержит `sync.Mutex` или другой **не-копируемый** | метод только читает и не нужна идентичность |
| нужна согласованность с другими методами типа (см. 4.5) | нужна семантика значения (две копии «равны») |

Эвристика по умолчанию: **сомневаешься — бери pointer receiver.** Он покрывает мутацию, избегает копирования и почти всегда безопасен. Value receiver — осознанный выбор для маленьких неизменяемых типов.

### 4.4 Автоматическое разыменование при вызове

Go **автоматически берёт адрес или разыменовывает** при вызове метода — синтаксис вызова `x.Method()` одинаков для обоих видов receiver, стрелки `->` как в C нет:

```go
x := Counter{}
x.Inc()        // компилятор подставляет (&x).Inc() — берёт адрес автоматически

p := &Counter{}
p.Value()      // компилятор подставляет (*p).Value() — разыменовывает автоматически
```

**Важная тонкость:** взять адрес автоматически можно только у **адресуемого** значения (переменная, поле переменной, элемент слайса). У значения из map адрес взять нельзя — поэтому вызвать pointer-receiver метод на элементе map напрямую **не получится**:

```go
m := map[string]Counter{"a": {}}
// m["a"].Inc()        // ❌ не компилируется: m["a"] не адресуем
c := m["a"]; c.Inc(); m["a"] = c   // обходной путь: достать, изменить, положить обратно
```

### 4.5 Согласованность receiver'ов

Идиоматическое правило: **все методы одного типа должны использовать один вид receiver** — либо все value, либо все pointer. Смешивать не стоит. Причины:

1. **Method set и интерфейсы.** Method set типа `T` включает только value-receiver методы; method set типа `*T` включает и value-, и pointer-receiver. Если часть методов на `*T`, то интерфейс реализует только `*T`, не `T` — и легко получить запутанную ошибку «`Counter` does not implement `Iface`» (детали — в [./INTERFACES.md](./INTERFACES.md)).
2. **Копирование.** Если хоть один метод pointer-receiver (т.е. тип «хочет» мутироваться/иметь identity), копировать значение опасно — `go vet` и линтеры на это ругаются.

Практически: если хоть одному методу нужен pointer receiver — делай pointer-receiver **все** методы типа.

## 5. Указатели в Go

Указатель — это адрес значения в памяти. Синтаксис как в C, но **без арифметики указателей** (нельзя `p++`, нельзя двигаться по памяти) — это закрывает целый класс ошибок и нужно сборщику мусора.

```go
x := 42
p := &x        // &x — взять адрес; p имеет тип *int
fmt.Println(*p)  // *p — разыменовать; печатает 42
*p = 100         // запись через указатель; теперь x == 100
```

| Оператор | Значение |
|---|---|
| `&x` | взять адрес `x` (получить указатель) |
| `*p` | разыменовать `p` (получить значение) |
| `*int` | **тип**: «указатель на int» |

Сравнение с Java/Kotlin: там все ссылочные типы (объекты) — это неявные указатели, а явного оператора «взять адрес» нет. В Go указатель **явный и опциональный**: можно передать структуру по значению (копия) либо `*Struct` (по адресу) — выбор за вами. Это и есть та самая развилка value vs pointer из раздела 4.

**Нулевое значение указателя — `nil`.** Разыменование `nil`-указателя — это `panic` (аналог `NullPointerException`), но в Go ловится через `recover` (см. [./ERRORS_PANIC.md](./ERRORS_PANIC.md)).

### 5.1 `new` vs составной литерал

Создать значение и сразу получить указатель можно двумя способами:

```go
p1 := new(Counter)       // выделяет zero-value Counter, возвращает *Counter
p2 := &Counter{}         // то же самое, но через составной литерал
p3 := &Counter{n: 5}     // составной литерал позволяет сразу задать поля
```

`new(T)` встречается редко (только когда нужен указатель на zero value примитива, например `*int`). **Идиоматичнее `&T{...}`** — он позволяет сразу инициализировать поля и читается естественнее. Аналога `new` из Java здесь нет: `new(T)` не вызывает никакого «конструктора», просто обнуляет память.

### 5.2 Стек или куча — решает компилятор (escape analysis)

В Java объекты почти всегда на куче, примитивы и ссылки — на стеке; программист на это не влияет. В Go **компилятор сам решает**, где разместить значение, с помощью **escape analysis**:

- значение, **не выходящее** за пределы функции → на **стеке** (дёшево, освобождается при возврате, GC не нагружается);
- значение, чей адрес **«убегает»** наружу (вернули `&x` из функции, положили в поле, передали в горутину) → на **куче** (управляется GC).

```go
func makeCounter() *Counter {
    c := Counter{n: 0}    // адрес уходит наружу через return → c «убегает» на кучу
    return &c             // в Go это безопасно: GC не даст значению исчезнуть
}
```

Ключевое отличие от C: **вернуть указатель на локальную переменную безопасно** — компилятор разместит её на куче, висячего указателя (dangling pointer) не будет. Подробно про escape analysis, GC и cost-модель — в [./MEMORY_GC.md](./MEMORY_GC.md).

## 6. Встраивание (embedding): композиция вместо наследования

В Go **нет наследования** (`extends`), нет классов, нет `super`. Переиспользование кода строится на **композиции**. Встраивание — синтаксический сахар, который делает композицию удобной: встроенный тип записывается **без имени поля**, и его поля и методы **продвигаются** (promoted) во внешний тип.

```go
type Engine struct {
    Power int
}

func (e Engine) Start() string { return "engine started" }

type Car struct {
    Engine          // встроенное поле — без имени, только тип
    Brand string
}
```

Теперь у `Car` поля и методы `Engine` доступны напрямую, будто они свои:

```go
c := Car{Engine: Engine{Power: 200}, Brand: "Tesla"}
c.Power            // 200 — продвинутое поле (на самом деле c.Engine.Power)
c.Start()          // "engine started" — продвинутый метод
```

Это **похоже** на наследование внешне, но устроено принципиально иначе:

| | Java-наследование (`Car extends Engine`) | Go-встраивание (`Engine` внутри `Car`) |
|---|---|---|
| Отношение | «is-a» (Car является Engine) | «has-a» (Car содержит Engine) |
| Полиморфизм | `Engine e = new Car()` работает | `Car` **не является** `Engine`; присвоить нельзя |
| Доступ к «родителю» | `super.start()` | `c.Engine.Start()` — обычное поле |
| Переопределение | виртуальные методы, late binding | shadowing (см. 6.2), **без** виртуальной диспетчеризации |

Главное: встраивание **не создаёт подтип**. `Car` нельзя использовать там, где ждут `Engine`. Полиморфизм в Go достигается **через интерфейсы**, а не через встраивание (см. [./INTERFACES.md](./INTERFACES.md)). Встраивание — это про переиспользование/делегирование, интерфейсы — про полиморфизм.

### 6.1 Встраивание — это делегирование, а не подмена

Продвинутый метод вызывается с получателем **встроенного** значения, а не внешнего. У `Engine.Start()` нет доступа к полям `Car` — он «не знает» про внешний тип. Это обычная композиция с автоматически сгенерированными методами-«пробросами», а не виртуальный вызов. Поэтому Go-встраивание свободно от классической проблемы хрупкого базового класса: нет восходящих вызовов от «родителя» к «потомку».

### 6.2 Переопределение (shadowing) продвинутых методов

Если внешний тип объявляет метод **с тем же именем**, что и встроенный, — внешний **затеняет** (shadow) встроенный. Виртуальной диспетчеризации нет: какой метод вызовется, определяется **статически по типу выражения**.

```go
func (c Car) Start() string {            // затеняет Engine.Start
    return "car starting: " + c.Engine.Start()   // явно зовём встроенный
}

c.Start()          // "car starting: engine started" — вызван метод Car
c.Engine.Start()   // "engine started" — встроенный напрямую
```

Поскольку диспетчеризация статическая, нельзя (как в Java через виртуальные методы) «подменить» поведение, которое встроенный тип вызывает внутри себя. Если `Engine` внутри одного своего метода вызывает другой свой метод, он вызовет **свой**, а не затеняющий из `Car`. Это снова контраст с late binding в Java.

### 6.3 Встраивание интерфейса в структуру

Можно встроить не только структуру, но и **интерфейс**. Тогда внешний тип получает все методы интерфейса как продвинутые — а реальную реализацию подставляют через поле. Краткие применения (детали — в [./INTERFACES.md](./INTERFACES.md)):

```go
type ReadCloser struct {
    io.Reader        // встроенный интерфейс: продвигает метод Read
    io.Closer        // продвигает метод Close
}
```

Частый приём — встроить интерфейс, чтобы в тесте/декораторе переопределить **один** метод, а остальные «пробросить» в вложенную реализацию.

### 6.4 Неоднозначность («диамонд») и её разрешение

Если два встроенных типа дают поле/метод с **одинаковым именем** на одной глубине, обращение к нему без уточнения — **ошибка компиляции** (неоднозначность). Go не выбирает «по приоритету», а заставляет уточнить явно:

```go
type A struct{ ID int }
type B struct{ ID int }
type C struct {
    A
    B
}

var c C
// c.ID        // ❌ ambiguous selector c.ID
c.A.ID         // ✅ явное уточнение
c.B.ID         // ✅
```

Правило разрешения: **меньшая глубина побеждает**. Поле, объявленное прямо во внешней структуре (глубина 0), затеняет одноимённое продвинутое (глубина 1). Конфликт возникает только при **равной** глубине, и тогда требуется явное уточнение. Это аккуратнее, чем диамонд-наследование в C++/Java-интерфейсах, потому что компилятор не молчит, а требует выбрать.

## 7. Теги полей (struct tags)

К каждому полю структуры можно прикрепить **тег** — строковый литерал в обратных кавычках после типа поля. Тег — это метаданные, которые сам Go **игнорирует**; их читают библиотеки через рефлексию. Ближайший аналог — аннотации в Java (`@JsonProperty`, `@Column`), но тег — просто строка, не типизированная конструкция.

```go
type User struct {
    ID    int    `json:"id"`
    Name  string `json:"name"`
    Email string `json:"email,omitempty"`   // omitempty — не сериализовать, если пусто
    pass  string `json:"-"`                  // "-" — игнорировать поле при сериализации
}
```

Синтаксис тега — соглашение: `ключ:"значение"` через пробел, ключ — имя библиотеки (`json`, `xml`, `db`, `validate`). Пример с `encoding/json`:

```go
u := User{ID: 1, Name: "Ann"}
b, _ := json.Marshal(u)   // {"id":1,"name":"Ann"}  — поля переименованы по тегам
```

Читаются теги через пакет `reflect` (детали и работа `encoding/json` — в [./STDLIB_CORE.md](./STDLIB_CORE.md)):

```go
f, _ := reflect.TypeOf(User{}).FieldByName("Email")
tag := f.Tag.Get("json")   // "email,omitempty"
```

Поскольку тег — нетипизированная строка, опечатка в нём (`jsom:"id"`) **не вызовет ошибки компиляции** — поле просто будет сериализовано с именем по умолчанию. Это частый источник тихих багов; `go vet` умеет проверять корректность синтаксиса тега (`go vet` → `structtag`).

## 8. `type` definition vs `type` alias

Две внешне похожие конструкции с разным смыслом:

```go
type Celsius float64       // DEFINITION — НОВЫЙ тип, отдельный от float64
type Centigrade = Celsius  // ALIAS (знак =) — ДРУГОЕ ИМЯ того же типа
```

| | Definition `type A B` | Alias `type A = B` |
|---|---|---|
| Создаёт новый тип | **да** | нет — `A` и `B` тождественны |
| Method set | начинается **пустым** (методы `B` не наследуются) | полностью совпадает с `B` |
| Присваивание без преобразования | требует явного `A(x)` | свободно, это одно и то же |
| Зачем | новый домен-тип, типобезопасность, свои методы | постепенный рефакторинг/переезд типа между пакетами без поломки кода |

Definition — основной инструмент (им создают `Celsius`, доменные типы, типы с методами). **Alias нужен редко** — в основном при переименовании/переносе типа в другой пакет, когда нужно временно сохранить старое имя работающим. Канонический пример из stdlib: `type any = interface{}` — `any` это просто псевдоним пустого интерфейса, добавленный в Go 1.18.

```go
type Celsius float64
type Centigrade = Celsius

var t Celsius = 20
var s Centigrade = t   // ✅ ok: alias — тот же тип, преобразование не нужно

type Kelvin float64
var k Kelvin = t       // ❌ не компилируется: Kelvin и Celsius — разные типы (нужно Kelvin(t))
```

## 9. Конструкторы-функции (`NewX`) и zero-value-дизайн

В Go **нет конструкторов на уровне языка** — нет `new ClassName(...)` с пользовательской логикой, нет ключевого слова, гарантированно вызываемого при создании. Есть два подхода.

**Подход А — zero value useful.** Спроектировать тип так, чтобы его **нулевое значение было сразу пригодно к использованию** без всякой инициализации. Это идиома Go (детали — в [./IDIOMS_PATTERNS.md](./IDIOMS_PATTERNS.md)). Классические примеры из stdlib:

```go
var mu sync.Mutex          // готов к Lock() без инициализации
var buf bytes.Buffer       // готов к записи: buf.WriteString("hi")
var b strings.Builder      // готов к Build
```

Контраст с Java, где `new StringBuilder()` обязателен. Если zero value пригоден — конструктор не нужен вовсе, и это **лучший** дизайн.

**Подход Б — функция-конструктор `NewX`.** Когда при создании нужна логика (валидация, неочевидные дефолты, выделение внутренних ресурсов), пишут обычную функцию по соглашению `New<Тип>`, возвращающую значение или указатель (и, часто, `error`):

```go
type Server struct {
    addr    string
    timeout time.Duration
}

func NewServer(addr string) (*Server, error) {
    if addr == "" {
        return nil, errors.New("addr is required")
    }
    return &Server{
        addr:    addr,
        timeout: 30 * time.Second,   // неочевидный дефолт
    }, nil
}
```

Соглашения об именах:
- Если пакет экспортирует **один основной тип** — конструктор называют просто `New` (вызов: `package.New()`, например `list.New()`).
- Если типов несколько — `NewServer`, `NewClient` и т.д.
- Возврат `error` — когда создание может не удаться (валидация); иначе возвращают только значение.

Когда параметров много и большинство опциональны — вместо телескопических конструкторов применяют паттерн **functional options** (`NewServer(addr, WithTimeout(5s), WithTLS(cfg))`), он подробно разобран в [./IDIOMS_PATTERNS.md](./IDIOMS_PATTERNS.md).

## 10. Типичные ошибки

### 10.1 Value receiver там, где нужна мутация

```go
func (c Counter) Inc() { c.n++ }   // ❌ инкрементит копию; снаружи ничего не меняется
```
Хотели менять оригинал — нужен `func (c *Counter) Inc()`. Это ошибка №1 у новичков из Java, где «всё по ссылке».

### 10.2 Копирование структуры с `sync.Mutex`

```go
type Cache struct {
    mu sync.Mutex
    m  map[string]int
}
func (c Cache) Get(k string) int {   // ❌ value receiver КОПИРУЕТ мьютекс
    c.mu.Lock(); defer c.mu.Unlock() // блокируется копия — защита не работает
    return c.m[k]
}
```
`sync.Mutex` нельзя копировать — копия защищает не то же состояние. Нужен pointer receiver и передача `*Cache`. `go vet` ловит это правилом `copylocks`.

### 10.3 Смешанные receiver'ы и «does not implement»

Часть методов на `T`, часть на `*T` → ломается реализация интерфейса (method set `T` уже, чем `*T`), и появляется загадочное «`X` does not implement `Iface`». Лечение — единый вид receiver для всех методов типа (см. 4.5 и [./INTERFACES.md](./INTERFACES.md)).

### 10.4 Позиционный литерал и эволюция структуры

```go
type Config struct{ Host string; Port int }
c := Config{"localhost", 8080}     // ❌ хрупко
```
Добавят поле в середину — смысл молча поедет или сломается компиляция. Всегда `Config{Host: "localhost", Port: 8080}`.

### 10.5 Структура со слайсом как ключ map

```go
type Key struct{ Parts []string }
m := map[Key]int{}                 // ❌ не компилируется: slice can only be compared to nil
```
Ключ map обязан быть сравнимым. Слайс/map/функция в составе — несравнимы. Замена: массив фиксированной длины, строка (например, `strings.Join`), или отдельный сравнимый тип ключа.

### 10.6 Путаница: встраивание ≠ наследование

```go
func process(e Engine) { ... }
var c Car
// process(c)         // ❌ Car НЕ является Engine; передать нельзя
process(c.Engine)     // ✅ передаём встроенное значение явно
```
Встраивание не даёт подтипа. Нужен полиморфизм — определяйте интерфейс ([./INTERFACES.md](./INTERFACES.md)).

## Шпаргалка

```go
// Структура + инициализация по полям (предпочтительно)
type Point struct{ X, Y int }
p := Point{X: 1, Y: 2}

// Пустая структура: множество и сигнал
set := map[string]struct{}{}
done := make(chan struct{})

// Метод на не-структурном типе
type Celsius float64
func (c Celsius) ToF() Fahrenheit { return Fahrenheit(c*9/5 + 32) }

// Value receiver (копия, чтение) vs pointer receiver (оригинал, мутация)
func (c Counter) Value() int { return c.n }   // читает
func (c *Counter) Inc()      { c.n++ }        // мутирует

// Указатель: & адрес, * разыменование; арифметики нет
x := 42; p := &x; *p = 100

// Встраивание = композиция (НЕ наследование)
type Car struct{ Engine; Brand string }
c.Start()        // продвинутый метод; c.Engine.Start() — встроенный явно

// Тег поля (метаданные для библиотек)
type User struct{ Name string `json:"name,omitempty"` }

// definition (новый тип) vs alias (= то же имя)
type Celsius float64       // новый тип
type Centigrade = Celsius  // псевдоним

// Конструктор-функция, когда zero value не достаточно
func NewServer(addr string) (*Server, error) { ... }
```
