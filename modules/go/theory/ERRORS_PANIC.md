# Go — Ошибки, panic и defer

> В Go **ошибки — это значения**, а не исключения. Нет `try/catch`, нет иерархии `Throwable`, нет проверяемых исключений. Функция, которая может сбоить, возвращает `error` последним результатом, а вызывающий код **обязан** его проверить.
>
> `panic`/`recover` существуют, но это **не** замена исключениям: паника — для невосстановимых программных ошибок, а не для штатного управления потоком.

Для разработчика из Java это самый непривычный сдвиг: то, что вы привыкли выражать через `throw`/`catch`, в Go выражается через обычный возврат значения и `if`. Где параллель с Java помогает — она проведена; но держите в голове: **ошибка в Go — это данные, которые текут по обычному пути возврата**, а не управляющий поток, который выпрыгивает из стека.

## 1. Интерфейс `error`

`error` — встроенный интерфейс из одного метода:

```go
type error interface {
    Error() string
}
```

Любой тип с методом `Error() string` **является** ошибкой (структурная типизация, см. [INTERFACES](./INTERFACES.md)). Нулевое значение интерфейса — `nil`; именно с ним сравнивают результат.

Каноническая идиома — **ранний возврат при ошибке**:

```go
func ReadConfig(path string) (*Config, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, err          // прокидываем ошибку наверх
    }
    cfg, err := parse(data)
    if err != nil {
        return nil, err
    }
    return cfg, nil              // успех: error == nil
}
```

Соглашения, которые нарушать не принято:

- `error` — **последний** результат функции: `(T, error)`, `(T1, T2, error)`.
- При ошибке остальные результаты — нулевые значения (`nil`, `0`, `""`), на них **нельзя полагаться**. Проверяйте `err`, а не `data`.
- `nil`-ошибка означает успех. Не возвращайте `non-nil` «успешную» ошибку.

### Почему Go отказался от исключений

| Аспект | Исключения (Java) | Ошибки-значения (Go) |
|---|---|---|
| Видимость | сигнатура `throws` есть не всегда (unchecked) | `error` явно в сигнатуре, виден всегда |
| Поток управления | невидимый прыжок из стека | обычный возврат, читается сверху вниз |
| Принуждение | можно забыть `catch` | компилятор/`go vet`/линтеры ловят непроверенный `err` |
| Стоимость | раскрутка стека + захват трассы | просто возврат значения, дёшево |

Дизайн-философия Go: ошибка — **ожидаемый** результат операции (файла нет, сеть отвалилась), значит её надо обрабатывать **локально и явно**, а не «где-то выше» невидимым прыжком. Цена — многословность (`if err != nil` повторяется часто); выгода — на месте каждого вызова видно, что может пойти не так и кто за это отвечает.

> Это не значит «у Go нет стектрейсов». Их нет в самом `error` по умолчанию — но контекст добавляется оборачиванием (раздел 4), а трассу при необходимости даёт сторонняя библиотека или `panic`.

## 2. Создание ошибок

### `errors.New` и `fmt.Errorf`

```go
import (
    "errors"
    "fmt"
)

err1 := errors.New("connection refused")
err2 := fmt.Errorf("user %d not found", id)   // с форматированием
```

- `errors.New(text)` — простейшая ошибка с фиксированным сообщением.
- `fmt.Errorf(format, args...)` — когда в сообщение нужно подставить значения.

Обе возвращают значение, реализующее `error`. Под капотом `errors.New` — это `*errors.errorString`, но снаружи это просто `error`; сравнивать такие ошибки **по значению через `==` нельзя** (две разные `errors.New("x")` не равны).

### Sentinel errors

**Sentinel** (часовой) — заранее объявленная переменная-ошибка, экспортируемая пакетом как часть API. Вызывающий сравнивает результат именно с ней.

```go
package store

import "errors"

var ErrNotFound = errors.New("store: not found")

func (s *Store) Get(id string) (Item, error) {
    item, ok := s.data[id]
    if !ok {
        return Item{}, ErrNotFound
    }
    return item, nil
}
```

```go
item, err := s.Get(id)
if errors.Is(err, store.ErrNotFound) {   // см. раздел 4 — почему Is, а не ==
    // обрабатываем «нет такого»
}
```

Канонический пример из stdlib — `io.EOF`, `sql.ErrNoRows`, `os.ErrNotExist`.

**Чем sentinel хрупки:**

1. **Жёсткая связанность по API.** Sentinel становится частью публичного контракта: переименуете/удалите переменную — сломаете всех потребителей. Текст менять можно, идентификатор — нет.
2. **Циклы импорта.** Чтобы сравнить с `pkg.ErrX`, потребитель импортирует `pkg`. Иногда это тянет нежелательную зависимость.
3. **Соблазн злоупотребления.** Десятки sentinel на каждый чих превращают пакет в свалку экспортируемых переменных (антипаттерн, раздел 5).

Рекомендация: sentinel хорош для **небольшого числа** общих, стабильных состояний («не найдено», «доступ запрещён»). Для богатого контекста — кастомный тип ошибки.

## 3. Кастомные типы ошибок

Когда ошибке нужны **поля** (какое поле невалидно, какой код ответа, сколько осталось попыток) — объявляют структуру, реализующую `error`:

```go
type ValidationError struct {
    Field string
    Value any
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed for field %q: invalid value %v", e.Field, e.Value)
}
```

```go
func Validate(u User) error {
    if u.Name == "" {
        return &ValidationError{Field: "name", Value: u.Name}
    }
    return nil
}
```

Доступ к полям у вызывающего — через `errors.As` (раздел 4), который умеет искать нужный тип в цепочке обёрток:

```go
err := Validate(u)
var ve *ValidationError
if errors.As(err, &ve) {
    log.Printf("поле %s невалидно", ve.Field)   // доступ к полю
}
```

### Ловушка: указатель-receiver и typed nil

Чаще всего метод `Error()` объявляют на **указателе** (`*ValidationError`), а ошибку возвращают как `&ValidationError{...}`. Это важно для `errors.As` (он ищет `*ValidationError`) и спасает от классической ловушки **typed nil** (подробно — в [INTERFACES](./INTERFACES.md)):

```go
func bad() error {
    var e *ValidationError   // nil-указатель
    return e                 // ❌ интерфейс НЕ nil: внутри (тип=*ValidationError, значение=nil)
}

if bad() != nil {            // true! хотя «ошибки» по смыслу нет
    // сработает — частый баг
}
```

Правило: возвращайте `nil` буквально (`return nil`), а не nil-указатель на тип ошибки.

## 4. Оборачивание ошибок (Go 1.13+)

До 1.13 контекст добавляли через `fmt.Errorf("...: %v", err)` — но это **затирало** исходную ошибку: получалась новая строка, по которой уже не сравнить с sentinel и не извлечь тип. Go 1.13 ввёл **обёртки** (wrapping): глагол `%w` сохраняет исходную ошибку внутри новой, образуя **цепочку**.

```go
func loadUser(id int) (*User, error) {
    row, err := db.Query(id)
    if err != nil {
        return nil, fmt.Errorf("loadUser %d: %w", id, err)   // оборачиваем
    }
    ...
}
```

Сообщение получится `loadUser 42: connection refused`, но при этом исходная ошибка **достижима** программно.

### `%w` против `%v`

| Глагол | Что делает | Когда |
|---|---|---|
| `%w` | оборачивает: исходная ошибка остаётся в цепочке, доступна для `Is`/`As`/`Unwrap` | вызывающему важно **различать** причину (sentinel/тип) |
| `%v` | форматирует в текст: исходная ошибка «расплющивается» в строку, цепочка обрывается | причина — деталь реализации, наружу её знать не надо |

Правило: `%w` — когда ошибка часть контракта (потребитель может на неё реагировать). `%v` — когда вы намеренно **скрываете** внутреннюю причину (инкапсуляция). В одном `Errorf` допустим **только один** `%w`; для нескольких — `errors.Join` (ниже).

### `errors.Unwrap`, `errors.Is`, `errors.As`

Три функции из пакета `errors` работают с цепочкой:

```go
errors.Unwrap(err)        // снимает один слой обёртки; nil, если разворачивать нечего
errors.Is(err, target)    // есть ли в цепочке ошибка, равная target (по == или методу Is)
errors.As(err, &target)   // есть ли в цепочке ошибка типа target; если да — присваивает
```

- **`errors.Is(err, ErrNotFound)`** — «является ли (где-то в цепочке) этой конкретной ошибкой». Заменяет `err == ErrNotFound`, который ломается, как только ошибку обернули. Проходит цепочку через `Unwrap` и сравнивает каждый слой.

```go
if errors.Is(err, sql.ErrNoRows) {        // сработает даже если err обёрнута
    return defaultValue, nil
}
```

- **`errors.As(err, &target)`** — «есть ли в цепочке ошибка такого **типа**»; если да — извлекает её в `target` (отсюда доступ к полям). `target` — всегда **указатель** на переменную нужного типа ошибки.

```go
var pathErr *fs.PathError
if errors.As(err, &pathErr) {
    log.Printf("операция %s над %s сбоила", pathErr.Op, pathErr.Path)
}
```

Аналогия с Java — но с оговоркой: `errors.Is` ≈ «поймать конкретный экземпляр», `errors.As` ≈ `catch (SpecificException e)` с доступом к `e.getField()`. Разница в том, что здесь **нет throw/catch** — это обычные функции над значением, которое уже у вас в руках.

> Кастомные `Is(target error) bool` и `Unwrap() error` можно реализовать на своём типе, чтобы управлять семантикой сравнения и разворачивания. Это нужно редко — обычно достаточно `%w` и стандартного обхода.

### Множественное оборачивание: `errors.Join` (Go 1.20)

Иногда нужно вернуть **несколько** ошибок сразу (накопленные ошибки валидации, отказы нескольких параллельных задач). `errors.Join` объединяет их в одну; `errors.Is`/`errors.As` проверяют **все** ветви.

```go
func validateAll(u User) error {
    var errs []error
    if u.Name == "" {
        errs = append(errs, ErrEmptyName)
    }
    if u.Age < 0 {
        errs = append(errs, ErrNegativeAge)
    }
    return errors.Join(errs...)   // nil, если errs пуст
}
```

```go
err := validateAll(u)
errors.Is(err, ErrEmptyName)    // true, если имя пустое — проверяет обе ветви
errors.Is(err, ErrNegativeAge)  // true, если возраст отрицательный
```

`errors.Join` пропускает `nil`-элементы и возвращает `nil`, если все аргументы `nil` (или список пуст) — удобно накапливать в срез без лишних проверок. В `Errorf` тоже допустимо несколько `%w` (с Go 1.20) — это эквивалент `Join`.

## 5. Антипаттерны обработки ошибок

| Антипаттерн | Почему плохо | Как правильно |
|---|---|---|
| Сравнение по строке: `if err.Error() == "not found"` | текст — не контракт, ломается от любой правки/обёртки/локали | `errors.Is(err, ErrNotFound)` |
| Чрезмерные sentinel: переменная на каждую мелочь | раздувает API, жёсткая связанность, циклы импорта | один тип ошибки с полем-дискриминатором или код |
| Потеря контекста: `return err` без обёртки в глубоком стеке | на верхнем уровне непонятно, **где** и **почему** сбоило | `fmt.Errorf("operation X: %w", err)` на каждом значимом слое |
| **Log-and-return**: `log.Println(err); return err` | одна ошибка логируется N раз на каждом уровне — шум в логах | обработать **или** прокинуть, но не оба; логировать на **одной** границе |
| Проглатывание: `_ = doSomething()` | ошибка молча теряется; `go vet`/`errcheck` ругаются | проверить `err`; если намеренно игнорируем — комментарий почему |
| Затирание через `%v`, когда нужен `Is` | потребитель не сможет распознать причину | `%w`, если причина — часть контракта |

Про **log-and-throw** в общесистемном смысле (антипаттерн логирования и проброса) — см. также [инфраструктурную теорию логирования](../../infrastructure/theory/LOGGING.md). Здесь правило короткое: **либо** обработай ошибку, **либо** добавь контекст и верни — но не делай и то, и другое на каждом уровне.

> Идиома «оборачивай при пересечении границы пакета/слоя, обрабатывай на верхнем уровне» — золотая середина между «`return err` без контекста» и «лог на каждом кадре стека». Подробнее о стиле раннего возврата — в [IDIOMS_PATTERNS](./IDIOMS_PATTERNS.md).

## 6. `panic` и `recover`

`panic` — механизм аварийного завершения. Когда вызывается `panic(v)`:

1. Текущая функция **немедленно** прекращает нормальное выполнение.
2. Начинается **раскрутка стека**: выполняются все отложенные (`defer`) вызовы текущей и вышестоящих функций — в порядке LIFO.
3. Если ни один `defer` не вызвал `recover`, программа **падает**, печатая сообщение и трассу стека всех горутин, с ненулевым кодом выхода.

```go
func mustPositive(n int) {
    if n <= 0 {
        panic(fmt.Sprintf("expected positive, got %d", n))
    }
}
```

`recover` **останавливает** раскрутку и возвращает значение, переданное в `panic`. Ключевое правило: **`recover` работает только внутри `defer`**. Вызванный напрямую — он возвращает `nil` и ничего не делает.

```go
func safeCall() (err error) {
    defer func() {
        if r := recover(); r != nil {       // recover ТОЛЬКО в defer
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    riskyOperation()                        // может паниковать
    return nil
}
```

### Когда паника **уместна**

- **Программистские баги** — нарушения инвариантов, которые в корректной программе невозможны: индекс за границей, разыменование `nil`, «недостижимая» ветвь `switch`. Тут паника = «контракт нарушен, продолжать бессмысленно».
- **Инициализация пакета** (`init`, построение глобальных таблиц): если без ресурса программа в принципе не может работать — `panic` на старте лучше, чем тихая поломка в рантайме. Идиома `MustCompile` (`regexp.MustCompile`) — паникует при невалидном входе, потому что он известен на этапе разработки.

### Когда паника **неуместна**

- **Штатные, ожидаемые сбои** — файл не найден, невалидный ввод пользователя, сеть отвалилась. Это `error`, а не паника. Использовать панику как «дешёвый throw» — антипаттерн: вызывающий не увидит этого в сигнатуре и не сможет нормально обработать.

> Правило большого пальца: *библиотека* почти никогда не должна паниковать наружу — она возвращает `error`. Паника допустима внутри, но её **ловят на границе** и конвертируют в `error`.

### `recover` на границе

Типичный сценарий — не дать панике в одном обработчике обрушить весь процесс. В HTTP-сервере это middleware, оборачивающее каждый запрос: паника в одном хендлере превращается в `500`, остальные запросы живут. Стандартный `net/http` уже делает это для своих обработчиков; в своих воркер-пулах и обёртках паттерн воспроизводят вручную (подробнее — в [NET_HTTP](./NET_HTTP.md)).

```go
func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("panic: %v", rec)
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

## 7. `defer` — отложенный вызов

`defer` откладывает вызов функции до момента **выхода из объемлющей функции** (через `return`, конец тела или панику). Главное применение — гарантированное освобождение ресурсов рядом с их захватом.

```go
func process(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()        // выполнится при любом выходе из process
    // ... работа с f; сколько бы return-ов ни было, Close гарантирован
    return nil
}
```

Аналог — `try-with-resources`/`finally` в Java, но привязка не к блоку, а к **функции**, и синтаксис — одна строка рядом с захватом ресурса.

### Семантика LIFO

Несколько `defer` выполняются в **обратном** порядке (стек):

```go
func demo() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}
// Вывод: 3, 2, 1
```

Это естественно для вложенных ресурсов: что захвачено последним — освобождается первым.

### Ловушка №1: аргументы вычисляются в момент `defer`

Аргументы отложенного вызова вычисляются **сразу**, когда исполняется строка `defer`, а не в момент фактического вызова на выходе.

```go
func trap() {
    i := 0
    defer fmt.Println("deferred:", i)   // аргумент i ВЫЧИСЛЕН здесь: 0
    i = 42
    fmt.Println("normal:", i)           // 42
}
// Вывод:
//   normal: 42
//   deferred: 0      <- зафиксировано значение на момент defer
```

Чтобы «видеть» финальное значение, оберните в **замыкание** (оно захватывает переменную, а не её копию):

```go
defer func() { fmt.Println("deferred:", i) }()   // прочитает i на выходе: 42
```

> Тонкость: получатель метода — тоже аргумент. `defer f.Close()` фиксирует **значение `f`** на момент `defer`; если потом переприсвоить `f`, закроется старое.

### Ловушка №2: `defer` + named return

Отложенная функция выполняется **после** вычисления возвращаемого выражения, но **до** фактического выхода. Через **именованный результат** она может его **изменить** — это легальный и распространённый приём (например, обернуть ошибку или восстановиться из паники).

```go
func withWrap() (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("withWrap: %w", err)   // модифицируем named return
        }
    }()
    return doSomething()   // если вернёт ошибку — defer её обернёт
}
```

Именно так `recover` (раздел 6) превращает панику в `error`: ловит `recover()` и присваивает именованному `err`. Без именованного результата изменить возвращаемое значение из `defer` нельзя.

### Ловушка №3: `defer` в цикле

`defer` привязан к **функции**, а не к итерации. В цикле отложенные вызовы **накапливаются** и срабатывают все разом только при выходе из функции — ресурсы не освобождаются вовремя, копится память (и дескрипторы):

```go
func leak(paths []string) error {
    for _, p := range paths {
        f, err := os.Open(p)
        if err != nil {
            return err
        }
        defer f.Close()   // ❌ накопится N открытых файлов до конца leak
        use(f)
    }
    return nil
}
```

Решение — вынести тело итерации в **отдельную функцию** (тогда `defer` сработает на каждой итерации):

```go
func ok(paths []string) error {
    for _, p := range paths {
        if err := handle(p); err != nil {   // defer внутри handle — на каждой итерации
            return err
        }
    }
    return nil
}

func handle(p string) error {
    f, err := os.Open(p)
    if err != nil {
        return err
    }
    defer f.Close()   // ✅ закроется в конце handle, т.е. каждую итерацию
    use(f)
    return nil
}
```

Подробнее о стоимости `defer` и аккумуляции в горячем цикле — в [PERFORMANCE_PROFILING](./PERFORMANCE_PROFILING.md).

### Типичные применения `defer`

```go
mu.Lock()
defer mu.Unlock()           // разблокировка при любом выходе — самый частый паттерн

f, _ := os.Open(path)
defer f.Close()             // закрытие файла

tx, _ := db.Begin()
defer tx.Rollback()         // откат, если не дошли до Commit (Commit делает Rollback no-op)
```

## 8. Паника в горутине рушит процесс

Критично и часто проверяется на собеседовании: **`recover` действует только в пределах своей горутины.** Паника в горутине, не пойманная **внутри неё самой**, обрушивает **весь процесс** — никакой внешний `defer/recover` её не перехватит.

```go
func main() {
    defer func() {
        recover()   // ❌ НЕ поймает панику из горутины ниже
    }()

    go func() {
        panic("boom")   // обрушит весь процесс
    }()

    time.Sleep(time.Second)
    // программа упадёт: defer в main не относится к стеку горутины
}
```

Правильно — ставить `recover` **внутри** самой горутины (или в обёртке, через которую её запускают):

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("goroutine panic: %v", r)
        }
    }()
    riskyWork()
}()
```

Это прямое следствие модели горутин: у каждой свой стек, и раскрутка не пересекает границу `go`. Поэтому в воркер-пулах и фоновых задачах **обязательно** оборачивают тело горутины в `recover`, иначе один сбойный таск убьёт всё приложение. Подробнее о запуске и жизненном цикле горутин — в [GOROUTINES_CHANNELS](./GOROUTINES_CHANNELS.md), а о безопасных воркер-пулах — в [CONCURRENCY_PATTERNS](./CONCURRENCY_PATTERNS.md).

## Шпаргалка

```go
// Идиома: ранний возврат
if err != nil {
    return nil, err
}

// Оборачивание с контекстом (часть контракта → %w)
return fmt.Errorf("loadUser %d: %w", id, err)

// Скрыть причину (инкапсуляция → %v)
return fmt.Errorf("internal failure: %v", err)

// Проверка причины по цепочке
if errors.Is(err, ErrNotFound) { ... }

// Извлечение типа + доступ к полям
var ve *ValidationError
if errors.As(err, &ve) { use(ve.Field) }

// Несколько ошибок сразу (1.20+)
return errors.Join(err1, err2, err3)

// panic → error на границе (через named return)
func safe() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    return risky()
}

// defer: освобождение ресурса рядом с захватом
mu.Lock()
defer mu.Unlock()

// Ловушка: аргумент defer зафиксирован сейчас
defer fmt.Println(i)            // значение i на момент defer
defer func() { fmt.Println(i) }()   // значение i на выходе

// Ловушка: defer в цикле — вынеси тело в функцию
for _, p := range paths {
    if err := handle(p); err != nil { return err }  // defer внутри handle
}

// Горутина: recover ВНУТРИ неё
go func() {
    defer func() { recover() }()
    work()
}()
```

| Памятка | Суть |
|---|---|
| `error` — значение | проверяй `if err != nil`, не лови исключение |
| `%w` vs `%v` | `%w` — причина в контракте; `%v` — причина скрыта |
| `errors.Is` | сравнение с конкретной ошибкой по цепочке |
| `errors.As` | извлечение по типу + доступ к полям |
| `errors.Join` | объединить несколько ошибок (1.20+) |
| `panic` | для багов/инвариантов, не для штатных сбоев |
| `recover` | только в `defer`; только своя горутина |
| `defer` LIFO | обратный порядок; аргументы вычислены сразу |
| `defer` + named return | можно изменить результат (обёртка/recover) |
| `defer` в цикле | накапливается — выноси тело в функцию |
| паника в горутине | не пойманная внутри — рушит процесс |
