# Go — Память, GC и модель памяти

> Три связанные темы под одной крышей. **Модель памяти** Go отвечает на вопрос «когда запись
> одной горутины гарантированно видна другой» (happens-before в терминах Go).
> **Распределение памяти** — где живут объекты (стек или куча) и как это решает компилятор
> (escape analysis). **Сборщик мусора** — конкурентный, tri-color, non-moving — объясняет,
> почему у Go очень короткие паузы и как их настраивают (`GOGC`, `GOMEMLIMIT`).

Аудитория — разработчик из Java/Kotlin, знакомый с JMM и устройством GC на JVM (поколения,
G1/ZGC, tri-color, write barrier). Поэтому общие концепции **не переопределяются**, а берутся
по ссылке у их канонических владельцев:

- общий **happens-before** и модель памяти (JMM) — каноника в
  [../../concurrency/theory/THREADS_BASICS.md](../../concurrency/theory/THREADS_BASICS.md);
- общие определения **data race / гонок / взаимоблокировок** — в
  [../../concurrency/theory/PROBLEMS.md](../../concurrency/theory/PROBLEMS.md);
- общий **tri-color invariant** и **write barrier (GC)** — в
  [../../java-core/theory/GARBAGE_COLLECTION.md](../../java-core/theory/GARBAGE_COLLECTION.md).

Здесь — то, что **специфично для Go**: его конкретные гарантии happens-before, инструмент
`-race`, escape analysis Go, рост стека горутины и параметры сборщика Go.

## 1. Модель памяти Go: happens-before по-Go

Общий смысл отношения happens-before (если A *happens-before* B, то эффекты A видны в B)
разобран на стороне JVM в
[../../concurrency/theory/THREADS_BASICS.md](../../concurrency/theory/THREADS_BASICS.md). Идея
одинаковая; различается **набор примитивов**, устанавливающих это отношение. Спецификация
«The Go Memory Model» задаёт следующие гарантии (это Go-специфика).

### Базовое правило внутри одной горутины

В пределах **одной** горутины чтения и записи происходят в порядке исходного текста (с учётом
компиляторных/процессорных переупорядочиваний, не нарушающих смысл одной горутины). Проблемы
видимости начинаются **между** горутинами — и решаются примитивами синхронизации.

### Каналы — главный механизм

Каналы дают happens-before напрямую:

- **Отправка** в канал *happens-before* завершения соответствующего **приёма** из этого
  канала.
- **Закрытие** канала *happens-before* приёма, который вернул «канал закрыт» (zero value,
  `ok == false`).
- Для **небуферизованного** канала: завершение **приёма** *happens-before* завершения
  **отправки** (приём и отправка встречаются «рукопожатием»).

```go
var data int
done := make(chan struct{})

go func() {
    data = 42          // (1) запись
    close(done)        // (2) close happens-before приёма ниже
}()

<-done                 // (3) приём из закрытого канала
fmt.Println(data)      // (4) ГАРАНТИРОВАННО видит 42: (1)→(2)→(3)→(4)
```

Без `done` чтение `data` в строке (4) было бы гонкой: нет ребра happens-before между записью в
одной горутине и чтением в другой. Девиз сообщества Go: **«Не общайтесь через разделяемую
память — разделяйте память через общение»** (через каналы), и причина именно в том, что канал
заодно даёт нужные гарантии видимости.

### Мьютексы

`sync.Mutex` / `sync.RWMutex` дают то же ребро, что и `synchronized`/`Lock` на JVM:

- `n`-й вызов `Unlock()` *happens-before* `m`-го `Lock()`, который вернул управление, при
  `m > n`. Проще: то, что одна горутина сделала под локом до `Unlock`, видно следующей
  горутине, взявшей этот `Lock`.
- Для `RWMutex`: `Unlock()` *happens-before* последующего `RLock()`, а `RUnlock()`
  *happens-before* следующего за ним `Lock()`.

### `sync.Once`

`once.Do(f)`: завершение **единственного** реального вызова `f()` *happens-before* возврата
**любого** `once.Do(f)`. Это и делает `Once` правильным примитивом для потокобезопасной
ленивой инициализации — все горутины, прошедшие через `Do`, видят результат `f`.

```go
var cfg *Config
var once sync.Once

func Get() *Config {
    once.Do(func() { cfg = load() }) // load() выполнится РОВНО раз; результат виден всем
    return cfg
}
```

### `sync/atomic`

Атомарные операции (`atomic.LoadInt64`, `atomic.StoreInt64`, `atomic.AddInt64`,
`atomic.CompareAndSwapInt64`, типы `atomic.Int64`/`atomic.Pointer[T]` и др.) тоже
устанавливают happens-before: атомарная операция, «наблюдающая» эффект другой атомарной
операции над тем же адресом, упорядочена после неё. С Go 1.19 у этих операций
**последовательно согласованная (sequentially consistent)** семантика — поведение, близкое к
Java `volatile`/`VarHandle` с volatile-доступом (каноника по `VarHandle` — в
[../../java-core/theory/REFLECTION_HANDLES.md](../../java-core/theory/REFLECTION_HANDLES.md)).

### Прочие источники happens-before

- запуск горутины (`go f()`) *happens-before* начала её выполнения — горутина видит всё, что
  было записано до `go`;
- завершение `init()` пакета *happens-before* старта `main`;
- `WaitGroup`: `wg.Done()` *happens-before* возврата `wg.Wait()`, который его «дождался».

> Важно: **завершение горутины НЕ даёт happens-before** само по себе. Нельзя «дождаться» конца
> горутины, просто перестав её трогать, и читать её результат без синхронизации. Нужен явный
> примитив: канал, `WaitGroup`, мьютекс.

Параллель с JMM: набор «рёбер» другой (там — `volatile`, `synchronized`, `final`-поля, старт
потока, `Thread.join`), но фундамент тот же — частичный порядок, дающий видимость. Каноника —
[../../concurrency/theory/THREADS_BASICS.md](../../concurrency/theory/THREADS_BASICS.md).

## 2. Data race и детектор `-race`

**Data race** (определение и общая теория гонок — в
[../../concurrency/theory/PROBLEMS.md](../../concurrency/theory/PROBLEMS.md)) — это когда две
горутины обращаются к **одной** ячейке памяти, **хотя бы одно** обращение — запись, и между
ними **нет** отношения happens-before. В Go гонка — это **неопределённое поведение**: программа
может работать «как ожидалось» месяцами, а потом выдать порченые данные, упасть или зациклиться
(особенно опасны гонки на полях `map` и интерфейсных значениях — они порушат внутренние
инварианты рантайма).

### Детектор гонок — Go-инструмент (OWN)

У Go есть встроенный **race detector** — то, чего в стандартной JVM из коробки нет (там нужны
сторонние инструменты вроде Java PathFinder или ThreadSanitizer-сборок). Включается флагом
`-race`:

```bash
go test -race ./...        # тесты под детектором (главный способ в CI)
go run -race main.go       # запуск программы под детектором
go build -race -o app .    # собрать инструментированный бинарь
```

### Как он работает

`-race` встраивает в бинарь **ThreadSanitizer** (TSan, из LLVM). Компилятор инструментирует
**каждое** обращение к памяти, а рантайм ведёт для адресов **векторные часы (vector clocks)** и
отслеживает операции синхронизации (каналы, мьютексы, atomic). Если детектор видит два
конфликтующих доступа к одной ячейке, **не упорядоченных** через happens-before, он печатает
подробный отчёт: стеки обеих горутин (кто читал, кто писал) и где они были созданы.

```
WARNING: DATA RACE
Write at 0x00c0000b4010 by goroutine 7:
  main.(*Counter).Inc()  counter.go:14
Previous read at 0x00c0000b4010 by goroutine 6:
  main.(*Counter).Value() counter.go:18
Goroutine 7 (running) created at: ...
```

### Стоимость и применение

- **Замедление**: исполнение в ~2–20 раз медленнее, память — в ~5–10 раз больше. Это **не для
  прода**, а для тестов и стейджинга.
- **Только динамический анализ**: детектор находит лишь те гонки, которые **реально
  произошли** на конкретном прогоне. Не покрытый тестом конкурентный путь он не увидит — отсюда
  правило: писать тесты, **реально запускающие конкурентные горутины** (см. упражнение
  [ex12_sync](../exercises/ex12_sync/)), и гонять их под `-race` в CI.
- **Нет ложных срабатываний**: если `-race` сообщил о гонке — это настоящая гонка (TSan
  основан на happens-before, а не на эвристиках-локсетах).

## 3. Стек, куча и escape analysis

В Go, как и в JVM, есть **стек** (на горутину) и **куча** (общая, под управлением GC). Но
**куда** попадёт переменная, решает **компилятор** на этапе компиляции через **escape analysis**
(анализ убегания) — а не программист и не ключевое слово `new`.

Ключевое отличие от Java: в Go можно **легально взять адрес локальной переменной и вернуть
его** из функции. В C это была бы ошибка (висячий указатель). В Go компилятор это видит и,
раз переменная «убегает» за пределы кадра, **размещает её в куче** автоматически.

```go
func stackAlloc() int {
    x := 42           // НЕ убегает: адрес наружу не уходит → стек
    return x
}

func heapAlloc() *int {
    x := 42           // адрес возвращается наружу → x ESCAPES → куча
    return &x         // в C это висячий указатель; в Go компилятор спасает, кладя x в кучу
}
```

### Что заставляет переменную «убежать» в кучу

- возврат **указателя** на локальную переменную (как выше);
- запись в значение **интерфейса**, если конкретный тип не помещается «по значению»
  (`var r io.Reader = &buf`);
- захват переменной **замыканием**, переживающим вызов;
- передача в `chan` / сохранение в долгоживущую структуру/`map`;
- слишком большой объект (не влезает в кадр стека);
- размер, неизвестный на этапе компиляции (например, слайс с переменной длиной).

### Как посмотреть решения компилятора

```bash
go build -gcflags=-m ./...        # печатает решения escape analysis
go build -gcflags='-m -m' ./...   # подробнее (с причинами)
```

```
./main.go:8:2: moved to heap: x          # x уехал в кучу
./main.go:14:13: &buf escapes to heap     # &buf убежал
./main.go:20:2: x does not escape         # x остался на стеке
```

### Почему это важно для производительности

Аллокация на стеке — почти бесплатна (сдвиг указателя, освобождается возвратом из функции) и
**не нагружает GC**. Аллокация в куче создаёт работу сборщику. Поэтому борьба за
производительность в Go во многом — это **сокращение убеганий в кучу** (переиспользование
буферов, `sync.Pool`, избегание лишних интерфейсных боксингов). Практические приёмы и связка с
бенчмарками/`pprof` — в [./PERFORMANCE_PROFILING.md](./PERFORMANCE_PROFILING.md).

Параллель с JVM: escape analysis там тоже есть, но это **оптимизация JIT во время исполнения**
(scalar replacement, удаление аллокации), а решение для всех объектов по умолчанию — куча.
Каноника — [../../java-core/theory/JIT_COMPILATION.md](../../java-core/theory/JIT_COMPILATION.md).
В Go escape analysis — **статический, на этапе компиляции**, и определяет место размещения
изначально, а не «спасает» уже решённую кучную аллокацию.

## 4. Рост стека горутины

Каждая горутина стартует с **крошечного стека ~2 КБ** (в JVM поток — это фиксированные ~512
КБ–1 МБ по `-Xss`, каноника — [../../java-core/theory/JVM_MEMORY_AREAS.md](../../java-core/theory/JVM_MEMORY_AREAS.md)).
Маленький стартовый стек — одна из причин, почему горутины так дёшево держать миллионами. Но
рекурсия и большие кадры требуют больше — стек должен **расти**.

### От сегментированных к непрерывным стекам (copy)

- **Сегментированные стеки (до Go 1.3)**: при нехватке места выделялся новый сегмент и
  связывался с предыдущим. Беда — **«hot split»**: цикл, вызывающий функцию ровно на границе
  сегментов, постоянно выделял/освобождал сегмент, давая резкие провалы производительности.
- **Непрерывные стеки (с Go 1.4)** — текущая модель: при нехватке рантайм выделяет **новый,
  вдвое больший** непрерывный блок, **копирует** туда весь старый стек и **корректирует
  указатели** на стек. Стек всегда непрерывен — «hot split» исчез.

Проверка «хватает ли стека» — на тех же точках, где и кооперативное вытеснение: в **прологе
функции** (см. [./SCHEDULER.md](./SCHEDULER.md)). Поэтому копирование стека требует, чтобы
рантайм точно знал, какие слова на стеке — указатели (для их корректировки); это обеспечивают
**карты указателей (stack maps)**, генерируемые компилятором. Стек может и **сжиматься**: во
время сборки мусора слишком просторный стек ужимается под реальную глубину.

Граница защиты — **максимальный размер стека** (по умолчанию **1 ГБ** на 64-битных,
настраивается `runtime/debug.SetMaxStack`). Превышение (как правило, бесконечная рекурсия) —
фатально:

```
runtime: goroutine stack exceeds 1000000000-byte limit
fatal error: stack overflow
```

В отличие от JVM, где переполнение стека — это `StackOverflowError` (ловимый `Throwable`), в Go
это **фатальная ошибка рантайма**, которую `recover` не перехватывает.

## 5. Сборщик мусора Go: конкурентный tri-color mark-sweep

Сборщик Go устроен принципиально иначе, чем основные сборщики JVM. Три определяющих свойства:

| Свойство | Go GC | Контраст с JVM |
|---|---|---|
| Конкурентность | mark идёт **параллельно** с приложением | G1/ZGC тоже конкурентны, но иначе |
| Поколения | **non-generational** (без молодого/старого) | G1/Parallel — поколенческие (Eden/Survivor/Old) |
| Перемещение | **non-moving** (объекты не двигаются) | G1/ZGC **перемещают** (компактизация, эвакуация) |
| Алгоритм | **tri-color mark-sweep** | tri-color используется и в G1 (concurrent mark) |

### Tri-color — по ссылке, не переопределяем

Сам **трёхцветный инвариант** (белый — мусор-кандидат, серый — найден, но не просканирован,
чёрный — жив и просканирован) и роль **write barrier (GC)** — общая теория сборки мусора,
каноника в
[../../java-core/theory/GARBAGE_COLLECTION.md](../../java-core/theory/GARBAGE_COLLECTION.md).
Кратко, чтобы текст был самодостаточным: маркировка красит от корней (стеки горутин, глобальные
переменные) граф достижимости; по завершении всё **белое** — недостижимо и подлежит
освобождению.

### Зачем write barrier в Go (кратко)

Поскольку приложение **работает во время маркировки**, оно может, пока сборщик красит граф,
записать ссылку на ещё-белый объект в уже-чёрный — и потерять её (нарушить инвариант). Чтобы
этого не случилось, компилятор Go вставляет **write barrier (GC)** на запись указателей: при
такой записи объект помечается серым (попадает в очередь маркировки). Go использует **гибридный
барьер записи Дейкстры–Янссона (с Go 1.8)**, который позволил почти полностью убрать повторное
сканирование стеков в STW. Детали самого механизма барьеров (SATB vs incremental update, card
table) — в каноническом файле по ссылке выше; здесь важно, что **в Go барьер есть и он на запись
указателя**, как и на JVM.

### Фазы цикла сборки

```
   ┌──────────────┐   ┌─────────────────────────┐   ┌──────────────┐   ┌─────────┐
   │ Mark Setup   │   │   Concurrent Mark        │   │ Mark         │   │  Sweep  │
   │   (STW)      │──►│   (конкурентно, с прилож.)│──►│ Termination  │──►│(конкур.)│
   │ короткая     │   │   + ассист-GC            │   │   (STW)      │   │ ленивый │
   │ пауза        │   │   + write barrier ВКЛ    │   │ короткая     │   │         │
   └──────────────┘   └─────────────────────────┘   └──────────────┘   └─────────┘
        ▲ обе паузы STW — обычно ДЕСЯТКИ–СОТНИ МИКРОСЕКУНД, цель < 1 мс
```

1. **Mark Setup (STW)** — очень короткая пауза: включить write barrier, подготовить корни.
   Останавливаются все горутины (здесь и нужна гарантированная остановка через вытеснение из
   [./SCHEDULER.md](./SCHEDULER.md)).
2. **Concurrent Mark** — основная работа: фоновые воркеры красят граф **параллельно с
   приложением**; барьер записи держит инвариант.
3. **Mark Termination (STW)** — короткая пауза: завершить маркировку, выключить барьер.
4. **Sweep** — освобождение белых объектов; идёт **конкурентно и лениво** (память
   возвращается по мере необходимости в аллокациях), без отдельной паузы.

### Ассист-GC (mark assist)

Если приложение аллоцирует **быстрее**, чем фоновые воркеры успевают маркировать, горутина,
делающая аллокацию, **сама обязана помочь** маркировке пропорционально объёму, который она
выделяет (mark assist). Это саморегуляция: чем агрессивнее код мусорит, тем больше он же платит
за сборку — и куча не убегает от сборщика. Сравните с G1, где аналог давления — паузы и режим
«to-space exhausted»; в Go давление транслируется в притормаживание самих аллоцирующих горутин.

### Цена non-moving

Объекты в Go **не перемещаются**, поэтому:

- **плюс**: указатели стабильны (упрощает взаимодействие с C/cgo — адрес не «уедет»), нет фазы
  эвакуации;
- **минус**: куча **фрагментируется**. Go смягчает это **size-классовым аллокатором** в духе
  TCMalloc (объекты раскладываются по ~70 классам размеров в спаны), но дефрагментирующего
  уплотнения, как у G1/ZGC, нет.

## 6. Настройка GC: GOGC, GOMEMLIMIT, pacer

Go сознательно даёт **мало ручек** (в отличие от десятков GC-флагов JVM). Главных — две.

### GOGC — целевой рост кучи

`GOGC` задаёт, **на сколько процентов** живой куче дать вырасти, прежде чем запустить
следующий цикл сборки. По умолчанию **`GOGC=100`**: следующая сборка стартует, когда куча
выросла на 100% (вдвое) относительно объёма, **выжившего** после прошлой сборки.

```
триггер_следующей_сборки ≈ живая_куча × (1 + GOGC/100)
GOGC=100 → старт при удвоении живого набора
GOGC=200 → реже собираем, больше памяти, выше пропускная способность
GOGC=50  → чаще собираем, меньше памяти, ниже пропускная
GOGC=off → GC по росту кучи отключён (только ручной/по GOMEMLIMIT)
```

```bash
GOGC=200 ./server         # реже сборки ценой памяти
GODEBUG=gctrace=1 ./server  # печатать строку статистики на каждый цикл GC
```

Это **единственная** основная ручка компромисса «частота сборки ↔ потребление памяти». Реже
собирать (больше `GOGC`) — выше пропускная способность и больше памяти; чаще — наоборот. На
паузы `GOGC` влияет слабо: они короткие почти всегда, потому что определяются работой в **STW**
(setup + termination), а не объёмом кучи.

### GOMEMLIMIT — мягкий лимит памяти (Go 1.19)

Проблема `GOGC` в одиночку: при всплеске живого набора куча может вырасти настолько, что
процесс убьёт ОС (на JVM это `OutOfMemoryError`/контейнерный `OOMKilled` — каноника в
[../../infrastructure/theory/KUBERNETES.md](../../infrastructure/theory/KUBERNETES.md)). С Go
1.19 есть **`GOMEMLIMIT`** — **мягкий (soft)** лимит общего объёма памяти рантайма:

```bash
GOMEMLIMIT=512MiB ./server      # держать память около 512 МиБ
```

По мере приближения к лимиту сборщик начинает работать **чаще и агрессивнее** (вплоть до
игнорирования `GOGC`), чтобы удержаться под порогом. «Мягкий» означает: если живого набора
физически больше лимита, рантайм его не нарушит ради лимита (предпочтёт нарушить лимит, чем
уронить приложение), но будет тратить на сборку всё больше CPU — вплоть до пробуксовки.

Идиоматичная связка для контейнеров: **`GOMEMLIMIT` ≈ 90–95% от лимита памяти пода**, чтобы Go
успевал собирать **до** `OOMKilled` от cgroup. Часто при этом ставят `GOGC=off`, отдавая всё
управление лимиту памяти (паттерн «GC по памяти, а не по росту кучи»).

### Pacer — кто рассчитывает момент старта

**Pacer** — управляющая часть сборщика, которая по `GOGC`/`GOMEMLIMIT` и скорости аллокаций
**предсказывает**, когда запустить следующий цикл и сколько mark-работы (включая ассист)
распределить, чтобы успеть домаркировать до достижения целевого размера кучи. Это контур
обратной связи: оценил скорость → запланировал старт и долю ассиста → измерил факт →
скорректировал. Цель — закончить маркировку как раз к триггеру, не дав куче перерасти.

### Почему у Go очень короткие паузы

Сводя воедино: паузы Go обычно **десятки–сотни микросекунд** (цель — **< 1 мс**), потому что:

1. **Почти вся работа GC конкурентна** — в STW лишь короткие setup и termination.
2. **Гибридный барьер записи (Go 1.8)** убрал дорогое повторное STW-сканирование стеков.
3. Сборщик **non-generational** и **non-moving** — нет STW-фаз компактизации/эвакуации
   объектов (которые в поколенческих сборщиках бывают «тяжёлыми»).
4. **Ассист-GC** не даёт аллокациям обогнать маркировку, так что догонять «в STW» нечего.

Расплата за такой выбор — **меньше пропускная способность** (барьеры записи и ассист отъедают
CPU у приложения) и **фрагментация кучи** (нет уплотнения). Go осознанно меняет пропускную и
память на **предсказуемо низкую задержку**. На JVM похожий компромисс выбирают **ZGC/Shenandoah**
(тоже конкурентные, sub-millisecond паузы), тогда как G1 балансирует, а Parallel максимизирует
пропускную ценой пауз — каноника в
[../../java-core/theory/GARBAGE_COLLECTION.md](../../java-core/theory/GARBAGE_COLLECTION.md).

## 7. Минимальный пример: гонка, её починка и наблюдение за GC

```go
package main

import (
    "fmt"
    "runtime"
    "sync"
)

type Counter struct {
    mu sync.Mutex
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()         // взятие лока даёт happens-before со следующим держателем
    c.n++               // защищено: без мьютекса здесь была бы гонка
    c.mu.Unlock()
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}

func main() {
    var c Counter
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); c.Inc() }()
    }
    wg.Wait()                       // Done happens-before Wait → видим финальное n
    fmt.Println("counter =", c.Value())

    var m runtime.MemStats
    runtime.ReadMemStats(&m)        // наблюдаемость GC из кода
    fmt.Printf("HeapAlloc=%d KB, NumGC=%d, PauseTotalNs=%d\n",
        m.HeapAlloc/1024, m.NumGC, m.PauseTotalNs)
}
```

Уберите мьютекс из `Inc`/`Value` — и `go test -race` (или `go run -race`) немедленно укажет на
гонку по полю `n`. Это ровно тот контракт, который проверяет упражнение
[ex12_sync](../exercises/ex12_sync/).

### Полезные переменные окружения

```bash
GODEBUG=gctrace=1 ./app    # строка на каждый цикл GC: размеры кучи, длительность пауз
GOGC=200 ./app             # реже собирать (больше памяти, выше пропускная)
GOMEMLIMIT=512MiB ./app    # мягкий лимит памяти (Go 1.19+)
GODEBUG=allocfreetrace=1 ./app  # (очень шумно) трасса каждой аллокации/освобождения
```

## Типичные ошибки

| Ошибка / заблуждение | Почему неверно | Как правильно |
|---|---|---|
| «горутина завершилась → её записи видны» | завершение горутины **не** даёт happens-before | синхронизировать каналом / `WaitGroup` / мьютексом |
| гонка «вроде безвредна» (счётчик, флаг) | гонка — неопределённое поведение, особенно на `map`/интерфейсах | `-race` в CI; защитить мьютексом или `atomic` |
| `-race` гоняют без конкурентных тестов | детектор видит лишь то, что реально исполнилось | тесты должны **реально** запускать горутины |
| «`-race` можно в прод» | замедление ×2–20, память ×5–10 | только тесты/стейджинг |
| «`new`/`&x` → точно куча» | место решает escape analysis | `go build -gcflags=-m`, не убежало — стек |
| надежда на `recover` при stack overflow | переполнение стека — **фатальная** ошибка рантайма | ограничить рекурсию; `recover` тут не работает |
| крутят GC-флаги как на JVM | у Go две ручки: `GOGC` и `GOMEMLIMIT` | начать с них; остальное — `GODEBUG` для диагностики |
| в контейнере без `GOMEMLIMIT` | при всплеске куча → `OOMKilled` от cgroup | `GOMEMLIMIT` ≈ 90–95% лимита пода |
| «GC уплотняет кучу» | сборщик Go **non-moving**, не двигает объекты | фрагментацию смягчает size-классовый аллокатор |
