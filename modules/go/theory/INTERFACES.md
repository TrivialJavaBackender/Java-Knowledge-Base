# Go — Интерфейсы

> Интерфейс в Go — это набор сигнатур методов. Тип реализует интерфейс **автоматически**,
> просто имея нужные методы. Никакого `implements`, никакого `extends` — связь устанавливается
> структурно и проверяется компилятором.
>
> Для разработчика из Java/Kotlin это главный сдвиг в мышлении: интерфейс и его реализацию
> можно объявить в разных пакетах, ничего не зная друг о друге.

---

## 1. Неявная реализация (structural typing)

В Java вы пишете `class ArrayList implements List` — связь **номинальная** (по имени), объявлена явно. В Go такой связи нет. Тип реализует интерфейс, если у него **есть все методы** из набора интерфейса. Это называют **структурной типизацией** (structural typing), а в обиходе — duck typing на этапе компиляции: «если оно крякает как утка — это утка».

```go
type Stringer interface {
    String() string
}

type Point struct {
    X, Y int
}

// Point получает метод String — и сразу же реализует Stringer.
// Слова "implements Stringer" нигде нет.
func (p Point) String() string {
    return fmt.Sprintf("(%d, %d)", p.X, p.Y)
}

func main() {
    var s Stringer = Point{1, 2} // присваивание просто работает
    fmt.Println(s.String())      // (1, 2)
}
```

### Сравнение с Java/Kotlin

| | Java / Kotlin | Go |
|---|---|---|
| Связь тип↔интерфейс | номинальная (`implements`) | структурная (по набору методов) |
| Где объявляется | у реализующего класса | нигде, выводится компилятором |
| Кто «знает» об интерфейсе | реализация знает о контракте | реализация может его не знать |
| Добавить интерфейс к чужому типу | нельзя (нужен адаптер) | можно объявить интерфейс **у себя** |

### Следствия для дизайна

1. **Интерфейс определяется у потребителя, а не у реализации.** Пакет, которому нужны определённые методы, объявляет минимальный интерфейс под свои нужды. Пакеты-производители возвращают конкретные типы. Об этом — раздел 9 и [./IDIOMS_PATTERNS.md](./IDIOMS_PATTERNS.md).
2. **Можно «навесить» интерфейс на чужой тип постфактум.** Если сторонний тип уже имеет метод `Read([]byte) (int, error)`, он автоматически удовлетворяет вашему `io.Reader` — адаптер не нужен.
3. **Нет циклической зависимости пакетов.** Реализация не импортирует пакет с интерфейсом, поэтому стрелка зависимости направлена так, как удобно потребителю.

### Проверка реализации на этапе компиляции

Поскольку связь неявная, легко **случайно перестать реализовывать** интерфейс (переименовали метод, поменяли сигнатуру) и узнать об этом лишь там, где происходит присваивание — иногда далеко от типа. Чтобы зафиксировать намерение «тип `T` обязан реализовывать `Iface`», используют идиому assertion на уровне пакета:

```go
// Compile-time проверка: *MyWriter обязан удовлетворять io.Writer.
// Если метод пропал или сигнатура разошлась — не скомпилируется здесь.
var _ io.Writer = (*MyWriter)(nil)
```

Разбор: `(*MyWriter)(nil)` — это типизированный nil-указатель типа `*MyWriter`; присваивание в `_` (blank identifier) ничего не исполняет в рантайме, но компилятор проверяет совместимость типов. Это аналог явного `implements` — но опциональный и пишется там, где удобно автору типа. Ставьте такую строку рядом с типом, если интерфейс важен для контракта.

## 2. Малые интерфейсы как идиома

Культура Go — **маленькие интерфейсы**, в идеале один-два метода. «The bigger the interface, the weaker the abstraction» (Rob Pike). Чем меньше интерфейс, тем больше типов его удовлетворяют и тем легче подменять реализации в тестах.

Канонические примеры из стандартной библиотеки — все по одному методу:

```go
// io.Reader — источник байт
type Reader interface {
    Read(p []byte) (n int, err error)
}

// io.Writer — приёмник байт
type Writer interface {
    Write(p []byte) (n int, err error)
}

// fmt.Stringer — текстовое представление (аналог toString())
type Stringer interface {
    String() string
}

// error — это просто интерфейс с одним методом (см. ./ERRORS_PANIC.md)
type error interface {
    Error() string
}
```

`io.Reader` удовлетворяют сотни типов: `*os.File`, `*bytes.Buffer`, `*strings.Reader`, сетевое соединение, gzip-декодер. Любая функция, принимающая `io.Reader`, работает со всеми ними без изменений.

### Композиция интерфейсов (встраивание)

Большие интерфейсы собираются из малых через **встраивание** (embedding) — имя интерфейса как поле без имени. Набор методов результата = объединение наборов вложенных интерфейсов.

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}

// ReadWriter = Reader + Writer (так и определён io.ReadWriter)
type ReadWriter interface {
    Reader
    Writer
}
```

Тип удовлетворяет `ReadWriter`, если у него есть и `Read`, и `Write`. Встраивание интерфейсов — это **объединение требований**, а не наследование реализации. (Встраивание структур — отдельная механика, см. [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md).)

## 3. Пустой интерфейс `interface{}` / `any`

Пустой интерфейс `interface{}` не требует **ни одного** метода, поэтому ему удовлетворяет **любой** тип. Это ближайший аналог `Object` в Java — контейнер для значения произвольного типа.

С Go 1.18 введён псевдоним `any`:

```go
// Это буквально одно и то же, any — алиас (type any = interface{})
var a any = 42
var b interface{} = "hello"
```

Используйте `any` — это канонический современный вид. `interface{}` встречается в старом коде.

### Цена пустого интерфейса

`any` выглядит удобно, но за гибкость платят:

1. **Потеря статической типизации.** Компилятор больше не проверяет тип внутри; чтобы что-то с ним сделать, нужен type assertion или type switch (разделы 4–5) — и это может паниковать в рантайме.
2. **Аллокация и боксинг.** Поместить значение в интерфейс часто означает выделение в куче (heap) и упаковку: интерфейс хранит указатель на данные (раздел 6). Передача миллионов `int` как `any` создаёт нагрузку на GC.
3. **Хуже читаемость и документируемость.** Сигнатура `func Process(v any)` не говорит, что туда можно передать.

Правило: **избегайте `any` в публичных API**, если можно выразить требование интерфейсом или (с Go 1.18) дженериком (см. [./GENERICS.md](./GENERICS.md)). `any` уместен в по-настоящему динамических сценариях: `encoding/json` для произвольного JSON, `fmt.Println(args ...any)`, контейнеры до эпохи дженериков.

## 4. Type assertion: извлечь конкретный тип

Интерфейс прячет конкретный тип. **Type assertion** `x.(T)` достаёт его обратно.

```go
var i any = "hello"

s := i.(string) // s == "hello", тип string
n := i.(int)    // ПАНИКА: interface conversion: interface {} is string, not int
```

Однозначная форма `x.(T)` **паникует**, если динамический тип не `T`. Чтобы проверить безопасно, используйте **comma-ok форму** — она не паникует, а возвращает второй булев результат:

```go
s, ok := i.(string)
if ok {
    fmt.Println("это строка:", s)
} else {
    // s == zero value типа string (""), паники нет
    fmt.Println("не строка")
}
```

Assertion работает и для интерфейсного целевого типа — проверить, реализует ли значение **другой** интерфейс:

```go
// Реализует ли w дополнительно io.Closer?
if c, ok := w.(io.Closer); ok {
    defer c.Close()
}
```

Это распространённый приём «прощупывания» опциональных возможностей (capability probing) — частый трюк в stdlib (например, `io.Copy` проверяет, не реализует ли аргумент `io.WriterTo`).

## 5. Type switch: ветвление по динамическому типу

Когда вариантов несколько, вместо цепочки assertion-ов пишут **type switch** — `switch` по типу значения:

```go
func Describe(v any) string {
    switch x := v.(type) {
    case nil:
        return "nil"
    case int:
        return fmt.Sprintf("целое: %d", x) // x имеет тип int в этой ветке
    case string:
        return fmt.Sprintf("строка длиной %d", len(x)) // x имеет тип string
    case Stringer:
        return "stringer: " + x.String() // x имеет тип Stringer
    case []int:
        return fmt.Sprintf("срез из %d чисел", len(x))
    default:
        return fmt.Sprintf("неизвестный тип %T", x) // %T печатает имя типа
    }
}
```

Ключевое: `x := v.(type)` (синтаксис допустим **только** внутри `switch`) внутри каждой ветки даёт переменной `x` **конкретный статический тип** этой ветки. В ветке `case int` можно делать арифметику; в `case Stringer` — вызывать `String()`. Это flow-scoped binding, идейно близкий к pattern matching в Java 21 (`switch` с типами) и Kotlin smart cast.

Нюансы:
- `case nil` ловит **nil-интерфейс** (интерфейс без значения); о его отличии от typed nil — раздел 7.
- Порядок веток важен: значение, удовлетворяющее `Stringer`, попадёт в первую подходящую ветку сверху.
- В ветке с несколькими типами (`case int, int64:`) переменная `x` сохраняет интерфейсный тип `any` — конкретный тип неизвестен, ведь их два.
- `default` ловит всё остальное — обязательно покрывайте его в тестах.

## 6. Устройство интерфейсного значения: пара (type, value)

Чтобы понять nil-trap (раздел 7), нужно знать, **как интерфейс устроен внутри**. Интерфейсное значение — это **два машинных слова**:

```
  ┌───────────────┬───────────────┐
  │   tab / type  │     data      │
  └───────────────┴───────────────┘
        ↓                 ↓
   таблица типа       указатель
   и методов          на данные
```

- **Первое слово** — указатель на дескриптор типа. Для непустого интерфейса это `itab` (interface table): пара «конкретный тип + таблица его методов под этот интерфейс». Для пустого интерфейса (`any`) метода нет, поэтому хранится просто `*_type` — дескриптор типа.
- **Второе слово** (`data`) — всегда указатель на данные конкретного значения (с Go 1.4 word-размерные скаляры инлайн не хранятся — поэтому упаковка, например, `int` в интерфейс обычно требует аллокации).

`itab` строится один раз на пару (конкретный тип, интерфейс) и кэшируется рантаймом. Он содержит метаданные типа плюс массив указателей на методы — по нему происходит динамическая диспетчеризация вызова (аналог vtable в C++ / itable в JVM, но собираемый по требованию из-за structural typing).

Отсюда главная формула: **«interface holds a concrete type»** — интерфейс всегда несёт информацию о том, какой конкретный тип в нём лежит. Именно поэтому работают type switch и assertion: рантайм сравнивает дескриптор типа в первом слове с искомым.

Интерфейс считается `nil` **только если оба слова нулевые** — нет ни типа, ни данных. Запомните это: ключ к следующему разделу.

> Глубокий разбор устройства `itab` и почему диспетчеризация в Go дешевле, чем кажется, — статья
> Russ Cox «Go Data Structures: Interfaces» (см. «Источники»).

## 7. NIL-INTERFACE TRAP (typed nil) — классическая ошибка

Это **самая известная ловушка Go** и почти гарантированный вопрос на собеседовании.

Поскольку интерфейс — пара (type, value), он равен `nil` только когда **оба** компонента нулевые. Если положить в интерфейс **типизированный nil-указатель** — например, `(*T)(nil)` — то слово типа становится непустым (`*T`), а слово данных нулевым. Такой интерфейс **не равен `nil`**, хотя «внутри» лежит nil.

```go
type MyError struct{ msg string }

func (e *MyError) Error() string { return e.msg }

func doWork() error {
    var p *MyError = nil // конкретный nil-указатель типа *MyError
    return p             // ⚠️ кладём typed nil в интерфейс error
}

func main() {
    err := doWork()
    if err != nil {
        // ЭТА ВЕТКА ВЫПОЛНЯЕТСЯ! err != nil == true,
        // потому что в интерфейсе тип = *MyError (не пустой),
        // хотя data-указатель = nil.
        fmt.Println("неожиданная ошибка:", err) // и упадёт в Error(), если разыменует поле
    }
}
```

Что произошло: `err` — это интерфейс с парой `(*MyError, nil)`. Тип не пустой, значит `err == nil` ложно. Проверка `if err != nil` проходит — и код считает, что произошла ошибка, хотя её не было.

### Откуда это берётся на практике

Классика — функция возвращает **конкретный** тип ошибки и где-то «пробрасывает» его в интерфейс:

```go
// ❌ Анти-паттерн: возвращаем конкретный *MyError
func validate(x int) *MyError {
    if x < 0 {
        return &MyError{"отрицательное"}
    }
    return nil // конкретный nil *MyError
}

func handle(x int) error {
    return validate(x) // nil *MyError → НЕ-nil интерфейс error
}

// handle(5) вернёт интерфейс (*MyError, nil) != nil — баг
```

### Как избежать

1. **Возвращайте тип `error`, а не конкретный `*MyError`** из функций. Тогда при `return nil` в интерфейс кладётся честный nil-интерфейс:

```go
// ✅ Возвращаемый тип — интерфейс error
func validate(x int) error {
    if x < 0 {
        return &MyError{"отрицательное"}
    }
    return nil // честный nil-интерфейс: оба слова пустые
}
```

2. Никогда не объявляйте переменную конкретного типа ошибки только чтобы вернуть её как `error`. Если нужно — проверяйте на nil **до** упаковки и возвращайте литеральный `nil`.

Эта же ловушка применима к любому интерфейсу, не только `error`: typed nil любого `*T` внутри любого интерфейса даёт не-nil интерфейс.

## 8. Method set и интерфейсы: почему `*T` реализует больше, чем `T`

Какие методы «видны» через значение, определяет его **method set** (множество методов). Правило (подробный вывод — в [./TYPES_STRUCTS_METHODS.md](./TYPES_STRUCTS_METHODS.md)):

| Объявлен метод с receiver | В method set `T` | В method set `*T` |
|---|---|---|
| value receiver `func (t T)` | да | да |
| pointer receiver `func (t *T)` | **нет** | да |

То есть **`*T` имеет все методы, а `T` — только value-receiver методы**. Прямое следствие для интерфейсов: если хотя бы один метод интерфейса объявлен с pointer receiver, то интерфейс удовлетворяет **только `*T`, но не `T`**.

```go
type Counter struct{ n int }

// pointer receiver — модифицирует состояние
func (c *Counter) Inc()      { c.n++ }
func (c *Counter) Value() int { return c.n }

type Incrementer interface {
    Inc()
    Value() int
}

func main() {
    var i Incrementer

    i = &Counter{} // ✅ ОК: *Counter имеет Inc и Value
    i.Inc()

    // i = Counter{} // ❌ НЕ КОМПИЛИРУЕТСЯ:
    // Counter does not implement Incrementer
    // (Inc has pointer receiver)
}
```

Почему так: если бы Go позволил `Counter{}` (значение) удовлетворять интерфейсу с `Inc()`, то `Inc()` модифицировал бы **копию** внутри интерфейса, и изменение терялось бы — молчаливый баг. Запрет на этапе компиляции предотвращает это.

Практический вывод: если у типа есть pointer-receiver методы (а так почти всегда, когда метод что-то меняет) — **присваивайте интерфейсу адрес (`&T{}`)**, а не значение. Конструкторы в Go обычно возвращают `*T` именно поэтому.

## 9. Идиома «accept interfaces, return structs»

Каноническое правило дизайна API в Go:

> **Принимай интерфейсы, возвращай конкретные типы (структуры).**

- **Аргументы — интерфейсы.** Функция декларирует минимальный набор методов, который ей нужен. Это даёт гибкость вызывающему (можно подставить любой подходящий тип, в т.ч. мок в тесте) и слабую связанность.
- **Возврат — конкретные типы.** Вернув `*bytes.Buffer`, вы отдаёте вызывающему все методы типа; он сам решит, к какому интерфейсу его свести. Вернув интерфейс, вы **сужаете** доступное и навязываете абстракцию преждевременно.

```go
// ✅ принимаем интерфейс (минимум), возвращаем конкретный тип
func CopyToBuffer(src io.Reader) (*bytes.Buffer, error) {
    var buf bytes.Buffer
    _, err := io.Copy(&buf, src) // src — любой Reader
    return &buf, err             // конкретный *bytes.Buffer
}
```

### Где определять интерфейс — у потребителя

Из structural typing вытекает: **интерфейс объявляется в пакете, который его использует** (consumer), а не в пакете реализации (producer). Пакет `database` возвращает конкретный `*DB`; пакет `service`, которому нужны только методы `Query` и `Exec`, объявляет **у себя** маленький интерфейс с этими двумя методами и принимает его. Это противоположно Java-привычке «сначала интерфейс в core-модуле, потом impl».

### Interface pollution

**Interface pollution** — антипаттерн, когда интерфейсы плодят преждевременно «на всякий случай»: один интерфейс на каждый тип, интерфейс с единственной реализацией, экспортируемый интерфейс там, где хватило бы конкретного типа. Это добавляет уровень косвенности без выгоды, мешает навигации и автодополнению. Идиома: **не добавляйте интерфейс, пока не появилась вторая реализация или реальная потребность в подмене (тесты, границы пакетов)**. Подробнее — [./IDIOMS_PATTERNS.md](./IDIOMS_PATTERNS.md).

## 10. Сравнение интерфейсных значений

Интерфейсы можно сравнивать через `==`. Два интерфейсных значения равны, если **равны их динамические типы И равны динамические значения**.

```go
var a any = 1
var b any = 1
fmt.Println(a == b) // true: оба (int, 1)

var c any = int64(1)
fmt.Println(a == c) // false: типы разные (int vs int64), хотя оба «1»

var d, e any        // оба nil-интерфейса
fmt.Println(d == e) // true
```

### Паника при несравнимом динамическом типе

Опасность: если динамический тип **несравним** (slice, map или function), сравнение интерфейсов **паникует в рантайме**:

```go
var a any = []int{1, 2}
var b any = []int{1, 2}
fmt.Println(a == b) // ПАНИКА: runtime error: comparing uncomparable type []int
```

Компилятор не может это поймать — статически оба `any`, и непонятно, что внутри. Поэтому:

- Не используйте `any` со срезами/maps/функциями как **ключи map** (ключ map обязан быть сравнимым — получите панику в рантайме при вставке такого значения, обёрнутого в `any`).
- Будьте осторожны со сравнением интерфейсов неизвестного происхождения. Если динамический тип может оказаться несравнимым — сравнивайте через `reflect.DeepEqual` (он не паникует, но медленный) или по конкретным полям после type switch.

Сравнимы: булевы, числа, строки, указатели, каналы, **сравнимые** структуры и массивы, интерфейсы. Несравнимы: slice, map, function. (Полный список — спецификация, раздел Comparison operators.)

## Типичные ошибки (шпаргалка)

| Ошибка | Симптом | Лечение |
|---|---|---|
| Вернуть typed nil как `error` | `err != nil` истинно при «нет ошибки» | Возвращать тип `error`, литеральный `nil` |
| `x.(T)` без comma-ok | паника при неверном типе | `v, ok := x.(T)` там, где тип не гарантирован |
| Присвоить интерфейсу `T` вместо `&T` | «does not implement» при pointer receiver | Присваивать `&T{}` |
| `any` в публичном API | потеря типобезопасности, боксинг | Интерфейс или дженерик ([./GENERICS.md](./GENERICS.md)) |
| Сравнение `any` со срезом внутри | паника в рантайме | `reflect.DeepEqual` или type switch |
| Большой интерфейс «на всё» | слабая абстракция, мало реализаций | Дробить на малые (1–2 метода) |
| Интерфейс у производителя | лишняя косвенность, pollution | Объявлять интерфейс у потребителя |
| Забыть compile-time проверку | реализация молча «отвалилась» | `var _ Iface = (*T)(nil)` |
