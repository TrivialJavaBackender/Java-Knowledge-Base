# Зачем разделять систему на сервисы и чем за это платят

> **Какую проблему решает.** Объясняет, что именно происходит с программой, когда вызов метода
> превращается в вызов по сети: сколько это стоит в наносекундах, какие гарантии при этом
> теряются безвозвратно и какую выгоду покупают взамен. Отсюда выводится единственный честный
> критерий «нужны ли здесь микросервисы».
> **Кому это надо.** Тому, кто собирается предложить разделение монолита — и должен объяснить
> руководителю, за что платит организация; и тому, кого на собеседовании спросят «зачем вам
> микросервисы», где неверный ответ — перечисление достоинств без единой цены.
> **Когда НЕ надо.** Если решение уже принято и нужен конкретный механизм (сага, circuit breaker,
> контракт) — идите сразу в профильный файл. Здесь нет ни одного рецепта, только модель, из
> которой рецепты выводятся.

Соседние файлы модуля: механика синхронного вызова и бюджет таймаутов —
[`SYNC_COMMUNICATION.md`](SYNC_COMMUNICATION.md); где именно проводить границу —
[`DECOMPOSITION.md`](DECOMPOSITION.md); что ломается, когда разрез сделан неправильно —
[`ANTIPATTERNS.md`](ANTIPATTERNS.md). Модульный монолит и соответствие «Bounded Context ↔ сервис»
принадлежат модулю DDD: [`ddd/ARCHITECTURE.md`](../../ddd/theory/ARCHITECTURE.md).

Все замеры сняты на машине, где написан текст: **Apple M4, 10 ядер, macOS 26.5.2, Temurin OpenJDK
21.0.9+10 LTS**. Это не JMH — порядок величин, а не бенчмарк. Каждый замер сопровождается кодом и
командой запуска; повторите у себя — числа будут другие, соотношения те же.

## 1. Сквозной пример: оформление заказа

Весь модуль разбирается на одной системе. Она нарочно маленькая — ровно настолько, чтобы в ней
уместились все интересные противоречия.

> **Оформление заказа в интернет-магазине.** Пять сервисов: `Checkout` принимает запрос,
> `Order` создаёт заказ, `Payment` ходит во внешнего платёжного провайдера, `Inventory`
> резервирует товар на складе, `Notification` шлёт письмо. Нагрузка — **500 запросов в секунду**
> на оформление. Внешний платёжный провайдер отвечает за **300 мс** по медиане и иногда зависает.
> Резерв склада обязан быть согласован с оплатой: нельзя списать деньги и не отгрузить, нельзя
> отгрузить и не списать.

Пока это монолит, вся задача — один метод:

```java
@Transactional
public OrderId checkout(Cart cart, Payment method) {
    Order order = orderService.create(cart);            // вызов метода
    inventoryService.reserve(order);                    // вызов метода
    paymentService.charge(order, method);               // вызов метода → внешний провайдер
    notificationService.sendConfirmation(order);        // вызов метода
    return order.id();
}
```

Свойства этого кода стоит перечислить явно, потому что дальше мы их будем терять по одному:

- четыре вызова стоят единицы наносекунд каждый (кроме похода к провайдеру);
- если `inventoryService.reserve` бросил исключение, `orderService.create` откатится — они в одной
  транзакции базы данных;
- если что-то упало, в стектрейсе видно всю цепочку от `checkout` до места отказа;
- «недоступен `Inventory`» — состояние, которого не бывает: он в той же JVM, что и вызывающий;
- сигнатура `reserve(Order)` проверяется компилятором, и переименовать поле нельзя, не сломав
  сборку.

Теперь то же самое, но `Order`, `Payment`, `Inventory`, `Notification` — отдельные процессы на
отдельных машинах. Ни одно из пяти свойств не сохранилось. Следующий раздел считает, во что
обошёлся каждый пункт.

## 2. Что происходит с вызовом метода, когда он становится сетевым

### 2.1 Задача: посчитать цену перед тем, как её платить

Фраза «вынесем `Inventory` в отдельный сервис» звучит как организационное решение. На уровне кода
это означает, что строка `inventoryService.reserve(order)` остаётся на месте, а за ней теперь
стоит совсем другая машинерия. Насколько другая — можно измерить.

Замер делает одну и ту же работу тремя способами: (1) обычный вызов метода, (2) тот же вызов, но
аргумент и результат прогоняются через JSON туда и обратно, (3) тот же вызов по HTTP через
локальную петлю (loopback) — то есть **без единого сетевого пакета, ушедшего с машины**.

```java
// CallCost.java — java -cp <jackson-2.17.2> CallCost.java
record Item(String sku, int qty) {}
record ReserveRequest(String orderId, String customerId, List<Item> items) {}
record ReserveResponse(String reservationId, boolean ok, int reservedCount) {}

static final class Inventory {                       // «сервис склада» как обычный класс
    long counter;
    ReserveResponse reserve(ReserveRequest r) {
        int n = 0;
        for (Item i : r.items()) n += i.qty();
        counter += n;
        return new ReserveResponse("res-" + r.orderId(), true, n);
    }
}
```

Один и тот же объект `ReserveRequest` (заказ из трёх позиций, 128 байт в JSON) прогоняется
5 000 000 раз через прямой вызов, 200 000 раз через сериализацию и 20 000 раз через HTTP;
перед каждым замером — прогрев. Три прогона подряд:

```
размер тела запроса: 128 байт
1. вызов метода                          10 нс
2. вызов + сериализация JSON          1 169 нс  (×117)
3. вызов по HTTP через loopback      94 479 нс  (×9448)   p50=89 209  p99=177 792  max=945 750

1. вызов метода                          11 нс
2. вызов + сериализация JSON          1 190 нс  (×108)
3. вызов по HTTP через loopback     109 882 нс  (×9989)   p50=95 958  p99=298 417  max=6 527 750

1. вызов метода                          11 нс
2. вызов + сериализация JSON          1 204 нс  (×109)
3. вызов по HTTP через loopback      97 603 нс  (×8873)   p50=87 583  p99=250 334  max=1 884 667
```

Читаем внимательно. **Одна и та же работа подорожала примерно в девять тысяч раз** — и это ещё
щадящая оценка: пакет никуда не уходил, TLS не поднимался, балансировщика не было, сериализовали
128 байт. Из девяти тысяч примерно сотня — сериализация, остальное — сетевой стек, планировщик и
цикл обработки на второй стороне.

Обратите внимание и на разброс: медиана 88–96 мкс, p99 — 178–298 мкс, а максимум за 20 000
вызовов доходит до 6.5 мс. У вызова метода такого разброса нет вовсе. Хвост появился вместе с
сетью, и дальше весь модуль занимается тем, что с ним делать.

**Правило.** Сетевой вызов — это не «немного медленнее»: это другой порядок величины и другой
характер распределения. Всё, что вы вызывали в цикле, надо перестать вызывать в цикле; см. цену
запроса через границу в [`DATA_OWNERSHIP.md`](DATA_OWNERSHIP.md).

### 2.2 Пропала общая сигнатура — появился контракт

В монолите `reserve(Order)` проверял компилятор: переименовали поле — сборка красная. После
разделения на той стороне провода — байты, и никто не гарантирует, что их разберут так же, как
собрали. Сборка `Order` остаётся зелёной, когда `Inventory` переименовывает поле в своей схеме.

Наивное решение — «договоримся и будем аккуратны» — ломается ровно в тот момент, когда
`Inventory` выкатывается в среду, где старые экземпляры `Order` ещё живут: во время раскатки в
проде одновременно работают обе версии. Механизм, который это чинит (правила совместимости,
tolerant reader, версионирование), — в [`CONTRACTS_AND_TESTING.md`](CONTRACTS_AND_TESTING.md).

**Правило.** Компилятор перестал быть арбитром совместимости. Его роль надо кому-то передать —
явно, иначе арбитром станет прод.

### 2.3 Пропала общая транзакция

`@Transactional` над `checkout` больше не действует: `Order` и `Inventory` пишут в разные базы, и
у них нет общего журнала. Отменить резерв на складе откатом транзакции `Order` невозможно —
это две независимые фиксации.

Наивное решение «сделаем распределённую транзакцию» существует (2PC), но платит за это
доступностью: координатор становится точкой, отказ которой оставляет участников с заблокированными
строками. Разбор и того и другого — в
[`DISTRIBUTED_TRANSACTIONS.md`](DISTRIBUTED_TRANSACTIONS.md); граница транзакционной
согласованности как доменное понятие — в
[`ddd/AGGREGATE_DESIGN.md`](../../ddd/theory/AGGREGATE_DESIGN.md).

**Правило.** Разрез, который проходит поперёк инварианта «деньги списаны ⇔ товар зарезервирован»,
не убирает инвариант — он перекладывает его на прикладной код. Это самая дорогая статья расходов
из всех перечисленных в этом файле.

### 2.4 Появился частичный отказ

Это отличие принципиальнее остальных, поэтому его стоит увидеть, а не прочитать. В монолите
вызов либо выполнился, либо бросил исключение. Третьего состояния нет. В сети оно есть: **работа
выполнена, а ответ до вас не дошёл**, и отличить это от «работа не выполнена» вызывающая сторона
не может в принципе.

Демонстрация: сервер списывает деньги и обрывает соединение до ответа. Клиент — обычный
`java.net.http.HttpClient` с таймаутом — и повторяет запрос, как поступил бы любой разумный клиент.

```java
// PartialFailure.java — java PartialFailure.java
int n = charged.incrementAndGet();               // деньги списаны — побочный эффект наступил
System.out.println("  [Payment]  списание выполнено, всего списаний: " + n);
s.setSoLinger(true, 0);                          // RST вместо ответа: провайдер «завис и упал»
s.close();
```

```
[Checkout] попытка 1: POST /charge
  [Payment]  списание выполнено, всего списаний: 1
[Checkout] исключение: java.io.IOException: HTTP/1.1 header parser received no bytes
[Checkout] списаны ли деньги — неизвестно. Повторяем.
[Checkout] попытка 2: POST /charge
  [Payment]  списание выполнено, всего списаний: 2
[Checkout] исключение: java.io.IOException: HTTP/1.1 header parser received no bytes
[Checkout] списаны ли деньги — неизвестно. Повторяем.

успешных ответов, которые видел Checkout: 0
фактических списаний на стороне Payment:  2
```

Клиент не видел ни одного успеха. Покупатель заплатил дважды. Никто не написал ни строчки
неправильного кода — `Checkout` сделал ровно то, что предписывает здравый смысл при сетевой
ошибке.

Механизм такой: побочный эффект и подтверждение о нём разнесены во времени и передаются по разным
направлениям одного и того же ненадёжного канала. Всё, что произошло между ними, для вызывающего
невидимо. Отсюда — не «пишите повторы аккуратно», а два жёстких следствия:

1. Любая операция с побочным эффектом, которую можно повторить, обязана быть **идемпотентной** —
   и идемпотентность обеспечивает **принимающая** сторона, а не повторяющая. Ключ идемпотентности
   как приём принадлежит
   [`system-design/RELIABILITY_PATTERNS.md`](../../system-design/theory/RELIABILITY_PATTERNS.md);
   идемпотентность потребителя сообщений — [`ASYNC_MESSAGING.md`](ASYNC_MESSAGING.md).
2. Повтор без ограничений превращает медленную зависимость в лавину — механика в
   [`FAILURE_ISOLATION.md`](FAILURE_ISOLATION.md).

**Правило.** Как только вызов ушёл в сеть, «неизвестно» становится штатным исходом, который надо
обрабатывать наравне с успехом и с ошибкой. Код, в котором два ветвления вместо трёх, — не
упрощённый, а неправильный.

### 2.5 Стектрейс кончается на границе процесса

В монолите стектрейс NPE показывает всю цепочку от контроллера до места отказа. После разделения
`Checkout` увидит `IOException` или HTTP 500 — и всё; что произошло в `Payment`, в этом стектрейсе
не будет никогда.

Наивное решение — «посмотрим в логах» — ломается на 500 запросах в секунду: логи пяти сервисов
надо сначала сшить между собой, а по времени они не сшиваются — часы соседних машин расходятся,
и «раньше» по меткам времени не означает «раньше» по причинности (почему так и что с этим делают,
разбирается в
[`system-design/distributed_systems.md`](../../system-design/theory/distributed_systems.md)).
Механизм, который чинит сшивание, — сквозной идентификатор и распространение контекста
трассировки; тема принадлежит
[`infrastructure/OBSERVABILITY.md`](../../infrastructure/theory/OBSERVABILITY.md).

**Правило.** Наблюдаемость — не «добавим потом». До разделения она была бесплатной (стектрейс),
после разделения это отдельная подсистема, которую надо построить и оплатить. Отсутствие
распределённой трассировки — один из трёх признаков «рано» из §10.

## 3. Восемь ошибочных допущений распределённых вычислений

Список появился в Sun Microsystems: семь пунктов сформулировал L. Peter Deutsch в 1994 году,
включив в них четыре допущения, найденные до него Биллом Джоем и Дэйвом Лайоном; восьмое — «сеть
однородна» — около 1997 года добавил Джеймс Гослинг. Ценность списка не в том, что кто-то всерьёз
верит в эти утверждения вслух. Ценность в том, что **код, написанный без явной мысли о них,
ведёт себя так, как будто автор в них верил**. Ниже каждый пункт — с ценой на сквозном примере.

### 3.1 Сеть надёжна

Допущение живёт в коде так: у вызова нет ветки «не получилось». Ровно эту ветку мы наблюдали в
§2.4 — и получили два списания вместо одного.

Реже вспоминают вторую половину: ненадёжна не только доставка, но и **порядок**. Два сообщения об
одном заказе — «резерв создан» и «резерв отменён» — могут прийти потребителю в обратном порядке.
Что при этом гарантируется, а что нет, разбирается в
[`ASYNC_MESSAGING.md`](ASYNC_MESSAGING.md).

**Цена в примере.** `Checkout` обязан уметь: повторить, не заплатив дважды; отличить «ещё не
ответили» от «отказали»; и оставить систему в согласованном состоянии, если ответ не придёт
никогда.

### 3.2 Задержка нулевая

Допущение живёт в коде так: вызов `inventory.getStock(sku)` внутри цикла по позициям заказа.
В монолите это 10 нс × 20 позиций = 200 нс, незаметно. После разделения — 90 мкс × 20 = 1.8 мс
только на складе, и это по локальной петле; между машинами одного ЦОД круговая задержка
порядка 500 мкс (порядки величин — в
[`system-design/LATENCY_NUMBERS.md`](../../system-design/theory/LATENCY_NUMBERS.md)), то есть
20 позиций дают уже 10 мс.

Второе следствие важнее первого: задержка не складывается, а **накапливается вдоль цепочки**.
Замер — та же локальная петля, но запрос делает то один вызов, то четыре подряд:

```java
// Chain.java — java Chain.java
for (int hops : new int[]{1, 4}) {
    for (int i = 0; i < 20_000; i++) {
        long t = System.nanoTime();
        for (int h = 0; h < hops; h++) c.send(req, HttpResponse.BodyHandlers.discarding());
        s[i] = System.nanoTime() - t;
    }
}
```

```
вызовов на запрос=1  p50= 83 417 нс  p95= 112 500 нс  p99= 145 875 нс  p999=  274 292 нс
вызовов на запрос=4  p50=237 333 нс  p95= 322 000 нс  p99= 406 583 нс  p999=  670 834 нс

вызовов на запрос=1  p50= 82 917 нс  p95= 109 250 нс  p99= 136 125 нс  p999=  268 083 нс
вызовов на запрос=4  p50=237 084 нс  p95= 311 000 нс  p99= 362 917 нс  p999=  659 500 нс
```

Здесь стоит отметить то, чего в замере **не** видно. Ожидание «хвост усилится: у цепочки p99
вырастет быстрее медианы» не подтвердилось: отношение p99/p50 у одного вызова 1.75, у цепочки из
четырёх — 1.71. Причина в том, что на одной машине хвосты звеньев не независимы: паузы сборщика
мусора и планировщика задевают все четыре вызова разом. Классическое усиление хвоста возникает,
когда звенья действительно независимы — то есть в настоящем кластере; приём, которым с этим
борются (дублирующий запрос после p95), принадлежит
[`system-design/RELIABILITY_PATTERNS.md`](../../system-design/theory/RELIABILITY_PATTERNS.md).

**Цена в примере.** Оформление заказа — это `Checkout → Order → Inventory` плюс `Payment` с его
300 мс у провайдера. Бюджет задержки надо распределять между звеньями заранее, иначе каждое
звено поставит «таймаут три секунды» и суммарный ответ окажется в разы больше терпения
пользователя. Механика бюджета и крайнего срока — в
[`SYNC_COMMUNICATION.md`](SYNC_COMMUNICATION.md).

### 3.3 Полоса бесконечна

Допущение живёт в коде так: «отдадим весь заказ целиком, там же всё нужное». В монолите передача
объекта — это передача ссылки, размер не имеет значения. После разделения ровно тот же `Order` с
позициями, адресом, историей статусов и вложенным профилем покупателя превращается в килобайты,
которые надо сериализовать, отправить, принять и разобрать — 500 раз в секунду, на каждом
звене цепочки.

Арифметика: 500 запросов в секунду × 4 звена × 5 КБ = 10 МБ/с только на оформлении заказа, в одну
сторону. Это не страшное число для ЦОД — страшно то, что оно растёт от каждого «добавим ещё
поле в ответ» и что процессорное время на сериализацию из замера §2.1 (примерно 1.2 мкс на 128
байт в обе стороны) масштабируется вместе с ним.

**Цена в примере.** Размер полезной нагрузки становится предметом проектирования: «толстое»
событие несёт всё нужное потребителю и избавляет его от обратного вызова, «тонкое» — только
идентификатор, зато не тащит по сети то, что никому не понадобилось. Критерий выбора — в
[`ASYNC_MESSAGING.md`](ASYNC_MESSAGING.md).

### 3.4 Сеть безопасна

Допущение живёт в коде так: `Inventory` доверяет полю `customerId` в запросе, потому что «запрос
пришёл изнутри». Внутри монолита это было верно: вызывающий и вызываемый — один процесс, границы
доверия нет. После разделения «изнутри» перестало что-либо означать: в сети между сервисами
находится всё, что находится в кластере, — включая скомпрометированный контейнер соседа.

**Цена в примере.** Нужно удостоверение самой рабочей нагрузки (кто вызывает) отдельно от
пользовательского контекста (от чьего имени) — иначе `Notification` не может доказать, что письмо
попросил отправить `Order`, а не кто-то ещё. Разбор — в
[`SERVICE_IDENTITY.md`](SERVICE_IDENTITY.md); mTLS и хранение секретов —
[`infrastructure/SECRETS.md`](../../infrastructure/theory/SECRETS.md).

### 3.5 Топология не меняется

Допущение живёт в коде так: адрес соседа в конфигурации. В монолите адресов не было вовсе. После
разделения экземпляры сервисов появляются и исчезают постоянно — при раскатке, при
масштабировании, при вытеснении с узла, — и «текущий список адресов `Inventory`» становится
величиной, которая меняется несколько раз в минуту.

Наивное решение — статический список в конфигурации плюс перезапуск при изменениях — ломается
дважды: во время раскатки трафик идёт на уже погашенный экземпляр, а при масштабировании новые
экземпляры простаивают. Механизм (реестр, время сходимости, клиентское против серверного
обнаружения) — в [`EDGE_AND_MESH.md`](EDGE_AND_MESH.md).

**Цена в примере.** Появляется целая подсистема — обнаружение сервисов, проверки живости,
балансировка, — которой в монолите не существовало и которую надо эксплуатировать.

### 3.6 Администратор один

Допущение живёт в коде так: «попросим соседей выкатиться вместе с нами» — то есть предполагается,
что кто-то один может согласованно изменить конфигурацию всех участников. В монолите это
буквально было так: одна сборка, одно развёртывание, один человек нажимает кнопку.

После разделения `Payment` дежурит одна команда, `Inventory` — другая, а внешний платёжный
провайдер вообще не ваша организация: у него своё окно обслуживания, свои сроки вывода версий API
и своя политика ограничения нагрузки, о которых вас уведомят письмом.

**Цена в примере.** Всё, что требует «выкатимся одновременно», перестаёт быть выполнимым. Отсюда
требование обратной совместимости изменений и двухшаговых миграций
([`CONTRACTS_AND_TESTING.md`](CONTRACTS_AND_TESTING.md)) — и отсюда же главный диагностический
признак неправильного разреза из [`DECOMPOSITION.md`](DECOMPOSITION.md) §4.

### 3.7 Стоимость передачи нулевая

Пункт про деньги и про процессор, а не про задержку. Байт, ушедший в сеть, надо сериализовать,
скопировать в буфер ядра, зашифровать, отправить, принять, расшифровать и разобрать. В замере
§2.1 одна только сериализация 128 байт в обе стороны стоила ~1.2 мкс — сотня вызовов метода.
На 500 запросах в секунду × 4 звена это 2000 сериализаций в секунду в каждую сторону, и это
процессорное время, за которое вы платите деньгами за узлы.

К этому добавляется то, чего в монолите не было как статьи расходов вообще: межзонный трафик у
облачных поставщиков тарифицируется, и сервисы, разложенные по зонам доступности «для
надёжности», начинают приносить счёт за собственную болтливость.

**Цена в примере.** «Разложим на 20 маленьких сервисов, так чище» — решение, у которого есть
счёт. Когда разрез мельче, чем цена одного пересечения границы, получаются наносервисы
([`ANTIPATTERNS.md`](ANTIPATTERNS.md)).

### 3.8 Сеть однородна

Последнее допущение, добавленное Гослингом, и самое «архитектурное»: предполагается, что все
участники одинаковы — один протокол, одна кодировка, одна версия библиотеки, один язык.

На практике `Payment` разговаривает с провайдером по его REST с его моделью ошибок, `Inventory`
внутри — по gRPC, склад партнёра отдаёт XML по расписанию, а мобильное приложение хочет одну
агрегированную выдачу вместо пяти запросов. Однородность приходится либо строить и охранять
(общий протокол, общий формат ошибки), либо явно изолировать чужую модель на границе — это
Anticorruption Layer (ACL) из
[`ddd/STRATEGIC_DESIGN.md`](../../ddd/theory/STRATEGIC_DESIGN.md).

**Цена в примере.** Появляется работа, которой не было: договориться о формате ошибки, о формате
идентификаторов, о часовом поясе в метках времени — и следить, чтобы договорённость не расползлась.

**Правило по всему разделу.** Список читается не как «страшилки», а как чек-лист проектного
решения: для каждого места, где вызов уходит в сеть, у вас должен быть ответ на восемь вопросов —
что если не дошло, сколько это стоит по времени, сколько по объёму, кто вызывает, куда именно
идти, кто выкатывает вторую сторону, во что обходится байт и на каком языке разговаривают.

## 4. Доступность цепочки перемножается

**Задача.** Руководитель спрашивает: «мы разложили монолит на пять сервисов, каждый с
доступностью 99.9% — какая доступность у оформления заказа?» Ответ «99.9%» неверен.

**Наивное рассуждение.** «Каждый сервис почти всегда работает, значит и вместе они почти всегда
работают». Ошибка в слове «вместе»: если `Checkout` синхронно ждёт `Order`, тот — `Inventory`,
тот — `Payment`, то оформление заказа успешно **только если успешны все четыре**. Отказ любого
звена — это отказ всей операции, потому что вызывающему нечего вернуть пользователю.

**Механизм.** При независимых отказах вероятность «все работают» — произведение. Арифметика для
месяца из 30 суток (43 200 минут):

```
   звеньев   доступность цепочки   простой в месяц
         1              99.9000%          43.2 мин     (каждое звено 99.90%)
         2              99.8001%          86.4 мин
         3              99.7003%         129.5 мин
         4              99.6006%         172.5 мин
         5              99.5010%         215.6 мин

         4              99.9600%          17.3 мин     (каждое звено 99.99%)
```

Читается это так: **разделение на четыре синхронно связанных звена увеличило допустимый простой
почти вчетверо** — с 43 до 172 минут в месяц (точное отношение 3.994), при том что каждое звено
осталось не хуже прежнего. Монолит здесь выигрывает по определению: у него одно звено.

Три вывода, которые из этой таблицы следуют, и все три неочевидны:

1. Чтобы цепочка из четырёх звеньев держала те же 99.9%, каждое звено должно держать примерно
   99.975% — на порядок более жёсткое требование, чем к монолиту. Это и есть цена, переложенная
   на эксплуатацию.
2. Выигрывает не «сделать каждое звено надёжнее», а **укоротить цепочку**. Если `Notification`
   вынести из синхронного пути (письмо можно отправить и через секунду), звеньев становится
   три вместо четырёх — и это дешевле, чем добавить каждому звену девятку.
3. Отказ звена не обязан означать отказ операции. Если `Inventory` недоступен, а бизнес готов
   принять заказ и зарезервировать позже, цепочка вообще перестаёт перемножаться на этом звене.
   Такое решение называется деградацией, и оно принимается в предметной области, а не в коде.

Механику цепочки — где ставить таймаут, как распределять бюджет, что делать с крайним сроком —
подробно разбирает [`SYNC_COMMUNICATION.md`](SYNC_COMMUNICATION.md); изоляцию отказа звена —
[`FAILURE_ISOLATION.md`](FAILURE_ISOLATION.md); перевод звена в асинхронное —
[`ASYNC_MESSAGING.md`](ASYNC_MESSAGING.md).

**Правило.** Считайте длину синхронной цепочки как проектную величину. Каждый добавленный в неё
сервис умножает доступность на число меньше единицы, и это единственный способ, которым
микросервисы делают систему **менее** надёжной, чем монолит, — не «в теории», а арифметически.

## 5. Что именно покупается

Первые четыре раздела считали расходы. Теперь доходы — но с обязательной оговоркой к каждому:
**при каком условии он вообще возникает и что его аннулирует**. Микросервисы не выдают эти
свойства фактом разделения; они делают их достижимыми.

### 5.1 Независимое развёртывание

**Что покупается.** Выкатить изменение в `Payment`, не пересобирая и не выкатывая остальные
четыре сервиса. В монолите любая правка требует пройти сборку и тесты всего приложения и попасть
в общее окно релиза.

**При каком условии работает.** Изменение затрагивает ровно один сервис. Это, а не размер
сервиса, — определяющее свойство: если правка «добавить купон в заказ» требует одновременного
выпуска `Order`, `Payment` и `Checkout`, вы платите за микросервисы, но получаете релизный цикл
монолита. Диагностика такого состояния — в [`DECOMPOSITION.md`](DECOMPOSITION.md) §4, полный
разбор антипаттерна — в [`ANTIPATTERNS.md`](ANTIPATTERNS.md).

**Что аннулирует.** Общая библиотека с доменными типами, которую все обязаны обновить;
несовместимое изменение контракта; общая база, схему которой нельзя поменять в одиночку.

**Как измеряется.** Частотой развёртывания и временем от коммита до прода — это метрики DORA,
и они принадлежат
[`engineering-process/DELIVERY_METRICS.md`](../../engineering-process/theory/DELIVERY_METRICS.md).
Если после разделения частота развёртывания не выросла, разделение не окупилось — за это
заплатили, но не купили.

### 5.2 Автономия команды

**Что покупается.** Команда `Payment` принимает решения о своём сервисе — версия языка, схема
базы, срок раскатки — не согласовывая их с четырьмя другими командами. Стоимость согласования
растёт квадратично от числа участников; убрать согласование — значит убрать основной источник
задержек в большой организации.

**При каком условии работает.** У сервиса есть **владелец** — одна команда, которая его пишет,
выкатывает и по нему дежурит. Формулировка Вернера Фогельса из интервью ACM Queue 2006 года:
«The traditional model is that you take your software to the wall that separates development and
operations, and throw it over and then forget about it. Not at Amazon. You build it, you run it».
Это не лозунг про ответственность, а условие, при котором автономия имеет смысл: решение о
размене «быстрее выкатить против надёжнее» принимает тот, кого разбудят ночью.

**Что аннулирует.** Сервис без владельца («общий»), сервис, который пишет одна команда, а
эксплуатирует другая, и внешний архитектурный комитет, утверждающий решения внутри сервиса.

### 5.3 Изоляция отказа

**Что покупается.** Отказ `Notification` не роняет оформление заказа. В монолите утечка памяти в
модуле рассылки убивает процесс, в котором живёт весь `checkout`.

**При каком условии работает.** Граница процесса изолирует только **ресурсы процесса**: кучу,
дескрипторы, аварийное завершение. Она не изолирует ни зависимость по вызову, ни общую базу, ни
пул потоков вызывающего. Медленный `Notification`, который вызывают синхронно, ровно так же
уронит `Checkout`, как уронил бы модуль в монолите: запросы займут все потоки в ожидании ответа.
Механика этого каскада и то, чем от него защищаются (bulkhead, circuit breaker), — в
[`FAILURE_ISOLATION.md`](FAILURE_ISOLATION.md).

**Что аннулирует.** Синхронный вызов на пути запроса без таймаута и без ограничения
конкурентности. То есть **изоляция отказа не покупается разделением — она покупается отдельно**,
и разделение только делает её возможной.

### 5.4 Независимое масштабирование

**Что покупается.** В сквозном примере на 500 запросов в секунду `Payment` ждёт внешнего
провайдера 300 мс, а `Order` отвечает за единицы миллисекунд. По закону Литтла (`L = λ × W`,
разбор — в
[`concurrency/WHY_CONCURRENCY.md`](../../concurrency/theory/WHY_CONCURRENCY.md) §2) внутри
`Payment` одновременно находится `500 × 0.3 = 150` запросов, а внутри `Order` при 5 мс —
`500 × 0.005 = 2.5`. Это разные машины по профилю: одному нужны места для ожидания, другому —
процессор. В монолите оба живут в одном пуле потоков и масштабируются вместе — значит, по
худшему из них.

**При каком условии работает.** Узкое место действительно в приложении. Если и `Payment`, и
`Order` упираются в одну общую базу данных, добавление экземпляров сервиса только увеличит
очередь за соединениями — масштабируется не сервис, а его хранилище.

**Что аннулирует.** Общая база на несколько сервисов; общий кэш с горячим ключом; внешний
провайдер с квотой, которая не зависит от числа ваших экземпляров.

**Правило по разделу.** Из четырёх покупок безусловна ровно одна — независимое развёртывание, и
то при условии, что изменения не расползаются по сервисам. Остальные три — это **возможности**,
за реализацию которых надо платить отдельно. Ответ «нам нужны микросервисы для отказоустойчивости»
на собеседовании неполон: отказоустойчивость даёт не граница процесса, а таймаут, bulkhead и
деградация за ней.

## 6. Закон Конвея и обратный манёвр

**Задача.** Архитектор нарисовал целевую схему из пяти сервисов с чистыми границами. Через год
в системе восемь сервисов, между ними тридцать связей, а любое заметное изменение требует
согласования трёх команд. Схема не была плохой. Почему получилось не по схеме?

**Наивное объяснение** — «команды не соблюдали дисциплину». Оно неверно, потому что предсказывает
случайный результат, а результат систематический: система расползлась ровно по линиям, по которым
командам было трудно разговаривать.

**Механизм.** Мелвин Конвей описал его в статье «How Do Committees Invent?» (Datamation, апрель
1968 года). Дословная формулировка вывода:

> «organizations which design systems (in the broad sense used here) are constrained to produce
> designs which are copies of the communication structures of these organizations»

Ключевое слово — **communication structures**, а не «структура подчинения». Конвей формулирует
это как математическое соответствие: «there is a homomorphism from the linear graph of a system to
the linear graph of its design organization» — граф системы отображается на граф организации с
сохранением связей.

Причина не мистическая. Интерфейс между двумя частями системы — это то, о чём надо договориться.
Договариваться дорого; чем труднее общение между двумя группами, тем реже они меняют
договорённость и тем толще становится интерфейс, который её фиксирует. Внутри одной группы
общение дешёвое — там интерфейсы возникают и переделываются свободно, и граница размывается.
Поэтому границы модулей стягиваются к границам групп независимо от того, что нарисовано на схеме.

Льюис и Фаулер приводят закон в статье «Microservices» (2014) в короткой формулировке —
«Any organization that designs a system (defined broadly) will produce a design whose structure is
a copy of the organization's communication structure» — и тут же показывают его как объяснение
классической беды: если организация разделена по технологическим слоям (команда интерфейса,
команда серверной логики, команда базы данных), то простое изменение превращается в межкомандный
проект с отдельным бюджетом, и разумная команда «оптимизирует под это»: положит логику туда, куда
у неё есть доступ. Отсюда — «логика везде».

**Обратный манёвр (Inverse Conway Manoeuvre).** Если структура общения задаёт архитектуру, то
менять надо структуру общения. Приём опубликован в Thoughtworks Technology Radar 8 июля 2014 года
(кольцо Trial) и формулируется как развитие структуры команд под желаемую архитектуру. Фаулер
описывает его в сноске к «Microservice Premium» так: «Some examples of microservice usage had
organizations deliberately split themselves into small, loosely coupled groups in order to push
the software into a similar modular structure — a notion that's called the Inverse Conway
Maneuver».

**Что это означает на практике сквозного примера.** Решение «разделить оформление заказа на пять
сервисов» — это не техническое решение, а организационное: вы объявляете, что будет пять команд с
раздельными зонами ответственности и что общаться они будут через контракты, а не через общий
код. Если организационная часть не сделана — все пять сервисов пишет одна команда, — закон Конвея
никуда не делся: система вернётся к структуре этой команды, то есть к монолиту, но с сетью
посередине. Это и есть распределённый монолит; разбор — в
[`ANTIPATTERNS.md`](ANTIPATTERNS.md).

**Правило.** Границу сервиса рисуют одновременно с границей команды и границей дежурства. Разрез,
у которого нет владельца, не выживает — не потому, что люди плохие, а потому, что дешёвое общение
внутри команды стирает границу быстрее, чем документ её фиксирует.

Отдельная оговорка, чтобы не переусердствовать: закон Конвея не утверждает, что «одна команда —
один сервис». Он утверждает соответствие **графов**, а не мощностей. Одна команда может владеть
несколькими сервисами (и это норма); чего не бывает — это одного сервиса, за который отвечают
две команды.

## 7. Экономический критерий: сервисы против модульного монолита

### 7.1 Что с чем сравнивать

Частая ошибка в этом сравнении — противопоставить микросервисы **грязному** монолиту: «у нас всё
переплетено, поэтому разделим на сервисы». Это подмена: переплетённость лечится наведением
порядка внутри одного развёртываемого артефакта, и такое решение называется **модульный монолит**
— один процесс, одно развёртывание, жёсткие внутренние границы между модулями, у каждого своя
схема данных и свой публичный интерфейс. Как он устроен и почему «Bounded Context ↔ модуль» —
такое же законное отображение, как «Bounded Context ↔ сервис», разбирается в
[`ddd/ARCHITECTURE.md`](../../ddd/theory/ARCHITECTURE.md); сами Bounded Context и Context Map —
в [`ddd/STRATEGIC_DESIGN.md`](../../ddd/theory/STRATEGIC_DESIGN.md).

Честное сравнение — **модульный монолит против микросервисов**. Разница между ними ровно одна:
проходит ли граница модуля через границу процесса. Всё, что мы считали в §2–§4, — это цена именно
этого перехода, и ничего больше.

### 7.2 Форма затрат: постоянная плата против переменной выгоды

Плата за микросервисы **в основном постоянная** — она возникает один раз и не зависит от того,
сколько у вас сервисов: автоматизация развёртывания, распределённая трассировка, сбор метрик и
логов со всех экземпляров, единый способ аутентификации между сервисами, стенды, механика
раскатки и отката. Фаулер перечисляет тот же набор: «When you use microservices you have to work
on automated deployment, monitoring, dealing with failure, eventual consistency, and other factors
that a distributed system introduces».

Выгода **переменная и растёт с числом команд**: она состоит из устранённого согласования.
Согласование живёт в парах: у 3 команд 3 пары, у 6 команд — 15, у 10 — 45 (число пар это
`n(n−1)/2`). Пока команда одна, устранять нечего — пар ноль, а постоянная плата уже внесена
целиком.

Отсюда форма ответа на вопрос «когда окупается»: не «при N сервисах» и не «при M разработчиках»,
а **когда переменная выгода перерастает постоянную плату**. Фаулер изобразил это как две кривые
производительности в зависимости от базовой сложности системы; подписи на его графике:

> «for less-complex systems, the extra baggage required to manage microservices reduces
> productivity» — кривая монолита начинается **выше**;
> «as complexity kicks in, productivity starts falling rapidly» — про монолит;
> «the decreased coupling of microservices reduces the attenuation of productivity» — про
> микросервисы;
> и внизу оговорка: «but remember the skill of the team will outweigh any monolith/microservice
> choice».

Главное в этом графике — что кривые **пересекаются**, а не что одна лучше другой. Слева от
пересечения правильный ответ — монолит, справа — сервисы, и находиться слева не стыдно.

### 7.3 Практический критерий

Прямого ответа «с какого числа людей» не существует, и это стоит признать вслух: Фаулер, глядя на
реальные внедрения, пишет «I've seen microservice systems vary from a team of 60 with 20 services
to a team of 4 with 200 services» и тут же добавляет, что неясно, насколько размер сервиса вообще
влияет на надбавку. В первом случае на человека приходится 0.33 сервиса, во втором — 50: разброс
в **150 раз**. Значит, число сервисов на человека — не тот параметр, который что-то определяет.

Работает другой набор вопросов — каждый проверяемый фактом, а не мнением:

| Вопрос | Что означает ответ «да» |
|---|---|
| Мешают ли команды друг другу при выпуске? Есть ли очередь на релиз, общее окно, «дождёмся соседей»? | Есть что покупать: устранённое согласование |
| Разные ли требования к масштабированию у частей? (§5.4) | Есть что покупать: раздельное масштабирование |
| Есть ли автоматическое развёртывание, откат в одно действие и распределённая трассировка? | Постоянная плата уже внесена — покупка дешевле |
| Устоялся ли домен? Границы модулей за последний год двигались? | Если двигались — разрез преждевременен (§10.2) |
| Кто будет дежурить по каждому будущему сервису? Есть ли на всех владельцы? | Нет владельцев — разрез не выживет (§6) |

Если первые два ответа «нет», покупать нечего — вы платите постоянную часть и не получаете
переменную. Это и есть та ситуация, для которой Фаулер сформулировал своё главное правило:

> «So my primary guideline would be don't even consider microservices unless you have a system
> that's too complex to manage as a monolith. The majority of software systems should be built as
> a single monolithic application. Do pay attention to good modularity within that monolith, but
> don't try to separate it into separate services.»

**Правило.** Микросервисы — решение организационной задачи техническими средствами. Если
организационной задачи (несколько команд, мешающих друг другу выпускаться) нет, техническое
средство остаётся, а решать ему нечего — и тогда оно превращается в чистые расходы.

Замечание про «переписать заодно»: решение «разделим и одновременно перепишем» смешивает две
разные ставки — организационную и техническую. Как отдельно оценивать «переписать или платить
проценты», разбирает
[`engineering-process/TECH_DEBT.md`](../../engineering-process/theory/TECH_DEBT.md).

## 8. Микросервисы против SOA

**Задача.** На собеседовании звучит вопрос-ловушка: «микросервисы — это ведь просто новое название
для SOA?» Ответ «да, просто мода» и ответ «нет, это совершенно другое» одинаково плохи. Правильный
ответ требует назвать признак, по которому они различаются.

**Наивный ответ** — «в SOA сервисы большие, в микросервисах маленькие». Он не работает, потому что
размер не определён ни там, ни там (§7.3), и потому что ничего не объясняет: из «маленькие» не
выводится ни одно следствие.

**Механизм.** Различие проходит по одному вопросу: **где живёт логика взаимодействия**. Льюис и
Фаулер в статье «Microservices» (25 марта 2014) описывают это прямо. О том, чем на практике
оказывался SOA:

> «The problem, however, is that SOA means too many different things, and that most of the time
> that we come across something called “SOA” it's significantly different to the style we're
> describing here, usually due to a focus on ESBs used to integrate monolithic applications.»

И о выборе микросервисного сообщества:

> «The microservice community favours an alternative approach: smart endpoints and dumb pipes.»

То есть: в характерной реализации SOA умной делают **шину** — маршрутизация, преобразование
сообщений, оркестрация процесса и бизнес-правила живут в интеграционном продукте (ESB) между
приложениями. В микросервисах умными делают **концы**, а канал остаётся тупым: HTTP или брокер,
который умеет только доставить сообщение.

Почему это не переименование, видно на сквозном примере. «Проведение заказа» — процесс из четырёх
шагов. Вопрос: где записано знание о том, что после оплаты идёт резерв, а после резерва — письмо?

- **Умная шина.** Знание живёт в конфигурации интеграционного продукта. Сервисы становятся
  наборами операций без собственного поведения — «сервис заказов» умеет `create`, `update`,
  `getById`, а сценарий собирается снаружи. Развёртывать сервисы независимо формально можно, но
  любое изменение процесса — это изменение шины, и очередь на релиз просто переехала туда. Это же
  явление под именем «сущностные сервисы» разбирается в [`ANTIPATTERNS.md`](ANTIPATTERNS.md).
- **Умные концы.** Знание живёт внутри сервисов: `Order` знает, что делает при оплате,
  `Inventory` знает, как реагирует на созданный заказ. Канал ничего не знает. Выбор между
  оркестрацией и хореографией внутри этого подхода — отдельный разговор в
  [`ASYNC_MESSAGING.md`](ASYNC_MESSAGING.md).

Стоит добавить и честную часть: авторы статьи не утверждают, что микросервисы — принципиально
новая архитектура. Они пишут, что «This common manifestation of SOA has led some microservice
advocates to reject the SOA label entirely, although others consider microservices to be one form
of SOA, perhaps service orientation done right», и в сноске отмечают, что Netflix до недавнего
времени называл свой стиль «fine-grained SOA». Термин понадобился не потому, что идея новая, а
потому, что старый термин перестал что-либо означать.

**Правило.** Отличие формулируется через расположение логики, а не через размер: «умные концы,
тупые каналы» против «умная шина, тонкие сервисы». Проверочный вопрос к любой архитектуре,
называющей себя микросервисной: если удалить из системы интеграционный слой, останется ли
поведение в сервисах? Если нет — у вас SOA с ESB, как бы ни назывались артефакты.

## 9. Чего разделение на сервисы не делает

Пять ожиданий, которые не оправдываются, и каждое встречается в разговоре регулярно.

**Не улучшает качество кода.** Класс на 4000 строк, разрезанный на пять сервисов, остаётся классом
на 4000 строк — теперь распределённым по пяти репозиториям и вызывающим сам себя по HTTP. Граница
процесса не выполняет рефакторинг; она фиксирует ту декомпозицию, которую вы принесли. Из этого
следует практический порядок работ: сначала навести границы внутри одного артефакта, потом
разносить (см. [`DECOMPOSITION.md`](DECOMPOSITION.md) §5).

**Не ускоряет систему.** Каждое пересечение границы добавляет от десятков микросекунд (§2.1) до
сотен, если между машинами. Разделение может улучшить пропускную способность — за счёт того, что
части масштабируются раздельно, — но задержка одного запроса от разделения только растёт. Ответ
«мы разделили для производительности» требует уточнения: пропускной способности или задержки?
Это разные цели, и разделение действует на них в разные стороны.

**Не даёт изоляцию отказа само по себе.** §5.3: граница процесса изолирует ресурсы процесса, а не
зависимость по вызову. Синхронная цепочка из §4 делает систему **менее** доступной, чем монолит,
пока к ней не добавлены таймауты, bulkhead и деградация.

**Не убирает связность — переводит её в другую форму.** В монолите связность видна компилятору:
изменил сигнатуру — сломалась сборка. После разделения та же связность осталась, но стала
невидимой: изменил формат поля — сборка зелёная, ломается прод. Микросервисы не уменьшают число
зависимостей, они лишь меняют способ, которым про них узнают.

**Не заменяет доменное моделирование.** Если непонятно, где кончается «заказ» и начинается
«отгрузка», разрез по сервисам не ответит на этот вопрос, а зафиксирует неправильный ответ в
сетевых вызовах — где его исправление стоит на порядок дороже, чем перемещение класса между
пакетами. Инструменты, которыми на этот вопрос отвечают, — Bounded Context
([`ddd/STRATEGIC_DESIGN.md`](../../ddd/theory/STRATEGIC_DESIGN.md)) и Event Storming
([`ddd/EVENT_STORMING.md`](../../ddd/theory/EVENT_STORMING.md)).

## 10. Когда это неправильный ответ

Три ситуации, в которых микросервисы берут по инерции и в которых правильный ответ другой.

### 10.1 Одна команда

**Ситуация.** Восемь человек, один продукт, все сидят рядом. Предложение: «разложим на шесть
сервисов, чтобы сразу было правильно».

**Почему это неправильный ответ.** Вся выгода из §5 сводится к устранению согласования между
командами. Команда одна — согласовывать не с кем, устранять нечего. При этом постоянная плата из
§7.2 вносится полностью: восемь человек теперь эксплуатируют шесть развёртываний, шесть наборов
метрик, шесть баз и стенд, где всё это должно подняться вместе.

Дополнительно срабатывает §6: одна команда общается внутри себя дёшево, поэтому границы между
шестью сервисами будут стираться — появится общая библиотека с доменными типами, потом общая база
«временно», и через год выйдет распределённый монолит.

**Правильный ответ.** Модульный монолит с жёсткими внутренними границами: пакеты, у каждого свой
публичный интерфейс и своя схема таблиц, зависимости между модулями проверяются в CI. Так вы
получите обратимость: если модуль понадобится вынести, граница уже проведена. Обратный переход из
микросервисов в монолит стоит несравнимо дороже.

### 10.2 Домен неизвестен

**Ситуация.** Новый продукт, гипотезы меняются каждый месяц, никто пока не знает, что окажется
«заказом», а что — «подпиской».

**Почему это неправильный ответ.** Стоимость переноса функциональности через границу
несимметрична. Внутри одного артефакта перенос метода из модуля в модуль — это правка, которую
проверяет компилятор, и она выкатывается одним развёртыванием. Между сервисами тот же перенос —
это изменение двух контрактов, миграция данных, переходный период с двойной записью и
согласованная выкатка двух команд. Пока границы двигаются часто, вы платите эту разницу на каждой
гипотезе.

**Правильный ответ.** Держать границы там, где их дёшево двигать, — то есть внутри одного
развёртывания, — и разносить по сервисам те части, которые перестали двигаться. Способ узнать,
что часть устоялась, — посмотреть в историю: если за полгода граница модуля не переезжала, её
можно закреплять сетью.

### 10.3 Нет автоматизации развёртывания и наблюдаемости

**Ситуация.** Релиз выкатывается вручную по инструкции, откат делается восстановлением из
резервной копии, логи смотрят на машине, распределённой трассировки нет.

**Почему это неправильный ответ.** Это ровно та постоянная плата из §7.2, которую придётся внести
до первой выгоды, — и она не масштабируется добрым отношением. Один ручной релиз в неделю — это
терпимо; шесть ручных релизов, которые надо согласовать между собой, — это новая профессия внутри
команды. То же с диагностикой: §2.5 показал, что стектрейс кончается на границе процесса, и без
сквозного идентификатора запроса разбор инцидента превращается в сопоставление логов по времени —
занятие, которое не работает уже при пяти сервисах.

**Правильный ответ.** Сначала конвейер: сборка, автоматические тесты, развёртывание одной
командой, откат одной командой, сбор логов и метрик в одном месте, трассировка. Это полезно и
монолиту — а значит, вложение окупается независимо от того, дойдёт ли дело до разделения. Только
после этого разрезать.

### 10.4 Признак, по которому себя проверяют

Если на вопрос «что перестанет болеть после разделения» ответ формулируется в терминах кода
(«станет чище», «уберём дублирование», «будет современный стек»), — это неправильный ответ. Все
эти цели достижимы внутри одного артефакта и дешевле. Правильный ответ формулируется в терминах
организации и эксплуатации: «команда X перестанет ждать команду Y при выпуске», «`Payment`
перестанет ронять оформление заказа», «`Inventory` можно будет масштабировать отдельно, не
удваивая всё остальное».

| Граница доверия одна — процесс | Всё, что в кластере, ходит в вашу сеть | `SERVICE_IDENTITY.md` |

### Восемь ошибочных допущений и цена каждого

| Допущение | Как выглядит в коде | Цена |
|---|---|---|
| Сеть надёжна | у вызова нет ветки «не получилось» | двойное списание (§2.4) |
| Задержка нулевая | вызов соседа внутри цикла | 20 позиций × 90 мкс вместо 200 нс |
| Полоса бесконечна | «отдадим весь объект, там всё нужное» | 500 запросов/с × 4 звена × 5 КБ = 10 МБ/с |
| Сеть безопасна | доверие полю в запросе «потому что изнутри» | удостоверение нагрузки нужно строить |
| Топология не меняется | адрес соседа в конфигурации | обнаружение сервисов как подсистема |
| Администратор один | «выкатимся одновременно» | обязательная обратная совместимость |
| Передача бесплатна | «разложим на 20 сервисов, так чище» | процессор на сериализацию + счёт за трафик |
| Сеть однородна | «у всех один формат ошибки» | Anticorruption Layer на границе |

### Доступность цепочки

```
звеньев по 99.9%:   1 → 43 мин/мес   2 → 86   3 → 130   4 → 173   5 → 216
чтобы цепочка из 4 звеньев держала 99.9%, каждому звену нужно 99.975%
```

### Дерево решения «сервисы или модульный монолит»

```
Мешают ли команды друг другу при выпуске?
├── нет ──────────────────────────────────► модульный монолит (§10.1)
└── да
    └── Домен устоялся? Границы модулей стояли на месте полгода?
        ├── нет ───────────────────────────► модульный монолит, разрезать позже (§10.2)
        └── да
            └── Есть автоматическое развёртывание, откат и трассировка?
                ├── нет ───────────────────► сначала конвейер (§10.3)
                └── да
                    └── У каждого будущего сервиса есть команда-владелец и дежурство?
                        ├── нет ───────────► сначала владельцы, иначе граница не выживет (§6)
                        └── да ────────────► разрезать; критерии разреза — DECOMPOSITION.md
```

### Формулировки, которые хорошо звучат

- «Микросервисы — это решение организационной задачи техническими средствами. Нет задачи —
  остаются только расходы.»
- «Граница процесса изолирует ресурсы процесса, а не зависимость по вызову: медленный сосед
  уронит вас точно так же, как уронил бы модуль в монолите.»
- «После разделения у вызова три исхода вместо двух: успех, ошибка и „неизвестно“. Код с двумя
  ветками не упрощённый, а неправильный.»
- «Синхронная цепочка перемножает доступность: четыре звена по 99.9% дают 99.6%, то есть
  вчетверо больше простоя. Это тот случай, где микросервисы делают систему хуже монолита не
  в теории, а арифметически.»
- «Закон Конвея не про подчинение, а про общение: граница модуля стягивается туда, где
  договариваться дорого.»

## Вопросы для самопроверки

1. Вызов метода стоит 10 нс, вызов через локальную петлю — 90 мкс. Из этих 90 мкс на сериализацию
   уходит около 1.2 мкс. Куда девается остальное и почему у сетевого вызова появляется хвост,
   которого у вызова метода нет вовсе?
2. Сервер выполнил списание и оборвал соединение до ответа. Клиент получил `IOException`.
   Какие ровно три состояния мог иметь в виду этот `IOException` и почему клиент не может их
   различить? Что из этого следует для повторов?
3. Почему идемпотентность обязана обеспечиваться принимающей стороной, а не той, которая
   повторяет запрос?
4. Пять сервисов, каждый с доступностью 99.9%, соединены синхронной цепочкой из четырёх вызовов.
   Какая доступность у операции и сколько это минут простоя в месяц? Что дешевле: добавить каждому
   звену девятку или убрать одно звено из цепочки?
5. Компания разделила монолит на шесть сервисов, но частота развёртывания не изменилась. Какое
   именно из четырёх приобретений §5 не состоялось и по какому признаку это диагностируется?
6. Почему «мы разделили монолит ради отказоустойчивости» — неполный ответ? Что именно даёт
   граница процесса и чего она не даёт?
7. Как закон Конвея формулируется в оригинале и почему в нём важно слово «общение», а не
   «подчинение»? Что предсказывает закон для случая «шесть сервисов пишет одна команда»?
8. Постоянная плата за микросервисы и переменная выгода — из чего состоит каждая и почему из
   этого следует, что «правильного числа сервисов» не существует?
9. Чем микросервисы отличаются от типичной реализации SOA? Сформулируйте отличие так, чтобы из
   него следовал проверочный вопрос к конкретной системе.
10. Восемь человек, один продукт, домен меняется каждый месяц. Разложить на шесть сервисов —
    что именно пойдёт не так, по шагам?
11. Почему перенос функциональности через границу сервиса стоит принципиально дороже, чем
    перенос между модулями внутри одного развёртывания? Назовите все составляющие разницы.
12. Что теряется на границе процесса из того, что раньше проверял компилятор, и кому передаётся
    эта роль?
