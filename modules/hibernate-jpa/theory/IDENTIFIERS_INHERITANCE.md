# Hibernate / JPA — Идентификаторы и стратегии наследования

Как Hibernate получает значение первичного ключа, почему выбор генератора напрямую влияет на
способность пакетировать INSERT (JDBC-батчинг), и как объектную иерархию классов отобразить на
таблицы тремя несовместимыми способами с разными компромиссами.

---

## 1. Генерация идентификаторов: `GenerationType`

`@GeneratedValue(strategy = …)` выбирает источник значения первичного ключа.

| Стратегия | Механизм в БД | Знаем id до INSERT | JDBC-батчинг |
|-----------|---------------|--------------------|---------------|
| `IDENTITY` | автоинкрементный столбец (`AUTO_INCREMENT`, `SERIAL`) | нет | сломан |
| `SEQUENCE` | объект-последовательность (`nextval`) | да | работает |
| `TABLE` | отдельная таблица-счётчик с блокировкой строки | да | работает, но медленно |
| `AUTO` | провайдер выбирает сам по диалекту | зависит | зависит |
| `UUID` | значение генерируется приложением | да | работает |

### Почему `IDENTITY` ломает JDBC-батчинг

Автоинкрементный столбец возвращает значение только **после** физического выполнения INSERT.
Hibernate обязан знать id сразу при `persist()` (id — ключ в Identity Map persistence context),
поэтому он вынужден выполнять каждый INSERT немедленно и по одному. Это полностью отключает
группировку INSERT в пакет: на 1000 новых сущностей — 1000 обращений к БД вместо нескольких пакетов.

`SEQUENCE` свободен от этой проблемы: Hibernate получает значения из последовательности заранее,
проставляет id в памяти и спокойно копит INSERT в пакет до flush.

> На PostgreSQL `GenerationType.IDENTITY` поверх `SERIAL`/`BIGSERIAL` — частый источник деградации
> на массовых вставках. Для массовой нагрузки используйте `SEQUENCE` с пулом значений.

### `TABLE` — переносимый, но медленный

Эмулирует последовательность через строку в служебной таблице. Чтобы выдать следующее значение,
берёт блокировку строки (`SELECT … FOR UPDATE` + `UPDATE`), что сериализует выдачу id и создаёт
точку конкуренции. Применяют только когда последовательностей в СУБД нет.

## 2. Оптимизаторы последовательностей: hi/lo, pooled, pooled-lo

Чтобы не дёргать `nextval` на каждую вставку, Hibernate резервирует диапазон значений за один
запрос и раздаёт id из него в памяти.

| Оптимизатор | Как трактует значение из последовательности |
|-------------|----------------------------------------------|
| **hi/lo** | значение — «высокая» часть; локально генерирует `allocationSize` идентификаторов |
| **pooled** | значение из последовательности — верхняя граница выделенного диапазона |
| **pooled-lo** | значение из последовательности — нижняя граница диапазона |

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "book_seq")
@SequenceGenerator(name = "book_seq", sequenceName = "book_sequence",
                   allocationSize = 50)   // резервируем по 50 id за один nextval
private Long id;
```

Главная проблема классического **hi/lo** — несовместимость с внешними клиентами: другое приложение
(или ручной SQL), читающее ту же последовательность напрямую, не знает про hi/lo-разметку и
сгенерирует пересекающиеся id. **pooled** и **pooled-lo** этого недостатка лишены: значения из
последовательности интерпретируются как реальные границы, поэтому сторонние потребители той же
последовательности безопасны. Hibernate по умолчанию использует pooled-оптимизатор.

`allocationSize` — компромисс: больше значение → меньше обращений к последовательности, но больше
«дыр» в нумерации при рестартах приложения. Дыры в id безвредны — это не нарушение целостности.

## 3. UUID как идентификатор

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)   // JPA 3.1
private UUID id;
```

- **Плюс:** id известен сразу в приложении, до обращения к БД; удобен для распределённой генерации и
  для стабильных `equals`/`hashCode` сущности (см. [MAPPINGS_ASSOCIATIONS.md](MAPPINGS_ASSOCIATIONS.md)).
- **Минус:** случайный UUIDv4 как первичный ключ ухудшает локальность вставок в B-tree-индекс
  (случайные точки вставки → фрагментация, раздувание индекса). Версии с временным префиксом
  (UUIDv7, ULID) восстанавливают монотонность и снижают этот эффект.
- Хранить как нативный `uuid` (PostgreSQL) или `BINARY(16)`, не как `varchar(36)` — иначе индекс
  и диск раздуваются вдвое.

## 4. Естественные идентификаторы (`@NaturalId`)

Первичный ключ сущности часто синтетический — суррогатный `id` (последовательность, UUID), не несущий
смысла предметной области. Но у сущности почти всегда есть и **естественный (бизнес-) ключ**: ISBN у
книги, e-mail или login у пользователя, артикул у товара. Аннотация `@NaturalId` помечает такое поле как
естественный ключ при сохранённом отдельном суррогатном первичном ключе.

```java
@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;               // суррогатный первичный ключ

    @NaturalId
    @Column(nullable = false, unique = true, updatable = false)
    private String isbn;           // естественный (бизнес-) ключ

    private String title;
}
```

Зачем это нужно, если поиск по `isbn` можно выразить и обычным запросом `where isbn = ?`. Затем, что
`@NaturalId` даёт семантически осмысленный поиск по бизнес-ключу с собственным кэшированием: Hibernate
предоставляет специализированный lookup-API и отдельный регион L2-кэша, отображающий естественный ключ
на первичный (см. ниже).

> Тот же бизнес-ключ обычно лежит в основе `equals`/`hashCode` сущности — это естественный и
> иммутабельный идентификатор, не зависящий от того, сохранена ли сущность. Подробный разбор —
> [ENTITY_IDENTITY_EQUALS.md](ENTITY_IDENTITY_EQUALS.md).

### Изменяемые и неизменяемые естественные ключи

По умолчанию естественный ключ **неизменяем** (immutable): Hibernate считает, что после сохранения
сущности значение `@NaturalId`-поля не меняется, и агрессивно кэширует отображение «естественный ключ →
первичный ключ». Это совпадает с природой большинства бизнес-ключей (ISBN у изданной книги не меняется) и
соответствует требованию `updatable = false` для полей, участвующих в `equals`.

Если бизнес-ключ всё же может меняться (например, пользователь сменил e-mail-login), указывают
`@NaturalId(mutable = true)`:

```java
@NaturalId(mutable = true)
@Column(nullable = false, unique = true)
private String email;
```

Последствие: при каждом изменении такого поля Hibernate обязан инвалидировать старую запись в кэше
естественных идентификаторов и добавить новую — это дополнительная работа на запись и потеря части
оптимизаций по сравнению с неизменяемым вариантом. Поэтому `mutable = true` включают только когда ключ
действительно может меняться; по умолчанию (immutable) — предпочтительнее.

### Кэш естественных идентификаторов

Естественный ключ получает **отдельный регион L2-кэша**, который хранит лёгкое отображение «естественный
ключ → первичный ключ». Он работает **поверх** обычного кэша сущностей: поиск по бизнес-ключу сначала
превращает естественный ключ в первичный через этот регион, а затем достаёт состояние сущности из
entity-кэша по первичному ключу. Как и любой L2-регион, кэш естественных идентификаторов требует
включённого L2 и провайдера (Infinispan/Redis/Caffeine); устройство регионов и стратегии параллельного
доступа (`READ_WRITE`, `NONSTRICT_READ_WRITE`, …) — в [CACHING.md](CACHING.md), здесь не дублируются.

```java
@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
@org.hibernate.annotations.NaturalIdCache               // включить кэш естественных id
public class Book {
    @Id @GeneratedValue Long id;
    @NaturalId String isbn;
}
```

### Оптимизированный поиск: `byNaturalId` / `bySimpleNaturalId`

Hibernate предоставляет специальный API поиска по естественному ключу:

```java
// одно @NaturalId-поле — упрощённая форма
Book book = session
    .bySimpleNaturalId(Book.class)
    .load("978-0134685991");

// одно или несколько @NaturalId-полей — явная форма
Book book = session
    .byNaturalId(Book.class)
    .using("isbn", "978-0134685991")
    .load();
```

Почему это эффективнее обычного запроса по полю. Запрос `where isbn = ?` каждый раз идёт в БД и не
использует кэш. А `byNaturalId` сначала смотрит в кэш естественных идентификаторов: находит первичный
ключ, затем достаёт сущность из entity-кэша L2 (или из L1, если она уже в persistence context). В лучшем
случае поиск по бизнес-ключу не порождает ни одного SQL-запроса, а в худшем — определяет первичный ключ
одним лёгким SELECT и дальше работает по первичному ключу, на котором стоит самый эффективный индекс.

### Когда оправдан

Естественные идентификаторы оправданы при сочетании двух условий: **стабильный бизнес-ключ** (в идеале
неизменяемый) и **частый поиск именно по нему**. Каталог книг, где код почти всегда ищет по ISBN;
справочник пользователей с поиском по login — классические примеры. Если же бизнес-ключ меняется часто
или поиск по нему редкий, выигрыш от кэша естественных id не покрывает накладных расходов на его
поддержание — проще обойтись обычным уникальным индексом и запросом по полю.

> Battle-story: на сервисе каталога замена `findByIsbn(...)` (Spring Data, обычный `where isbn = ?`) на
> `bySimpleNaturalId(...)` с включённым `@NaturalIdCache` убрала тысячи одинаковых SELECT в час на
> «горячих» бестселлерах — повторные обращения к одной и той же книге стали обслуживаться из L2 без
> похода в БД. Ключевая предпосылка: ISBN неизменяем, поэтому кэш естественных id ни разу не пришлось
> инвалидировать.

## 5. Наследование сущностей

JPA отображает иерархию классов на таблицы тремя стратегиями через `@Inheritance(strategy = …)`.

| Критерий | `SINGLE_TABLE` | `JOINED` | `TABLE_PER_CLASS` |
|----------|----------------|----------|-------------------|
| Таблиц | одна на всю иерархию | по таблице на класс | по таблице на конкретный класс |
| Дискриминатор | `@DiscriminatorColumn` | опционально | нет |
| `NOT NULL` на полях подклассов | невозможно | возможно | возможно |
| Полиморфный запрос | один `SELECT` | `JOIN` родителя с потомками | `UNION ALL` |
| Нормализация | нет (много NULL-столбцов) | полная | дублирование столбцов родителя |
| Производительность чтения | лучшая | хуже из-за `JOIN` | плохая на полиморфных запросах |

### `SINGLE_TABLE` (по умолчанию)

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type")
public abstract class Payment { @Id Long id; BigDecimal amount; }

@Entity @DiscriminatorValue("CARD")
public class CardPayment extends Payment { String cardNumber; }

@Entity @DiscriminatorValue("WIRE")
public class WirePayment extends Payment { String iban; }
```

Все подклассы в одной таблице, тип строки определяет столбец-дискриминатор. Самая быстрая стратегия:
любой полиморфный запрос — это один `SELECT` без `JOIN`. Цена — невозможность повесить `NOT NULL`
на столбцы, специфичные для подкласса (у строк другого типа там NULL), и разрастание таблицы
разреженными столбцами.

### `JOINED`

Каждый класс — отдельная таблица; таблица подкласса хранит только свои поля и внешний ключ на
таблицу родителя. Полностью нормализовано, разрешает `NOT NULL`-ограничения на полях подклассов.
Цена — `JOIN` на каждое чтение и вставка в две таблицы при сохранении подкласса.

### `TABLE_PER_CLASS`

По таблице на каждый конкретный класс, столбцы родителя дублируются в каждой. Полиморфный запрос
собирается через `UNION ALL` по всем таблицам — самый дорогой вариант. Плюс несовместим с
`GenerationType.IDENTITY` (id должен быть уникален во всей иерархии). Применяют редко.

## 6. `@MappedSuperclass` vs `@Embeddable` vs наследование сущностей

Три способа переиспользовать общие поля — выбираются по тому, нужен ли полиморфизм и есть ли у части
собственная идентичность.

| Конструкция | Это сущность | Полиморфные запросы | Назначение |
|-------------|--------------|---------------------|------------|
| Наследование сущностей | да | да | подтипы с собственной таблицей/строкой и общим запросом |
| `@MappedSuperclass` | нет | нет | общие поля-столбцы (например, `createdAt`/`updatedAt`) без своей таблицы |
| `@Embeddable` | нет | нет | value-объект, встроенный в таблицу владельца |

```java
@MappedSuperclass
public abstract class Auditable {
    @Column(updatable = false) private Instant createdAt;
    private Instant updatedAt;
}

@Entity
public class Invoice extends Auditable {   // столбцы createdAt/updatedAt в таблице invoice
    @Id @GeneratedValue Long id;
}
```

- `@MappedSuperclass` отдаёт поля-столбцы в таблицу наследника, но сам не сущность: по нему нельзя
  выполнить запрос и нельзя сослаться ассоциацией.
- `@Embeddable` — value-объект без идентичности, встраивается как компонент (см.
  [MAPPINGS_ASSOCIATIONS.md](MAPPINGS_ASSOCIATIONS.md)).
- Наследование сущностей выбирают только когда действительно нужны полиморфные запросы и ссылки на
  базовый тип; иначе оно избыточно дорого.

## 7. Полиморфные запросы

Запрос по базовому типу возвращает экземпляры всех подтипов; форма SQL зависит от стратегии
наследования.

```java
// вернёт CardPayment и WirePayment
List<Payment> all = em.createQuery("select p from Payment p", Payment.class)
                      .getResultList();
```

- `SINGLE_TABLE` — один `SELECT` с фильтром по дискриминатору; самый дешёвый.
- `JOINED` — `LEFT JOIN` родителя со всеми таблицами потомков.
- `TABLE_PER_CLASS` — `UNION ALL` по всем таблицам конкретных классов; дороже всего.

Ограничить тип в JPQL можно через `type(p) = CardPayment`. Если полиморфизм фактически не нужен —
запрос всегда идёт к конкретному подтипу — это сигнал, что наследование сущностей здесь лишнее и
стоило обойтись `@MappedSuperclass`.
