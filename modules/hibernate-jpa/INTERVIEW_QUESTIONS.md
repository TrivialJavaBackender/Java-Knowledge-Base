# Hibernate / JPA — вопросы для собеседования

## 1. Основы: JPA vs Hibernate

### Q1: В чём разница между JPA и Hibernate?
**A:** JPA (Jakarta Persistence) — это **спецификация** (набор интерфейсов и аннотаций: `EntityManager`, `@Entity`, JPQL), которая сама ничего не делает. Hibernate — конкретная **реализация** (провайдер) этой спецификации, причём с собственными расширениями поверх стандарта (`Session` как надмножество `EntityManager`, HQL как надмножество JPQL, `@BatchSize`, `@Fetch`). Код против чистого JPA переносим между провайдерами; код против Hibernate-API — нет, но даёт больше возможностей.
> Jakarta Persistence 3.1 Specification

### Q2: Чем `EntityManagerFactory` отличается от `EntityManager` по жизненному циклу и потокобезопасности?
**A:** `EntityManagerFactory` (аналог `SessionFactory`) — тяжёлый, потокобезопасный, создаётся один раз на persistence unit и живёт всё время работы приложения. `EntityManager` (аналог `Session`) — лёгкий, **не потокобезопасный**, создаётся под одну единицу работы (обычно транзакцию) и хранит persistence context. Делить один `EntityManager` между потоками нельзя.

### Q3: Какой режим `ddl-auto` использовать в продакшене и почему `update` опасен?
**A:** В продакшене — `none` или `validate` (схема управляется миграциями: Flyway/Liquibase). `update` опасен тем, что генерирует ALTER на основе различий маппинга и схемы: он только добавляет, никогда не удаляет колонки, не умеет переименовывать без потери данных, непредсказуем при конкуренции инстансов и может заблокировать таблицу. Это инструмент для прототипов, не для прода.

## 2. Жизненный цикл сущности

### Q4: Назовите четыре состояния сущности и переходы между ними.
**A:** **Transient** (новый объект, не в контексте, без id) → `persist()` → **Managed** (в persistence context, изменения отслеживаются и попадут в БД на flush) → `detach()`/`clear()`/закрытие сессии → **Detached** (вне контекста, изменения не отслеживаются) → `merge()` → снова Managed. Из Managed через `remove()` → **Removed** (помечена на удаление, DELETE на flush).

### Q5: Чем `merge` отличается от `persist`, и почему `merge` для новой сущности — антипаттерн?
**A:** `persist` делает переданный объект managed (тот же экземпляр) и работает только с transient-сущностями. `merge` копирует состояние в **другой** managed-экземпляр и возвращает его — исходный объект остаётся `detached`. Для новой сущности `merge` лишний раз выполняет SELECT (проверяя, нет ли её в БД) и заставляет работать с возвращённым объектом, а не с переданным — это запутывает и медленнее, чем `persist`.

### Q6: Когда Hibernate выполняет flush и как dirty checking это решает?
**A:** Flush происходит в трёх случаях: при коммите транзакции, автоматически перед выполнением JPQL/HQL-запроса (FlushMode AUTO, чтобы запрос видел незакоммиченные изменения) и при явном `flush()`. На flush работает **dirty checking**: Hibernate хранит снимок (snapshot) загруженного состояния каждой managed-сущности и сравнивает его с текущим — для изменившихся генерирует UPDATE. Цена — память на снимок для каждой сущности в контексте.

## 3. Маппинг и ассоциации

### Q7: Что определяет owning side ассоциации и почему изменение inverse-стороны не пишет FK?
**A:** Owning side — сторона **без** `mappedBy`; именно она владеет внешним ключом (FK) и определяет, что запишется в БД. Inverse-сторона (с `mappedBy`) — только зеркало для навигации. Hibernate смотрит на синхронизацию FK исключительно по owning side, поэтому добавление в inverse-коллекцию без установки ссылки на owning-стороне не приводит к записи FK. Отсюда правило helper-методов, синхронизирующих обе стороны.

### Q8: Чем `orphanRemoval` отличается от `CascadeType.REMOVE`?
**A:** `CascadeType.REMOVE` удаляет дочерние сущности только когда удаляется родитель. `orphanRemoval = true` удаляет дочернюю сущность ещё и тогда, когда её **отвязали** от родителя (убрали из коллекции или обнулили ссылку), даже если родитель остаётся. `orphanRemoval` подразумевает строгое composition-владение (заказ → позиции заказа), а `REMOVE` — обычный каскад удаления.

### Q9: Почему id-based `equals()`/`hashCode()` ломается с `HashSet`?
**A:** Для transient-сущности id ещё `null`, а после `persist`/flush БД присваивает id — значит `hashCode()` объекта **меняется** после добавления в `HashSet`, и объект «теряется» в наборе. Решения: использовать стабильный бизнес-ключ (natural key) или назначать UUID в приложении до сохранения; дефолтный `equals` от Lombok `@Data` для сущностей опасен (тянет lazy-поля и ассоциации).

## 4. Идентификаторы и наследование

### Q10: Почему `GenerationType.IDENTITY` отключает JDBC-батчинг, а `SEQUENCE` — нет?
**A:** При IDENTITY значение id генерирует БД в момент INSERT (auto-increment), и Hibernate узнаёт его только после выполнения каждого INSERT отдельно — поэтому не может сгруппировать вставки в один пакет. При SEQUENCE Hibernate получает значения из последовательности **заранее** (с оптимизаторами pooled/pooled-lo — пачками), поэтому знает id до INSERT и может объединять вставки в один JDBC-пакет.

### Q11: Сравните три стратегии наследования (SINGLE_TABLE / JOINED / TABLE_PER_CLASS).
**A:** **SINGLE_TABLE** — все классы иерархии в одной таблице с discriminator-колонкой: быстрые запросы (без JOIN), но колонки подклассов обязаны быть nullable. **JOINED** — таблица на класс, общие поля в родительской: нормализованно и с NOT NULL, но каждый запрос делает JOIN. **TABLE_PER_CLASS** — таблица на конкретный класс со всеми полями: полиморфные запросы превращаются в UNION ALL — обычно худший вариант. По умолчанию выбирают SINGLE_TABLE или JOINED.

## 5. Fetch-стратегии и N+1

### Q12: Почему `@ManyToOne(fetch = EAGER)` опасен и как именно даёт N+1?
**A:** `@ManyToOne` и `@OneToOne` по умолчанию EAGER, и это нельзя «выключить» на уровне запроса. При загрузке коллекции сущностей через JPQL/HQL Hibernate не умеет автоматически делать JOIN для EAGER-ассоциаций — он дозагружает каждую отдельным SELECT, давая классический N+1. Правило: ставить всем ассоциациям `LAZY` и подгружать явно через `JOIN FETCH`/`@EntityGraph` там, где нужно.
> Vlad Mihalcea — High-Performance Java Persistence

### Q13: Почему `JOIN FETCH` коллекции несовместим с пагинацией и каков корректный паттерн?
**A:** JOIN с коллекцией умножает строки (декартово произведение), поэтому БД-уровневый LIMIT применился бы к «размноженным» строкам, а не к корневым сущностям. Hibernate в этом случае тянет весь результат в память и пагинирует в Java (предупреждение `HHH90003004`/`HHH000104`). Корректный паттерн — два запроса: первый выбирает id корневых сущностей с пагинацией, второй делает `JOIN FETCH ... WHERE id IN (:ids)`.

### Q14: В чём причина `LazyInitializationException` и какие решения корректны?
**A:** Исключение возникает при обращении к неинициализированной LAZY-ассоциации **после** закрытия persistence context (например, в контроллере вне транзакции). Корректные решения: загрузить нужные связи заранее внутри транзакции (`JOIN FETCH`, `@EntityGraph`) или вернуть DTO-проекцию. Open-Session-In-View «лечит» симптом, но это антипаттерн: держит соединение на весь HTTP-запрос и маскирует N+1.

## 6. Кэширование

### Q15: В чём разница L1 и L2 кэша и почему L1 нельзя отключить?
**A:** L1 (first-level) — это сам persistence context: он действует в пределах одной сессии/транзакции и реализует identity map (один объект на id). Отключить его нельзя, потому что от него зависит **корректность** (dirty checking, гарантия одного экземпляра). L2 (second-level) — общий кэш на уровне `SessionFactory`, переживает транзакции, хранит «дегидрированное» состояние сущностей (не JVM-объекты), требует провайдера и опционален.
> Hibernate ORM User Guide — Caching

### Q16: Чем `READ_WRITE` отличается от `NONSTRICT_READ_WRITE` и когда что выбирать?
**A:** `NONSTRICT_READ_WRITE` после коммита просто инвалидирует запись в кэше без блокировки — между коммитом и инвалидацией возможно короткое окно устаревших данных; подходит для редко меняющихся данных, где допустима небольшая рассинхронизация. `READ_WRITE` использует «soft lock»: помечает запись заблокированной на время изменения, прочие транзакции в это окно идут в БД — строже и консистентнее, но дороже. `READ_ONLY` — для неизменяемых справочников.

## 7. Транзакции и блокировки

### Q17: Почему `OptimisticLockException` прилетает на коммите, а не в месте изменения?
**A:** Оптимистичная блокировка через `@Version` не блокирует ничего при чтении. Конфликт обнаруживается только в момент UPDATE: Hibernate выполняет `UPDATE ... SET version = version+1 WHERE id = ? AND version = ?`. Если другая транзакция уже увеличила version, условие `WHERE version = ?` не находит строку → 0 обновлённых строк → Hibernate бросает `OptimisticLockException`. А UPDATE откладывается до flush/коммита — отсюда «позднее» исключение.

### Q18: Когда выбирать `@Version` (оптимистичную), а когда `PESSIMISTIC_WRITE`?
**A:** Оптимистичную (`@Version`) — когда конфликты редки и важна пропускная способность: нет блокировок в БД, нет риска deadlock, но нужна логика повтора (retry) на `OptimisticLockException`. Пессимистичную (`LockModeType.PESSIMISTIC_WRITE` → `SELECT ... FOR UPDATE`) — когда конфликты вероятны и повтор дорог/нежелателен (списание баланса, очередь задач, ограниченный инвентарь): транзакция держит блокировку строки до коммита, остальные ждут.

## 8. Производительность

### Q19: Что делает `StatelessSession` и от каких возможностей ORM она отказывается?
**A:** `StatelessSession` — низкоуровневый API для массовых операций: нет persistence context (L1), нет dirty checking, нет каскадов, нет ленивой загрузки и взаимодействия с L2. Каждая операция (`insert`/`update`/`delete`) идёт в БД напрямую без накопления состояния, поэтому память не растёт на больших объёмах. Платой за это является ручное управление: автоматического отслеживания изменений и каскадов нет.

### Q20: Почему Open-Session-In-View считается антипаттерном?
**A:** OSIV держит persistence context (и часто соединение с БД) открытым на всё время обработки HTTP-запроса, включая рендеринг ответа. Это: (1) удерживает соединение из пула дольше нужного → исчерпание пула под нагрузкой; (2) маскирует N+1 — ленивые связи «молча» дозагружаются на этапе сериализации; (3) размывает границы транзакции. В Spring Boot он включён по умолчанию — рекомендуется сразу ставить `spring.jpa.open-in-view=false` и загружать данные явно.
> Vlad Mihalcea — The Open Session In View Anti-Pattern
