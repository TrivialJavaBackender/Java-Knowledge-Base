# Создать новый модуль

Создай новый interview prep модуль в `modules/$ARGUMENTS`.

## Модель работы — оркестрация, НЕ написание теории руками

**Главный агент только оркестрирует.** Он делает дешёвую работу (скаффолдинг, план
батчей, диспетчинг, агрегация коротких отчётов). **Теорию пишут сабагенты.** Так главный
контекст остаётся лёгким, а перевод — единым.

> **Почему так.** Раньше главный агент писал все 8–15 файлов теории сам (по 150–300 строк
> каждый) → контекст раздувался, терминология дрейфовала между файлами, сессия дорожала.
> Делегирование решает все три проблемы сразу.

**НИКОГДА не пиши теорию в главном контексте.** Если тянет написать `theory/*.md`
самому — остановись и запусти сабагента (Фаза 3). Образец паттерна батчинга/волн —
`.claude/commands/check-translation.md`.

### Устойчивость к обрыву — это часть протокола, а не пожелание

Прогон выжигает 5-часовое окно, и обрыв в середине волны — штатная ситуация, а не авария.
Три правила ниже делают потерю дешёвой; они обязательны на всех фазах.

1. **Ничего ценного не живёт только в контексте.** Проверенный факт, написанный раздел и
   отчёт попадают на диск в момент получения, а не в конце работы агента.
2. **Каждая фаза идемпотентна.** Повторный запуск команды на том же модуле досбирает
   недостающее, а не переписывает готовое (Фаза 3.5).
3. **Состояние читается с диска, а не из памяти.** Главный агент определяет, что сделано,
   по файлам, а не по тому, что помнит из отчётов.

## Что считается хорошей теорией

**Канонический документ — [`knowledge/THEORY_CONTRACT.md`](../../knowledge/THEORY_CONTRACT.md).**
Он обязателен к прочтению и главным агентом (Фаза 1), и каждым сабагентом (Фаза 3).

Коротко, чтобы не расходиться в понимании задачи:

- Теория — **объяснение, а не справочник**. Каталог методов не нужен: javadoc полнее.
- Каждый файл открывается тремя ответами: **какую проблему решает / кому это надо / когда НЕ надо**.
- Каждый смысловой раздел: **задача → наивное решение и где оно ломается → механизм → правило**.
- Каждое утверждение о поведении подпёрто **исходником с номером строки, прогоном или
  спецификацией**. Формулировки «известно, что» запрещены.
- У модуля есть **сквозной пример**, проходящий через все файлы.

Типичный провал, ради предотвращения которого всё это написано: получается набор верных фактов,
по которому человек, не работавший с темой, не разберётся, — плюс несколько правдоподобных
утверждений, оказавшихся при проверке неверными.

## Фаза 0 — Уточнение (главный агент, дёшево)

Спроси у пользователя:
- Имя модуля (папка в `modules/`) — обычно это `$ARGUMENTS`.
- Тема (краткое описание).
- Тип сборки: `kotlin` | `java-plain` | `java-spring` | `no-build`.
- **Список файлов теории с однострочной областью каждого** (например:
  `BASICS.md — иерархия кэшей, locality, метрики`).
- **Сквозной пример модуля** — одна задача, на которой будут сравниваться подходы во всех файлах
  (например: «сервис на 1000 rps, запрос = три вызова по 100 мс»). Если пользователь не назвал —
  предложи свой вариант и подтверди.
- **На чём проверять утверждения**: версии стека (JDK, библиотеки), доступны ли исходники
  (`$JAVA_HOME/lib/src.zip`), можно ли запускать код. Это определяет, чем сабагенты будут
  подпирать факты.

## Фаза 1 — NO-OVERLAP + план батчей (главный агент, дёшево)

1. Прочитай [`knowledge/THEORY_CONTRACT.md`](../../knowledge/THEORY_CONTRACT.md),
   `knowledge/GLOBAL_INDEX.md` и таблицу модулей в корневом `CLAUDE.md`.
2. Для каждой темы реши **OWN vs LINK**:
    - **OWN** — концепт ещё не имеет владельца → этот модуль становится владельцем.
    - **LINK** — концепт уже принадлежит другому модулю → даём ссылку, **не дублируем**.
      Зафиксируй точный путь цели (`modules/<slug>/theory/FILE.md`).
3. **Спроектируй порядок файлов от мотивации к механизму.** Первым идёт файл, отвечающий
   «зачем это всё и чем мы платим», а не «основы API». Если в модуле есть тема
   «как оно устроено внутри» — она должна быть отдельным файлом, а не абзацем в конце.

### 4. Сгруппируй файлы в батчи

**Батч по умолчанию — 2–3 смежных файла, а не один.**

> **Почему.** Каждый сабагент обязан прочитать `THEORY_CONTRACT.md`, `GLOSSARY.md`,
> `CANONICAL_TERMS.md`, релевантную часть `GLOBAL_INDEX.md` и файл-образец. Это фиксированная
> цена входа, и при «1 файл = 1 батч» она платится 8–15 раз за модуль. Батч из трёх файлов
> платит её один раз на три файла. Плюс терминология и перекрёстные ссылки внутри батча
> получаются согласованными без отдельной вычитки.

Правила размера:

- **2–3 файла** — норма. Группируй по смысловой близости: файлы, которые ссылаются друг на
  друга и раскрывают одну механику с разных сторон (`CACHE_PATTERNS.md` + `EVICTION_POLICIES.md`).
- **1 файл** — если тема изолирована (ни с чем не пересекается), ожидается большой объём
  (>700 строк) или тяжёлая проверочная часть (много прогонов).
- **Потолок батча — 3 файла или ~1800 строк** ожидаемого вывода, что наступит раньше.
  Практически это значит: три файла в батче — только когда они небольшие (по 400–600 строк);
  при ожидаемых 800–1000 строк на файл батч — это два файла, а то и один.
- Ограничение не про деньги, а про контекст сабагента: при инкрементальной записи текст
  проходит через контекст дважды (сам `Edit` и его результат), сверху ложится вывод
  проверочных прогонов. За этой границей включается авто-компактификация, после которой
  падает точность ссылок на уже написанные разделы.
- Файлы внутри батча сабагент пишет **последовательно**, полностью закрывая один перед
  переходом к следующему (см. шаблон промпта). Обрыв стоит хвоста одного файла, а не батча.

### 5. Выбери модель на батч

Не прибивай `opus` ко всем батчам — это самый быстрый способ упереться в 5-часовое окно.

- `opus` — батчи, где сложное **объяснение механизма** (внутреннее устройство, модели памяти,
  протоколы согласования).
- `sonnet` — батчи, где доминирует **проверочная часть** и структурированное изложение
  (сравнение подходов, паттерны, конфигурация).

Укажи выбранную модель для каждого батча в плане.

### 6. Покажи план пользователю

**До запуска сабагентов** покажи: батчи (файлы + модель + ожидаемый объём), решения OWN/LINK,
сквозной пример. Это обязательный шаг.

## Фаза 2 — Скаффолдинг (главный агент, дёшево, без тяжёлой прозы)

Создай структуру директорий.

`kotlin` / `java-plain`:
```
modules/<name>/
├── theory/
├── .build/            ← служебное, в .gitignore
│   ├── reports/
│   └── verified/
├── pom.xml
└── src/
    ├── main/
    │   └── kotlin/exercises/   (или java/by/pavel/)
    └── test/
```
`java-spring`:
```
modules/<name>/
├── theory/
├── .build/{reports,verified}/
├── pom.xml
├── Dockerfile
└── src/main/
    ├── java/by/pavel/
    └── resources/application.properties
```
`no-build`:
```
modules/<name>/
├── theory/
├── .build/{reports,verified}/
└── exercises/
```

Затем:
- **`.gitignore`** — добавь `modules/*/.build/`, если ещё нет. Директория служебная:
  журнал проверок и отчёты сабагентов, нужна только между фазами и для досбора после обрыва.
- **`pom.xml`** — скопируй из соседнего модуля того же типа, адаптируй `<artifactId>`.
  ⚠️ Проверь версии зависимостей на совместимость: в двух существующих модулях
  `kotlin-test-junit5` оказался пиньнут на версию новее компилятора. Собери пустой модуль
  (`mvn -q test-compile`) до того, как передавать его дальше.
- **`README.md`** — описание, структура, команды сборки/запуска/тестов и (если есть
  упражнения) модуль-специфичный фокус code review. Прогресс НЕ трекаем — это web app.
- **`ROADMAP.md`** — **перечисли файлы теории в нужном порядке прохождения**.
  ⚠️ web-sync берёт порядок теории на сайте из первого упоминания `theory/<NAME>.md`
  в `ROADMAP.md`; сабагенты тоже опираются на этот список. Файлы не из roadmap уйдут
  в конец по алфавиту.
- **`.build/PLAN.md`** — запиши сюда план батчей из Фазы 1: для каждого батча файлы, модель,
  решения OWN/LINK, сквозной пример, стек для проверки. Это единственный источник правды
  при досборе после обрыва; без него Фаза 3.5 не восстановит контекст запуска.

**Теорию, `INTERVIEW_QUESTIONS.md`, `_SUMMARY.md` здесь НЕ пиши.**

## Фаза 3 — Диспетч сабагентов теории (параллельно ≤2, волнами)

**Перед каждой волной прогони `/usage`.** Если остатка окна на волну явно не хватает —
не запускай: скажи пользователю, сколько осталось и когда сброс. Дождаться сброса дешевле,
чем потерять волну на середине.

Запусти по одному сабагенту на батч:

```
Agent(
  subagent_type: "general-purpose",
  model: <модель батча из Фазы 1>,
  name: "theory-<первый файл батча без .md>",
  maxTurns: 80,
  prompt: <см. шаблон>
)
```

- **Максимум 2 параллельно** (оба Agent-вызова в одном сообщении). Больше батчей — волнами
  по 2, дожидаясь предыдущей волны.
- `name` обязателен: именованного сабагента можно адресовать и возобновить после обрыва,
  не выковыривая agent ID из транскрипта.
- `maxTurns: 80` — предохранитель от агента, ушедшего в бесконечные перепроверки.
  Подними до 100–120, если батч из трёх файлов с тяжёлой проверочной частью упирается в лимит.

**Упражнения модуля** (для блока «Упражнения»): `<перечисли Ex*.kt / applied-пакеты, если есть>`.

#### Протокол записи — инкрементальный, это обязательно

Твоя работа может быть оборвана лимитом в любой момент. Всё, что существует только в твоём
контексте, при обрыве теряется; всё, что записано на диск, — переживает. Поэтому:

**Журнал проверок.** Перед началом работы прочитай
`modules/<name>/.build/verified/<FILE>.notes.md`, если он есть: проверки оттуда **повторять
не надо**, они уже сделаны прошлым запуском. Каждый факт, который ты проверил, дописывай
туда **сразу после проверки, до того как использовал его в тексте**:
```
- <утверждение>
  чем подпёрто: <путь:строка> | <команда → реальный вывод> | <цитата спецификации>
```
Это самая дорогая часть работы — прогоны и лазанье в исходники. Она не должна прогоняться дважды.

**Тело файла.** По каждому файлу:
1. Сразу после чтения контракта запиши `Write`-ом скелет: шапка из трёх вопросов + заголовки
   всех разделов + последней строкой маркер `<!-- WIP -->`.
2. Дальше наполняй по одному разделу через `Edit`, заменяя заголовок на готовый текст.
3. Когда файл дописан целиком — убери `<!-- WIP -->`.

Файл с `<!-- WIP -->` считается недописанным: его доделает следующий запуск, опираясь на
твой журнал проверок. Файл без маркера считается готовым.

**Отчёт.** По каждому закрытому файлу дописывай отчёт в
`modules/<name>/.build/reports/<FILE>.md` — **и только потом переходи к следующему файлу**.
Тот же текст верни в финальном ответе.

**Текстовые чекпоинты.** После каждого закрытого файла выведи одну строку обычным текстом:
`готов <FILE>.md, <N> строк`. Это не косметика: агент, чей вывод состоял только из вызовов
инструментов, при обрыве по лимиту падает с голой ошибкой и не отдаёт наверх ничего.

**Требования к содержанию — по `THEORY_CONTRACT.md`. Ключевое:**
- Шапка файла отвечает на три вопроса: какую проблему решает / кому это надо / когда НЕ надо.
- Каждый раздел: задача → наивное решение и где ломается → механизм → правило.
- **Никаких каталогов API** вне финальной шпаргалки. Выбор метода выводится из критерия
  (что у вас на входе → что брать), а не даётся списком.
- Обязательны разделы «чего этот инструмент не делает» и «когда это неправильный ответ».
- В конце: «Шпаргалка», «Упражнения» (если есть), «Вопросы для самопроверки» (7–12, про
  механизм, а не про сигнатуры), «Источники».
- **Объём — сколько нужно объяснению. 800–1000 строк — верхняя граница, а не цель.**
  Не сокращай написанное ради попадания в число: ужимание текста, который уже удовлетворяет
  контракту, — потраченные ходы и испорченный результат. Объяснение длиннее перечисления,
  и это нормально; вода — нет.
- Если файл перевалил за 1000 строк — это сигнал, что тему стоило разделить на два файла,
  а не повод его резать. Закончи файл как есть и добавь в отчёт строку
  `- Перебор объёма: <N> строк, напрашивается разделение на <как именно>`.
  Решение о разделении принимает главный агент, не ты.
- Файлы одного батча смежны по теме: связывай их перекрёстными ссылками и не дублируй
  объяснение, данное в предыдущем файле батча, — ссылайся на него.

**Требования к достоверности — это не формальность:**
- **Проверяй перед тем, как написать.** Есть Bash — пользуйся: скомпилируй пример
  (`java Файл.java`), загляни в исходник (`unzip -p $JAVA_HOME/lib/src.zip …`, `grep -n`),
  проверь наличие класса или флага. Утверждения «по памяти» регулярно оказываются неверными.
- Каждое утверждение о поведении подпирается **файлом и номером строки**, **реальным выводом
  прогона** либо **точной цитатой из спецификации**. Формулировки «известно, что»,
  «обычно считается» запрещены.
- Выводы программ в блоках — **настоящие**, скопированные из прогона. Придуманный вывод —
  худшая из возможных ошибок: он выглядит как доказательство.
- Замеры оформляй с машиной, версиями, оговоркой про точность и командой для повторения.
  Разброс показывай честно.
- Если проверить утверждение не удалось — **не пиши его**, либо пометь явно как непроверенное
  и вынеси в отчёт.

**Перевод — строго по `GLOSSARY.md`:**
- Латиницей оставляй **только** раздел 1 глоссария (аббревиатуры/протоколы/продукты/алгоритмы/
  имена паттернов и механизмов) и содержимое code-блоков.
- Всё остальное — русский по разделу 2 (request → запрос, latency → задержка, …).
- Запрещены формы из раздела 3 (транслит-глаголы «стримит/фетчит/роутят», латиница в теле
  предложения, апостроф-формы `node'ы`).

**Формат отчёта (на каждый файл, ≤250 слов, БЕЗ полного текста файла):**
```
- Файл: modules/<name>/theory/<FILE>.md (<N> строк)
- Сквозной пример использован: да/нет — где
- Ключевые концепты: …
- Чем подпёрто: <исходники с номерами строк> / <что прогнал и что получил> / <спецификации>
- Что проверил и оказалось неверным (если было): …
- Не удалось проверить (если было): …
- Перекрёстные ссылки: …
- Кандидаты Q&A (2–3): Q… / A…
- В GLOBAL_INDEX добавить: <концепт> → modules/<name>/theory/<FILE>.md
```

**Если задача оказалась больше ожидаемого** — не начинай новый файл батча наспех.
Закрой текущий, запиши отчёт и верни список ненаписанных файлов: их подберёт следующий запуск.

## Фаза 3.5 — Досбор после обрыва (главный агент, дёшево)

Прогоняй **перед каждой волной** и **при любом возобновлении работы над модулем**.
Эта фаза делает Фазу 3 идемпотентной: повторный запуск команды досбирает недостающее.

```bash
S=<slug>
for f in $(grep -o 'theory/[A-Z_]*\.md' modules/$S/ROADMAP.md | sort -u); do
  n=$(basename $f)
  if   [ ! -f "modules/$S/$f" ];                          then echo "НЕ НАЧАТ:  $n"
  elif grep -q '<!-- WIP -->' "modules/$S/$f";            then echo "ОБОРВАН:   $n"
  elif [ ! -f "modules/$S/.build/reports/$n" ];           then echo "БЕЗ ОТЧЁТА: $n"
  else echo "готов:     $n"; fi
done
```

Действия по состояниям:

- **НЕ НАЧАТ** → обычный запуск батча по шаблону.
- **ОБОРВАН** → запуск с добавкой в промпт: «Файл `<FILE>.md` начат, в нём есть маркер
  `<!-- WIP -->`. Журнал проверок лежит в `.build/verified/<FILE>.notes.md` — прочитай его
  и **не повторяй уже сделанные проверки**. Допиши недостающие разделы, сними маркер».
- **БЕЗ ОТЧЁТА** → файл дописан, но агент умер до записи отчёта. Не перезапускай написание:
  попроси сабагента прочитать готовый файл и сформировать по нему отчёт (дёшево, `sonnet`).
- **готов** → пропустить.

Пересобирать батчи под досбор не надо — бери состав из `.build/PLAN.md`.

> Именованных сабагентов из **той же сессии** можно вместо этого просто возобновить
> (`SendMessage` по имени `theory-<FILE>`) — они сохраняют полную историю. Но после рестарта
> Claude Code или на следующий день это уже не работает, а проверка по диску работает всегда.
> Дисковое состояние — основной путь, резюм — оптимизация.

## Фаза 4 — Агрегация (главный агент, дёшево, из отчётов на диске)

> **Инвариант параллелизма.** Общие файлы (`INTERVIEW_QUESTIONS.md`, `_SUMMARY.md`,
> `GLOBAL_INDEX.md`, `CLAUDE.md`) пишет **только главный агент здесь**. Сабагенты их не
> трогают — иначе гонка записи. Каждый сабагент пишет лишь свои файлы теории, свой журнал
> проверок и свой отчёт.

Читай `modules/<name>/.build/reports/*.md` **с диска** (не по памяти из ответов сабагентов и
НЕ перечитывая полные файлы теории). Отчёты на диске переживают компактификацию главного
контекста и обрыв сессии — память нет.

- **`INTERVIEW_QUESTIONS.md`** — ≥15 вопросов из кандидатов Q&A. Формат `qa-bold`
  (`### Q1:` / `**A:**`) либо формат модуля согласно `web/content.config.ts`. Номера Q
  уникальны. Вопросы — про механизм и про «почему», а не про сигнатуры; ответ должен
  содержать причину, а не только факт.
- **`_SUMMARY.md`** — структура: Core Model / Key Concepts / Important Invariants /
  Common Pitfalls / Related Modules. Ориентир ≤2 КБ; для русского текста фактически
  выходит 3–4 КБ, и это приемлемо (сверься с соседними модулями).
- **`knowledge/GLOBAL_INDEX.md`** — дописать секцию `## <Модуль>` со строками
  `<концепт> → modules/<name>/theory/<FILE>.md`. Если концепт легитимно встречается в
  нескольких модулях — добавь строку в «Disambiguated Concepts» с указанием, что именно
  принадлежит кому.
- **Корневой `CLAUDE.md`** — добавить строку только в таблицу модулей ("Структура").
  Концепт→файл идёт лишь в `GLOBAL_INDEX.md` (пункт выше); в CLAUDE.md его НЕ дублировать.
- **Если сабагенты нашли неверные утверждения** в существующей теории других модулей —
  вынеси это пользователю отдельным списком, не правь молча.
- **Если сабагенты сообщили о непроверенных утверждениях** — собери их одним списком
  и покажи пользователю до синка.
- **Если в отчётах есть строки «Перебор объёма»** — покажи их пользователю с предложением
  разделить тему на два файла в следующей итерации. Сам ничего не режь и не переписывай:
  сокращение готовой теории главным агентом — это ровно та работа, ради выноса которой
  из главного контекста придуманы сабагенты.

## Фаза 4.5 — Приёмка (главный агент, дёшево, автоматически)

Прогони до синка. Всё, что не прошло, — либо чини, либо возвращай сабагенту.

```bash
S=<slug>

# 0. Недописанные файлы (маркер обрыва) — должно быть пусто
grep -l '<!-- WIP -->' modules/$S/theory/*.md 2>/dev/null && echo "^^^ незакрытые файлы"

# 1. Шапка из трёх вопросов в каждом файле
for f in modules/$S/theory/*.md; do
  head -12 "$f" | grep -q "Какую проблему решает" || echo "нет шапки: $f"
done

# 2. Обязательные блоки
for f in modules/$S/theory/*.md; do
  grep -q "Вопросы для самопроверки" "$f" || echo "нет самопроверки: $f"
  grep -q "^## Источники"            "$f" || echo "нет источников:  $f"
done

# 3. Битые локальные ссылки (должно быть 0)
SLUG=$S python3 - <<'PY'
import os, re, glob
slug, fence, bad = os.environ['SLUG'], chr(96) * 3, 0
for f in glob.glob(f'modules/{slug}/theory/*.md') + glob.glob(f'modules/{slug}/*.md'):
    txt = re.sub(fence + '.*?' + fence, '', open(f, encoding='utf-8').read(), flags=re.S)
    for m in re.finditer(r'\[[^\]]*\]\(([^)\s]+)\)', txt):
        t = m.group(1).split('#')[0]
        if not t or t.startswith(('http', 'mailto')): continue
        if not os.path.exists(os.path.normpath(os.path.join(os.path.dirname(f), t))):
            print('БИТАЯ', f, t); bad += 1
print('битых ссылок:', bad)
PY

# 4. Каждый файл теории упомянут в ROADMAP (иначе уедет в конец списка на сайте)
for f in modules/$S/theory/*.md; do
  grep -q "theory/$(basename $f)" modules/$S/ROADMAP.md || echo "нет в ROADMAP: $f"
done

# 5. У каждого файла теории есть отчёт (иначе агрегация была неполной)
for f in modules/$S/theory/*.md; do
  [ -f "modules/$S/.build/reports/$(basename $f)" ] || echo "нет отчёта: $f"
done

# 6. Файлы за верхней границей объёма — не ошибка, но повод подумать о разделении темы
for f in modules/$S/theory/*.md; do
  n=$(wc -l < "$f")
  [ "$n" -gt 1000 ] && echo "объём $n строк, рассмотри разделение: $f"
done

# 7. Сборка (если модуль с pom.xml)
[ -f modules/$S/pom.xml ] && (cd modules/$S && mvn -q test-compile)
```

Плюс ручная проверка, которую не автоматизировать — **прочитай подряд первые два-три файла
теории** и убедись, что ответы на «зачем это» и «как оно работает» находятся в тексте, а не
подразумеваются. Если файл читается как справочник — верни сабагенту.

Отдельно проверь **стыки внутри батча**: файлы, написанные одним сабагентом, не должны
дублировать объяснение друг друга — второй файл обязан ссылаться на первый, а не пересказывать.

Затем терминология:

```bash
/check-translation <slug>
```

`.build/` при синке не участвует и в git не попадает. Удалять его не обязательно: журнал
проверок остаётся полезным следом, если позже придётся править утверждения в теории.

## Правило теории

Перед добавлением темы — сверься с `knowledge/GLOBAL_INDEX.md` (single source of truth,
включая секцию «Disambiguated Concepts»). Если концепт уже принадлежит другому модулю —
**ссылка, а не дублирование** (решение OWN/LINK в Фазе 1). При перекрытии с существующим
файлом >30% — расширяй существующий, а не создавай новый.

## Пример

```
/new-module algorithms
```
→ Фаза 0 уточняет тип (`kotlin`), список тем, сквозной пример и стек для проверки →
Фаза 1 группирует 9 файлов в 4 батча по 2–3 смежных, назначает модель на батч и показывает
план + OWN/LINK → Фаза 2 ставит скаффолдинг и пишет `.build/PLAN.md` →
Фаза 3 гоняет 2 волны по 2 сабагента, каждый пишет свои файлы инкрементально и ведёт журнал
проверок → Фаза 3.5 перед второй волной сверяет состояние по диску →
Фаза 4 собирает INTERVIEW_QUESTIONS/_SUMMARY/GLOBAL_INDEX/CLAUDE.md из `.build/reports/` →
Фаза 4.5 прогоняет приёмку → Фаза 5 делает sync.

Обрыв по 5-часовому окну на любой фазе: дождаться сброса, запустить `/new-module <slug>`
заново — Фаза 3.5 подберёт незакрытое, готовое не тронет.
