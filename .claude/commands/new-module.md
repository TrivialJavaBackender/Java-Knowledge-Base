# Создать новый модуль

Создай новый interview prep модуль в `modules/$ARGUMENTS`.

## Модель работы — оркестрация, НЕ написание теории руками

**Главный агент только оркестрирует.** Он делает дешёвую работу (скаффолдинг, план
батчей, диспетчинг, агрегация коротких отчётов). **Теорию пишут сабагенты.** Так главный
контекст остаётся лёгким, а перевод — единым.

> **Почему так.** Раньше главный агент писал все 8–15 файлов теории сам (по 150–300 строк
> каждый) → контекст раздувался, терминология дрейфовала между файлами, сессия дорожала.
> Делегирование решает все три проблемы сразу.

**НИКОГДА не пиши теорию в главном контексте.** Если тянет написать `theory/*.md`
самому — остановись и запусти сабагента (Фаза 3). Образец паттерна батчинга/волн —
`.claude/commands/check-translation.md`.

### Устойчивость к обрыву — это часть протокола, а не пожелание

Прогон выжигает 5-часовое окно, и обрыв в середине волны — штатная ситуация, а не авария.
Три правила ниже делают потерю дешёвой; они обязательны на всех фазах.

1. **Ничего ценного не живёт только в контексте.** Проверенный факт, написанный раздел и
   отчёт попадают на диск в момент получения, а не в конце работы агента.
2. **Каждая фаза идемпотентна.** Повторный запуск команды на том же модуле досбирает
   недостающее, а не переписывает готовое (Фаза 3.5).
3. **Состояние читается с диска, а не из памяти.** Главный агент определяет, что сделано,
   по файлам, а не по тому, что помнит из отчётов.

## Что считается хорошей теорией

**Канонический документ — [`knowledge/THEORY_CONTRACT.md`](../../knowledge/THEORY_CONTRACT.md).**
Он обязателен к прочтению и главным агентом (Фаза 1), и каждым сабагентом (Фаза 3).

Коротко, чтобы не расходиться в понимании задачи:

- Теория — **объяснение, а не справочник**. Каталог методов не нужен: javadoc полнее.
- Каждый файл открывается тремя ответами: **какую проблему решает / кому это надо / когда НЕ надо**.
- Каждый смысловой раздел даёт **тезис → доказательство → следствие**, и ничего больше.
  «Наивное решение» пишется только там, где наивный вариант действительно распространён и
  действительно ломается; ритуальная сценка ради полноты схемы — это вода.
- **Объём меряется знаками: `wc -m`.** Потолок файла — 14 000 знаков, ожидаемый размер
  11 000–13 000: столько читается за 10–15 минут с телефона. Раздел — 800–1500 знаков прозы.
  Блоки с кодом и выводом команд входят в общий счёт. Строки метрикой не являются: перенос
  строки в markdown на отображение не влияет, и «уложился в 300 строк» достигается снятием
  переносов без единого убранного слова.
- **У каждого раздела есть источник и, отдельно, проверка.** Это две разные вещи, и их нельзя
  подменять одну другой:
    - **источник** — откуда взято знание: страница официальной документации с полным URL, глава
      книги, спецификация. Обязателен. Раздел без источника не пишется.
    - **проверка** — чем утверждение подтверждено на стенде: прогон с настоящим выводом, чтение
      исходника. Необязательна, но именно она ловит правдоподобные ошибки.

  Раньше здесь было одно поле «опора», и агенты писали в него «прогон». Результат: 47 файлов
  теории в репозитории имеют раздел «Источники» без единой ссылки, а утверждения опираются на
  память модели. Формулировки «известно, что» запрещены. Для нетехнических модулей источник —
  цитата документа (Scrum Guide, спецификация) или публичный список вопросов; правдоподобная
  цифра без источника хуже, чем её отсутствие.
- **Читатель открывает теорию в веб-приложении с телефона.** У него нет доступа к файлам, к
  контейнерам и к IDE. Поэтому `## Источники` — это только кликабельные URL; путь к файлу
  конфигурации, имя класса и «прогон на контейнере» источниками не являются.
- **Прогон, разошедшийся с документацией, — самое ценное, что производит модуль.** Такие места
  помечаются явно и попадают в отчёт: именно они отличают текст, написанный по документации, от
  текста, написанного человеком, который систему трогал.
- **Каждый раздел отвечает на вопрос, который реально задают на собеседовании.** Раздел, для
  которого такого вопроса нет, не пишется. Это проверяется в Фазе 3a, до написания прозы.
- У модуля есть **сквозной пример**, проходящий через все файлы.

Типичный провал, ради предотвращения которого всё это написано: получается набор верных фактов,
по которому человек, не работавший с темой, не разберётся, — плюс несколько правдоподобных
утверждений, оказавшихся при проверке неверными.

## Фаза 0 — Уточнение (главный агент, дёшево)

Спроси у пользователя:
- Имя модуля (папка в `modules/`) — обычно это `$ARGUMENTS`.
- Тема (краткое описание).
- Тип сборки: `kotlin` | `java-plain` | `java-spring` | `no-build`.
- **Список файлов теории с однострочной областью каждого** (например:
  `BASICS.md — иерархия кэшей, locality, метрики`).
- **Сквозной пример модуля** — одна задача, на которой будут сравниваться подходы во всех файлах
  (например: «сервис на 1000 rps, запрос = три вызова по 100 мс»). Если пользователь не назвал —
  предложи свой вариант и подтверди.
- **На чём проверять утверждения**: версии стека (JDK, библиотеки), доступны ли исходники
  (`$JAVA_HOME/lib/src.zip`), можно ли запускать код. Это определяет, чем сабагенты будут
  подпирать факты.
- **Источники темы**: какая официальная документация считается авторитетной (и для какой версии),
  какие книги и статьи стоит указывать. Если пользователь не назвал — предложи свой список и
  подтверди. Из этого вырастает реестр источников в Фазе 2.5; без него аутлайны писать нельзя.

## Фаза 1 — NO-OVERLAP + план батчей (главный агент, дёшево)

1. Прочитай [`knowledge/THEORY_CONTRACT.md`](../../knowledge/THEORY_CONTRACT.md),
   `knowledge/GLOBAL_INDEX.md` и таблицу модулей в корневом `CLAUDE.md`.
2. Для каждой темы реши **OWN vs LINK**:
    - **OWN** — концепт ещё не имеет владельца → этот модуль становится владельцем.
    - **LINK** — концепт уже принадлежит другому модулю → даём ссылку, **не дублируем**.
      Зафиксируй точный путь цели (`modules/<slug>/theory/FILE.md`).
3. **Спроектируй порядок файлов от мотивации к механизму.** Первым идёт файл, отвечающий
   «зачем это всё и чем мы платим», а не «основы API». Если в модуле есть тема
   «как оно устроено внутри» — она должна быть отдельным файлом, а не абзацем в конце.

### 4. Сгруппируй файлы в батчи

**Батч по умолчанию — 2–3 смежных файла, а не один.**

> **Почему.** Каждый сабагент обязан прочитать `THEORY_CONTRACT.md`, `GLOSSARY_CORE.md`,
> `CANONICAL_TERMS.md` и `THEORY_SAMPLE.md`. Это фиксированная цена входа (~89 КБ), и при
> «1 файл = 1 батч» она платится 8–15 раз за модуль. Батч из трёх файлов платит её один раз
> на три файла. Плюс терминология и перекрёстные ссылки внутри батча получаются
> согласованными без отдельной вычитки.

Правила размера:

- **2–3 файла** — норма. Группируй по смысловой близости: файлы, которые ссылаются друг на
  друга и раскрывают одну механику с разных сторон (`CACHE_PATTERNS.md` + `EVICTION_POLICIES.md`).
- **1 файл** — если тема изолирована (ни с чем не пересекается) или у неё тяжёлая проверочная
  часть (много прогонов).
- **Потолок батча — 3 файла или ~40 000 знаков** суммарного бюджета из аутлайнов (Фаза 3a),
  что наступит раньше. При потолке файла в 14 000 знаков это обычно три файла; батч из двух —
  когда в них много проверочных прогонов.
  Состав батчей окончательно фиксируется после Фазы 3a, когда бюджеты известны.
- Ограничение не про деньги, а про контекст сабагента: при инкрементальной записи текст
  проходит через контекст дважды (сам `Edit` и его результат), сверху ложится вывод
  проверочных прогонов. За этой границей включается авто-компактификация, после которой
  падает точность ссылок на уже написанные разделы.
- Файлы внутри батча сабагент пишет **последовательно**, полностью закрывая один перед
  переходом к следующему (см. шаблон промпта). Обрыв стоит хвоста одного файла, а не батча.

### 5. Выбери модель на батч

Не прибивай `opus` ко всем батчам — это самый быстрый способ упереться в 5-часовое окно.

- `opus` — батчи, где сложное **объяснение механизма** (внутреннее устройство, модели памяти,
  протоколы согласования).
- `sonnet` — батчи, где доминирует **проверочная часть** и структурированное изложение
  (сравнение подходов, паттерны, конфигурация).

Укажи выбранную модель для каждого батча в плане.

### 6. Покажи план пользователю

**До запуска сабагентов** покажи: батчи (файлы + модель + ожидаемый объём), решения OWN/LINK,
сквозной пример. Это обязательный шаг.

## Фаза 2 — Скаффолдинг (главный агент, дёшево, без тяжёлой прозы)

Создай структуру директорий.

`kotlin` / `java-plain`:
```
modules/<name>/
├── theory/
├── .build/            ← служебное, в .gitignore
│   ├── outlines/
│   ├── reports/
│   └── verified/
├── pom.xml
└── src/
    ├── main/
    │   └── kotlin/exercises/   (или java/by/pavel/)
    └── test/
```
`java-spring`:
```
modules/<name>/
├── theory/
├── .build/{outlines,reports,verified}/
├── pom.xml
├── Dockerfile
└── src/main/
    ├── java/by/pavel/
    └── resources/application.properties
```
`no-build`:
```
modules/<name>/
├── theory/
├── .build/{outlines,reports,verified}/
└── exercises/
```

Затем:
- **`.gitignore`** — добавь `modules/*/.build/`, если ещё нет. Директория служебная:
  журнал проверок и отчёты сабагентов, нужна только между фазами и для досбора после обрыва.
- **`pom.xml`** — скопируй из соседнего модуля того же типа, адаптируй `<artifactId>`.
  ⚠️ Проверь версии зависимостей на совместимость: в двух существующих модулях
  `kotlin-test-junit5` оказался пиньнут на версию новее компилятора. Собери пустой модуль
  (`mvn -q test-compile`) до того, как передавать его дальше.
- **`README.md`** — описание, структура, команды сборки/запуска/тестов и (если есть
  упражнения) модуль-специфичный фокус code review. Прогресс НЕ трекаем — это web app.
- **`ROADMAP.md`** — **перечисли файлы теории в нужном порядке прохождения**.
  ⚠️ web-sync берёт порядок теории на сайте из первого упоминания `theory/<NAME>.md`
  в `ROADMAP.md`; сабагенты тоже опираются на этот список. Файлы не из roadmap уйдут
  в конец по алфавиту.
- **`.build/PLAN.md`** — запиши сюда план батчей из Фазы 1: для каждого батча файлы, модель,
  решения OWN/LINK, сквозной пример, стек для проверки. Это единственный источник правды
  при досборе после обрыва; без него Фаза 3.5 не восстановит контекст запуска.

**Теорию, аутлайны, `INTERVIEW_QUESTIONS.md`, `_SUMMARY.md` здесь НЕ пиши.**
Аутлайны — Фаза 3a, теория — Фаза 3, остальное — Фаза 4.

## Фаза 2.5 — Реестр источников (один сабагент, `sonnet`, дёшево)

**Зачем.** Если источник не зафиксирован до написания, он не появится никогда: агент напишет
раздел по памяти, а в «Источники» впишет «прогон на стенде». Так и получилось в шести модулях
репозитория. Реестр переворачивает порядок — сначала находим, на что опираемся, потом пишем.

Запусти одного сабагента (`sonnet`), который собирает `modules/<name>/.build/SOURCES.md`:

```markdown
# Источники модуля <name>

## Официальная документация (<продукт> <версия>)
| Тема | Страница | URL | Код |
|------|----------|-----|-----|
| путь записи | Architecture / Storage Engine | https://…/architecture/storage-engine.html | 200 |
| уплотнение | Operating / Compaction | https://…/operating/compaction/index.html | 200 |

## Книги и статьи
- A. Lakshman, P. Malik. «Cassandra — A Decentralized Structured Storage System», ACM SIGOPS, 2010
  — первоисточник модели; главы: вся статья, 6 страниц.
- M. Kleppmann. «Designing Data-Intensive Applications» — гл. 5 (репликация), гл. 6 (партиционирование).

## Чего в источниках нет
- <утверждение, которое придётся подпирать прогоном, потому что документация о нём молчит>
```

**Промпт сабагенту:**

---
Собери реестр источников для модуля `<name>` — тема `<тема>`. Файлы теории и их области:
`<список из Фазы 0>`. Авторитетные источники по словам пользователя: `<из Фазы 0>`.

На каждую тему найди страницу официальной документации нужной версии и **проверь, что она
существует**: `curl -sI <url> | head -1` должен дать 200. Выдуманный или протухший адрес хуже
отсутствующего, поэтому в реестр идут только проверенные URL с кодом ответа.

Не скачивай страницы целиком — тебе нужен адрес и название раздела, а не содержимое. Оглавление
документации (`.../doc/stable/`) и поиск по сайту дешевле, чем чтение каждой страницы.

Отдельным разделом «Чего в источниках нет» перечисли темы из списка, под которые страницы не
нашлось: их придётся подпирать прогоном, и это надо знать заранее.

Верни: сколько тем закрыто ссылками, сколько осталось без источника.
---

**Отсечка.** Тема без источника и без возможности прогона — кандидат на вылет из модуля. Реши
это здесь, а не после написания прозы.

## Фаза 3a — Аутлайны (один сабагент на весь модуль, `sonnet`, дёшево)

**Зачем эта фаза.** Дорогая часть работы — не написание лишнего, а **переписывание уже
написанной прозы**. Выбросить раздел из аутлайна на шесть строк стоит ничего; выбросить
написанный раздел на 120 строк стоит всей работы, которая в него ушла. Поэтому агент сначала
проектирует файл, и только потом пишет. Ограничение объёма при этом перестаёт быть внешним
числом (которое агент читает как цель) и становится бюджетом, выведенным из содержания.

Запусти **одного** сабагента на весь модуль:

```
Agent(subagent_type: "general-purpose", model: "sonnet",
      name: "outline-<slug>", maxTurns: 40, prompt: <ниже>)
```

Он пишет по одному файлу на каждый файл теории —
`modules/<name>/.build/outlines/<FILE>.outline.md`:

```markdown
# <FILE>.md — аутлайн
Отвечает на вопросы с собеседования: «…», «…», «…»

## §1 <заголовок раздела>
- вопрос:    «как это звучит на собеседовании»
- тезис:     одно предложение — что читатель должен унести
- источник:  <URL из .build/SOURCES.md> — название раздела документации / глава книги
- проверка:  <какой командой подтвердить на стенде> — или «нет, только документация»
- НЕ пишем:  что напрашивается по теме, но уводит в справочник
- бюджет:    ~1200 знаков прозы

## §2 …

Итого: ~12 000 знаков
```

**Промпт аутлайн-сабагенту** (короткий — он не пишет прозу):

---
Ты проектируешь файлы теории, **не пишешь их**. Прочитай `knowledge/THEORY_CONTRACT.md` и
`knowledge/THEORY_SAMPLE.md`. Модуль: `<name>` — `<тема>`. Сквозной пример: `<пример>`.
Решения OWN/LINK: `<список>`. Файлы теории и их области: `<список из Фазы 0>`.

На каждый файл напиши `modules/<name>/.build/outlines/<FILE>.outline.md` в формате выше.
**Пиши по одному файлу и сразу на диск** — обрыв должен стоить одного аутлайна, не всех.

Жёсткие правила:
- **Поле «вопрос» обязательно и должно быть настоящим.** Если раздел не отвечает ни на один
  вопрос, который задают на собеседовании, — не включай его в аутлайн вовсе. Натяжка вида
  «ну про это могут спросить» — это и есть будущая вода, режь на этом шаге.
- Поле «НЕ пишем» — не формальность: назови то, что по теме напрашивается, но уводит
  в справочник (каталог API, разбор формата, консольные прогоны ради прогонов).
- **Поле «источник» обязательно и берётся из `modules/<name>/.build/SOURCES.md`.** Раздел, под
  который в реестре нет ни страницы документации, ни главы книги, ни возможности прогона, —
  не включай вовсе. Это второе после «вопроса» правило отсечки: оно отделяет знание от памяти
  модели.
- **Поле «проверка» заполняй честно.** Написал «нет, только документация» — нормально; это
  предупреждение сабагенту теории, что придётся цитировать, а не прогонять. Хуже, когда проверка
  выдумана и в Фазе 3 выясняется, что команда так не работает.
- Бюджет выводи из содержания: сколько знаков **прозы** нужно, чтобы раскрыть тезис, и не больше.
  Блоки с выводом команд считай отдельно — доказательство не режут, но и оно занимает место
  в общем потолке файла.
- Концепт из списка LINK разделом не делается — только ссылкой внутри чужого раздела.
- Прозу не пиши ни в каком виде. Твой вывод — только аутлайны.

Верни одной строкой на файл: `<FILE>: N разделов, бюджет ~M знаков`.
---

**Отсечка — обязательный шаг.** Прочитай аутлайны всего модуля целиком (это ~1.5–2 КБ на файл,
дёшево) и вычисти:

- раздел, у которого в поле «вопрос» натяжка, — удалить;
- **раздел с пустым или выдуманным полем «источник»** — удалить либо вернуть на доработку с
  конкретным URL из реестра;
- два раздела с одним тезисом — слить;
- раздел с бюджетом больше ~2000 знаков прозы — либо разделить, либо урезать тезис;
- концепт из LINK, пролезший отдельным разделом, — удалить.

**Бюджет — потолок для прозы, а не цель и не размер файла.** Замер на модуле `cassandra`:
при бюджетах 93–141 файлы вышли 233–426 строк, и перебор дали блоки прогонов и раздел
«Источники», тогда как проза укладывалась в бюджет или превышала его на 3–6 строк. Считать
надо прозу; урезать написанное по общему `wc -l` — ошибка, которую пользователь останавливал
трижды.

Затем **покажи пользователю итог** (файлы, число разделов, суммарный бюджет) и только после
этого запускай Фазу 3. Резать здесь стоит копейки — после написания прозы уже нет.

## Фаза 3 — Диспетч сабагентов теории (параллельно ≤2, волнами)

**Перед каждой волной прогони `/usage`.** Если остатка окна на волну явно не хватает —
не запускай: скажи пользователю, сколько осталось и когда сброс. Дождаться сброса дешевле,
чем потерять волну на середине.

Запусти по одному сабагенту на батч:

```
Agent(
  subagent_type: "general-purpose",
  model: <модель батча из Фазы 1>,
  name: "theory-<первый файл батча без .md>",
  maxTurns: 80,
  prompt: <см. шаблон>
)
```

- **Максимум 2 параллельно** (оба Agent-вызова в одном сообщении). Больше батчей — волнами
  по 2, дожидаясь предыдущей волны.
- `name` обязателен: именованного сабагента можно адресовать и возобновить после обрыва,
  не выковыривая agent ID из транскрипта.
- `maxTurns: 80` — предохранитель от агента, ушедшего в бесконечные перепроверки.
  Подними до 100–120, если батч из трёх файлов с тяжёлой проверочной частью упирается в лимит.

русском языке**.

**Сначала прочитай (обязательно, в этом порядке, ровно один раз на весь батч —

5. **Свои аутлайны** из `modules/<name>/.build/outlines/<FILE>.outline.md` — они утверждены

`GLOBAL_INDEX.md` читать не надо: решения OWN/LINK приняты в Фазе 1 и переданы тебе списком
ниже. Если понадобился концепт вне списка — точечный `grep` по индексу, а не чтение целиком.

**Контекст модуля:** `<name>` — `<тема модуля>`.
**Сквозной пример модуля:** `<пример из Фазы 0>` — используй его во всех своих файлах, чтобы
разные подходы сравнивались на одной задаче.
**Стек для проверки:** `<версии из Фазы 0>`.

**Твой батч — написать файлы (строго в этом порядке, по одному, полностью закрывая
предыдущий):**
- `modules/<name>/theory/<FILE>.md` — `<область из Фазы 0>`
- (…остальные файлы батча)

**Решения OWN/LINK для этого батча:**
- `<концепт>` — OWN (раскрываем здесь полностью).
- `<концепт>` — LINK на `modules/<slug>/theory/<FILE>.md` (только ссылка, без дублирования).

**Соседние файлы теории модуля** (для корректных относительных перекрёстных ссылок):
`<перечисли остальные theory/*.md модуля>`.
**Упражнения модуля** (для блока «Упражнения»): `<перечисли Ex*.kt / applied-пакеты, если есть>`.

#### Протокол записи — инкрементальный, это обязательно

Твоя работа может быть оборвана лимитом в любой момент. Всё, что существует только в твоём
контексте, при обрыве теряется; всё, что записано на диск, — переживает. Поэтому:

**Журнал проверок.** Перед началом работы прочитай
`modules/<name>/.build/verified/<FILE>.notes.md`, если он есть: проверки оттуда **повторять
не надо**, они уже сделаны прошлым запуском. Каждый факт, который ты проверил, дописывай
туда **сразу после проверки, до того как использовал его в тексте**:
```
- <утверждение>
  чем подпёрто: <путь:строка> | <команда → реальный вывод> | <цитата спецификации>
```
Это самая дорогая часть работы — прогоны и лазанье в исходники. Она не должна прогоняться дважды.

**Тело файла.** По каждому файлу:
1. Собери `Write`-ом скелет **из утверждённого аутлайна**: шапка из трёх вопросов + заголовки
   всех разделов, и под каждым заголовком — строки `вопрос / тезис / опора / бюджет` из
   аутлайна, закомментированные (`<!-- … -->`). Последней строкой маркер `<!-- WIP -->`.
2. Дальше наполняй по одному разделу через `Edit`, заменяя закомментированное задание на
   готовый текст. **Ты пишешь против тезиса, а не против пустого заголовка** — это и есть
   защита от воды: тезис уже сформулирован и утверждён, задача раздела — его раскрыть.
3. Когда файл дописан целиком — убери `<!-- WIP -->` и проверь, что комментариев-заданий
   не осталось.

Файл с `<!-- WIP -->` считается недописанным: его доделает следующий запуск, опираясь на
твой журнал проверок. Файл без маркера считается готовым.

**Отчёт.** По каждому закрытому файлу дописывай отчёт в
`modules/<name>/.build/reports/<FILE>.md` — **и только потом переходи к следующему файлу**.
Тот же текст верни в финальном ответе.

**Текстовые чекпоинты.** После каждого закрытого файла выведи одну строку обычным текстом:
`готов <FILE>.md, <N> знаков (wc -m)`. Это не косметика: агент, чей вывод состоял только из вызовов
инструментов, при обрыве по лимиту падает с голой ошибкой и не отдаёт наверх ничего.

**Требования к содержанию — по `THEORY_CONTRACT.md`. Ключевое:**
- Шапка файла отвечает на три вопроса: какую проблему решает / кому это надо / когда НЕ надо.
- Каждый раздел: задача → наивное решение и где ломается → механизм → правило.
- **Никаких каталогов API** вне финальной шпаргалки. Выбор метода выводится из критерия
  (что у вас на входе → что брать), а не даётся списком.
- Разделы «чего этот инструмент не делает» и «когда это неправильный ответ» пиши, **только
  если каждому есть что сказать по существу**. Они не обязательны: в `engineering-process` они
  выродились в 15–53 строки наполнителя, ни один не привязан ни к одному вопросу.
- **Раздела «Вопросы для самопроверки» не пиши.** Вопросы живут в `INTERVIEW_QUESTIONS.md`
  модуля и встраиваются в текст плашкой «Проверь себя» по ссылке `> theory/FILE.md §N`.
  Дублировать их в конце файла не надо.
- В конце: «Шпаргалка» (≤25 строк, не пересказ разделов), «Упражнения» (если есть), «Источники».
- **Раздел «Источники» — только кликабельные ссылки.** Читатель открывает теорию в веб-приложении
  с телефона: доступа к файловой системе, к контейнерам и к IDE у него нет, кнопка «open in IDE»
  не работает. Поэтому позиция вида «Прогоны: одноузловой кластер, инструменты `cqlsh`,
  `nodetool`», путь `/etc/…/config.yaml — строки 68, 75`, имя класса или `javap` — **мёртвый
  источник**: пойти по нему некуда. Формат:
  ```
  - <Продукт> <версия> Documentation, [Название раздела](https://полный.url/страница.html)
    — что именно отсюда взято.
  ```
  Адреса бери из `modules/<name>/.build/SOURCES.md` и **проверяй перед тем, как вписать**:
  `curl -sI <url> | head -1` должен дать 200. Выдуманная ссылка хуже отсутствующей.
  Прогоны допустимы **одной завершающей строкой** («Проверено на …»), и она не заменяет ссылок.
  Ссылку на документацию полезно дать и в теле раздела, где вводится параметр или порог.
- **Каждый раздел обязан отвечать на вопрос, который реально задают на собеседовании.**
  Этот вопрос уже назван в аутлайне. Раздел, для которого такого вопроса нет, не пишется —
  ни в каком объёме. Это главный анти-водный критерий, он важнее всех остальных.
- **Объём файла = сумма бюджетов разделов из утверждённого аутлайна.** Внешнего числа нет и
  не должно быть: бюджет выведен из содержания, а не назначен сверху. Расхождение факта
  с бюджетом больше чем на 20 % означает, что раздел поехал в сторону, — вернись к тезису
  из аутлайна, а не подгоняй число.
- Если по ходу написания выяснилось, что аутлайн неверен (тезис не держится, раздел надо
  разделить или выбросить), **не переписывай прозу молча**: закончи текущий раздел, впиши
  в отчёт строку `- Аутлайн разошёлся: <FILE> §N — <что не так>` и продолжай. Решение
  принимает главный агент — переделка аутлайна стоит копейки, переписывание прозы нет.
- Файлы одного батча смежны по теме: связывай их перекрёстными ссылками и не дублируй
  объяснение, данное в предыдущем файле батча, — ссылайся на него.

**Требования к достоверности — это не формальность:**
- **Проверяй перед тем, как написать.** Есть Bash — пользуйся: скомпилируй пример
  (`java Файл.java`), загляни в исходник (`unzip -p $JAVA_HOME/lib/src.zip …`, `grep -n`),
  проверь наличие класса или флага. Утверждения «по памяти» регулярно оказываются неверными.
- **Пиши от источника, а не от памяти.** У каждого раздела в аутлайне назван источник — открой
  его и напиши раздел по нему. Память модели годится для плана, но не для утверждений: она
  помнит версию, которой у пользователя нет.
- Каждое утверждение о поведении подпирается **страницей документации со ссылкой**, **реальным
  выводом прогона**, **файлом и номером строки** либо **точной цитатой из спецификации**.
  Формулировки «известно, что», «обычно считается» запрещены.
- **Прогон, разошедшийся с документацией или с ходовой формулировкой, — самое ценное, что ты
  можешь найти.** Не заглаживай расхождение и не подгоняй текст под источник: опиши, что
  документация говорит одно, а версия на стенде ведёт себя иначе, и вынеси это отдельной строкой
  в отчёт. Примеры такого улова из модуля `cassandra`: запрета `EACH_QUORUM` на чтении в 5.0.9
  не существует, хотя формулировка ходит по собеседованиям; несработавшая условная запись стоит
  столько же, сколько сработавшая; снитч перекрывает `cassandra-rackdc.properties`.
- Выводы программ в блоках — **настоящие**, скопированные из прогона. Придуманный вывод —
  худшая из возможных ошибок: он выглядит как доказательство.
- Замеры оформляй с машиной, версиями, оговоркой про точность и командой для повторения.
  Разброс показывай честно.
- Если проверить утверждение не удалось — **не пиши его**, либо пометь явно как непроверенное
  и вынеси в отчёт.
- **Для нетехнических модулей** (процессы, поведенческое интервью, коммуникация) требование
  «файл:строка» неприменимо: подпирать там нечего, и попытка соблюсти букву даёт имитацию
  строгости — придуманные проценты, «исследования показывают», ссылки на несуществующие
  замеры. Опора в таких модулях — это точная цитата из документа-источника (Scrum Guide,
  спецификация), ссылка на публичный список вопросов или честно названная практика.
  **Правдоподобная цифра без источника хуже, чем её отсутствие.**

**Перевод — строго по `GLOSSARY_CORE.md`** (полный `GLOSSARY.md` — только при сомнении
в конкретном термине)**:**
- Латиницей оставляй **только** раздел 1 глоссария (аббревиатуры/протоколы/продукты/алгоритмы/
  имена паттернов и механизмов) и содержимое code-блоков.
- Всё остальное — русский по разделу 2 (request → запрос, latency → задержка, …).
- Запрещены формы из раздела 3 (транслит-глаголы «стримит/фетчит/роутят», латиница в теле
  предложения, апостроф-формы `node'ы`).

**Формат отчёта (на каждый файл, ≤250 слов, БЕЗ полного текста файла):**
```
- Файл: modules/<name>/theory/<FILE>.md (<N> знаков по `wc -m`)
- Сквозной пример использован: да/нет — где
- Ключевые концепты: …
- Чем подпёрто: <исходники с номерами строк> / <что прогнал и что получил> / <спецификации>
- Что проверил и оказалось неверным (если было): …
- Не удалось проверить (если было): …
- Перекрёстные ссылки: …
- Кандидаты Q&A (2–3): Q… / A…
- В GLOBAL_INDEX добавить: <концепт> → modules/<name>/theory/<FILE>.md
```

**Если задача оказалась больше ожидаемого** — не начинай новый файл батча наспех.
Закрой текущий, запиши отчёт и верни список ненаписанных файлов: их подберёт следующий запуск.

## Фаза 3.5 — Досбор после обрыва (главный агент, дёшево)

Прогоняй **перед каждой волной** и **при любом возобновлении работы над модулем**.
Эта фаза делает Фазу 3 идемпотентной: повторный запуск команды досбирает недостающее.

```bash
S=<slug>
for f in $(grep -o 'theory/[A-Z_]*\.md' modules/$S/ROADMAP.md | sort -u); do
  n=$(basename $f)
  o="modules/$S/.build/outlines/${n%.md}.outline.md"
  if   [ ! -f "$o" ];                                     then echo "НЕТ АУТЛАЙНА: $n"
  elif [ ! -f "modules/$S/$f" ];                          then echo "НЕ НАЧАТ:  $n"
  elif grep -q '<!-- WIP -->' "modules/$S/$f";            then echo "ОБОРВАН:   $n"
  elif [ ! -f "modules/$S/.build/reports/$n" ];           then echo "БЕЗ ОТЧЁТА: $n"
  else echo "готов:     $n"; fi
done
```

Действия по состояниям:

- **НЕТ АУТЛАЙНА** → вернуться в Фазу 3a на эти файлы. Прозу без утверждённого аутлайна
  не запускать: именно этот порядок защищает от переписывания.
- **НЕ НАЧАТ** → обычный запуск батча по шаблону.
- **ОБОРВАН** → запуск с добавкой в промпт: «Файл `<FILE>.md` начат, в нём есть маркер
  `<!-- WIP -->`. Журнал проверок лежит в `.build/verified/<FILE>.notes.md` — прочитай его
  и **не повторяй уже сделанные проверки**. Допиши недостающие разделы, сними маркер».
- **БЕЗ ОТЧЁТА** → файл дописан, но агент умер до записи отчёта. Не перезапускай написание:
  попроси сабагента прочитать готовый файл и сформировать по нему отчёт (дёшево, `sonnet`).
- **готов** → пропустить.

Пересобирать батчи под досбор не надо — бери состав из `.build/PLAN.md`.

> **Внутри живой сессии возобновление — основной путь, а не оптимизация.** Агент, оборванный
> лимитом, остаётся адресуемым: `SendMessage` по его имени (`theory-<FILE>`) или agentId
> поднимает его с транскрипта, где уже прочитаны контракт, глоссарий, образцы и половина правок
> текущего файла. Запуск нового агента на ту же работу означает повторную оплату всего входного
> чтения плюс написание длинного промпта заново.
>
> Проверка по диску выше нужна для другого — **узнать, что именно осталось**, и передать это
> в сообщении возобновляемому агенту. Одно не заменяет другое: диск отвечает «что сделано»,
> резюм отвечает «кто продолжит дёшево».
>
> Новый агент вместо возобновления оправдан ровно в трёх случаях: сессия рестартовала или идёт
> следующий день (транскрипт недоступен); состав работы изменился так, что старое задание не
> переиспользуется; замена уже начала править файлы — тогда переключаться обратно дороже, чем
> дать ей закончить.

## Фаза 4 — Агрегация (главный агент, дёшево, из отчётов на диске)

> **Инвариант параллелизма.** Общие файлы (`INTERVIEW_QUESTIONS.md`, `_SUMMARY.md`,
> `GLOBAL_INDEX.md`, `CLAUDE.md`) пишет **только главный агент здесь**. Сабагенты их не
> трогают — иначе гонка записи. Каждый сабагент пишет лишь свои файлы теории, свой журнал
> проверок и свой отчёт.

Читай `modules/<name>/.build/reports/*.md` **с диска** (не по памяти из ответов сабагентов и
НЕ перечитывая полные файлы теории). Отчёты на диске переживают компактификацию главного
контекста и обрыв сессии — память нет.

- **`INTERVIEW_QUESTIONS.md`** — ≥15 вопросов из кандидатов Q&A. Формат `qa-bold`
  (`### Q1:` / `**A:**`) либо формат модуля согласно `web/content.config.ts`. Номера Q
  уникальны. Вопросы — про механизм и про «почему», а не про сигнатуры; ответ должен
  содержать причину, а не только факт.
- **`_SUMMARY.md`** — структура: Core Model / Key Concepts / Important Invariants /
  Common Pitfalls / Related Modules. Ориентир ≤2 КБ; для русского текста фактически
  выходит 3–4 КБ, и это приемлемо (сверься с соседними модулями).
- **`knowledge/GLOBAL_INDEX.md`** — дописать секцию `## <Модуль>` со строками
  `<концепт> → modules/<name>/theory/<FILE>.md`. Если концепт легитимно встречается в
  нескольких модулях — добавь строку в «Disambiguated Concepts» с указанием, что именно
  принадлежит кому.
- **Корневой `CLAUDE.md`** — добавить строку только в таблицу модулей ("Структура").
  Концепт→файл идёт лишь в `GLOBAL_INDEX.md` (пункт выше); в CLAUDE.md его НЕ дублировать.
- **Если сабагенты нашли неверные утверждения** в существующей теории других модулей —
  вынеси это пользователю отдельным списком, не правь молча.
- **Если сабагенты сообщили о непроверенных утверждениях** — собери их одним списком
  и покажи пользователю до синка.
- **Если в отчётах есть строки «Перебор объёма»** — покажи их пользователю с предложением
  разделить тему на два файла в следующей итерации. Сам ничего не режь и не переписывай:
  сокращение готовой теории главным агентом — это ровно та работа, ради выноса которой
  из главного контекста придуманы сабагенты.

## Фаза 4.5 — Приёмка (главный агент, дёшево, автоматически)

Прогони до синка. Всё, что не прошло, — либо чини, либо возвращай сабагенту.

```bash
S=<slug>

# 0. Недописанные файлы (маркер обрыва) — должно быть пусто
grep -l '<!-- WIP -->' modules/$S/theory/*.md 2>/dev/null && echo "^^^ незакрытые файлы"

# 1. Шапка из трёх вопросов в каждом файле
for f in modules/$S/theory/*.md; do
  head -12 "$f" | grep -q "Какую проблему решает" || echo "нет шапки: $f"
done

# 2. Обязательные блоки
for f in modules/$S/theory/*.md; do
  grep -q "^## Источники" "$f" || echo "нет источников: $f"
  grep -q "Вопросы для самопроверки" "$f" && echo "ЛИШНЕЕ (самопроверка вынесена в INTERVIEW_QUESTIONS.md): $f"
done

# 2a. Источники — это ССЫЛКИ, а не прогоны и не пути к файлам.
# Читатель открывает теорию в вебе с телефона: файлов, контейнеров и IDE у него нет.
for f in modules/$S/theory/*.md; do
  n=$(sed -n '/^## Источники/,$p' "$f" | grep -c 'https\?://')
  [ "$n" -eq 0 ] && echo "НИ ОДНОЙ ССЫЛКИ в источниках: $f"
done
# мёртвые опоры, которым не место в «Источниках»
grep -n -A40 '^## Источники' modules/$S/theory/*.md \
  | grep -E 'javap|/etc/|/var/lib/|\.jar|^\s*-\s*Прогоны:' \
  && echo "^^^ убрать: это способ проверки, а не источник"

# 2b. Каждая внешняя ссылка модуля реально открывается (200)
grep -rhoE 'https?://[^)> ]+' modules/$S/theory/*.md | sort -u | while read -r u; do
  code=$(curl -sI -o /dev/null -w '%{http_code}' --max-time 10 "$u")
  [ "$code" = "200" ] || echo "$code $u"
done

# 3. Битые локальные ссылки (должно быть 0)
SLUG=$S python3 - <<'PY'
import os, re, glob
slug, fence, bad = os.environ['SLUG'], chr(96) * 3, 0
for f in glob.glob(f'modules/{slug}/theory/*.md') + glob.glob(f'modules/{slug}/*.md'):
    txt = re.sub(fence + '.*?' + fence, '', open(f, encoding='utf-8').read(), flags=re.S)
    for m in re.finditer(r'\[[^\]]*\]\(([^)\s]+)\)', txt):
        t = m.group(1).split('#')[0]
        if not t or t.startswith(('http', 'mailto')): continue
        if not os.path.exists(os.path.normpath(os.path.join(os.path.dirname(f), t))):
            print('БИТАЯ', f, t); bad += 1
print('битых ссылок:', bad)
PY

# 4. Каждый файл теории упомянут в ROADMAP (иначе уедет в конец списка на сайте)
for f in modules/$S/theory/*.md; do
  grep -q "theory/$(basename $f)" modules/$S/ROADMAP.md || echo "нет в ROADMAP: $f"
done

# 5. У каждого файла теории есть отчёт (иначе агрегация была неполной)
for f in modules/$S/theory/*.md; do
  [ -f "modules/$S/.build/reports/$(basename $f)" ] || echo "нет отчёта: $f"
done

# 6. Объём файла целиком — в ЗНАКАХ. Потолок 14000, цель 11000-13000: это 10-15 минут чтения.
# Строки метрикой не являются: перенос строки в markdown ничего не меняет для читателя,
# и «уложился в 300 строк» достигается снятием переносов без единого убранного слова
# (замер на ci-cd: строк -58%, слов -22%, ширина строки 60 → 112).
for f in modules/$S/theory/*.md; do
  n=$(wc -m < "$f")
  [ "$n" -gt 14000 ] && echo "перебор объёма: $(basename $f) — $n знаков против потолка 14000"
done

# 6b. Бюджет ПРОЗЫ из аутлайна (знаки вне блоков кода, до «Шпаргалки»).
for f in modules/$S/theory/*.md; do
  o="modules/$S/.build/outlines/$(basename $f .md).outline.md"
  [ -f "$o" ] || { echo "нет аутлайна: $f"; continue; }
  bud=$(grep -oE 'Итого: ~[0-9 ]+' "$o" | grep -oE '[0-9]+' | tr -d ' ')
  [ -z "$bud" ] && { echo "в аутлайне нет строки 'Итого: ~N знаков': $o"; continue; }
  prose=$(awk '/^##.*(Шпаргалка|Упражнения|Источники)/{exit} /^```/{c=!c; next} !c{n+=length($0)} END{print n+0}' "$f")
  d=$(( (prose - bud) * 100 / bud ))
  [ "${d#-}" -gt 25 ] && echo "проза ${d}%: $(basename $f) — $prose знаков против бюджета $bud"
done

# 7. Сборка (если модуль с pom.xml)
[ -f modules/$S/pom.xml ] && (cd modules/$S && mvn -q test-compile)
```

Плюс ручная проверка, которую не автоматизировать — **прочитай подряд первые два-три файла
теории** и убедись, что ответы на «зачем это» и «как оно работает» находятся в тексте, а не
подразумеваются. Если файл читается как справочник — верни сабагенту.

Отдельно проверь **стыки внутри батча**: файлы, написанные одним сабагентом, не должны
дублировать объяснение друг друга — второй файл обязан ссылаться на первый, а не пересказывать.

## Правило теории

Перед добавлением темы — сверься с `knowledge/GLOBAL_INDEX.md` (single source of truth,
включая секцию «Disambiguated Concepts»). Если концепт уже принадлежит другому модулю —
**ссылка, а не дублирование** (решение OWN/LINK в Фазе 1). При перекрытии с существующим
файлом >30% — расширяй существующий, а не создавай новый.

## Пример

```
/new-module algorithms
```
→ Фаза 0 уточняет тип (`kotlin`), список тем, сквозной пример и стек для проверки →
Фаза 1 группирует 9 файлов в 4 батча по 2–3 смежных, назначает модель на батч и показывает
план + OWN/LINK → Фаза 2 ставит скаффолдинг и пишет `.build/PLAN.md` →
**Фаза 3a одним дешёвым сабагентом пишет 9 аутлайнов, главный агент их чистит и показывает
пользователю — здесь режется всё лишнее, до единой строки прозы** →
Фаза 3 гоняет 2 волны по 2 сабагента, каждый пишет свои файлы против утверждённого аутлайна,
инкрементально и ведя журнал проверок → Фаза 3.5 перед второй волной сверяет состояние по диску →
Фаза 4 собирает INTERVIEW_QUESTIONS/_SUMMARY/GLOBAL_INDEX/CLAUDE.md из `.build/reports/` →
Фаза 4.5 прогоняет приёмку → Фаза 5 делает sync.

Обрыв по 5-часовому окну на любой фазе: дождаться сброса, запустить `/new-module <slug>`
заново — Фаза 3.5 подберёт незакрытое, готовое не тронет.
